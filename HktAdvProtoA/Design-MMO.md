# MMORPG 적용 설계

> [Design-WorldState.md](Design-WorldState.md)(상태 형식)와 [Design-WorldLaws.md](Design-WorldLaws.md)(법칙 내용), 그리고 실물 `data/world-state.json` + `data/state-engine.mjs`(결정론 틱 엔진)를 실제 MMORPG 에 적용하는 설계다. 프로토타입은 **단일 세계 · 단일 플레이어 · 단일 프로세스** 가정 위에 서 있다 — 이 문서는 그중 무엇이 그대로 가고(§1), 무엇이 재설계인지(§3~§5)를 확정하고, 실행 아키텍처(§2)·게임플레이 접합(§8)·운영(§10)·적용 로드맵(§11)을 정한다.

## 0. 적용 대상과 격차 진단

프로토타입이 이미 증명한 것:

```text
증명 1  세계 상태가 다섯 층(vars/initial/rules/actions/objectives) 데이터로 완결된다.
증명 2  결정론 틱 루프 ①~⑦ 하나로 자율 법칙·NPC 정책·목적 판정이 전부 굴러간다.
증명 3  무입력에서도 세계가 살아 움직인다 — 대표 사건 5종이 자율 재생 (트리 §16 검증 13·14).
증명 4  스냅샷(once 발화 기록 포함)만으로 어느 시점에서든 동일 리플레이가 된다.
```

MMORPG 적용 시 남는 격차 4가지 — 이 문서의 본론이다:

| # | 격차 | 프로토 가정 | MMORPG 현실 | 해소 |
|---|---|---|---|---|
| 1 | 플레이어 다수성 | `E_플레이어` 노드 1개 | 동시 수천 캐릭터 | 스코프 분리 §3 + 기여 패턴 §4 |
| 2 | 시뮬 해상도 | 세계틱 하나 (서사 해상도) | 30Hz 전투·이동 (HktCore) | 2계층 분리 §2 |
| 3 | 실행 형태 | 단일 mjs 프로세스, 휘발 | 지속 서버·DB·네트워크 | 권위·지속성 §6·§7 |
| 4 | 콘텐츠 규모 | 사건 5종·vars 73 | 권역 수십·상시 라이브 | 파이프라인 §10 |

## 1. 보존 불변 — 프로토에서 그대로 가져가는 것

아래 다섯은 MMO 화 과정에서 **변형 금지**다. 이 불변들이 깨지면 이 트랙을 적용하는 의미가 없다.

```text
불변 1  모든 상태 변수는 그래프 노드에 귀속된다 (단축·쌍축·파생축, basis 필수).
불변 2  상태 변화는 법칙·행동의 발화로만 일어난다 — 외부 임의 쓰기 금지.
        (운영 툴·GM 명령·게임플레이 서버도 예외 없음: 전부 '행동'으로 정의해 발화시킨다)
불변 3  목적 완료는 수단이 아니라 상태 술어로 판정한다.
불변 4  틱 의미론 ①~⑦ — 읽기/쓰기 분리, set 충돌 거부, once 발화 기록=상태.
불변 5  런타임 노드 생성 금지 — 등장 가능한 모든 존재는 그래프에 미리 있다 (변형 #18).
```

주목할 동형성: 불변 2·3 은 HktGameplay 절대 원칙과 정확히 겹친다 — 원칙 3(서버 권위: 클라는 읽기 전용 `FHktWorldView`), 원칙 4(VM 은 WorldState 직접 쓰기 금지, proxy 경유). 즉 이 트랙의 세계층은 HktGameplay 가 개체 단위에서 하던 규율을 **세계 단위**로 반복하는 것이고, 두 층의 접합(§2)은 같은 철학의 두 해상도를 잇는 일이다.

## 2. 아키텍처 — 2계층 시뮬레이션

세계층과 게임플레이층은 **해상도가 다른 별개의 시뮬레이션**이며, 정해진 계약으로만 통신한다.

```text
┌─ World Director (거시·세계층) ── 월드당 1 프로세스 ─────────────────────┐
│  world-state 다섯 층 + 틱 루프 ①~⑦ (state-engine 의 이식)              │
│  틱 주기: 1 세계틱 = 실시간 N초 (기본 5s, config)                        │
│  담당: S/X/E군집/R공급/L/F/K/T 세계 변수 · 자율 법칙 · NPC 정책 · 사건 사슬 │
└──────┬─ 하향: 세계 상태 구독 (읽기 전용)      ▲ 상향: 행동 발화 요청·기여 보고 ─┘
┌──────▼──────────────────────────────────┴──────────────────────────┐
│  Zone 서버들 (미시·게임플레이층) — HktCore 30Hz 결정론 VM                │
│  담당: 전투·이동·개체 스폰·채집 노드·NPC 액터 — 세계 변수의 '연출과 실행'    │
└──────┬─ FHktWorldView (기존 경로 그대로)                               │
┌──────▼─────────────────────────────────────────────────────────────┐
│  클라이언트 — 읽기 전용. 세계 변수 뷰 + 개체 뷰                           │
└────────────────────────────────────────────────────────────────────┘
```

- **World Director 는 월드당 1개, 샤딩하지 않는다.** 세계 변수는 수백~수천 개 규모(현재 73, 완역 후에도 수천 이하)이고 틱이 초 단위라 단일 프로세스로 충분하다. 세계층을 쪼개면 결정론(불변 4)이 깨진다. 지역 분할이 필요한 것은 미시층(Zone)이며, 세계층은 L 노드가 어느 Zone 에 속하는지만 안다.
- **하향 계약**: Zone 서버는 세계 변수를 구독해 게임플레이로 **번역**한다(§8 매핑 표). 번역은 읽기 전용 — Zone 이 세계 변수를 직접 쓰는 경로는 없다.
- **상향 계약**: 미시층에서 일어난 일은 두 형태로만 세계층에 도달한다.
  - **행동 발화 요청** — 플레이어 입력이 세계 행동(ACT_*)에 해당하면 Zone 이 요청을 올리고, Director 가 when/cost 를 평가해 승인·거부한다(§6).
  - **기여 보고** — 개체 단위 결과의 집계치(늑대 12마리 사냥됨, 심연유리 340개 채취됨)를 정해진 count 변수 add 로 보고한다. 이 add 자체도 데이터로 선언된 행동이다(불변 2 — "집계 보고 행동"의 반복 발화).
- **엔진 구현은 교체 가능해야 한다.** 세계층의 정체는 코드가 아니라 *데이터(다섯 층) + 틱 의미론*이다. 초기에는 `state-engine.mjs` 를 Node 서비스로 그대로 서비스화하고(검증기·시뮬레이터를 운영 도구로 공유), 장기적으로 HktCore 계열 C++ 포팅으로 교체한다 — 스냅샷과 데이터가 같으면 어느 구현이든 같은 세계다(불변 4가 이 교체 가능성을 보장한다).

## 3. 스코프 재설계 — 격차 1 의 절반

프로토의 `E_플레이어` 는 노드 1개다. MMO 에서는 캐릭터마다 쌍축(보유·습득·감염·계약·관계)이 필요하다. 변수에 **scope** 를 도입해 저장·평가 위치를 분리한다.

### 3.1. 변수 스코프 3종

```jsonc
// world (기본값) — 공유 단일 값. Director 스냅샷에 1개 존재.
{ "id": "R_심연유리.공급", "scope": "world", ... }

// player — 캐릭터별 인스턴스. owner 가 E_플레이어인 쌍축이 전부 여기로 승격.
//          id 의 E_플레이어 자리가 캐릭터 키로 치환되는 템플릿 변수가 된다.
{ "id": "E_플레이어.보유.R_재생섬유", "scope": "player", ... }   // → {char}.보유.R_재생섬유

// faction — F 노드 소속 집단 값 (길드 도입 시 길드도 이 스코프). NPC 정책 변수는 world 유지.
```

- **그래프는 그대로다.** `E_플레이어` 노드 1개가 "플레이어라는 존재 유형"을 대표하고(불변 1·5 유지), 인스턴스화는 상태층의 일이다 — WorldState §9 해상도 원칙("이름 없는 개체를 추적해야 하면 노드가 필요하다는 신호")의 유일한 예외를 명시적 스코프로 제도화하는 것.
- **평가 규칙**: 술어·효과가 player 스코프 변수를 참조하면 그 법칙·행동·목적은 **캐릭터 문맥에서** 평가된다. `{actor}` 치환 메커니즘이 이미 이것이다 — actor 가 캐릭터 키로 확장될 뿐, 엔진 변경이 최소다.
- **저장 분리**: world/faction 스코프는 Director 의 월드 스냅샷(작다 — kv 하나), player 스코프는 캐릭터 DB 레코드. 캐릭터 로그인 시 해당 캐릭터의 player 축만 Director(또는 담당 Zone)에 로드된다.

### 3.2. 목적 스코프 3종

목적도 같은 축으로 갈린다. **판별은 기계적이다: complete 술어가 읽는 변수의 스코프가 목적의 스코프다** (검증 M2).

| 스코프 | 진행 변수 | 의미 | 예 |
|---|---|---|---|
| world | `G*.진행` 월드에 1개 | 세계가 한 번 도달하면 전 서버 완료 — 사건 사슬·세계 전환 | 강의 귀환, 아르카론의 죽음 |
| player | 캐릭터마다 1개 | 개인 서사 — 발견·완료가 캐릭터별 (술어는 world+player 변수 혼합 가능) | 감염 치료, 계약 체결, 개인 습득 |
| faction | NPC 정책용, 프로토 그대로 | 세력의 목적 — Director 의 ⑦단계가 수행 | 수문회 제어탑 파괴 |

world 목적의 완료는 **서버 역사**가 된다(한 번뿐). 개인 기여의 인정은 world 목적이 아니라, 같은 사건에 걸린 player 목적(개인 기여 술어)이 담당한다 — §4.2.

## 4. once 행동의 MMO화 — 격차 1 의 나머지 절반

프로토의 세계 전환은 once 행동 1발이다(`ACT_제어탑_복구` → `L_제어탑.가동=true`). 수천 명의 세계에서 "누가 그 한 발을 쏘는가"는 잘못된 질문이다 — 세계 전환을 **개인의 행동**에서 **집단 기여의 임계**로 옮긴다.

### 4.1. 기여 축적 패턴 (P8 — 법칙 패턴 8번째로 추가)

```text
프로토:  ACT_제어탑_복구 (once, 플레이어 1인)  →  L_제어탑.가동 = true

MMO:     ACT_복구_기여 (player, 반복 가능)      →  {char}.기여.EV_강의귀환 +1  (개인 기록)
                                              →  L_제어탑.복구진척 +1        (world count)
         RULE_제어탑_가동 (once, world)         →  when 복구진척 ≥ 임계
                                              →  L_제어탑.가동 = true
```

- **세계 전환의 주어가 행동에서 법칙으로 이동한다.** "복구했더니 가동됐다"가 아니라 "진척이 임계에 닿으면 가동된다" — 불변 3(상태 술어 판정)의 자연 확장이라 사슬 법칙(R1~R5)은 한 글자도 안 바뀐다. 사슬은 `L_제어탑.가동` 만 보기 때문이다.
- **반대 방향 기여가 공짜로 열린다.** 수문회 편에 선 플레이어의 `ACT_방해공작` 이 같은 `복구진척` 을 깎으면, 충돌 관계(그래프의 9쌍)가 그대로 **진영 콘텐츠**가 된다. 프로토의 "같은 변수를 반대로 미는 쌍" 규율이 MMO 에서 비로소 본색을 드러내는 지점.
- **once 를 유지하는 행동도 있다**: 유일물 제작(무광의 쐐기), 이름 있는 개체와의 서사적 결정(세리아 배신). 이것은 world 유일 사건으로 남기되, "서버 최초" 콘텐츠로 명시 설계한다. 기본값은 기여 패턴이고 once 유지는 예외로 표기한다.

### 4.2. 개인 인정과 보상

world 사건은 한 번 완료되지만 개인의 몫은 player 목적이 판정한다:

```jsonc
{ "id": "OBJ_P_강의귀환_기여", "goal": "G1.2.6", "scope": "player",
  "complete": { "all": [ { "var": "EV_강의귀환.단계", "op": ">=", "value": 2 },
                         { "var": "{char}.기여.EV_강의귀환", "op": ">=", "value": 5 } ] } }
```

늦게 합류한 캐릭터에게는 이미 완료된 world 사건이 **역사**(H 노드적 사실)로 보이고, 진행 중인 사건에는 기여로 참여한다 — "살아있는 세계"의 서버 나이가 콘텐츠 격차가 아니라 서사 깊이가 되도록, 사건 사슬의 끝이 항상 새 목적의 발견이라는 기존 원칙(WorldLaws §3)이 신규 플레이어의 진입 지점을 계속 만들어 준다.

### 4.3. 경제와 희소성

채취 행동의 이중 효과(개인 `보유 +1` / 세계 `공급 -1`)는 프로토 그대로가 곧 MMO 경제의 뼈대다. 공급은 world 단일 값이므로 수천 명의 채취가 **공유 자원 고갈**로 자동 집계되고(P5 경제), 회복 짝(LAW-B01)이 재생을 담당한다. 단 부하가 천 배가 되므로: 채취류 행동의 세계측 효과는 건별이 아니라 **집계 보고**(§2 상향 계약, 세계틱당 1회 합산 add)로 올린다 — add 는 교환법칙이 성립하므로(§5.3) 집계해도 결정론이 유지된다. 임계·회복률의 재조정은 §10 부하 시뮬로 검증한다.

## 5. NPC 정책 행동 = 월드 이벤트 — 경합 창 설계

프로토에서 수문회의 반격은 Director 안에서 조용히 발화한다(`ACT_수문회_제어탑파괴`, duration 10). MMO 에서는 이 **duration 이 플레이어 개입의 창**이 된다.

```text
Director: ⑦단계에서 수문회가 ACT_수문회_제어탑파괴 발화 (duration 10 세계틱 = 50초… 실제로는 수십 분 규모로 조정)
   ↓ 하향
Zone:     제어탑 존에 '수문회 습격' 월드 이벤트 인스턴스 스폰 — 습격 NPC 부대, 방어 오브젝트
   ↓ 플레이어 개입 (미시층 전투)
Zone:     이벤트 결과를 기여 보고로 상향 — 방어 성공: ACT_습격격퇴 발화 요청 (pending 효과 취소)
                                        방어 실패/무개입: duration 만기 → 원래 효과 착지 (가동=false)
```

- **pending 효과의 취소 가능성**을 엔진에 추가한다: duration 진행 중인 행동은 정의된 **대항 행동**(counter)으로만 취소된다. 대항 행동도 데이터다(불변 2) — `"counters": "ACT_수문회_제어탑파괴"` 필드.
- 검증 M4: 세계를 깎는 모든 NPC 행동은 `duration > 0` 이고 대항 행동이 존재해야 한다 — "플레이어가 막을 수 없는 세계 악화"는 연출이 아니라 설계 결함으로 취급한다. (예외: 사슬 법칙의 전파 자체는 대항 불가 — 개입 지점은 법칙이 아니라 그 원인 축을 미는 행동이다.)
- 무개입 시 프로토와 동일하게 굴러간다는 점이 중요하다 — **월드 이벤트에 아무도 안 와도 세계는 스스로 결말을 낸다**(증명 3). 이벤트는 세계 변화의 원인이 아니라 세계 변화의 *무대 연출*이다.

## 6. 권위·네트워킹

- **행동 발화 요청 프로토콜**: 플레이어 입력 → Zone → Director. Director 가 다음 세계틱 ⑦에서 when/cost 를 평가해 승인·거부한다(엔진의 `inputs` Map 이 이미 이 형태다). 거부 사유(어느 전제가 미충족인지)를 응답에 담아 클라 UI 가 "무엇이 부족한지"를 보여준다 — 전제가 데이터라서 가능한 UX.
- **낙관 예측 금지(세계층)**: 미시층(이동·전투)은 GGPO 롤백으로 예측하지만, 세계층 행동은 초 단위 틱이라 예측이 불필요하다. 요청→다음 틱 확정의 지연(≤N초)은 연출(시전 모션·건설 애니메이션)로 흡수한다.
- **구독 모델**: 클라는 (a) 전역 변수(S/X 활성·EV 단계 — 수십 개), (b) 현재 Zone 의 L/E/R 변수, (c) 자기 캐릭터의 player 변수만 구독한다. 파생축은 formula 가 공개 데이터이므로 클라가 재계산한다 — 전송 불필요.
- **치팅 면**: 클라가 보내는 것은 행동 id 뿐이고 모든 판정·효과는 Director 에 있다. 세계층의 치팅 면적은 구조적으로 0 에 수렴한다 — 미시층(이동·전투 입력)의 치팅 면은 기존 HktRuntime 책임 그대로.

## 7. 지속성

- **월드 스냅샷 = 상태의 전부.** once 발화 기록·everyLast·pending·clock 위상까지 스냅샷에 포함하면(증명 4) 주기 저장 + 종료 시 저장만으로 서버 재시작이 무손실이다. 상태량이 작아(수천 변수) 매 틱 저장도 가능하다.
- **발화 로그 = 이벤트 소싱.** 틱마다 fired(rules/actions/objectives)를 append-only 로 남긴다. 스냅샷 + 로그로 임의 시점 재구성·감사·사고 롤백이 되고, 이 로그가 그대로 운영 텔레메트리(§10)와 "서버 역사 연대기"(게임 내 콘텐츠 — 이 서버에서 언제 강이 돌아왔는가) 원천이 된다.
- **player 스코프는 캐릭터 DB.** 캐릭터 저장과 월드 스냅샷은 트랜잭션 경계가 다르다 — 행동의 cost(개인)와 효과(세계)가 갈라지는 유일한 지점이므로, 발화 로그에 행동 단위 기록을 남겨 크래시 시 재대사(reconcile)한다.

## 8. 하향 번역 표 — 세계 축 → 게임플레이 구현

Zone 서버가 세계 변수를 소비하는 표준 대응. 이 표의 각 행은 데이터(GameplayTag ↔ 노드 id·축 매핑 테이블)로 관리하고, HktAsset 경로로 로드한다.

| 세계 축 | 게임플레이 구현 (미시층) |
|---|---|
| `E_*.개체수`/`서식` | 스포너 밀도·리스폰율 파라미터. 멸종(0)=스포너 정지 |
| `E_*.위치` (ref) | 해당 종 스포너의 활성 Zone 전환 (심해포식자의 해안 상륙) |
| `R_*.공급` | 채집 노드 밀도·리스폰율. NPC 상점 가격은 공급의 파생축을 그대로 표시 |
| `L_*.발견/접근/가동/지배` | 맵 마커·입장 게이트·시설 액터 상태 머신·점령 깃발 |
| `S_*.활성/단계` | 존 날씨·환경 이펙트·필드 버프/디버프 (영원한 겨울=한랭 지대) |
| `X_*.활성/강도` | 위협 이벤트 스폰 테이블 (늑대 습격 빈도), 전역 디버프 |
| `F_*.세력/관계/체제` | NPC 진영 태도(적대/중립)·경비 배치 밀도·대사 분기 |
| `K/T.공개` + `습득` 쌍축 | 훈련 NPC 의 교습 목록·제작 레시피 해금 |
| `G*.진행` (world) | 월드 이벤트 공지·서버 연대기. (player) 퀘스트 저널 |
| NPC 행동 발화 (duration 중) | 월드 이벤트 인스턴스 (§5 경합 창) |
| `CLOCK_*` 위상 | 하늘 연출(일식)·주기 이벤트 스케줄 UI |

번역은 전부 **읽기 전용 소비**다 — HktFeature 의 불변 원칙("세계 속성 → ViewModel → 렌더(속성 그대로)")과 같은 규율이 3D 게임플레이 층에도 적용된다: Zone 은 세계 상태의 렌더러다.

## 9. 시간 의미론

- **1 세계틱 = 실시간 N초** (config, 기본 5s). 사슬 전파 속도(`every`)·경합 창(`duration`)·주기(`clock.period`)가 전부 이 배율로 실시간화된다. 프로토의 틱 수치는 서사 해상도 기준이므로, MMO 적용 시 사건 사슬이 **시간 단위~일 단위**로 퍼지도록 every/duration 을 재조정한다(값 조정이지 구조 변경이 아님 — 데이터 패치).
- **서버는 멈추지 않는다.** 플레이어 0명이어도 Director 는 틱을 돈다 — 증명 3(무입력 자율)이 그대로 "밤사이 세계가 변해 있는" MMO 운영 특성이 된다. 점검 다운타임은 스냅샷 정지·재개로 처리하며 경과 실시간을 따라잡지 않는다(세계 시간=틱 카운트, 벽시계 아님).

## 10. 콘텐츠 파이프라인과 라이브 운영

- **원본은 프로토 파일 그대로**: `objective-graph.json` + `world-state.json` 이 콘텐츠의 유일 원본이고, `validate-graph.mjs`/`validate-state.mjs` 가 CI 게이트다(검증 1~13 + 법칙검증 8종 + §12 의 M 검증). 빌드 시 문자열 id → 정수 핸들 테이블로 컴파일해 Director·Zone·클라가 공유한다(PropertyId 와 같은 방식).
- **시즌·패치 = 그래프 권역 추가**: 새 콘텐츠는 노드·관계 추가 → §9 번역 절차(WorldLaws) → 검증 통과 → 배포. 기존 스냅샷과의 호환은 "vars 추가는 init 로 채움, 삭제·타입 변경은 마이그레이션 스크립트 필수" 규칙으로 고정한다.
- **무입력 시뮬 = 밸런스 리허설 도구**: `simulate-state.mjs` 계열을 확장해 (a) 가상 플레이어 부하 프로파일(채취율·기여율 분포)을 주입한 장기 시뮬로 고갈·인플레·단조 붕괴를 배포 전 검출하고, (b) 라이브 스냅샷을 내려받아 "이 패치를 지금 세계에 적용하면 어떻게 되는가"를 미리 돌린다. 결정론이라 재현 가능하다.
- **운영 개입도 행동이다**(불변 2): GM 툴은 `ACT_GM_*` 로 선언된 행동만 발화할 수 있다. 발화 로그에 남으므로 감사가 공짜다.
- **텔레메트리**: 발화 로그를 HktInsights 계열로 흘려(`HKT_INSIGHT_COLLECT` 대응) 법칙별 발화 빈도·목적 완료 분포·기여 참여율을 본다. "발화된 적 없는 법칙"과 "아무도 완료 못 한 목적"이 콘텐츠 건강 지표다.

## 11. 적용 로드맵 — 프로토 안에서 검증하고 나간다

각 단계는 앞 단계의 검증 통과가 전제다. 1~2 는 프로토 저장소 안에서 끝난다 — **엔진을 옮기기 전에 MMO 의미론을 프로토에서 먼저 증명한다.**

```text
1. 스코프 확장     world-state.json 에 scope 필드 도입, E_플레이어 쌍축 5종을 player 스코프로 승격.
                  state-engine 에 다중 캐릭터 문맥({char} 치환) 추가. 시뮬: 가상 캐릭터 N명 동시 구동.
                  검증 M1·M2 를 validate-state 에 추가.
2. 기여 패턴 변환  세계 전환 once 행동을 P8(기여 임계)로 변환 — '강의 귀환' 권역부터.
                  counter 필드·pending 취소 추가(§5). 시뮬: N명 기여 경쟁 + 반대 진영 기여로 사건 5종 재검증.
                  검증 M3·M4 추가. once 유지 예외 목록 명시.
3. Director 서비스화  엔진을 상주 서비스로: 실시간 틱 스케줄러(§9), 스냅샷 저장·복구(§7), 발화 로그,
                  행동 요청/구독 API. 기존 mjs 검증기·시뮬레이터가 같은 데이터를 계속 소비.
4. 브리지 모듈     HktGameplay 측 구독·번역 모듈(§8 매핑 테이블의 데이터화, GameplayTag ↔ 노드id),
                  기여 집계 보고 경로. HktCore 순수성·ISP 레이어 원칙 준수(세계층은 Intent 위 상위 레이어).
5. 수직 슬라이스   '강의 귀환' 한 사건을 실존으로: 제어탑 액터(가동 상태 번역), 복구 기여 행동,
                  수문회 습격 월드 이벤트(경합 창), N인 동시 기여 — 사슬 6단계가 실제 존에서 재생되면 완료.
```

## 12. 검증 확장 — MMO 추가 검증 (validate-state 에 누적)

```text
검증 M1  owner 또는 술어에 E_플레이어 가 등장하는 변수는 전부 scope: player 로 선언되어 있다.
검증 M2  world 스코프 목적의 complete/fail 술어는 world 변수만 읽는다 (player 변수 참조 = 스코프 오류).
검증 M3  세계 전환 once 법칙의 임계 count 변수에는 그것을 미는 player 행동이 1개 이상 존재한다.
검증 M4  세계 축을 깎는 NPC 행동은 duration > 0 이고 counter 행동이 존재한다 (§5 경합 창).
검증 M5  부하 시뮬(가상 플레이어 프로파일)에서 모든 R.공급·E.서식이 단조 붕괴하지 않는다
         — 회복 짝(WorldLaws §6)의 부하 스케일 재검증.
검증 M6  once 유지(비-기여) 행동은 전부 '서버 최초' 예외 목록에 등재되어 있다 (§4.1).
```

## 핵심 문장

프로토가 증명한 것은 "세계는 다섯 층 데이터와 하나의 틱 루프로 스스로 굴러간다"는 것이고, MMORPG 적용은 그 세계에 플레이어를 **하나에서 수천으로** 늘리는 일이다. 답은 구조 변경이 아니라 두 가지 분리다 — 변수와 목적에 스코프(world/player/faction)를 도입해 "세계의 값"과 "나의 값"을 가르고, 세계 전환의 주어를 개인의 once 행동에서 집단 기여의 임계 법칙으로 옮긴다. 완료가 상태 술어라는 불변 덕에 사슬 법칙은 그대로이고, NPC 의 duration 은 플레이어가 개입하는 경합 창이 되며, 무입력 자율성은 밤사이에도 살아 있는 서버가 된다. 세계층은 월드당 하나의 결정론 프로세스로 남고, 30Hz 게임플레이층은 그 상태의 렌더러이자 기여의 집계자다 — 임의 쓰기 없음, 근거 없는 상태 없음, 서사가 아니라 값과 규칙. 프로토의 규율이 곧 MMO 의 서버 권위다.
