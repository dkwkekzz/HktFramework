# 세계 상태 데이터화 설계

> 이 문서는 [Design-ObjectiveTree.md](Design-ObjectiveTree.md)(방법론)와 [Design-ObjectiveGraph.md](Design-ObjectiveGraph.md)(상흔계 아벨리온 정본), 그리고 실물 데이터 [data/objective-graph.json](data/objective-graph.json) — 즉 **1번(목적 그래프)** 을 근거로, 세계의 **상태**를 데이터로 표현하는 방법을 설계한다. 설계 단계 문서이며 실물 데이터(`data/world-state.json`)는 다음 단계에서 작성한다.

## 0. 왜 상태인가 — 1번 문서에서의 근거

목적 그래프는 세계에 **무엇이 존재해야 하는가**(노드)와 **왜 존재하는가**(관계)를 정한다. 그러나 1번 문서는 곳곳에서 그 존재들의 **현재 값**을 요구한다.

```text
"목적은 행동이 아니라 만들고자 하는 세계 상태다."          (트리 §17-3)
"완료 조건: 어떤 세계 상태가 되면 완료로 판정하는가"        (트리 §5 목적 노드 표준 구조)
"성공 여부를 세계 상태로 판정할 수 있다."                  (트리 §6 분해 종료 조건 5)
"목적 완료는 세계 상태가 다른 상태로 전환되는 사건이다."     (트리 §3.3)
"목적 완료 후 세계 상태가 실제로 달라지는가?"              (트리 §16 검증 11)
"플레이어가 개입하지 않아도 세계 요소들이 변화하는가?"       (트리 §16 검증 14)
```

즉 목적의 **완료 판정**과 **완료 결과**, 사건의 **변화 사슬**은 모두 세계 상태에 대한 읽기와 쓰기다. 상태가 데이터가 되지 않으면 판정·변화·시뮬레이션이 전부 서술(산문)에 머문다.

정리하면 역할 분담은 다음과 같다.

```text
목적 그래프 (objective-graph.json)   =  세계의 뼈대. 무엇이 존재하고 왜 존재하는가. (거의 불변)
세계 상태   (world-state.json 예정)  =  그 존재들이 지금 어떤 값인가.               (계속 변함)
전이 규칙   (world-state.json 예정)  =  어떤 상태가 어떤 상태를 만드는가.            (거의 불변)
```

## 1. 핵심 결정 — 3층 모델

세계 상태 데이터는 세 층으로 나눈다. 그래프의 노드 id 가 세 층을 관통하는 유일한 앵커다.

```text
① 상태 변수 정의 (vars)      어떤 노드의 어떤 축이 상태를 갖는가. 스키마이자 존재 근거 기록.
② 초기 스냅샷   (initial)    시각 0 의 변수값 집합. 순수 key-value.
③ 전이 규칙     (rules)      전제(상태 읽기) → 효과(상태 쓰기). 그래프의 관계·EV 사슬의 기계 번역.
```

원칙:

- **모든 상태 변수는 그래프 노드에 귀속된다.** 노드 없는 상태 변수는 존재 근거 없는 세계 요소와 같다(트리 §14). 필요하면 먼저 그래프에 노드를 추가한다.
- **그래프는 수정하지 않는다.** 세계 상태는 별도 파일이 그래프 id 를 참조한다. 그래프는 계속 "유일한 원본"으로서 존재·관계만 담는다.
- **판정 가능한 값만 상태다.** 서술이 필요한 내용은 그래프 노드의 `detail` 에 남기고, 상태 변수는 기계 판정(비교 연산) 가능한 값만 가진다.
- **결정론.** 상태 변화는 규칙의 적용 결과로만 발생한다. 시간은 정수 틱으로 표현한다(실수 시각·난수 없음 — 난수가 필요해지면 시드 명시).

## 2. 상태 변수 정의 (vars)

### 2.1. 형식

```jsonc
{
  "id": "E_회색등늑대.개체수",        // "<노드id>.<축이름>" — 전역 유일
  "owner": "E_회색등늑대",           // 그래프 노드 id (필수, 참조 무결성 검증 대상)
  "kind": "count",                  // flag | level | count | ref
  "levels": null,                   // kind=level 일 때 단계 라벨 배열
  "init": 40,                       // 초기값 (초기 스냅샷의 원본)
  "basis": "G2.1 늑대 위협 · EV_늑대멸종 사슬의 판정 축"   // 존재 근거 — 어느 목적·사건 때문에 이 축이 필요한가
}
```

`basis` 는 트리 §13(양방향 연결)의 상태판 대응이다. 상태 변수를 역추적하면 어떤 목적·사건의 판정을 위해 존재하는지 설명할 수 있어야 하고, 설명할 수 없는 변수는 추가하지 않는다.

### 2.2. 값 종류는 네 가지로 제한한다

| kind | 값 | 용도 | 예 |
|---|---|---|---|
| `flag` | true/false | 존재·활성·발생 여부 | `S_영원한겨울.활성` |
| `level` | 0..N 정수 + 라벨 | 단계적 질의 축. 연속 실수 대신 사용 | `L_굶주린평원.식량` = 0고갈/1부족/2보통/3풍족 |
| `count` | 0 이상 정수 | 개체수·수량 | `E_회색등늑대.개체수` |
| `ref` | 노드 id 또는 null | 소유·지배·계약 대상 | `L_수원.지배세력` = `F_청동수문회` |

연속 실수(0.0~1.0)를 쓰지 않는 이유: 판정 임계값이 데이터 곳곳에 흩어지고, 서사적 의미("부족하다", "붕괴했다")와 값의 대응이 흐려진다. `level` 은 임계값을 라벨로 스키마에 고정한다.

### 2.3. 노드 타입별 표준 축

모든 노드가 상태를 갖는 것은 아니다. 타입별로 기본 축을 정하고, 필요한 노드에만 선언한다.

| 노드 타입 | 표준 축 | 비고 |
|---|---|---|
| `S` 상태 | `활성`(flag) 또는 `단계`(level) | S 노드는 상태 그 자체 — 반드시 1개 이상의 축을 가진다 |
| `X` 위협 | `강도`(level), `활성`(flag) | 위협 소멸=강도 0 이 아니라 활성 false (재발화 구분) |
| `E` 생명체·인물 | `개체수`(count) 또는 `생존`(flag), `관계`(level: 적대/중립/계약) | 인물은 생존+관계, 종은 개체수 |
| `F` 세력 | `세력`(level), `대아벨리온 관계` 대신 개별 `관계`(level) | 권력·규모를 `세력` 하나로 시작 |
| `L` 장소 | `접근`(flag), `지배`(ref), 장소 고유 축(`식량`, `오염` 등) | 고유 축은 basis 필수 |
| `R` 재료 | `공급`(level: 고갈/희소/보통/풍부) | 시장 가격 아님 — 세계에 존재하는 양 |
| `K` 지식 / `T` 기술 | `공개`(level: 소실/독점/제한/공개) | "누가 아는가"가 이 세계의 핵심 자원 (§4.1 정보=자원) |
| `G` 목적 | `진행`(level: 숨김/발견/진행/완료/실패) | §3 참조 — 목적 자체가 상태를 가진다 |
| `EV` 사건 | `단계`(count: 사슬에서 몇 번째까지 진행했나) | §5 참조 |
| `H` 역사 | 없음 | 과거 사건은 불변 — 상태를 갖지 않는다 |

## 3. 목적의 상태화 — G 노드의 생애주기

트리 §5 의 `완료 조건 / 완료 결과 / 실패 결과 / 발견 방식`, 그래프 §14 의 단계적 공개는 전부 G 노드의 상태다.

```text
G.진행 :  숨김(0) → 발견(1) → 진행(2) → 완료(3) | 실패(4)
```

- **숨김→발견**: 그래프 §14 의 공개 단계를 데이터로 구현하는 지점. 발견 조건도 규칙이다 (예: `K_금지된이벨연대기.공개 >= 제한` 이면 `G2.5.1.진행 = 발견`).
- **진행→완료**: 완료 조건 = 세계 상태에 대한 술어 (§4). 행동 카운트가 아니라 상태 판정이다 — "늑대를 10마리 잡았다"가 아니라 "야영지 습격이 멎었다".
- **완료/실패 → 세계 변화**: 완료 결과·실패 결과 = 효과 목록 (§4). 목적 완료는 콘텐츠 종료가 아니라 상태 전환 사건(트리 §3.3)이므로, 완료 효과가 다른 목적의 발견·발생을 다시 일으킨다(트리 §16 검증 12).

목적별 완료 조건·효과는 말단 G 노드부터 채운다. 조건을 상태 술어로 쓸 수 없는 목적은 아직 분해가 덜 된 것이다(트리 §6 종료 조건 5의 데이터판 검증).

## 4. 판정과 효과 — 규칙 (rules)

### 4.1. 형식

```jsonc
{
  "id": "RULE_늪서식지_감소",
  "basis": "EV_강의귀환 6단계 · 그래프 관계: 강복구 ─방해→ 늪 생명체",
  "when": { "all": [
    { "var": "S_강흐름.단계", "op": ">=", "value": 2 }
  ]},
  "then": [
    { "var": "L_하류늪.서식지", "op": "add", "value": -1 }
  ],
  "once": false          // true = 한 번만 발화, false = 조건 유지 시 틱마다 재평가
}
```

- **when (술어)**: `{var, op, value}` 비교의 `all`/`any`/`not` 조합. op 는 `== != >= <= > <` 6종.
- **then (효과)**: `set`(대입) / `add`(증감, count·level 만) 2종. 효과 대상도 반드시 선언된 변수.
- **once**: 사건성 규칙(제어탑 파괴 시도)은 true, 압력성 규칙(서식지가 줄면 포식자가 이동한다)은 false.

### 4.2. 그래프 관계와 규칙의 대응

규칙은 자유 창작이 아니라 그래프 관계의 기계 번역이다. `basis` 에 근거 관계를 기록한다.

| 그래프 관계 | 상태 데이터에서의 표현 |
|---|---|
| `필요` A─필요→B | A 관련 목적의 완료 조건 술어에 B 상태가 들어간다 |
| `제공` A─제공→B | A 상태가 좋을수록 B 획득 규칙이 발화 가능 (전제에 A 등장) |
| `변화` A─변화→B | 규칙 그 자체 — A 상태를 전제로 B 상태를 쓰는 효과 |
| `방해` A─방해→B | A 활성을 전제로 B 관련 축을 낮추는 효과 |
| `충돌` A─충돌→B | 같은 변수에 반대 방향 효과를 갖는 규칙 쌍 (동시 만족 불가가 데이터로 드러남) |
| `상호`/`파생` | 양방향 규칙 쌍 / 완료 효과가 다른 목적을 `발견`으로 올리는 효과 |

이 대응 덕분에 검증기가 "133개 관계 중 규칙으로 번역된 것/안 된 것"을 셀 수 있고, 세계 시뮬의 커버리지가 수치로 나온다.

## 5. 사건(EV)의 상태화 — 변화 사슬은 규칙의 열이다

그래프 §13 의 대표 사건 5종은 각각 규칙 사슬로 번역한다. 사건 노드의 `단계` 변수가 사슬 진행도를 담고, 각 단계가 규칙 하나에 대응한다.

예시 — **사건 1. 강의 귀환** 의 앞부분 번역 (실제 데이터는 다음 단계에서):

```text
사슬:  제어탑 복구 → 강 흐름 → 농업 회복 → 식량 가격 하락 → 수문회 권력 약화 → …

필요한 상태 변수 (전부 기존 그래프 노드에 귀속):
  L_제어탑.가동(flag)  S_강흐름.단계(level)  L_농경지.생산(level)
  R_식량.공급(level)   F_청동수문회.세력(level)  EV_강의귀환.단계(count)

규칙:
  R1: 제어탑.가동           → 강흐름.단계 +1,  사건단계=1        (once)
  R2: 강흐름 ≥ 회복         → 농경지.생산 +1,  사건단계=2        (once)
  R3: 농경지.생산 ≥ 보통    → 식량.공급 +1,    사건단계=3        (once)
  R4: 식량.공급 ≥ 풍부      → 수문회.세력 -1,  사건단계=4        (once)
  R5: 수문회.세력 ≤ 약화    → G_수문회_제어탑파괴.진행=발견       (once)  ← 세력의 새 목적 발생
```

주목할 점: 사슬 5단계(수문회의 제어탑 파괴 시도)는 플레이어의 행동이 아니라 **세력의 목적이 발견되는 것**으로 번역된다. 이것이 트리 §16 검증 13·14(다른 주체의 행동만으로 사건 발생, 플레이어 없이도 변화)를 데이터 구조로 보장하는 방법이다 — 주체가 누구든 목적의 `진행` 이 굴러가면 세계가 변한다.

## 6. 초기 스냅샷 (initial)

세계 시드(그래프 `meta.world`)의 서술을 값으로 고정한 것이 초기 스냅샷이다.

```jsonc
"initial": {
  "S_영원한겨울.활성": true,          // 시드: "일부 지역에 영원한 겨울"
  "S_과잉별빛.활성": true,
  "X_검은태양병.강도": 2,             // 확산 중
  "E_아르카론.생존": true,
  "G0.진행": 2,                      // 생존 목적은 시작부터 '진행'
  "G2.5.진행": 0                     // 아르카론 제거는 '숨김' — §14 공개 단계
  // ...
}
```

초기 스냅샷은 vars 의 `init` 을 모은 산출물이므로 별도 편집하지 않는다 — 단일 원본은 vars. 런타임/시뮬 중간 스냅샷은 같은 key-value 형식의 파생 데이터다.

## 7. 파일 구조와 편집 원칙

```text
data/objective-graph.json    (기존) 존재와 관계 — 유일한 원본, 상태 데이터가 참조만 함
data/world-state.json        (예정) { meta, vars, rules } — 상태의 유일한 원본
data/validate-graph.mjs      (기존) 그래프 무결성
data/validate-state.mjs      (예정) 상태 무결성 — §8 검증 규칙 자동화
```

- 편집은 `world-state.json` 한 곳. 그래프와 마찬가지로 단일 원본 원칙.
- `world-state.json` 의 meta 에 스키마 자기 기술(kinds, ops, G 진행 단계 라벨 등)을 그래프와 같은 방식으로 담는다.
- 뷰어(objective-tree.html)는 이후 단계에서 상태 오버레이(노드 위 현재값 표시, 규칙 발화 시뮬)를 추가한다.

## 8. 검증 규칙 (validate-state.mjs 가 자동 점검할 것)

```text
검증 1. 모든 var 의 owner 가 그래프에 존재하는가. (고아 상태 금지)
```

## 핵심 문장

목적 그래프가 세계에 무엇이 왜 존재하는지를 정한다면, 세계 상태는 그 존재들이 지금 어떤 값인지를 정한다. 상태 변수는 반드시 그래프 노드에 귀속되고, 목적의 완료는 상태 술어로 판정되며, 세계의 변화는 상태를 읽고 쓰는 규칙의 발화다. 서술이 아니라 값과 규칙이 되었을 때, "목적 완료는 세계 상태가 다른 상태로 전환되는 사건이다"라는 1번 문서의 선언이 비로소 실행 가능해진다.
