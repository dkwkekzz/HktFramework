# step-0029 concepts — 쓰기 정족수: "보냈다"와 "durable 하다"를 가르다

> 정식 기록: [step-0029.md](step-0029.md) · 현재 위치: [STATE.md](STATE.md)

## 개념 한눈표

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|------|-----------|---------------------|
| Write quorum (W) | 쓰기를 W개 사본이 *확인*해야 durable 로 친다 | `quorumW: W` — W개 ack 후에만 durableSeq 전진 |
| Acknowledgement (ack) | 받은 쪽이 "저장했다"를 발신자에 회신 | PersistStore → `journal_ack{seq}` |
| Durable watermark | "여기까지는 확실히 산다"는 연속 경계 | `durableSeq` — [0..]에서 ≥W ack 인 끝 |
| 정합성 윈도(Consistency window) | 보냈지만 아직 정족수 미확인인 구간 | `(보낸 최대 seq) − durableSeq` |
| Fire-and-forget | 보내고 잊음 — 도달 여부를 안 봄 | 0028 fan-out (이 step 이전) |
| Read/Write quorum 짝 | W+R>N+1 이면 읽기·쓰기 사본이 겹침 | 0028=read·0029=write |

## 핵심 통찰: "보냈다"는 "durable 하다"가 아니다

0028 은 저널을 primary + 복제 N 개에 *뿌렸다*. 하지만 **뿌리고 잊었다**(fire-and-forget). 서비스는 자기가 보낸 저널이 실제로 몇 개 사본에 *닿았는지* 모른다.

```
_journal(seq=42) → primary ✓
                 → 복제2   ✗ (전송 손실)
                 → 복제3   ✗ (전송 손실)
                 → 복제4   ✓
서비스 믿음: "42 보냄 = durable" ← 낙관
실제: 2 사본뿐. primary+복제4 둘 다 죽으면? → 42 소실, 그런데 서비스는 몰랐다.
```

이 *모름*이 0028 §9 의 정합성 윈도다. fire-and-forget 은 "보낸 것"과 "진짜 durable 한 것"을 구별하지 못한다. 쓰기 정족수는 그 둘을 **가른다**: 저장소가 "저장했다"를 회신(ack)하고, 서비스는 **W개 ack 가 모인 seq 만 durable 로 선언**한다.

## ack 와 durable watermark

각 저장소는 저널을 받으면(=RAM 저장) 발신자에게 `journal_ack{seq}` 를 돌려준다. 서비스는 seq 별로 *누가 ack 했는지*를 모은다:

```
ackSeqs[42] = {primary, 복제4}      size 2
ackSeqs[43] = {primary, 복제3, 복제4} size 3
...
durableSeq = [0,1,2,...] 에서 연속으로 size≥W 인 마지막 seq
```

`durableSeq` 는 **커밋 워터마크** — "여기까지는 W개 사본에 있으니 (N+1−W) 죽음을 견딘다"는 *보장된 프런티어*. 그 위는 정합성 윈도(아직 정족수 미확인). 윈도가 워터마크 *위로 정확히 드러난다* — 0028 이 못 본 것이 이제 보인다.

### 왜 "연속(contiguous)"인가

`durableSeq` 는 seq 0 부터 *끊김 없이* ≥W ack 인 끝까지만 전진한다. seq 42 가 정족수 미달이면 43·44 가 다 ack 됐어도 워터마크는 41 에 멈춘다. replay 가 연속 prefix 를 전제하기 때문(빈칸 있는 저널은 그 앞까지만 안전). 보수적이지만 안전한 정의다.

## (N+1−W) 죽음을 견딘다 — 정족수 산수

사본 N+1=4, 정족수 W=3 이라 하자. seq 가 durable(≥3 사본 보유)이면:

```
4 사본 중 3 이 그 seq 보유 → (N+1−W)=1 죽음에도 ≥2 생존(보유) → 복구 가능
```

이 step 의 증명은 그 경계를 *정확히* 짚는다. tail 손실로 **윈도 seq 는 2 홀더뿐**(primary, 복제4)이다. 그 2 홀더를 죽이면:

```
crash {primary, 복제4}:
  durable seq (3 홀더)  → 복제3 생존 → 복구 ✓
  윈도   seq (2 홀더)   → 둘 다 죽음 → 소실 ✗
```

`durableSeq` 가 **복구되는 것과 소실되는 것의 경계를 정확히 예측**한다. 워터마크 이하는 전부 살고, 윈도는 전부 죽는다(이 손실 패턴에서). 검증의 `durable복구=예 / 윈도소실=예` 가 이것이다.

## 0028 과의 짝: read + write quorum

| | 0028 | 0029 |
|---|------|------|
| 무엇 | quorum **read** | quorum **write** |
| 언제 | 복구 시 *생존 사본 합치기* | 쓰기 시 *W개 ack 기다리기* |
| 무엇을 닫나 | "한 사본 골라 읽으면 부족" | "보내고 잊으면 durable 불명" |

분산 저장의 고전 보장 **W+R>N+1**(쓰기·읽기 사본이 반드시 겹침)의 두 절반이다. 0028 이 읽기 절반, 0029 가 쓰기 절반을 깐다.

## 회귀 0 — 왜 안 깨지나

`quorumW: 0`(default)이면 `_journal` 이 저널에 `q` 플래그를 *안* 붙이고, 저장소는 `q` 없는 저널에 ack 하지 않으며, `durableSeq` 집계는 휴면한다. 페이로드가 0028 과 비트 동일 → 25/25 reg 0 → 29-step 비트 사슬 통과. 정족수는 *순수 추가*다 — 켜면 가시성을 얻고, 끄면 0028 그대로.

## 정직한 한계 (전문은 [step-0029.md](step-0029.md) §9)

- **워터마크는 감지지 전환이 아니다** — 윈도를 *보이게* 할 뿐, 윈도 seq 를 재발행해 정족수를 *채우지는* 않는다(후속: 0023 재전송 결합).
- **ack = RAM 도달이지 디스크 fsync 아님** — 진짜 전원-손실 내구성은 미착수.
- **"윈도는 반드시 죽는다"는 보장 아님** — `durableSeq` 의 약속은 "durable 은 반드시 산다"(보수적 하한). 윈도 생존 여부는 손실 분포 의존.
