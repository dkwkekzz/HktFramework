# step-0017 — 가방 서비스 failover·영속 (계층 6 데이터 첫 진입 · 인벤토리 원장을 영속 저널에서 재구성 · "세계가 세션보다 오래 산다")

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0017/net-core.js`(0016 액터·토폴로지 빌더 복사 전진 + **PersistStore** 박스 + 가방 `_journal`/`crash`/`replay` + run() **invRestart** 분기) · `step-0017/cluster.js`(broker — 0016 그대로 + **가방 failover 안무**(진짜 kill→새 호스트 spawn→init→replay)·**persist 재구성**) · `step-0017/host.js`(0016 그대로 + **persist 스냅샷**·**replay 명령**) · 헤드리스: `step-0017/verify.js` · 관찰: `step-0017/panel.js`(+`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **SPINE 계층 6(데이터)의 *첫 박스* — 가방 원장에 *영속 진실*(append-only 효과 저널)을 깔아, 가방 서비스를 죽여도(RAM 소실) 새 가방이 저널을 *replay* 해 원장을 죽기 전과 *비트 동일*하게 재현한다 = "세계가 세션보다 오래 산다".** 0014~0016 의 게임 서비스(가방·채팅·버스·감사)는 전부 *영속 0*(프로세스와 함께 죽음)이었다. 이 step 은 `PersistStore`(저널 `[{seq,kind:'mint'|'xfer',...}]` SSOT, **onTick 없음 = tick 무관 순수 반응형**)를 자기 OS 프로세스로 세우고: 가방이 수락한 모든 변이(pickup=mint·give=xfer)를 persist 로 *write-behind 저널*(fire-and-forget — 결과 ack 는 영속 ack 를 안 기다림). 가방 failover(`invRestart.at`) = 0013 재-provisioning 의 *서비스 판*: 인프로세스는 같은 가방 객체를 `crash()`(RAM 소실) 후 `replay(저널)`, 멀티프로세스는 broker 가 ⒜ persist(*안 죽음*)에서 저널 읽고 ⒝ 가방 호스트 *진짜 child.kill* ⒞ 새 호스트 spawn·init·`replay` ⒟ 'inventory' 라우팅 전환. 복구는 전부 *제어 평면*(net.log 비-기여) → 인프로세스/멀티프로세스 **비트 동일**. 가방의 영속 인터페이스는 버스가 아닌 *직접 명시 인터페이스*(서비스 자기 데이터 스토어 = DB 연결의 더미판 — §4 "버스/**명시 인터페이스**" 허용).

## 2. 메커니즘 — 가방 원장을 영속 저널에서 재현 (이 step 의 한 조각)

**영속 모델 = event sourcing(상태 전송 아님 = §4 "복제=재현").** 가방이 수락한 변이마다 *효과*를 PersistStore 저널에 append:
- `pickup` 성공 → `{seq, kind:'mint', itemId, owner}`
- `give` 성공 → `{seq, kind:'xfer', itemId, from, to}`
- 실패한 give(미소유/중복/자기자신)는 원장 무변경 → 저널 무기록.

**write-behind**: 가방은 저널 메시지를 *fire-and-forget*(`net.send(inventory→persist)`)로 보내고 결과(item_result)를 영속 ack 없이 즉시 발신한다 — 신성한 tick 밖 비동기. PersistStore 는 *발신 0*(관찰 전용 스토어 — 읽기는 복구 시 제어 평면으로만).

**복구(crash + replay)**:
- **인프로세스**(`run`): `invRestart.at` tick 의 deliver 직전에 `inventory.crash()`(원장·역인덱스·카운터·mintTotal 전부 비움 = RAM 소실 모델) 후 `inventory.replay(persist.journal)`. PersistStore 는 *별 객체*라 crash 영향 없음.
- **멀티프로세스**(`runMulti`): broker 가 같은 위치에서 ⒜ `snapshotOne(persist)` 로 저널 읽기(persist 안 죽음) ⒝ `killHost(inventory)`(진짜 `child.kill('SIGKILL')`·소켓 RST·RAM 소실) ⒞ `spawnOne('inventory_r')`·`init`(빈 InventoryService)·`replay(저널)` ⒟ `placement.set('inventory','inventory_r')`(이후 라우팅 전환).

`replay` 는 저널을 seq 순서로 적용해 ledger·byOwner·minted·transfers 를 재구성하고 **mintTotal 을 mint 항목 수로 복원**(다음 itemId 연속성 = 복구가 원장에 투명). 복구는 net.log 에 *안 나타난다*(제어 평면) → 인프로세스/멀티프로세스 net.log 비트 동일.

**복구 투명의 조건(quiescent restart)**: 저널은 1-tick 비동기라 crash 시점에 in-flight 항목이 있으면 손실(write-behind 윈도). 시나리오는 가방이 *정지*(모든 item op·저널 drain 완료)한 늦은 tick(60)에 재시작 → 저널이 효과 전부를 담아 복구가 무재시작과 *비트 동일*. 활성 중 재시작의 bounded loss(ack/resend·스냅샷 압축)는 후속(§9).

## 4. 척추 체크 5항

1. **신성한 tick** ✅ — 저널 쓰기·replay 는 존 tick 밖(persist onTick 0). 존 net.log·상태가 persist on/off·restart 유무에 비트 동일·존 도달 persist 0.
2. **결정론 코어** ✅ — 저널 = 수락 순서의 함수(시드·로그). replay 는 같은 저널 → 같은 원장(mintTotal 복원 → itemId 연속성). 멀티 2회 = 인프로세스 동일.
3. **권위 단일 소유** ✅ — 원장 쓰기 권위 단일(InventoryService). 죽어도 저널이 *재현*의 진실(상태 전송 아님). 복구 후 belief 소유 ≤1.
4. **은닉·단일 연결** ✅ — 클라는 게이트웨이만. 저널/persist/replay/복구 안무는 전부 서버간/제어 평면 경계(클라 누설 0).
5. **headless·원격 검증** ✅ — node verify.js 한 줄이 persist 를 별 프로세스로 띄우고 가방을 진짜 kill→replay 로 복구해 4기둥 검증(persist ON 11 프로세스·restart 12).

## 9. 의외의 발견 / 정직한 한계

**의외의 발견**
- **"세계가 세션보다 오래 산다"는 *두 객체의 독립*으로 떨어진다.** PersistStore(데이터)와 InventoryService(서비스)가 *다른 박스*이기만 하면, 가방 객체를 crash 해도 persist 객체는 무관 — 인프로세스에서조차 "프로세스 사망"을 객체 wipe 로 충실히 모델링할 수 있다. 멀티프로세스의 진짜 child.kill 과 *비트 동일*(복구가 제어 평면이라 net.log 비-기여)인 것이 핵심 — 영속/failover 는 *응용 메시지 스트림 밖*의 일이다.
- **복구 투명 = "재현의 입력이 온전한가"의 함수.** quiescent restart 면 저널이 효과 전부를 담아 replay 가 무재시작과 비트 동일. mintTotal 복원 한 줄이 itemId 연속성을 지켜 *이후* op 도 같은 itemId 를 받는다(복구가 미래에도 투명).
- **0013 재-provisioning 패턴이 서비스에 그대로 재사용된다.** 존의 kill→spawn→loadstate(상태 동기)가 가방의 kill→spawn→replay(저널 재현)로 거의 일대일 — 차이는 *상태 전송(loadstate)* 대 *재현(replay)*. 후자가 §4 "복제=재현"에 더 충실(영속 저널이 진실).

**정직한 한계**
- **write-behind 윈도(영속의 핵심 한계)** — 저널은 1-tick 비동기라 가방이 *활성 중*(in-flight 저널 있을 때) 죽으면 그 변이는 손실(client 는 ack 받았는데 영속엔 없음). 이 step 은 *quiescent restart*(가방 정지 후)로 윈도를 비워 투명을 보였다. 활성 중 failover 의 bounded loss·복구 후 재수렴(client 재시도·ack/resend·write 손실 감지)은 후속.
- **저널 무한 성장·스냅샷 압축 없음** — 저널은 append-only 로 무한 성장. 주기 스냅샷 + 저널 tail 압축(SPINE "intent 로그 + 스냅샷")은 후속.
- **단일 PersistStore·디스크 fsync·다중 복제 0** — persist 자체가 죽으면 영속 소실(새 단일점). 진짜 디스크 영속·fsync·다중 복제·persist failover 는 후속.
- **가방만 영속** — 채팅 구독·버스 라우팅·존 월드(intent 로그)는 여전히 영속 0. 채팅/버스/월드 영속은 후속.
- **다운타임 가용성 미보장** — 복구를 tick 경계에 *seamless* 하게 했다(다운 윈도 0). kill→재spawn 사이 들어오는 item op 의 큐잉/재시도는 미착수(가용성은 이 step 의 *상태 보존*과 별개 조각).
- **여전히 Node·lockstep 배리어·C++ 시뮬 미교체.**
