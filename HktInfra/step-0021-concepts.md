## 1. 효과 소싱 vs 커맨드 소싱 — 무엇을 로그할까 (이 step 의 핵심)

**무엇**: event sourcing 은 상태를 *직접 저장*하지 않고 *로그를 재생*해 복원한다. 그런데 "무엇을 로그할까"에는 두 갈래가 있다. ⒜ **효과 소싱**: 결정 *결과*(효과)를 로그한다 — 가방(0017)은 `mint`/`xfer`(아이템이 누구 것이 됐다)를 적었다. replay 는 효과를 그대로 재적용한다. ⒝ **커맨드 소싱**: 들어온 *입력*(커맨드)을 로그한다 — 채팅은 `join`/`say`/`whisper`/`leave`(누가 무엇을 요청했다)를 적는다. replay 는 커맨드를 *다시 처리*한다.

**왜 중요한가**: 어느 쪽이냐는 *상태의 성질*이 가른다. 가방 원장은 *값*이다 — 효과(소유권 이전)를 재적용하면 끝. 하지만 채팅의 `deliveries`(누가 무엇을 받았나)는 *say 시점의 라우팅 테이블에 의존하는 파생*이다. say 하나가 *그 순간의 구독자 집합*으로 팬아웃되므로, 효과(개별 배달)를 따로 저장하기보다 *커맨드(say)를 재실행*해 — 그때까지 재생된 라우팅 위에서 — 배달을 다시 유도하는 게 자연스럽다. 라우팅이 join/leave 로 시시각각 변하므로 커맨드를 *순서대로* 재생해야 정확하다.

**어떻게 검증했나**: 채팅을 진짜 kill 한 뒤 커맨드 로그(chatpersist)를 replay 해 라우팅 테이블과 deliveries 를 재유도했다. 복구된 채팅 상태가 무재시작과 *비트 동일*(chatDigest·배달 211~229 재현)임을 5시드에서 보였다. 대조군(chatpersist OFF + 같은 kill)은 replay 불가 → 구독/배달 소실(배달 0).

## 2. 단일 리듀서 공유 — 복구가 라이브와 *같은 코드*여야 하는 이유

**무엇**: `onMsg` 를 둘로 갈랐다 — 정규화(페이로드→커맨드)와 `_process(op)`(상태 변이 + 팬아웃 + 저널). 라이브 처리도 복구 replay 도 *같은 `_process`* 를 호출한다. 복구 시엔 `replaying=true` 로 `_deliver` 의 *재발신만* 끄고(클라 중복 0·net.log 비-기여), deliveries 적재·계측은 동일하게 수행한다.

**왜 중요한가**: 만약 복구가 라이브와 *다른 코드 경로*였다면, 미묘한 규칙 불일치(발신자 자기-에코 제외·지역 채널을 발신자 region 으로 해석·미가입자 무시…)가 복구 후 desync 를 낳는다. 단일 리듀서는 "라이브 == 복구"를 *구조적으로* 보장한다 — event sourcing 복구의 정확성은 "replay 가 원래 처리와 같은 함수인가"에 달렸다. 이는 일반 원칙이다: 복구 경로를 따로 작성하지 말고 *처리 경로를 재사용*하라.

**보너스 — 회귀 0 보존**: 리팩터(onMsg→_process)는 *동작 보존*이라, chatpersist OFF 면 0020 과 비트 동일(reg 25/25). 래퍼만 바뀌고 상태 변이·_deliver 호출·net.send 가 동일하므로.

## 3. 라우팅 복구의 정확성은 *작동적으로* 검증된다

**무엇**: 가방 복구는 원장 값 일치(invDigest)로 충분했다. 하지만 라우팅 테이블 복구는 자료구조 일치를 넘어 "복구 후 *새 say* 가 올바른 구독자에게만 가는가"로 봐야 진짜다 — 비-구독자 누설 0·지역 격리 보존. 복구된 `channels`/`byAvatar` 가 단지 같은 모양인 게 아니라 *작동적으로* 정확함을 chatLeak 0·chatPhantom 0 으로 확인한다.

**왜 중요한가**: 상태 복구의 검증 기준은 상태의 *용도*를 따라야 한다. 원장은 값을 *읽기* 위한 것이라 값 일치가 곧 정확성이다. 라우팅 테이블은 *팬아웃을 결정*하기 위한 것이라, 복구의 진짜 시험은 "복구된 테이블로 라우팅했을 때 옳은가"다. 0015 의 불변(누설 0·격리)이 복구 후에도 성립함을 보임으로써 "라우팅이 살아 돌아왔다"를 증명한다.

**한계(정직)**: 검증은 *quiescent*(활동 정지) 재시작이다. 활성 중 채팅 다운타임(다운타임 구독 변경 후 클라 재발행)은 미착수. 또 커맨드 로그는 *비유계*(압축 없음) — 가방의 0018 스냅샷 압축에 해당하는 "라우팅 스냅샷 + tail" 은 채팅 판으로 후속이다.

## 한 줄 요약

채팅도 죽었다 살아난다 — *커맨드 로그*(join/say/whisper/leave)를 replay 해 라우팅 테이블+deliveries 를 *리듀서 재실행*으로 재유도(가방의 효과 소싱과 달리 라우팅 의존 파생이라 커맨드 소싱). live·복구가 단일 리듀서 `_process` 를 공유해 분기 0, 복구된 라우팅은 *작동적으로* 정확(say 누설 0·격리). 서비스 복구 3부작(가방·랭킹·채팅) 완성.
