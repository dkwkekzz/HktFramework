# step-0058 — 미확인 명령 *재시도*: recover 분실 시 orch 재발신 (recoverRetry)

> 직전: [step-0057](step-0057.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0057 의 `recoverAck` 가 명령 *확인*을 줬다(orch 가 recover 전달·수행 여부를 안다). 그러나 명령이 *분실*되면(메시지 손실·소비자 일시 무응답) ack 가 영영 안 오고 치유가 막힌다 — 0057 은 분실을 *감지*만 할 뿐(acks<commands) *복구*하지 못한다. 이 step 은 그 위에 *재시도*를 세운다: orch 가 `recoverTimeout` 경과 후에도 미확인인 recover 를 재발신해, 분실에도 치유가 결국 수렴하게 한다(0008 의 ack/NAK 재전송을 *제어 평면*에 옮긴 것). 닫는 조건: ⒜ `recoverRetry=0` 이면 0057 비트 동일(reg 0·재시도 0) ⒝ recover 분실(dropRecover 2) 시 retry OFF 면 영영 down(ack 0·readmit 0·consumerDown={ranking}) vs retry ON 이면 재발신으로 치유(recoverRetries≥1·ack 1·readmit 1·consumerDown 비움) ⒞ 비-침습(ON==OFF 원장 minted).

## 2. 메커니즘 — 확인 기반 재시도 (recoverRetry OFF → baseline 비트 동일 = 회귀 0)

0057 의 recoverAck 위에 *미확인 추적 + 재발신*을 더한다. orch 는 recover 발신 시 `pendingRecover.set(consumer, curTick)` 로 확인 대기 목록에 올리고, recoverAck 수신 시 `pendingRecover.delete(consumer)` 로 내린다. `onTick` 마다:

- `pendingRecover` 의 각 항목에 대해 `tick - sentAt >= recoverTimeout` 이면 recover 를 재발신하고 `sentAt` 갱신·`recoverRetries++`.

소비자(`RankingService`)는 명령 분실을 모델하기 위해 `dropRecover>0` 이면 처음 N개 recover 를 *떨군다*(재구독·ack 0). 그러면 orch 는 ack 를 못 받아 recoverTimeout 뒤 재발신 → 분실분이 소진되면(dropRecover→0) 소비자가 처리해 재구독+ack → 치유 수렴. ack 가 오면 pendingRecover 에서 빠져 재시도 루프가 종료된다(무한 재발신 0).

`recoverRetry=0` 이면 onTick 재시도 루프 미실행 → pendingRecover 가 차도 재발신 0 → NET 비트 동일. 닿는 박스: `orchestrator.js`(pending 추적·onTick 재발신)·`svc-ranking.js`(dropRecover 분실 주입)·`topo-build.js`(플래그 배선). 순수 제어 평면(존 tick 밖·원장 권위 불변).

## 9. 의외의 발견 / 정직한 한계

- **제어 평면이 데이터 평면의 신뢰성 패턴을 *재사용*한다**: recover 의 fire-and-forget(0056)→ack(0057)→timeout 재시도(이 step)는, 데이터 평면이 0008 에서 밟은 길(전송→ack→NAK/재전송)과 정확히 같은 계단이다. 신뢰성은 평면(데이터/제어)을 가리지 않는 *같은 문제*이며, 같은 해법(확인+재시도)이 작동한다. 이는 인프라가 한 번 푼 패턴을 다른 층에 *이식*할 수 있다는 증거.
- **재시도 종료는 ack 가 보장한다(무한 루프 0)**: pendingRecover 는 recoverAck 수신에만 비워진다 — 즉 *성공 확인*이 재시도를 멈춘다. 소비자가 영영 안 받으면(영구 분실) 재시도가 무한해질 수 있다(현 모델은 dropRecover 가 유한이라 수렴). 진짜 영구 분실에는 *재시도 상한 + 대체 소비자 spawn*(계층 5 오케스트레이션의 다음 단계)이 필요 — 이 step 은 *일시 분실*의 복구까지.
- **recoverTimeout 의 트레이드오프**: 짧으면 빠른 복구지만 ack 가 늦게 오는 정상 경우에 *불필요한 재발신*(소비자 중복 recover 수신 — 멱등이라 무해하나 대역 낭비). 길면 복구 지연. 현 상수(4 tick)는 본 시드/틱에 충분 — 적응형 timeout(관측 RTT 기반)은 후속(0050 의 cadence 적응을 제어 평면에 옮기는).
- **분실 모델은 소비자-드롭으로 근사**: 진짜 메시지 손실(전송 계층 드롭)이 아니라 소비자가 *받고 떨구는* 것으로 모델했다 — orch 관점(ack 안 옴)에선 동일하나, 전송 드롭이면 소비자는 recover 를 아예 못 본다. 두 경우 모두 재시도가 같은 방식으로 복구하므로 검증 가치는 동등(orch 측 재시도 로직이 검증 대상).
