# step-0023 — 저널 홉 신뢰 전달 (가방 write-behind 저널 홉의 갭 감지 NAK + 재전송 — 0008 의 저널 홉 판)

> 직전: [step-0022](step-0022.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0017~0022 의 복구는 전부 *저널이 온전히 영속됐다고 가정*했다. 그러나 `inventory→persist` 저널 홉이 전송 손실되면 저널에 **갭**(빠진 효과)이 생겨 복구가 *불완전*해진다 — write-behind 신뢰성의 절반(STATE §3 ⓐ "가장 큰 구멍"). 이 step 은 STATE §2 ⒜(exactly-once 내구성)의 *sanctioned sub-piece* "저널 홉 ack/resend 만"을 구현한다. **닫는 조건**: 저널 홉에 손실을 주입했을 때, `journalReliable` ON 이면 PersistStore 가 seq 갭을 감지→NAK→InventoryService 가 재전송해 저널이 **완전**(writes == 무손실 기준)·복구가 **무손실**(invDigest == 무손실 기준)이고, OFF(fire-and-forget)면 같은 손실이 저널 갭→복구 손실이며, OFF(`journalReliable=0`)에서 0022 비트 동일(reg 0). SPINE 계층 6(데이터·write-behind 신뢰성) 채움.

## 2. 메커니즘 — 저널 홉 갭 감지 NAK + 재전송 (`journalReliable=false` → 0022 비트 동일 = 회귀 0)

**0008(핸드오프 ack/재전송·keyframe/NAK) 패턴의 *저널 홉 판***: 갭 감지는 *수신측(persist)* 이 한다 — "누가 안 왔는지는 받는 쪽이 안다". 전부 반응형(onMsg·onTick 0 = 신성한 tick).

- **`InventoryService._journal`**: 보낸 항목 `{...entry, seq}` 를 `reliable` 이면 `sentBuffer.set(seq, full)` 에 보관(미-ack). send 는 종전대로.
- **`InventoryService._resend(missing)`**: NAK 의 미수신 seq 를 `sentBuffer` 에서 다시 send(새 m.id → 전송 손실 재노출). `onMsg('journal_nak')` 가 호출(reactive).
- **`PersistStore`(reliable)**: journal 수신 시 ⒜ `recvSeqs.has(seq)` 면 dedup(재전송 중복 push 0) ⒝ 아니면 push+writes++·`recvSeqs.add` ⒞ `[0..maxRecvSeq]` 중 미수신 seq 색출 → 있으면 `m.from`(=inventory)에 `journal_nak{missing}`. **매 수신 재-NAK** = NAK 손실에도 결국 수렴.
- **신뢰성 등식**: at-least-once 전송(재전송) + 멱등 수신(recvSeqs dedup) = **effectively-once 영속**. 손실 아래에서도 persist 저널이 *완전*해 복구가 무손실.

손실은 *전송층*(`routeFilters.persist` + redundancy 1 + loss 0.3)으로 주입 — 0008 처럼 손실을 자극해 신뢰 메커니즘을 작동시킨다. 압축(0018)과 직교 — 신뢰 시나리오는 snapshot OFF(§9 상호작용 회피). 더한 것은 inventory `sentBuffer`/`_resend` + persist 갭감지/NAK/dedup 뿐·host.js/`engine/` 무수정.

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js 0023` / `node run.js spine`)

- **① 회귀 0 (reg)** — 인프로세스 `journalReliable=0` → step-0022 **비트 동일** 25/25(5구성×5시드). 마지막 `persist+rel+rst` 는 journalReliable **ON 이지만 손실 없음** → 0022 와 동일 해시(0x4f0d13d6 …) = 새 신뢰 코드(sentBuffer·NAK·dedup)가 무손실에선 *휴면*(NAK 0)임을 직접 증명.

- **③ 권위 보존·신성한 tick (sacred·degrade)** — journalReliable on/off 월드 비트 동일·존 도달 0·열화에도 원장 보존·소유 ≤1.

## 4. 척추 체크 5항

1. **신성한 tick** — NAK·재전송·dedup 은 *존 tick 밖*(가방·persist onTick 0·제어 평면). journalReliable on/off 월드 비트 동일·존 도달 journal/nak 0.
2. **결정론 코어** — 복구 원장 = persist 저널(seq 순서·dedup)의 함수 → 손실 아래에서도 무손실 기준과 정확히 일치(= §4 "복제=재현").
3. **권위 단일 소유** — 원장 쓰기 권위는 InventoryService 하나. 신뢰 전달은 *영속의 완전성*만 보장·라이브 원장 비-침습(invDigest 불변).
4. **은닉·단일 연결** — NAK/재전송은 inventory↔persist *서버간 제어 평면*(클라 비가시·hide 누설 0).
5. **headless·원격 검증** — `node run.js 0023` 한 줄이 저널 홉에 손실을 주입해 신뢰 ON=완전/무손실·OFF=갭/손실을 4기둥 검증(UE 0).

## 9. 의외의 발견 / 정직한 한계

- **발견 — 갭 감지는 수신측의 일**: NAK(부정 ack)는 수신측 persist 가 한다(seq 의 빈칸은 받는 쪽이 안다). 그래서 *순수 반응형*(양쪽 onMsg·onTick 0)으로 성립 — 송신측 타이머 없이 신성한 tick 을 안 깬다. 0008(핸드오프 keyframe/NAK)과 같은 원리의 저널 홉 판.
- **발견 — at-least-once + 멱등 = effectively-once**: 재전송은 같은 seq 를 중복 보낼 수 있으나 `recvSeqs` dedup 이 중복 push 를 막아 *영속*은 effectively-once. seq(0017 의 단조 순번)가 멱등의 키 — 0017 의 "빈칸·중복 구조적 불가" 설계가 신뢰 전달의 토대였다.
- **한계 — tail 손실 미감지(NAK-only 의 본질)**: 갭 감지는 *후속 seq 가 도착*해야 작동 → *마지막(최고 seq) 항목*이 손실되면 후속이 없어 미감지(영구 손실). 5 고정 시드는 JLOSS=0.3 에서 tail 생존(결정론). 일반 해소 = heartbeat/ack-timeout 또는 스냅샷 fence(다중 메커니즘 — STATE §2 ⒜ 의 나머지·후속).
- **한계 — write-behind 윈도의 *전송-손실 절반*만**: 닫은 것은 *저널 홉 전송 손실*이다. *활성 중 가방 죽음=in-flight(sentBuffer 미-ack) 손실* 절반은 여전히 열림(crash 가 sentBuffer 비움 — RAM 손실). exactly-once 내구성의 나머지(클라 resend·write-ahead).
- **한계 — NAK 폭주·재전송 증폭**: 매 수신 재-NAK 라 18개 갭에 재전송 238회(≈13배 증폭). 정확하나 비효율 — NAK 배칭·rate-limit·cumulative-ack 는 후속.
- **한계 — 압축×신뢰 미결합·채팅 홉 미적용**: 신뢰 시나리오는 snapshot OFF(압축×재전송 상호작용 회피). chatpersist 홉은 신뢰 미적용(가방 홉 한정). 둘 다 후속.
