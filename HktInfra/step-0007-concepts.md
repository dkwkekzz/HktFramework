# step-0007 — Concepts: Incremental Sync — Bandwidth Proportional to Change, Zero When Still

> 이 문서는 [step-0007.md](step-0007.md)(시리즈 정식 기록·압축적)에 깔린 **핵심 개념들을 풀어 설명**한다.
> 코드 변경 자체보다 "이 step 이 다루는 개념이 무엇이고, 왜 그게 인프라에서 중요한가"에 초점을 둔다.
> (개념 해설 문서는 step-0010 에서 규약화됐다 — 이 문서는 시리즈 일관성을 위한 소급 작성이다.)

---

## 0. 이 step 이 다루는 개념 한눈에

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|---|---|---|
| **증분 (델타) 동기화** (incremental/delta sync) | 전체 상태 대신 *달라진 것만* 보냄 | view → view_delta(enter/exit/update) |
| **키프레임 vs 델타** (keyframe / delta) | 전체 재구성(keyframe) ↔ 변화분(delta)의 표준 쌍 | reset=키프레임, enter/exit/update=델타 |
| **누적 재구성** (cumulative reconstruction) | 클라가 델타를 *쌓아* 가시 집합을 복원 | seen.set/delete 누적 |
| **변화량 비례 대역폭** (bandwidth ∝ change) | 전송량이 밀도가 아니라 *변화량*에 비례 | 정지하면 무발신(대역폭 0) |
| **직교 합성** (orthogonal composition) | 증분과 핸드오프가 *서로 모른 채* 합쳐짐 | 세션 이주 시 자동 reset(키프레임) |
| **손실 취약성** (loss fragility) | 누적 사슬은 델타 1개 유실에 *영구* desync | 전체 스냅샷의 자가치유를 잃음 |

이 step 의 본질은 **"가시를 *전체 스냅샷*이 아니라 *변화분(enter/exit/update)* 으로 보내면 대역폭이 밀도가 아니라 변화량에 비례하고 — 정지하면 0 으로 수렴한다"** 는 한 문장이다.

---

## 1. 출발점 — 정지한 엔터티를 매 tick 다시 보내는 낭비

step-0006 의 AOI 는 *전체 스냅샷*이었다 — 매 tick 각 세션에 반경 안 엔터티를 *전부* 재전송한다(0005 상속). 그런데 엔터티가 *정지*해 있어도 매 tick 같은 위치를 다시 보낸다. 이는 낭비다 — 변하지 않은 것을 재전송할 이유가 없다.

해법은 **증분**(incremental) — 직전에 보낸 가시 집합과 *달라진 것만* 보낸다. 0006 의 ①~③(이동·핸드오프·경계 띠 ghost)·구조는 *그대로* 두고, ④ 뷰 발행 *한 단계*만 전체 스냅샷에서 증분으로 바꾼다. 존은 여전히 *시뮬하지 않는다*(C++ 최후 교체).

---

## 2. 핵심 개념 ① — 증분(델타) 동기화와 키프레임

**증분 동기화**(delta sync)는 매 tick 전체 상태가 아니라 *변화분*만 보내는 것이다. 비디오 코덱(키프레임 + 인터프레임), 데이터베이스 복제(스냅샷 + WAL)와 같은 패턴이다.

존이 세션별 직전 가시(`prevSeen`)를 들고, 매 tick `cur`(현재 가시)와 비교해 셋으로 쪼갠다:

| 종류 | 의미 | 페이로드 |
|---|---|---|
| **enter** | 새로 보임 (cur \ prev) | id, x, y |
| **exit** | 안 보임 (prev \ cur) | id |
| **update** | 보이는데 움직임 (cur ∩ prev, 위치 변함) | id, x, y |
| **reset(키프레임)** | 전부 재구성 (prev 없음) | 전 엔터티 enter |

**키프레임**(reset)은 델타의 짝이다 — 델타는 *기준점이 있어야* 의미가 있으므로, 기준이 없을 때(새 세션·핸드오프 직후) 전체를 한 번 보내 기준을 세운다. `prevSeen` 은 *방금 보낸 가시 = 클라 seen 과 동기*로 갱신되어 다음 tick 의 기준이 된다.

회귀: 증분을 끄면(incremental=false) 0006 의 `view`(전체 배열)를 *비트 동일*하게 보낸다(reg 0).

---

## 3. 핵심 개념 ② — 누적 재구성과 변화량 비례 대역폭

클라는 델타를 받아 **누적 재구성**(cumulative reconstruction)한다 — `reset`→seen 비움, `enter`/`update`→seen.set, `exit`→seen.delete. 매 tick 전체를 받는 게 아니라 *변화를 쌓아* 가시 집합을 유지한다.

`delta` 검증이 이를 못 박는다 — 클라가 증분만 누적해 재구성한 가시 집합(위치 포함)이 *전체 스냅샷* 모드의 가시 집합과 **매 tick 전 클라 비트 동일**(288/288 셀, 불일치 0). 즉 **증분 ≡ 전체 스냅샷** — 인코딩만 다를 뿐 클라가 보는 것은 같다.

그 결과가 **변화량 비례 대역폭**이다. 핵심은 **무발신**(no-send): enter·exit·update 가 모두 비고 reset 도 아니면 *메시지 자체를 안 보낸다*. 그래서 *정지하면 대역폭이 0 으로 수렴*한다.

| | 전체 스냅샷 | 증분 |
|---|---|---|
| 이동 중 | 매 tick 전부 | 변화분만 |
| **정지 시** | 매 tick 전부(낭비) | **0** |

`bw`: 정지 후 꼬리 8 tick 증분 = 0. 대역폭이 *밀도*(0005~0006)가 아니라 *변화량*에 비례한다 — 실 MMO 처럼 대다수 엔터티가 간헐적으로만 움직이면 절감이 극적이다(§5 의 정직: 동시 이동 worst case 라 여기선 19~33%).

## 4. 핵심 개념 ③ — 직교 합성: 증분과 핸드오프가 서로 모른다

증분은 *직전 가시*에 의존한다. 그런데 권위 핸드오프(0006)로 세션이 존을 넘어 이주하면, 새 소유 존은 그 세션의 `prevSeen` 이 없다 — 증분 사슬이 끊긴다.

순진한 해법은 "핸드오프 때 `prevSeen` 도 새 존으로 옮긴다"이지만, 이는 증분 코드가 핸드오프 메시지에 가시 상태를 실어야 해(결합) 복잡해진다.

우아한 해법은 **직교 합성**(orthogonal composition) — *새 소유 존은 직전 가시를 모르므로 첫 tick 에 자동 reset(키프레임)*. 증분은 핸드오프를 *전혀 알 필요가 없다*(prevSeen 없음 → 자동 reset). 키프레임→델타의 표준 패턴이 분산 권위 이주에 *그대로* 맞아떨어진다.

이것이 직교성의 힘이다 — **증분(뷰 인코딩)과 핸드오프(권위)가 서로 무지한 채 합성된다.** 두 메커니즘이 서로의 내부를 모르고도 옳게 합쳐지므로, ②(증분≡전체)가 핸드오프 너머에서도 stale 0 이다. `prevSeen` 은 release/leave 때 세션과 함께 폐기되고 *옮겨지지 않는다*(새 존이 reset 으로 다시 세운다). 이 직교성은 0008 의 손실 복원(seq+keyframe)·0009 의 failover(승격+keyframe)에서 한 겹씩 더 쌓인다.

---

## 5. 핵심 개념 ④ — 손실 취약성: 누적의 대가

증분의 어두운 면 — **누적 재구성은 손실에 취약하다.** 델타 1개를 잃으면 클라 seen 이 *영구히* 어긋난다. 전체 스냅샷은 다음 tick 재전송으로 *자가 치유*했지만, 증분은 잃은 변화를 영영 못 메운다(다음 델타는 그 잃은 상태 *위에* 쌓이므로).

```
전체 스냅샷: 델타 유실 → 다음 tick 전체 재전송으로 자가 치유
증분:        델타 유실 → 영구 desync (잃은 변화가 영영 안 옴)
```

이 step 은 손실 0(행복 경로)에서만 증분을 본다 — *반응적 복원*(seq 로 유실 감지 → NAK → keyframe 재동기)이 선결이고, 그것이 0008 의 일이다. 증분이 손실에 취약해진 *지금*이 반응적 복원을 더할 적기다.

또한 증분은 **cross-zone 지연을 *줄이지 않는다*** — 같은 뷰 파이프라인을 탄다. 0006 의 ~3tick 지연은 증분에서도 그대로다. 증분은 *얼마나 보내는가*만 바꿀 뿐 *언제 보이는가*는 안 바꾼다(STATE 가 기대한 "지연 완화"는 증분 단독으론 안 옴 — 예측/보간이 선결).

## 6. 의외의 발견 (개념적 함의)

1. **세션 이주를 reset(키프레임)으로 다루면 증분과 핸드오프가 깔끔히 직교한다.** §4 의 핵심 — 키프레임→델타의 표준 패턴이 분산 권위 이주에 그대로 맞아떨어졌다. 두 메커니즘이 서로 무지한 채 합성.

2. **"동시 이동" 시나리오는 증분에 *불리한* worst case — 실제 MMO 는 정반대.** 전 클라가 30tick 내내 움직이면 절감이 ~25% 에 그치나, 증분의 *구조적* 이득은 "변화량 비례"(정지 꼬리에서 0). 실 오픈월드는 idle 비율이 높아 절감이 훨씬 크다. 더미의 25% 는 *바닥*이지 천장이 아니다.

3. **증분은 cross-zone 지연을 줄이지 않는다.** §5 — 증분은 대역폭만 바꾼다. 지연 완화는 클라 예측/보간 또는 ghost 채널 증분화가 필요(후속).

---

## 7. 개념적 한계 — 무엇을 *아직* 단순화로 남겼나

1. **증분도 행복 경로 — 손실 시 desync** — 누적이라 델타 1개 유실에 영구 desync(전체 스냅샷의 자가치유 상실). 반응적 복원(keyframe 재동기·NAK)이 선결(→ 0008).
2. **cross-zone 지연 완화는 *오지 않았다*** — 증분=대역폭만, 같은 뷰 파이프라인. 지연은 예측/보간의 일.
3. **존↔존 ghost 채널은 여전히 전체 스냅샷** — 클라 향 뷰만 증분화. ghost 증분화는 후속.
4. **절감률 = 시나리오 의존(동시 이동 worst case)·레코드 카운트=대역폭 프록시** — 수치는 "구조(변화량 비례·정지 0)"의 증거지 절대 절감률의 약속이 아니다.

이 한계들이 다음 step 들의 후보다. 가장 유력한 다음은 **전송 열화 아래 핸드오프 + 반응적 복원**이다.

---

## 8. 한 문단 정리

step-0007 은 가시를 *전체 스냅샷*에서 **증분(델타)** 으로 바꿨다 — 직전 가시 대비 enter/exit/update 만 보내고, 클라가 *누적 재구성*해 가시 집합을 복원한다(증분≡전체, 매 tick 288/288 비트 일치). 그 결과 **대역폭이 밀도가 아니라 변화량에 비례** — 정지하면 *무발신*으로 0 에 수렴한다(전체 스냅샷은 정지해도 매 tick 재전송). **키프레임(reset)↔델타**의 표준 쌍이 핵심이고, 세션이 존을 넘어 이주하면 새 존이 *자동 reset* 으로 재동기해 — **증분과 핸드오프가 서로 무지한 채 직교 합성**된다(키프레임 패턴이 권위 이주에 그대로 맞아떨어짐). 대가는 **손실 취약성** — 누적 사슬은 델타 1개 유실에 영구 desync(전체 스냅샷의 자가치유 상실)라, *반응적 복원*이 다음 선결이다. 지연 완화·ghost 증분화 같은 나머지 개념은 다음 step 의 추상으로 남겼다.
