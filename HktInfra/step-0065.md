# step-0065 — 프레즌스 보고 버스화: orch→PresenceService 보고를 point-to-point → 버스 토픽 (presenceReportBus)

> 직전: [step-0064](step-0064.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0064 가 프레즌스 박스(PresenceService)를 orch 에서 분리했지만, orch→PresenceService 의 전이 *보고*는 여전히 *point-to-point*(presenceAddr 명시 주소)였다 — orch 가 프레즌스 박스의 주소를 알아야 했다(0064 §9 한계·잔존 결합). 이 step 은 그 보고를 버스 토픽 `svc.presence.report` 로 올린다 — orch 가 프레즌스 박스 *주소를 모른다*(토픽만 안다·완전 decouple). 이로써 다중 orch·프레즌스 박스 failover 의 기반(주소 결합 제거)이 선다. 0016 이 *서비스* 결합을 버스로 끊은 것을 *코디네이션 보고 경로*에 적용. 닫는 조건: ⒜ `presenceReportBus=0` 이면 0064 비트 동일(point-to-point·reg 0) ⒝ ON 이면 orch presenceAddr 무지(null)·버스로 보고→presence 박스가 구독으로 수신(reports/발행 동일) ⒞ 다운스트림(presmon) 관측 ON==OFF(행동 보존·보고 경로만 교체) ⒟ 비-침습(minted 동일).

## 2. 메커니즘 — 보고 경로 버스화 (presenceReportBus OFF → baseline 비트 동일 = 회귀 0)

orch `_track(kind, consumer)` 에 버스 보고 분기를 더한다: `presenceBox && presenceReportBus && bus` 면 `svc.presence.report` 토픽에 `{kind, consumer}` 를 pub(주소 무지)·아니면 point-to-point(0064)·아니면 직접(0063). PresenceService.onMsg 는 point-to-point(`{type:'presence'}`)와 버스(`{type:'ev', topic:'svc.presence.report'}`) *둘 다* 수신해 같은 SSOT 갱신+발행. 토폴로지는 `presenceReportBus` ON 일 때만 `['svc.presence.report','presence']` 구독 + orch 에 `presenceAddr=null`(주소 무지)·`presenceReportBus=true` 배선.

`presenceReportBus=0` 이면 point-to-point(presenceAddr 명시)·구독 행 미추가 → 0064 와 동일. 닿는 박스: `orchestrator.js`(`_track` 버스 분기)·`svc-presence.js`(버스 보고 수신)·`topo-build.js`(구독·orch 배선). 순수 제어 평면·원장 권위 불변.

## 9. 의외의 발견 / 정직한 한계

- **주소 결합 제거가 failover 의 *전제*다**: 0064 의 point-to-point 보고는 orch 가 `presenceAddr` 라는 *고정 주소*를 알아야 했다 — 그 주소의 박스가 죽으면 orch 는 보고할 곳을 잃는다(SPOF). 보고를 토픽으로 올리면 orch 는 "누가 받는지" 모른 채 발행만 한다 → 프레즌스 박스가 죽고 다른 인스턴스가 같은 토픽을 구독하면 보고가 *자동 재라우팅*(0034 버스 failover 의 "진실 원천=구독자"). 즉 이 step 은 프레즌스 박스 failover 자체는 아니지만 *그 전제*(주소 무지)를 깐다.
- **양방향 수신이 마이그레이션을 무중단으로 만든다**: PresenceService 가 point-to-point 와 버스 보고를 *둘 다* 받게 둔 것은 단순 편의가 아니라 *무중단 전환* 패턴이다 — 같은 박스가 두 경로를 지원하므로, 보고 경로를 점진적으로(orch 별로) 버스로 옮겨도 SSOT 가 깨지지 않는다. 분산 시스템의 프로토콜 마이그레이션 정석(구·신 동시 지원→전환→구 제거).
- **decouple 의 3단 적용 — 서비스·발행·보고**: 0016 은 *서비스 호출*(가방/채팅)을 버스로 끊었고, 0060 은 *프레즌스 발행*(svc.presence)을 버스로 외재화했으며, 0065 는 *코디네이션 보고*(orch→presence)를 버스로 올렸다. 같은 원리(주소 대신 토픽)가 데이터 평면→관측 평면→제어 평면으로 번졌다 — 결합 제거가 계층을 가리지 않는다.
- **보고와 발행이 *다른* 토픽인 이유(정직한 구분)**: svc.presence.report(orch→presence·입력)와 svc.presence(presence→구독자·출력)는 별 토픽이다 — presence 박스가 *판정의 SSOT 게이트*이기 때문이다(보고를 받아 SSOT 갱신 *후* 발행). 한 토픽으로 합치면 보고와 발행이 구분 안 돼 구독자가 미가공 보고까지 받는다(SSOT 우회). 입력/출력 토픽 분리가 SSOT 의 단일 관문성을 지킨다. 단 현재 보고 발행자는 단일 orch — 다중 orch 시 보고에 epoch/순서 필요(비동기 결정론 §3 격차와 연결).
