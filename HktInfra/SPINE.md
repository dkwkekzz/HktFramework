# SPINE — 오픈월드 MMORPG 네트워크 인프라 큰 그림 (모든 step 작업 전 필독)

> 이 문서의 역할: **step 을 시작할 때 방향을 잡는다.** 상용 수준 오픈월드 MMORPG 의 목표 토폴로지(어디로 가는가) · 계층별 책임과 병목 제거 근거(왜 분리하는가) · 불변(무엇을 지키는가)을 한 장에 담는다.
> 방법론·규칙은 [CLAUDE.md](CLAUDE.md), 현재 위치·다음 가설은 [STATE.md](STATE.md), **각 박스를 무슨 도구로 어떻게 짓는가는 [TOOLS.md](TOOLS.md)**. 세부 설계는 여기 박지 않는다 — step 이 진행되며 이 그림의 박스를 하나씩 채우고, 결정된 사실은 STATE §4 로 떨어진다.
>
> **이 문서(SPINE)는 *목표 토폴로지*(어디로 가는가)다. 그 박스들이 *지금 어디까지 실제로 도는가*의 시각 전체도는 [SYSTEM.html](SYSTEM.html)** — 브라우저로 그냥 열면 액터·메시지 흐름·서버별 상태(작동/스텁/없음)를 한 장으로 본다(STATE.md 의 파생 시각 요약, step 마다 갱신).
>
> 핵심 한 줄: **한 프로세스가 모든 일을 하면 모든 일이 서로의 병목이다. 책임을 headless 서버로 분리하되 — 시뮬 tick 은 신성하게, 클라이언트는 내부를 모르게 — 그리고 모든 서버가 원격 환경에서 빌드·통신·검증되게 한다.**
>
> **이 시리즈가 완성시키려는 것 = *검증 가능한 네트워크 인프라*.** 토폴로지를 그리는 것이 목적이 아니라, 그 토폴로지의 *모든 서버가 headless 로 돌고 서로 완전히 통신하며 원격에서 E2E 로 검증되는* 것이 목적이다. 그림보다 `node verify.js` 의 ALL OK 가 우선한다.

## 1. 목표 토폴로지 — 완성됐을 때의 그림 (6계층)

```
                        클라이언트 (수만) — 단일 연결, 내부 토폴로지를 모른다
                           │ ① 인증·대기열                 │ ② 세션 티켓으로 접속 (이후 고정)
                  ┌────────▼─────────┐         ┌─────────▼──────────────────┐
 [엣지]           │  로그인/인증 서버    │         │  게이트웨이 군                │
                  │  계정·로그인큐·티켓   │         │  연결 종단·암호화·세션 라우팅    │
                  └────────┬─────────┘         └──┬─────────▲──────────┬───┘
                           │                intent│      뷰(AOI)│       │ 서비스 요청(가방·채팅…)
                  ┌────────▼─────────┐         ┌──▼──────────┴───┐  ┌──▼─────────────────────┐
 [코디네이션]      │ 세션/프레즌스        │◄───────►│  존(리전) 서버 군   │  │  게임 서비스 군            │
                  │ 오케스트레이터       │ 배치·    │  = 결정론 시뮬 VM    │  │  가방(인벤토리)·채팅·길드·   │
                  │ ("누가 어디에" SSOT) │ 핸드오프  │  공간분할·AOI·조정   │  │  거래소·우편·랭킹 (tick 무관)│
                  └────────┬─────────┘         └──┬─────▲────────┘  └──┬─────────────────────┘
                           │                      │     │ 인스턴스(던전) 서버 — 수요 따라 spawn/despawn
 [버스]      ══════════════╪══════════════════════╪═ 이벤트 버스 (pub/sub — 서버간 직접 결합 제거) ═╪═════
                           │                      │                       │
                  ┌────────▼──────────────────────▼───────────────────────▼───┐
 [데이터]         │  캐시(핫: 세션·가방·시세)  →  게임 DB · 계정 DB  (write-behind)  │
                  └───────────────────────────────────────────────────────────┘
```

- **같은 화살표는 같은 형식**: 클라→존은 **intent 업스트림**, 존→클라는 **읽기전용 뷰 다운스트림** — 게이트웨이는 이를 *중계*할 뿐 변형하지 않는다.
- **모든 박스 = headless 서버**: 위 그림의 어떤 박스도 GUI·엔진 런타임·특정 머신에 묶이지 않는다. 각각 원격에서 한 줄로 띄워지고, 서로 직렬화 가능한 메시지로만 통신하며, headless 하니스로 검증된다.
- 오늘은 이 박스 전부가 **한 프로세스(headless 더미 프로토타입)** 안에 산다 — HktInfra 는 그걸 위 그림으로 풀어내, 각 박스를 *원격에서 도는 독립 headless 서버*로 하나씩 세우고 검증한다. 토대 netcode 원칙(서버 권위 · 결정론 코어 · 읽기전용 뷰)은 무엇이 시뮬을 돌리든 불변이다(§5).

## 2. 계층별 책임 — 무엇을 분리하고, 어떤 병목이 사라지는가

| 계층 | 서버 | 책임 | 분리로 제거되는 병목 |
|---|---|---|---|
| 엣지 | **로그인/인증** | 계정 검증 · 로그인 대기열 · 세션 티켓 발급 | 접속 폭주(오픈/이벤트)가 월드에 안 닿는다 — 대기열은 엣지에서 끝난다 |
| 엣지 | **게이트웨이** | 수만 소켓 종단 · 암호화 · 세션→존/서비스 라우팅 | 소켓 관리 CPU 가 시뮬과 분리. 존 이동·서버 재배치에도 클라 재연결 0 (은닉) |
| 월드 | **존(리전) 서버** | 결정론 시뮬 *전용* — 공간분할 · AOI · 예측/조정 · 핸드오프 | tick 안에서 I/O·트랜잭션·팬아웃 0 — 시뮬 헤드룸이 곧 동접 |
| 월드 | **인스턴스 서버** | 던전/매치 일회성 시뮬 | 수요 탄력(spawn/despawn) — 오픈월드 존과 수명주기 분리 |
| 서비스 | **가방(인벤토리)** | 아이템 원장 트랜잭션 — 이동·거래·복제(dupe) 방지 | 아이템 연산이 존 tick 을 안 막고, *존을 넘는 거래*가 존간 결합 없이 성립 |
| 서비스 | **채팅** | 채널 팬아웃(전체/지역/귓속말) | 대규모 브로드캐스트 대역이 시뮬 대역과 분리 |
| 서비스 | **길드/소셜 · 거래소 · 우편 · 랭킹** | 비-시뮬 게임 상태 | 동일 — tick 과 무관한 책임은 전부 이 줄로 |
| 버스 | **이벤트 버스** | 서버간 pub/sub(구독 기반 전파) | N×N 직접 RPC 그물 제거 — 새 소비자 추가가 발행자 무수정 |
| 코디네이션 | **세션/프레즌스** | "플레이어 X 는 어느 게이트웨이·어느 존" 의 SSOT | 귓속말·파티·핸드오프의 라우팅 조회가 한 곳 |
| 코디네이션 | **오케스트레이터** | 존 배치 · 부하 분산 · 인스턴스 spawn | 정적 배치 한계 제거 — 어떤 단일 서버도 영구 중심이 아니다 |
| 데이터 | **캐시** | 핫 데이터(세션·가방·시세) | 매 조회가 DB 직행하지 않는다 |
| 데이터 | **게임/계정 DB** | 영속 진실 — write-behind 큐로 비동기 기록 | 동기 디스크 I/O 가 *어떤* 서버 tick 에도 없다. 세계가 세션보다 오래 산다 |

> 분리의 판정 기준은 하나다: **그 일이 존 시뮬 tick 과 같은 박자로 돌아야 하는가?** 아니라면(인증·아이템 트랜잭션·채팅 팬아웃·디스크 기록) 존 밖으로 — 비동기 경유.
>
> **이 판정 기준이 그대로 도구 선택 기준이 된다** ([TOOLS.md](TOOLS.md)): tick 동기는 결정론 때문에 C++ 로 고정(협상 불가), 그 외는 원격에서 빌드·검증 가능한 도구(Go·Node·컨테이너). 단 *시뮬도 예외 아님* — 언어만 C++ 일 뿐, 그 *검증*은 여전히 UE 없이 headless 로 가능해야 한다(§5 ⑤). 계층별 스택·데이터 3분할(월드=intent 로그 / 가방=트랜잭션 SQL / Redis=휘발)은 TOOLS.

## 3. 씨앗 매핑 — 오늘의 헤드리스 프로토타입에서 미래의 분산 서버로

현 HktInfra 프로토타입(`engine/` + `src/`)의 headless 박스가 각 미래 서버의 *씨앗*이다. step 에서 검증하며 이 표를 갱신한다.

> **씨앗 = 같은 *계약*의 첫 구현이지, 임시 코드가 아니다.** 더미 서버(헤드리스 Node)는 미래 서버의 *알고리즘·메시지 계약*을 원격에서 도는 형태로 재현한다. 그래서 UE 는 더미·원격 검증 단계에 **0** 이고 — UE 는 *제거*가 아니라 *연기*된다 — 풀-UE 클라 통합과 (선택적) C++ 시뮬 정교화에서만 복귀한다. 표의 이름은 "오늘 이 박스가 어디 사는가"의 포인터다.

| 미래 박스 | 오늘의 헤드리스 씨앗 (HktInfra 프로토타입) |
|---|---|
| 로그인/인증 서버 | `engine` `Login` 스텁 — 일회성 티켓 발급·은닉 |
| 게이트웨이 | `engine` `Net` 라우팅 + host 태그 프로세스 경계 |
| 존 서버의 심장 | 동결 `ISimCore` 뒤 더미 시뮬(`engine`) — 인터페이스 무변경의 최후 C++ 교체 대상 |
| AOI/뷰 | `EntityZone` — 위치 맵 + 반경 R AOI + 증분(enter/exit/update) |
| 결정론 복제/조정 | 추종자 존(입력열 미러 탭) — 상태 전송 0바이트로 권위와 같은 해시 수렴 |
| 공간 분할/핸드오프 | 존 2개 경계 ghost 상호 구독 + 권위 release+acquire 쌍 거래 + ack/재전송 복원 |
| 이벤트 버스 | `engine` `Net` 전송 substrate(지연·손실·재정렬·신뢰성) → NATS/Redpanda 로 현실화 |
| 데이터 계층 | (미착수) intent 로그(event sourcing) + 주기 스냅샷 |

> **동결된 Sim 인터페이스(`ISimCore`)가 곧 분리의 이음새(seam)** — 더미(헤드리스) 구현을 원격 서비스/C++ 호스트로 갈아끼우는 지점이다. 오늘은 더미 서버가 그 뒤에 서서 전체 인프라를 원격 E2E 로 세우고, C++ 정교화는 인터페이스 무변경의 *최후 교체*다 ([TOOLS.md](TOOLS.md) §4). 이 순서를 뒤집어 C++ 를 먼저 지으면 원격 검증 루프가 끊긴다 — 그러므로 인터페이스 우선, headless 더미로 전 인프라 검증, C++ 는 마지막.

## 4. 데이터 흐름 — 네 경로뿐

1. **월드 업스트림 = intent**: 클라 → 게이트웨이 → 존. 세계 상태의 유일한 쓰기 경로.
2. **월드 다운스트림 = 읽기전용 뷰**: 존 → 게이트웨이 → 클라, AOI 범위만. 복제의 기본은 *재현*(결정론 덕에 intent 로그만으로 동일 상태 재구성) — 전체 스냅샷은 late-join·복구의 최후 수단.
3. **서비스 경로 = 요청/응답**: 클라(게이트웨이 경유) 또는 존 → 가방·채팅 등. 시뮬 tick 과 비동기.
4. **서버간 = 이벤트 버스**: 발행/구독. 서버가 서로의 주소·내부를 모른다.

클라이언트의 단일 게이트웨이 연결이 1·2·3 을 다중화한다 — 클라는 어떤 내부 주소도 모른다. 네 경로 모두 *직렬화 가능한 메시지 경계*(transport seam)를 통과하므로, 인프로세스 더미든 원격 분산 서버든 같은 검증 하니스가 적용된다.

## 5. 불변 5항 — 매 step 이 통과해야 할 척추 체크

verify 4기둥([CLAUDE.md](CLAUDE.md) — 측정)과 별개로, *설계*가 답해야 할 다섯 질문:

1. **신성한 tick** — 이 step 이 존 시뮬 tick 안에 시뮬 외 작업(동기 I/O·인증·트랜잭션·팬아웃)을 넣지 않았는가? §2 의 판정 기준을 통과했는가?
2. **결정론 코어** — 세계 상태 변경이 여전히 intent→결정론 시뮬 코어 경로 *하나*인가? (복제=재현 가능성 유지 — 시드·로그 동일이면 해시 동일)
3. **권위 단일 소유** — 모든 상태 조각(시뮬 엔티티·아이템·세션)의 *쓰기* 권위가 정확히 한 곳인가? 권위/엔티티 이동은 쌍 거래(release+acquire / 트랜잭션)인가? (공백도 이중쓰기도 없음)
4. **은닉·단일 연결** — 클라는 게이트웨이 하나만 알고, 서버끼리는 버스/명시 인터페이스로만 통신하는가? (타 서버 내부·DB 직접 접근 = 결합 = 위반)
5. **headless·원격 검증** — 이 step 이 더한 박스가 *시뮬을 포함해* UE/GUI 없이 빌드·실행되고, 원격(이 환경/CI)에서 한 줄로 띄워 서로 통신하며, `node verify.js` 로 동작이 수치 증명되는가? (어떤 박스도 로컬 엔진 빌드·특정 머신에 묶이면 위반)

하나라도 "아니오"면 그 step 은 척추에서 벗어난 것 — 재설계한다.

## 6. 6계층과 진행 — [STATE.md](STATE.md) §5 진행 현황의 정의

| # | 계층 | 박스 |
|---|---|---|
| 1 | 엣지 | 로그인/인증 · 게이트웨이 |
| 2 | 월드 | 존(리전) · 인스턴스 — 공간분할·AOI·조정·핸드오프 |
| 3 | 게임 서비스 | 가방 · 채팅 · 길드 · 거래소 · 우편 · 랭킹 |
| 4 | 버스 | 이벤트 버스 (서버간 pub/sub) |
| 5 | 코디네이션 | 세션/프레즌스 · 오케스트레이터 |
| 6 | 데이터 | 캐시 · 게임/계정 DB · write-behind |

어느 박스를 어떤 순서로 채우는가의 권위는 [STATE.md](STATE.md) §2(다음 가설)·§3(열린 격차)다. 모든 박스의 완성 기준은 동일하다 — *headless 로 돌고, 서로 완전히 통신하며, 원격에서 검증된다*(§5 ⑤).

> **진행은 단계적(너비→고도화)**: 1차는 위 표 *모든 박스*를 기본 통신 선까지, 심화는 2차. 단계 판정은 `infra-review`(너비 지도 `reviews/progress/`), 다음 조각은 [STATE.md](STATE.md) §2.
