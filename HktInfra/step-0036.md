# step-0036 — 버스 failover *결과 경로 무손실*: producer replay 로 gap desync 0

> 직전: [step-0035](step-0035.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

step-0034 는 버스 crash 후 *재구독*으로 라우팅을 복구했지만, **crash gap 에 떨군 `svc.item.out` 결과**(원장엔 적용됐으나 클라가 못 받은 것)는 영구 손실로 남겼다 — 클라 belief 가 원장보다 뒤처져 `itemDesync ≥ 0`(0034 §9). 이 step 의 한 조각: **가방(producer)이 발신 결과를 보관했다가 버스 복구 시 재발행**(0023 홉 신뢰·0025 give-resend 의 *버스 판*) → 뒤처진 클라가 따라잡아 `itemDesync → 0`. SPINE §6 의 **버스** 박스(요청/결과 경로 신뢰성)를 채운다.

닫는 조건: ⒜ `busResend` OFF → 0035 비트 동일(reg 0) ⒝ recover(재구독만) = desync 잔존(대조군) vs resend(재발행 ON) = desync 0 ⒞ 재발행이 원장 비-침습(보존·정합) ⒟ spine 36-step 사슬.

## 2. 메커니즘 — 결과 producer replay (OFF 플래그 `busResend`)

**왜 producer 인가**: 버스는 crash 후 *살아 돌아온 새 박스*(라우팅 RAM 만 들고 영속 0 — 0034 의 핵심)다. 그래서 crash gap 동안(라우팅 빈 채) 도착한 pub 은 어디에도 버퍼되지 않고 사라진다 — 버스 자신은 그 gap 메시지를 **못 메운다**. 메울 수 있는 건 crash 를 살아남은 **진실 원천 = producer(가방)**뿐이다. 이는 0023(저널 홉 NAK 재전송)·0025(클라 give-resend)와 같은 원리의 *버스 판*: at-least-once 전송 + 멱등 소비 = effectively-once.

**한 조각**(닿는 박스 `svc-inventory.js`·`topology.js` 둘):
- `InventoryService._out(msg)`: `busResend` ON 이면 발신 결과를 `outBuffer` 에 push(보관). 발신 자체는 무변경 → OFF 면 push 0 = 0035 비트 동일.
- `InventoryService.resendOut()`: 보관 결과를 `svc.item.out` 에 다시 pub. 버스 복구(재구독) *직후* 토폴로지가 트리거.
- `topology.js`: `busRestart.renegAt` 의 재구독 sub 발신 **직후** `inventory.resendOut()` 호출(같은 tick·FIFO → 다음 step 에서 bus 가 sub→pub 순 처리 = 라우팅 복구 후 fan-out). `busResend` OFF 면 호출돼도 즉시 반환.

**왜 consumer dedup 불요**: 클라 belief 는 `Set` — `item_result(pickup)` → `items.add`, `give` → `items.delete`, `item_recv` → `items.add` 전부 **멱등**. 재배달된(이미 받은) 결과는 belief 를 안 바꾸고, gap 에 떨군 결과만 belief 를 원장으로 끌어올린다. 그래서 (publisher,seq) 키 dedup 없이도 정확. 재발행은 *읽기 전용 fan-out*(원장 비-침습)이라 보존·정합 불변.

**왜 desync 의 원인이 결과(요청 아님)인가**(측정으로 확정): crash gap 은 `svc.item`(요청)과 `svc.item.out`(결과)을 둘 다 끊지만 —
- *요청* 드롭 → mint 자체가 안 일어남(원장에도 없고 클라도 모름) → **양측 일치 = desync 0 기여**(단 base 보다 mint 적음: 51→33).
- *결과* 드롭 → mint 는 됐는데 클라가 결과를 못 받음 → 클라 belief < 원장 = **desync**. 측정상 6 desync 전부 "belief < 원장"(behind) → 결과 드롭이 유일 원인. 따라서 결과 재발행만으로 desync 0 달성.

## 4. 척추 체크 5항

① **신성한 tick**: 결과 보관·재발행은 가방의 *순수 반응형/제어 평면*(존 tick 밖·net.log 비-기여) — 존 시뮬 비-침습. ② **결정론 코어**: 재발행은 제어 평면 트리거(시드 무관 상수 위치)·세계 상태 쓰기 경로 무변경. ③ **권위 단일 소유**: 재발행은 원장을 안 건드림(읽기전용 결과 스트림) — 소유자=1 불변. ④ **은닉·단일 연결**: 클라는 여전히 gateway 만 안다(결과는 gateway 가 중계). ⑤ **headless·원격 검증**: Node `run.js` 로 수치 증명·멀티프로세스 E2E 영향 없음(busResend 인프로세스 가설 모드 — cluster 무수정).

## 9. 의외의 발견 / 정직한 한계

- **desync 원인은 결과 드롭이지 요청 드롭이 아니다**: 직관은 "gap 의 *요청*이 떨궈져 원장이 뒤처진다"였으나(0034 §9 도 그렇게 적음), 측정상 6 desync 전부 *belief < 원장*(클라가 뒤처짐)이었다 — 즉 mint 는 됐는데 *결과*가 안 닿은 것. 요청 드롭은 mint 자체를 막아 양측 모두 모르므로 desync 에 기여 안 한다. 그래서 **결과 경로 재발행만으로 desync 0** 이 달성된다(요청 경로는 별도 — 후속).
- **outBuffer 무계(v1)**: 발신 결과를 전부 보관하고 복구 시 전량 재발행한다(0017 무계 저널 → 0018 스냅샷 압축의 선례와 동형). 유계 슬라이딩 창(gap 만 덮는 K — 0032 wfWindow 패턴)은 후속. 무계라 audit/ranking 이 재발행분을 중복 수신(이 모드는 그 토픽 수를 단언하지 않음 — desync·원장만 단언).
- **give 결과 ahead 케이스는 미측정**: 측정 시드들에선 give 결과 드롭(sender belief > 원장 = ahead)이 0 이었다(전부 pickup 결과 behind). give ahead 복구는 0025 give-resend 영역(클라 측)이라 이 결과-재발행과 직교 — 결합 검증은 후속.
