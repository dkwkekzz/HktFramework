# step-0119 — 거래소↔가방 cancel/expire 반환 (exchInventory leg 3 · escrow→판매자 실물 반환)

> 직전: [step-0118](step-0118.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0117 인출+0118 입금으로 list→buy 실물 거래는 닫혔으나, *미체결* 매물의 종결(취소 0107·만료 0114)은 거래소 회계만 굴리고 escrow custody 아이템이 판매자에게 안 돌아왔다. 반환 레그(escrow→seller)를 더해 escrow 의 *모든 출구*(체결→구매자·취소/만료→판매자)가 실물 이동을 동반하는가? 닫는 조건: exchInventory ON 이면 취소/만료된 itemId 가 판매자 가방 소유·escrow 0·minted 불변, OFF 면 give 0 = 0118 비트 동일(reg).

## 2. 메커니즘 — escrow→판매자 실물 반환 (exchInventory OFF → baseline 비트 동일 = 회귀 0)

- **exchCancel 반환 레그**: 취소(delete+cancelled++ +returned) 직후 `_custody(l.itemId, 'escrow', p.seller)`.
- **exchSweep 만료 반환 레그**: 만료(delete+expired++ +returned) 직후 `_custody(l.itemId, 'escrow', l.seller)`.
- **escrow 모든 출구 실물화**: 0117 인출(seller→escrow) 후 escrow 가 닫히는 세 경로 — 체결(escrow→buyer·0118)·취소(escrow→seller·0119)·만료(escrow→seller·0119) — 가 모두 가방 give 를 동반. 미체결 아이템이 escrow 에 영영 묶이지 않는다.
- **권위 = 가방**: 반환도 가방이 권위로 수행(escrow 보유 검사·release+acquire 쌍). 거래소는 요청만.
- **회귀 0**: exchInventory OFF(또는 itemId 부재)면 give 분기 휴면 = 0118 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 거래소↔가방 결합이 *escrow 를 중개 소유자로 둔 닫힌 장부*로 완성됐다 — escrow 의 입구(인출 seller→escrow·0117)와 세 출구(체결→buyer·취소→seller·만료→seller)가 모두 같은 give 연산이고, 매 순간 모든 아이템이 정확히 한 소유자(seller/escrow/buyer)를 가진다(가방 권위·minted 불변). 거래소 보존식(listed==open+sold+cancelled+expired)이 *가방 원장의 소유자 분포*와 짝을 이룬다 — 두 서비스가 결합해도 권위 단일 소유가 깨지지 않음.
- **한계**: give 는 여전히 *낙관적*(fire-and-forget) — escrow 가 (가방 손실로) 아이템을 안 가지면 give 실패하지만 거래소 종결은 성립(2-서비스 원자성/saga 보상은 후속). give 결과(item_result)를 거래소가 안 들어 실패를 모른다. 2-서비스 보존 불변(가방 escrow 소유 수 == 거래소 open)의 명시적 단언은 후속 step.
