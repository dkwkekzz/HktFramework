# step-0040 — 요청 replay 버퍼 *자기-크기조정* (ack 기반 가지치기·busAck)

> 직전: [step-0039](step-0039.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0039 는 0036/0037 의 무계 replay 버퍼를 *고정 K 슬라이딩 창*(`busWindow`)으로 유계화했다 — 단, 그 §9 가 정직하게 남긴 한계: **고정 K 는 *최대 예상 gap(다운타임×발신율)* 을 사전 추정해야 한다** — 작게 잡으면 gap 초과분 손실, 크게 잡으면 메모리 낭비. 운영자가 gap 을 *모르면* 안전한 K 를 못 고른다. 이 step 의 질문: *K 추정 없이* 버퍼를 유계로 유지하면서 무손실일 수 있는가? **소비자 ack 가지치기**로 답한다 — 가방이 처리한 reqId 를 통보하면 게이트웨이가 ack 된 요청을 버퍼에서 제거해, 버퍼엔 *미-ack(in-flight)* 요청만 남는다(자기-크기조정). SPINE §6 계층 4(이벤트 버스)의 *흐름 제어* 를 채우고 0039 §9 를 닫는다.

닫는 조건: ① `busAck=0`(기본) → 0039 비트 동일(reg 0) ② ack → minted==base·desync 0(K 추정 0 으로 무손실) ③ 미-튜닝 고정 K(<gap) 는 손실(대조) ④ 버퍼 peak 가 *가동 길이 무관*(무계는 ∝발신 수) + quiescent 면 idle drain.

## 2. 메커니즘 — ack 워터마크 가지치기 (플래그 `busAck`; 0 → 0039 비트 동일 = 회귀 0)

- **소비자 ack (가방)**: `svc.item` 을 받을 때마다(reqId 실린 경우) `svc.item.ack {reqId}` 발행. *dedup 으로 폐기하는 재발행분도 ack 한다* — 그래야 ack 손실로 안 지워진 `inBuffer` 항목이 재발행→재-ack 되어 끝내 가지쳐진다(수렴).
- **producer 가지치기 (게이트웨이)**: ack 수신 시 `inAcked = max(inAcked, reqId)`(단조 워터마크), 그 후 `inBuffer` front 가 `reqId ≤ inAcked` 인 동안 `shift`(O(가지친 수)). `inBuffer` 는 inSeq 순서라 front 가 최소 reqId → 미-ack(in-flight) 요청만 남는다.
- **자동 크기조정**: 정상 구간엔 ack 가 흘러 버퍼가 0 으로 drain. gap 구간(버스 crash)엔 ack 도 끊겨 버퍼가 gap 만큼 *자동 성장* → 복구 replay 가 정확히 그만큼 덮어 무손실. **K 사전 추정 불필요**.
- **OFF**: `busAck=0` 이면 ack 발행 0·가지치기 0·`svc.item.ack` 구독 미추가 → 토폴로지·net.log 0039 비트 동일. `busResendReq` 전제(reqId·inBuffer 필요). 배선은 `topo-build.js`(버스 ON 시만). 존 tick 밖 순수 제어 평면(신성한 tick 보존).

## 9. 의외의 발견 / 정직한 한계

- **ack peak(48)는 완벽-튜닝 고정 K(=gap 18)보다 크다**: ack 도 gap 에 끊기므로, 버퍼는 *gap 요청* 뿐 아니라 *가방이 처리했으나 ack 미반환된 in-flight 백로그*까지 잡는다(crash 시점 backlog ≈30 + gap 18). 따라서 ack-가지치기는 메모리를 *최소화* 하지 않는다 — 완벽히 튜닝된 고정 K 가 더 작다. ack 가 주는 것은 *다른* 이점: ⒜ K 추정 불필요(어떤 gap 도 자동 커버) ⒝ idle drain(quiescent 면 0) ⒞ peak 가 *가동 길이 무관*(in-flight 상한·∝발신 수 아님). 즉 "가장 작은 버퍼"가 아니라 "튜닝 없이 가동-길이에 독립적으로 유계인 버퍼".
- **정직한 한계**: ⒜ *결과 경로* outBuffer(0036)는 여전히 고정 `busWindow` — ack-가지치기의 결과판(게이트웨이→가방 결과 ack)은 후속. ⒝ `seenReqs`(가방 dedup 집합)는 여전히 무계 성장 — ack 로 게이트웨이는 가지쳐도 가방은 reqId 이력을 못 버린다(워터마크 기반 seenReqs 유계화는 별도 조각). ⒞ give 요청×result-ahead 결합(0037/0039 §9)은 미해소.
