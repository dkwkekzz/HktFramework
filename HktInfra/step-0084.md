# step-0084 — 증분 가입/탈퇴 + 멤버십 변경 발행(partyChange·svc.party.changed)

> 직전: [step-0083](step-0083.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0075 의 PartyService 는 멤버십을 `partyCreate`(*전체 목록 덮어쓰기*)로만 갱신했다 — 한 명 가입/탈퇴에도 전체 목록을 다시 보내야 하고, 변경이 *관측 불가*(누가 언제 들고 났는지 스트림 없음·0075 §9). 멤버십을 *증분 델타*로 갱신하고 그 변경을 버스로 노출해, 발행자 무수정 소비자(채팅·랭킹·감사)가 반응하게 할 수 있는가? SPINE 계층3(길드/소셜) 멤버십 변경 스트림.

## 2. 메커니즘 — 증분 델타 + 변경 발행 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-party.js`): 기존 `partyCreate`(전체 set·reg 보존) 옆에
- `partyJoin{partyId, member}` — 멤버 추가(미존재 파티는 새로 연다·이미 있으면 멱등 no-op). `joins++`.
- `partyLeave{partyId, member}` — 멤버 제거(없으면 멱등 no-op). `leaves++`.
- 실제 변경 시에만 `_publishChange(partyId, kind, member)` → `{type:'pub', topic:'svc.party.changed', ev:{partyId,kind,member}}` 를 bus 로(`published++`). no-op 변경은 발행 안 함(멱등).

0082 failedPublish(전달 실패 발행)·0060 presencePublish 의 *멤버십 변경* 판 — 상태 변경을 토픽으로 노출. audit 는 spec·코드 무변경, 구독 행 `['svc.party.changed','audit']` 하나만 추가돼 가입/탈퇴 스트림을 본다. `partyChange` OFF·증분 명령 미주입이면 발행 0·구독 행 미추가·증분 핸들러 휴면 = 0083 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 증분 명령과 발행이 자연히 짝을 이룬다 — *실제 변경*이 일어난 델타만 발행(멱등 no-op 가입/탈퇴는 침묵)하므로, 발행 스트림이 곧 멤버십의 *진짜 변경 이력*이다. 이는 event sourcing 의 씨앗(svc.party.changed 가 곧 멤버십 저널의 변경 이벤트).
- **한계**: 멤버십은 여전히 *휘발*(in-memory) — PartyService crash 시 결성·가입/탈퇴 전부 소실(영속 0). svc.party.changed 스트림을 저널로 모아 crash→replay reconstruct(0017 가방·0021 채팅 영속의 파티 판)가 후속. 또한 partyCreate(전체 set)와 partyJoin/Leave(델타)가 공존 — 둘의 정합(create 후 동일 멤버 join 멱등)은 보장되나, 변경 발행은 *델타 명령만*(create 는 발행 안 함) — create 도 변경으로 발행할지는 의미론 선택(현재 결성은 발행 0).
