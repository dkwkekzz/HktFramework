# step-0034 — 버스 failover: 구독 재협상으로 라우팅 복구

> 직전: [step-0033](step-0033.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0016 ServiceBus 는 *단일 박스·영속 0* 이라 죽으면 서비스 경로가 단절되는 새 단일점이었다(STATE §3). 0033 이 *동적 구독/해지*(런타임 sub/unsub)를 깔았으니, 이제 그것을 써서 **버스 failover** 를 만든다: 버스가 죽고 routing 이 사라져도 소비자들이 *재구독*(재협상)하면 서비스 경로가 복원되는가? 핵심 통찰을 검증한다 — **버스는 *파생 상태*(라우팅 테이블)만 들고 진실 원천은 *소비자*다. 그래서 버스 failover 는 버스 내부 영속(저널/스냅샷) 없이도, 소비자가 (같은 주소의) 새 버스에 sub 를 재발신하면 라우팅이 재구성된다(이력 replay 불필요).**

채우는 박스/계약: **이벤트 버스(계층 4)** 의 failover. 닫는 조건: 4기둥(회귀 0·E2E 동치·신성한 tick·가설) + 척추 5항.

## 2. 메커니즘 — crash + 재협상 (busRestart OFF → 0033 비트 동일 = 회귀 0)

- **`svc-bus.js`**: `crash()` → `this.topics = new Map()`(라우팅 테이블 비움 = 서비스 경로 단절·이후 pub 전부 unrouted). 버스는 *파생 상태*(누가 무엇을 구독하나)만 들고 *이력은 0* 이라, crash 가 비우는 것은 routing 뿐 — 복구는 버스 내부가 아니라 *소비자의 재구독*으로 일어난다. 회계(publishes/deliveries…)는 누적 totals 라 유지(외부 관찰자 audit·소비자 ranking 으로 복구 측정).
- **`topology.js`**: `busSubs` = 정적 subs spec(재협상 원천 — "소비자가 무엇을 구독했나"). run 루프 트리거 `busRestart={at,renegAt}`: `at` 에 `bus.crash()`, `renegAt` 에 *각 소비자가 재구독*(`busSubs` 의 `[topic,addr]` 마다 `net.send(addr,'bus',{type:'sub',topic})` — 0033 동적 sub 의 재협상 용례). `renegAt` 없으면 재협상 0 = 영구 단절(대조군).
  - **발행자 무수정**: 버스가 *같은 주소*('bus')에서 재시작(인프로세스 crash 모델 — inventory/chat 의 crash 와 동형)하므로 gateway/inventory/chat/ranking 은 'bus' 로 계속 발신 — 발행자 코드 0 수정.
- **OFF 경로**: `busRestart` 미제공 → `crash()` 0회 → 0033 비트 동일. 멀티프로세스 E2E 는 `busRestart` 를 안 주므로 **`cluster.js` 무수정**.

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

- **회귀 0 (reg)**: busRestart OFF → 0033 net-core 와 **25/25 비트 동일**.
- **가설 (busfail)**: `svc.item.out`(audit·ranking 공동 구독) 측정. bus.crash(@12) → 재협상(@14, 정적 subs 재발신). 3런 비교 — 기준선(crash 0)·crash만(영구 단절·대조군)·crash+재협상(복구).

  | seed | A0 base | A_crashOnly | A_recover | ranking R0/Rc/Rr | bus subN base/recov/crashO | 원장 valid | gap(desync) r/c |
  |---|---|---|---|---|---|---|---|
  | 42 | 60 | 6 | 30 | 60/6/27 | 3/3/0 | 예 | 6/6 |
  | 7 | 60 | 6 | 30 | 57/6/27 | 3/3/0 | 예 | 6/6 |
  | 1234 | 60 | 6 | 30 | 60/6/28 | 3/3/0 | 예 | 6/6 |
  | 99 | 60 | 6 | 30 | 59/6/27 | 3/3/0 | 예 | 6/6 |
  | 2026 | 60 | 6 | 30 | 59/6/29 | 3/3/0 | 예 | 6/6 |

  - **crash 단절**: crashOnly 는 audit·ranking 둘 다 crash 후 수신 멈춤(A 60→6·R 60→6), 라우팅 구독자 수 0(`subNc`=0 = 서비스 경로 영구 단절·버스 단일점의 대가).
  - **재협상 복구**: recover 는 routing 재구성(`subNr`=3 == 기준선 `subN0`=3) → 팬아웃 재개(A 6→30·R 6→27). re-sub 가 0033 동적 sub 그대로.
  - **gap 만 손실**: A_recover(30) < A0(60) — crash~재협상 사이 발행분은 at-most-once 손실(버스 이력 0). 복구는 *라우팅*을 되살릴 뿐 떨군 메시지를 메우지 않는다.
  - **원장 무손상**: itemConserved && ledgerConsistent (recover·crashOnly 둘 다) — 버스 failover 가 권위 원장을 *오염*시키지 않는다.
- **E2E 동치**: busRestart 미주입 → 멀티프로세스 = 인프로세스 비트 동일(0033 그대로). `node run.js` **19모드 ALL OK** · spine **34-step 사슬**.

## 4. 척추 체크 5항

① **신성한 tick**: 버스 `onTick` 0(순수 반응형) — crash/재협상은 존 시뮬 tick 밖 제어 평면. 존 비-침습(reg). ② **결정론 코어**: 세계 쓰기 경로 불변. crash/sub 재발신은 정규 `net.send`(시드 로그) → 전 시드 동일 수치. ③ **권위 단일 소유**: 버스는 라우팅(파생)만 — 원장 권위는 가방. failover 가 보존/정합 유지(소유자 수 무영향). ④ **은닉·단일 연결**: 클라 와이어 불변(failover 는 서버간/제어 평면 경계·비가시). 발행자는 같은 'bus' 주소라 무수정. ⑤ **headless·원격 검증**: `node run.js` 로 수치 증명·E2E 비트 동일·UE 0.

## 9. 의외의 발견 / 정직한 한계

- **버스 failover 의 손실은 *두 종류*다 — 관찰 미스와 요청 드롭**. svc.item.out(결과 스트림 → ranking/audit) 손실은 *관찰 미스*(읽기 모델은 내구 저널에서 나중에 reconstruct 가능 — 0020 패턴 → 결과적 일관). 그러나 svc.item(*요청* 스트림 → inventory)도 버스를 지나므로(0016 토폴로지: gateway 가 svc.item 발행), crash gap 의 in-flight 요청이 떨궈지면 그 item op 은 원장에 안 닿는다 → **itemDesync=6**(클라 belief 와 격차). 이는 *손상*이 아니라 *손실*이다 — 원장은 보존·정합을 유지(dupe 0·conserved)하되 떨군 op 만큼 적게 반영. 재협상은 *라우팅*을 복구할 뿐 떨군 메시지를 메우지 않는다(reneg 가 악화시키지도 않음 — dR ≤ dC).
- **요청 경로 무손실은 후속(홉 신뢰의 버스 판)**. desync 0 인 무손실 버스 failover 는 (a) 버스 라우팅·in-flight 영속 또는 (b) 발행자측 재발신(0025 give-resend·0023 홉 NAK 의 버스 판)이 추가로 필요 — 이 step 은 *재협상으로 라우팅을 복구하는* 토대만 깐다. STATE §2 ⒝ 본체(라우팅 영속·이력 replay)로 전가.
- **crash 시점이 desync 를 안 바꾼다(=6 고정)**: 활성 item-op 구간 어디서 crash 해도 떨구는 in-flight give 집합이 구조적으로 6 — 버스가 요청 경로의 임계 substrate 임을 보인다(요청이 활동 내내 흐름). quiescent crash(활동 후)는 desync 0 이나 복구를 보일 결과 스트림이 없다 — 그래서 활성 구간 crash + 정직한 gap 보고를 택했다.
