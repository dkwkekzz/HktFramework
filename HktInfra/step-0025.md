# step-0025 — in-flight give 손실 복구 (클라 give-resend 로 복구 원장을 belief 로 재수렴)

> 직전: [step-0024](step-0024.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0023~0024 는 *전송 손실*(저널 홉의 중간 갭·tail)을 닫았다. 그러나 write-behind 신뢰성엔 한 격차가 남았다(0024 §9): 가방이 *활성 중* 죽으면 미-ack `sentBuffer`(in-flight 저널)가 소실된다. 이미 **라이브로 acked 된** 전송(give)의 저널이 영영 사라져, 복구 원장이 클라 belief 보다 *뒤처진다* — **라이브 ack ≠ 내구성**. 클라는 아이템을 줬다고/받았다고 믿는데(item_result/item_recv 수신) 복구 원장엔 그 전송이 없다 → itemDesync.

이 step 은 그 격차를 *give 한정*으로 닫는다: 클라가 *확인한 give* 를 보관했다가 가방 복구 후 **같은 itemId 로 재발행** → 복구 원장(전송 미반영 = 아이템이 아직 sender 소유)이 `owner==from` 으로 재적용 → **원장이 클라 belief 를 따라잡는다**(원장 측 손실을 클라 측 진실로 재수렴). 닫는 조건: clientResend OFF 면 0024 비트 동일(reg 0), ON 이면 in-flight give 손실 아래 itemDesync 0·복구 원장 == 무손실 truth·dupe 0(멱등).

> **범위 결정(사용자 승인)**: pickup *mint* 손실은 itemId 가 *서버 할당*이라 재발행 시 **새 id** 가 나옴 → 클라 belief(옛 id) 복구 불가. 이는 belief reconciliation(id 재매핑) 필요 — 본 step 에서 제외하고 §9 로 정직하게 연기. give 는 *기존 id* 를 옮기므로(재할당 없음) 깔끔히 닫힌다.

## 2. 메커니즘 — 클라 give-resend (clientResend OFF → 0024 비트 동일 = 회귀 0)

- **Client** (`net-core.js`):
  - `givePending` — 발신했으나 결과 미확인 give. `toAvatar` 는 *발신 시점에만* 안다(게이트웨이가 item_result 에서 toAvatar 를 은닉 — `_relayItemResult` line 58) → 발신 시 `{itemId,toAvatar}` 를 pending 에 보관.
  - `_confirmGive(itemId, ok)` — item_result(give) 수신 시 pending 에서 itemId 매칭분을 빼서 **ok → giveLog**(재발행 소스)·**fail → 폐기**. itemId 는 pending 사이에서 유일(준 아이템은 belief 에서 빠져 재-give 불가) → FIFO 매칭 안전.
  - `resendGives()` — giveLog 의 각 give 를 *같은 itemId* 로 게이트웨이에 재발행(정규 `item_give` 와이어). 전부 clientResend 게이트.
- **run 루프**: `opts.clientResync.at` 에서 각 클라 `resendGives()` 호출(제어 평면 트리거 — invRestart 처럼 run 루프가 주입 = 가방 복구 핸드셰이크의 클라 측). 미제공/OFF → 호출 0(reg 0 불변).
- **가방/persist 무수정**: 재발행 give 의 멱등성은 *이미 존재*하는 0014 의 `owner==from` 체크가 제공 — lost give 는 복구 원장에서 `owner==from(sender)` → 재적용·durable give 는 `owner==receiver(≠from)` → 거부(이중 전송 0).
- **복사 전진**: 월드·존/orch/추종자·버스·랭킹·채팅·영속/압축·0023~0024 신뢰 전달은 *그대로*. 더한 것은 Client give-resend 4종 + run 루프 트리거 뿐.

## 4. 척추 체크 5항

1. **신성한 tick** — 클라 재발행은 *존 tick 밖*(가방 결과 스트림 위 클라 행동·제어 평면 트리거). 존 net.log/상태가 clientResend on/off 에 비트 동일·존 도달 0.
2. **결정론 코어** — 복구 원장 = persist 저널(mint) + 재발행 give 의 함수 → 무손실 truth 와 비트 동일(invDigest). 재발행은 시드 로그의 일부(결정론).
3. **권위 단일 소유** — 원장 쓰기 권위는 InventoryService 하나. 클라 재발행은 *요청*일 뿐(가방이 `owner==from` 판정·멱등). 소유 belief ≤ 1(dupe 0).
4. **은닉·단일 연결** — 재발행 give 는 클라→게이트웨이 *정규 와이어*(item_give). toAvatar 은닉 유지·서비스 내부 비가시·복구 안무 누설 0.
5. **headless·원격 검증** — `node verify.js inflight` 한 줄이 xfer 저널에 손실을 주입해 resend ON=원장 belief 재수렴(==truth) / OFF=원장 뒤처짐(itemDesync>0)을 4기둥 수치 검증.

## 9. 의외의 발견 / 정직한 한계

- **의외**: 가방·persist 를 **한 줄도 안 고쳤다**. give 멱등성(`owner==from`)이 *이미* 0014 에 있어, in-flight give 손실 복구는 순수 *클라 측* 한 조각(보관 + 재발행)으로 닫혔다. 복구의 본질은 "원장을 belief 로 끌어올리기" — 클라 belief 가 *의도된 진실*이고 원장이 뒤처진 것이므로, 클라가 진실을 다시 말하면 된다.
- **의외**: `toAvatar` 가 게이트웨이 은닉(`_relayItemResult`)으로 item_result 에 없어, 재발행에 필요한 수신자를 *발신 시점*(`_itemAction`)에 잡아 pending 에 둬야 했다 — 은닉(척추 ④)이 복구 설계를 *제약*한 사례.
- **한계 (이 step 의 범위)**: **pickup mint 손실은 미해결** — itemId 가 서버 할당이라 재발행 pickup 은 *새 id* 를 mint → 클라의 옛-id belief 와 영영 불일치. id-reconciliation(클라가 새 id 채택·belief 재구성)이 필요(후속·§9). 본 step 은 손실을 *xfer 저널만*(mint durable)로 격리해 이 문제를 회피.
- **한계 (모델)**: 재발행의 *배달*은 신뢰 모델(`resend:true` 제외)·트리거는 run 루프 제어 평면(실제론 가방 복구 신호→게이트웨이→클라 핸드셰이크 필요). 활성 중 다운타임+재발행의 *일반* 형태(quiescent 아닌)는 미검증.
- **한계 (남은 §9)**: ⓐ in-flight *mint* 손실(id-reconciliation) ⓑ 버스/월드 영속 0·persist 단일점 ⓒ 채팅 in-flight 손실 미적용 ⓓ 재전송 amplification(0023/0024)·heartbeat×압축 ⓔ C++ 시뮬 미교체·lockstep 배리어.
