# step-0020 — 읽기 모델 영속·late-join (RankingService crash→쓰기 저널 reconstruct — 자기 영속 0 인 CQRS 읽기 모델의 복구)

> 직전: [step-0019](step-0019.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0019 가 `RankingService`(svc.item.out 소비→rank 투영→svc.rank.out 발행·CQRS 읽기 모델)를 세웠으나, 그 rank 투영은 **RAM·영속 0**이었다(0019 §9 한계: ranking 크래시 시 투영 소실·late-join 미착수). 이 step 은 그 격차를 닫는다. 핵심 통찰은 0019 §9 의 발견에서 온다 — **읽기 모델은 권위를 *복제*하지 않고 *재계산*한다.** 그러므로 읽기 모델은 *자기 영속이 필요 없다*: 크래시하면 **쓰기 모델의 영속 저널**(PersistStore — 0017 event sourcing·0018 스냅샷 압축)을 replay 해 투영을 재계산(reconstruct)하면 된다.

**닫는 조건**: ① rankRestart OFF → 0019 비트 동일(회귀 0) ② 랭킹 진짜 kill→쓰기 저널 reconstruct 후 복구 투영 == 원장 byOwner(복구 정합) ③ persist OFF+kill 대조군은 투영 *소실*(영속이 복원의 원인) ④ 복구 후 rankDesync 0 ⑤ 멀티프로세스 kill→reconstruct = 인프로세스 crash()+reconstruct() 비트 동일.

## 2. 메커니즘 — RankingService.reconstruct (rankRestart OFF → 0019 비트 동일 = 회귀 0)

한 조각 = **읽기 모델의 late-join**. 더한 로직은 `RankingService.crash()/reconstruct()` + run()/cluster.js 의 rankRestart 훅(`engine/` 무수정).

1. **crash()** — 읽기 모델 프로세스 사망(RAM 소실)의 인프로세스 모델: `ranks`·소비/발행 회계를 비운다. 읽기 모델은 *잃을 게 없다*(원장 권위는 가방) — 쓰기 저널에서 언제든 재계산 가능.
2. **reconstruct(journal, snapshot)** — `inventory.replay`(0017)의 *읽기 모델 판*: 같은 PersistStore 저널을 *다른 투영*으로 접는다(원장 vs 보유 수). 매핑: **mint → owner +1, xfer → from −1·to +1** = item_result(pickup/give) 투영과 *정확히 같다*(저널은 가방이 *수락한* 효과만 담아 `ev.ok` 게이트와 1:1). 스냅샷(0018 압축 베이스)이 있으면 폐기된 헤드를 *원장 히스토그램*으로 대신하고 tail(seq>upToSeq)만 적용. 발신 0(비-침습).
3. **rankRestart 훅** — invRestart 와 *같은 위치*(deliver 직전·제어 평면·net.log 비-기여): `ranking.crash()` 후 `if (persist) ranking.reconstruct(...)`. persist OFF 면 reconstruct 없음 = 투영 소실(대조군). 늦은 quiescent tick(활동 정지 후)이라 클라 belief 는 이미 수렴 → 재발행 불필요(rankDesync 0 유지).
4. **멀티프로세스(cluster.js)** — invRestart 의 *읽기 모델 판*: ① persist(안 죽음)에서 저널 읽기 ② 랭킹 호스트 진짜 kill ③ 새 호스트 spawn·init·`cmd:'reconstruct'`(쓰기 저널) ④ 'ranking' 라우팅 전환(placement). reconstruct 발신 0 → 인프로세스와 비트 동일.

월드·가방 영속(0017)·압축(0018)·버스·채팅(0015)·발행/구독(0019) *무변경*. inject seam 그대로.

## 9. 의외의 발견 / 정직한 한계

- **발견 — 읽기 모델은 자기 영속이 필요 없다**: 0019 의 "읽기 모델은 복제하지 않고 재계산한다"가 *복구*까지 자연히 확장된다. ranking 은 자기 상태를 한 바이트도 영속하지 않는데, 크래시 후 *쓰기 모델*의 저널만으로 완전 복원된다(투영==원장). CQRS 읽기 모델의 복구는 "내 상태 저장/로드"가 아니라 "쓰기 로그 재생". 단 — 읽기 모델이라도 *어딘가의* 내구 로그가 필요하다(persist OFF 대조군은 소실): 영속이 *읽기 모델 자신*에 없어도 되는 것이지, 시스템 어디에도 없어도 되는 게 아니다.
- **발견 — 쓰기·읽기 모델이 *같은 저널*을 다른 투영으로 접는다**: `inventory.replay`(저널→원장 itemId→owner)와 `ranking.reconstruct`(저널→보유 수 owner→count)가 *같은 PersistStore 저널*을 입력으로 쓴다. mint/xfer 라는 하나의 효과 로그가 여러 읽기 모델을 먹인다 — event sourcing 에서 새 투영(랭킹·업적·통계…)이 *발행자 무수정*으로 얹히듯, *복구*도 무수정으로 얹힌다.
- **발견 — 0018 스냅샷 압축이 읽기 모델 복구를 자동 가속**: reconstruct 가 inventory.replay 와 같은 (스냅샷 히스토그램 + tail) 경로를 타므로, 0018 의 저널 유계화가 읽기 모델 복구 비용도 유계화한다(저널 tail 0~5항목만 replay). 한 step(0018)의 데이터 계층 개선이 두 step 뒤 읽기 모델에 *공짜로* 적용된다.
- **한계 — quiescent restart 만(활성 중 다운타임 미검증)**: rankRestart 는 활동 정지 후 늦은 tick 에서 검증했다(클라 belief 이미 수렴 → 재발행 불필요). *활성 중* 크래시(다운타임에 svc.item.out 흘림 → reconstruct 후 재발행으로 클라 재수렴)는 미착수. 단 복구원이 *내구 저널*이라 다운타임 이벤트도 *구조적으로* 복원됨은 입증됨(faithful) — 빠진 건 다운타임 후 클라 belief 재발행 경로뿐.
- **한계 — late-join 은 *완전 재계산*만(증분 follow 없음)**: reconstruct 는 저널 전체(스냅샷+tail)를 한 번에 접는다. 라이브 스트림에 *증분 합류*(스냅샷 시점 이후만 따라잡기)나 읽기 모델 자체 스냅샷(reconstruct 비용 절감)은 미착수.
- **한계 — write-behind 윈도(0017 잔존)**: 저널은 1-tick 비동기라 활성 중 가방/persist in-flight 손실 가능(ack/resend 없음). 읽기 모델 복구는 *저널이 담은 것*만 복원한다(저널 자체의 신뢰성은 0017 잔존 격차).
