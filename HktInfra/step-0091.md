## 검증 질문

0090 의 epoch 워터마크 유계화는 더 높은 epoch 도착 시 낮은 epoch 워터마크를 *즉시* 가지친다 — 즉 *단조 epoch 도착*을 가정한다(0090 §9). 가지친 *뒤* 옛 epoch 의 지연 straggler 가 도착하면 워터마크가 없어 *신규로 오인 재수신*된다(중복 적재 — 0089 전달 유실 버그의 거울상). 유계 메모리를 깨지 않고 straggler 내성을 줄 수 있는가? SPINE 계층3·5 epoch 펜싱에 0051 lease grace 의 *유예 윈도* 를 더한다.

## 2. 메커니즘 — 옛 epoch 워터마크 grace 유예 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**관찰**: 0090 의 `_pruneEpoch` 는 epoch e 도착 시 *e 미만* 의 모든 옛 epoch 워터마크를 제거한다 — 지연 straggler 가 가지친 epoch 에서 오면 워터마크 부재로 dedup 실패(신규 오인 적재).

**구현** (`src/svc-mailbox.js`): `epochGrace = N` 일 때
- `_pruneEpoch(base, epoch)` 의 제거 기준을 `< epoch` → `< epoch - epochGrace` 로 완화 — 가장 최근 N개 닫힌 epoch 워터마크 키(`base#e`)를 *유예*(슬라이딩 윈도). 유예 구간의 straggler 는 워터마크가 살아 있어 `_seenHas` 가 정상 dedup(중복으로 인식·inbox 재적재 안 함).
- epoch 차원은 producer 당 `epochGrace + 1`(현재 + 유예 N) 로 여전히 유계 — 0051 lease grace 의 epoch 판.

`epochGrace 0`(기본) 이면 `< epoch` = 0090 즉시 가지치기 = 비트 동일. straggler 주입은 topology `mboxStraggler`(net.log 밖 직접 도착·digest 불변·미제공 시 휴면).

## 9. 의외의 발견 / 정직한 한계

- **발견**: grace 윈도는 *유계화(0090)와 내성(straggler)의 트레이드오프 노브*다 — N=0 은 최소 메모리·straggler 취약(0090), N↑ 은 straggler 내성↑·메모리 producer 당 N+1. 0051 lease grace(시작 cadence bootstrap)와 같은 "유계를 풀지 않는 유예"의 epoch 판. 또한 OFF 경로의 straggler 재수신은 `_seenAdd` 로 가지친 키를 *되살려* epochKeyCount 를 다시 늘린다 — 무계 성장의 씨앗(grace 가 막는 둘째 효과).
- **한계**: grace 는 *유예 윈도(N) 안*의 straggler 만 구한다 — N 보다 더 오래 닫힌 epoch 의 straggler 는 여전히 신규 오인. 현 토폴로지는 재시작이 inflight 를 비워 straggler 가 1 epoch 지연이 상한이라 N=1 로 충분하나, 다단 재시작·큰 지연 환경은 N 을 키우거나 옛 epoch 를 "닫힘 TTL"로 명시 기억하는 보강이 후속. straggler 주입은 인프로세스 직접 호출(net.log 밖) — 실 멀티프로세스 지연 straggler 의 E2E 재현은 후속.
