# step-0067 — 프레즌스 박스 failover 승격(presencePromote)

> 직전: [step-0066](step-0066.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0066 의 standby(presence2)는 SSOT 를 *그림자 복제*만 했다(발행 억제). 마지막 고리를 닫는다 — **primary 프레즌스 박스가 죽으면 standby 가 승격해 발행을 끊김 없이 인계하는가?** primary 사망 시 standby 를 `promote()`(active=true) 해 `svc.presence` 발행을 인계한다. shadow 가 모든 보고를 이미 먹었으므로(0066) 승격 시점 **SSOT 갭 0**: 죽음 전 보고(down)는 둘 다 봤고, 죽음 후 보고(permanent)는 승격된 standby 가 발행 → 다운스트림(presmon)이 전 전이열(down→permanent)을 무손실 수신. 닫는 조건: primary 사망·standby 승격(발행 인계)·다운스트림 연속성(미승격 대조군 대비 갭 제거)·비-침습. 존 shadow follower 승격(0009)·버스 failover(0034)의 **코디네이션 판**.

## 2. 메커니즘 — 사망+승격 (`presenceFailover` 미제공 → baseline 비트 동일 = 회귀 0)

- **`src/svc-presence.js`**: ⒜ `this.dead`(기본 false) + `onMsg` 머리에 `if (this.dead) return` — 사망 박스는 보고 무시·발행 0. ⒝ `crash()` → `dead=true`(RAM 소실 인프로세스 모델·진실 원천=shadow). ⒞ `promote(tick)` → standby `active=false`→`true` 전환(발행 인계)·`promotedAt` 기록.
- **`src/topology.js`** 틱 루프: `if (opts.presenceFailover && presence && i+1===at) { presence.crash(); if (opts.presencePromote && presenceShadow) presenceShadow.promote(i+1); }`. presenceFailover 미제공 → 휴면(crash 0·0066 비트 동일).
- A/B 변수 = *승격만*: ON/OFF 둘 다 primary 가 죽고 standby 가 존재(presenceShadow). ON 만 `promote()` 호출 → 발행 인계 vs OFF passive(갭).

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

`prespromote` 가설 (rankDie 14·dropRecover 99·상한 3·failover@30). 보고 타이밍: down 발행@23(죽음 전·primary)·permanent 보고@36→발행@38(죽음 후):

| seed | primary dead/pub | standby promoted@30/pub | presmon ON state/ev | presmon OFF state/ev | 발행분담 |
|---|---|---|---|---|---|
| 42 | true/1 | true/1 | permanent/2 | down/1 | 1+1 |
| 7 | true/1 | true/1 | permanent/2 | down/1 | 1+1 |
| 1234 | true/1 | true/1 | permanent/2 | down/1 | 1+1 |
| 99 | true/1 | true/1 | permanent/2 | down/1 | 1+1 |
| 2026 | true/1 | true/1 | permanent/2 | down/1 | 1+1 |

- **사망+승격**: primary `dead=true`(둘 다)·standby `active=true`·`promotedAt=30`(ON만; OFF passive `active=false`).
- **발행 분담·무손실**: primary 가 죽음 전 `down`(pub 1)·승격된 standby 가 죽음 후 `permanent`(pub 1) — 합 2(0066 단일 active 박스의 pub 2 와 동일 총량, *failover 를 가로질러* 보존).
- **다운스트림 연속성**: ON presmon 이 full 전이열(down→permanent) 수신(`state='permanent'`·events 2). OFF(미승격) presmon 은 `down` 에 갇힘(events 1) — 죽음 후 전이 영영 미발행 = failover 가 막는 갭.
- **SSOT 연속성**: 승격된 standby `permanentDown={ranking}`(그림자 복제 + 죽음 후 보고).
- **비-침습**: `minted` ON==OFF·원장 자기-정합 보존.
- **회귀 0**: `node run.js`(4기둥+E2E 14프로세스 비트동일)·`node run.js spine`(67-step src 누적 회귀) ALL OK. reg(키트·presenceFailover 미제공) = 0066 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **failover 트리거가 주입식**: 이 step 은 primary 사망 *감지*(heartbeat/lease 타임아웃)와 승격을 *외부 주입*(presenceFailover.at)으로 한다 — 0009 가 orch lease 타임아웃으로 follower 를 승격한 것 같은 *자율 감지*는 미적용. 승격 *메커니즘*(SSOT 갭 0·발행 인계)은 증명됐으나, "누가 primary 죽음을 알아채 promote 를 트리거하는가"(monitor/lease)는 후속.
- **shadow 가 라이브여야 갭 0**: SSOT 갭 0 은 standby 가 *처음부터* 보고를 구독해 죽음 전 모든 전이를 그림자 복제했기 때문(0066). late-join standby(보고 스트림 replay/워터마크로 따라잡기)는 미적용 — 0066 §9 의 한계가 그대로.
- **단일 standby·1회 승격**: standby 1개·승격 후 그 standby 의 failover(승격된 박스가 또 죽으면)는 미검증. 다중 standby 풀·연쇄 failover 는 후속.
