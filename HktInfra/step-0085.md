# step-0085 — 파티 멤버십 영속·failover(partyPersist·변경 저널 replay)

> 직전: [step-0084](step-0084.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0084 까지 PartyService 의 멤버십은 *휘발*(in-memory)이라 박스 crash 시 결성·가입/탈퇴가 전부 소실된다(영속 0·0084 §9). 0017 가방·0020 랭킹·0021 채팅이 event sourcing(저널 replay)으로 푼 *세계가 세션보다 오래 산다*를 멤버십에 적용해, crash 후 멤버십을 죽기 전과 비트 동일하게 복원할 수 있는가? SPINE 계층3(길드/소셜) 멤버십의 영속.

## 2. 메커니즘 — 변경 저널 + crash/reconstruct (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-party.js`): 멤버십을 *휘발 projection*(`parties`)과 *durable 저널*(`journal`)로 분리.
- `persist` ON 일 때 멤버십 변경 명령(create/join/leave)이 실제 변경되면 `_journalChange({seq, kind, partyId, member|members})` 로 저널에 append(no-op 변경은 저널 안 함 — 0084 발행과 같은 의미론).
- `crash()` — projection(`parties`)·계측만 비운다(RAM 소실). **저널은 durable** 이라 보존.
- `reconstruct()` — 저널을 seq 순 replay 해 projection 재계산(create=목록 설정·join=추가·leave=제거 — onMsg 멤버십 변경과 정확히 같은 매핑) → 죽기 전과 비트 동일.

0017/0020/0021 event sourcing 의 *멤버십* 판. 0084 의 svc.party.changed 발행 스트림이 곧 이 저널의 변경 이벤트(발행=관측, 저널=복구원). `partyPersist` OFF 면 저널 미기록·crash 후 reconstruct 해도 빈 멤버십 = 0084 비트 동일(휴면).

## 4. 척추 체크 5항

① **신성한 tick** — PartyService 는 onTick 없는 순수 반응형, crash/reconstruct 는 제어 평면, 존 tick 밖. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF). ③ **권위 단일 소유** — 멤버십 권위는 PartyService 하나(저널은 그 복구원). ④ **은닉·단일 연결** — 저널은 박스 내부, 외부는 partyQuery 계약만. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 0084(변경 발행)과 0085(변경 저널)가 *같은 이벤트*의 두 소비처다 — svc.party.changed(관측용 발행)와 journal(복구용 영속)이 같은 create/join/leave 델타에서 나온다. event sourcing 에서 "발행 스트림 == 저널"이 자연히 성립하는 작은 사례.
- **한계**: 저널이 *무계 성장*(0018 가방·0022 채팅의 스냅샷 압축 미적용) — 가입/탈퇴가 누적되면 replay 비용·메모리가 ∝변경 수. 주기 스냅샷+tail replay(멤버십 현재 상태 스냅샷 후 압축)가 후속. 또한 crash/reconstruct 는 *in-process 직접 호출* — 실제 별-프로세스 kill→fresh spawn→저널 replay 의 cluster 통합(0021 채팅처럼)은 다음 단계. 저널 자체의 영속(PersistStore 위탁·홉 신뢰)도 미적용(현재는 박스-내 durable 배열).
