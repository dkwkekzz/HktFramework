# step-0087 — 전달 수명주기 관측(deliveredPublish·svc.whisper.delivered)

> 직전: [step-0086](step-0086.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0082 는 전달 *실패*(포기)만 svc.whisper.failed 로 발행해, 운영 평면이 보는 전달 스트림이 *실패 절반*뿐이었다 — 성공한 전달과 그 비용(재시도 횟수)은 관측 불가(0082 §9). 전달 *성공*도 발행해 수명주기를 완성하되, 0082 와 같은 audit sink·발행자 무수정으로 할 수 있는가? SPINE 계층3 전달 관측의 완성.

## 2. 메커니즘 — 성공 전달 발행 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-whisper.js`): `whisperAck` 핸들러에서 inflight 가 확인 해제될 때(`delivered++`), `deliveredPublish && bus` 면 `{type:'pub', topic:'svc.whisper.delivered', ev:{to, seq, tries}}` 를 bus 로 발행(`deliveredPublished++`). `tries` = 확인까지 재발신 횟수 = *전달 비용*(0 이면 첫 시도에 성공, N 이면 N번 재시도 후).

0082 failedPublish(포기 발행)의 *성공 경로* 짝 — 같은 사건 모델(발행→audit 관측)을 성공에 적용. audit 는 svc.whisper.failed(0082)와 svc.whisper.delivered(0087)를 둘 다 구독해 전달 *수명주기 전체*(성공·포기·각각의 비용)를 본다. `deliveredPublish` OFF 면 발행 0·구독 행 미추가 = 0086 비트 동일.

## 4. 척추 체크 5항

① **신성한 tick** — whisperAck 처리·발행은 라우터 제어 평면, 존 tick 밖. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF). ③ **권위 단일 소유** — 발행 권위 0(원장 무관). ④ **은닉·단일 연결** — 라우터는 bus 주소만 알고 구독자(audit) 무지. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: `tries` 가 전달 *비용*을 그대로 노출한다 — 같은 svc.whisper.delivered 스트림이 "전달됐다"뿐 아니라 "몇 번 만에"까지 담아, 운영 평면이 네트워크 품질(재시도율 분포)을 사건당으로 관측할 수 있다. 성공/실패 이분법보다 풍부한 텔레메트리.
- **한계**: 수명주기의 *중간 단계*(첫 시도·각 재시도 시점)는 여전히 미발행 — delivered 는 *종료*(성공) 시점만, failed 는 *종료*(포기) 시점만. 시도·재시도마다 이벤트를 내면(svc.whisper.attempt) 더 세밀하나 발행량이 ∝재시도라 트레이드오프. 또한 audit 는 집계(seen count)+records 만 — 비용 분포 히스토그램·SLO 알림은 전용 모니터 박스의 일.
