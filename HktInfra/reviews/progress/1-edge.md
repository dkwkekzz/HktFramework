# ① 엣지 — 바깥세상과 만나는 문

> 인덱스: [README.md](README.md) · 구조 권위: [../../SPINE.md](../../SPINE.md) §2 · 마커: [../../STATE.md](../../STATE.md) §5
>
> **계층 한 줄**: 접속 폭주·소켓 관리 같은 *바깥의 소란*을 문턱에서 흡수해 안쪽(월드)에 안 닿게 한다. 클라는 이 문 하나만 알고 안쪽 토폴로지는 *모른다*.

---

## 로그인/인증 서버 🟡 자라는 중

**무슨 서버인가**: 계정을 검증하고, 접속 대기열을 세우고, 한 번 쓰는 세션 티켓을 내주는 엣지 서버. *비유 — 놀이공원 매표소*: 줄은 입구에서 서고, 표 한 장으로 한 번만 들어간다.

**필요한 기능들**:

1. **일회성 세션 티켓 발급** ✅ — 왜: 신원을 안쪽으로 안전히 넘기고 도용·재사용을 막아야. / 어떻게: 1회용 자격 토큰(capability token·재사용 불가). / 했나: `step-0001` 티켓 1회 발급·재사용 불가.
2. **단일 연결 은닉 계약** ✅ — 왜: 클라가 내부 토폴로지를 알면 안 된다. / 어떻게: 게이트웨이 하나만 노출하는 계약. / 했나: `step-0001` 클라는 게이트웨이 하나만 봄(은닉의 첫 못).
3. **로그인 대기열(폭주 흡수)** ✅ 기본 — 왜: 오픈·이벤트 접속 폭주가 시뮬까지 밀려들면 게임이 멈춤. / 어떻게: 입장 제어(admission control·문 앞 FIFO 줄서기·중복 멱등). / 했나: `step-0209` `LoginQueue` 새 박스(`src/loginqueue.js`)·loginEnqueue→큐·loginDequeue→맨 앞 입장+티켓 발급(admitted SSOT). 폭주가 엣지서 끝남(0001 스텁의 대기열 실체화).
4. **수용량 백프레셔(동접 상한)** ✅ — 왜: 폭주해도 월드 동접이 무한히 늘면 안 됨. / 어떻게: admission control 의 상한 — admitted 가 capacity 도달이면 dequeue 가 입장 보류(player 큐 잔류). / 했나: `step-0219` loginCapacity(월드 동접 상한을 엣지가 강제·초과분은 엣지 큐 대기). 미설정이면 capacity=∞(reg 0).
5. **티켓 만료·재접속 흐름** ✅ — 왜: 끊긴 세션 복귀·만료 티켓 차단. / 어떻게: TTL(issuedAt+ttl≤now 회수) + 재접속 시 유효 티켓 재개(멱등 resume·줄 다시 안 섬). / 했나: `step-0210` loginExpire(만료 회수) + `step-0220` loginReconnect(유효 admitted player 면 기존 티켓 재개·새 티켓 0·만료/미발급이면 재큐 필요). 끊김에 강한 세션 연속성.
6. **계정 검증(엣지 차단)** ✅ — 왜: 진짜 계정만 줄에 세워 불량 접속이 대기열·월드를 못 건드리게. / 어떻게: 줄서기 *이전* 자격 조회(validAccounts)·통과만 enqueue·미인증 거부(0001 LoginServer 검증의 큐 실체화). / 했나: `step-0229` loginAuth(validAccounts 통과만 줄·미인증 authRejects·줄 이전 차단). 미주입/빈 목록이면 휴면(reg 0). *잔여: validAccounts 는 주입 더미 — 실 계정 DB 조회는 데이터 계층 연동 후속.*
7. **큐 이탈(좀비 슬롯 회수)** ✅ — 왜: 기다리다 떠난 player 가 큐에 남으면 길이가 과대 → 백프레셔(0219) 판단이 틀어짐. / 어떻게: 입장 전 명시 이탈(대기열서 제거·미줄 멱등). / 했나: `step-0230` loginAbandon(줄 떠남→제거·뒤 player 당겨짐·abandonMisses). 큐 길이를 사실대로 유지. 미주입이면 휴면(reg 0). *잔여: 무응답 자동 타임아웃 이탈(현재는 명시 이탈만)·2차.*

**지금 어디 / 다음**: 티켓·은닉 스텁 → 대기열+티켓 발급+만료 → 수용량 백프레셔·재접속 재개(0219·0220) → **계정 검증·큐 이탈(0229·0230)**까지 — 입장 제어(검증→줄→상한→이탈→재개) 완비. 다음 = 실 계정 DB 연동·무응답 자동 이탈·게이트웨이 군 풀.

## 게이트웨이 서버 🟡 자라는 중

**무슨 서버인가**: 수만 소켓을 종단하고 암호화하고 세션을 존/서비스로 라우팅하는 엣지 서버. 클라가 *유일하게 아는* 주소. *비유 — 호텔 프런트*: 손님은 프런트만 상대하고 객실 재배치·직원 이동을 모른다.

**필요한 기능들**:

1. **소켓 종단 ↔ 시뮬 분리** ✅ — 왜: 한 프로세스에 두면 소켓 CPU 와 시뮬이 서로 잡아먹음. / 어떻게: 별도 OS 프로세스로 종단을 떼냄. / 했나: `step-0010` 게이트웨이를 별 프로세스로(분리 실물화).
2. **내부 은닉(재연결 0)** 🟡 — 왜: 클라가 안쪽 주소를 알면 존 이동·서버 재배치마다 재연결. / 어떻게: 단일 연결 간접층(내부가 바뀌어도 클라는 그대로). / 했나: `step-0001` 단일 연결 계약(완성은 군 풀 토폴로지에서).
3. **다중 게이트웨이 메시지 비충돌** ✅ — 왜: 여러 게이트웨이가 같은 reqId 를 쓰면 섞임. / 어떻게: 발신자별 네임스페이스 복합키((producer,reqId)). / 했나: `step-0046`.
4. **존 위치 디렉토리 + 실 존 직접 라우팅(서비스 디스커버리)** ✅ 기본 — 왜: 0290 까지 entity 트래픽(enter/move/leave)이 게이트웨이→**orch**→런타임 경유였다 — orch 가 라우팅 *결정*을 쥐어 데이터 평면이 코디네이션 박스를 거쳐갔다(#9·SPINE §4 경로1·2 는 게이트웨이가 *직접* 중계해야). / 어떻게: ⒜ orch 가 배치 집행마다 zone→host 위치를 게이트웨이에 push(`zoneLoc`)→게이트웨이 `zoneDir` 캐시(서비스 디스커버리·게이트웨이는 orch 내부 무지·명시 메시지로만 학습) ⒝ 게이트웨이가 클라 entity intent 를 자기 `zoneDir` 로 host 해소→`zoneDeliver`(host 태깅)로 *직접* 라우팅(라우팅 결정이 게이트웨이로 이동) ⒞ 이주/장애 시 dir 갱신(zoneLoc)·일괄 무효화(hostDown broadcast)·낡은 host frame 거부(stale). / 했나: `step-0293` zoneDir+zoneLoc(`src/gateway.js`·`gateway-msg.js`)→`0294` 직접 enter→`0295` 직접 move/leave→`0296` 이주 정합+stale 거부→`0297` 장애 dir 무효화+복구→`0299` 다중 churn bijection(`zoneDirSnapshot`). 미설정이면 entity 가 0290 경로(→orch·reg 0). *잔여: 현 zone-host 핸들은 orch 인프로세스 Map — 게이트웨이가 host 태깅 후 orch 가 적용·실 host.js 물리 소켓 분리는 후속.*
5. **게이트웨이 군(pool)·세션 라우팅** ⬜ — 왜: 한 대로는 수만 소켓·내고장성 부족. / 어떻게: 풀 토폴로지 + 세션→존/서비스 라우팅. / 했나: 미착수.
6. **암호화** ⬜ — 왜: 연결 보안. / 어떻게: 종단 암호화. / 했나: 미착수.

**지금 어디 / 다음**: 별 프로세스·다중 게이트웨이 네임스페이스 + **존 위치 디렉토리(서비스 디스커버리)·실 존 직접 entity 라우팅(0293~0299·#9)**까지 — 게이트웨이가 자기 라우팅 테이블로 존을 *직접* 친다(orch 데이터 평면 우회). 다음 = 실 host.js 물리 프로세스/소켓 분리·게이트웨이 *군(pool)* 으로 늘려 한 대 죽어도 재연결 0 검증.
