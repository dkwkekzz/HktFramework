# ① 엣지 — 바깥세상과 만나는 문

> 인덱스: [README.md](README.md) · 구조 권위: [../../SPINE.md](../../SPINE.md) §2 · 마커: [../../STATE.md](../../STATE.md) §5
>
> **계층 한 줄**: 접속 폭주·소켓 관리 같은 *바깥의 소란*을 문턱에서 흡수해 안쪽(월드)에 안 닿게 한다. 클라는 이 문 하나만 알고 안쪽 토폴로지는 *모른다*.
>
> 이 계층은 "최초 구조 = 모든 일이 한 프로세스" 에서 *제일 바깥* 두 박스를 떼어낸 자리다.

---

## 로그인/인증 서버 🌱 씨앗만

- **무슨 서버인가**: 계정을 검증하고, 접속 대기열을 세우고, 한 번 쓰는 세션 티켓을 내주는 엣지 서버.
- **이론 기반**: *입장 제어(admission control)* + *일회성 자격 토큰(capability token)*. 비유 — 놀이공원 매표소: 줄은 *입구에서* 서고, 표 한 장으로 *한 번만* 들어간다. 표가 있어야 안으로 갈 수 있다.
- **왜 필요했나 → 어떻게 구현했나**:
  - *최초 구조*에선 로그인도 시뮬과 한 프로세스에 산다. 오픈·이벤트 때 몰리는 **접속 폭주가 그대로 월드(시뮬)까지 밀려들면 게임이 멈춘다** — 줄서기는 문 앞에서 끝나야 한다. 그래서 접속 수락을 시뮬 *앞단*에 두는 박스가 필요하다.
  - `step-0001` — 로그인 스텁을 심었다: 세션 티켓을 *1회만* 발급(재사용 불가)하고, 클라는 게이트웨이 하나만 보게 했다(은닉의 첫 못). 폭주 흡수의 자리·티켓 계약·은닉을 *계약으로* 먼저 세운 씨앗.
- **지금 어디 / 남은 것**: 티켓 1회 발급·단일 연결 계약의 *스텁*까지. 실제 로그인 대기열(폭주 흡수)·계정 검증·티켓 만료·재접속 흐름은 미착수(STATE §3 ⬜ "로그인 큐·티켓 실체화").

## 게이트웨이 🟡 자라는 중

- **무슨 서버인가**: 수만 소켓을 종단하고, 암호화하고, 세션을 존/서비스로 라우팅하는 엣지 서버. 클라가 *유일하게 아는* 주소.
- **이론 기반**: *관심사 분리*(소켓 I/O ↔ 시뮬) + *간접층을 통한 은닉*(클라는 게이트웨이만 알고 내부는 모른다 → 내부가 바뀌어도 클라는 그대로). 비유 — 호텔 프런트: 손님은 프런트만 상대하고 객실 재배치·직원 이동을 모른다.
- **왜 필요했나 → 어떻게 구현했나**:
  - *최초 구조*에선 소켓 종단 CPU 와 시뮬이 한 프로세스 → 둘이 서로 잡아먹는다. 또 클라가 안쪽 주소를 직접 알면 존 이동·서버 재배치 때마다 재연결해야 한다. → *소켓 종단을 시뮬에서 떼고*, *클라에는 내부를 숨겨* 재연결 0 을 만드는 박스가 필요하다.
  - `step-0010` — 게이트웨이를 *별도 OS 프로세스*로 분리(소켓 CPU ↔ 시뮬 분리의 실물화). 이제 한쪽 부하가 다른 쪽 tick 을 안 막는다.
  - `step-0046` — 게이트웨이가 *여러 대* 공존할 때 같은 reqId 를 써도 메시지가 안 섞이게, 발신자별 네임스페이스 복합키((producer,reqId))를 도입(버스 계층과 짝).
- **지금 어디 / 남은 것**: 별 프로세스로 떨어졌고, 다중 게이트웨이가 공존해도 안 겹친다. 게이트웨이 *군(pool)* 풀 토폴로지·세션 라우팅·암호화는 후속.
