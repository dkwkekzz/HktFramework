# ③ 게임 서비스 — tick 과 무관한 책임

> 인덱스: [README.md](README.md) · 구조 권위: [../../SPINE.md](../../SPINE.md) §2 · 마커: [../../STATE.md](../../STATE.md) §5
>
> **계층 한 줄**: 아이템 거래·채팅 팬아웃·랭킹 집계처럼 *존 tick 과 같은 박자로 돌 필요 없는* 책임을 전부 비동기 서비스로 떼어낸다. 판정 기준: "그 일이 시뮬 tick 박자여야 하나?" 아니면 이 줄로.
>
> 박스가 가장 많은 계층. 박스마다 *무슨 서버·어떤 이론·왜 필요→어떻게* 를 따로 푼다.

## 가방(인벤토리) 서버 🟡 자라는 중

- **무슨 서버인가**: 아이템 원장을 트랜잭션으로 관리하는 서버 — 이동·거래·복제(dupe) 방지(`src/svc-inventory-core.js`+`-txn.js`).
- **이론 기반**: *단일 소유 원장 + 쌍 거래(닫힌 장부, 복식부기)* + *write-behind/quorum 영속*. 비유 — 은행 계좌이체: 한쪽서 빠지고 다른쪽에 들어가는 *한 트랜잭션*, 총량은 보존(복제 0).
- **왜 필요했나 → 어떻게 구현했나**:
  - *최초 구조*: 아이템 연산이 존 tick 에 끼면 시뮬을 막고, 존 넘는 거래가 존간 직접 결합을 부른다 → **존 tick 밖 단일 소유 원장**: `step-0014` 아이템 단일 소유·이동은 쌍 거래.
  - 죽으면 원장이 날아간다 → **영속·신뢰**: `step-0017~0018` failover·효과 저널·압축. `step-0023~0029` write-behind 신뢰성(NAK·heartbeat·give·mint)→quorum(이중쓰기·N복제·write ack)(데이터 계층과 짝).
- **지금 어디 / 남은 것**: 단일 소유 원장 → 떨어뜨려도 안 새는 신뢰 전달까지. give-resend 재정렬 견고성·멀티프로세스 패리티(transfers≠base 잔류·#9) 잔여.

## 채팅 서버 🟡 자라는 중

- **무슨 서버인가**: 채널 팬아웃(전체/지역/귓속말)을 비동기로 뿌리는 서버(`src/svc-chat.js`).
- **이론 기반**: *구독 기반 팬아웃 + 지역 격리* + *커맨드 로그 영속*. 비유 — 라디오 채널: 같은 주파수(채널) 구독자에게만 가고, 다른 지역 방송은 안 섞인다.
- **왜 필요했나 → 어떻게 구현했나**: *최초 구조*에선 대규모 브로드캐스트 대역이 시뮬 대역을 잡아먹는다 → **분리·격리**: `step-0015` 채널 팬아웃·지역 격리(누설 0). 죽어도 대화가 남아야 → **영속**: `step-0021~0022` 커맨드 로그 replay·스냅샷 압축.
- **지금 어디 / 남은 것**: 팬아웃·지역 격리·영속까지. per-message ack/resend·홉 신뢰(#7·지금은 best-effort 팬아웃) 잔여.

## 랭킹 서버 🟡 자라는 중

- **무슨 서버인가**: 발행 스트림을 구독해 순위를 집계하는 *읽기 모델(CQRS)* 서버(`src/svc-ranking.js`).
- **이론 기반**: *CQRS(쓰기↔읽기 분리)* + *버스 구독으로 따라붙기*(발행자 무수정) + *frontier ack/lease/self-healing*. 비유 — 신문 구독자가 기사를 모아 자기 색인을 만든다 — 신문사(발행자)는 구독자를 모른다.
- **왜 필요했나 → 어떻게 구현했나**: *최초 구조*에선 집계가 발행자(가방 등)를 직접 건드린다 → **구독으로 따라붙기**: `step-0019~0020` 발신 소비자로 붙고 읽기모델 late-join 복구. 버퍼·죽음 관리 필요 → **frontier·lease**: `step-0044~0045` 따로 frontier ack→min 까지만 가지치기→영영 죽으면 lease 축출. 사람 개입 없이 되살아나야 → **self-healing**: `step-0056~0057·0061~0062` recover 받아 자기 재구독·recoverAck → standby 가 permanent 에 자기 활성화·저널 reconstruct 로 갭 복원.
- **지금 어디 / 남은 것**: 발신 소비자 → 1급 소비자(frontier ack) → self-healing → 대체 소비자 인계까지. 다중 보드·*런타임 동적 spawn*(지금은 사전 등록 standby) 잔여.

## 귓속말/파티 라우터(wrouter) + 수신함(mbox) 서버 🟡 자라는 중

- **무슨 서버인가**: "X 에게"·"파티 전원에게" 를 프레즌스 SSOT 로 라우팅하고 *진짜 닿았는지*까지 보장하는 라우터(`svc-whisper-*.js`) + 받은 메시지를 쌓고 비우는 수신함(`svc-mailbox.js`).
- **이론 기반**: *프레즌스 조회 기반 라우팅* + *신뢰 전달(영수증→재시도→상한→exactly-once dedup)* + *유계 메모리(워터마크·epoch·cap)* + *1:N 종결*. 비유 — 등기우편: 받는 사람을 *주소록(프레즌스)* 으로 찾아 보내고, *수령 확인*을 받고, 안 오면 재시도하다 끝내 *반송/실패 통지*하며, 같은 편지를 두 번 안 받게(dedup) 한다.
- **왜 필요했나 → 어떻게 구현했나** (각 마디가 앞 마디의 한계를 푼다):
  - *최초 구조*: 메시지가 *어디 있는지·살아있는지* 모른 채 보내진다 → **조회 라우팅 + exactly-once**: `step-0071~0080` 라우터(질의→전달/반송·failover 재타깃)·1:N 파티·멤버십 분리 → 전달 신뢰 호(영수증→재시도→상한→통지→dedup exactly-once).
  - dedup 기억이 무한히 큰다·라우터 재시작에 깨진다 → **두 축 유계화**: `step-0081·0089~0091` seq 연속 워터마크(O(gap))·epoch 재시작 펜싱(0089 버그 수정→0090 옛 epoch 가지치기→0091 grace 유예로 지연 straggler 까지·`svc-mailbox.js:44`).
  - 결과가 밖에서 안 보인다 → **세 결말 관측**: `step-0082·0087·0097` 포기(svc.whisper.failed)·성공(delivered{tries})·반송(bounced·`svc-whisper-handlers.js:57`)을 audit 에 발행.
  - 1:N 파티는 *끝났는지* 가 모호하다 → **세 종결**: `step-0083·0088·0092~0093·0095` done(라우팅 결정)·acked(전원 실수신)·incomplete(일부 영구 실패·0092·`svc-whisper-core.js:78`) + 성공/실패 발행.
  - 한 수신함에 다 쌓으면 N>1 에서 ack 가 거짓이다 → **멤버별 수신함**: `step-0096` mbox2(파티원마다 자기 수신함→모든 up 멤버 ack).
  - 수신함 메모리가 무한히 큰다·소비가 손실되면 안 된다 → **메모리·수명·관측 완성**: `step-0099~0104` inbox cap·**drainAck 2단계 읽음**(보유 checkout→ackDrain 안전 제거·재드레인 무손실·exactly-once·`svc-mailbox.js:58,69`)·checkout cap·소비/손실 발행(drained·overflowed).
  - 지연 공지가 죽은 박스로 역-재타깃한다 → **메아리 펜싱**: `step-0105~0106` wrouter 도 epoch 가드(`svc-whisper-handlers.js:12`)로 낡은 공지 거부.
- **지금 어디 / 남은 것**: 프레즌스 첫 실사용 → 전달 exactly-once → 유계·관측·재시작 안전 → 파티 세 종결·멤버별 수신함·수신함 유계화까지. 종결 단일성(#25)·게이트웨이 경유 read E2E(#9)·동적 N 수신함(#27)·멀티프로세스 미배선(#9) 잔여.

## 길드/소셜(파티 멤버십) 서버 🟡 자라는 중

- **무슨 서버인가**: 파티/길드 멤버십(오래 사는 상태)을 관리하는 서버(`src/svc-party.js`). 라우팅과 직교한 *멤버십 SSOT*.
- **이론 기반**: *멤버십 SSOT(2단 조회)* + *증분 변경 + 발행* + *event sourcing 영속*. 비유 — 동호회 명부: 한 명 들고 날 때 명부 전체를 다시 쓰지 않고(증분), 변경을 게시(발행)하며, 사무실이 타도 변경 일지(저널)로 복원한다.
- **왜 필요했나 → 어떻게 구현했나**: *최초 구조*: 멤버십이 라우팅에 섞여 있다 → **전용 박스로 분리**: `step-0075` 멤버십 전용 박스(2단 조회). 전체 덮어쓰기는 비효율·변경을 남이 못 본다 → **증분+발행**: `step-0084` 증분 가입/탈퇴(멱등)+변경 발행(svc.party.changed). 죽으면 명부가 날아간다 → **영속**: `step-0085~0086` 변경 저널 replay·crash→recon → 스냅샷+tail 압축(가방·채팅과 같은 event sourcing 짝).
- **지금 어디 / 남은 것**: 인메모리 SSOT 씨앗 → 증분·관측·영속까지. cluster kill→replay 통합(현 in-process·#9) 잔여.

## 거래소 서버 🟡 자라는 중 *(실물 거래 → 2-서비스 saga 신뢰 전달·원자성)*

- **무슨 서버인가**: *두 당사자* 사이 아이템↔대가 교환을 존 tick 밖에서·이중판매 0 으로 성사시키는 서버(`src/svc-exchange-core.js`+`-txn.js`). 가방과 *두 서비스 saga* 로 엮인다.
- **이론 기반**: *escrow(에스크로) 쌍 거래* + *event sourcing 영속* + *분산 saga(보상 트랜잭션) + 신뢰 전달(재전송+멱등 dedup)*. 비유 — 중고거래 안전결제: 판매자 물건을 *제3자 보관(escrow)* 에 잡아두고, 거래 성사면 구매자에게, 실패면 판매자에게 *되돌린다(보상)* — 통신이 끊겨도 같은 결과를 *한 번만* 반영(멱등).
- **왜 필요했나 → 어떻게 구현했나** (각 마디가 앞 마디의 한계를 푼다):
  - *최초 구조*: 존 넘는 거래가 존간 결합 없이·이중판매 없이 성사돼야 → **escrow 단일 권위**: `step-0107~0110` 서비스 분리(escrow 쌍 거래·보존)→체결 발행→영속(op 저널 replay)→스냅샷+tail 압축.
  - 매물이 영영 안 팔리면 묶인 채 남는다 → **수명주기 종결**: `step-0111·0114~0115` 취소 발행·만료 TTL 자동 회수·만료 발행(보존식 4종).
  - escrow 가 *말뿐*이면 실물 아이템이 안 빠진다 → **가방과 실물 거래**: `step-0117~0120` escrow 를 가방 원장 아바타로 실체화(인출·입금·반환 전부 가방 give)→2-서비스 보존 단언(거래소 open ≡ 가방 escrow 소유).
  - 두 서비스 give 가 *낙관적*이면 한쪽 실패가 유령 상태를 남긴다 → **닫힌 saga 고리**: `step-0121~0123` give 결과 비동기 수신(replyTo+cause)→실패 보상(saga 롤백·phantom 0)→보상 발행(svc.exchange.aborted).
  - 회신이 손실되면 saga 가 멈추거나 잘못 보상한다 → **신뢰 전달**: `step-0125~0127` 미해결 추적+손실 감지(gid·pending)→재전송+**멱등 dedup**(가방 (replyTo,gid) 재실행 0·`svc-inventory-txn.js:65`)→dedup 유계화(saga_done ack-of-ack).
  - "정확히 한 번 옮겨졌나"를 *증명*해야 → **세 정합 층 합류**: `step-0128~0130` 회계 닫힘(sagaConsistent `gives==acked+pending`·`core.js:119`)→자동 재전송(autoRetry·지속 손실도 회복)→교차 정합 capstone(escrowXfers==giveOks·요청 회계≡실행 회계·`inventory-txn.js:74`). 물리(0120)·회계(0128)·교차(0130)로 give 가 정확히 한 번 옮겨짐을 양 서비스서 증거(#31 해소).
  - 정리: `step-0124` svc-exchange 32.4KB→core/txn/entry 분할(기능 0).
- **지금 어디 / 남은 것**: 분리→발행→영속→압축→수명주기·시세 피드→실물 거래→2-서비스 saga 신뢰 전달·교차 정합까지. 거래소 저널 *별 PersistStore 박스화*(#30b)·멀티프로세스 배선(#9)·자동 재전송 상한/나이(#35)·**우편/길드 전용 박스 미착수** 잔여.

## 시세 피드(MarketFeed) 서버 🟡 자라는 중 *(0019 ranking 의 거래소 판)*

- **무슨 서버인가**: 거래소 발행을 구독해 item별 시세(체결가·거래량·회전)를 집계하는 *읽기 모델(CQRS)* 서버(`src/svc-market.js`).
- **이론 기반**: *CQRS 읽기 모델*(권위는 거래소·발신 0·관찰 전용) + *저널 replay late-join*. 비유 — 증권 시세판: 거래소(권위)가 체결을 내보내면 시세판은 그걸 모아 보여줄 뿐, 거래를 일으키지 않는다.
- **왜 필요했나 → 어떻게 구현했나**: 거래량·시세는 거래소(발행자)를 안 건드리고 구독으로 따라붙어야 → **구독 집계**: `step-0112` svc.exchange.sold+cancelled 구독→item별 {시세·거래량}(0019 RankingService 와 같은 CQRS 골격). 다운타임 누락을 따라잡아야 → **late-join 복원**: `step-0113` 자기 영속 0 이어도 *거래소 op 저널* replay 로 시세 복원. 수명주기 전부 흘러야 → **만료 반영**: `step-0116` svc.exchange.expired 구독 추가(체결·취소·만료 3종 모두 시세에·`svc-market.js:29`).
- **지금 어디 / 남은 것**: 발행 구독→저널 replay 복원→수명주기 3종 반영까지. reconstruct==라이브 가 *전-수명주기-발행 ON* 전제(#32)·매물 깊이(open depth)·자기 스냅샷 영속·멀티프로세스 배선(#9) 잔여.
