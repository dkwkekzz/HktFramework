> **계층 한 줄**: 서버가 늘수록 서로 직접 부르면 N×N 그물이 된다. pub/sub 으로 *주소·내부를 서로 모른 채* 구독으로만 전파한다 — 새 소비자 추가가 발행자를 안 건드린다.

---

## 이벤트 버스 서버 🟡 자라는 중 *(서비스 다음으로 깊게 자람)*

**무슨 서버인가**: 서버끼리 직접 RPC 로 안 엮이게 *발행/구독(pub/sub)* 으로만 메시지를 나르는 중계 서버(`src/svc-bus.js` + 배선 `cluster-*.js`). *비유 — 신문 구독*: 발행사는 구독자가 누군지 몰라도 찍어내고, 늦게 온 구독자는 빠진 호를 받는다(replay).

**필요한 기능들** (기능마다 다른 이론에 기댄다):

1. **나르는 전송 substrate** ✅ — 왜: 메시지를 옮길 바닥이 먼저. / 어떻게: 지연·손실·재정렬·신뢰성 모델을 가진 전송. / 했나: `step-0004`.
2. **토픽 pub/sub + 디커플링** ✅ — 왜: "누구에게"가 없으면 결합이 안 풀림. / 어떻게: 토픽 발행/구독 + 발행자 무수정 소비자 추가. / 했나: `step-0012` 토픽 pub/sub → `step-0016` ServiceBus → `step-0019` 첫 발신 소비자.
3. **동적 구독 + failover** ✅ — 왜: 운영 중 구독 변경·소비자 사망에도 끊기면 안 됨. / 어떻게: 런타임 구독/해지 + 재협상(진실 원천=소비자). / 했나: `step-0033` 동적 구독 → `step-0034` failover.
4. **무손실 전달(producer replay)** ✅ — 왜: 죽거나 늦어도 결국 전부 도착해야. / 어떻게: at-least-once + producer replay(결과/요청 양경로). / 했나: `step-0036~0037`.
5. **replay 버퍼 유계화·자기조정** ✅ — 왜: 버퍼가 무한히 쌓이면 누설. / 어떻게: 슬라이딩 K 창 + ack 워터마크 자기조정 + dedup 유계. / 했나: `step-0039~0042`(dedup peak 60→24) → `step-0044` 다중 소비자 min-워터마크.
6. **죽은 소비자 lease 수명관리** ✅ — 왜: 죽은 소비자가 버퍼를 영영 붙들면 안 됨. / 어떻게: 침묵 길이로 축출 + 적응형 leaseSpan(관측 cadence 로 임계 self-size). / 했나: `step-0045` 축출 → `step-0046~0047` producer 네임스페이스/워터마크 → `step-0048~0052` lease lifecycle·적응(오축출 0).
7. **lease 생애 관측화** ✅ — 왜: 죽음/되살아남을 남이 알아야 치유 가능. / 어떻게: lease 전이를 svc.item.lease 이벤트로 발행. / 했나: `step-0054`(코디네이션이 구독할 토대).
8. **물리 분산** ⬜ — 왜: 지금은 인프로세스 가설 버스. / 어떻게: NATS/Redpanda 등가. / 했나: 미착수(STATE §3 🟡).
9. **per-producer ack·라우팅 영속·서버간 인증** ⬜ — 했나: 미착수.

**지금 어디 / 다음**: 단순 전송관 → pub/sub → failover·무손실·유계화·소비자 수명관리·관측까지. 다음 = 물리 분산 + 서버간 인증.
