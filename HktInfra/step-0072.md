# step-0072 — 귓속말 라우터 failover 연속성: 승격 공지→라우터 재타깃(whisperFailover)

> 직전: [step-0071](step-0071.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0071 의 귓속말 라우터는 `queryAddr` 를 *고정*(primary 프레즌스 박스)으로 가리킨다 — primary 사망 후 귓속말 질의가 죽은 박스로 가 끊긴다(0071 §9). 이는 0069 의 질의자(presmon)가 겪었던 한계가 *라우터*로 옮겨온 것이다. 0070 이 presmon 에 준 해법(svc.presence.active 공지→queryAddr 재타깃)을 **라우터**에 적용하면, primary 프레즌스 박스가 죽어도 귓속말 라우팅이 끊기지 않는가? (닫는 조건: 사망 후 귓속말이 승격된 박스로 질의돼 라우팅 완료·whisperFailover OFF=0071 비트 동일)

## 2. 메커니즘 — 라우터 재타깃(플래그 `whisperFailover` OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-whisper.js`** — `onMsg` 에 `svc.presence.active` 핸들러 추가: 승격된 박스가 공지한 새 active 주소로 `queryAddr` 갱신 + `retargets++`. 0070 의 presmon 재타깃과 *동형*(라우터 판). 미구독이면 미발화(0071 비트 동일).
- **배선(`topo-build.js`)** — `whisperFailover` 플래그 추가. ON(+whisperRouter+presenceAnnounce+shadow+질의 전제)이면 `subs.push(['svc.presence.active','wrouter'])`. OFF 면 미추가 = 0071 토폴로지 비트 동일.
- **failover 흐름**: primary 프레즌스 박스 crash(t30·presenceFailover) → standby(presence2)가 하트비트 침묵으로 자율 승격(presenceLease·0068) → 승격 시 svc.presence.active 공지(presenceAnnounce·0070) → wrouter 구독해 queryAddr 를 presence2 로 재타깃 → 사망 후(t50) 귓속말 질의가 승격 박스로 감.

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

- **reg**(키트·src vs baseline): **ALL OK** — whisperFailover 미설정 → wrouter 의 active 구독·재타깃 0·월드해시 `0x7a122947`(seed42)… 0071 비트 동일.
- **whisperfo**(가설·ON vs OFF) — 5시드 전부 OK:
  - 재타깃: `retargets 1`·`queryAddr presence2`(ON) vs `retargets 0`·`queryAddr presence`(OFF·죽은 primary 고정).
  - 라우팅 연속성: 사망 후 질의 무손실 `q/recv 2/2`·`routed 1`(inventory up)·`bounced 1`(ranking permanent).
  - 판정: `decision[inventory]=routed`·`decision[ranking]=bounced`.
  - 대조(OFF): `recv<sent`(죽은 primary 로 질의→손실)·`routed+bounced<2`(귓속말 미해소).
  - 비-침습: `minted ON==OFF`.
- **결정론/E2E**: `node run.js` ALL OK(14프로세스 E2E 비트 동일). 재타깃은 inproc 제어 평면(presenceFailover/whispers 주입)으로만 자극 — 멀티프로세스 무영향.
- **spine**(src 누적 회귀 72-step): ALL OK.

3. **권위 단일 소유** ✅ — 라우터 권위 0(질의·전달만). 프레즌스 SSOT 는 승격 박스가 단일 active(이중 발행 0·0066/0067). minted ON==OFF.
4. **은닉·단일 연결** ✅ — 라우터는 승격된 박스 주소를 *공지로* 알게 된다(하드코딩 0·디스커버리). 클라는 여전히 라우터만 안다.
5. **headless·원격 검증** ✅ — Node·UE 0. `node run.js`/`spine` 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **재타깃 윈도 질의는 여전히 손실 가능**: 공지 도착 *전*(승격~공지 전파 사이)에 들어온 귓속말 질의는 죽은 primary 로 가 손실된다(0070 §9 의 라우터 판). 시나리오는 귓속말을 공지 후(t50, 승격 t33 후)에 주입해 이를 피한다. 윈도 질의 재시도(0058 recoverRetry 의 질의 판)는 후속.
- **연쇄 failover·다중 standby 미검증**: 단일 standby(presence2) 1회 승격만 검증. 승격된 박스가 또 죽으면(연쇄) 다음 standby·재공지 사슬은 미착수(active 자기-하트비트 메아리 정리·0068 §9 가 선결).
- **전달 신뢰는 그대로 best-effort**: 0071 과 동일 — whisperDeliver 1회 발신. failover 후에도 전달 ack/재시도는 없다(라우팅 *결정*의 연속성만 이 step 의 범위).
