# step-0003 — Sim 인터페이스 동결: 시뮬은 "구현"이 아니라 "계약"이다

> 코어: `step-0003/net-core.js`(step-0002 골격 + ISimCore 계약 + 구현 2종) · 헤드리스: `step-0003/verify.js`
> 이 step 이 더한 한 조각: **존 시뮬을 동결된 ISimCore 계약 뒤로 빼내고, 오늘의 VM 스텁을 그 계약의 *첫 구현*(더미)으로 공식 승격 — 교체 지점은 단일 seam.**

step-0001·0002 는 *시뮬을 인라인 구현*으로 두고 골격·복제를 세웠다. 그러나 큰 목표(MMO 인프라)의 핵심 전략은 **시뮬을 먼저 짓지 않는 것**이다 — 실 C++ 시뮬을 *먼저* 지으면 원격 빌드·검증 루프가 끊긴다([TOOLS.md](TOOLS.md) §4). 그래서 순서를 뒤집는다: **시뮬은 인터페이스만 동결**하고(onTick·intent 적용·뷰·enter/leave 수명주기 + 결정론 보장), 오늘의 VM 스텁을 그 인터페이스의 **더미 구현**으로 박는다. 인프라(엣지·코디·존 호스트·복제 탭)는 더미 뒤에서 전부 원격 E2E 로 서고, 나중에 더미를 *얇은 C++ 호스트로 교체만* 한다 — 인터페이스가 동일하므로 인프라 무수정. step-0003 은 이 "Sim = 계약, C++ = 최후 교체"를 격리 증명한다.

결과: **전 시드 전 항목 통과.** ① 회귀 — 인터페이스 추출은 비-침습, step-0001/0002 골든 비트 동일(off=골든, on=권위 불변) ② 계약 동결(`conf`) — 동결 명세를 *실행 가능한 검사*로: 더미·array 두 구현이 seed-only 결정론·수명주기·intent 적용수를 통과하고 **표현 무관**(객체맵 vs 병렬배열 trace 해시 비트 동일) ③ 전파·권위 — 권위·추종자 매 tick 사슬 일치(불일치 0/60), 권위 위반 0·추종자 자기권위 0·desync 0(0002 유지) ④ 가설(`swap`) — **단일 seam(`run.makeSim`) 하나만 바꿔** 더미→array(C++ 스탠드인) 교체 시 두 구현 모두 골든 비트 동일·전 E2E 불변, **인프라 7개 클래스의 구체 시뮬 이름 참조 = 0건**(교체 = 팩토리 1줄, 인프라 코드 무수정).

## 검증 질문

> ① **회귀 0**: 시뮬을 ISimCore 뒤로 빼낸 추출이 동작 비-침습인가? off=골든, on=권위 불변? (`reg`)
> ② **계약 동결**: 동결된 ISimCore v1 을 실행 가능 명세로 박았는가? 더미·array 둘 다 통과하고 *표현 무관*(trace 비트 동일)인가? (`conf`)
> ③ **결정론 전파 + 권위**: 권위·추종자 매 tick 사슬 일치(불일치 0)·권위=유일 소유·추종자 자기권위 0·desync 0 가 유지되는가? (`prop`·`auth`)
> ④ **단일 seam 교체**: makeSim 하나만 바꿔 더미↔array 교체 시 골든 비트 동일·E2E 불변이고, 인프라가 구체 시뮬을 0건 참조(무수정)인가? (`swap`)

모든 수치는 시드 [42, 7, 1234, 99, 2026], `node step-0003/verify.js <mode> [seed]` (mode: reg | conf | prop | auth | hide | bytes | swap | all). 시나리오 상수는 step-0001/0002 그대로(60 tick · intent 20 · 계정 1 · 존 1 권위 + 1 추종자). 전송은 여전히 **무손실·즉시** — 지연·손실 아래 복제 강건성은 동결된 이 인터페이스 *위로* 미룬다.

## 2. 메커니즘 — Sim = 동결 계약, C++ = 최후 교체 (이 step 의 진짜 산출물)

```
                 [인프라 — 구체 시뮬 이름 0건]          [동결 계약 ISimCore v1]      [교체 가능 구현]
  클라 ─intent→ 게이트웨이 ─→ ZoneHost(권위) ───────────→ this.sim ───────────────→ ┌ DummySimCore  (객체맵, 오늘)
                          └─→ ZoneHost(추종자) ─────────→ this.sim ───────────────→ └ ArraySimCore  (SoA, C++ 스탠드인)
                                  ↑ run.makeSim ─── 단일 seam: 이 팩토리 하나만 바꾸면 구현이 갈린다
```

설계 결정 셋이 "Sim = 계약, C++ = 최후 교체"를 *불변*으로 만든다:

1. **계약과 호스트의 분리 = 회귀 0.** step-0002 `ZoneServer` 에서 *시뮬 계산*(spawn 초기상태·intent 적용·VM 전진·직렬화)만 `ISimCore` 뒤로 빼내고, 나머지(메시징·세션·소유자 장부·역할·뷰·해시)는 `ZoneHost`(인프라)에 남겼다. 더미 구현은 0002 계산을 *그대로* 옮긴 것이라 골든 해시·사슬이 비트 동일 — 추출은 순수 비-침습 리팩터(`reg` 통과). 권위 단일 소유는 *호스트*가 지킨다(소유자 장부는 시뮬 밖) — SPINE §5 ③ 정합.

2. **계약은 표현을 누설하지 않는다 — 두 구현으로 증명.** `DummySimCore`(객체맵)와 `ArraySimCore`(병렬배열=struct-of-arrays, C++ HktCore 가 `TArray` 로 짤 그 모양)는 *전혀 다른 내부 표현·코드 경로*지만 같은 (seed+호출열) → **비트 동일 serialize/해시**. `conf` 가 이를 trace 해시 교차 일치로 못 박는다(seed 42 → 둘 다 `0x2d68f3c7`). 핵심: rng 호출 순서(x→y)·iteration 순서·산술이 계약대로면 메모리 레이아웃은 무관 — *C++ 교체가 의존할 바로 그 성질*.

3. **교체는 단일 seam — 인프라 무수정.** 구체 시뮬을 이름으로 아는 곳은 `SIM_FACTORIES`/`run.makeSim` *하나*뿐. 인프라 7개 클래스(Net·Login·Registry·Gateway·ZoneHost·Client·Intruder) 소스에 `DummySimCore`/`ArraySimCore` 참조 **0건**(`swap` 가 `toString()` 스캔으로 구조 검사). 그래서 더미→array 교체는 팩토리 1줄 — 인프라·검증 하니스 코드는 1바이트도 안 바뀌고 두 구현 모두 골든·전 E2E(사슬·권위·은닉) 불변. 이것이 C++ HktCore 가 들어올 때 쓸 정확히 그 교체 경로다.

## 7. 의외의 발견

1. **"표현 무관"이 C++ 교체 안전성의 진짜 계약이다 — 그리고 그것은 rng 호출 순서에 민감하다.** 더미(객체맵)와 array(SoA)가 비트 동일 골든에 도달하는 조건은 *직렬화 형식*만이 아니라 **rng 호출 순서**였다. `ArraySimCore.spawn` 에서 x 를 y 보다 먼저 push 해야(더미의 객체리터럴 `{x:rng(), y:rng()}` 평가 순서와 일치) 같은 초기 좌표가 나온다 — 순서를 뒤집으면 trace 가 갈린다. 교훈: 동결할 계약은 "같은 입력 → 같은 출력"만이 아니라 **부수효과(난수 소비)의 순서**까지다. C++ HktCore 가 들어올 때 비트 동일을 깨는 첫 후보가 바로 이 *난수 소비 순서*이며, `conf` 의 cross-impl trace 일치가 그 회귀를 잡는 그물이 된다.
2. **소유자 장부를 호스트에 남긴 결정이 척추를 지켰다.** 권위 단일 소유(SPINE §5 ③)는 *시뮬*의 책임이 아니라 *인프라*의 책임이다 — 시뮬은 결정론 상태 전이만 하고, "누가 이 엔티티를 쓸 권위가 있는가"는 호스트(나중엔 코디네이션)가 안다. 그래서 추종자/권위 구분(`role`)이 시뮬 계약을 오염시키지 않았고(같은 `DummySimCore` 가 권위로도 추종자로도 쓰임), 미래의 권위 핸드오프도 시뮬 인터페이스 무변경으로 호스트 측에서만 일어날 수 있다.

## 8. 정직한 한계

1. **인터페이스는 동결됐지만 *최소*다.** 현 ISimCore v1 은 spawn/despawn/tick/liveIds/serialize 5개 — 단일 엔티티·단일 존·intent={dx,dy} 의 최소 표면이다. 실 HktCore 의 계약(PropertyId·`SetPropertyDirty`·이벤트·다중 엔티티 인터리빙)은 이보다 훨씬 넓다. 이 step 은 *교체 메커니즘(seam)*과 *표현 무관 불변*을 증명했지, 계약의 *완전성*은 아니다 — 후속 step 이 다중 엔티티·이벤트를 더하면 인터페이스는 버전이 오른다(v1→v2). 동결의 의미는 "불변"이 아니라 "버전 고정된 단일 교체 지점".
2. **array 구현은 C++ 의 *스탠드인*이지 C++ 가 아니다.** ArraySimCore 는 "메모리 레이아웃이 달라도 계약이면 비트 동일"을 JS 안에서 증명할 뿐, 실제 C++ 의 정수 오버플로·부동소수·`TArray` 순회 결정론은 미검증. UE-모듈-free 코어 분리(STATE §3 격차)가 선결이며, 진짜 C++ 교체는 그 step 의 일. 이 step 은 *그날의 교체가 인프라를 안 건드림*을 미리 보장한 것.
3. **단일 seam 검사는 정적 문자열 스캔이다.** `toString().includes('DummySimCore')` 는 인프라가 구체 시뮬을 *이름으로* 참조하지 않음을 보이지만, 동적 결합(전역 변수·프로토타입 오염)까지 막지는 못한다. 프로토타입 규모에선 충분하나, 실 코드에선 의존성 주입·인터페이스 타입으로 컴파일 타임에 강제해야 한다.
4. **전송은 여전히 무손실·즉시·순서보장** — 0001 §8.1·0002 §8.1 백로그 그대로. 동결된 이 인터페이스 *위에서* 지연·손실·재정렬을 다음에 자극한다.
5. **추종자 승격(failover)·N-추종자·다중 엔티티** — 0002 §8.3·8.4·8.5 한계 연장. 이 step 은 시뮬을 계약으로 박았을 뿐, 그 위의 분산 시나리오는 후속.

## 9. 다음 (step-0004 예고)
