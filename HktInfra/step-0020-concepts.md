# step-0020 concepts — Read-Model Persistence & Late-Join (CQRS recovery via the write log)

> 정식 기록: [step-0020.md](step-0020.md) · 현재 위치: [STATE.md](STATE.md)

## 개념 한눈표

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|------|-----------|---------------------|
| 읽기 모델(read model) | 권위 상태에서 *파생한* 질의용 투영(원장에 쓰지 않음) | RankingService.ranks(아바타→보유 수) |
| late-join / 복구 | 늦게 합류·재시작한 노드가 *과거를 따라잡아* 현재 상태에 도달 | 크래시한 ranking 이 저널 replay 로 투영 재구성 |
| 쓰기 모델 저널이 복구원 | 읽기 모델은 자기 영속 없이 *쓰기 모델*의 event log 로 재계산 | reconstruct(PersistStore.journal, snapshot) |
| 투영 fold(접기) | 하나의 효과 로그를 *여러* 읽기 형태로 환산 | mint→+1·xfer→from-1/to+1 = 보유 수 |
| 자기 영속 0(stateless read model) | 읽기 모델이 자기 상태를 저장하지 않아도 복구 가능 | ranking 은 RAM 만·persist 없음 → kill 후에도 복원 |
| 휘발 스트림 vs 내구 로그 | 버스 스트림은 지나가면 끝·저널은 남는다 | 다운타임에 놓친 svc.item.out 도 저널엔 있음 |

## 1. 읽기 모델은 왜 자기 영속이 필요 없는가 (이 step 의 핵심)

**무엇**: 0019 의 RankingService 는 *읽기 모델*(CQRS read model)이다 — 아이템 원장(쓰기 모델·권위)에서 파생한 "아바타별 보유 수" 투영을 RAM 에 유지한다. 이 투영은 원장에 *쓰지 않는다*(권위 아님). 0019 §9 는 이 투영이 영속 0 이라 크래시 시 소실됨을 한계로 남겼다.

**왜 중요한가**: 분산 시스템에서 모든 상태는 "죽으면 어떻게 되돌리나"를 답해야 한다. 권위 상태(원장)는 0017 에서 event sourcing 저널로 답했다(kill→replay). 그런데 *읽기 모델*은 다른 답을 가진다 — **자기 상태를 저장할 필요가 없다.** 왜냐하면 읽기 모델은 권위의 *함수*이고, 권위(의 효과 로그)가 영속돼 있으면 읽기 모델은 *언제든 다시 계산*되기 때문이다. 이것이 CQRS 의 깊은 성질이다: 읽기 측은 *버릴 수 있는 캐시*다 — 단, 쓰기 측 로그가 살아 있는 한.

**어떻게 검증했나**: `RankingService.crash()`(RAM 투영 소실) 후 `reconstruct(journal, snapshot)` 가 PersistStore 의 *쓰기 모델 저널*을 읽어 투영을 재계산한다. 복구된 ranks 가 원장 byOwner 와 *정확히 일치*(6아바타·faithful)함을 5시드에서 보였다. 대조군(persist OFF + 같은 kill)은 reconstruct 불가 → 투영 소실(rank 0). 즉 *영속이 복원의 원인*이되, 그 영속은 *읽기 모델 자신*이 아니라 *쓰기 모델*에 있으면 충분하다.

## 2. 같은 저널, 다른 투영 — fold 의 재사용

**무엇**: PersistStore 저널은 `{seq, kind:'mint'|'xfer', ...}` 효과 로그다(0017). 0017 의 `inventory.replay` 는 이 로그를 *원장*(itemId→owner)으로 접는다. 이 step 의 `ranking.reconstruct` 는 *같은 로그*를 *보유 수*(owner→count)로 접는다 — mint 면 owner +1, xfer 면 from −1·to +1.

**왜 중요한가**: 매핑이 우연이 아니다. 저널의 mint/xfer 는 가방이 *수락한* 효과만 담는다(실패 give 는 미기록) — 이는 ranking 이 라이브로 소비하던 `item_result`(ev.ok 게이트)와 *정확히 1:1* 이다. 그래서 "라이브 스트림 소비"와 "저널 replay"가 *같은 투영*을 만든다. 이것이 event sourcing 의 힘이다: 하나의 진실 로그가 여러 읽기 모델(랭킹·업적·통계·검색 인덱스…)을 먹이고, 새 읽기 모델도 *복구도* 발행자(쓰기 모델) 무수정으로 얹힌다.

**보너스 — 0018 압축의 공짜 적용**: reconstruct 는 inventory.replay 와 같은 (스냅샷 히스토그램 + tail) 경로를 탄다. 0018 이 저널을 (스냅샷+짧은 tail)로 유계화했으므로, 읽기 모델 복구도 tail 0~5항목만 replay 하면 된다. 데이터 계층의 개선이 두 step 뒤 읽기 모델에 *자동* 전파된다.

## 3. 휘발 스트림 vs 내구 로그 — 왜 버스가 아니라 저널인가

**무엇**: ranking 이 크래시한 동안 버스는 svc.item.out 을 계속 흘려보내지만 죽은 ranking 은 *못 받는다*(휘발: 지나가면 끝). 그런데 그 효과들은 가방이 PersistStore 저널에 *영속*했다. 그래서 reconstruct 의 복구원은 *버스 스트림*이 아니라 *내구 저널*이다 — 다운타임에 놓친 이벤트까지 *구조적으로* 복원된다.

**왜 중요한가**: 이것이 "이벤트 버스로 읽기 모델을 만든다"의 함정을 푼다. 버스만으로는 다운타임 이벤트가 영영 사라진다(버스 이력/replay 없음 — 0016 격차). 복구를 위해서는 *어딘가에* 재생 가능한 로그가 있어야 한다. 이 step 은 그 로그를 *쓰기 모델의 저널*에서 빌린다(읽기 모델 전용 영속을 새로 짓지 않고). 무엇이 복구의 진실 원천인지를 분명히 한다: **권위의 event log.**

**한계(정직)**: 검증은 *quiescent*(활동 정지) 재시작이다 — 활성 중 다운타임에 이벤트가 흐르고 reconstruct 후 클라 belief 를 재발행해 재수렴시키는 경로는 미착수. 복구원이 내구 저널임은 입증됐으니(faithful), 남은 건 다운타임 후 클라 통지 경로뿐이다.

## 한 줄 요약

읽기 모델(랭킹)은 *자기 영속이 0* 이어도 크래시에서 살아 돌아온다 — 권위(쓰기 모델)의 event 저널을 다시 접으면 투영이 재계산되기 때문(CQRS 읽기 모델 = 버릴 수 있는 캐시, 쓰기 로그가 살아 있는 한). 같은 저널이 원장과 랭킹을 모두 먹이고, 0018 압축이 복구까지 가속한다.
