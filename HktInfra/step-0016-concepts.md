# step-0016 개념 해설 — 이벤트 버스의 "서비스 의미"와 발행자 무수정

## 개념 한눈표

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|---|---|---|
| **이벤트 버스(서비스 의미)** | 서버끼리 주소가 아닌 *토픽*으로 결합하는 발행/구독 계약 | ServiceBus 박스 — 0012 토픽 *전송* 위에 올린 *의미* 층 |
| **전송 vs 의미** | 프레임을 나르는 층 ≠ 누가 무엇을 받는가의 계약 | broker(0012)=전송, ServiceBus(0016)=의미 — 독립으로 쌓임 |
| **N×N 직접 결합** | 발행자가 소비자 주소를 알고 직접 쏘는 그물 | 0014·0015 의 gateway↔service — 이 step 이 제거(직접 0) |
| **주소 무지(decoupling)** | 발행자는 토픽만 알고 소비자 주소·존재를 모름 | gateway spec 의 서비스 주소 = null(구조적) |
| **발행자 무수정 소비자 추가** | 새 구독자가 늘어도 발행자는 비트 하나 안 변함 | audit ON/OFF 에 spec·발신 스트림·결과 비트 동일 |
| **구독 라우팅 테이블(SSOT)** | `topic → [구독자…]` — 팬아웃의 단일 진실 | ServiceBus 의 핵심 자료구조(0015 채널 테이블의 서버 판) |
| **관찰 전용 소비자(발신 0)** | net.send 가 *없는* 소비자 — 되먹임이 구조적 0 | AuditService — "무수정" 증명의 도구 |
| **unrouted 폐기(at-most-once)** | 구독자 없는 발행은 버려짐 — 발행자는 모름 | pub/sub 의 정직한 기본 의미(이력·replay 없음) |
| **write-seam(inject)** | 검증 도구가 클라 intent 를 주입하는 1줄 이음새 | run()/runMulti() tick 직전 — 미제공=no-op(reg 0) |

## 1. 왜 버스인가 — 직접 결합은 *조용히* 자란다

0014 가 가방을, 0015 가 채팅을 존 밖으로 분리했다 — 신성한 tick 은 지켜졌다. 그런데 그 두 박스 모두 게이트웨이가 *서비스 주소를 알고* 직접 라우팅했다(`this.inventory`·`this.chat`). 박스가 2개일 땐 문제가 안 보인다. 하지만 길드·거래소·우편·랭킹이 늘 때마다: ① 게이트웨이에 주소·분기 추가 ② "아이템 이벤트를 랭킹도 받고 싶다" 면 *발행자(inventory)를 고쳐* 랭킹 주소로도 쏘게 해야 한다. 발행자 수 × 소비자 수의 그물(N×N)이 조용히 자란다 — 박스를 *분리*했는데 *결합*이 남는 역설.

SPINE §2 버스 행의 약속이 정확히 이것이다: "N×N 직접 RPC 그물 제거 — **새 소비자 추가가 발행자 무수정**". 이 step 은 그 약속을 게임 서비스 경로에서 실체화하고 *수치로* 증명한다.

## 2. 전송 vs 의미 — 0012 와 0016 은 다른 층이다

혼동하기 쉬운 지점: 0012 에서 이미 "토픽 pub/sub 버스"를 만들지 않았나?

- **0012 = 전송(transport).** broker 가 `cmd.<host>`/res 프레임을 토픽으로 라우팅한다 — *어느 소켓으로 바이트를 나르는가*의 층. 액터들은 여전히 서로의 *주소*(`net.send(from, to, …)`)로 말했다.
- **0016 = 의미(semantics).** 액터 층에서 gateway 가 `send('inventory', item_req)` 대신 `send('bus', {pub, topic:'svc.item', ev})` 를 쏜다 — *누가 이 이벤트를 받는가*를 발신자가 모르는 계약. ServiceBus 가 구독 테이블로 팬아웃한다.

멀티프로세스에선 이 둘이 *포개진다*: ServiceBus 액터(의미)가 broker 토픽 전송 위에 실려 돈다 — pub/sub 위의 pub/sub 인데 층이 섞이지 않는다. 전송이 바뀌어도(0010 IPC→0011 TCP→0012 토픽) 의미가 불변이었듯, 이제 의미가 더해져도 전송이 불변이다(broker 코드는 bus 를 특별 취급하지 않는다 — 범용 호스트). 이 직교성이 "인프라는 확장하되 깨지 않는다"의 구체적 모양이다.

## 3. 주소 무지 — 은닉 불변의 *서버간* 판

"클라는 게이트웨이만 안다"(은닉)는 0001 부터의 불변이다. 이 step 은 같은 원리를 *서버 사이*에 적용한다: **발행자는 토픽만 알고 소비자의 주소·존재를 모른다.**

구조적 증명이 두 겹이다:

1. **정적**: 버스 ON 토폴로지에서 gateway spec 의 `inventoryAddr/chatAddr = null` — 알 수 없는 것은 쓸 수 없다.
2. **동적**: net.log 에서 gateway↔service 직접 메시지가 **0**(버스 OFF 대조군은 409~427건). 결합 제거가 선언이 아니라 와이어 사실이다.

소비자가 없으면? 발행은 *폐기*된다(unrouted). 이것이 pub/sub 의 정직한 기본 의미다 — 발행자는 "누가 받았나"는 물론 "누가 있나"도 모른다. (그래서 신뢰 전달이 필요한 경로는 별도 프로토콜이 필요하다 — §6 한계.)

## 4. "발행자 무수정 소비자 추가" — 슬로건을 비트 명제로

이 step 의 가설 검증에서 가장 중요한 개념. "새 소비자를 붙여도 발행자를 안 고친다"는 보통 아키텍처 슬로건인데, 결정론 하니스에선 **비교 가능한 비트 명제**가 된다. AuditService(새 소비자)를 켠 런과 끈 런을 나란히 돌려:

| 층 | 비교 대상 | 증명하는 것 |
|---|---|---|
| 정적 | 발행자들의 spec JSON | 구성을 안 고쳤다 |
| 동적 | 발행자별 발신 스트림 다이제스트(내용+순서) | 발신 *행동*이 비트 하나 안 변했다 |
| 의미 | world/원장/deliveries 다이제스트 | 게임 결과가 같다 |
| 수신 | audit.seen[토픽] == net.log 의 토픽별 발행 수 | 소비자는 *전수*를 받았다 |

넷이 동시에 성립해야 "무수정 추가"다. 정적 비교만으로는 "코드는 같은데 타이밍이 변했다"를 놓치고, 수신 검증이 없으면 "아무것도 안 하는 소비자라 무수정"이라는 공허한 증명이 된다.

AuditService 가 *발신 0*(net.send 호출 코드가 없음)인 것도 설계다 — 0014 가 "신성한 tick"을 *onTick 의 부재*로 증명했듯, 비-침습을 *능력의 부재*로 증명한다. 받은 이벤트로 무엇을 하든 발행자·월드로 되먹임할 방법이 구조적으로 없다. (대가: *발신하는* 소비자의 순서/루프 문제는 미검증 — 후속.)

## 5. 같은 자료구조, 세 번째 등장 — 라우팅 테이블의 일반성

| step | 테이블 | 단위 | 보장 |
|---|---|---|---|
| 0012 | `topic → Set<sock>` (broker) | 전송 프레임 | 주소 무지 전송 |
| 0015 | `channel → Set<avatar>` (chat) | 클라 메시지 | 비-구독자 누설 0 |
| 0016 | `topic → [subscriber…]` (ServiceBus) | 서버 이벤트 | 직접 결합 0·발행자 무수정 |

세 번 다 "**순회 대상이 곧 도달 집합**" — 누설/오라우팅을 막는 것이 필터가 아니라 자료구조다. 채팅 팬아웃이 이미 pub/sub 골격이라 버스 승격이 자연하다던 STATE 의 가설이 코드에서 그대로 확인됐다: ChatService 의 `_sub`/팬아웃 루프와 ServiceBus 의 그것은 단위만 다른 같은 모양이다.

검증 항목도 패턴을 따른다: 자료구조가 공짜로 주는 것(누설 0·직접 0)은 *교차검증*하고, 공짜가 아닌 것(완전성 — 소비자가 전수를 받았나, E2E 비트 동일)을 *증명*한다.

## 6. 신뢰성 모델은 끝점의 것 — 버스를 끼워도 변하지 않는다

gateway↔service 1홉이 gateway↔**bus**↔service 2홉이 되면 손실 표면이 늘어난 듯하다. 그러나 `degrade`(버스 홉 loss 0.2·redundancy 3)가 보인 분리는 0014·0015 와 동일하다:

- **loss-직교(보존)**: 누설/phantom 0 — 라우팅 정확성은 테이블 순회의 성질. 원장 보존/정합·belief 소유 ≤1 — 끝점 자료구조(원장 멱등·belief Set 키 충돌)의 성질.
- **graceful(열화)**: 완전성(itemDesync·chatDesync > 0) — ack/resend 가 없는 한 손실은 복원 안 됨(0015 best-effort 상속 + unrouted 폐기).

교훈: **신뢰성은 경로 길이가 아니라 끝점이 결정한다.** 버스는 *라우팅 의미*를 바꿨지 *신뢰성 모델*을 바꾸지 않았다 — 신뢰 전달이 필요하면 끝점에 시퀀스/ack 를 더해야 하고(후속), 버스에 더하는 게 아니다.

대신 버스는 *새 단일점*을 만들었다 — 서비스 트래픽 전체가 한 프로세스를 지난다. 분리(0014·0015)가 결합(이 step)을 낳고, 결합 제거가 단일점을 낳는다 — 각 step 의 해법이 다음 step 의 격차가 되는 시리즈의 리듬 그대로(버스 분산·failover 후속).

## 7. write-seam(inject) — 동결 불변 아래에서 도구를 심는 법

부록 격이지만 방법론적으로 중요하다. 테스트베드의 시나리오 `inject`(클라 intent 주입)는 net-core 의 *쓰기 이음새*가 필요했는데, 닫힌 step 은 수정 불가(동결)고 run.js 단독 구현은 "둘째 구현 0" 위배였다. 해법은 0011 의 onTick 선례와 같다: **다음 복사 전진에서 reg-safe 이음새를 심는다** — `opts.inject` 미제공이면 호출 0(비트 불변, `reg` 25/25 가 증명), 제공되면 run()/runMulti() 의 *같은 위치*에서 주입(멀티프로세스도 비트 동일). 주입이 클라 발신과 같은 형식이라 "명령도 시드 로그의 일부"(결정론) 원칙이 지켜진다. 동결·회귀 0·둘째 구현 0 세 제약이 충돌할 때, *시간축*(다음 step 의 복사 전진)이 출구라는 것 — 이 시리즈의 동결 규율이 만드는 고유한 작업 리듬이다.
