# step-0106 — 귓속말 라우터 공지 epoch 펜싱(announceEpoch·라우터 메아리 정리)

> 직전: [step-0105](step-0105.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0105 는 presmon 의 active 공지 메아리를 epoch 으로 닫았다 — 그러나 *같은 svc.presence.active 채널의 둘째 소비자* wrouter(0072 whisperFailover)도 공지를 *무조건* 받아 queryAddr 를 재타깃하고 보류 질의를 재발신한다. 낡은/메아리 공지가 도착하면 죽은 박스로 역-재타깃되고 재시도가 죽은 주소로 폭주한다(0072 §9). 디스커버리 채널의 *모든* 소비자에 펜싱을 일관 적용할 수 있는가? SPINE 계층3·5 라우팅 읽기 경로의 메아리 안전.

## 2. 메커니즘 — 라우터 공지 펜싱 (announceEpoch OFF → baseline 비트 동일 = 회귀 0)

**구현**: ⒜ `src/svc-whisper-core.js` — wrouter 에 `activeEpoch`(-1)·`staleAnnounces` 필드 추가. ⒝ `src/svc-whisper-handlers.js` — svc.presence.active 핸들러에서 `ev.epoch != null` 이면 *본 최고 epoch 이하* 공지를 메아리로 거부(`staleAnnounces++`·return·재타깃/재시도 안 함), 더 높은 epoch 만 `activeEpoch` 갱신 후 재타깃+보류 재발신. epoch 없으면(0072) 무조건 재타깃(비트 동일). ⒞ `src/topology.js` — `whisperAnnounceStraggler` 훅으로 지연/메아리 공지를 wrouter 에 직접 주입.

0105 presmon 펜싱과 *동일 메커니즘*을 같은 채널의 둘째 소비자에 적용 — 공지 epoch 은 0105 에서 이미 presence 박스가 싣는다(추가 발행자 변경 0).

## 4. 척추 체크 5항

① **신성한 tick** — 펜싱은 wrouter(존 tick 밖) 순수 반응형. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF). ③ **권위 단일 소유** — queryAddr 는 읽기 디스커버리 뷰(원장/권위 무관). ④ **은닉·단일 연결** — 공지는 버스 토픽, wrouter 무수정 구독. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 같은 발행(svc.presence.active + epoch·0105)에 *발행자 무수정*으로 둘째 소비자(wrouter)가 같은 펜싱을 얻었다 — 0016 "발행자 무수정 소비자" 패턴이 펜싱 *로직*에도 적용됨을 보인다(presmon·wrouter 가 같은 epoch 규약을 독립 honor). 디스커버리 채널의 일관성은 *공지 규약*(epoch 동반)에서 나오고, 각 소비자는 그 규약을 지키기만 하면 된다 — 중앙 조정 없이 채널 전체가 메아리 안전.
- **한계**: presmon(0105)·wrouter(0106)가 펜싱 로직을 *각자* 들고 있다(코드 중복) — 공지 epoch 펜싱을 공통 헬퍼(engine 승격)로 빼면 DRY 이지만 이번엔 두 박스에 인라인(셋째 소비자 추가 시 정리 step 후보). 또한 epoch=promotedAt(tick)의 단일 클럭 가정은 0105 와 동일(논리 클럭 term 이 진짜 해법·🔴). 주입은 인프로세스 직접 호출(straggler 훅)·실 버스 재정렬 E2E 는 후속.
