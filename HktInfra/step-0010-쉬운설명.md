# step-0010 쉬운 설명 — "여러 컴퓨터처럼 진짜로 나눠 돌려보기"

> 이 문서는 [step-0010.md](step-0010.md)(시리즈 정식 기록, 압축적·전문적)를 **비유와 쉬운 말로 풀어 쓴 해설**이다.
> "이번에 뭘 했고, 왜 했고, 어떻게 확인했나"를 처음 보는 사람도 이해할 수 있게.

---

## 0. 한 줄 요약

지금까지 우리 게임 서버들(로그인·게이트웨이·존·…)은 **사실 한 프로그램 안에 사는 객체**였다. 이번 step 에서 그것들을 **진짜로 따로 도는 별개의 프로그램(프로세스)** 으로 쪼개고, 서로 **편지(직렬화 메시지)** 로만 대화하게 만들었다. 그런데도 결과가 **쪼개기 전과 글자 하나 안 틀리게 똑같다**는 걸 증명했다.

---

## 1. 비유로 먼저

### 쪼개기 전 (step-0001 ~ 0009)

큰 회사를 상상하자. **접수처(로그인), 안내데스크(게이트웨이), 1팀·2팀(존), 백업 직원, 관리자(orch)** 가 있다. 그런데 지금까지 이 사람들은 전부 **한 명의 머릿속에 있는 상상의 인물**이었다. 한 사람이 "이제 접수처 역할" "이제 안내데스크 역할" 하며 1인극을 한 셈이다.

이렇게 1인극으로 한 이유는 — **대본(프로토콜)이 제대로 굴러가는지** 먼저 싸고 빠르게 확인하려고. 실제로 사람을 여러 명 고용하고 사무실을 나누면 검증이 느리고 복잡해진다. 그래서 "일단 혼자 다 연기해서 대본부터 완성하자"가 0001~0009 였다.

### 쪼갠 후 (step-0010, 이번)

이제 진짜로 **사람을 따로 고용**했다. 접수처 직원, 안내데스크 직원, 1팀 직원… 각자 **다른 방(다른 프로세스)** 에 앉아 있고, 서로 얼굴도 못 본다. 대화는 오직 **쪽지(메시지)를 우편으로 주고받는 것**뿐이다. 옆방 사람의 책상 서랍을 직접 열어볼 수 없다(= 메모리 공유 0).

**놀라운 점**: 1인극으로 돌렸을 때와 여러 명이 우편으로 돌렸을 때의 **최종 결과가 완전히 똑같다.** 회의록(로그) 한 줄까지 동일하다.

---

## 2. 왜 이게 중요한가?

우리의 큰 목표는 "그림 속 멋진 분산 서버"가 아니라 **"진짜로 따로 돌고, 서로 완전히 통신하며, 원격에서 검증되는 인프라"** 다([CLAUDE.md](CLAUDE.md) 큰 목표).

- **한 프로그램 안의 객체**는 아무리 잘 짜도 결국 한 컴퓨터의 한계에 갇힌다(한 사람이 모든 일을 하면 모든 일이 서로의 병목).
- **진짜 프로세스로 나뉘면** 나중에 각각을 다른 컴퓨터·다른 나라 서버로 옮길 수 있다. 그게 오픈월드 MMO 가 수만 명을 받는 방법이다.

이번 step 은 그 "진짜로 나누기"의 **첫 실현**이다. 그리고 나누면서도 **기존에 증명한 모든 것(권위 이동·시야 동기화·손실 복원·서버 사망 시 백업 승격)이 그대로 작동**함을 보였다.

---

## 3. 무엇이 어려웠나? — "따로 돌리면 결과가 달라지지 않나?"

여러 사람이 동시에 일하면 보통 **순서가 뒤죽박죽**이 된다. A가 먼저 보낸 편지가 B의 편지보다 늦게 도착하기도 한다. 게임에서 순서가 틀어지면 → 두 플레이어가 **다른 세계**를 보게 된다(desync). 이건 치명적이다.

그래서 핵심 질문은: **"진짜로 나눠 돌려도 결과가 안 틀어지게 할 수 있나?"**

---

## 4. 어떻게 해결했나 — "우체국 박자 맞추기(broker)"

해법은 **broker(중앙 우체국 겸 박자 지휘자)** 를 두는 것이다.

```
        ┌─────────────  broker (우체국 + 박자 지휘자)  ─────────────┐
        │  "이번 박자(tick)에 받을 편지들을 순서대로 나눠준다"          │
        │  "각 방의 답장(새 편지)을 다시 원래 순서대로 모아 정리한다"     │
        └──┬──────────┬──────────┬──────────┬────── … ──────────────┘
        편지(우편)   편지        편지        편지       ← 메모리 공유 0
      ┌────▼───┐ ┌───▼────┐ ┌───▼────┐ ┌───▼────┐
      │ 접수처  │ │안내데스크│ │  1팀   │ │ 관리자 │  …  각 방 = 진짜 별개 프로그램
      └────────┘ └────────┘ └────────┘ └────────┘
```

매 박자(tick)마다 broker 가 하는 일:
1. **나눠주기**: 이번 박자에 처리할 편지들을, 받는 사람(방)별로 묶어서 **순서표(번호표)를 붙여** 전달한다.
2. **각 방이 일 처리**: 각 방은 받은 편지를 읽고(onMsg), 자기 차례 일을 하고(onTick), 보낼 새 편지를 **번호표와 함께** 돌려준다.
3. **순서대로 다시 정리**: broker 가 모든 방의 답장을 모아 **번호표 순서대로** 다시 줄 세운다.

이 **"번호표로 순서를 강제하는 것"** 이 핵심이다. 여러 방이 동시에 일해도, 편지의 최종 순서는 **혼자 1인극 할 때와 똑같이** 유지된다. 그래서 결과가 글자 하나 안 틀린다.

> 비유: 합주단이 여러 명이어도 **지휘자가 박자를 맞추면** 혼자 녹음한 것과 똑같은 곡이 나온다. broker 가 지휘자다.

## 5. 어떻게 "진짜로 나뉘었다"고 확신하나?

말로만 "나눴다"가 아니라 **숫자로 증명**했다(`node verify.js`).

| 확인 항목 | 쉬운 말 | 결과 |
|---|---|---|
| **회귀 0** (`reg`) | "1인극 모드는 예전(step-0009)과 글자 하나 안 틀리나?" | ✅ 20가지 경우 전부 동일 |
| **E2E 동치** (`e2e`) | "여러 명으로 나눠 돌린 결과 = 1인극 결과? (글자까지)" | ✅ 회의록 해시·최종 상태 전부 동일 |
| **프로세스 분리** (`isolate`) | "진짜로 각자 다른 프로그램인가? (운영체제가 준 고유번호 PID 가 다 다른가?)" | ✅ 9개 방 = 9개 다른 PID, 우체국과도 다름, 대화는 편지(직렬화)뿐, 책상 공유 0 |
| **은닉** (`hide`) | "쪼개도 손님(클라)은 내부 사정을 모르나?" | ✅ 손님은 여전히 안내데스크만 안다, 누설 0 |
| **재현** (`repro`) | "같은 입력이면 늘 같은 결과인가? (운빨 없나?)" | ✅ 두 번 돌려도 동일, 게다가 step-0009 결과와도 일치 |

특히 마지막이 강력한 교차 증거다 — 여러 프로세스로 나눠 돌린 최종 상태값(`0x14c8832e` 등)이 **step-0009 의 단일 프로세스 결과와 정확히 일치**한다. 진짜로 나눴는데 결과는 똑같다는 뜻.

그리고 이 모든 검증이 **`node verify.js` 명령 한 줄**로, 이 원격 환경에서 돈다(약 6초). 특별한 컴퓨터·게임 엔진 빌드가 필요 없다 — 이게 우리가 지키려는 "원격에서 검증된다"는 제1 원칙이다.

## 6. 직접 보고 싶다면

- **브라우저로**: `step-0010.html` 파일을 그냥 더블클릭해 열면 된다. 각 박스가 프로세스, 박스 사이 선이 "프로세스 경계를 넘는 편지(IPC)"다. 빨간 ✝ 는 죽은 서버, 주황 ▲ 는 승격한 백업 서버. 아래 막대그래프는 박자마다 오간 편지 양.
- **터미널로**: `node step-0010/panel.js 42` → 글자로 그린 요약(어느 프로세스끼리 편지를 얼마나 주고받았는지).
- **검증**: `node step-0010/verify.js all` → 위 표의 모든 항목이 ALL OK 로 뜬다.

## 7. 솔직한 한계 (아직 안 한 것)

이번에 한 건 "**진짜 프로세스로 나누기**"까지다. 다음은 아직 못 했다:

1. **우체국(broker)이 박자를 다 맞춘다** — 진짜 실시간 비동기(각자 자기 속도로)가 아니라, 결정론 검증을 위해 "다 같이 한 박자씩" 가는 방식이다. 진짜 자유 실행은 다음 과제.
2. **편지가 아직 "같은 건물 안 사내 우편(IPC 파이프)"** — 진짜 인터넷 소켓(TCP)이나 메시지 버스(NATS 등)는 아니다. 와이어만 바꾸면 되는 자리는 마련됐다.
3. **우체국이 하나뿐** — 진짜 분산이면 우체국도 여러 개(버스)여야 한다.
4. **서버 "죽음"은 아직 연기** — 진짜로 프로그램을 강제 종료(kill)하는 게 아니라, "이 박자부터 일 안 함"으로 흉내 낸다(결정론 검증을 위해). 진짜 kill 은 다음.
5. **여전히 Node** — 진짜 게임 시뮬레이션 코어(C++)는 아직 안 갈아끼웠다(맨 마지막에 교체할 자리로 비워둠).

이 한계들이 바로 **다음 step 들의 후보**다([STATE.md](STATE.md) §2). 가장 유력한 다음은 "사내 우편 → 진짜 인터넷 소켓/버스로 바꾸기".

---

## 8. 한 문단 정리

게임 서버들을 **한 프로그램 안의 1인극**에서 **진짜 따로 도는 여러 프로그램**으로 쪼갰다. 서로 편지(직렬화 메시지)로만 대화하고 서랍은 못 연다(메모리 공유 0). 중앙 우체국(broker)이 박자와 편지 순서를 맞춰주는 덕에, 쪼갰는데도 결과가 1인극 때와 **글자 하나 안 틀리게** 똑같다(비트 동일). 그리고 지금까지 만든 모든 기능 — 플레이어가 존 경계를 넘을 때 권위 넘기기, 시야 동기화, 통신 손실 복원, 서버 죽으면 백업 승격 — 이 **프로세스 경계를 넘어서도 그대로 작동**한다. 명령 한 줄로 원격에서 9개 프로세스를 띄워 이 전부를 숫자로 증명했다.
