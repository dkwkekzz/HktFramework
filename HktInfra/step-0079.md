# step-0079 — 전달 포기 통지: 발신자가 아는 실패(deliverNotify·deliveryFailed)

> 직전: [step-0078](step-0078.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0078 의 포기(undeliverable)는 라우터 *내부 계측*일 뿐 — 귓속말을 보낸 클라는 전달이 영영 실패했음을 모른다(0078 §9). 포기를 *발신자에게 가시화*하면, 클라가 "상대에게 끝내 닿지 못함"을 아는가? (닫는 조건: 상한 도달 포기 시 원 발신자에 deliveryFailed 회신·발신 클라 events 에 'deliveryFailed' 수신·deliverNotify OFF=0078 비트 동일)

## 2. 메커니즘 — 포기 통지(플래그 `deliverNotify` OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-whisper.js`** — `deliverNotify` opt·`failedNotified` 계측. onTick 의 포기 분기(`tries>=deliverMaxRetries`)에서 inflight 제거·undeliverable++ 후: deliverNotify ON 이면 원 발신자(`e.from`)에 `{type:'deliveryFailed', to:e.to, body:e.body}` 회신(`failedNotified++`). inflight 엔트리는 이미 `from`(원 발신자) 보유(0076). OFF 면 통지 0 = 0078 비트 동일.
- **배선(`topo-build.js`)** — `deliverNotify` 플래그. wrouter opt 로 전달. 미설정 = 0078 비트 동일.
- **수신측**: Client.onMsg 가 모든 payload.type 을 `events` 에 적재 — deliveryFailed 도 발신 클라의 events 에 들어가 *발신자 가시성*을 직접 검증.

## 4. 척추 체크 5항

1. **신성한 tick** ✅ — 통지는 라우터 onTick(제어 평면) 안 — 존 시뮬 tick 무관.
2. **결정론 코어** ✅ — 통지는 세계 상태 무변경. 정규 net.send(시드 로그) — 같은 시드 같은 해시.
3. **권위 단일 소유** ✅ — 통지는 *전달 실패 알림*만(원장 무관·minted ON==OFF). 권위 0.
4. **은닉·단일 연결** ✅ — 클라는 자기가 보낸 귓속말의 *결과*(deliveryFailed)를 라우터에서 직접 받는다(은닉 유지 — 라우터 내부 미노출).
5. **headless·원격 검증** ✅ — Node·UE 0. `node run.js`/`spine` 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **통지는 point-to-point(발행 아님)**: deliveryFailed 는 발신자에게만 간다 — 감사/모니터가 전달 실패율을 보는 *발행*(svc.delivery 토픽·0060 presencePublish 의 전달 판)은 미착수. 운영 관측(전달 실패 메트릭)은 후속.
- **bounce(반송)와 의미 구분**: 0071 의 bounce 는 *도달 불가 즉시*(대상 permanent), 0079 의 deliveryFailed 는 *유계 재시도 소진 후*(대상 up 이었으나 전달 실패) — 둘은 다른 실패 양상이나 클라 입장에선 모두 "안 닿음". 클라가 둘을 구분해 다루는 UX(재시도 권유 vs 오프라인)는 미착수.
- **여전히 at-least-once(중복 가능)**: ack 손실 시 중복 전달은 이 step 도 해소 안 함 — 수신측 dedup(exactly-once·0026 패턴)은 별도.
- **파티 1:N 미적용**: 통지는 1:1 귓속말 경로만 — 파티 부분 전달의 멤버별 실패 통지(0073 위)는 멤버별 inflight/통지 집계가 선결.
