> 직전: [step-0149](step-0149.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0142~0149 가 우편 박스(입금→수령→발행→영속→압축→읽음발행→만료TTL→만료발행)를 쌓았다. 그 회계가 *대수적으로 닫혀* 있는가? 이번 한 조각(capstone): `mailConsistent` — 우편 1통은 매 순간 정확히 한 상태에 있다 — **보유(held)·수령(fetched)·만료(expired)** 으로 분할되며 공백·중복 0. `sent == totalHeld + fetched + expired` 가 *모든 체제*(수령만·만료만·혼합·crash 복구)서 성립. 거래소 0140(sagaLiveConsistent)의 우편 판. 닫는 조건: 가설 `exmail`(4체제 mailConsistent true + 분할 카운트 일치 + crash 복구 정합)·미호출 accessor = 0149 비트 동일.

## 2. 메커니즘 — mailConsistent 단언용 read accessor(미호출 → 0149 비트 동일 = 회귀 0)

- **`svc-mail.js`**: `mailConsistent()` — `sent === totalHeld() + fetched + expired`(0143 accountConsistent 와 동치이나 capstone 의 명시 이름). 우편 1통이 매 순간 정확히 한 상태(보유/수령/만료)에 분할됨을 단언하는 *읽기 accessor*.
- **회귀 0 구조**: 새 accessor 는 정상 run 에서 *호출되지 않는다* → 우편 박스 동작 0149 비트 동일. mail OFF → 박스 0. capstone 은 코드를 *더하지 않고 불변을 단언*(거래소 0128·0140 capstone 패턴).

## 9. 의외의 발견 / 정직한 한계

- **우편 arc(0142~0150) 완성** — SPINE §2 게임 서비스 *우편* 박스가 입금/수령/발행 3종(sent·read·expired)/영속·압축/만료 TTL/회계 정합 capstone 으로 섰다. 거래소 arc(0107~0140)와 *동형 골격* — 서비스 박스 패턴(분리→수명주기 발행→영속/압축→만료→회계 정합)의 재현력을 두 번째로 입증.
- 남은 우편 백로그(블로킹 아님): 클라↔게이트웨이 우편 와이어 계약·아이템 우편(가방 연동 give·만료 시 발신자 반환)·미수령 알림 배지(읽기 모델)·우편 정렬/페이지네이션. 거래소↔가방(0117~0120) 류 2-서비스 보존이 아이템 우편의 다음 자연 확장.
- accountConsistent 와 mailConsistent 가 동치 코드다(이름만 다름) — capstone 의 명시 이름을 둔 것은 거래소 0128/0140 의 명명 관례를 따른 것(리뷰 가독성). 향후 만료 시 아이템 반환이 더해지면 capstone 이 2-서비스 보존(open≡escrow 류)으로 강화될 자리.
