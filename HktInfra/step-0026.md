# step-0026 — in-flight mint 손실 복구: 클라 id-reconciliation

## §1 조각 요약

write-behind 신뢰성 체인의 마지막 조각. 서비스 crash 직전 *mint* 저널이 persist 에 도달하지 못한 경우, 재시작 후 복구 원장은 그 itemId 를 모른다. 클라는 라이브 ack 로 이미 확인했으므로 belief 에 그 id 가 남아 있다. id-reconciliation 프로토콜로 이 불일치를 해소한다:

1. 클라가 보유 itemId 목록(`owned`)을 `item_reconcile` 메시지로 서버에 선언
2. 서버는 원장에 없는 id 를 새 id 로 *re-mint* → `item_recon_map({ oldId, newId })` 응답
3. 클라가 belief 에서 `oldId → newId` 교체 → itemDesync 0, per-avatar count = 무손실 truth

## §2 프로토콜 플로우

```
[crash+restart+XMINTLOSS]
        ↓
Client A.items = {item1, item3}   (라이브 ack 로 확인된 belief)
Server ledger = {item0→B}         (xfer replay 만 생존·mint 전량 손실)
        ↓
clientResync 트리거 (tick RESTART_AT+2)
Client A → gateway → inventory:  { type:'item_reconcile', owned:['item1','item3'] }
        ↓
inventory._reconcile:
  mintTotal floor 보정: max(owned IDs) + 1 → mintTotal ≥ 4
  item1: ledger 없음 → re-mint 'item4', journal({kind:'mint',itemId:'item4',owner:A})
  item3: ledger 없음 → re-mint 'item5', journal({kind:'mint',itemId:'item5',owner:A})
  → _out({ type:'item_recon_map', reqAvatar:A, mappings:[{item1→item4},{item3→item5}] })
        ↓
gateway → Client A:  item_recon_map
Client A: items.delete('item1'), items.add('item4'); items.delete('item3'), items.add('item5')
        ↓
ledger = {item0→B, item4→A, item5→A} · Client A.items = {item4,item5} → itemDesync 0
```

## §3 버그 수정 2건

### ① mintTotal=0 충돌 (replay xfer 미추적)

`replay()` 가 `kind:'mint'` 항목에서만 `maxMintId` 를 갱신했다. XMINTLOSS 로 mint 항목 전량 손실 시 `maxMintId=-1 → mintTotal=0`. xfer replay 로 복원된 item0 이 있으면 re-mint 'item0' 발급 → ID 충돌 → `ledgerConsistent` 실패.

**fix**: `xfer` 브랜치에도 `maxMintId` 갱신 추가.

### ② mintTotal 하한 미보정 (owned ID 범위 초과)

xfer 항목으로 mintTotal 이 보정되더라도 클라가 신고한 owned ID 가 mintTotal 보다 크면 동일 충돌 발생. 예: item0 give → mintTotal=1, 클라가 {item1,item3} 신고 → 'item3' 으로 re-mint → 실제 item3 이 skip.

**fix**: `item_reconcile` 핸들러 초입에 `owned` 최대 ID 스캔 → `mintTotal = max(mintTotal, maxOwned+1)`.

## §5 척추 체크 5항

1. **신성한 tick**: `item_reconcile` 은 존 tick 밖(클라 제어 평면 트리거·가방 비동기 onMsg). 존 net.log·world 상태가 mintRecon on/off 에 비트 동일.
2. **결정론 코어**: re-mint ID 는 `mintTotal` 단조 증가 — 동일 seed·동일 crash 시점 = 동일 newId 시퀀스.
3. **권위 단일 소유**: 원장 SSOT 는 InventoryService 만. re-mint 도 `_journal` → PersistStore → replay-safe.
4. **은닉·단일 연결**: 클라는 `item_reconcile/item_recon_map` 만 봄. 서비스 내부 `mintTotal`, `byOwner`, `journal` 비공개.
5. **headless·원격 검증**: node run.js 인프로세스 + 멀티프로세스 E2E 모두 ALL OK.
