# step-0021 — 채팅 서비스 영속·failover (ChatService crash→커맨드 로그 replay — 라우팅 테이블+deliveries 의 event sourcing 복구)

> 직전: [step-0020](step-0020.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0017 이 가방(InventoryService)에, 0020 이 랭킹(읽기 모델)에 영속·failover 를 줬으나, **채팅의 구독 라우팅은 여전히 영속 0**이었다(§3 🟡 "채팅 구독·버스 라우팅은 영속 0"). 이 step 은 *서비스 복구 3부작의 마지막*으로 채팅에 영속·failover 를 준다. 핵심 차이는 복구 대상의 *성질*이다: 가방은 *효과 로그*(mint/xfer — 값 보존)를 replay 했지만, 채팅의 복구 대상은 **구독 라우팅 테이블**(channel→Set<avatar>)이고 say 의 팬아웃은 *그 시점 라우팅에 의존*한다. 그래서 채팅은 *커맨드*(join/say/whisper/leave)를 저널하고, replay 가 **리듀서를 재실행**해 라우팅과 deliveries 를 재유도한다(순수 event sourcing).

**닫는 조건**: ① chatpersist OFF → 0020 비트 동일(회귀 0 — onMsg→_process 리팩터·crash/replay 비-침습) ② 채팅 진짜 kill→커맨드 로그 replay 후 복구 라우팅+deliveries == 무재시작(복구 투명·chatDigest 비트 동일) ③ chatpersist OFF+kill 대조군은 구독/배달 *소실* ④ 복구 후 say 가 올바로 팬아웃(비-구독자 누설 0·지역 격리) ⑤ 멀티프로세스 kill→replay = 인프로세스 crash()+replay() 비트 동일.

## 2. 메커니즘 — ChatService 커맨드 소싱 (chatpersist OFF → 0020 비트 동일 = 회귀 0)

한 조각 = **채팅 서비스 영속·failover**. 더한 박스 로직은 `ChatService.crash()/replay()` + 단일 리듀서 `_process` + chatRestart 훅(`engine/` 무수정).

1. **단일 리듀서 `_process(op)`** — `onMsg` 를 정규화(페이로드→커맨드)와 `_process`(상태 변이 + `_deliver` 팬아웃 + `_journal` 커맨드 로그)로 갈랐다. live(onMsg)와 복구(replay)가 *같은 리듀서*를 써 로직 분기 0(divergence 위험 제거). 동작은 0020 onMsg 와 비트 동일.
2. **커맨드 로그(`_journal`)** — 처리한 효과 커맨드(join·say·whisper 전달·실제 leave)를 chatpersist 로 write-behind(fire-and-forget·ack 비대기·신성한 tick 밖). 가방이 *효과*를 적었다면 채팅은 *커맨드*를 적는다(라우팅 의존 팬아웃 → 재유도 필요).
3. **crash()/replay(journal)** — crash 는 라우팅·역인덱스·deliveries·계측 비움. replay 는 커맨드 로그를 seq 순서로 `_process` 재실행하되 `replaying` 플래그로 *재발신 0*(deliveries/팬아웃 계측만 재현). replay = §4 "복제=재현"(상태 전송 아님).
4. **chatRestart 훅** — invRestart 와 *같은 위치*(deliver 직전·제어 평면·net.log 비-기여): `chat.crash()` 후 `if (chatpersist) chat.replay(...)`. OFF 면 replay 없음 = 구독/배달 소실(대조군). 멀티프로세스(cluster.js)는 채팅 호스트 진짜 kill→chat_r spawn·init·`cmd:'replay'`(host 의 'replay' 재사용 — chat.replay 는 snapshot 무시).

월드·가방 영속/압축(0017~0018)·버스·발행/구독(0019)·읽기 모델 복구(0020) *무변경*. inject seam 그대로.

## 9. 의외의 발견 / 정직한 한계

- **발견 — 효과 소싱 vs 커맨드 소싱은 *상태의 성질*이 가른다**: 가방(0017)은 *효과 로그*(mint/xfer)를 replay 했다 — 값 보존 원장이라 효과를 그대로 재적용하면 된다. 채팅은 *커맨드 로그*(join/say/…)를 replay 한다 — say 의 팬아웃이 *그 시점 라우팅*에 의존하므로, 효과(deliveries)를 직접 저장하는 대신 *커맨드를 재실행*해 deliveries 를 다시 유도해야 한다. event sourcing 의 "무엇을 로그할까"는 상태가 *값*인가 *라우팅 의존 파생*인가에 달렸다.
- **발견 — 단일 리듀서 공유가 복구 정확성의 토대**: live(onMsg)와 복구(replay)가 *같은 `_process`* 를 쓰므로 "라이브 처리"와 "복구 재실행"이 *구조적으로 같은 코드*다 → 분기 divergence 0. 다른 코드 경로였다면 미묘한 불일치(예: 발신자 제외 규칙·지역 채널 해석)가 복구 desync 를 낳았을 것. replaying 플래그 하나로 *재발신만* 끄고 상태 재현은 동일.
- **발견 — 라우팅 복구의 정확성은 *작동적으로* 검증된다**: 가방 복구는 원장 값 일치(invDigest)로 충분했지만, 라우팅 테이블 복구는 "복구 후 새 say 가 올바른 구독자에게만 가는가"(누설 0·격리)로 검증해야 진짜다 — 자료구조 일치를 넘어 *작동적* 정확성. chatDigest(투명) + chatLeak 0(작동)의 두 축으로 본다.
- **한계 — quiescent restart 만(0017/0020 과 동일)**: chatRestart 는 채팅 정지 후 늦은 tick(60). 활성 중 채팅 다운타임(다운타임 구독 변경·재발행)은 미착수. 복구원이 내구 커맨드 로그라 다운타임 커맨드도 구조적 복원되나, 다운타임 후 클라 belief 재발행 경로는 후속.
- **한계 — 커맨드 로그 비유계(압축 없음)**: 가방은 0018 스냅샷 압축으로 저널을 유계화했지만, 채팅 커맨드 로그는 *전체 보존*(say 마다 1항목 — 고-볼륨). 라우팅 스냅샷 압축(현 구독 상태 스냅샷 + tail 커맨드)은 미착수 — 채팅 판 0018 이 후속.
- **한계 — write-behind 윈도(0017 잔존)**: 커맨드 로그도 1-tick 비동기라 활성 중 채팅/chatpersist in-flight 손실 가능(ack/resend 없음). 복구는 *로그가 담은 것*만 재현.
