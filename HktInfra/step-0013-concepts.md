# step-0013 개념 해설 — 진짜 프로세스 kill 아래 failover

> 정식 기록은 [step-0013.md](step-0013.md), 현재 위치는 [STATE.md](STATE.md). 이 문서는 step-0013 이 다루는 *핵심 개념*("무엇을·왜·어떻게 검증했나")을 풀어 설명한다. 비유는 보조, 개념 설명이 주.

## 개념 한눈표

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|---|---|---|
| 진짜 프로세스 kill | `child.kill('SIGKILL')` 로 자식 OS 프로세스를 *실제 소멸*시키는 것(소켓 RST·pid 사라짐) | 0012 의 *논리 분단 윈도*를 *실 프로세스 소멸*로 내림(`kill` 모드) |
| 윈도 vs 신호 vs 추측 | 침묵의 *감지* 방식 — 사전에 *앎*(윈도) / 전송이 *통보*(소켓 close 신호) / 길이로 *짐작*(타임아웃 추측) | 0012=윈도, 0013 kill=소켓 close 신호, 0013 거짓사망=타임아웃 추측 |
| bounded gap (failover) | 사망~승격 사이 *권위 공백 구간* — 회복은 예방이 아니라 *감지 후 복구* | orch lease 가 침묵을 감지·승격하기까지의 창(0009 상속) |
| 재-provisioning | 죽은 노드 자리에 *새 프로세스를 띄워* 이중화(N)를 복원하는 것 | kill→승격으로 N=1 → 새 standby spawn·상태 동기·미러(`reprovision` 모드) |
| 상태 동기 (state sync) | 새 노드를 *전체 스냅샷*으로 현재 상태까지 따라잡게 하는 것(late-join 복구) | `loadstate` — 권위 ents·sessions·핸드오프 멱등 상태를 standby 에 주입 |
| 입력 미러 (input mirror) | 권위가 받는 *입력 스트림의 사본*을 standby 로 보내 같은 상태로 복제 | broker 가 권위 deliver 사본을 standby 로(권위 경로 비-침습) |
| 거짓 사망 (false death) | *살아 있는* 노드를 죽었다 *오판*하고, 그 노드가 *복귀*하는 상황 | 링크 침묵→추측 사망→복귀(`falsedeath` 모드) |
| split-brain | 같은 상태에 *권위가 둘*(승격된 추종자 + 부활한 원권위) = 이중 쓰기 | 거짓 사망 복귀가 만드는 위험 — epoch 펜싱으로 차단 |
| epoch / fencing token | 사망 선언마다 올라가는 *세대 번호* — stale(옛 세대) 노드의 출력을 거부하는 근거 | broker 가 epoch 을 올리고 stale 호스트 발신을 전량 드롭(`epochFenced`) |
| divergence (복제 충실도) | 권위와 standby 의 상태가 얼마나 어긋났나(0 = 완전 복제) | 재-provisioning standby 가 권위와 divergence 0 |

## 1. 왜 이 step 인가 — 0012 가 남긴 격차

step-0012 는 서버를 *토픽 pub/sub 버스*로 분산하고, 소켓 링크의 *드롭·분단·재연결*에 내성을 세웠다. 그러나 그 "분단"은 두 가지 의미에서 *진짜 사망이 아니었다*:

- **broker 가 침묵 시점을 *알았다*(윈도).** 분단을 `T>at`/`T>=at` *논리 윈도*로 모델해, broker 가 "이 tick 부터 이 호스트를 안 부른다"를 *미리* 정했다. 실제로는 노드가 *언제* 죽을지 broker 가 알 수 없다 — *감지*해야 한다.
- **분단 호스트가 *살아 있었다*.** 링크만 끊겼지 프로세스는 멀쩡했다(그래서 복귀 시 일회성 fence 가 필요했다). 실제 노드 크래시는 *프로세스가 소멸*한다(소켓 RST·pid 소멸) — 돌아오지 않는다.
- **죽은 추종자 자리 재충원이 없었다(N=1).** 추종자가 승격되면 그 구역은 백업이 0 이 된다 — 다음 사망에 무방비.

이 step 은 그 격차를 친다 — 분단 윈도를 *진짜 `child.kill()`* 로 내리고, *감지*(소켓 신호·타임아웃 추측)·*재충원*(재-provisioning)·*거짓 사망 방어*(epoch 펜싱)를 더한다. 액터·프로토콜·배리어·토픽 버스는 *그대로*(회귀 0).

## 2. 진짜 프로세스 kill — 윈도가 아니라 신호로 감지

**개념.** 0012 의 분단은 broker 의 *지식*(윈도)이었다. 0013 의 kill 은 broker 가 `child.kill('SIGKILL')` 로 자식 프로세스를 *실제로 죽이고*, 그 죽음을 *소켓 `'close'` 이벤트*(전송 층이 주는 사망 통보)로 *감지*한다. broker 는 "언제 죽는지"를 윈도로 *아는* 대신, "소켓이 끊겼다"를 *관측*한다.

**왜 비트 동일인가.** 죽은 프로세스의 침묵 패턴이 인프로세스 *액터 사망*(deathTick)과 같아야 다이제스트가 같다. 핵심은 kill 을 *deliver 후·tick 전*에 주입하는 것:
- tick T=at 의 deliver 단계: 호스트는 아직 살아 메시지를 처리한다(인프로세스 deathTick 도 at 의 deliver 는 처리 — 사망은 onTick 에서 설정).
- tick T=at 의 tick 단계: kill 직후라 호스트 침묵(인프로세스 onTick 이 dead 로 0 발신과 동치).
- T>at: deliver·tick 모두 침묵.

이 비대칭(deliver `T>at`·tick `T>=at`)이 정확히 같아 **logDigest·fullDigest 비트 동일**.

**0012 분단과의 차이.** 죽은 프로세스는 *돌아오지 않는다* — 그래서 0012 의 재연결 fence 가 *필요 없다*. 검증은 `kill` 모드: 죽인 호스트의 pid 가 `livePids` 에서 *소멸*함을 확인(진짜 프로세스 죽음, 공유 메모리 0).

**비유(보조).** 0012 는 "그 사람은 9시부터 회의 불참"이라고 *일정표에 적은* 것이고, 0013 은 "그 사람의 전화가 *뚝 끊겼다*"를 *듣고* 불참을 *아는* 것이다.

## 3. 벽시계 비결정을 논리 tick 으로 가두기

**문제.** 진짜 kill 의 소켓 RST 가 *언제* 도착하는지는 벽시계 비결정이다(1ms? 10ms?). 그런데 다이제스트는 *비트 재현*되어야 한다(불변 규칙). 모순처럼 보인다.

**해법.** `killHost` 는 `child.kill` 직후 `socketDead` 플래그를 *즉시* 세우고, 소켓 `'close'` 를 *기다린* 뒤에야 배리어가 다음 tick 으로 간다. 그래서 *어느 tick 에서 침묵이 시작되는가*는 `kill.at`(논리 tick)의 *순수 함수*다 — RST 의 벽시계 지연이 다이제스트에 *닿지 않는다*. lockstep 배리어가 "진짜 비동기 아님"의 대가를 치르는 대신, *진짜 kill 의 비결정성을 결정론으로 흡수*하는 자산이 된다(`repro`: 멀티 2회 = 인프로세스 = 0012~0009 비트 동일).

## 4. 재-provisioning — 죽은 자리 재충원

**개념.** 추종자가 승격되면(권위가 되면) 그 구역의 백업은 0(N=1). *재-provisioning* 은 *새 프로세스를 띄워* 다음 사망에 대비하는 핫 standby 를 만든다 — 이중화(N≥2)의 *회복*.

**세 조각.**
1. **spawn** — broker 가 런 도중 `spawnOne` 으로 새 OS 프로세스(zone1g)를 띄운다(초기 기동과 같은 경로).
2. **상태 동기(loadstate)** — 새 노드는 빈 상태로 시작하니, 승격된 권위(zone1f)의 *전체 스냅샷*(ents·sessions·핸드오프 멱등 상태)을 주입해 현재까지 따라잡는다. 이는 "전체 스냅샷 = late-join·복구의 최후 수단"의 정당한 사용.
3. **입력 미러** — 이후 권위가 받는 *입력 스트림의 사본*을 standby 로 보낸다(broker 가 권위 deliver 를 미러). 새 standby 는 *같은 시드 의사난수 + 같은 입력열* 로 복제해 권위와 **divergence 0**.

**비-침습.** 새 standby 는 shadow·orch 0 라 *발신이 0* — net.log 가 안 바뀐다. 그래서 권위 세계의 `fullDigest` 가 *재-provisioning 없는* 인프로세스 deathTick 과 *동일*. 이중화를 더해도 게임 세계는 *변하지 않는다*.

**함정(의외의 발견 §8-4).** ents 만 복사하면 divergence 가 *작게* 샌다. (a) 핸드오프 *재전송*이 standby 에서 *재-acquire* 로 위치를 리셋하거나(`acquired` 멱등 상태 미동기), (b) standby 가 권위와 *다른 sibling* 이라 경계 크로서를 *핸드오프 안 해서*(ents 잔류) 어긋난다. 그래서 ents·sessions *와* 핸드오프 멱등(`acquired`)·*같은 sibling* 까지 동기해야 같은 입력이 같은 ents 진화를 낳는다. **"복제=재현"의 재현 단위는 순수 상태가 아니라 멱등·라우팅 컨텍스트를 포함한다.**

## 5. 거짓 사망과 epoch 펜싱

**개념.** *감지*는 *틀릴 수 있다*. 소켓이 *살아 있는* 침묵(일시 링크 분단)은 close 신호가 없어 broker 가 *침묵의 길이*로 *추측*(타임아웃)할 수밖에 없다 — 그리고 그 추측이 *오판*(거짓 사망)일 수 있다. 죽었다고 추측해 추종자를 승격시켰는데 원 노드가 *복귀해* 권위를 재개하면 → 같은 상태에 *권위가 둘* = **split-brain**(이중 쓰기).

**해법 — epoch/fencing token.** broker 는 사망을 *선언*할 때마다 *세대 번호*(epoch)를 올린다. 복귀한 노드는 *옛 세대*(stale epoch)다 — broker 가 그 노드의 발신을 *전량 거부*(드롭)한다. 노드는 *살아 출력*하지만(거짓 사망의 증거 — `epochFenced` 55~64 = 실제 출력 시도) 그 출력이 세계에 *닿지 않는다*.

**왜 비트 동일인가.** 펜싱된 발신은 net.log 에 *0 기여* → 거짓 사망(복귀)이 *진짜 사망과 비트 동일*. 거짓 사망의 "살아 있음"이 다이제스트에 닿지 않는다. 검증은 `falsedeath` 모드: presumedDead(추측 사망)@42·epoch 1·epochFenced>0 인데도 logDigest·fullDigest 가 인프로세스 진짜 사망과 동일·소유자 1.

**0012 fence 와의 관계.** 0012 는 분단 호스트를 *일회성*으로 dead 못박았다(돌아오지 않는다 가정). epoch 은 그것을 *지속 토큰*으로 올린다 — *복귀해 거듭 출력하는* 호스트를 *매번* 거부한다. "회복은 침묵의 함수, *안전은 복귀의 함수*"(0012 발견)가 epoch 으로 구체화.

**비유(보조).** 회사가 "A 가 퇴사했다"고 *추측*하고 후임 B 에게 권한을 넘겼다. A 가 *살아 돌아와* 옛 권한으로 결재를 시도해도, 시스템이 "당신의 사번은 *이전 세대*"라며 결재를 *전부 반려*한다 — 그래서 결재 권한은 *언제나 한 명*(B)뿐.

## 6. 이 step 이 척추에서 선 자리

- **신성한 tick**: 액터 무변경 — kill·epoch·재-provisioning 은 전송 substrate 층(tick 안 시뮬 외 작업 0).
- **권위 단일 소유(한 발 더)**: 진짜 kill→추측 감지→승격→재충원→거짓 사망 복귀 전 구간 소유자=1. *추측 오판 너머로* epoch 으로 단일 소유를 지킨다.
- **headless·원격 검증**: `node verify.js` 한 줄이 원격에서 전 프로세스를 *진짜 child.kill·재충원·epoch 펜싱* 아래 4기둥 수치 증명.

코디네이션 계층(노드 소멸 아래 권위 보존)이 *진짜 프로세스 kill* 까지 버틴다 — 0009 의 failover 가 추상 사망에서 시작해, 0012 의 링크 분단을 거쳐, 0013 에서 *실 프로세스 소멸·재충원·거짓 사망 방어*로 현실화됐다. 다음은 그 위에 *진짜 비동기*(벽시계 타임아웃·논리 클럭)나 *물리적 다중 브로커*를 더하는 일([STATE.md](STATE.md) §2).
