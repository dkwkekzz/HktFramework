## 검증 질문

SPINE §2 게임 서비스 계층의 **우편**(§3 OPEN GAPS 의 ⬜→🟡 첫 박스)을 연다. 귓속말(0071~ wrouter)은 *온라인* 라우팅(수신자 접속 시 즉시 전달, 아니면 반송)이지만, MMO 의 우편은 *오프라인* 배송이다 — 발신자가 수신자 우편함에 넣으면 수신자가 **나중에 접속해 수령**한다(접속 무관·"세계가 세션보다 오래"). 이번 한 조각: `mailSend` 입금 + 수신자별 우편함. 닫는 조건: 입금이 우편함에 정확·멱등 적재되고(가설 `exmail`), mail OFF = 0141 비트 동일(reg 0). 거래소(0107)·시세 피드(0112) 박스 도입 패턴을 따른다.

## 2. 메커니즘 — 우편 박스 + mailSend(플래그 mail OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-mail.js`**(신규) — `MailService`. `boxes`: recipient → Map(mailId → {id,from,to,body,sentAt}) = *우편함 권위(단일 소유)*. `onMsg({payload:{type:'mailSend',id?,from,to,body},tick})` → 수신자 우편함에 우편 1통 적재. `id` 미지정이면 결정론 시퀀스(`'mail'+seq`). **같은 id 재전송은 멱등**(이중 적재 0 — 재전송 신뢰성 0145~ 의 토대). 회계: `sent`(총 입금 통수). accessor: `held(rcpt)`·`totalHeld()`·`boxOf(rcpt)`·`digest()`. 발신 0(0142 — 수령 0143·발행 0144~).
- **배선**: net-core `__p('svc-mail')` 추가 · topo-actors `MailService` import + `case 'mail'` · topo-build `mail=false` 플래그 + `if (mail) add({addr:'mail',kind:'mail',opts:{bus:busAddr}})` · topo-run `mail` 핸들 + `mailOps` 주입 핸들러(tick 동봉 — sentAt·0148 만료 대비) + 반환 노출.
- **회귀 0 구조**: `mail` 기본 OFF → 박스 미생성·`mailOps` 미제공 → 주입 0 → net.log·월드·기존 서비스 전부 0141 비트 동일. mail 은 거래소·시세 피드와 *독립*(다른 우편함 자료구조) — 기존 경로 무간섭.

## 9. 의외의 발견 / 정직한 한계

- 0142 는 *입금만* — 수신자가 우편을 *가져가는* 경로(mailFetch)가 없어 우편함이 무한히 쌓인다(수령 0143·유계화 후속). 회계도 sent==totalHeld 로만 닫힘(fetched·expired 0); 0143 에서 sent==held+fetched 로, 0150 capstone 에서 sent==held+fetched+expired 로 확장.
- 우편 입금은 현재 *주입 seam*(`mailOps`)으로만 들어온다 — 실제로는 가방(give)·거래소(낙찰 알림)·시스템(보상)이 발신자가 될 것이다. 클라↔게이트웨이 우편 와이어 계약은 후속(실 버스 체인은 0144 발행부터).
