## 검증 질문

0050~0052 의 cadence/lease 기능이 `svc-inventory-core.js` 에 누적되며 **31.9KB > 30KB**(CLAUDE.md 박스 임계 규칙 위반)가 됐다. 규칙: "박스 파일이 30KB 를 넘으면 다음 *기능* step 전에 정리 step(재분할/engine 승격·기능 0·reg 비트 동일)을 끼워 박스 크기를 유계로 묶는다." 이 step 은 원장 *트랜잭션 핸들러*(`onMsg`)를 별 부품 파일 `svc-inventory-txn.js` 로 *바이트 동일* 추출한다 — `svc-inventory-persist.js`·`svc-inventory-bus.js` 가 이미 쓰는 프로토타입 증강(`Object.assign`) 패턴 그대로. 닫는 조건: ⒜ reg = 0052 **비트 동일**(코드 재배치일 뿐 동작 무변경) ⒝ 추출된 onMsg 가 프로토타입에 살아 트랜잭션 정상 동작(원장 자기-정합·minted>0) ⒞ 모든 박스 파일 ≤30KB.

## 2. 메커니즘 — 트랜잭션 부품 추출 (기능 0 → baseline 비트 동일 = 회귀 0)

`svc-inventory.js`(진입점)은 이미 원장을 세 부품으로 묶는다: `svc-inventory-core.js`(생성자 + 트랜잭션 + crash + 조회) + `svc-inventory-persist.js`(write-behind) + `svc-inventory-bus.js`(버스 결과/replay). persist·bus 는 `Object.assign(InventoryService.prototype, {…})` 로 코어 클래스의 프로토타입을 증강한다(런타임에 한 객체).

이 step 은 코어의 가장 큰 단일 메서드 **`onMsg`**(트랜잭션 핸들러·pickup/give 쌍 거래·reconcile·dedup·ack — ~67줄/~6KB)를 새 부품 `svc-inventory-txn.js` 로 *바이트 동일* 옮긴다(같은 증강 패턴). `onMsg` 가 호출하는 `_journal`·`_out`·`_recordAck`·`_resend`·`_onOutAck`·`_onSeenWatermark`·`_own`/`_unown` 은 전부 같은 프로토타입에 살아 있어(다른 부품이 증강) 동작 불변이다. 진입점은 core 직후 txn 을 require 한다(증강 순서 무관 — 인스턴스화는 그 뒤).

결과: `svc-inventory-core.js` 31.9KB → **25.5KB**, 신규 `svc-inventory-txn.js` 6.3KB. 모든 박스 ≤30KB 회복. 코드는 한 줄도 *바뀌지* 않았다(이동만) → NET 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **박스 누적 압력은 src/ 전환으로도 안 사라진다**: 0049 가 디렉토리 통복사(복사 전진)를 없앴지만, *한 박스 파일* 안의 기능 누적은 여전히 자란다(cadence/lease 3-step 으로 core +2KB). 박스-1개=파일-1개 규칙은 *기능이 한 박스에 쏠릴 때* 주기적 재분할을 요구한다 — 0030/0035/0038/0043 에 이은 다섯째 분할.
- **추출 단위 = 단일 메서드(콤마 외과수술 회피)**: onMsg 만 옮겼다(생성자·crash·조회는 코어 잔류). 여러 메서드를 한 번에 Object.assign 으로 옮기면 메서드 사이 콤마 삽입이 필요해 오류 위험 — 단일 메서드 추출이 가장 안전한 verbatim 이동이다. 다음 비대화 시 crash/조회도 같은 방식으로 분리 가능.
- **생성자가 여전히 코어의 대부분**: core 25.5KB 중 생성자(opts + 주석)가 ~절반. 생성자 자체는 Object.assign 으로 못 옮긴다(인스턴스 state init) — 더 줄이려면 opts 파싱을 헬퍼로 빼거나 주석을 reviews/ 로 이관해야(후속).
