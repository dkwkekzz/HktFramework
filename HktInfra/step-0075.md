# step-0075 — 파티 멤버십 SSOT: 멤버십 ⟂ 라우팅 분리(partyService)

> 직전: [step-0074](step-0074.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0073 의 파티 라우터는 멤버 목록을 요청에 *인라인*으로 받았다 — "누가 어느 파티인가"(멤버십)와 "그 파티에 어떻게 전달하나"(라우팅)가 한 요청에 섞여 있었다. 실제 길드/파티는 멤버십이 *오래 사는 상태*(결성·가입·탈퇴)다. 멤버십을 전용 박스로 분리하고 라우터가 멤버 목록을 *질의*로 얻으면, 멤버십 ⟂ 라우팅 관심사가 분리되고 SPINE 계층3(길드/소셜)의 첫 멤버십 박스가 서는가? (닫는 조건: partyTo 가 멤버 인라인 없이 멤버십 SSOT→프레즌스 SSOT→라우팅 2단 조회로 완결·partyService OFF=0074 비트 동일)

## 2. 메커니즘 — 멤버십 SSOT(플래그 `partyService` OFF → baseline 비트 동일 = 회귀 0)

- **새 박스 `src/svc-party.js` (`PartyService`)** — 존 tick 밖 순수 반응형. `parties: Map partyId→[member]`(멤버십 SSOT). `partyCreate{partyId,members}`→멤버십 쓰기. `partyQuery{partyId}`→`partyMembers` 회신(request/reply).
- **`src/svc-whisper.js`** — `membershipAddr` opt 추가. `{type:'partyTo', partyId}`(멤버 인라인 X) → 멤버십 SSOT 에 `partyQuery`(`membershipQueries++`), `partyPending[partyId]` 보류. `partyMembers` 응답 → 멤버마다 `_queryFor`(0073 의 프레즌스 질의→라우팅 경로 재사용). **멤버십 SSOT→프레즌스 SSOT→라우팅 2단 조회**.
- **배선(`topo-build.js`)** — `partyService` 플래그. `partyAddr=(partyService && whisperAddr)?'pservice':null`. wrouter opt `membershipAddr: partyAddr`. makeActor `'party'` kind. `net-core.js` require 1줄.
- **주입(`topology.js`)** — `opts.partyCreate`(→pservice)·`opts.partyTo`(→wrouter). 인라인 `party`(0073)는 그대로 공존.

## 4. 척추 체크 5항

1. **신성한 tick** ✅ — PartyService·WhisperRouter 둘 다 onTick 없음(순수 반응). 존 tick 밖 비동기 서비스(SPINE §2: 멤버십은 tick 박자 무관).
2. **결정론 코어** ✅ — 멤버십/라우터는 세계 상태 무변경. 결성/질의/전송 전부 정규 net.send(시드 로그) — 같은 시드 같은 해시.
3. **권위 단일 소유** ✅ — PartyService 는 *멤버십* 권위만(원장 무관·minted ON==OFF). 라우터 권위 0.
4. **은닉·단일 연결** ✅ — 라우터는 멤버십 저장 방식을 모르고 질의 계약만 안다(decouple). 클라는 라우터/파티서비스에 명시 메시지만.
5. **headless·원격 검증** ✅ — Node·UE 0. `node run.js`/`spine` 수치 증명. 새 박스도 같은 buildTopology/makeActor 경로.

## 9. 의외의 발견 / 정직한 한계

- **멤버십 SSOT 는 인메모리·영속 0**: PartyService 가 crash 하면 멤버십 소실(프레즌스 박스의 0064~0067 영속/failover 호가 멤버십엔 미적용). 파티 멤버십 저널/failover 는 후속(가방·채팅·프레즌스가 걸은 같은 길).
- **멤버십 모델은 덮어쓰기**: `partyCreate` 가 멤버 목록을 통째 설정한다 — 증분 가입/탈퇴(addMember/removeMember)·멤버십 변경 이벤트 발행은 미착수(단순 SSOT 모델). 변경 알림(파티 목록 갱신 푸시)도 후속.
- **전달(deliver)은 여전히 best-effort**: 멤버십→프레즌스→라우팅 *결정* 경로는 견고하지만, whisperDeliver 자체의 전달 영수증/ack/재시도는 0071 이래 그대로 미착수(라우팅 후 단계). 전달 신뢰는 여전히 다음 후보.
- **멤버십 질의도 failover 윈도에 취약**: PartyService 는 0072/0074 의 재타깃/재시도(프레즌스 박스용)를 안 받는다 — PartyService failover 시 라우터의 멤버십 질의는 끊긴다(프레즌스가 걸은 길을 멤버십에도 적용하면 해소).
