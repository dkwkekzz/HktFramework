# step-0131 — saga 재시도 상한(sagaMaxRetries — autoRetry/exchRetry 재전송을 gid 당 N회로 유계)

> 직전: [step-0130](step-0130.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0129 autoRetry 는 회신 손실이 *영구*하면 매 exchSweep 마다 같은 give 를 무한 재전송한다 — 실서버는 상한이 필요하다(0059 recoverMaxRetries 의 프레즌스 명령 판이 거래소 saga 에도 와야 한다). **회신이 영영 안 오는 give 를 거래소가 *유계한 횟수*만 재전송하고 포기하되, 그 포기가 2-서비스 안전(open==escrow)과 회계 정합(sagaConsistent)을 깨지 않는가?** 채우는 박스/계약: SPINE 계층3(게임 서비스) 거래소↔가방 saga 신뢰 전달의 *liveness 유계화*.

## 2. 메커니즘 — 재전송 추출 + 상한(플래그 OFF → baseline 비트 동일 = 회귀 0)

- **추출(정리·기능 0)**: 0126 `exchRetry` 와 0129 `exchSweep` autoRetry 의 *동일한* 재전송 루프를 `ExchangeService._resendPending()` 한 곳으로 추출. 두 호출처는 `this._resendPending()` 한 줄. 메시지 바이트·순서 불변(`[...this.pendingGive]` 스프레드는 삽입 순서 보존).
- **상한**: `sagaMaxRetries`(기본 0 = 무제한). >0 이면 `retryCount: gid→횟수` 로 gid 당 재전송을 센다. `c >= sagaMaxRetries` 면 그 give 를 포기 — `pendingGive.delete(gid)`(이후 sweep 에서 비-순회)·`retryCount.delete(gid)`·`giveAbandoned++`. 재전송하지 않는다.
- **포기 ≠ abort**: give 가 실제로는 성공했을 수 있다(dedup 으로 가방이 escrow 에 item0 을 이미 넘김, 회신만 손실). 그러므로 listing 을 abort 하지 않고 낙관적 open 을 유지 → `open==escrow` 안전. 포기한 give 는 `pending`(Set)에 *남겨* 미해결로 둔다 → `sagaConsistent`(gives==acked+pending) 불변.
- **회귀 0**: `sagaMaxRetries===0` 이면 `if (this.sagaMaxRetries > 0)` 분기가 통째로 휴면 → `_resendPending()` 이 원래 루프와 비트 동일 송신. `retryCount` 는 빈 맵(ack 시 `delete` 도 no-op)·`giveAbandoned` 불변 0. crash() 리셋만 추가(saga OFF 면 무관). → baseline(0130) 비트 동일.

## 4. 척추 체크 5항

① **신성한 tick**: 거래소는 onTick 없는 순수 반응형 — 재전송은 외부 exchSweep/exchRetry op 트리거(존 tick 밖). ② **결정론 코어**: 상한 비교는 단조 gid·정수 카운트(Math.random 0)·시드 전 결정론 동일. ③ **권위 단일 소유**: 거래소가 escrow 단일 쓰기 권위 — 포기는 재전송만 멈출 뿐 권위 이동/이중쓰기 0. ④ **은닉·단일 연결**: 재전송/포기는 서버간(거래소→가방) 제어 평면 — 클라 와이어 계약 불변. ⑤ **headless·원격 검증**: Node `node run.js` 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **포기는 인지일 뿐 해소가 아니다**: 상한 도달 give 는 영구 미해결로 pending 에 남는다(giveAbandoned 가 신호). 이 미해결을 *발행*해(audit/운영 가시화) 또는 *보상*해(영구 실패 시 listing abort) 처리하는 것은 후속 step(0132~). 현재는 "유계화 + 안전 유지"까지.
- **상한이 합법 give 도 포기시킬 수 있다**: 회신 경로가 단지 느린(손실 아님) 경우에도 상한 도달 시 포기한다 — 거래소 관점에선 구별 불가(회신 부재만 본다). dedup 덕에 *안전*은 깨지지 않지만(open==escrow 유지) liveness 는 상한·sweep 주기 튜닝 문제로 남는다.
