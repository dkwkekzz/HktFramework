## 2. 메커니즘 — 파티 단위 영수증 집계 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-whisper.js`): 0083 의 partyReceipts 엔트리에 `delivered` 추가.
- 라우팅(presenceReply) 시 inflight 엔트리에 `party: w.party` 를 실어 영수증을 파티에 귀속.
- `whisperAck` 확인 시 `_partyAck(e.party)` — 그 전달이 속한 파티의 `delivered++`.
- `partyDone(id)` = `routed+bounced==members`(라우팅 *결정* 완료·0083) / `partyAcked(id)` = `routed>0 && delivered==routed`(실수신 *확인* 완료·0088).

라우팅 결정(0083)과 영수증 확인(0088)이 파티 전송의 *두 완료 기준*. 1:1 영수증(0076 delivered)의 1:N 집계 완성. `partyReceipt` OFF·receipt 부재면 집계 0 = 0087 비트 동일(inflight 의 party 필드는 비-파티 시 undefined·net 무관).

## 9. 의외의 발견 / 정직한 한계

- **발견**: 파티 전송이 *두 완료 시점*을 갖는다 — done(라우팅 결정·즉시)과 acked(실수신 확인·왕복 지연 후). 1:N 전송에서 이 둘의 시간 간격이 곧 "전송했다고 믿은 시점"과 "정말 도달한 시점"의 격차다(분산 시스템의 결정 vs 확인).
- **한계**: 실수신 집계는 *Mailbox(영수증 박스)를 가진 up 멤버*만 — 현 토폴로지엔 mbox 하나뿐이라 up 멤버 중 mbox 만 delivered 에 기여한다. up 멤버가 여럿이고 일부만 Mailbox 면 acked 가 영영 false(delivered<routed) — 모든 up 멤버가 ack 가능해야 acked 가 의미 있다. 멤버별 Mailbox 토폴로지(파티원마다 수신함)가 후속. 또한 부분 ack(N-of-M acked)의 *타임아웃 포기*(0078 의 파티 판)는 미적용.
