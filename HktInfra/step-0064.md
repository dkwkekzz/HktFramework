# step-0064 — 전용 프레즌스 박스 분리: 프레즌스 SSOT+발행을 orch 에서 PresenceService 로 (presenceBox)

> 직전: [step-0063](step-0063.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

SPINE 계층 5(코디네이션)는 *두* 박스다 — "세션/프레즌스"(누가 어디에 SSOT)와 "오케스트레이터"(배치·부하·복구 결정). 그러나 0055~0063 동안 orch 하나가 프레즌스 *결정·SSOT(consumerDown/permanentDown)·발행(svc.presence)·행동(recover/retry/포기)* 을 전부 했다. 이 step 은 그 중 *프레즌스 SSOT + 발행* 을 전용 `PresenceService` 박스로 떼어낸다 — orch 는 전이를 *보고*만(point-to-point) 하고, PresenceService 가 SSOT 를 쥐고 svc.presence 로 발행. orch 는 순수 오케스트레이터(결정·행동)로 남는다. 닫는 조건: ⒜ `presenceBox=0` 이면 0063 비트 동일(박스 0·orch 직접·reg 0) ⒝ ON 이면 presence 박스가 SSOT(permanentDown)·발행·orch 위임(presencePublished 0·orch SSOT 빔) ⒞ 다운스트림(presmon) 관측 ON==OFF(행동 보존·발행자만 교체) ⒟ 발행==보고(무손실) ⒠ 비-침습(minted 동일).

## 2. 메커니즘 — 프레즌스 책임 분리 (presenceBox OFF → baseline 비트 동일 = 회귀 0)

새 박스 `svc-presence.js`(PresenceService) — 존 tick 밖 *순수 반응형*. orch 가 `{type:'presence', kind, consumer}` 로 전이를 *보고*하면 consumerDown/permanentDown SSOT 갱신 + svc.presence 로 발행. orch 에 `_track(kind, consumer)` 헬퍼를 더해 세 전이 지점(evict→down·readmit→up·giveup→permanent)을 일원화: `presenceBox && presenceAddr` 면 PresenceService 에 보고(SSOT/발행 안 함)·아니면 직접 SSOT 갱신+발행(0063 동일). **OFF 경로 비트 불변**(`_track` OFF = 기존 inline set-update+`_presence` 와 동일).

토폴로지는 `presenceBox && presencePublish` 일 때만 `presence` 박스 + orch 에 `presenceAddr` 배선. `presenceBox=0` 이면 박스 미존재·orch 직접 → NET 비트 동일. 닿는 박스: `svc-presence.js`(신규)·`orchestrator.js`(`_track`·세 전이)·`net-core.js`(require)·`topo-build.js`(박스·orch 배선·makeActor)·`topology.js`(노출). 순수 제어 평면·원장 권위 불변.

## 4. 척추 체크 5항

① **신성한 tick** — PresenceService·보고 둘 다 존 tick 밖 제어 평면(reg=월드 비트 동일). ② **결정론 코어** — SSOT/발행은 결정론 전이 순서의 함수(월드해시 보존). ③ **권위 단일 소유** — 프레즌스 SSOT 는 *정확히 한* 박스(PresenceService)가 쥔다(ON 이면 orch 사본 0 — 이중 SSOT 제거). 원장 권위 불변(minted ON==OFF). ④ **은닉·단일 연결** — orch 는 presenceAddr 명시 인터페이스로 보고·다운스트림은 토픽만(발행자 교체 무지). ⑤ **headless·원격 검증** — Node 헤드리스 `node run.js`·UE 0·E2E 14프로세스.

## 9. 의외의 발견 / 정직한 한계

- **분리 판정 기준(SPINE §2)이 코디네이션 *안*에서도 작동한다**: "그 일이 같은 박자로 돌아야 하는가?" 는 tick vs 비-tick 분리에 쓰였지만, 같은 논리가 코디네이션 계층 *내부*에도 적용된다 — 프레즌스 *SSOT 유지/조회*("누가 어디에")와 *복구 결정/행동*(recover/retry/포기)은 다른 박자·다른 책임이다. 전자는 *읽기 많은 조회처*(미래 귓속말·파티·핸드오프 라우팅이 질의), 후자는 *쓰기 적은 결정 루프*. 한 박스에 두면 조회 부하가 결정 루프를 막는다 — 분리가 그 병목을 없앤다.
- **이중 SSOT 제거가 분리의 핵심 이득**: 0063 까지 orch 가 consumerDown 을 *사유 사본*으로 들고 있었다(권위 단일 소유의 회색 지대 — 누가 진짜 SSOT?). presenceBox ON 이면 SSOT 가 *정확히 한* 박스로 모인다(orch 사본 0). 이는 척추 ③(권위 단일 소유)을 프레즌스에도 엄밀히 적용한 것 — 시뮬 엔티티·아이템처럼 *프레즌스 상태*도 단일 소유자.
- **발행자 교체가 다운스트림에 *투명*(decouple 의 코디네이션 판)**: audit·presmon·ranking2 는 svc.presence 를 누가 발행하는지 모른다(토픽만). 그래서 발행 책임을 orch→PresenceService 로 옮겨도 다운스트림 코드·관측이 비트 동일(presmon ON==OFF). 0016 이 *서비스* 결합을 버스로 끊은 것을 *코디네이션* 발행에 적용 — 책임 재배치가 소비자 무수정.
- **보고 경로는 아직 point-to-point(정직한 한계)**: orch→PresenceService 전이 보고는 명시 주소(presenceAddr) point-to-point 다 — 버스 경유가 아니다. 다중 orch·프레즌스 박스 failover 를 하려면 이 보고도 버스 토픽(svc.presence.report)으로 올리고 PresenceService 가 구독해야 한다(후속). 이 step 은 *책임 분리*까지, 보고 경로의 완전 decouple·프레즌스 박스 자체의 failover 는 다음.
