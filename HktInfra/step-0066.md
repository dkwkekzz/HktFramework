> 직전: [step-0065](step-0065.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0065 가 orch→PresenceService 보고를 *버스 토픽*(`svc.presence.report`)으로 올려 orch 가 프레즌스 박스 *주소 무지*가 됐다(완전 decouple). 그 위에 — **두 PresenceService 인스턴스가 같은 보고 스트림을 먹으면 같은 SSOT 로 수렴하는가?** *대기(standby)* PresenceService(`presence2`)를 같은 토픽에 구독시켜 SSOT(`consumerDown`/`permanentDown`)를 그림자 복제하되 발행은 억제(`active=false` → `svc.presence` 이중 발행 0)한다. 닫는 조건: standby SSOT == primary SSOT(reports/down/perm 동일)·standby 발행 0·primary 발행 보존·다운스트림(presmon) 행동 보존·비-침습. SPINE 계층 5 "세션/프레즌스" — 존 follower 복제(0002)·shadow follower(0009)의 *코디네이션 판* = 프레즌스 박스 failover 의 토대(승격 시 SSOT 갭 0).

## 2. 메커니즘 — standby 박스 그림자 복제 (플래그 `presenceShadow` OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-presence.js`**: `PresenceService` 에 `active` 플래그 추가(기본 `true`=primary). `onMsg` 의 SSOT 갱신(consumerDown/permanentDown/reports)은 **active·standby 둘 다** 수행하되, `svc.presence` 발행은 `this.active && this.bus` 일 때만 — standby(`active=false`)는 그림자 복제만 하고 이중 발행 억제. `active` 미지정 = `true` = 0065 비트 동일(단일 active 박스).
- **`src/topo-build.js`**: `presenceShadowAddr = (presenceShadow && presenceSvcAddr && presenceReportBus) ? 'presence2' : null` — 보고 버스화(0065) 전제. 구독 `['svc.presence.report','presence2']` 를 primary 행 *뒤*에 push(팬아웃 순서 primary 먼저). 액터 `presence2`(kind `presence`·`{bus, active:false}`) 를 primary 뒤 등록.
- **`src/topology.js`**: 결과에 `presenceShadow = map.get('presence2')` 노출.
- OFF(`presenceShadow=0`) → standby 액터·구독 0 → 0065 토폴로지·동작 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **shadow 는 "라이브" 복제 — 다운타임 갭 미해결**: presence2 가 *처음부터* 같은 토픽을 구독하므로 모든 보고를 받는다(갭 0). 하지만 standby 가 *늦게 합류*(late-join)하거나 보고가 *손실*되면 SSOT 가 벌어진다 — 보고 스트림 replay/워터마크는 미적용(후속). 현재는 "둘 다 처음부터 켜진" 라이브 shadow 만 증명.
- **승격 미구현**: standby 는 발행을 *억제*만 한다 — primary 사망 시 standby 가 `active=true` 로 *승격*해 발행을 인계하는 고리(0009 follower 승격·0034 버스 failover 의 코디네이션 판)는 다음 step(presencePromote 후보). 이 step 은 그 토대(SSOT 갭 0)만 깐다.
- **failover 트리거 부재**: primary 사망 *감지*(heartbeat/lease)와 승격 트리거는 아직 없다 — 0067 후보가 죽음 주입+승격을 함께 검증.
