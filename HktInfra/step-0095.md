## 2. 메커니즘 — 성공 종결 발행 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-whisper-core.js`·`-handlers.js`): `partyCompletePublish` ON 일 때
- whisperAck 핸들러에서 `_partyAck(e.party)` 직후, 이 ack 로 파티가 `partyAcked`(routed>0 && delivered==routed)에 *처음* 이르면(`_completePub` 중복 방지) `svc.party.complete{partyId, members, routed, delivered}` 를 bus 로 발행 + `partyCompletePublished++`.
- bus 부재·비-파티·OFF 면 no-op.

**구독** (`src/topo-build.js`): `audit && partyCompletePublish && whisperRouter` 면 `['svc.party.complete', 'audit']` 행 추가. OFF 면 구독 행 0 = 0094 토폴로지 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 파티 전송의 *발행 수명주기*가 양 끝을 얻었다 — 멤버십 변경(`svc.party.changed`·0084) + 실패 종결(`svc.party.incomplete`·0093) + 성공 종결(`svc.party.complete`·0095). 같은 audit sink 가 1:N 전송의 결정·성공·실패를 한 스트림으로 본다(개별 전달의 0082+0087 수명주기가 파티 차원에 거울처럼 재현).
- **한계**: 성공/실패 종결은 *상호 배타*가 강제되지 않는다 — 같은 partyId 가 (불가능하지만) 둘 다 트리거하면 둘 다 발행될 수 있다(현 토폴로지에선 acked 와 incomplete 가 동시 참 불가라 무사). 종결 *판정의 단일성*(파티당 정확히 한 종결 이벤트)을 토폴로지-독립으로 보장하는 것은 후속. 멤버별 Mailbox(0088 §9)가 서면 acked 의 의미가 완전해져 complete 발행이 N>1 에서도 정확해진다.
