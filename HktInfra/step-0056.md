# step-0056 — 프레즌스 *반응*(self-healing): orch recover 명령 → 소비자 자기 재구독 (busPresenceRecover)

> 직전: [step-0055](step-0055.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0055 가 코디네이션 프레즌스(`consumerDown`)를 *상태*로 세웠다 — orch 가 "ranking 이 지금 down 임"을 버스 이벤트만으로 안다. 그러나 *행동* 0: 알 뿐 아무것도 하지 않는다(0055 §9 "프레즌스는 상태, 아직 행동 0"). 이 step 은 lease 이벤트→프레즌스→**액션**의 마지막 고리를 닫는다 — orch 가 down 소비자에게 `recover` 명령을 직접 보내고(0009 promote/reroute 와 같은 코디네이션 제어 평면), 소비자가 *스스로* 재구독해 살아 돌아온다. 닫는 조건: ⒜ `busPresenceRecover=0` 이면 0055 비트 동일(reg 0·orch 무행동) ⒝ 영구-down(rankDie) 소비자가 OFF(0055)에선 영영 down(consumerDown={ranking}·readmit 0) vs ON 에선 자동 치유(recoversSent≥1·소비자 resub≥1·readmit≥1·consumerDown 비움·소비 재개) ⒞ 비-침습(ON==OFF 원장 minted — recover 는 순수 제어 평면).

## 2. 메커니즘 — self-healing 고리 (busPresenceRecover OFF → baseline 비트 동일 = 회귀 0)

0055 의 프레즌스 갱신(`consumerDown.add` on evict)에 *행동*을 더한다. orch 가 `evict` 이벤트를 소비할 때 `busPresenceRecover` ON 이면:

- `this.net.send(this.addr, consumer, { type: 'recover', topic: 'svc.item.out' })` — down 소비자에 recover 명령(evict 1회당 1 recover·`recovered` Set 으로 중복 억제).

소비자(`RankingService`)는 `recover` 를 받으면 *스스로* 버스에 재구독한다: `net.send(addr, bus, { type:'sub', topic })`. **재구독은 구독자 자신이 보내야 라우팅이 맞다** — orch 가 대신 `sub` 하면 orch 가 구독자로 등록된다(0055 §9 난점·0034 "진실 원천=소비자"와 동형). 재구독 후 결과 스트림 재개 → 재-ack → 가방이 `readmit`(0048 lifecycle) → svc.item.lease(readmit) → orch `consumerDown.delete` = 고리 닫힘.

self-healing 고리: **rankDie(영구 해지) → 가방 leaseSpan 뒤 evict → svc.item.lease → orch consumerDown.add + recover 명령 → ranking 자기 재구독 → 결과 재개 → 재-ack → 가방 readmit → svc.item.lease → orch consumerDown.delete.**

`busPresenceRecover=0` 이면 orch 가 recover 미발신 → ranking 은 recover 메시지를 영영 못 받음(handler 는 존재하나 trigger 0) → NET 비트 동일. 닿는 박스: `orchestrator.js`(recover 발신)·`svc-ranking.js`(recover 수신→자기 재구독)·`topo-build.js`(플래그 배선). 순수 제어 평면(존 tick 밖·원장 권위 불변).

## 9. 의외의 발견 / 정직한 한계

- **소비 회복이 self-healing 의 비자명한 증거**: ON 의 `consumed` 가 OFF(24)의 5배 이상(119~128)이라는 것은, 치유가 *형식적 재구독*에 그치지 않고 소비자가 실제로 결과 스트림을 다시 흡수했다는 뜻이다. readmit(가방 측)과 consumed(소비자 측)가 *양쪽에서* 회복을 확인 — 고리가 닫혔다는 양면 증거.
- **재구독은 반드시 소비자가 보낸다(0034 의 메아리)**: 0055 §9 가 지적한 난점 — orch 가 소비자를 대신해 `sub` 하면 라우팅이 orch 를 구독자로 등록한다. 해법은 *명령/실행 분리*: orch 는 "recover 하라"는 명령만 보내고(코디네이션), 실제 sub 는 소비자가 보낸다(실행). 이는 0034 버스 failover 의 "진실 원천 = 소비자"와 정확히 같은 원리 — 라우팅의 권위는 언제나 구독자에게 있다.
- **치유는 *재구독*까지 — 투영 catch-up 은 별도 경로**: 이 step 은 스트림 재개·readmit 까지 증명한다. 다운타임 동안 놓친 결과로 인한 투영(ranks) 공백은 ranking 자기 저널 reconstruct(0020)가 메우는 별도 경로다 — 이 step 은 "다시 흐르게" 까지, "놓친 것 메우기" 는 0020 의 책임(둘이 합쳐 완전 복구).
- **orch 가 세 역할 겸함**: zone failover(0009)·소비자 프레즌스(0055)·소비자 치유(이 step). 모두 "lease 기반 건강 감시+반응"이라 자연스럽지만, 규모가 크면 전용 PresenceService/HealService(계층 5 둘째 박스) 분리가 필요(후속).
- **evict 1회당 1 recover 의 멱등성**: `recovered` Set 이 같은 down 소비자에 중복 recover 를 억제하고, readmit 시 비워 재발(다음 down)에 대비한다. 만약 치유 후 소비자가 다시 죽으면 새 evict→새 recover 가 다시 발화 — 영구 self-healing 루프(이 step 은 1회 사이클만 검증·반복 사이클은 동형).
