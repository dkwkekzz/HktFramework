# step-0016 — 이벤트 버스 서비스 층 (게임 서비스 발행/구독 의미 · gateway↔service 직접 결합 제거 · 발행자 무수정 소비자 추가)

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0016/net-core.js`(0015 액터·토폴로지 빌더 복사 전진 + **ServiceBus**·**AuditService** 박스 + Gateway/서비스 버스 분기(가산) + **inject write-seam**) · `step-0016/cluster.js`(broker — 0015 그대로 + **bus/audit 재구성·inject seam**) · `step-0016/host.js`(0015 그대로 + **bus/audit 스냅샷**) · 헤드리스: `step-0016/verify.js` · 관찰: `step-0016/panel.js`(+`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **SPINE 계층 4(이벤트 버스)의 *서비스 의미* — 0012 토픽 버스가 깐 *전송* 위에 *발행/구독 계약*을 올려, 게임 서비스 경로(가방·채팅)의 gateway↔service 직접 결합(N×N)을 제거하고 "새 소비자 추가가 발행자 무수정"을 수치로 증명한다.** 0014·0015 가 게임 서비스 두 박스를 세웠으나 둘 다 gateway 가 service *주소*를 알고 직접 라우팅했다. 이 step 은 `ServiceBus`(토픽→구독자 라우팅 테이블 `Map<topic,[subscriber...]>`, **onTick 없음 = tick 무관 순수 반응형**)를 자기 OS 프로세스로 세우고: gateway 는 item/chat 인텐트를 *토픽*(svc.item·svc.chat)으로 발행(서비스 주소 무지 — spec 의 inventoryAddr/chatAddr=null), 서비스는 결과를 *토픽*(svc.item.out·svc.chat.out)으로 발행(gateway 주소 미사용). 가설의 핵 = `AuditService`(새 소비자): 4개 svc 토픽 구독·*발신 0* — 추가는 버스 구독 테이블 행뿐인데 서비스 이벤트 *전수*를 받고, 발행자들의 spec·발신 스트림·world/원장/deliveries 는 **비트 동일**. 클라 와이어 계약은 0015 그대로(토픽·pub/ev 봉투는 *서버간* 경계 — 은닉). + TESTBED §10-4 의 시나리오 **inject write-seam**(클라 intent 주입, 미제공=no-op → reg 0)을 이번 복사 전진에서 심어 `run.js scenario` 의 `inject` 명령이 활성화됐다.
>
> **관찰(눈으로)**: 전체 흐름 시각화는 `node run.js report`(0015 의 gateway↔service 직접 엣지가 사라지고 *bus 박스를 지나는 별 모양*이 보임 — bus 는 *버스* 계층 행). 시각화는 단일 testbed 로 일원화([TESTBED.md](TESTBED.md)).

step-0015 가 게임 서비스 분리를 둘째 박스(채팅)로 일반화했으나, ⓐ 가방·채팅 둘 다 gateway↔service *직접 결합*(gateway 가 서비스 주소를 알고 라우팅 — 새 소비자를 붙이려면 발행자를 고쳐야 하는 N×N 그물의 시작)이었고 ⓑ 0012 토픽 버스는 *전송*(broker 프레임 라우팅)이지 *서비스 의미*(발행/구독 계약)가 아니었다. 이 step 은 그 한 조각을 친다 — 서비스 경로를 발행/구독 의미로 올리고, *직접 결합 0·주소 무지·발행자 무수정 소비자 추가·신성한 tick·은닉·헤드리스*를 수치로 증명한다. 0001~0015 의 프로토콜·토폴로지·복원·failover·토픽 버스 전송·kill 생애주기·가방/채팅 박스는 *그대로* 두고, *버스 의미 박스 하나*(ServiceBus)와 *증명용 소비자 하나*(AuditService)만 더한다. 월드 경로(intent→존·존→뷰)와 제어 평면(orch/lease)은 의도적으로 직접 유지(시뮬 지연 경로).

결과: **전 시드 전 항목 통과.** ① 회귀 0(`reg`) — 인프로세스 모드(버스 OFF)면 0015 와 *비트 동일*(net.log·상태, *서비스 ON·버스 OFF 구성 포함* 25/25) ② E2E 동치(`e2e`) — 멀티프로세스(버스+감사 ON·토픽 버스·무열화)가 인프로세스와 *비트 동일*(log·world·inv·chat·bus·audit 6중 다이제스트)·누설 0·phantom 0·원장 보존/정합(basic-bus 10프로세스·failover-bus 13프로세스) ③ 신성한 tick(`sacred`) — 버스+감사 ON vs 전부 OFF 월드 상태 *비트 동일*·버스는 실제 일함(pub 409~427·팬아웃 818~854)·존 도달 svc 메시지 **0**·bus/audit onTick **없음** ④ 가설(`decouple`) — gateway↔service 직접 메시지 busOFF 409~427 → busON **0**(N×N 제거)·gateway 주소 무지(spec 의 서비스 주소 null)·audit 추가에 발행자 spec/발신 스트림/world·inv·chat *비트 동일*(발행자 무수정)·audit 수신 == 토픽별 발행 *전수*(409~427) ⑤ 열화 보존(`degrade`) — 버스 홉 loss 0.2·redundancy 3 에도 누설/phantom **0**·원장 보존/정합·belief 소유 ≤1(완전성만 graceful: itemDesync 1~3·chatDesync 2~6) ⑥ inject(`inject`) — 주입 실효·결정론·멀티 비트 동일 5/5 ⑦ 분리(`isolate`)·은닉(`hide`)·재현(`repro`) — bus·audit 각자 OS pid(10 호스트)·클라 누설 0·같은 시드 멀티 2회 = 인프로세스 같은 ev 스트림(auditDigest 42=0x5b289d1e … 2026=0x34678131).

## 검증 질문

> ① **회귀 0**: 인프로세스 모드(버스 OFF)면 — 서비스 ON 구성을 포함해 — 0015 동작과 비트 동일한가? (`reg`)
> ② **E2E 동치**: 멀티프로세스(버스+감사 ON·무열화)가 인프로세스와 비트 동일인가(log+world+inv+chat+bus+audit)? (`e2e`)
> ③ **신성한 tick**: 버스를 붙여도 월드 시뮬 상태가 *비트 동일*(비-침습)이면서 버스는 실제 일하고, 존에 svc/pub/ev 메시지가 0건 도달하며 bus/audit 이 onTick 을 갖지 않는가? (`sacred`)
> ④ **발행/구독 의미(가설)**: gateway↔service 직접 메시지가 0이 되고(버스 OFF 대조 >0), gateway 가 서비스 주소를 모르며, *새 소비자(audit)를 발행자 무수정으로* 추가해도(spec·발신 스트림·결과 비트 동일) 소비자가 이벤트 전수를 받는가? (`decouple`)
> ⑤ **열화 보존**: 버스 홉 열화에도 0014·0015 의 신뢰성 의미(누설/phantom 0·원장 보존/정합·소유 ≤1)가 보존되는가? (`degrade`)
> ⑥ **분리·은닉·재현 + inject**: bus·audit 이 각자 프로세스에 살고, 클라에 토픽/봉투가 안 새며, 같은 시드가 같은 ev 스트림을 재현하고, inject seam 이 결정론·멀티 동치를 지키는가? (`isolate`·`hide`·`repro`·`inject`)

## 2. 메커니즘 — 서비스 경로를 발행/구독 의미로 (이 step 의 한 조각)

```
 인프로세스(run): bus 플래그 OFF → 0015 액터 그대로 — 0015 비트 동일(reg 0, 서비스 ON 구성 포함).
                  bus 플래그 ON → ServiceBus 박스 + 발행/구독 라우팅. audit ON → 새 소비자 1박스(발신 0).

 서비스 경로(0015 직접 → 0016 발행/구독):
   0015:  client ──item_*/chat_*──▶ gateway ──item_req/chat_req──▶ inventory/chat ──결과──▶ gateway   (gateway 가 주소를 앎)
   0016:  client ──item_*/chat_*──▶ gateway ──pub(svc.item│svc.chat, ev)──▶ bus ──ev──▶ 구독자{inventory│chat, audit}
          inventory/chat ──pub(svc.*.out, ev)──▶ bus ──ev──▶ 구독자{gateway, audit} ──(gateway 가 클라로 중계)──▶ client
        (발행자는 토픽만 안다 — 구독자 0 이면 폐기(unrouted). 존(zone1/zone2)은 이 경로에 *없다* → 신성한 tick.)

 ServiceBus (tick 무관 순수 반응형 — onTick 0):
   topics: Map<topic, [subscriber...]>   ← 구독 라우팅 테이블(SSOT — 등록 순서 = 결정론 팬아웃 순서)
   pub:    for addr in topics[topic]: send(addr, {type:'ev', topic, ev})   // 구독자 전부에 사본 — 채팅 팬아웃의 서버 박스 판
   구독:   토폴로지 빌더의 선언 spec(opts.subs). 새 소비자 추가 = 이 테이블에 행 추가뿐(발행자 spec/코드 무수정).

 토픽 4개: svc.item(인텐트→가방) · svc.item.out(결과→gateway) · svc.chat · svc.chat.out  (+audit 이 4개 전부 구독)
```

0015 대비 더한 것은 *버스 의미 박스 + 증명용 소비자*뿐 — 존/배리어/kill 생애주기/서비스 로직은 *그대로*:

1. **발행/구독 = 주소 무지(은닉의 서버간 판).** 버스 ON 이면 gateway spec 의 `inventoryAddr/chatAddr = null` — gateway 는 *구조적으로* 서비스 주소를 모른다(`decouple` ②). 발신은 `_svcSend(topic, …)` 단일 경로: 버스 ON 이면 `pub(topic, ev)`, OFF 면 0015 직접 라우팅(비트 동일). 서비스도 결과를 `svc.*.out` 토픽으로 발행 — gateway 주소 미사용. net.log 에서 gateway↔service 직접 메시지가 **0**(busOFF 대조 409~427 → busON 0)이 됨이 N×N 제거의 와이어 증거.

2. **"새 소비자 추가가 발행자 무수정" — 가설의 수치 증명.** AuditService 는 4개 svc 토픽을 구독하는 새 박스다 — 추가는 *버스 구독 테이블 행 4개*뿐. `decouple` 이 audit ON/OFF 두 런을 비교한다: 발행자들(gateway·inventory·chat)의 *spec JSON 동일* + *발신 스트림(senderDigest — 내용+순서) 비트 동일* + world/inv/chat 결과 다이제스트 동일. 한편 audit 은 토픽별 발행 *전수*를 받았다(audit.seen[t] == net.log 의 pub 수, 409~427). 즉 소비자가 늘어도 발행자 우주는 비트 하나 안 변한다 — SPINE 버스 행의 약속.

3. **소비자의 비-침습은 *발신 0* 으로 구조적.** AuditService 는 `net.send` 를 호출하는 코드가 없다 — 관찰만. 0014 가방의 "onTick 부재 = 신성한 tick" 증명처럼, *능력의 부재*가 가장 강한 불변 증명이다(audit 이 받은 ev 로 무엇을 하든 발행자·월드에 되먹임 0).

4. **버스도 tick 무관 순수 반응형 + 존 우회(신성한 tick).** ServiceBus 는 onTick 이 없고(`sacred`), 존에 도달한 svc/pub/ev 메시지 0 · 월드 상태가 버스+서비스 전부 ON vs 전부 OFF 에 *비트 동일*. "그 일이 존 tick 과 같은 박자로 돌아야 하는가?" — 서비스 *라우팅*도 아니오.

5. **0014·0015 의 신뢰성 의미가 버스 경유 후에도 보존.** 버스 홉(svcbus 라우트 전체) loss 0.2·redundancy 3 열화에도: 누설/phantom **0**(라우팅 정확성 — 구독 테이블 순회는 loss 와 직교), 원장 보존/정합·belief 소유 ≤1(서비스 내부 SSOT 불변). 잃는 것은 완전성뿐(itemDesync 1~3·chatDesync 2~6 — 0015 best-effort 그대로 graceful). 홉이 1→2 로 늘어도(extra hop = gateway↔bus↔service) 신뢰성 *모델*은 변하지 않았다.

6. **inject write-seam(테스트베드 마무리 — 가산).** `opts.inject = [{tick, client, move:[dx,dy]}]` 를 run()/runMulti() 의 tick 직전 *같은 위치*에 심었다(미제공 = 호출 0 → reg 0). 주입은 클라 발신과 같은 형식(시드 로그의 일부 = 결정론)이라 멀티프로세스도 비트 동일(`inject` 5/5). run.js 의 `loadScenario` 가 `cmds[].inject` 를 이 seam 으로 번역(`NET.SUPPORTS.inject` 기능 탐지 — 과거 step 은 경고 후 무시 유지) → `node run.js scenario scenarios/inject-move.json` 이 ALL OK. TESTBED §12 의 "남은 단 하나" 가 닫혔다.

> 클라는 여전히 게이트웨이만 안다 — 토픽·pub/ev 봉투·구독 테이블·audit 은 전부 *서버간* 경계다(`hide` 누설 0). `node verify.js` 한 줄이 bus·audit 을 별 프로세스로 spawn 해 0012 토픽 *전송* 위에 묶어 4기둥을 검증한다 — 제1 운영 제약의 충족(원격·헤드리스).

## 7. ⑤ 분리 · 은닉 · 재현 · inject — `isolate`·`hide`·`repro`·`inject`, 통과

**프로세스 분리(`isolate`)** — bus·audit = 각자 구분 OS pid·통신은 버스 프레임뿐:

```
broker pid P0(TCP :Pn) · 호스트 10개 · bus pid Pb(≠broker) · audit pid Pa(≠broker≠bus) · 토픽 4개(svc.*) · pub 409·팬아웃 818 · audit 수신 409 · 버스 out 998프레임
배치: login·registry·gateway·bus·inventory·chat·audit·zone1·zone2 각 1 프로세스 · client0..5 → clients 1 프로세스
```

**은닉(`hide`)** — 전 시드: 버스+감사 ON 에도 클라 접점이 공개 주소(login·gateway)뿐, 내부 토폴로지(zone/sessionId/handoff/lease/inventory/chat_req/**"pub"/"sub"/"ev"/topic/svc.*/audit/"bus"**) 누설 **0**, 뷰 받은 클라 4/4·서비스 쓴 클라 4/4. 클라 와이어 계약은 0015 와 동일(item_*·chat_*) — 발행/구독은 순수 *서버간* 의미.

**재현(`repro`)** — 같은 시드 멀티프로세스 2회 → 같은 (audit+bus+inv+chat) 다이제스트, *인프로세스와도 동일*·world 동일: auditDigest 42=0x5b289d1e · 7=0x6b805cca · 1234=0xc3445264 · 99=0x9f18e2e9 · 2026=0x34678131. 시드별 ev 스트림이 서로 달라(5/5) 결정론이 시드의 함수임을 교차 확인.

**inject(`inject`)** — write-seam: 주입 실효(월드 변화)·결정론(2회 동일)·멀티프로세스 비트 동일 — 전 시드 5/5. `node run.js scenario scenarios/inject-move.json` → 4기둥 ALL OK(미제공 no-op 은 `reg` 25/25 가 증명).

## 8. 의외의 발견

1. **"발행자 무수정" 은 비교 가능한 *비트* 명제가 된다 — 발신 스트림 다이제스트로.** "새 소비자 추가가 발행자 무수정" 은 보통 설계 슬로건인데, 결정론 하니스에선 *수치*가 된다: audit ON/OFF 두 런에서 발행자별 발신 스트림(senderDigest — 내용+순서)을 fnv1a 로 접으면 *비트 동일*이 그 슬로건의 정의가 된다. spec JSON 동일(정적)·발신 동일(동적)·결과 동일(의미) 세 층이 전부 잡혀야 무수정이다 — 정적 비교만으론 "코드는 같은데 타이밍이 변했다"를 놓친다.
2. **버스 의미는 *전송*과 독립으로 쌓인다 — 같은 자료구조가 세 번째 등장.** 0012 broker 의 topic→Set<sock>(전송), 0015 채팅의 channel→Set<avatar>(클라 단위), 0016 ServiceBus 의 topic→[subscriber](서버 박스 단위) — 셋 다 "라우팅 테이블 순회 = 도달 집합" 패턴이고, 누설 0/주소 무지가 자료구조에서 공짜로 나온다. 멀티프로세스에선 ServiceBus *액터*가 broker 토픽 *전송* 위에 실려 돈다 — pub/sub 위의 pub/sub 인데 층이 섞이지 않는다(전송은 cmd/res 프레임만, 의미는 ev 만).
3. **홉이 늘어도 신뢰성 모델은 변하지 않는다 — 열화가 다시 갈라 보여줌.** gateway↔service 1홉이 gateway↔bus↔service 2홉이 되면 손실 표면이 2배가 될 듯하지만, `degrade` 가 보인 것은 0014·0015 와 *같은 분리*다: 라우팅 정확성·원장 불변(loss-직교) vs 완전성(graceful). 신뢰성은 *경로 길이*가 아니라 *끝점의 자료구조*(원장 멱등·belief Set)가 결정한다 — 버스를 끼워도 끝점이 같으면 모델이 같다.
4. **(작은 발견) 직접 결합 제거가 회귀 0 과 공존하려면 *분기 가산*이 유일한 길.** `_svcSend` 단일 경로로 직접/버스를 갈랐는데, 직접 모드의 메시지 객체·순서가 0015 와 한 바이트도 달라지면 reg 가 즉시 잡는다(서비스 ON·버스 OFF 행이 이를 감시). "리팩토링 했는데 와이어 불변" 을 기계가 증명해주는 것이 복사 전진+reg 의 실익.

## 9. 정직한 한계

1. **버스 의미 = 서비스 경로만(월드·제어 평면은 직접).** intent→존, 존→뷰, 존↔존 핸드오프, orch/lease 는 여전히 주소 직접 라우팅이다 — 시뮬 지연 경로라 의도적이지만, "서버간은 버스로" 의 전면 적용은 아니다. 존간 이벤트(핸드오프·ghost)의 버스 승격 여부는 후속 판단(지연 1홉 추가 비용 vs 결합 제거 이득).
2. **ServiceBus = 단일 박스·영속 0(버스가 새 단일점).** 서비스 트래픽이 전부 한 프로세스를 지난다 — bus 가 죽으면 서비스 경로 전체가 끊긴다(가방·채팅 자체는 살아 있어도). 다중 브로커 분산(0012 §9-1)·버스 failover 는 미착수. 구독 테이블도 메모리뿐.
3. **구독 = 선언 spec(정적).** 런타임 `sub` 메시지 seam 은 있으나 토폴로지는 부팅 시 고정 — 동적 구독/해지·구독자 장애 감지(죽은 구독자에게 계속 팬아웃)는 안 탔다. unrouted 폐기는 at-most-once 의미다(구독자가 늦게 붙으면 그 전 발행은 소실 — 이력/replay 없음).
4. **audit = 관찰 전용 소비자(소비자 다양성 미검증).** "발행자 무수정 추가" 증명에 발신 0 소비자를 썼다 — *발신하는* 둘째 소비자(예: 랭킹이 아이템 이벤트를 받아 자기 상태 갱신 후 발행)에서의 순서/루프 문제는 미검증. 길드·거래소·우편이 이 패턴의 실전 후속.
5. **버스 경유 완전성 = 여전히 best-effort.** 채팅 ack/resend 없음(0015 §9-2 상속) + 버스 unrouted/loss 폐기 — 신뢰 전달(채널 시퀀스·ack)은 후속.
6. **여전히 Node · 서비스 영속/failover 0 · C++ 시뮬 미교체 · lockstep 배리어.** 가방·채팅·버스 전부 프로세스와 함께 죽는다(계층 6 미진입). C++ 결정론 시뮬 코어 교체([STATE.md](STATE.md) §3 🔴)·배리어 해제(비동기 결정론)는 상속된 후속.
