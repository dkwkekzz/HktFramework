# step-0071 — 귓속말 라우터: 프레즌스 SSOT 질의로 라우팅(whisperRouter)

> 직전: [step-0070](step-0070.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0069/0070 은 프레즌스 SSOT 의 *질의 인터페이스*(presenceQuery→presenceReply·pull)와 그 failover 연속성을 세웠다. 하지만 그 질의자는 **presmon**(관찰 모델 — "질의가 도는가"를 보이는 *대역*)이었지, 인터페이스를 *써먹는* 소비자가 아니었다. SPINE 계층5 의 큰 그림은 명시한다: **프레즌스 SSOT("누가 어디에/어떤 상태인가")가 곧 귓속말·파티·핸드오프 라우팅의 단일 조회처**다. 이 step 은 그 인터페이스의 첫 *진짜* 라우팅 소비자를 더해 큰 그림을 한 칸 채운다 — 클라가 다른 대상에게 귓속말을 보내면, 라우터가 대상 상태를 프레즌스 SSOT 에 질의하고 *그 답으로 라우팅 결정*을 내리는가? (닫는 조건: up=전달·permanent=반송이 프레즌스 질의로 구동되고, whisperRouter OFF=0070 비트 동일)

## 2. 메커니즘 — 귓속말 라우터(플래그 `whisperRouter` OFF → baseline 비트 동일 = 회귀 0)

- **새 박스 `src/svc-whisper.js` (`WhisperRouter`)** — 존 tick 밖 순수 반응형(onTick 없음·권위 0). 상태: `pending`(consumer→대기 귓속말)·`routed`/`bounced`·`decisions`·질의 계측.
  - `{type:'whisper', to, body}` 수신 → `pending[to]` 에 적재 + 프레즌스 SSOT(`queryAddr`)에 `presenceQuery{consumer:to}` 발신(pull). 대상 상태를 *모르므로* 묻는다.
  - `presenceReply{consumer, state}` 수신 → `pending[consumer]` 해소: `state==='up'` 이면 대상에게 `whisperDeliver` 전달(routed), 아니면 반송(bounced). **라우팅 결정이 프레즌스 질의로 구동** — 이것이 이 step 의 핵심.
- **배선(`topo-build.js`)** — `whisperAddr = whisperRouter && presenceQuery && presenceSvcAddr && presMonAddr ? 'wrouter' : null`(질의 인터페이스 전제). 박스 생성 시 `queryAddr=presenceSvcAddr`. makeActor 에 `'whisper'` kind. `net-core.js` 진입점에 `svc-whisper` require 1줄.
- **주입(`topology.js` run 루프)** — `opts.whispers=[{at,from,to,body}]` 가 at tick 에 `client→wrouter` 귓속말 발신(정규 net.send·시드 로그 = 결정론). `wrouter` 부재(OFF)면 주입 0 = 라우팅 없음(대조군).
- **OFF 경로**: whisperRouter 미설정 → wrouter 박스 0 → 0070 토폴로지 비트 동일(reg).

## 4. 척추 체크 5항

1. **신성한 tick** ✅ — WhisperRouter 는 onTick 없음(순수 반응형). 존 tick 안에 귓속말/질의 작업 0. 비동기 서비스(SPINE §2 판정: 귓속말 라우팅은 tick 박자와 무관).
2. **결정론 코어** ✅ — 라우터는 세계 상태를 안 건드린다(권위 0). 귓속말 주입은 정규 net.send(시드 로그의 일부) — 같은 시드 같은 해시.
3. **권위 단일 소유** ✅ — 라우터는 읽기(질의)·전달만. 프레즌스 SSOT 무변경(질의는 순수 읽기). 원장 minted ON==OFF.
4. **은닉·단일 연결** ✅ — 클라는 라우터에 귓속말만 보낸다(대상 위치 무지). 라우터는 SSOT 내부를 모르고 질의/응답 계약만 안다(decouple).
5. **headless·원격 검증** ✅ — Node·UE 0. `node run.js`/`spine` 수치 증명. 새 박스도 같은 buildTopology/makeActor 경로(멀티프로세스 동치 보존).

## 9. 의외의 발견 / 정직한 한계

- **질의↔응답 상관은 consumer 키로**: presenceReply 는 `consumer`+`state` 만 싣고 어느 귓속말의 답인지는 안 싣는다 → 라우터가 `pending[consumer]` 묶음으로 상관한다. 같은 대상에 동시 다발 귓속말이면 한 응답이 묶음 전체를 해소(정확·효율). 단 *서로 다른* 질의를 구분할 reqId 상관은 아직 없다 — 같은 consumer 의 연속 질의가 인터리브하면 묶음이 합쳐질 수 있다(현 시나리오는 대상별 단발이라 무해).
- **failover 중 라우팅 연속성은 미적용(다음 후보)**: presmon 은 0070 에서 svc.presence.active 공지를 구독해 queryAddr 를 재타깃했다. wrouter 는 이 step 에서 *고정 queryAddr*(primary)만 쓴다 — primary 프레즌스 박스 사망 후 귓속말 질의가 끊긴다(0069 §9 의 라우터 판). 0070 의 재타깃 패턴을 wrouter 에 적용하면 라우팅도 failover-safe 가 된다.
- **전달은 best-effort 단발**: `whisperDeliver` 는 대상 주소로 1회 발신(대상이 서비스면 무시). 실제 플레이어 세션으로의 게이트웨이 경유 전달·전달 ack·재시도는 미착수. "routed" 는 *라우팅 결정(도달 가능 판정)+전달 시도* 까지를 센다.
- **대상 풀이 프레즌스가 아는 consumer 로 한정**: 현재 프레즌스 SSOT 는 *소비자*(서비스: ranking·inventory…) 건강만 안다 — 플레이어별 "어느 게이트웨이/어느 존" 의 진짜 프레즌스(SPINE §2 코디네이션)는 아직 SSOT 에 없다. wrouter 는 그 인터페이스가 채워지면 플레이어 귓속말로 자연 확장된다(계약 동일·질의 대상만 확대).
