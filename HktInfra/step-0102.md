# step-0102 — 미확인 체크아웃 유계화(checkoutBound·읽음측 0099 판)

> 직전: [step-0101](step-0101.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0101 의 2단계 읽음은 ack 전 미확인 메시지를 *체크아웃에 무계 보유*한다 — 읽는 이가 느리거나 죽어 영영 ack 안 하면 checkout 이 received 에 비례해 성장(0101 §9 한계). 0099 가 *수신함(inbox)* 을 최근 K 로 cap 했듯, *미확인 체크아웃* 도 유계화할 수 있는가? SPINE 계층3·5 수신함 메모리 모델의 *읽음-미확인* 차원 방어.

## 2. 메커니즘 — 체크아웃 cap (checkoutBound 0 → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-mailbox.js`): `drain()` ON 경로에서 미확인 체크아웃 msgs 를 구성한 뒤, `checkoutBound > 0` 이면 `while (msgs.length > checkoutBound) { msgs.shift(); checkoutOverflowed++; }` 로 최근 K개만 보유(가장 오래된 미확인 드롭·lossy). `drained`(ack 확인 소비)는 무손실 보존(0101). 구성 옵션 `mailboxCheckoutBound`(`src/topo-build.js` → `__mboxOpts.checkoutBound`). 0(기본)이면 cap 없음 = 0101 비트 동일.

0099 inbox cap(미읽음 방어)과 0102 checkout cap(읽음-미확인 방어)이 짝 — 둘 다 lossy 유계화, drained 만 무손실.

## 4. 척추 체크 5항

① **신성한 tick** — checkout cap 은 수신함 보유 정리, 존 tick 밖 순수 반응형. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF). ③ **권위 단일 소유** — checkout 은 수신 뷰(원장 권위 무관). ④ **은닉·단일 연결** — cap 은 Mailbox 내부. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 0099+0100+0101+0102 가 수신함 메모리를 *세 차원* 모두 유계로 닫았다 — *미읽음* inbox cap(0099·lossy)·*읽음-미확인* checkout cap(0102·lossy)·*확인 소비* drained(0100/0101·무손실). 그리고 `received`(총 수신 회계)는 셋 다 진실 SSOT 로 보존. "보유는 차원별로 cap/소비로 유계, 진실은 분리"가 일관된 형태 — 메모리 ⟂ 진실의 4-step 완성.
- **한계**: checkout cap 은 *가장 오래된 미확인*을 드롭한다 — 슬로/데드 리더의 보유 누설 방어지만, 드롭된 미확인 메시지는 잃는다(lossy). 정말 살아있는 리더라면 drained(무손실)로 가야 하고, cap 은 죽은 리더 한정 안전망이다. 또한 cap 은 *현 배치* 크기 기준 — drain 사이 inbox 가 inboxBound 로 이미 cap 되면 중복 방어(직교지만 합성 동작은 미검증). E2E 게이트웨이 경유 읽음 경로는 여전히 후속(0101 §9).
