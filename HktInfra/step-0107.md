# step-0107 — 거래소 서비스 분리(아이템 escrow 거래·쌍 거래 보존)

> 직전: [step-0106](step-0106.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

SPINE 계층3 게임 서비스의 *거래소* 박스가 아직 비어 있다(거래소/우편/길드 미착수). 가방(0014)이 *한 소유자* 원장이라면, 거래소는 *두 당사자 사이*의 아이템↔대가 교환을 존 tick 밖에서 비동기로 성립시켜야 한다 — 그러면서도 핵심 netcode 불변(권위 단일 소유 + 쌍 거래)을 깨지 않을 수 있는가? *존을 넘는 거래가 존간 결합 없이* 성립하는가(SPINE §2 가방 행)?

## 2. 메커니즘 — escrow 쌍 거래 원장 (exchange OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-exchange.js` 새 박스): `ExchangeService` — `onMsg` 만(onTick 0·발신 0·순수 반응형). `exchList{seller,item,price}` = 매물 등록(거래소 escrow 로 acquire·listed++·open++). `exchBuy{buyer,id}` = 매물 있으면 체결(escrow→구매자 deliver·대가→판매자 proceeds·매물 delete·sold++), 없으면/닫혔으면 거부(rejects++·이중 판매 0). `exchCancel{seller,id}` = 소유자 일치 매물이면 escrow 반환(returned·cancelled++), 아니면 거부. 배선: `net-core`(require)·`topo-actors`(case 'exchange')·`topo-build`(exchange 옵션→박스)·`topology`(exchangeOps 훅·exchange 반환). exchange OFF(기본)면 박스 0 = 0106 비트 동일.

**보존 불변**: `listed == open + sold + cancelled` — 모든 listed 아이템은 매 순간 정확히 한 상태(공백·중복 0). 가방(0014)의 단일 소유+쌍 거래를 두 당사자 교환으로 확장.

## 4. 척추 체크 5항

① **신성한 tick** — 거래소는 onMsg 만(존 tick 밖)·발신 0 비-침습. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF)·listingId 단조 발급(결정론). ③ **권위 단일 소유** — escrow 는 거래소의 단일 쓰기 권위·이동은 쌍 거래(list=acquire/buy·cancel=release)·매 순간 소유자 1(보존). ④ **은닉·단일 연결** — 거래 요청은 메시지 계약(exchList/Buy/Cancel)만·내부 escrow 비가시. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 거래소가 가방(0014)과 *같은 골격*(존 밖 단일 소유 원장 + 쌍 거래)으로 섰다 — 다른 것은 *당사자 수*(가방=1, 거래소=2)뿐. "권위 단일 소유 + release+acquire 쌍"이 1-당사자(가방 이동)·2-당사자(거래소 체결)·N-당사자(파티 0083)에 같은 형태로 적용됨이 또 확인된다. 닫힌 매물 재거래 거부는 0026 belief dedup(이중 mint 차단)의 *거래* 판 — exactly-once 체결.
- **한계**: 거래소는 *자기 escrow 원장*만 권위 — 실제로는 list 시 가방(inventory)에서 아이템이 *빠지고* buy 시 구매자 가방으로 *들어가야* 한다(거래소↔가방 2-서비스 원자 거래·존 넘는 거래의 진짜 형태). 이번엔 거래소 단독 보존만 증명(가방 결합은 후속). 또한 영속(crash→매물 재구성·0017 가방 판)·발행(svc.exchange.* 관측)·대가 통화 모델도 후속. 거래 요청은 인프로세스 직접 주입(exchangeOps 훅)·게이트웨이 경유 E2E 는 후속.
