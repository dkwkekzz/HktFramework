# step-0117 — 거래소↔가방 list 인출 (exchInventory leg 1 · escrow 실체화)

> 직전: [step-0116](step-0116.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0107~0116 의 escrow 는 *추상*이었다 — 거래소 자기 카운터로만 굴러 실제 가방(inventory) 아이템은 빠지지 않았다(판매자가 list 후에도 보유·존 넘는 거래의 진짜 형태 아님·0107 §9). escrow 를 *가방 원장의 reserved 아바타 'escrow'* 로 실체화해, exchList 가 가방 아이템을 판매자→escrow 로 실제 이동시키는가? 닫는 조건: exchInventory ON 이면 list 한 itemId 가 가방 원장에서 'escrow' 소유(판매자 0)·gives/transfers 만큼·minted 불변, OFF 면 give 0 = 0116 비트 동일(reg·추상 escrow).

## 2. 메커니즘 — escrow 를 가방 원장에 실체화 (exchInventory OFF → baseline 비트 동일 = 회귀 0)

- **`_custody(itemId, from, to)` 헬퍼**: `invMode && inv && itemId != null` 이면 가방에 `{type:'item_req', op:'give', itemId, fromAvatar:from, toAvatar:to}` 전송 + `gives++`. 미충족이면 no-op(추상 escrow).
- **exchList 인출 레그**: 매물 등록 시 `_custody(p.itemId, p.seller, 'escrow')` — 아이템이 판매자 가방 → escrow custody 로. 가방이 give 를 처리(보유 검사·xfer·역인덱스) → escrow 소유. listing 에 itemId 저장(buy/cancel/expire 의 입금/반환 레그가 쓸 참조·후속).
- **권위 = 가방**: 거래소는 *요청만*(명시 인터페이스 give), 실제 소유 전이는 가방이 권위로 수행(판매자가 이미 안 가진 아이템은 give 거부 = 이중 판매 0). escrow custody 가 가방 원장에 산다.
- **배선**: topo-build(`exchInventory` → 거래소 spec 에 `inv: inventoryAddr, invMode`)·topology(`invOps` 테스트 seam — 판매자 가방 선-적재)·svc-exchange(`_custody`·listing/journal itemId·reconstruct·crash gives).
- **회귀 0**: exchInventory OFF(또는 itemId 부재)면 give 분기 휴면 = 0116 비트 동일. itemId/gives 필드는 추가될 뿐 동작 무영향.

## 9. 의외의 발견 / 정직한 한계

- **발견**: escrow 를 *가방의 reserved 아바타*로 모델하니 거래소↔가방 결합이 새 권위 충돌 없이 성립한다 — 아이템 쓰기 권위는 여전히 가방 *하나*(escrow 도 가방 원장의 한 소유자일 뿐)이고, 거래소는 give *요청자*다. 0014 가방의 "단일 소유 + 쌍 거래"가 *두 서비스에 걸친* 거래에도 그대로 적용됨이 확인(권위는 한 박스, 다른 박스는 요청). list 인출이 0014 give(아바타↔아바타)와 정확히 같은 연산(seller↔escrow).
- **한계**: 이번엔 *인출 레그*만 — buy/cancel/expire 의 입금(escrow→buyer)·반환(escrow→seller) 레그는 후속(0118~). give 는 *낙관적*(fire-and-forget) — 판매자가 아이템을 안 가졌으면 가방이 give 를 거부하지만 거래소 listing 은 그대로 생성된다(원자성/보상 롤백은 후속·saga). give 결과(item_result)를 거래소가 아직 안 듣는다(비동기 ack 후속).
