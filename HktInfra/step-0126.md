## 검증 질문

0125 는 회신 손실을 *감지*만 했다(pending 잔존). 0125 §9 는 경고했다 — **naive 재전송은 위험**: 회신만 손실된 give(가방서 이미 성공)를 거래소가 재전송하면, 가방이 *재실행*해 `owner≠from`(이미 escrow) 으로 `ok:false` 오판 → 보상(0122)이 *valid 매물을 잘못 abort*(안전 위반). 질문: 거래소가 미해결 give 를 재전송해 pending 을 닫되, 그 재전송이 *안전*한가 — 즉 가방이 멱등(재실행 0)으로 *원래 결과를 재회신*하는가. 채우는 계약: 거래소↔가방 saga 의 신뢰 전달(0042 seenReqs 요청 dedup 의 *saga 회신 판*) — 0125 감지의 *복구* 절반.

## 2. 메커니즘 — 재전송 + 멱등 dedup (exchRetry op + sagaDedup; OFF → baseline 비트 동일)

- **거래소 재전송**: `_custody` 가 give 파라미터를 `pendingGive`(gid→{itemId,from,to,cause})에 보관. `exchRetry` op 수신 시 `pendingGive` 의 각 gid 를 *같은 gid* 로 재발신(`retries++`·gives/pending 무증가 = 재전송). ack 도착 시 pending/pendingGive 함께 delete.
- **가방 멱등 dedup**: give 에 (replyTo,gid) 가 있고 `sagaDedup` ON 이면 키 `replyTo+' '+gid`. `sagaResults` 에 키가 있으면 *재실행 없이* 저장된 ok 를 `_sagaReply` 로 재회신. 없으면 실행 후 결과 저장.
- **OFF 플래그**: `sagaDedup` 기본 false → 저장 0·dedup 0. `exchRetry` op 은 테스트 시나리오에만 → reg 시나리오엔 재전송 0·pendingGive 빔. 둘 다 → 0125 비트 동일.

- **dedup ON = 안전 복구**: 재전송→가방이 저장 ok:true 재회신→pending 0·giveOks 1·aborted 0·open 매물 ≡ 가방 escrow `["item0"]`(2-서비스 안전 회복). 0125 의 지식 격차가 닫힌다.
- **dedup OFF = 오보상(dedup 필요성)**: 재전송→가방 *재실행*→owner=escrow≠s1→ok:false→보상이 valid 매물 abort→거래소 open `[]` ≠ 가방 escrow `["item0"]`(안전 위반). 0125 §9 경고의 재현.

## 9. 의외의 발견 / 정직한 한계

- **dedup OFF 의 corruption 이 *보상* 경유로만 터진다**: dedup OFF 라도 보상(compensate)이 없으면 재실행 실패는 *무해*(아이템은 이미 옮겨졌고 false ack 는 회계에만 영향). compensate 와 결합할 때 valid 매물 abort 로 *안전*이 깨진다 — 즉 0122 보상과 0125 재전송이 *함께* 오면 멱등이 필수. 이 결합이 dedup 필요성의 정확한 조건.
- **한계 — sagaResults 무계 성장**: dedup 맵은 처리한 모든 (replyTo,gid)를 무계로 쌓는다. 유계화(워터마크 가지치기·0042 busSeenBound 의 saga 판)는 후속. 현 테스트는 give 소수라 무해.
- **한계 — 재전송 트리거가 명시 op**: exchRetry 는 외부 op 주입(거래소가 onTick 없는 순수 반응형이므로). 실서버는 타임아웃 기반 자동 재전송이 필요 — 제어 평면 sweep(0031 wfPeriod 판)으로 후속. 요청 손실(give 자체 손실)도 같은 재전송이 복구하나(가방 미실행→첫 실행), 본 테스트는 회신 손실만 다룸.
