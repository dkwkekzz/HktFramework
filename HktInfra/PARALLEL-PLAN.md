# PARALLEL-PLAN — step-0002 시대의 병렬 분해안 (계획, 실행 보류)

> 이 문서의 역할: HktInfra 시리즈가 **"한 step = 한 조각, 직전 step을 잇고 회귀 0 증명"**(CLAUDE.md)이라 STATE §2 "다음"이 항상 step 하나만 가리키는 구조적 직렬성을, **방법론의 두 불변(reg-0 사슬 · STATE 단일 SSOT)을 깨지 않으면서** 병렬로 푸는 방법을 적는다.
>
> 상태: **계획만 확정. 실제 step 구현은 보류.** 실행 결정 시 이 문서의 갈래 카드를 그대로 집어 worktree 격리 에이전트에 분배한다.

---

## 1. 진단 — 왜 지금 "다음 step"이 1개뿐인가

우연이 아니라 설계다. `CLAUDE.md` 불변 규칙:

- **한 step = 한 조각** — 직전 step의 `net-core.js`를 이어받아 `reg`로 비트 단위 회귀 0을 증명해야 한다.
- **STATE.md = 단일 SSOT** — "지금 어디까지·다음은 무엇"이 오직 STATE §2에만 살고, 항상 하나의 가설만 가리킨다(현재 step-0002 = 존 결정론 복제).

→ 모든 step이 **같은 결정론 코어**(`step-NNNN/net-core.js`)를 직렬로 수정하기 때문에, 둘을 동시에 돌리면 코어가 충돌하고 reg-0 기준선이 갈라진다. **이것이 진짜 병목이다.**

---

## 2. 병렬화의 열쇠 — 두 종류의 격차

STATE §3 열린 격차를 **"존 VM tick(결정론 코어)을 변형하는가"** 로 가른다.

### 🔴 코어 경로 (반드시 직렬 — VM 상태 위에 reg-0를 사슬로 쌓음)

`ZoneServer.onTick`(존 VM)을 직접 건드리므로 직전 VM 해시 사슬에 의존한다. 동시 진행 불가.

- **step-0002 존 결정론 복제** ← 현 임계 경로 (STATE §2)
- 다중 클라 intent 인터리빙 · 존 배정 로직 · AOI · 클라 예측/조정 · 공간분할+권위 핸드오프

### 🟢 주변 박스 (각자 step-0001 동결본에서 분기 → 서로 독립으로 reg-0 증명)

존 VM tick을 변형하지 않고 **서로 다른 박스 + 서로 다른 verify 차원**을 채운다. step-0001 `net-core.js`의 **각기 다른 이음새**에 붙는다:

| 갈래 | 이음새 (step-0001 코드) | 박스 (SPINE §6) |
|---|---|---|
| A 전송 모델 | `Net.send/step` (무손실·즉시 큐) | 버스/전송 |
| B 직렬화 포맷 | 메시지 `payload` · `ZoneServer.serialize()` | (횡단) 와이어 포맷 |
| C 로그인 수명주기 | `LoginServer` · `SessionRegistry` | 엣지 · 코디네이션 |
| E 시각 관찰 셸 | `run()` 결과 → panel/html | (관찰) |

A·B·C·E는 `ZoneServer.onTick`의 ①intent적용 ②VM전진 ③권위장부를 **한 줄도 바꾸지 않으므로**, 같은 동결 베이스에서 각자 독립적으로 회귀 0을 증명할 수 있다. (HWS가 step-0007에서 `engine/`을 공통화한 것과 같은 수순.)

---

## 3. 선행 1회 — `engine/` 동결 베이스 추출 (병렬의 전제)

병렬 갈래들이 충돌 없이 같은 토대를 공유하려면, 먼저 step-0001의 공통 커널을 **동결**해야 한다. STATE §2가 이미 예고한 작업이다("공통 하니스는 초기 몇 step 뒤 `engine/` 한 곳으로 — 0002가 0001 코어를 잇는 첫 사례").

- **추출 대상**: `mulberry32` · `fnv1a` · `Net` · 박스 4종(`LoginServer`/`SessionRegistry`/`Gateway`/`ZoneServer`) · `Client` → `engine/`
- **불변**: 추출 직후 step-0001 verify가 **골든 해시 5종(42·7·1234·99·2026)과 비트 동일** — 순수 리팩터(reg-0).
- **이후**: 각 갈래는 `engine/`을 import 하고 **자기 이음새만** 확장하는 `net-core.js`를 새로 쓴다. `engine/` 자체는 갈래가 건드리지 않는다(읽기 전용 토대).

> 이 한 번의 직렬 작업이 병렬화의 게이트다. 동결 없이 병렬화하면 4갈래가 각자 step-0001을 포크해 `Net`/박스를 중복 수정 → 충돌·reg-0 분기.

---

## 4. 병렬 갈래 카드 (동결 베이스에서 동시 진행)

각 카드는 step 작성법(CLAUDE.md)의 산출물 형태를 따른다: `net-core.js`(이 갈래가 더한 로직만) + `verify.js`(reg-0 + 가설). 번호는 임시 네임스페이스 `0002-X` — 수렴 step에서 재선형화한다.

### 🟢 0002-A — 전송 모델 (지연·손실·순서)
- **더할 한 조각**: `Net`을 `LossyNet`으로 — tick 지연 분포·드롭률·재정렬을 시드 의사난수로. 핸드셰이크/뷰/intent가 손실·재정렬 아래서도 계약을 지키는가.
- **독립성 근거**: 메시지 *배달 타이밍*만 바꾼다. 존 VM 로직 미접촉.
- **verify 차원**: ① reg-0 (drop=0·delay=0이면 step-0001 골든 해시 비트 동일) ② 손실/재정렬 아래 핸드셰이크 완료율·뷰 도달 ③ **타이밍 비결정 ↔ 상태 결정론 분리** 증명(같은 intent 로그면 도착 순서 흔들려도 최종 해시 동일 — STATE §3 ⬜ 핵심).
- **해소 격차**: STATE §3 "⬜ 전송이 무손실·즉시".

### 🟢 0002-B — 메시지 직렬화 포맷
- **더할 한 조각**: 박스 간 메시지(intent/뷰/제어)를 명시적 와이어 포맷으로 encode/decode. 현재 JS 객체 직통을 바이트(또는 정규 문자열) 경유로.
- **독립성 근거**: 의미는 그대로, *표현*만 추가. round-trip(encode∘decode=항등)이면 VM 입력 불변.
- **verify 차원**: ① reg-0 (round-trip 후 골든 해시 비트 동일) ② 포맷 안정성(필드 순서·정수 인코딩 결정론) ③ 크기 계측(후속 AOL/대역폭 step의 기준선).
- **해소 격차**: STATE §3 병행 백로그 "⬜ 메시지 직렬화 포맷".

### 🟢 0002-C — 로그인 큐·티켓 만료·재접속
- **더할 한 조각**: `LoginServer` 스텁 → 로그인 대기열(admission) · 티켓 TTL 만료 · 재접속(동일 계정 재입장) 경로. `SessionRegistry`의 수명주기 확장.
- **독립성 근거**: 엣지/코디네이션 박스. 존 VM은 enter/leave 계약만 보므로 영향 0.
- **verify 차원**: ① reg-0 (큐 깊이=0·TTL=∞·재접속 시나리오 off면 step-0001 비트 동일) ② 대기열 입장 순서 결정론 ③ 만료 티켓·재접속 후 세션 SSOT 정합(권위 보존).
- **해소 격차**: STATE §3 "⬜ 로그인 큐·티켓 실체화" + 병행 백로그 "⬜ 재접속·티켓 만료".

### 🟢 0002-E — 시각 관찰 셸
- **더할 한 조각**: `panel.js` + `step-0002-E.html` — 토폴로지(박스·메시지 흐름) · 대역폭 · 해시 사슬 타임라인 관찰 셸. (HWS 공통 UI 엔진 패턴 차용.)
- **독립성 근거**: 순수 관찰. `run()` 결과만 읽고 코어 0 영향.
- **verify 차원**: 4기둥 비자극(reg-0 자명) — 산출물은 *관찰 가능성*. 후속 갈래들의 디버깅 토대.
- **해소 격차**: STATE §3 병행 백로그 "⬜ 시각 관찰 셸".

> **묶음 권장**: A·B는 와이어(전송·포맷)로 인접하나 이음새가 달라(`Net` vs `payload`) 충돌 없음. C는 엣지로 완전 분리. E는 무충돌. 4갈래 전부 동시 가능. 보수적으로 가면 가장 독립적인 **A·B 2갈래 선발** 후 패턴 검증.

## 5. 임계 경로 (병렬 갈래와 별도로 진행)

### 🔴 step-0002 — 존 결정론 복제 (STATE §2 그대로)
권위·추종자 두 존 인스턴스에 같은 intent 로그를 공급해 상태 바이트 0 전송으로 매 tick 해시 일치. **코어 경로라 직렬** — 동결 `engine/` 위에서 진행하되, 위 4갈래와 코드 충돌 없음(존 VM의 *복제* 차원, 갈래들은 전송/포맷/엣지/관찰 차원).

---

## 6. 수렴 1회 — 통합 step (병렬의 닫기)

병렬 갈래는 닫힐 때 STATE를 각자 갱신하지 않는다(SSOT 충돌 방지). 대신:

1. 4갈래 + step-0002가 각자 worktree에서 **reg-0 vs 동결 베이스**를 통과.
2. **통합 step**이 검증된 갈래들을 `engine/`로 병합 — 합쳐도 reg-0(모든 플래그 off = 동결 베이스 비트 동일) 재증명.
3. STATE §1~6을 **한 번에** 덮어쓰고, §7 INDEX에 갈래별 1행씩 append(재선형화: `0002` · `0002-A` …).
4. 각 갈래의 *의외의 발견·정직한 한계 전문*은 각 `step-0002-X.md`에 남긴다(STATE는 중복 누적 금지 — CLAUDE.md).

## 7. 방법론 정합 — 무엇을 지키고 무엇만 바꾸는가

| 불변 | 병렬화 후에도 유지되는가 |
|---|---|
| 회귀 0 (reg, maxDiff=0) | ✅ 각 갈래가 *동결 베이스* 대비 비트 동일 증명. 사슬의 마디가 1개→공통 베이스 1개 + 갈래 N개로 바뀔 뿐. |
| 결정론 코어 (intent→VM 단일 경로) | ✅ 갈래들은 VM 미접촉(전송/포맷/엣지/관찰). step-0002만 VM 복제 차원. |
| 권위 단일 소유 | ✅ C(세션)·step-0002(복제)가 각자 검증. 갈래 간 권위 교차 없음. |
| 은닉·단일 연결 | ✅ 변경 없음. |
| STATE 단일 SSOT | ✅ 병렬 중엔 갈래가 STATE 미수정 → **수렴 step에서 1회 갱신**으로 SSOT 보존. |
| 한 step = 한 조각 | 🟡 **여기만 완화** — 각 갈래는 여전히 "한 조각"이되, 조각들이 *동시에* 굴러간다. 직렬 번호는 수렴 step에서 재선형화. |

**유일한 일탈**: "한번에 한 조각만 진행"의 *동시성*. 각 조각의 크기·검증 엄밀성은 그대로다.

## 8. 정직한 한계 / 주의

- **동결 게이트가 진짜 전제**: §3 `engine/` 추출 없이 병렬화하면 4갈래가 step-0001을 중복 포크 → `Net`/박스 충돌·reg-0 분기. 동결을 건너뛰지 말 것.
- **B(직렬화)와 A(전송)의 약한 결합**: 둘 다 와이어를 만지므로, 통합 시 "포맷된 메시지를 손실 전송에 태우는" 교차가 생긴다 — 수렴 step에서 한 번 더 reg-0 재증명 필요(개별 갈래 통과만으론 부족).
- **step-0002(복제)는 여전히 코어 임계 경로**: 병렬 갈래가 빨라도 월드 계층의 다음 직렬 마디(복제→인터리빙→AOI→핸드오프)는 순서를 지킨다. 병렬화는 *주변 박스*의 처리량을 올릴 뿐, 코어 사슬을 단축하지 않는다.
- 이 문서는 **계획**이다. 실행 결정 시 §4 갈래 카드를 worktree 격리 에이전트에 분배하고, §6 수렴 step으로 닫는다.
