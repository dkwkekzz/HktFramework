# step-0018 — 가방 저널 스냅샷 압축 (event sourcing 의 "intent 로그 + 주기 스냅샷")

> 직전: [step-0017](step-0017.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

step-0017 이 가방 원장을 *append-only 영속 저널*(event sourcing)로 깔았으나, 그 저널은 **무한 성장**했다 — 모든 mint/xfer 가 영원히 쌓이고 복구는 *전체 저널*을 처음부터 replay 했다(0017 한계 ⓑ). 이 step 은 SPINE·§4 DURABLE 의 정전 패턴 **"intent 로그 + 주기 스냅샷"** 을 가방에 깐다: 저널을 (스냅샷 1개 + 짧은 tail)로 *유계*화하면서, **스냅샷+tail replay 가 전체-저널 replay 와 비트 동일**(무손실 압축)함을 증명한다. SPINE 계층 6(데이터)의 PersistStore 박스를 *프로덕션 형태*(유계 저장)로 한 걸음 더 민다.

**닫는 조건**: ① snapshot OFF(=0) 면 0017 과 비트 동일(회귀 0) ② 스냅샷+tail replay == 전체 replay == 무재시작 원장 *비트 동일*(무손실) ③ 저널 크기 절감(full→tail) ④ 압축이 라이브 원장·월드·E2E 에 비-침습.

## 2. 메커니즘 — 스냅샷 압축 (snapshot:N OFF → 0017 비트 동일 = 회귀 0)

한 조각 = **반응형 스냅샷 + persist-측 저널 압축 + 스냅샷-베이스 replay**. 세 곳만 더했다(`engine/` 무수정).

1. **가방 — 반응형 스냅샷 발신** (`InventoryService._journal`/`_snapshot`): 저널 항목 N개마다(`journalSeq % N === 0`) 현재 원장 스냅샷 `{upToSeq, ledger, mintTotal, minted, transfers}` 를 persist 로 write-behind. *op 처리 중*(onMsg) 발신 = onTick 0 유지(신성한 tick 밖). 라이브 원장은 안 건드린다 → invDigest 불변.
2. **PersistStore — 압축** (`onMsg` snapshot 분기): 스냅샷 수신 시 `journal = journal.filter(e => e.seq > snap.upToSeq)` — 스냅샷이 *이미 담은* 헤드 저널을 폐기, tail 만 보존. `writes` 는 *안 줄인다*(영속된 변이 누적 수 = 완전성 진실).
3. **가방 — 스냅샷-베이스 replay** (`replay(journal, snapshot)`): 스냅샷이 있으면 원장 베이스를 스냅샷에서 복원(폐기된 헤드 저널을 대신)하고, `maxMintId/maxSeq` 를 스냅샷 값으로 시드한 뒤 tail(seq>upToSeq)만 적용. snapshot 없으면(압축 OFF) 0017 전체 replay 경로 *비트 동일* 휴면.

복구 안무(crash→spawn→replay·라우팅 전환)는 0017 그대로 — inproc `run()` 과 multiproc `cluster.js`/`host.js` 모두 snapshotOne 이 `{journal(tail), snapshot}` 를 함께 읽어 `replay` 에 넘긴다. **압축은 전부 persist-측/제어 평면** → 월드·net.log·E2E 에 비-침습.

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

**compact(이 step 의 가설)** — 무손실 압축 + 저널 절감:

| 42 | 0x7a122947 | 0x7a122947 | 0x7a122947 | 예 | 60→0 | 100 | 10 |
| 7 | 0x9a31a1e5 | 0x9a31a1e5 | 0x9a31a1e5 | 예 | 57→3 | 95 | 9 |

세 복구 경로(스냅샷+tail · 전체 저널 · 무재시작)가 *전부 같은 invDigest* = 무손실. 저널 92~100% 절감. desync 0·소유≤1·저널완전(writes==변이) 전 시드. invDigest 가 0017 값(42=0x7a122947…2026=0x4bc176e1)과 *동일* = 압축이 라이브 원장에 비-침습.

**sacred(신성한 tick)** — world on=off 비트 동일 · 저널 writes 57~60(==mint+xfer) · 존 도달 0 · persist onTick 없음. 스냅샷 발신도 존 우회.

**e2e(E2E 동치)** — 멀티프로세스=인프로세스 비트 동일(log+world+inv+chat+bus+audit+persist), persist-bus 11·restart-bus 12 프로세스, 누설 0. multiproc 도 60항목→스냅샷 압축·복구 via 스냅샷 베이스(저널 tail 0).

**recover(0017 가설 유지)** — 압축 ON 에도 복구 투명(복구 원장==무재시작)·영속 OFF+restart 는 소실(0 vs 51~56)·itemDesync 0·저널 완전.

**degrade(열화 내성)** — 버스 홉 loss 0.2+redundancy 3 에도 누설/phantom 0·보존/정합·소유≤1(압축은 라우팅 의미 비-침습).

**isolate/hide/inject/repro** — persist 자기 pid·안 죽음·60항목 압축·복구 via 스냅샷(tail 0) · 클라 누설 0(스냅샷/압축은 제어 평면) · inject 그대로 · 멀티 2회=인프로세스 동일.

**spine** — 18 step 비트 사슬 통과(`결과: ALL OK (18 step 비트 사슬 통과)`).

## 4. 척추 체크 5항

1. **신성한 tick** ✅ — 스냅샷 발신은 op 처리 중(반응형·onTick 0), 압축은 persist-측. world on=off 비트 동일·존 도달 0.
2. **결정론 코어** ✅ — 스냅샷=원장 상태의 함수(시드·로그). 스냅샷+tail replay == 전체 replay 비트 동일(무손실 결정론).
3. **권위 단일 소유** ✅ — 원장 쓰기 권위 단일(InventoryService). 압축은 *보관 형태*만 바꿈 — 소유≤1·보존/정합 유지.
4. **은닉·단일 연결** ✅ — 스냅샷/압축/replay 전부 서버간/제어 평면. 클라 누설 0(hide).
5. **headless·원격 검증** ✅ — `node run.js` 한 줄이 압축·multiproc 복구를 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **발견 — 완전 압축(tail 0)에서도 복구 투명**: SNAP_N=6·RESTART_AT=60(quiescent)이면 마지막 op 가 마침 스냅샷 경계에 떨어져 tail 이 *0*이 되는 시드(42·1234)가 있다. 이때 복구는 `replay([], snapshot)` = *순수 스냅샷 베이스*만으로 원장을 재현한다 — 저널 항목 0개로도 invDigest 일치. 압축의 극한(저널 완전 흡수)이 복구를 깨지 않음을 우연히 검증.
- **발견 — `writes` 가 완전성의 올바른 진실**: 압축이 `journal.length` 를 줄이므로 0017 의 `journalComplete = journal.length == mint+xfer` 는 압축 후 깨진다. 영속된 변이의 진실은 *누적 writes*(압축 불변)다 — `journalComplete` 를 writes 기반으로 옮기니 0017(압축 OFF, writes==length)·0018 양쪽에서 성립. 압축은 *보관*을 줄일 뿐 *영속된 변이 수*는 안 줄인다는 불변의 코드화.
- **한계 — 스냅샷 자체의 비유계**: 저널 tail 은 유계화됐으나 스냅샷은 *전체 원장*을 매번 직렬화한다(원장 크기에 비례). 대형 원장이면 스냅샷 비용이 크다(증분 스냅샷·델타 체크포인트 미착수).
- **한계 — write-behind 윈도 잔존**: 0017 의 *활성 중 죽음=in-flight 손실*(ack/resend 없음)은 여전히 열려 있다 — 이 step 은 *저널 크기*를 풀 뿐 *신뢰성*은 안 건드린다(후속 ⒜).
- **한계 — 압축의 단일 트리거**: 스냅샷은 *항목 수*(N)로만 발화한다 — 시간·바이트·idle 기반 트리거나, 스냅샷 발신 자체의 손실/ack(스냅샷이 전송 중 유실되면 압축 미발생)·다중 복제는 미착수. 압축 정책은 단순 고정.
- **한계 — 단일 PersistStore·디스크 0**: 0017 의 단일점·메모리 저널·fsync/복제 0 은 그대로(데이터 계층의 *영속 자체*는 여전히 프로세스 RAM).
