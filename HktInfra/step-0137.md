# step-0137 — saga 재admission 횟수 상한(readmitMax — 무한 abandon↔readmit 루프 방지·2단 유계)

> 직전: [step-0136](step-0136.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0134/0136 §9: 손실이 영구하면 abandon→readmit→retry→abandon→… 이 무한 반복될 수 있다(특히 autoReadmit 가 매 회복 신호마다 재개). **gid 가 일정 횟수 재admission 된 뒤 영구 실패로 처리해 루프를 끊으면서, 영구 실패 give 가 2-서비스 안전(open==escrow)·회계 정합(sagaConsistent)을 깨지 않는가?** 채우는 박스/계약: SPINE 계층3 saga liveness 의 *상한 종결*(0131 재전송 상한과 합친 2단 유계).

## 2. 메커니즘 — 재admission 카운트 + 영구 실패(플래그 OFF → baseline 비트 동일 = 회귀 0)

- `_readmit()` 가 재개하는 gid 마다 `readmitCount[gid]++`.
- `_resendPending()` 포기 분기에서 `readmitMax>0 && readmitCount[gid] >= readmitMax` 면 *영구 실패*: `abandonedGive` 에 넣지 않고(재admission 차단)·`readmitCount.delete`·`permFailed++`·`continue`(saga_abandoned 발행도 skip — 0138 의 saga_failed 로 예약). 그 give 는 pending(Set)에 남아 미해결.
- **회귀 0**: `readmitMax===0` 이면 영구 실패 분기 건너뜀 → 항상 abandonedGive(0136 동일). readmitCount 는 내부 맵(_readmit 에서만 채워짐·관찰 무영향)·crash() 리셋·ack 정리만 추가 → baseline(0136) 비트 동일.

## 4. 척추 체크 5항

① **신성한 tick**: 영구 실패는 외부 exchSweep op 포기 분기(존 tick 밖). ② **결정론 코어**: 카운트 비교 결정론(시드 전 동일). ③ **권위 단일 소유**: 영구 실패는 재admission 차단일 뿐 권위 이동/이중쓰기 0. ④ **은닉·단일 연결**: 서버간 제어 평면(클라 무관). ⑤ **headless·원격 검증**: `node run.js` 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **2단 유계**: 0131 재전송 상한(abandon 당 sagaMaxRetries 회) × 0137 재admission 상한(readmitMax 회 재개) → 한 give 의 총 재전송 ≤ sagaMaxRetries×(readmitMax+1) 로 닫힌다. 영구 손실에도 작업이 발산하지 않는다.
- **영구 실패는 종결이지 해소가 아님**: permFailed give 는 pending 에 영영 남는다(미해결·sagaConsistent 가 그것을 정직하게 셈). 이를 *발행*(svc.exchange.saga_failed·운영 종결 통보)하거나 *보상*(운영 개입)하는 것은 후속(0138).
