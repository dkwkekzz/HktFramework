# step-0046 concepts — Per-Producer Namespacing (composite dedup keys for multiple gateways)

> 정식 기록: [step-0046.md](step-0046.md) · 현재 위치: [STATE.md](STATE.md)

## 개념 한눈표

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|------|-----------|---------------------|
| producer-local id | 발신자마다 *독립적으로* 0,1,2… 세는 카운터 | 게이트웨이 reqId — 발신자가 다르면 겹친다 |
| 네임스페이스 충돌 | 서로 다른 출처의 같은 id 가 한 공간에서 부딪침 | gw1 reqId k vs gw2 reqId k → 단일 Set 에서 동일 |
| 복합키(composite key) | (출처, 지역 id)를 묶어 전역 유일 키로 | seenReqs 키 = (producer, reqId) |
| 은닉과 네임스페이스 | 수신자가 발신자를 *모르므로* 출처는 *메시지에 실려야* 한다 | producer 태그 = 결합 없는 네임스페이스 신호 |
| 거울 대칭(producer↔consumer) | 0044 가 소비자 측 다중화였다면 이건 producer 측 | 둘 다 "단일→다중 참여자" 일반화 |

## 1. producer-local id 는 왜 겹치는가

분산 시스템에서 각 발신자(게이트웨이)는 *자기만의* 단조 카운터로 메시지에 순번을 매긴다 — 전역 합의 없이(그게 빠르고 결정론적이니까). 0037 의 reqId 가 그렇다: 게이트웨이가 보내는 k 번째 요청에 reqId=k. 단일 게이트웨이면 reqId 가 곧 전역 유일 id 다. 그러나 게이트웨이가 *둘* 이상이면 — SPINE 의 "게이트웨이 군"이 그 목표다 — 각자 0,1,2… 로 세므로 **gateway1 의 reqId 5 와 gateway2 의 reqId 5 가 같은 값**이 된다. 이건 버그가 아니라 producer-local id 의 *정의상* 그렇다.

문제는 이 id 를 *전역 공간*(가방의 단일 seenReqs 집합)에 넣을 때 터진다. 가방이 "reqId 5 는 이미 처리했다"고 기억하면, gateway2 가 보낸 *전혀 다른* reqId 5 를 중복으로 오인해 폐기한다 — 둘째 게이트웨이의 요청이 통째로 사라진다. 단조 dedup 카운터가 다중 producer 를 만나 무너지는 고전적 실패다.

## 2. 복합키 — 출처를 키에 접붙이기

해법은 단순하고 보편적이다: **지역 id 를 전역 유일하게 만들려면 출처를 접붙인다.** seenReqs 의 키를 `reqId` 가 아니라 `(producer, reqId)` 복합키로 바꾼다. 그러면 `(gateway1, 5)` 와 `(gateway2, 5)` 는 별개 키 — 충돌이 사라진다. 이는 0044 가 결과 워터마크를 *소비자별*로 키잉한 것의 정확한 거울이다(거기선 소비자, 여기선 producer). "단일 참여자 가정"을 "참여자별 네임스페이스"로 일반화하는 같은 패턴이 요청 경로(producer)와 결과 경로(consumer) 양쪽에 적용된다.

## 3. 은닉이 네임스페이스의 *근거*다

왜 producer 를 *메시지에 실어야* 하나? 가방은 버스 너머의 발신 게이트웨이를 **모르기 때문**이다. 클라는 게이트웨이 하나만 알고(단일 연결), 서버끼리는 버스로만 통신한다(은닉·척추 ④) — 가방이 "이건 gateway2 가 보냈군" 하고 직접 알면 그건 결합 위반이다. 그래서 출처 정보는 *결합*이 아니라 *데이터*로 흘러야 한다: 요청에 producer 태그를 실어 보내면, 가방은 게이트웨이를 *아는 것*이 아니라 메시지가 *말해준 것*으로 네임스페이스를 가른다. 은닉(서버가 서로를 모름)이 오히려 "출처는 명시 신호여야 한다"는 설계를 강제하고, 그 신호가 곧 네임스페이스가 된다. 이것이 이 step 의 둘째 게이트웨이를 *버스 seam 주입*으로 대표할 수 있는 이유이기도 하다 — 가방은 실제 게이트웨이와 주입된 pub 을 구별할 수 없으니, seam 의 메시지가 곧 producer 의 전부다.

## 한 줄 요약

producer-local id(게이트웨이 reqId)는 다중 발신자에서 겹친다 — 단일 네임스페이스 dedup 이 둘째 게이트웨이 요청을 중복으로 오인해 폐기한다. dedup 키를 (producer, reqId) 복합키로 바꿔 출처를 접붙이면 충돌이 사라지고(0044 소비자 측 다중화의 producer 측 거울), 그 출처는 은닉 때문에 *메시지에 실린 데이터*로 흘러야 한다.
