# step-0128 — saga 회계 정합 불변 (sagaConsistent · 체제 무관 대수적 닫힘)

> 직전: [step-0127](step-0127.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0121~0127 이 saga 회계(`gives`·`ackedGives`·`pendingGives`·`giveOks`·`giveFails`)를 단계적으로 쌓았다. 이 step 은 그 회계가 **대수적으로 닫혀** 있는지를 *불변*으로 단언한다 — 두 항등식: ① `gives == ackedGives + pendingGives`(보낸 모든 give 는 *정확히* acked 또는 pending·새는 give 0) ② `ackedGives == giveOks + giveFails`(받은 모든 회신은 ok 또는 fail·분류 누락 0). 질문: 이 불변이 *정상·회신손실·재전송* 모든 체제에서 성립하는가(체제 무관 회계 정합). 채우는 계약: 거래소↔가방 saga 의 *창발 불변*(0120 2-서비스 보존의 회계 평면 판).

## 2. 메커니즘 — sagaConsistent 불변 accessor (미호출 → baseline 비트 동일)

- **accessor**: `sagaConsistent()` = `gives === ackedGives + pending.size && ackedGives === giveOks + giveFails`. 회계 상태의 *읽기*만 — 쓰기·발신 0.
- **체제 무관**: 정상(pending 0·oks==gives)·회신손실(pending==gives·acked 0)·재전송+dedup(pending 0·oks 회복) 어디서도 항등식이 깨지면 안 된다.
- **reg 0**: accessor 미호출이면 동작 무영향 → 0127 비트 동일. reg 시나리오엔 거래소 OFF.

| 회신손실 | 9 | 0 | 9 | 0 | 0 | 예 | 예 | 예 |

- **체제 무관 닫힘**: 두 항등식이 모든 체제·시드서 성립 → `sagaConsistent()==true`. 손실 체제서도 `gives==0+9`(새는 give 0)·재전송서도 `9==9+0`. 회계가 고장 주입 아래서도 새거나 중복되지 않는다.

## 9. 의외의 발견 / 정직한 한계

- **항등식이 *체제*를 구분하지 않는다**: 같은 두 항등식이 정상·손실·재전송 모두서 성립 — 체제는 항(pending vs acked, oks vs fails)의 *분포*만 바꾸고 *합*은 불변(gives). 이것이 "대수적 닫힘"의 뜻: 회계가 어떤 고장 경로에서도 보존량(gives)을 재분배할 뿐 생성·소멸하지 않는다.
- **한계 — 종점(end-state) 단언**: 항등식을 run 종료 시점에만 확인한다. tick 별 성립(매 순간 닫힘)은 per-tick 훅이 필요 — gives/acked 는 단조 증가라 종점 성립이 강한 증거이나 엄밀한 *상시* 불변은 후속.
- **한계 — sagaConsistent 는 회계만**: 이 불변은 거래소 *내부 회계*의 닫힘이다. 가방 원장과의 *물리적* 정합(open==escrow)은 0120/0122 가 별도로 단언 — 회계 닫힘 + 물리 정합이 함께 2-서비스 안전을 이룬다.
