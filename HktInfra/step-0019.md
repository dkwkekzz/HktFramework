# step-0019 — 발신하는 둘째 소비자 (RankingService — 버스 consume→publish 루프·이벤트 기반 읽기 모델)

> 직전: [step-0018](step-0018.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0016 의 AuditService 는 *관찰 전용*(발신 0)이었다 — 버스 이벤트를 *소비*만 했지 *발행*은 안 했다. 그래서 "이벤트를 소비해 *다시 발행*하는" **consume→publish 루프**(랭킹·거래소·업적처럼 게임 이벤트에 반응해 파생 이벤트를 내는 서비스)는 미검증이었다(0016 §9-4). 이 step 은 `RankingService` — svc.item.out(가방 결과 스트림)을 소비해 아바타별 보유 수(rank)를 투영하고 svc.rank.out 으로 발행하는 **이벤트 기반 읽기 모델**(CQRS read model) — 을 세워 그 루프를 검증한다.

**닫는 조건**: ① ranking OFF → 0018 비트 동일(회귀 0) ② consume→publish 루프 작동 ③ rank 프로젝션 == 원장 byOwner *정확 일치*(읽기 모델 ≡ 쓰기 모델) ④ 발행자(inventory) 무수정(decouple) ⑤ 루프 없음(발행 유계)·클라 rankDesync 0.

## 2. 메커니즘 — RankingService (ranking OFF → 0018 비트 동일 = 회귀 0)

한 조각 = **발신하는 둘째 소비자**. 더한 박스는 `RankingService` 하나(`engine/` 무수정).

1. **RankingService** (게임 서비스, onTick 0): svc.item.out 의 item_result 를 소비 — pickup ok → 요청자 +1, give ok → from −1·to +1(실패 op 는 p.ok 게이트로 무변경). 변경된 아바타마다 `svc.rank.out {avatar, count}` 를 *발행*(consume→publish). `ranks` = 아바타→보유 수 투영(원장에 대한 *권위 없음* — item_result 스트림에서 재계산하는 파생 뷰).
2. **버스 구독 추가**(decouple): `['svc.item.out','ranking']`(둘째 소비자 — gateway 와 *함께* 같은 토픽 구독) + `['svc.rank.out','gateway']`(클라 중계) + `['svc.rank.out','audit']`(관찰). 발행자(inventory) spec·코드·발신 *무수정*.
3. **gateway 중계**: svc.rank.out ev → 그 아바타 클라에 `rank_update {count}`. 클라 `rankBelief` 가 원장 진실(byOwner 크기)로 수렴.
4. **루프 없음**: svc.rank.out 은 *어떤 item 서비스도 안 먹는다* → consume→publish 가 다시 item 이벤트를 안 낳음(발행 유계).

월드·영속(0017)·압축(0018)·채팅(0015)·제어 평면 *무변경*. inject seam 그대로.

## 9. 의외의 발견 / 정직한 한계

- **발견 — 읽기 모델은 권위 보존을 자연히 만족**: ranking 은 원장에 *쓰지 않는다*(파생 투영) → "권위 단일 소유"가 *구조적으로* 성립(읽기 모델은 권위를 *복제*하지 않고 *재계산*). 같은 이벤트 스트림이라 byOwner 와 자동 일치 — 권위 충돌의 여지가 없는 게 CQRS read model 의 본질.
- **발견 — 발행 > 소비는 정상(쌍 이동)**: give 한 건이 from −1·to +1 *두* 아바타를 바꾸므로 발행이 소비보다 많다(69 vs 60). 이는 루프가 아니라 *한 이벤트의 다중 효과* — `bounded` 체크를 published ≤ consumed×2 로 둬 진짜 발산(루프)과 구별.
- **한계 — rank belief 는 최신값만(이력 없음)**: 클라는 rank_update 의 *최신 count* 만 보관(중간값·랭킹 순위표 미전달). 전역 리더보드(top-N)·순위 변동 알림은 미착수(이번은 *자기 보유 수* 투영뿐).
- **한계 — 루프 방지는 토폴로지 규약**: svc.rank.out 을 item 서비스가 안 먹는 건 *구독 테이블 설계*로 보장될 뿐, 런타임 사이클 탐지(누가 무엇을 먹는지의 그래프 검사)는 없다. 소비→발행 그래프가 커지면 사이클 정적 검증이 후속.
- **한계 — 읽기 모델 영속 0**: ranking 의 rank 테이블은 RAM(영속 0) — ranking 크래시 시 재구성하려면 이벤트 재생(persist 의 item 저널 replay)이나 자체 영속이 필요(미착수). 읽기 모델은 원장에서 *언제든 재계산 가능*이라 영속이 덜 급하지만, late-join/크래시 복구는 후속.
