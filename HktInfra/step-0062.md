# step-0062 — 대체 소비자 late-join reconstruct: 활성화 후 저널 replay 로 다운타임 갭 복원 (spawnReconstruct)

> 직전: [step-0061](step-0061.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0061 의 대체 소비자(ranking2)는 *활성화 이후* 결과만 인계했다 — 원 ranking 사망(t14)~활성화(t37) 사이 처리된 효과를 놓쳐 투영이 원장에 뒤처졌다(0061 §9 의 정직한 한계). 이 step 은 그 갭을 메운다: 활성화된 ranking2 가 *쓰기 모델의 영속 저널*(PersistStore)을 `reconstruct`(ranks 리셋 후 전수 재계산)해 다운타임 이력까지 복원 → 투영==원장. 이는 0020 의 읽기 모델 late-join(랭킹 crash→쓰기 저널 reconstruct)을 *대체 소비자*에 적용한 것 — CQRS 의 핵심(읽기 모델은 자기 영속 0·휘발 스트림이 아니라 내구 저널이 복구원). 닫는 조건: ⒜ `spawnReconstruct=0` 이면 0061 비트 동일(reconstruct 0·reg 0) ⒝ ON 이면 ranking2 활성화 + 투영==원장(갭 복원) ⒞ 대조(0061·reconstruct 없음)는 활성화돼도 투영!=원장(다운타임 갭) ⒟ 비-침습(원장 minted 불변).

## 2. 메커니즘 — 활성화된 대체 소비자의 저널 reconstruct (spawnReconstruct OFF → baseline 비트 동일 = 회귀 0)

run 드라이버에 reconstruct 트리거를 더한다(0020 rankRestart 와 같은 제어 평면 위치). `spawnReconstruct && ranking2.activated && persist` 이고 늦은 quiescent tick(`reconstructAt`)이면 `ranking2.reconstruct(persist.journal, persist.snapshot)` 호출 — 이미 존재하는(0020) `RankingService.reconstruct` 가 `this.ranks` 를 *리셋-재구성*(mint→owner +1·xfer→from -1/to +1)하므로 라이브 인계분(0061)과 *이중 계산 0*이며, quiescent(활동 정지 후)라 이후 라이브 효과가 없어 저널이 완전 = 투영 완전.

핵심: 대체 소비자도 *자기 영속 0* — 활성화로 *역할*은 인계하되(0061·스트림 재개), 다운타임 *이력*은 쓰기 저널 replay 로 메운다. `spawnReconstruct=0`·미활성·persist 부재면 트리거 휴면 → NET 비트 동일. 닿는 박스: `topology.js`(reconstruct 트리거 — 드라이버). svc-ranking.js 무수정(reconstruct·activated 는 0020/0061 산물 재사용). 순수 제어 평면(존 tick 밖·원장 권위 불변).

## 9. 의외의 발견 / 정직한 한계

- **"역할 인계"와 "이력 복원"은 서로 다른 책임 — 둘을 합쳐야 완전한 대체**: 0061 은 *역할*(스트림 재개)을, 0062 는 *이력*(다운타임 갭)을 인계한다. 대체 소비자가 완전하려면 둘 다 필요하다 — 활성화만으로는 "지금부터" 만 보고, reconstruct 만으로는 "그 순간의 스냅샷" 만 본다. 활성화(라이브 재개)+reconstruct(과거 복원)의 결합이 끊김 없는 인계다. 이는 CQRS 읽기 모델의 일반 원리(라이브 구독 + 저널 catch-up)와 정확히 동형.
- **reconstruct 의 리셋-재구성이 이중 계산을 구조적으로 막는다**: ranking2 는 활성화 후 라이브 효과를 _bump 으로 누적하고 있다. 그 위에 reconstruct 가 *덧셈*이면 이중 계산이지만, `reconstruct` 는 `this.ranks=new Map()` 으로 *리셋 후 저널 전수 재계산* — 라이브 누적분을 *대체*한다. 그래서 활성화 시점·reconstruct 시점이 겹쳐도(라이브+저널 중복) 최종 투영은 저널 SSOT 한 벌. 이 멱등성이 0020 reconstruct 를 대체 소비자에 *무수정 재사용* 가능하게 했다.
- **저널이 ranking 죽음과 독립이라 갭이 *보존*된다(데이터 계층의 값어치)**: 다운타임 동안 버스가 흘려보낸 svc.item.out 은 ranking2 가 *놓쳤지만*, 그 효과는 가방이 PersistStore 에 영속했으므로 저널엔 *남아있다*. "세계가 세션보다 오래 산다"(계층 6)가 곧 "소비자가 죽어도 그 입력 이력은 복구 가능"을 함의 — 데이터 계층이 서비스 계층 복원의 토대.
- **harness-driven reconstruct(정직한 한계)**: reconstruct 호출은 드라이버(제어 평면·0020 선례)가 quiescent tick 에 한다 — ranking2 가 *자율적으로* 저널을 가져오지 않는다. 자율 대체(활성화 즉시 persist 에 버스 요청→저널 응답→catch-up)는 persist 를 버스 참여자로 만드는 추가 프로토콜(후속). 이 step 은 *복원 가능성*까지, 자율 fetch 는 다음.
