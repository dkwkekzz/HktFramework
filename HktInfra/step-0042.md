# step-0042 — 가방 seenReqs dedup 집합 *유계화* (게이트웨이 prune 워터마크·busSeenBound)

> 직전: [step-0041](step-0041.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0040·0041 은 게이트웨이 inBuffer·가방 outBuffer 를 소비자 ack 워터마크로 유계화했다. 그러나 가방의 *요청 dedup 집합* `seenReqs`(0037 — 재발행 이중 mint 방어)는 여전히 처리한 *전* reqId 를 무계로 쌓는다 → 장기 가동 시 무한 성장(0040/0041 §9). 핵심 관찰: **게이트웨이가 재발행하는 건 inBuffer(미-ack = reqId>inAcked)뿐**이므로 `reqId ≤ inAcked` 는 영영 재출현하지 않는다 → 가방은 그 이하 dedup 상태를 잊어도 안전. 이 step 은 게이트웨이가 `inAcked`(prune 프런티어)를 `svc.item.seen` 으로 통보 → 가방이 그 이하 `seenReqs` 를 가지친다. **busAck(0040)의 역방향 워터마크** — ack 핸드셰이크의 대칭 완성. SPINE §6 계층 4(버스)·계층 3(가방) — failover 무손실 기계의 메모리 유계화.

닫는 조건: ⒜ `busSeenBound=0` 이면 0041 비트 동일(reg) ⒝ dedup 정확성 보존(minted==base·dupe 0)·seenReqs 유계(run-length 무관)·failover 에도 dupe 0.

## 2. 메커니즘 — 역방향 워터마크 가지치기 (busSeenBound OFF → 0041 비트 동일 = 회귀 0)

- **게이트웨이(producer)**: `_onItemAck` 에서 `inAcked` 가 전진하면(`> before`) `svc.item.seen{upTo: inAcked}` 발행. inAcked 이하는 이미 inBuffer 에서 가지쳐져 *재발행 후보 아님*.
- **가방(consumer)**: `_onSeenWatermark(ev)` 가 `upTo > seenWatermark` 일 때 워터마크를 전진시키고 `seenReqs` 에서 `reqId ≤ upTo` 를 순회 제거(Set 이라 순서 없음 → O(가지친 수)).
- **안전성(dupe 0)**: reqId 는 게이트웨이 단조 카운터 + 각 reqId 는 1회만 발신(재발행만 중복·재발행 범위는 항상 >inAcked). 따라서 `reqId ≤ inAcked` 는 영영 재출현 0 → dedup 상태를 잊어도 이중 mint 0.
- **자기-크기조정**: 정상 구간 워터마크가 흘러 seenReqs 가 in-flight 만 남고(드레인), gap 구간(bus crash→ack 끊김) 워터마크 정지로 gap reqId 가 *보존* → 복구 재발행이 dedup 으로 폐기.
- **OFF 경로**: busSeenBound OFF 면 seen 미발행·토폴로지에 `svc.item.seen` 구독 미추가 → 0041 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **ack 핸드셰이크의 대칭 완성**: 0040 은 소비자→producer 의 *전진* ack(svc.item.ack — "처리했다")로 inBuffer 를 가지쳤다. 이 step 은 그 producer 가 *다시* 소비자(가방)에게 "이 이하는 내가 재발행 안 한다"(svc.item.seen)를 보내 seenReqs 를 가지친다. 즉 ack 가 한 바퀴 돌아 producer/consumer 양쪽의 무계 상태를 모두 묶는다 — 신뢰 전달의 메모리는 *합의된 워터마크* 아래로 떨어진다.
- **dedup 은 영원히 필요하지 않다**: 흔한 오해는 "exactly-once dedup 집합은 영구 보관해야 한다"는 것이다. 사실은 *재발행이 닿을 수 있는 창*만 기억하면 된다 — replay 소스(inBuffer)가 유계(0039~0040)이므로 dedup 집합도 유계일 수 있다. 재발행 범위(>inAcked)와 dedup 보관 범위(≤seenWatermark)가 정확히 상보적이라 둘을 같은 워터마크로 자른다.
- **정직한 한계**: ① 워터마크는 *게이트웨이 단일 producer* 기준 — 다중 게이트웨이가 같은 가방에 발신하면 producer 별 reqId 네임스페이스가 겹쳐 per-producer 워터마크가 필요(현재 단일 게이트웨이라 충분). ② failover 시 seenReqs peak 가 gap 만큼 커진다(60→54) — gap 동안 워터마크가 정지해 gap reqId 를 보존하기 때문(dupe 0 의 대가). 이는 0040/0041 의 "ack 도 gap 에 끊긴다"와 동일 트레이드오프 — 유계지만 *완벽 튜닝된 고정 창*보다 클 수 있다.
