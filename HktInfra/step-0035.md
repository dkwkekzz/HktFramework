# step-0035 — 정리 step: `cluster.js` 박스-부품 4분할 (45KB>30KB 트리거·기능 0·reg 0)

> 직전: [step-0034](step-0034.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

`cluster.js`(broker 멀티프로세스 드라이버)가 45,293 바이트로 **박스 파일 30KB 비대화 트리거**(0030 수립·CLAUDE.md "분할 임계")를 넘었다. 다음 기능 step 전에 *정리 step*을 끼워 복사 전진 페이로드를 유계로 묶는다: **기능 추가 0·바이트 동일(verbatim 이동)·export 집합 불변 → reg 0**. 0030(net-core.js 박스 분할)의 *cluster 판*. 어느 SPINE 박스도 채우지 않는다 — 빌드 인프라(복사 전진 페이로드)의 위생 작업이다.

닫는 조건: ⒜ `cluster.js` 의 모든 함수/클래스가 부품 파일로 이동하되 *바이트 동일* ⒝ `require('./cluster.js').runMulti` 진입점 무변경 ⒞ 모든 박스-부품 < 30KB ⒟ 18+busfail 모드 ALL OK·멀티프로세스 E2E 비트 동일·spine 35-step 사슬.

## 2. 메커니즘 — `cluster.js` → 5파일(진입점 1 + 부품 4)

`net-core.js` 가 박스 부품을 묶는 진입점이듯, **`cluster.js` 를 진입점으로 남기고** 내부를 부품 파일로 분리한다. 각 함수/클래스는 *원본 바이트 그대로* 옮기고(verbatim), 파일 경계에 `require`/`module.exports` 배선만 추가한다.

| 파일 | 담는 것 | 원본 위치 | 크기 |
|---|---|---|---|
| `cluster-wire.js` | `frameOf` · `Framer` (길이-프리픽스 프레이밍) | 0034 cluster.js L45–64 | 1.2KB |
| `cluster-core.js` | `Cluster` 클래스 (broker 버스 허브·토픽 pub/sub·진짜 kill 생애주기·재-provisioning) | L66–295 | 19.7KB |
| `cluster-reconstruct.js` | `reconstruct` (스냅샷 → run() 형태 r 재구성·dead 표기) | L547–653 | 7.4KB |
| `cluster-run.js` | `computePlacement` · `runMulti` (멀티프로세스 lockstep 드라이버) | L297–545 | 17.9KB |
| `cluster.js` (진입점) | 위 넷을 `require` 해 `{ runMulti, Cluster, computePlacement, frameOf, Framer }` 재노출 | — | 1.3KB |

배선 의존(런타임 require 그래프):
- `cluster-core.js` → `cluster-wire.js`(frameOf·Framer) + engine(fnv1a) + node(net·child_process·path)
- `cluster-run.js` → `cluster-core.js`(Cluster) + `cluster-reconstruct.js`(reconstruct); `Net` 은 호출자 deps 인자(무변경)
- `cluster-reconstruct.js` → 외부 런타임 의존 0(전부 인자)
- `cluster.js`(진입점) → 위 넷

**왜 reg 0 인가**: ⒜ 이동한 코드가 바이트 동일(공백·주석·순서 보존) ⒝ `module.exports` 집합이 0034 와 동일(`{ runMulti, Cluster, computePlacement, frameOf, Framer }`) ⒞ `cluster.js` 는 `net-core.js` 의 dual-mode 번들에 포함되지 않는 **Node 전용** 파일 — 브라우저 경로 무영향 ⒟ 유일 소비자 `topology.js` 는 여전히 `require('./cluster.js').runMulti` — 진입점 무변경. cluster.js 는 인프로세스 `reg` 모드가 닿지 않으므로(net-core 가 cluster 를 require 하지 않음), 분할 투명성은 **멀티프로세스 E2E 비트 동일**(e2e·summary·inject·recover-* 모드)과 **spine 사슬**이 증명한다.

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

- **reg(인프로세스)**: 0027/0028 기준 비트 동일 25/25 — 분할은 net-core 무관(휴면 경로 무변경).
- **e2e(멀티프로세스 = 인프로세스 비트 동일)**: log+world+inv+chat+bus+audit+persist+rank+chatpersist 전부 *비트 동일 true*(전 시드) — `runMulti`(분할된 cluster) 가 인프로세스 `run()` 과 동일 다이제스트.
- **repro**: 같은 시드 멀티프로세스 2회 동일·인프로세스 동일·world 동일(결정론) — inv 다이제스트 0x7a122947 / 0x9a31a1e5 / 0xbccd9849 / 0x99774ef5 / 0x4bc176e1.
- **busfail(0034 가설 잔존)**: bus crash→재구독 복구 여전 통과(분할 후에도 0034 failover 의미 보존).
- **sacred·hide·compact·chat-compact·recover-***: 전부 OK(분할 비-침습).
- **크기 예산**: cluster.js 45,293B(단일) → 진입점 1.3KB + 부품 4(최대 cluster-core 19.7KB) · 최대 박스-부품 19.7KB < 30KB · step 디렉토리 272KB < 300KB.

## 9. 의외의 발견 / 정직한 한계

- **5파일 합계(48.0KB) > 원본(45.3KB)**: 분할은 파일당 헤더 주석·require·export 보일러플레이트를 더하므로 *총 바이트는 소폭 증가*한다. 정리 step 의 목적은 총량 최소화가 아니라 **단일 박스 파일을 30KB 아래로 유계화**(복사 전진 1회 비용·self-review diff 가독·미래 분산 토폴로지와 파일=박스 정합)이다 — 그 목적은 달성(최대 19.7KB).
- **topology.js 29.7KB — 다음 트리거 후보**: 30KB 에 근접. 이번 트리거(>30KB)엔 미달이라 건드리지 않았다. 다음 기능 step 이 topology 를 키우면 30KB 를 넘을 수 있어, 그때 *존/서비스 배선* 분리 정리 step 을 끼운다(후속·STATE §2).
- **cluster-* 부품은 Node 전용·dual-mode 불요**: `cluster.js` 가 애초 `require('net')` 인 Node 한정 파일이라(브라우저 testbed 는 인프로세스 `run()` 만 씀), 부품도 `module.exports` 단방향이면 충분 — net-core.js 의 `globalThis` 이중 노출 패턴이 불필요(분할 단순화).
