## 1. 왜 채팅을 *분리*하는가 — 게임 서비스 둘째 박스

핵심 신념(SPINE): **한 프로세스가 모든 일을 하면 모든 일이 서로의 병목이다.** 채팅의 대규모 브로드캐스트(수천 명이 보는 전체 채널)가 존 시뮬 tick *안*에서 돌면, 채팅 트래픽이 시뮬 헤드룸을 잡아먹는다. 분리 판정 기준은 하나다 — *그 일이 존 시뮬 tick 과 같은 박자로 돌아야 하는가?* 채팅 팬아웃은 아니다. 그래서 존 밖 비동기 서비스로 뺀다.

step-0014 가 *가방*(첫 게임 서비스 박스)으로 이 분리를 처음 실증했다. 하지만 박스가 *하나*뿐이면 "분리가 일반 패턴인가, 가방에만 맞는 우연인가?"가 미검증이다. 이 step 은 *둘째 박스*(채팅)를 같은 패턴으로 세워 — 별 프로세스·tick 무관·E2E 비트 동일·은닉 — 분리가 **일반 패턴**임을 보인다. 그리고 가방과 *대비되는* 서비스 의미(팬아웃)를 골라, 패턴이 *다른 모양의 책임*에도 적용됨을 보인다.

## 2. 팬아웃(멀티캐스트) — 가방의 *원장* 과 무엇이 다른가

- **가방(0014) = 원장(단일 소유).** `Map<itemId, owner>` — 아이템 하나에 소유자 하나. 핵심 연산은 *이동*(release+acquire 쌍 거래). 불변은 "매 시점 소유자=1".
- **채팅(0015) = 구독 라우팅(팬아웃).** `Map<channel, Set<avatar>>` — 채널 하나에 구독자 *여럿*. 핵심 연산은 *팬아웃*(한 발화 → 구독자 전원에 복제). 불변은 "비-구독자 도달=0".

둘은 *반대 모양*이다(하나↔여럿). 그런데도 **같은 설계 원리**를 따른다: *자료구조가 핵심 불변을 공짜로 보장하고, 증명할 것은 정합/완전성이다.*

- 가방: 원장 `Map` 이 소유자=1 을 *구조적*으로 보장 → 증명할 건 *byOwner 정합*(비-원자 이동 검출).
- 채팅: 팬아웃이 구독 `Set` *만* 순회 → 비-구독자 도달=0 이 *구조적* → 증명할 건 *완전성*(deliveries ≡ 클라 belief)·*지역 격리*.

"누설을 막는 게 별도 필터가 아니라 *순회 대상이 곧 구독자 집합*" 이라는 점이 핵심이다 — 가방이 "소유자 카운트가 아니라 Map 의 함수성" 이었던 것과 같다.

## 3. 채널 셋 — global · region · whisper

- **global(전체)** — 모든 가입 아바타가 구독. 한 발화가 전원(발신자 제외)에게.
- **region:X(지역)** — 같은 region 멤버만 구독. region 은 *클라 속성*(client i → region i%2)으로 선언 — 존 공간 상태를 읽지 *않는다*(읽으면 은닉·신성한 tick 위반). 그래서 여기선 "지역 채팅" 이 *명시적 룸*(길드·지역 ID)에 가깝다. region:0 발화는 region:0 멤버에게만 → **지역 격리**.
- **whisper(귓속말)** — 구독 *무관*. byAvatar[to] 로 타깃 게이트웨이를 조회해 *타깃 1명에게만* 직접 라우팅(point-to-point). 제3자 0 = **프라이버시**.

## 4. best-effort vs idempotent transfer — 전송 열화가 가른 차이

채팅 홉(gateway↔chat)을 redundancy 3·loss 0.2 로 열화했을 때 두 성질이 갈렸다:

- **라우팅 정확성**(누설 0·지역 격리) — **loss 와 무관하게 보존**. 어디로 갈지는 구독 테이블이 정하지, 손실이 정하지 않는다.
- **전달 완전성**(모든 발화가 모든 구독자에) — best-effort 로 *graceful 열화*. 채팅은 per-message ack/resend 가 없어 손실은 *복원 안 됨*.

이것이 가방과의 *대비*다. 가방의 idempotent transfer 는 *완전성까지* 보존했다(아이템은 소멸 없는 이동만 — 재-give 거부로 멱등). 채팅은 fire-and-forget 이라 *정확성만* loss-독립이다. 두 서비스가 *같은 분리 패턴*이되 *신뢰성 모델*은 다르다(트랜잭션 vs best-effort). 상용 채팅이 신뢰 전달을 원하면 채널 시퀀스·ack 를 얹어야 한다(0008 복원 패턴의 채팅 판 — 후속).

## 5. belief Set — 멱등의 위치가 옮겨갔다

클라는 채팅을 *서버 chat_msg 로만* 갱신하고 belief 를 `Set<channel|from|seq>` 로 둔다. 재전송으로 같은 메시지가 두 번 와도 *키 충돌로 멱등 흡수*(effectively-once). 서버가 안 보낸 걸 믿는 일은 구조적으로 없다(phantom 0).

가방에선 멱등이 *서버* 측(원장의 재-give 거부)에 있었고, 채팅에선 *클라* 측(belief Set 키 충돌)에 있다. **멱등의 위치가 트랜잭션(서버)에서 수신(클라)으로 옮겨갔지만, 둘 다 자료구조의 키 충돌로 멱등을 얻는다** — redundancy 3 에서도 phantom 0 인 비결.

## 6. 신성한 tick — 둘째 실증

채팅도 가방처럼 **onTick 이 없다**. 오직 chat_req 에만 반응하는 *순수 반응형 서비스*다. 검증의 세 줄:

1. **chat onTick 0** — 채팅이 tick 박자와 무관.
2. **존 net.log·상태 비트 동일**(채팅 on/off) — worldDigest(on)==worldDigest(off).
3. **존 도달 chat 0** — 채팅은 존을 우회.

여기에 *별도 chatRng*(seed^0xC4A7, move/item rng 와 독립)가 결정적이다 — 클라 채팅 행동이 월드 move 스트림을 건드리지 않아야 worldDigest 가 on/off 에 비트 동일하다(0014 가 itemRng 분리로 배운 교훈의 반복). "비-침습 = 결정론 스트림 격리".

## 7. 이 step 이 검증한 것 (요약)

- **회귀 0**(`reg`) — 채팅 OFF = 0014 비트 동일(20/20).
- **E2E 동치**(`e2e`) — 멀티프로세스 = 인프로세스 비트 동일(log+world+chat)·누설 0·phantom 0·chatDesync 0.
- **신성한 tick**(`sacred`) — 월드 on=off·says 55~64·fanout 211~229·존 도달 chat 0·chat onTick 0.
- **팬아웃 라우팅**(`fanout`) — 누설 0·phantom 0·완전성 수렴·whisper 프라이버시·열화에도 누설 0·지역 격리 보존.
- **분리·은닉·재현**(`isolate`·`hide`·`repro`) — chat 자기 pid·누설 0·시드별 deliveries 재현.
