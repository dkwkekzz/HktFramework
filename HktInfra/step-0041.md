# step-0041 — 버스 failover *결과 경로* replay 버퍼 자기-크기조정 (ack 가지치기·busOutAck)

> 직전: [step-0040](step-0040.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0040 은 *요청* 버퍼(게이트웨이 inBuffer)를 ack-가지치기로 자기-크기조정해, 0039 고정 K(busWindow)가 요구하던 *최대 예상 gap 사전 추정*을 없앴다. 그러나 *결과* 버퍼(가방 outBuffer·0036)는 여전히 고정 busWindow(0039) 였다 — 작으면 결과 손실(클라 belief<원장 = itemDesync)·크면 메모리 낭비(0040 §9). 이 step 은 그 §9 를 *결과 경로*에서 0040 과 같은 원리로 푼다: **결과의 소비자(게이트웨이)가 중계한 outSeq 를 `svc.item.out.ack` 로 통보 → 가방이 ack 워터마크 이하 outBuffer 를 가지친다.** 버퍼엔 *미-ack(클라 미반영 가능)* 결과만 남는다(자기-크기조정). SPINE §6 계층 4(버스) — `svc.item.out` 결과 경로의 유계 replay 를 K 추정 없이 완성한다.

닫는 조건: ⒜ `busOutAck=0` 이면 0040 비트 동일(reg) ⒝ ack 무손실(desync 0·K 추정 0)·미-튜닝 고정 K 는 결과 손실→desync(대조)·idle drain·가동-길이 무관·원장 보존.

## 2. 메커니즘 — 결과 ack-가지치기 (busOutAck OFF → 0040 비트 동일 = 회귀 0)

- **가방(producer)**: `_out(msg)` 에서 busOutAck ON 이면 `msg.outSeq = this.outSeq++`(단조 순번 부여) 후 outBuffer push. `_onOutAck(ev)` 가 `svc.item.out.ack` 수신 시 `outAcked` 워터마크를 단조 전진시키고 `outBuffer[0].outSeq ≤ outAcked` 동안 front 를 shift(O(가지친 수)). outBuffer 는 outSeq 순서라 front 가 최소 — 미-ack 만 남는다.
- **게이트웨이(consumer)**: `svc.item.out` 결과를 클라에 중계(`_relayItemResult`/`_relayItemRecon`)한 *직후* `_ackOut(ev)` 로 그 `outSeq` 를 `svc.item.out.ack` 에 실어 버스 발행. 결과는 belief Set 갱신이라 *멱등*(0036 발견) → ack 는 dedup 이 아니라 *가지치기 신호*일 뿐(consumer dedup 불요).
- **자기-크기조정**: 정상 구간엔 ack 가 흘러 outBuffer 가 0 으로 drain(idle drain). gap 구간(bus crash→재구독)엔 게이트웨이가 끊겨 ack 도 멈춰 outBuffer 가 gap 만큼 *자동 성장* → 재협상 직후 `resendOut` 이 정확히 그만큼 재발행해 뒤처진 클라가 따라잡는다(desync 0). **K 사전 추정 0.**
- **OFF 경로**: busOutAck OFF 면 outSeq 미부여·ack 미발행·토폴로지에 `svc.item.out.ack` 구독 미추가 → 0040 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **0040 의 정확한 거울**: 요청 경로(inBuffer·게이트웨이 producer·가방 consumer)와 결과 경로(outBuffer·가방 producer·게이트웨이 consumer)는 producer/consumer 가 뒤바뀐 대칭 구조다. 같은 ack-워터마크-가지치기 원리가 양 방향에 그대로 적용된다 — `_onItemAck`↔`_onOutAck`, `svc.item.ack`↔`svc.item.out.ack`.
- **결과 손실은 minted 가 아니라 desync 로 나타난다**: 요청 손실은 mint 미발생(ledger·belief 둘 다 미반영 → 정합) — desync 0. 결과 손실은 mint 됐으나 클라 belief 가 뒤처짐 → desync>0. 그래서 결과 경로의 무손실 지표는 itemDesync 다(요청 경로의 minted 와 대조). 0040 fixed 의 "desync 4" 가 바로 이 결과 경로 손실이었다(busWindow 가 양 버퍼를 함께 묶었기 때문) — 이 step 이 그 절반을 ack 로 분리·해소.
- **정직한 한계**: ① ack 는 *게이트웨이*(클라 접점 소비자) 중계에 키잉된다 — `svc.item.out` 의 둘째 소비자(ranking)가 게이트웨이보다 뒤처지면 outBuffer 를 너무 일찍 가지칠 위험이 있다. 현 토폴로지는 두 소비자가 lockstep 으로 배달/재구독되어 충분하다(rankDesync 0 확인). 일반 N-소비자에선 *min-워터마크*(모든 구독자 ack 의 최소)가 필요 — 후속. ② `seenReqs`(가방 요청 dedup 집합)는 여전히 무계 — ack 워터마크 기반 유계화 후속. ③ ack 도 gap 에 끊겨 peak 는 in-flight 백로그까지 잡으므로 *완벽 튜닝된* 고정 K(=gap)보다 클 수 있다 — 무튜닝·idle drain·가동-길이 무관이 그 대가(0040 과 동일 트레이드오프).
