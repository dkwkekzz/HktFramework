# step-0082 — 전달 실패 발행(failedPublish·svc.whisper.failed)

> 직전: [step-0081](step-0081.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0079 의 포기 통지(deliverNotify)는 영구 전달실패를 *원 발신자*에게만 deliveryFailed 로 회신한다 — 운영/감사 평면(audit·모니터)은 전달 실패를 못 본다(0079 §9). 전달 실패를 *관측 가능*하게 만들되, 발신자 통지와 직교하게(두 소비자 분리), 발행자(라우터) 무수정 소비자로 할 수 있는가? SPINE 계층3(채팅/소셜) 실패 스트림을 버스 토픽으로 노출한다.

## 2. 메커니즘 — 포기를 토픽으로 발행 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-whisper.js`): WhisperRouter 의 `onTick` 포기 분기(상한 도달 → undeliverable)에서, 발신자 통지(deliveryFailed·0079) *이후* `failedPublish && bus` 면 `{type:'pub', topic:'svc.whisper.failed', ev:{to, from, body}}` 를 bus 로 발행(`failedPublished++`). 0060 presencePublish(프레즌스 판정을 svc.presence 로 발행)의 *전달 실패* 판.

**두 평면 분리**: point-to-point 통지(deliveryFailed → 원 발신자·행동용)와 토픽 발행(svc.whisper.failed → audit·관측/감사용)이 *직교* — 한 사건(포기)이 두 다른 소비자에게 다른 목적으로 간다. 라우터는 bus 주소만 알고 구독자는 모른다(은닉).

**발행자 무수정 소비자**: audit 는 spec·코드 무변경, 버스 구독 테이블에 `['svc.whisper.failed', 'audit']` 행 하나만 추가돼 실패 스트림을 본다(0016 decouple 가설의 연속). `failedPublish` OFF 면 발행 0·구독 행 미추가 = 0081 비트 동일.

## 4. 척추 체크 5항

① **신성한 tick** — WhisperRouter 의 onTick 은 라우터 제어 평면(벽시계 timeout), 존 시뮬 tick 밖. ② **결정론 코어** — 세계 쓰기 경로 무변경(minted ON==OFF). ③ **권위 단일 소유** — 발행 권위 0(원장·세션 무관). ④ **은닉·단일 연결** — 라우터는 bus 주소만 알고 구독자(audit) 무지, audit 는 토픽만 구독. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 한 사건(포기)을 *두 소비자*(발신자·audit)에게 *다른 채널*(point-to-point·pub/sub)로 보내는 것이 자연스럽게 갈린다 — 행동용 신호는 직접 회신, 관측용 신호는 토픽 발행. 이는 SPINE 의 "서버간은 버스, 클라엔 직접"의 작은 사례다.
- **한계**: 발행은 *포기 시점*만 — 재시도 진행 중(아직 포기 전)이나 *성공* 전달은 토픽에 안 실린다. 전달 수명주기 전체(시도·재시도·성공·포기)를 관측하려면 svc.whisper.lifecycle 류의 더 풍부한 토픽이 필요(후속). 또한 audit 는 *집계*(seen count)만 — 실패 사유별 분류·알림 라우팅은 모니터 박스(presmon 류)의 일.
