# step-0012 — Concepts: Pub/Sub Bus Distribution, Network Partition as Realized Death, and Reconnect Fencing

> 이 문서는 [step-0012.md](step-0012.md)(시리즈 정식 기록·압축적)에 깔린 **핵심 개념들을 풀어 설명**한다.
> 코드 변경 자체보다 "이 step 이 다루는 개념이 무엇이고, 왜 그게 인프라에서 중요한가"에 초점을 둔다.

---

## 0. 이 step 이 다루는 개념 한눈에

| 개념 | 한 줄 정의 | 이 step 에서의 위치 |
|---|---|---|
| **pub/sub 버스** | 발행자가 *수신자를 모르고* 토픽으로 발행, 구독자가 토픽을 듣는 통신 | broker 직접 소켓 주소지정 → `cmd.<host>` 토픽 |
| **주소 무지(無知)** | 발행자가 누가 듣는지 모른다 = N×N 직접 결합 제거의 본질 | tap 소비자를 더해도 발행자 무수정 |
| **네트워크 분단** (partition) | 링크가 끊겨 한쪽이 *침묵*하는 것(프로세스는 살아 있을 수 있다) | 권위 존 링크를 t0 부터 게이팅 |
| **분단 = 사망의 현실화** | "왜 침묵하는가"와 무관히 *침묵의 관측*이 같으면 복구도 같다 | 링크 분단이 deathTick 과 비트 동일 |
| **재연결** (reconnect) | 분단됐던 링크가 복귀 — 프로세스가 *살아* 돌아온다 | 복귀 호스트가 fence 에 응답(생존 증거) |
| **split-brain** | 승격된 추종자 + 부활한 원권위 = *둘 다 권위*(소유자 2) | 재연결이 깨우는 위험 |
| **펜싱** (fencing) | 부활한 옛 권위를 막아 권위 단일 소유를 지키는 것 | fence 명령 = 액터 dead 못박음 |
| **멱등** (idempotency) | 같은 요청을 여러 번 받아도 *한 번만* 실행 | reqId 캐시 → resend 안전 |

이 step 의 본질은 **"broker 단일점을 *발행자가 수신자를 모르는* 토픽 버스로 풀고, 그 버스 링크에 실 네트워크 열화(드롭·분단·재연결)를 주입해도 권위가 단일 소유로 보존됨을 증명한다"** 는 한 문장이다. 특히 *링크 분단이 0009 의 추상 사망과 비트 동일*이고, *재연결은 펜싱이 필요한 새 위험*이라는 두 깨달음이 중심이다.

## 1. 출발점 — 0011 이 남긴 "단일 broker + 신뢰 소켓"

step-0011 은 서버 사이 통신선을 *실 TCP 소켓*으로 내렸다(스트림 프레이밍·spawn IPC 0·E2E 비트 동일). 그러나 둘이 남았다:

1. **broker 가 단일 코디네이터**로 각 호스트 소켓을 *직접 주소지정*했다(`socks.get(host).write`). 이건 별 모양(star) — 새 소비자를 더하려면 broker 코드를 고쳐야 한다.
2. **소켓이 localhost·TCP 신뢰 전송**이라 *실 네트워크 열화*(분단·재연결)는 안 탔다.

목표 토폴로지는 서버간을 *이벤트 버스*(pub/sub)가 잇고([SPINE.md](SPINE.md) §1·§4), 그 버스가 *열화* 아래에서도 권위 보존·desync 0 을 지키는 것이다. 이 step 은 그 한 발 — 직접 주소지정을 *토픽 pub/sub* 로 분산하고, 링크에 드롭·분단·재연결을 주입한다.

## 2. 핵심 개념 ① — pub/sub 버스와 "주소 무지"

**직접 주소지정**(0011)은 발행자가 "*zone1 의 소켓*에 쓴다"라고 말한다 — 발행자가 수신자의 *정체*를 안다. **pub/sub 버스**는 발행자가 "`cmd.zone1` *토픽*에 발행한다"라고만 말한다 — 그 토픽을 *누가 듣는지* 발행자는 *모른다*. 라우팅 테이블(`subs: topic→sockets`)이 구독자에게 배달한다.

이 *주소 무지*가 왜 중요한가? **새 소비자를 더하는 일이 발행자를 안 건드린다.** 이 step 은 `tap(topic, fn)` 으로 `cmd.zone1` 토픽에 *수동 소비자*를 하나 더 단다 — 그 소비자는 124개 사본을 받지만, *발행 경로(배리어)는 한 줄도 안 바뀐다*. 그리고 tap 이 있든 없든 다이제스트가 *동일*하다(비-침습).

> "N×N 직접 결합 제거"라는 추상적 구호의 *실체*가 바로 이 **주소 무지**다. 서버 A 가 서버 B 의 주소를 알면 A↔B 가 *결합*된다 — B 가 옮겨가거나 새 소비자 C 가 붙으면 A 를 고쳐야 한다. 발행자가 토픽만 알면, 구독자 집합이 어떻게 바뀌든 발행자는 불변이다. 다이제스트 불변이 이 무지를 못 박는다.

비유: 직접 주소지정은 *전화*(상대 번호를 알아야 건다)이고, pub/sub 은 *라디오 방송*(주파수에 쏘면 누가 듣든 방송국은 모른다)이다.

## 3. 핵심 개념 ② — 네트워크 분단, 그리고 "분단 = 사망의 현실화"

이게 이 step 의 가장 깊은 깨달음이다. **분단**(partition)은 링크가 끊겨 한쪽이 *침묵*하는 것이다 — 중요한 건, *프로세스는 살아 있을 수 있다*는 점이다(그냥 말이 안 닿을 뿐).

0009 의 failover 는 서버 *사망*을 "이 tick 부터 액터 무동작"으로 모델했다. 이 step 은 *액터를 건강하게 둔 채* broker 가 그 호스트 링크를 *침묵*시킨다(deliver/tick 발행 skip). 그런데 결과가 인프로세스 *사망*과 **logDigest·fullDigest 비트 동일**이다.

왜 같은가? **orch 의 lease 감지는 "권위가 *침묵*하는가"만 보지 "*왜* 침묵하는가"는 안 본다.** 사망이든 분단이든, 관측자에게 도착하는 신호는 똑같다 — *lease 가 안 온다*. 그래서:

> **권위 보존은 *원인 무관*하게 *침묵의 함수*다.** 죽었든, 끊겼든, 멈췄든 — 침묵이 같으면 복구도 같다. 0009 가 추상적으로 세운 failover 가 실 네트워크 분단을 *공짜로* 흡수한 셈이다.

이것이 분산 시스템의 핵심 원리 하나다 — *failure detector* 는 사망과 분단을 구별하지 못한다(둘 다 "응답 없음"으로 보인다). 그래서 사망을 다루는 메커니즘이 분단도 다룬다. 분단을 사망으로 *수렴*시킨 것.

## 4. 핵심 개념 ③ — 재연결이 깨우는 split-brain, 그리고 펜싱

그러나 사망과 분단엔 *진짜* 차이가 하나 있다 — **복귀**다.

사망(0009~0011)은 *영구* 침묵이었다 — 죽은 서버는 돌아오지 않으니, 추종자를 승격하면 끝이었다. 분단은 다르다 — **분단된 호스트는 살아 있어 복귀한다.** 복귀하면 옛 권위가 출력을 *재개*한다. 그런데 그 사이 추종자가 *이미 승격*됐다. 이제 *둘 다 권위*다 — 같은 엔티티를 둘이 쓴다 = **split-brain**(소유자 2). 권위 단일 소유([SPINE.md](SPINE.md) §5 ③)의 위반.

이걸 막는 게 **펜싱**(fencing)이다. broker 가 복귀 호스트에 *fence* 명령을 보내 그 액터를 `dead` 로 못박는다 — 살아 돌아왔지만 *출력이 수용되지 않는다*. 소유자는 1 로 유지된다.

> "회복은 침묵의 함수지만, *안전*은 복귀의 함수다." 분단은 사망보다 *한 조각 더*(재연결 펜싱)를 요구한다 — 옛 권위가 살아 돌아올 수 있으니까. 실제 분산 시스템(Zookeeper·etcd 의 fencing token, 리더 epoch)이 정확히 이 문제를 푼다.

그리고 미묘한 정합: fence 를 *게임 메시지*로 보냈다면 발신 로그가 달라져 "분단 ≠ 사망"이 됐을 것이다. fence 를 *제어 평면* 와이어 명령(데이터 평면 substrate 밖)에 두자, 액터는 dead 가 되되 발신 스트림은 불변 — **분단=사망 비트 동일과 split-brain 펜싱이 양립**한다. 제어 평면과 데이터 평면의 분리가 등치를 깨지 않고 안전을 더하는 자리다.

## 5. 핵심 개념 ④ — 멱등성: resend 를 안전하게 만드는 것

링크가 *양방향*(cmd·res) 프레임을 *드롭*하면(열화 a), broker 는 재전송한다. 그런데 위험이 있다 — *cmd 는 도착했는데 응답만 드롭*되면? broker 가 재전송한 cmd 를 호스트가 *두 번째로* 실행하면 — deliver/tick 이 *이중 적용*된다(엔티티가 두 번 움직인다). 결정론 파괴. 그리고 이건 *가상의* 위험이 아니다 — 양방향 드롭이라 res 유실이 *실제로* ~290회 일어나 중복 cmd 를 만든다.

해법이 **멱등성**(idempotency)이다. 호스트가 *reqId 별 응답을 캐시*한다 — 같은 reqId 가 또 오면 *재실행 없이* 캐시된 응답만 회신한다(`idempotentHits` ~290 = 실발동 증거). "같은 요청을 여러 번 받아도 한 번만 실행"이 보장되니, broker 는 *마음껏 재전송*할 수 있다.

이게 ack/resend 신뢰성의 *호스트 반쪽*이다 — broker 는 "통과할 때까지 재전송", 호스트는 "중복은 멱등 무시". 둘이 합쳐 *링크 드롭을 투명*하게 만든다(양방향 드롭 ~600개를 전부 메워 비트 동일 — *그 비트 동일이 곧 이중 적용 0 의 증거*다: 멱등이 깨졌다면 중복 cmd 가 다이제스트를 어긋냈을 것). 0008 이 *게임-층 손실*에 반응적 복원을 세웠듯, 이 step 은 *와이어 층 손실*에 같은 패턴을 세운다.

> exactly-once 배달은 분산 시스템의 성배다 — at-least-once(재전송) + 멱등(중복 무시) = effectively-once. [TOOLS.md](TOOLS.md) §5 의 "idempotency/exactly-once · 멱등 키"가 바로 이것.

## 6. 핵심 개념 ⑤ — 두 층의 손실, 두 층의 복원

0011 이 *게임-층 전송 모델*(0004)과 *소켓 와이어*를 두 층으로 나눴다. 이 step 은 그 분리를 *손실*에서 확인한다 — 손실이 *두 층 다*에 있고, *각 층이 자기 복원*을 갖는다:

1. **게임-층 손실**(0004·0008): intent·뷰·핸드오프가 겪는 지연·손실. broker 의 engine Net 이 결정론적으로 *시뮬*하고, 0008 의 ack/재전송·NAK/keyframe 이 복원한다(`transport` 시나리오).
2. **와이어-층 손실**(이 step): broker↔host 버스 프레임이 겪는 드롭. broker 의 resend + 호스트 멱등이 복원한다(`drop` 시나리오).

두 층이 안 섞인다 — `drop` 시나리오는 *와이어* 프레임을 드롭하지 게임 메시지를 잃지 않는다(게임 메시지는 결국 다 배달된다). 각 층이 자기 손실을 자기 메커니즘으로 메우므로, 둘 다 desync 0 으로 수렴한다. *관심사 분리*가 복원을 합성 가능하게 만든다.

## 7. 무엇이 *그대로* 작동하는가 — 개념의 합성

버스를 토픽으로 분산하고 링크에 드롭·분단·재연결을 넣었는데도, 0001~0011 의 모든 불변이 선다:

- **결정론 전파**: 같은 시드 2회 같은 다이제스트(`repro`) — 더구나 0009 까지 거슬러 *비트 동일*.
- **권위 단일 소유**: 분단→failover→재연결 펜싱 전 구간 소유자 1(`partition`: maxOwners 1).
- **수렴**: 드롭·분단 아래 desync 0.
- **은닉**: 버스·분단·펜싱이 갈려도 클라 누설 0.

핵심은 *액터 코드 0줄*을 안 건드린 것이다 — 버스 분산과 열화는 전부 broker↔host *와이어/제어 평면*에 산다. transport seam([SPINE.md](SPINE.md) §4)이 "직렬화 가능한 메시지 경계"로 설계됐기에, 직접 주소지정 → 토픽 pub/sub 의 재배선이 매끄러웠다.

## 8. 개념적 한계 — 무엇을 *아직* 추상화로 남겼나

1. **버스 *허브* vs 다중 브로커**: 토픽으로 *주소결합*은 풀었지만, 버스 허브는 여전히 broker 한 프로세스다. 상용은 *여러 브로커*(NATS/Redpanda 클러스터)로 물리 분산한다.
2. **논리 분단 vs 물리 소켓 파괴**: 분단을 broker 의 *논리 게이팅*으로 모델했다(결정론·비트 동일을 위해). 실제 `socket.destroy()`·재연결 핸드셰이크·in-flight 유실은 물리 층의 일(0011 이 실 OS 소켓을 이미 증명했으나 *파괴 후 재수립*은 별개).
3. **드롭 모델 vs 지연·재정렬·비대칭 분단**: 링크 열화를 *프레임 드롭 + resend* 로 모델했다. 명시적 지연·재정렬·한 방향만 끊기는 비대칭 분단은 후속.
4. **진짜 kill vs 링크 침묵**: 분단은 *링크* 침묵이지 `child.kill()` 이 아니다(그래서 펜싱이 필요했다 — 프로세스가 살아 있으니까). 진짜 kill·거짓 사망 오판 취소는 후속.
5. **언어**: 전 박스가 Node 다. 월드 시뮬 C++ 결정론 코어 교체는 동결 인터페이스 뒤 *최후*.

가장 유력한 다음은 **진짜 프로세스 kill 아래 failover**(링크 침묵을 넘어 실제 kill·타임아웃 추측 감지·재-provisioning·거짓 사망 취소) 또는 **물리적 다중-브로커 버스 분산**이다([STATE.md](STATE.md) §2).

## 9. 한 문단 정리

step-0012 는 broker 단일점을 *발행자가 수신자를 모르는* **토픽 pub/sub 버스**로 풀었다 — 직접 소켓 주소지정을 `cmd.<host>` 토픽 발행/구독으로 재배선하니, tap 소비자를 더해도 발행자가 무수정(주소 무지 = N×N 결합 제거의 본질). 그 버스 링크에 *실 네트워크 열화*를 주입했다: **드롭**은 reqId 멱등 재전송이 메워 비트 동일하게(at-least-once + 멱등 = effectively-once), **분단**은 권위 존 링크를 침묵시켜 — *액터를 죽이지 않고 링크만 끊었는데* 인프로세스 deathTick 과 **비트 동일**이다(권위 보존은 원인 무관한 *침묵의 함수* — 0009 의 failover 가 분단을 공짜로 흡수). 사망과 분단의 진짜 차이는 **재연결**이다 — 분단 호스트는 살아 돌아와 split-brain 을 깨우므로, *fence* 명령(제어 평면 — 발신 로그 불변)으로 부활을 막아 소유자 1 을 지킨다("회복은 침묵의 함수지만 안전은 복귀의 함수"). 다중 브로커 물리 분산·물리적 소켓 파괴·진짜 kill 은 의도적으로 다음 step 의 추상으로 남겼다.
