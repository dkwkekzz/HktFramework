# step-0057 — 치유 *확인 고리*: recover 명령 → 소비자 recoverAck 회신 (recoverAck)

> 직전: [step-0056](step-0056.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0056 의 recover 명령은 *fire-and-forget* 였다 — orch 가 down 소비자에 recover 를 보냈지만, 그 명령이 *전달·수행*됐는지는 몰랐다(분실 명령과 수행된 명령을 구별 못 함). 분산 제어 평면에서 명령은 유실될 수 있고, 그러면 코디네이션은 재시도해야 한다 — 그 토대가 *확인*이다. 이 step 은 소비자가 recover 를 받아 재구독할 때 명령 보낸 orch 에 `recoverAck` 를 회신하게 하고, orch 가 `recoverAcks` 로 명령 결과를 알게 한다. 닫는 조건: ⒜ `busPresenceRecover=0` 이면 0056 비트 동일(reg 0·recover/ack 0) ⒝ recover 보낸 모든 명령이 확인됨(`recoverAcks == recoversSent`·분실 0)·치유 완료(readmit≥1·consumerDown 비움) ⒞ 비-침습(ON==OFF 원장 minted).

## 2. 메커니즘 — 확인된 제어 평면 (busPresenceRecover OFF → baseline 비트 동일 = 회귀 0)

0056 의 recover 발신/재구독에 *역방향 확인*을 더한다. 소비자(`RankingService`)가 `recover` 를 받으면:

- `net.send(addr, bus, { type:'sub', topic })` — 자기 재구독(0056·라우팅 권위=구독자).
- `net.send(addr, m.from, { type:'recoverAck', consumer:addr })` — 명령 보낸 orch(`m.from`)에 확인 회신(주소 무지·명시 경로).

`Orchestrator.onMsg` 가 `recoverAck` 를 받아 `recoverAcks++`. `recoverAcks == recoversSent` 이면 orch 가 보낸 *모든* recover 명령이 전달·수행됐다(분실 0). 이는 0056 의 fire-and-forget 를 *확인된 루프*로 바꾼다 — orch 가 명령의 결과를 알므로, 미확인 명령(acks < commands)을 재시도하는 신뢰성 메커니즘(후속)의 토대가 된다.

`busPresenceRecover=0` 이면 orch 가 recover 미발신 → 소비자가 recoverAck 회신할 일 없음(handler 는 존재하나 trigger 0) → NET 비트 동일. 닿는 박스: `orchestrator.js`(recoverAck 수신)·`svc-ranking.js`(recoverAck 회신)·`topology.js`(0056 rankReDie 탐색분 정리·기능 0). 순수 제어 평면(존 tick 밖·원장 권위 불변).

## 9. 의외의 발견 / 정직한 한계

- **반복 사이클은 적응형 lease 가 *의도적으로* 억제한다(이 step 의 탐색에서 발견)**: 애초 이 step 은 "치유 *반복 사이클*"(소비자가 죽고-치유-다시 죽고-다시 치유)을 노렸으나, 적응형 lease(busLeaseAdapt·전체 러닝 max)에서는 첫 사망의 *긴 다운타임 gap* 이 cadence 추정을 영구 부풀려 둘째(동일/더 짧은) 사망을 *감지 못 한다* — 시스템이 한 번 오래 쉰 소비자를 "더 느긋한" 것으로 신뢰하기 때문(threshold=est+leaseSpan 이 커짐). 고정 임계(adapt off)는 둘째를 감지하지만 *살아있는* 소비자도 normal gap>leaseSpan 에 flapping(0050 의 문제)으로 22회 오축출. 즉 **적응형 lease 는 둘째-결함 민감도를 flapping 면역과 맞바꾼다** — 이는 버그가 아니라 트레이드오프. 윈도 cadence(0052)가 옛 gap 을 늙혀 부분 회복하나, 본 시드/틱 예산에선 깔끔히 안 나뉜다. → 그래서 이 step 은 "반복"이 아니라 *단일 사이클의 확인 고리*(recoverAck)로 조각을 다시 잡았다(반복 사이클의 신뢰 가능한 검증은 cadence 튜닝을 동반한 별도 step).
- **확인이 재시도의 전제**: recoverAck 자체는 카운터일 뿐이지만, `recoverAcks < recoversSent`(미확인 명령 존재)를 orch 가 *볼 수 있게* 한 것이 핵심이다 — 명령 분실 시 재발신하는 신뢰성 루프(0008 의 ack/NAK 가 데이터 평면에 한 일을 *제어 평면*에 하는)의 토대. 이 step 은 확인까지, 재시도는 후속.
- **회신 주소는 명령의 m.from**: 소비자는 orch 주소를 *모른다* — 받은 recover 의 발신자(m.from)로 회신한다. 이는 요청-응답의 자연한 은닉(응답은 늘 요청자에게)이며, 다중 코디네이터(후속)에서도 올바른 코디네이터에 회신됨을 보장한다.
