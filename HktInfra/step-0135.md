# step-0135 — saga 재admission 발행(readmitPublish — 포기↔재개 양방향 관측·liveness 수명주기 완비)

> 직전: [step-0134](step-0134.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0134 의 exchReadmit 은 *조용히* 재개했다. 0132 가 포기(saga_abandoned)를 발행했듯, 재개도 발행돼야 운영이 saga liveness 수명주기(포기↔재개)를 양방향으로 본다. **재admission 을 버스로 발행해 audit 가 관측하면서, 발행이 재개 동작/안전을 바꾸지 않는가?** 채우는 박스/계약: SPINE 계층3 거래소 발행 스트림에 saga_readmitted 합류(포기 발행의 짝).

## 1. 6계층 지도 ([SPINE.md](SPINE.md) §6)

| 계층 | 이번 step |
|------|-----------|
| 게임 서비스 | **거래소 재admission 발행** — exchReadmit 핸들러에서 `readmitPublish` ON 시 gid 마다 `svc.exchange.saga_readmitted` 1회 발행(`readmitPublished`) |
| 이벤트 버스 | audit 구독 행 1개 추가(`svc.exchange.saga_readmitted`→audit) |

## 2. 메커니즘 — 재개 시 발행(플래그 OFF → baseline 비트 동일 = 회귀 0)

- exchReadmit 핸들러의 재개 루프에서 `readmitPublish && bus` 면 `svc.exchange.saga_readmitted{ gid, itemId, cause }` 를 gid 마다 1회 발행하고 `readmitPublished++`(0132 abandonPublish 의 짝·readmitted 와 1:1).
- 토폴로지: `audit && exchange && readmitPublish` 면 audit 가 그 토픽 구독(0132 패턴).
- **회귀 0**: `readmitPublish===false`(또는 bus 부재) 면 발행 분기·구독 행 비활성 → 0134 비트 동일. readmitPublished 불변 0·crash() 리셋만 추가.

## 4. 척추 체크 5항

① **신성한 tick**: 발행은 외부 exchReadmit op 핸들러에서(존 tick 밖). ② **결정론 코어**: 발행 게이트는 결정론(시드 전 동일). ③ **권위 단일 소유**: 발행은 통보만·상태 변이 0. ④ **은닉·단일 연결**: 서버간 버스 pub/sub·audit 발행자 무수정. ⑤ **headless·원격 검증**: `node run.js` 수치 증명.

## 9. 의외의 발견 / 정직한 한계

- **수명주기 관측은 완비, 자동화는 아직**: 이제 포기(0132)·재개(0135)가 모두 발행돼 운영이 본다. 하지만 재admission 트리거(exchReadmit)는 여전히 *수동 op* — "가방 회복을 감지해 자동 재admit"(0056 busPresenceRecover 의 saga 판)은 후속. 관측이 그 자동화의 입력(svc.exchange.saga_abandoned 구독→재admit 결정)이 될 수 있다.
- **거래소 발행 6종**: sold/cancelled/expired/aborted/saga_abandoned/saga_readmitted — 발행 표면이 계속 큰다. 발행 정책 통합(한 게이트)·발행 토픽 네이밍 정리는 후속 정리 여지.
