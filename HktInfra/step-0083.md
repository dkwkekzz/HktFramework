## 검증 질문

0073/0075 의 파티 팬아웃은 멤버마다 라우팅(전달/반송)하지만 *파티 단위 완료*를 집계하지 않는다 — "이 파티 전송이 N 멤버 중 몇에 전달/반송됐고 다 끝났는가"를 모른다(0073 §9). 1:N 전송에 *파티 단위 완료 원장*을 더해, 부분 전달(N-of-M)을 가시화할 수 있는가? 개별 영수증(0076·delivered)의 1:N 집계 판.

## 2. 메커니즘 — partyId 별 완료 원장 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**구현** (`src/svc-whisper.js`): `partyReceipt` ON 일 때 `partyReceipts: Map<partyId, {members, routed, bounced}>` 원장.
- 파티 수신(`party`/`partyMembers`) 시 `_partyOpen(partyId, n)` — 멤버 수로 원장 초기화.
- `_queryFor(to, from, body, party)` — 보류 엔트리에 partyId 를 실어 라우팅 판정을 파티에 귀속.
- 라우팅(`presenceReply`) 시 멤버별로 `_partyTally(w.party, deliverable)` — up=routed++·아니면 bounced++ 를 그 파티에 집계.
- `partyDone(partyId)` = `routed + bounced === members` — 모든 멤버 해소(부분 전달 가시).

집계는 *추가 회계*일 뿐 — 라우팅(routed/bounced 총계)·원장 권위는 불변. `partyReceipt` OFF 면 `_partyOpen/_partyTally` no-op = 0082 비트 동일. 파티 주입의 partyId 는 payload 옵셔널 필드(미설정이면 직렬화 생략 → reg 0 불변).

① **신성한 tick** — 집계는 라우터 onMsg 의 자료구조 갱신, 존 tick 밖 순수 반응형. ② **결정론 코어** — 세계 쓰기 무변경(minted ON==OFF). ③ **권위 단일 소유** — 집계 권위 0(원장 무관). ④ **은닉·단일 연결** — partyId 는 라우터 내부 회계, 멤버는 모름. ⑤ **headless·원격 검증** — `node run.js`·`spine` 수치 증명, UE 0.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 파티 완료(done)는 *라우팅 판정* 기준(routed+bounced==members)이지 *실제 수신*(ack·delivered) 기준이 아니다 — 즉 "모든 멤버에게 전송을 *결정*했다"이지 "모든 up 멤버가 *받았다*"는 아니다. 라우팅 결정과 전달 확인이 다른 시간 척도라 자연히 갈린다.
- **한계**: 실제 ack 기반 파티 완료(up 멤버 전원 whisperAck 수신)는 멤버마다 Mailbox(영수증 경로·0076)가 필요한데 현 토폴로지엔 mbox 하나뿐 — up 멤버 중 mbox 만 ack 한다. ack 집계(deliveredByParty)는 멤버별 Mailbox 가 갖춰질 때 후속. 또한 같은 partyId 재전송 시 원장 덮어쓰기(_partyOpen 재초기화) — 멱등 집계(dedup)는 별도 step.
