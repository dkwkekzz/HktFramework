> 직전: [step-0142](step-0142.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0142 는 *입금만* — 수신자가 우편을 가져가는 경로가 없어 우편함이 무한히 쌓였다. 이번 한 조각: `mailFetch` — 수신자가 우편함을 pull 해 **보유(held)→수령(fetched) 무손실 이동**(이중 수령 0·빈 우편함 재수령 0통). 회계가 0142 의 `sent==totalHeld` 에서 **`sent==held+fetched`** 로 닫힌다(우편 1통은 매 순간 보유/수령 정확히 한 상태·공백·중복 0). 닫는 조건: 가설 `exmail`(수령 후 held↓·fetched↑·sent 불변·accountConsistent·재수령 0)·mail OFF = 0142 비트 동일.

## 2. 메커니즘 — mailFetch + 회계(새 op 타입; mailFetch 미주입 → 0142 동일 = 회귀 0)

- **`svc-mail.js`**: `onMsg` 에 `mailFetch` 분기 추가 — `{type:'mailFetch',to}` → 수신자 우편함 보유분 전부를 `read`(읽음 보관 Map recipient→[mail…])로 옮기고 `box.clear()`(보유→수령). 빈 우편함이면 0통(이중 0). 마지막 배치는 `_lastFetch`(0147 발행 대비).
- 새 상태: `fetched`(총 수령)·`expired`(0148 대비·현 0)·`read`(읽음 보관). accessor: `fetchedOf(rcpt)`·`readOf(rcpt)`·**`accountConsistent()`**(`sent === totalHeld() + fetched + expired`).
- **회귀 0 구조**: `mailFetch` 는 *새 메시지 타입* — `mailOps` 가 fetch 를 안 주면(reg 시나리오는 mail 자체 OFF) 분기 미진입 → 0142 비트 동일. 토폴로지 플래그 추가 0(배선 무변경). 거래소가 'cancel' op 를 더했듯 새 op 는 본질적으로 후방 호환.

## 4. 척추 체크 5항

① 신성한 tick — 수령은 존 tick 밖 우편 박스 연산(동기 I/O 0). ② 결정론 코어 — 수령은 결정론(난수 0·box→read 순서 결정적). ③ 권위 단일 소유 — 우편 1통은 매 순간 보유/수령 정확히 한 상태(accountConsistent 가 공백·중복 0 단언). ④ 은닉·단일 연결 — mailFetch 메시지로만 통신. ⑤ headless·원격 검증 — `node run.js`/`spine` 통과(UE 0).

## 9. 의외의 발견 / 정직한 한계

- 수령은 현재 *전부 가져가기*(box 통째 비움) — 부분 수령(페이지네이션)·읽음/안읽음 구분은 후속(필요 시). 회계 불변엔 무관(보유 또는 수령 둘 중 하나).
- 수령 손실(fetch 응답이 클라에 도달 못 함)은 아직 안 다룬다 — read 보관이 그 토대(0147 읽음 확인 발행에서 재수령 무손실 재반환 가능). 영속(0145) 전엔 crash 시 read/box 둘 다 휘발.
