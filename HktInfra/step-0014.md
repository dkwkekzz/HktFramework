# step-0014 — 가방 서비스 분리 (아이템 원장을 존 tick 밖 비동기 서비스로 · 단일 소유 · 쌍 거래 · dupe 0)

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0014/net-core.js`(0013 액터·토폴로지 빌더 복사 전진 + **InventoryService** 박스 + Gateway/Client 가방 라우팅·인텐트(가산)) · `step-0014/cluster.js`(broker — 0013 그대로 + **inventory 재구성**) · `step-0014/host.js`(0013 그대로 + **inventory 스냅샷**) · 헤드리스: `step-0014/verify.js` · 관찰: `step-0014/panel.js`(+`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **SPINE 계층 3(게임 서비스)의 첫 박스 — 가방(인벤토리)을 *독립 서비스*로 떼어 "신성한 tick"(시뮬 tick 엔 시뮬만, 그 외는 비동기 서비스/버스 경유)의 판정 기준을 처음으로 실증한다.** 0001~0013 은 월드(존 시뮬)·버스·코디네이션을 채웠으나 *비-시뮬 게임 상태*(아이템 원장)는 아직 어디에도 없었다. 이 step 은 `InventoryService`(원장 `Map<itemId,owner>` + `byOwner` 역인덱스, **onTick 없음 = tick 무관 순수 반응형**)를 자기 OS 프로세스·버스 구독자로 세우고, 클라가 *별도 itemRng·별도 채널*로 pickup/give 인텐트를 게이트웨이→inventory 로 보낸다. 아이템 이동(give)은 *쌍 거래*(원장에서 sender release + receiver acquire 를 한 onMsg 안에 원자적) — 존 권위 핸드오프(release+acquire)의 아이템 판. 가방은 *존을 우회*하므로 존 net.log·상태가 가방 on/off 에 **비트 동일**(시뮬 비-침습). 클라는 여전히 게이트웨이만 안다 — inventory 주소·원장·item_req 는 *서버간* 경계(은닉).
>
> **관찰(눈으로)**: 헤드리스 미리보기는 `node step-0014/panel.js [seed]`(ANSI — inventory 박스가 프로세스 목록·gateway↔inventory 엣지로 보임). 전체 흐름 시각화는 `node run.js report`. 시각화는 단일 testbed 로 일원화([TESTBED.md](TESTBED.md)).

step-0013 까지 6계층 중 월드(2)·버스(4)·코디네이션(5)은 채웠으나 **게임 서비스(3)는 0% (⬜)** 였다 — 채팅·가방·거래소 같은 *tick 과 무관한* 게임 상태가 아직 어디에도 살지 않았다. 목표 토폴로지의 founding belief 는 "한 프로세스가 모든 일을 하면 모든 일이 서로의 병목이다 — 단 *시뮬 tick 에는 시뮬만*"([CLAUDE.md](CLAUDE.md)·[SPINE.md](SPINE.md) §2)이고, 그 분리 판정 기준은 하나다: *그 일이 존 시뮬 tick 과 같은 박자로 돌아야 하는가?* 아이템 트랜잭션은 아니다(SPINE §2). 이 step 은 그 한 조각을 친다 — 가방을 *존 tick 밖 비동기 서비스*로 떼고, *단일 소유·쌍 거래·dupe 0·신성한 tick·은닉·헤드리스*를 수치로 증명한다. 0001~0013 의 프로토콜·토폴로지·복원·failover·토픽 버스·kill 생애주기는 *그대로* 두고, *게임 서비스 박스 하나*만 더한다.

결과: **전 시드 전 항목 통과.** ① 회귀 0(`reg`) — 인프로세스 모드(가방 OFF)면 0013 과 *비트 동일*(net.log·상태, zones 1·2 · recovery off/on · failover off/on(+death) 20/20) ② E2E 동치(`e2e`) — 멀티프로세스(가방 ON·토픽 버스·무열화)가 인프로세스와 *비트 동일*(logDigest·worldDigest·invDigest)·아이템 단일 소유·itemDesync 0(basic-inv 7프로세스·failover-inv 10프로세스) ③ 신성한 tick(`sacred`) — 가방 ON vs OFF 월드 상태 *비트 동일*(가방이 시뮬에 비-침습)·한편 가방은 실제 일함(minted 47~53·transfer 6~13)·존에 도달한 item 메시지 **0**·inventory onTick **없음** ④ 권위 단일 소유(`ownership`) — 아이템 belief 소유자=1·conserved(원장 ≡ minted)·consistent(원장 ≡ byOwner)·itemDesync 0·*전송 열화*(redundancy+loss)에도 원장 보존·미소유 give 거부(failedOps 1~6) ⑤ 분리(`isolate`) — inventory = 자기 OS pid(7 호스트)·원장 47아이템·버스 프레임뿐 ⑥ 은닉(`hide`)·재현(`repro`) — 클라 누설 0·가방 쓴 클라 4/4, 같은 시드 멀티 2회 = 인프로세스 같은 원장(invDigest 42=0x2171a222 … 2026=0x43c2e335).

## 2. 메커니즘 — 가방을 존 tick 밖 비동기 서비스로 분리 (이 step 의 한 조각)

```
 인프로세스(run): inventory 플래그 OFF → engine/Net + 0013 액터 그대로 — 0013 비트 동일(reg 0).
                  inventory 플래그 ON → 가방 박스 + 클라 아이템 인텐트(별도 itemRng·별도 채널).

 아이템 경로(존 우회 = 신성한 tick):
   client ──item_pickup/item_give(itemId·toAvatar)──▶ gateway ──item_req(op·avatar)──▶ inventory
   client ◀──item_result(ok·op·itemId)/item_recv─── gateway ◀──item_result(reqAvatar·toAvatar)── inventory
        (존(zone1/zone2)은 이 경로에 *없다* — net.log 의 존 비트열 불변 → 월드 비-침습)

 InventoryService (tick 무관 순수 반응형 — onTick 0):
   ledger:  Map<itemId, owner>     ← 단일 진실(매 시점 소유자 정확히 1, 구조적 dupe 불가)
   byOwner: Map<owner, Set<itemId>> ← 역인덱스(트랜잭션 정합 교차검증: 원장 ≡ byOwner)
   pickup:  itemId = 'item'+(mintTotal++); ledger.set(itemId,avatar); byOwner[avatar].add(itemId)   // 신규 mint
   give:    owner==from && to && to!=from ?  byOwner[from].delete(id); ledger.set(id,to); byOwner[to].add(id)  // 쌍 거래(원자)
                                          :  fail(미소유/이미이동/자기자신 — 중복이동·phantom 0)
```

0013 대비 더한 것은 *게임 서비스 박스 하나*뿐 — 존/버스/배리어/kill 생애주기는 *그대로*:

1. **가방 = 존 tick 밖 비동기 서비스(신성한 tick).** 0013 까지 모든 상태 변경은 존 tick(onTick) 안에서 일어났다. 이 step 의 `InventoryService` 는 **onTick 이 없다** — 오직 `onMsg`(item_req)에만 반응한다. 즉 *존 시뮬 tick 의 박자와 무관*하게 도는 비동기 서비스다. 아이템 트랜잭션이 존 tick 을 *막지 않고*(SPINE §2 병목 제거), 존을 *우회*하므로 존 net.log·상태가 가방 on/off 에 비트 동일하다(`sacred`: worldDigest(on)==worldDigest(off)). "그 일이 존 tick 과 같은 박자로 돌아야 하는가?"의 답이 "아니오"인 책임을 존 밖으로 뺀 *첫 실증*.

2. **단일 소유 + 쌍 거래(dupe 0).** 원장은 `itemId→owner` 의 *함수*(Map)라 어떤 아이템도 *동시에 두 소유자*를 가질 수 없다(구조적 소유자=1). 이동(give)은 *한 onMsg 안에서* sender release(`byOwner[from].delete`)와 receiver acquire(`ledger.set`+`byOwner[to].add`)를 *원자적*으로 한다 — 존 권위 핸드오프의 release+acquire 쌍 거래를 아이템에 적용한 것. `byOwner` 역인덱스가 원장과 *항상 일치*(consistent)함을 교차검증해 비-원자 이동(한쪽만 갱신)을 잡는다.

3. **idempotent transfer — 전송 열화에도 원장 보존.** 옮긴 아이템을 *다시* give 하면 owner≠from 이라 *거부*(fail)된다 → 재적용(전송 redundancy/dedup)이 와도 *중복 이동 0*. 미소유·이미이동·자기자신 give 도 거부(phantom 0). 그래서 가방 홉(gateway↔inventory)을 redundancy 3·loss 0.2 로 열화해도 원장이 *보존*(conserved: ledger.size==minted)·*정합*(consistent)하다(`ownership` 열화 컬럼). 아이템은 소멸 없이 이동만 하므로 손실·중복 0.

4. **belief = 서버 권위로만 수렴.** 클라는 아이템을 *낙관적으로* 바꾸지 않고 *서버 결과*(item_result/item_recv)로만 `items` 를 갱신한다 — 원장 진실로 수렴(itemDesync 0). 클라가 보낸 give 가 도중에 owner 가 바뀌어 fail 나도 belief 는 보수적(과대 소유 안 함). "수렴(desync 0)" 불변의 아이템 판.

5. **별도 itemRng — 월드 무오염.** 클라의 아이템 행동은 *move rng(seed^0xC11E)와 독립된 itemRng(seed^0x17E1)* 를 쓴다 → 월드 move 스트림을 *건드리지 않는다*. give 대상은 클라의 *AOI 뷰(seen)에 보이는 피어*(이미 0005+ 에서 클라가 아는 엔티티 id) 중 선택 → 새 누설 0. 그래서 가방 on/off 에 존 상태가 비트 동일.

> 클라는 여전히 게이트웨이만 안다 — inventory 주소·원장·item_req 는 *서버간* 경계다. `node verify.js` 한 줄이 inventory 를 별 프로세스로 spawn 해 버스로 묶어 4기둥을 검증한다 — 제1 운영 제약의 충족(원격·헤드리스).

- 어떤 아이템도 두 클라가 동시에 소유 믿지 않음(belief 소유자=1)·원장 보존(ledger.size==minted)·정합(원장 ≡ byOwner)·belief 가 진실로 수렴(itemDesync 0). 가방 홉을 redundancy 3·loss 0.2 로 열화해도 원장 *보존·정합* — 옮긴 아이템 재-give 가 owner≠from 으로 거부(idempotent transfer)되어 중복 이동 0(거부 1~6건 = 트랜잭션 거부 실증).

## 7. ⑤ 분리 · 은닉 · 재현 — `isolate`·`hide`·`repro`, 통과

**프로세스 분리(`isolate`)** — inventory = 구분 OS pid·통신은 버스 프레임뿐:

```
broker pid P0(TCP :Pn) · 호스트 7개 · inventory pid Pi(≠broker) · 원장 47아이템(minted 47·transfer 13) · 토픽 7개 · 버스 out 742프레임
배치: login·registry·gateway·inventory·zone1·zone2 각 1 프로세스 · client0..5 → clients 1 프로세스
```

- inventory 가 자기 OS 프로세스에 살고(원장 47아이템), 경계 넘는 *모든* 토픽 프레임이 양방향 직렬화 가능. broker 코드는 가방을 *특별 취급하지 않는다*(범용 호스트).

**은닉(`hide`)** — 전 시드: 가방 ON 에도 클라 접점이 공개 주소(login·gateway)뿐, 내부 토폴로지(zone/sessionId/handoff/lease/promote/**inventory/item_req/ledger/byOwner/reqAvatar**) 누설 **0**, 뷰 받은 클라 4/4·가방 쓴 클라 4/4. (클라는 itemId·toAvatar 만 보고 — toAvatar 는 이미 AOI 로 아는 가시 엔티티 id, inventory 주소·원장은 비가시.)

**재현(`repro`)** — 같은 시드 멀티프로세스(가방) 2회 → 같은 invDigest, *인프로세스와도 동일*·world 동일: 42=0x2171a222 · 7=0x99602bbb · 1234=0x18acb00a · 99=0x2475e305 · 2026=0x43c2e335. 시드별 원장이 서로 달라(5/5) 결정론이 시드의 함수임을 교차 확인.

## 8. 의외의 발견

1. **"신성한 tick" 은 *onTick 의 부재*로 가장 깔끔히 증명된다.** 가방을 비-침습으로 만드는 데 가장 효과적인 단언은 복잡한 격리가 아니라 *inventory 가 onTick 을 갖지 않음* + *존 net.log 비트 동일* + *존 도달 item 0* 세 줄이었다. "시뮬 박자와 무관하다"가 코드 구조(반응형 서비스)와 검증(worldDigest 불변)에 *그대로 드러난다* — 분리의 본질이 "tick 에 붙지 않음"임을 onTick 부재가 못 박았다.
2. **별도 RNG 스트림이 비-침습의 *비결*이다.** 클라가 아이템 행동에 *move 와 같은 rng* 를 쓰면 가방 on/off 가 move 시퀀스를 어긋나게 해 월드가 갈렸다(worldDigest 깨짐). itemRng(0x17E1)를 move rng(0xC11E)와 *분리*하자마자 월드가 가방 on/off 에 비트 동일이 됐다 — "비-침습"이 단순히 *메시지가 존에 안 닿음*이 아니라 *결정론 스트림의 격리*까지 포함함을, worldDigest 가 가르쳤다.
3. **아이템 단일 소유는 *자료구조*가 공짜로 보장한다 — 증명할 것은 *정합*이다.** 원장을 `Map<itemId,owner>` 로 두면 소유자=1 은 구조적으로 자명(dupe 불가). 진짜 위험은 *비-원자 이동*(한쪽만 갱신)이고, 그것은 원장 단독으로는 안 보인다 — `byOwner` 역인덱스를 두고 *원장 ≡ byOwner* 를 교차검증해야 잡힌다. "단일 소유"의 부담이 *소유 카운트*에서 *두 표현의 정합*으로 옮겨갔다.
4. **idempotent transfer 가 전송 신뢰성을 *공짜로* 흡수한다.** 옮긴 아이템 재-give 가 owner≠from 으로 *자연 거부*되므로, 가방 홉을 열화(redundancy/loss)해도 별도 dedup 없이 원장이 보존된다 — give 의 *멱등성*(같은 이동의 재적용 = no-op fail)이 0008 의 ack/재전송·0012 의 reqId 멱등과 같은 안전을 *애플리케이션 의미* 층에서 준다. 트랜잭션의 멱등이 전송의 멱등과 만난다.

## 9. 정직한 한계

1. **아이템 = mint+이동만(소비·스택·속성 없음).** 원장을 itemId→owner 로 단순화했다 — 아이템 소멸(소비·드롭), 수량 스택, 속성(등급·내구도), 동시 다중 아이템 거래(번들)는 안 탔다. "쌍 거래·단일 소유"의 *netcode 골격*을 보였지 게임 아이템 시스템의 풍부함은 아니다. 소멸이 들어오면 conserved 단언이 minted-destroyed 로 바뀐다.
2. **거래 = 일방 give(원자) — 2-party 동의·에스크로 없음.** give 를 *발신자 단독* 트랜잭션으로 모델했다(받는 쪽 동의 없이 양도). 상용 거래는 *양자 동의*(둘 다 확인)·에스크로(중간 잠금)·2단계 커밋이 필요하다 — 이 step 은 *원장의 원자성*을 보였지 *분산 거래 프로토콜*(존 넘는 거래·서비스 넘는 2PC)은 세우지 않았다(SPINE §2 "존을 넘는 거래"는 후속).
3. **단일 inventory 인스턴스·영속 0.** 가방이 *하나*의 프로세스에 살고(샤딩·복제 없음), 상태는 *메모리*에만 산다(영속 0 — 프로세스와 함께 죽는다). failover·재-provisioning 을 *존*엔 적용했으나 *가방엔 안 했다* — 가방 죽으면 원장 소실. 계층 6(데이터·write-behind)·가방 failover 는 상속된 후속.
4. **give 대상 = AOI 가시 피어(근접 거래만).** 클라가 *보이는* 아이템만 양도 대상으로 골랐다(AOI seen). 우편·원거리 거래소·오프라인 수령은 안 탔다(SPINE §3 채팅·우편·거래소의 반복 패턴). 또 클라 belief 는 *서버 권위 수렴*만 — 예측/롤백(낙관적 UI)은 안 했다.
5. **여전히 Node · C++ 시뮬 미교체 · 비동기 결정론 미착수.** 가방은 게임 서비스라 결정론 시뮬 코어와 무관하나, 월드의 C++ 결정론 시뮬 코어 교체([STATE.md](STATE.md) §3 🔴)·lockstep 배리어 해제(비동기 결정론)는 상속된 후속. testbed `inject`(클라 intent 주입)도 0013 상속(가방 인텐트는 net-core 내부 클라 RNG 함수라 testbed write-seam 과 별개).
