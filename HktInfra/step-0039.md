# step-0039 — 버스 failover replay 버퍼 *유계화* (busWindow 슬라이딩 K 창)

> 직전: [step-0038](step-0038.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0036(결과 경로)·0037(요청 경로)은 버스 failover 무손실을 *producer replay* 로 달성했다 — 가방이 발신 결과를(`outBuffer`), 게이트웨이가 발신 요청을(`inBuffer`) 보관했다 버스 복구 시 재발행. 두 버퍼 모두 발신한 *전* 항목을 무계로 쌓았다(두 step 문서가 "무계" 를 §9 한계로 명시) — **장기 가동 시 메모리 무한 성장**(런타임 위험). 이 step 의 질문: *그 replay 버퍼를 유계 창으로 묶으면서 무손실을 유지할 수 있는가?* failover 가 메우려는 건 gap 구간(crash→재구독)뿐이므로, 버퍼는 그 창을 덮을 만큼만 있으면 된다는 가설을 0032 `wfWindow`(정합성 윈도 sweep 의 유계 K 창)의 *버스 판*으로 검증한다. SPINE §6 계층 4(이벤트 버스)의 *무계 자원* 한계를 닫는다.

닫는 조건: ① `busWindow=0`(기본) → 0038 비트 동일(reg 0) ② `busWindow=K` → 두 버퍼 ≤K(유계) ③ K≥gap → minted==base·desync 0(유계화 투명) ④ K<gap → 손실 재현(바운드 load-bearing).

## 2. 메커니즘 — replay 버퍼 슬라이딩 K 창 (플래그 `busWindow`; 0 → 0038 비트 동일 = 회귀 0)

- **두 producer 버퍼에 동일 슬라이딩 규칙**: push 후 `length > K` 면 가장 오래된 항목 `shift()`. `busWindow=K` 가 *최근 K 개*만 유지.
  - `gateway.js` `_itemReq`: `inBuffer.push(ev); if (busWindow>0 && inBuffer.length>busWindow) inBuffer.shift()`.
  - `svc-inventory.js` `_out`: `outBuffer.push(msg); if (busWindow>0 && outBuffer.length>busWindow) outBuffer.shift()`.
  - `busWindow=0` 이면 `if` 가짓→ push 만 = 0038 비트 동일. `busResend`/`busResendReq` OFF 면 버퍼 자체 미사용 → `busWindow` 무관(reg 0 불변).
- **왜 *최근* K 가 옳은가**: 버퍼는 push-순서(FIFO). gap(crash→reneg)에 떨군 요청/결과는 재구독 시점 기준 *가장 최근* 항목들이다 → `shift`(오래된 것 제거)는 gap 항목을 보존한다. 따라서 K≥|gap| 이면 전 gap 항목이 버퍼에 남아 재발행 = 무손실. K<|gap| 이면 가장 오래된 gap 항목이 evict → 그만큼 손실.
- **배선**: `topo-build.js` 가 `busWindow` 를 destructure → 버스 ON 일 때만 gateway·inventory opts 로 전달(`busAddr ? busWindow : 0`). makeActor 가 Gateway 생성자 7번째 인자로 전달. 존 tick 밖 순수 제어 평면(신성한 tick 보존).

## 3. 검증 결과 (시드 [42,7,1234,99,2026] · `node run.js` / `node run.js spine`)

**reg (회귀 0)**: `busWindow=0` → NET 이 0038 과 **비트 동일** — 25/25 OK(net.log+상태+inv/chat/bus/rank 다이제스트). replay 버퍼 미사용/OFF 경로 휴면이라 슬라이딩 코드 비-기여.

**buswin (가설)**: `crash@12 → 재협상@14`, 모두 `busResend+busResendReq` ON(전 replay). gap = 18 요청/결과 드롭(recov 대조군 사전측정). unbnd(K=0·무계) vs bnd(K=24≥gap) vs tiny(K=8<gap).

| seed | minted base/unbnd/bnd/tiny | buf unbnd/bnd/tiny | desync unbnd/bnd/tiny | 판정 |
|---|---|---|---|---|
| 42   | 51/51/51/41 | 60/24/8 | 0/0/4 | OK |
| 7    | 53/53/53/43 | 60/24/8 | 0/0/4 | OK |
| 1234 | 54/54/54/44 | 60/24/8 | 0/0/4 | OK |
| 99   | 53/53/53/43 | 60/24/8 | 0/0/4 | OK |
| 2026 | 56/56/56/46 | 60/24/8 | 0/0/4 | OK |

- **① 유계**: bnd 버퍼 ≤24, tiny ≤8, unbnd 60(무계 — 활성 op 수만큼 성장). → 슬라이딩이 메모리를 K 로 묶음(무계 60 → bnd 24 = 40%).
- **② K≥gap 무손실·투명**: bnd 가 unbnd(무계)와 *같은 결과* — minted==base 이고 desync 0. 유계화가 동작에 무영향(gap 항목이 K 안에 남음).
- **③ 바운드 load-bearing**: tiny(K=8<gap 18)는 가장 오래된 gap 요청/결과 evict → minted<base(−10)·desync 4(손실 재현). *임의 K 가 아니라 gap 을 덮어야* 무손실 — 바운드가 정직하게 작동한다.
- **원장 무손상**: 세 변형 전부 `itemConserved`·`ledgerConsistent`(size==minted·byOwner≡ledger) — 유계 슬라이딩이 dupe 0.

**E2E·spine**: `node run.js`(현재 step 4기둥) ALL OK · `node run.js`(default 멀티프로세스 E2E) ALL OK · `node run.js spine`(39-step 회귀 사슬) ALL OK. (멀티프로세스 경로는 `busWindow` 미제공 = 무계 = 0038 동일 — cluster.js 무수정.)

## 9. 의외의 발견 / 정직한 한계

- **gap=18 은 "2 tick 창" 의 직관보다 크다**: crash@12→reneg@14 는 2 tick 이지만, svc.item 요청 스트림이 활성 초반에 몰려(BASE 베이스) 그 창에 18 요청/결과가 떨어진다. minted 손실이 K 에 *매끄럽게* 비례(K=8→−10, K=16→−2, K=18→0)한 이유 — gap 항목 하나당 mint 하나. K 임계(=gap=18)는 시간 창이 아니라 *그 창의 발신 수*가 정한다.
- **정직한 한계**: K 임계(18)는 crash↔reneg 창 × 발신율의 함수 — 고정 K 는 *최대 예상 다운타임 × 최대 발신율* 로 잡아야 안전하다. 부하/다운타임이 그를 넘으면 손실(tiny 가 보인 실패 모드). 발신율·관측 다운타임으로 K 를 자동 조정하는 *적응형 창*은 후속(0032 `wfPeriod` 의 적응형 sweep 미착수와 같은 계열). 또한 이 step 은 *give 요청 × result-ahead 결합*(0037 §9)을 건드리지 않는다 — busWindow 는 두 한계 중 *무계* 만 닫는다.
