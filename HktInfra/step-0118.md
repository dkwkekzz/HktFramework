# step-0118 — 거래소↔가방 buy 입금 (exchInventory leg 2 · escrow→구매자 실물 인도)

> 직전: [step-0117](step-0117.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0117 은 list 인출 레그만 더해 escrow 를 가방 원장에 실체화했으나, exchBuy 는 거래소 sold 회계만 굴리고 구매자 가방엔 아이템이 안 들어왔다. buy 입금 레그(escrow→buyer)를 더해 list(인출)+buy(인도)가 *존 넘는 실물 거래*를 완성하는가? 닫는 조건: exchInventory ON 이면 산 itemId 가 구매자 가방 소유·escrow 에서 빠짐·minted 불변, OFF 면 give 0 = 0117 비트 동일(reg·추상 sold).

## 2. 메커니즘 — escrow→구매자 실물 인도 (exchInventory OFF → baseline 비트 동일 = 회귀 0)

- **exchBuy 입금 레그**: 체결(listings.delete+sold++ +delivered/proceeds 회계) 직후 `_custody(l.itemId, 'escrow', p.buyer)` — escrow custody 아이템이 구매자 가방으로(가방이 give 처리: escrow 보유 검사·xfer·역인덱스). 0117 `_custody` 헬퍼 재사용(invMode OFF 면 no-op).
- **실물 거래 완성**: list(인출 0117) + buy(인도 0118) → 판매자가 escrow 에 맡긴 *실제 가방 아이템*이 체결 시 구매자 가방으로. 거래소 회계(sold/proceeds)와 가방 권위(소유 전이)가 짝을 이룬다.
- **권위 = 가방**: 거래소는 give *요청만*, 소유 전이는 가방이 권위로 수행. escrow custody 가 가방 원장에 단일 소유로 산다(구매자 인도도 release+acquire 쌍).
- **회귀 0**: exchInventory OFF(또는 itemId 부재)면 give 분기 휴면 = 0117 비트 동일(추상 sold).

## 9. 의외의 발견 / 정직한 한계

- **발견**: 인출(seller→escrow·0117)과 인도(escrow→buyer·0118)가 *완전히 같은 give 연산*이고 방향만 다르다 — 존 넘는 실물 거래가 0014 가방 give(아바타↔아바타) 두 번으로 정확히 분해된다(escrow 가 중간 custody). "권위 단일 소유 + 쌍 거래"가 *두 당사자 + 중개 escrow* 의 3-홉 거래에도 그대로 — escrow 가 거래의 원자성을 보장하는 중개 소유자(닫힌 장부의 거래 판).
- **한계**: 아직 cancel/expire 반환 레그(escrow→seller)가 없어 미체결 매물의 아이템이 escrow 에 묶인다(0119). give 는 *낙관적* — escrow 가 (가방 손실 등으로) 아이템을 안 가지면 give 실패하지만 거래소 sold 는 성립(원자성 보상은 후속·saga). 대가(통화) 이동은 추상(proceeds 회계만·실물 통화 가방 미모델).
