# step-0022 — 채팅 커맨드 로그 스냅샷 압축 (라우팅 스냅샷 + tail replay — 0018 가방 압축의 커맨드-소싱 판)

> 직전: [step-0021](step-0021.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0021 은 채팅을 *커맨드 로그* event sourcing 으로 복구했지만 그 로그를 **비유계**로 남겼다(압축 없음 — §3 격차 ⓒ). 0018 이 가방 *효과* 저널을 "intent 로그 + 주기 스냅샷"으로 유계화했듯, 이 step 은 채팅 *커맨드* 로그를 같은 패턴으로 유계화한다. **닫는 조건**: 채팅 커맨드 N항목마다 라우팅 스냅샷을 발신해 헤드 커맨드를 폐기하되, *라우팅 스냅샷 + tail 커맨드 replay == 전체-커맨드 replay == 무재시작* 이 **chatDigest 비트 동일**(무손실)이고, 커맨드 로그가 (스냅샷 1개 + 짧은 tail)로 유계화되며, 압축 OFF(`chatSnapshot=0`)면 0021 과 비트 동일(reg 0). SPINE 계층 6(데이터·write-behind 유계화) + 계층 3(게임 서비스 채팅) 채움.

## 2. 메커니즘 — 채팅 커맨드 로그 라우팅 스냅샷 압축 (`chatSnapshot=0` → 0021 비트 동일 = 회귀 0)

**핵심 차이(효과소싱 vs 커맨드소싱의 압축)**: 가방 스냅샷(0018)은 *원장 값*(itemId→owner)을 직렬화하지만, 채팅 스냅샷은 *파생 라우팅 상태* — 커맨드 로그의 **리듀스 결과**(channels: channel→Set\<avatar\> · byAvatar 역인덱스 · deliveries · 계측)를 통째로 뜬다. say 의 팬아웃이 *그 시점 라우팅* 의존이므로 복구의 베이스도 라우팅 그 자체다.

- **`ChatService._journal`**: 커맨드를 chatpersist 로 fire-and-forget 한 뒤, `snapInterval>0 && journalSeq % snapInterval === 0` 이면 `_snapshot()` 호출(write-behind·반응형·onTick 0).
- **`ChatService._snapshot()`**: `{upToSeq, channels, byAvatar, deliveries, joins/says/whispers/whisperFails/fanout/leaves}` 발신. Set/Map 은 *삽입 순서* 보존 직렬화 — say 의 구독자 순회 순서 = deliveries 순서 결정론이므로 복원도 동순서.
- **`PersistStore.onMsg('snapshot')`**(0018 그대로·제네릭): `snapshot.upToSeq` 이하 커맨드를 폐기, tail 만 보존. `writes`(누적 append 수)는 *안 줄인다*(완전성 회계의 진실).
- **`ChatService.replay(journal, snapshot)`**: snapshot 있으면 channels/byAvatar/deliveries/계측을 직접 복원(상태 = 헤드 커맨드의 리듀스 결과) → tail(seq>upToSeq) 커맨드만 `_process` 재실행(`replaying` 가드로 재발신 0). snapshot 없으면(0021) 이 블록 휴면 → 전체-커맨드 replay 와 비트 동일.
- **`leaves` 누적 카운터**(신규): 압축으로 `journal.length` 가 줄어도 `writes`(누적)는 불변 — 완전성은 `writes == joins+says+whispers+leaves`(영속된 *커맨드 수*, journal.length 아님)로 본다. 0018 `journalComplete`(`writes==minted+transfers`)의 채팅 판.

더한 것은 `chat._snapshot` + `replay` 스냅샷 베이스 + `leaves` 회계 + cluster.js 채팅 스냅샷 전달뿐. host.js 무변경(replay·snapshotActor 제네릭). 월드·버스·가방 영속/압축·랭킹·채팅 failover(0017~0021)는 복사 전진.

## 4. 척추 체크 5항

1. **신성한 tick** — 스냅샷·압축·replay 는 *존 tick 밖*(제어 평면·chat onTick 0). chatSnapshot on/off 월드 비트 동일·존 도달 snapshot 0(sacred·svcMsgsToZones 0).
2. **결정론 코어** — 복구 라우팅+deliveries = (스냅샷 베이스 + tail 커맨드)의 함수 → 전체-커맨드 replay·무재시작과 정확히 일치(= §4 "복제=재현", 상태 전송 아님). Set/Map 삽입 순서 보존으로 deliveries 순서 결정론.
3. **권위 단일 소유** — 채팅 라우팅의 쓰기 권위는 ChatService 하나. 압축은 *보관*만 줄이고 라이브 권위 비-침습(라이브 chatDigest 불변). PersistStore 는 데이터 계층.
4. **은닉·단일 연결** — 스냅샷/replay 는 커맨드 로그를 *제어 평면*으로 읽을 뿐(클라 비가시·hide 누설 0). 복구 후 say 도 누설 0/격리 보존.
5. **headless·원격 검증** — `node run.js 0022` 한 줄이 채팅을 *진짜 kill→스냅샷+tail replay* 로 띄워 무손실·복구 투명·E2E 비트 동일을 4기둥 검증(UE 0).

## 9. 의외의 발견 / 정직한 한계

- **발견 — 커맨드소싱 압축의 스냅샷은 "리듀스 결과 전체"다**: 효과소싱(가방)은 원장 값만 떠도 충분하지만, 커맨드소싱(채팅)은 *say 팬아웃이 라우팅 의존*이라 스냅샷이 channels+byAvatar+deliveries+계측 *전부*를 떠야 한다(파생 상태가 곧 복구 베이스). 그럼에도 PersistStore 의 snapshot 핸들러는 snap 모양 무관(`upToSeq` 만 봄)이라 *제네릭으로 가방·채팅 공용*(무변경 재사용) — event sourcing 압축의 추상이 효과/커맨드 양쪽에 동일하게 성립.
- **발견 — 완전성 회계는 `journal.length` 가 아니라 *누적 커맨드 수*여야 한다**: 압축이 journal.length 를 줄이므로 0021 의 `writes==journal.length` 검사는 깨진다. `leaves` 누적 카운터를 더해 `writes==joins+says+whispers+leaves` 로 바꿔야 압축-인지 완전성이 성립(0018 `journalComplete` 의 채팅 판 — 같은 함정·같은 해법).
- **한계 — quiescent restart 만**: chatRestart=tick60(채팅 정지 후). 활성 중 다운타임 + 재발행은 미검증(0020/0021 §9 잔존).
- **한계 — 스냅샷 비유계·단일 트리거**: 스냅샷이 *전체 라우팅 직렬화*(증분 0)·압축 트리거는 *고정 주기 N*만(0018 잔존 한계의 채팅 판). 다중 트리거·증분 스냅샷·스냅샷 손실 ack 미착수.
- **한계 — write-behind 윈도·persist 단일점**: 활성 중 죽음=in-flight 손실·ack/resend 없음(0017 잔존, 가장 큰 신뢰성 구멍)·chatpersist 단일점(fsync/복제 0).
