# step-0069 — 프레즌스 SSOT 질의 인터페이스(presenceQuery)

> 직전: [step-0068](step-0068.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0064~0068 이 프레즌스 박스를 *쓰기·발행·failover* 까지 세웠다. 이제 **읽기 경로** — 다른 박스가 "소비자 X 는 지금 어떤 상태인가"를 *질의*(pull)할 수 있는가? PresenceService 가 `{type:'presenceQuery', consumer}` 요청에 `{type:'presenceReply', consumer, state}`(state=`stateOf`=up/down/permanent)로 답한다. 발행(push)이 *전이 알림*이라면 질의(pull)는 *현재 상태 조회* — "누가 어디에" SSOT 의 단일 조회처(귓속말·파티·핸드오프 라우팅의 미래 기반·SPINE 계층 5). 닫는 조건: 질의↔응답 무손실(request/reply 닫힌 루프)·*구독 못 한* 소비자 상태도 pull 로 앎(독립 읽기 경로)·질의 비-침습(관측 행동 불변·원장 불변). presmon 이 첫 질의자.

## 2. 메커니즘 — request/reply 읽기 경로 (`presenceQuery` OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-presence.js`**: `onMsg` 에 `presenceQuery` 분기 — `{consumer}` 요청에 `stateOf(consumer)` 를 `presenceReply` 로 회신(`queriesRx`/`repliesSent` 1:1). 순수 읽기(SSOT 무변경). 질의 미수신이면 미발화 = 0068 비트 동일.
- **`src/svc-presence-monitor.js`**: presmon 에 질의자 추가 — `queryAddr`(SSOT 박스 주소·명시 의존)·`queryFor`(질의 소비자 목록). svc.presence 이벤트를 받을 때마다 `queryFor` 를 질의. `presenceReply` 수신→`queried` 맵 기록. `queryAddr` 없으면 미발화(비-침습 관찰형 유지). `constructor(opts)` 로 변경(팩토리가 `spec.opts` 전달).
- **`src/topo-build.js`**: `presenceQuery` opt. presmon 에 `queryAddr=presenceSvcAddr`·`queryFor=['ranking','inventory']`(관측 대상+미관측) 전달. 팩토리 `new PresenceMonitor(spec.opts)`.

|---|---|---|---|---|---|---|

- **질의↔응답 무손실**: presmon `queriesSent`(4 = 이벤트 2 × queryFor 2) == `repliesRecv` == 박스 `repliesSent` == 박스 `queriesRx` — request/reply 닫힌 루프.
- **관측 일치**: pull 로 받은 `queried['ranking']='permanent'` == 관측한 `stateOf('ranking')='permanent'`.
- **독립 읽기 경로**: `queried['inventory']='up'` *이지만* `stateOf('inventory')=null` — presmon 은 inventory 의 전이 이벤트를 *한 번도 못 받았는데도* 질의로 그 상태를 안다. 발행 구독과 직교한 pull 경로 증명.
- **비-침습**: 관측 행동(events/state/permCount) ON==OFF·`stateOf('ranking')='permanent'` 동일. OFF 는 질의 0·`queried` 빔. `minted` ON==OFF·원장 정합.
- **회귀 0**: `node run.js`(4기둥+E2E 14프로세스 비트동일)·`node run.js spine`(69-step src 누적 회귀) ALL OK. reg(키트·presenceQuery 미설정) = 0068 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **질의자가 박스 주소를 안다(0065 decouple 과 대비)**: 0065 는 orch→presence *보고*를 버스 토픽으로 올려 orch 가 박스 주소를 모르게 했다. 그러나 request/reply *질의*는 명시 주소가 필요하다(SPINE §4 경로3 = 요청/응답). presmon 이 `queryAddr` 를 명시 의존으로 갖는다 — 이는 보고(decouple)와 질의(명시 인터페이스)의 *의도된 다른 결합*이다. 미래엔 질의도 게이트웨이/세션 라우터가 단일 진입점으로 다중화(클라는 박스 주소 무지) 후속.
- **presmon 이 질의자 대역**: 진짜 질의 소비자는 *귓속말/파티 라우터*(클라가 X 에게 귓속말→라우터가 presence 에 X 상태 질의)다. 이 step 은 presmon(프레즌스 대시보드)을 질의자 대역으로 써 인터페이스를 증명 — 실제 라우팅 박스는 후속.
- **failover 와 질의 미교차**: 이 시나리오는 단일 active 박스에 질의(presenceFailover 없음). 승격된 standby 가 질의를 인계하는가(failover 중 읽기 연속성)는 미검증 — 후속.
