# step-0011 — 실 네트워크 소켓 전송 현실화: IPC 파이프 → 실 TCP 소켓 (와이어만 교체·실 전송 E2E)

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0011/net-core.js`(액터 **무수정 복사 전진**(0010 그대로) + 토폴로지 빌더 + `run`(인프로세스) + `runMulti`(멀티프로세스 위임, `opts.channel='ipc'|'tcp'`)) · `step-0011/cluster.js`(**broker** — engine Net 을 전송 substrate 로 소유 + **채널 추상**(`ChannelBase`→`IpcChannel`|`TcpChannel`) + lockstep 배리어) · `step-0011/host.js`(자식 프로세스 진입점 — `--ipc`=process IPC, `--tcp`=**순수 TCP 소켓**) · `step-0011/frame.js`(**길이-프리픽스 프레이밍** — broker·host 양쪽이 공유) · 헤드리스: `step-0011/verify.js` · 관찰: `step-0011.html`(+ `step-0011/panel.js`·`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **0010 이 host 태그 경계를 *실 OS 프로세스*로 분리하고 broker↔host 를 child_process IPC 파이프로 통신시켰다 — 그러나 전송은 아직 *로컬 IPC 파이프*였다(0010 §8.2: 실 네트워크 소켓 아님). 이 step 은 그 *와이어*를 *실 TCP 소켓*(`net.createServer`/`net.connect`, 127.0.0.1 임시 포트)으로 갈아끼운다. broker↔host RPC 를 *바꿔 끼울 수 있는* 채널 추상(`ChannelBase`) 뒤에 두고, `IpcChannel`(0010 그대로 — 와이어 OFF 기준)과 `TcpChannel`(이 step — 실 소켓)을 둔다. TCP 모드는 호스트를 *IPC 채널 없이* spawn 해(`stdio` 에 ipc 없음) 통신이 *오직 소켓*뿐이다. TCP 는 *바이트 스트림*이라 메시지 경계가 없으므로 — IPC 파이프가 OS 차원에서 보존해 주던 경계가 사라지므로 — `frame.js` 의 **길이-프리픽스 프레이밍**(`[4바이트 BE 길이][JSON]`)으로 경계를 *우리가* 재조립한다. 이것이 "실 네트워크 전송"이 IPC 파이프와 다른 가장 구체적인 지점이다. lockstep 배리어·액터·broker substrate 는 *무변경* — 와이어만 갈렸다.**
>
> **관찰(눈으로)**: `step-0011.html` 을 브라우저로 *그냥 열면* 프로세스 토폴로지가 뜬다 — 각 박스=독립 OS 프로세스, 선=프로세스 경계를 넘는 **소켓 프레임**(굵기=메시지 수), ✝사망 존·▲승격 추종자. 소켓 프레임 트래픽 타임라인에 사망(lease 끊김)·승격(keyframe 버스트) 세로선. (브라우저는 인프로세스 run() 만 그린다 — 실 소켓 멀티프로세스는 node verify.js 로.) 헤드리스 미리보기는 `node step-0011/panel.js [seed]`(ANSI 스파크라인).

step-0010 이 프로세스 경계를 *실 OS 프로세스*(child_process·공유 메모리 0)로 현실화했다 — 그러나 전송은 아직 *로컬 IPC 파이프*였고 broker 가 단일점이었다(0010 §8.2 🔴·[STATE.md](STATE.md) §3). 재정렬된 큰 목표는 *그림*이 아니라 *도는 인프라*다: 모든 서버가 headless 로 돌고, 서로 *실 네트워크 전송*으로 완전히 통신하며, 원격에서 E2E 로 검증되는 것([CLAUDE.md](CLAUDE.md) 큰 목표). 이 step 은 그 다음 한 조각 — *전송 seam 의 와이어*를 인메모리/IPC 에서 *실 TCP 소켓*으로 현실화한다. 0001~0010 의 프로토콜·토폴로지·복원·failover 는 *그대로* 두고, *와이어만* 교체한다([TOOLS.md](TOOLS.md) §2 버스·§6 transport seam). 전송 모델(0004)이 이미 substrate 에 살아 있으니([SPINE.md](SPINE.md) §3 씨앗 매핑 'NATS/Redpanda 로 현실화'), 새 직렬화·새 와이어 포맷이 아니라 *디스패치 채널*만 갈아끼우면 된다.

결과: **전 시드 전 항목 통과.** ① 회귀 0(`reg`) — 인프로세스 모드(와이어 OFF)면 0010 과 *비트 동일*(net.log 해시·상태, zones 1·2 · recovery off/on · failover off/on(+death) 전 조합 20/20). 채널 추상화 도입이 인프로세스 경로를 안 건드림. ② 실 전송 동치(`sock`) — 멀티프로세스가 *실 TCP 소켓*(길이-프리픽스 프레이밍)으로 통신해도 인프로세스와 *비트 동일*(logDigest·fullDigest)·승격 일치·desync 0. 대조로 IPC 와이어(0010)·TCP 와이어(0011) **둘 다 == 인프로세스**(basic 6 프로세스·transport 손실 0.2·failover 9 프로세스, 5 시드). ③ 프로세스 분리(`isolate`) — 각 서버가 *구분 pid*·broker 와 다름·통신은 *실 TCP 소켓*(broker listen 포트 + 호스트별 *구분 remote 포트* 9개·길이-프리픽스 프레임·공유 메모리 0·전 메시지 양방향 직렬화 가능). ④ 은닉(`hide`) — 실 소켓 전송(서버간) 후에도 클라 접점 공개 주소뿐·내부 누설 0. ⑤ 재현(`repro`) — 같은 시드 TCP 소켓 2회 같은 상태 + 인프로세스와도 동일(와이어 교체가 결정론을 안 깸; 더구나 fullDigest 가 *0010·0009 다이제스트와 일치*).

## 검증 질문

> ① **회귀 0**: 인프로세스 모드(와이어 교체 OFF)면 0010 동작과 비트 동일한가? (`reg`)
> ② **실 전송 동치**: 멀티프로세스가 *실 TCP 소켓*으로 통신해도 인프로세스와 같은 상태(나아가 비트 동일)인가? IPC·TCP 와이어 둘 다? (`sock`)
> ③ **프로세스 분리(소켓)**: 각 서버가 별 OS 프로세스에 살고 *실 TCP 소켓*(구분 remote 포트)으로만 통신하는가(공유 메모리 0·바이트 스트림 경계 재조립)? (`isolate`)
> ④ **원격 한 줄 기동**: `node verify.js` 한 줄이 broker 를 listen 시키고 전 프로세스를 띄워 소켓 연결·4기둥을 ALL OK 로 검증하는가? (전 모드)
> ⑤ **은닉·재현**: 실 소켓 전송 후에도 클라에 내부가 안 새고, 같은 시드 → 같은 결과인가? (`hide`·`repro`)

모든 수치는 시드 [42, 7, 1234, 99, 2026], `node step-0011/verify.js <mode> [seed]` (mode: reg | sock | isolate | hide | repro | all). 기본 시나리오: 클라 6 · 이동 30 · grid 16×16 · 분할 경계 x=8 · AOI 반경 4. sock/repro 의 failover 시나리오는 0009 그대로(80 tick·사망 40·leaseTimeout 3), basic 은 48 tick, transport 는 60 tick. reg 은 0010 대조라 48 tick·클라 4. **배치(placement)**: 0010 그대로(각 서버 박스 = 자기 프로세스, 클라는 한 호스트) — failover 시 9 프로세스 + broker. 와이어는 `channel` 로 선택(기본 `ipc`, verify 의 sock/isolate/hide/repro 는 `tcp`).

## 2. 메커니즘 — 와이어를 IPC 파이프에서 실 TCP 소켓으로 (이 step 의 한 조각)

```
 인프로세스(run): engine/Net 그대로 — 0010 비트 동일(reg 0). 와이어 교체 OFF.

 멀티프로세스(runMulti, channel='tcp'):
   ┌── broker(코디네이터, cluster.js) ──────────────────────────────────────────┐
   │  engine/Net 을 *전송 substrate* 로 소유(큐·seq·dedup·로그·전송 모델) — 0010 그대로     │
   │  채널 추상 ChannelBase 뒤: TcpChannel = net.createServer(127.0.0.1:임시포트)        │
   │  매 tick lockstep 배리어(*채널 무관* — channel.rpc(host,msg) 만 부름):              │
   │    ① deliver: due 메시지 → 원격 onMsg → 발신을 (전역 gi, 로컬 si)로 재정렬·재생         │
   │    ② tick:    전 액터 onTick → 발신 재정렬·재생 (engine step 의미 보존)               │
   └────────────────┬──────────────┬──────────────┬────────────── ... ──────────┘
        TCP 소켓(frame: [len32][JSON])  TCP            TCP                 (공유 메모리 0·IPC 채널 0)
   ┌────────▼─────┐ ┌──▼──────┐ ┌──▼──────┐
   │ host: gateway│ │host:zone1│ │host:orch │ ...  각 호스트 = 별 OS 프로세스(host.js --tcp)
   │  Gateway 액터 │ │ Zone 액터 │ │ Orch 액터 │      net.connect(broker 포트) → hello{hostId}
   └──────────────┘ └──────────┘ └──────────┘      FrameReader 로 바이트 스트림 경계 재조립
```

0010 대비 더한 것은 *와이어의 현실화*뿐 — 액터·프로토콜·failover·lockstep 배리어는 *그대로*:

1. **채널 추상(`ChannelBase`) — broker↔host RPC 를 *바꿔 끼울 수 있는* 이음새.** 0010 의 `Cluster`(fork + `child.send`/`on('message')`)가 하던 일을 *공통 골격*(`ChannelBase`: pending·reqId·계측·직렬화 검증·`init`/`snapshotAll`)으로 올리고, 와이어별 구현(`spawn`/`_deliver`/`shutdown`)만 서브클래스가 채운다. `IpcChannel`=0010 그대로(fork + process IPC), `TcpChannel`=실 소켓. **runMulti 루프는 채널 무관** — `ch.rpc(host,msg)` 만 부른다. 그래서 와이어를 갈아도 lockstep 배리어 코드는 한 줄도 안 변하고, broker.net.log 가 인프로세스와 비트 동일(실 전송 동치). reg 0 은 이 추상화 도입이 인프로세스 경로를 안 건드림을 증명(채널은 멀티프로세스에서만 산다).

2. **TcpChannel — 실 TCP 소켓 + 순수 소켓 분리.** broker 가 먼저 `127.0.0.1:0`(임시 포트)에 listen → 호스트를 *IPC 채널 없이* `spawn`(`stdio:['ignore','inherit','inherit']` — ipc 없음·`HKT_BROKER_PORT` env 로 포트 전달) → 각 호스트가 `net.connect(포트)` 로 broker 에 연결해 `hello{hostId,pid}` 로 자기를 식별(broker 가 소켓↔hostId 매핑). 통신은 *오직 TCP 소켓*뿐 — IPC 파이프가 아예 없다(진짜 소켓 분리). RPC(init/deliver/tick/snapshot/bye)는 전부 소켓 위 프레임으로 오간다.

3. **길이-프리픽스 프레이밍(`frame.js`) — 바이트 스트림에 경계를 다시 세운다.** IPC(0010)는 *메시지 경계*를 OS 가 보존해 줬다(한 `send` = 한 `message` 이벤트). 그러나 TCP 는 *바이트 스트림*이다 — 경계가 없다. 한 `write` 가 여러 청크로 쪼개져 도착하거나(부분 읽기), 여러 `write` 가 한 청크로 합쳐져(coalescing) 도착한다. 그래서 메시지 경계를 *우리가* 다시 세운다: 프레임 = `[4바이트 BE 길이][UTF-8 JSON]`. 수신측 `FrameReader` 는 청크를 모아 길이가 다 차면 한 메시지를 떼어내고 나머지는 버퍼에 보관한다. broker·host 양쪽 프로세스가 *같은 모듈*(`frame.js`)을 `require` — 와이어 포맷이 한 곳. 이게 "실 네트워크 전송"이 IPC 파이프와 다른 가장 구체적인 지점이다(0010 §8.2 → 0011 현실화).

> 클라는 여전히 게이트웨이만 안다 — 소켓 전송은 *서버간* 경계다. lease/promote/relink/reroute·핸드오프·ghost·증분이 전부 *프로세스 경계를 넘는 실 TCP 소켓 프레임*이 됐지만 클라엔 닿지 않는다(은닉 불변). `node verify.js` 한 줄이 broker 를 listen 시키고 전 프로세스를 띄워(원격에서) 소켓 연결로 같은 4기둥을 검증한다.

- 멀티프로세스 실행이 인프로세스와 *logDigest 비트 동일*(전 메시지 from>to:payload 스트림 일치) + *fullDigest 동일*(소유 존·클라 seen·승격 수) + 최종 desync 0 — **IPC 와이어(0010)·TCP 소켓 와이어(0011) 둘 다**. broker 의 lockstep 배리어가 *채널 무관*으로 전역 발신 순서를 보존하므로, 와이어가 실 소켓이 되어 바이트 스트림 경계를 재조립해도 *의미가 완전히 보존*됨을 증명 — 0001~0010 의 프로토콜·토폴로지·핸드오프·증분·복원·failover 가 실 소켓 너머로도 *그대로* 선다. **transport 시나리오**(손실 0.2·지연 0~2·중복 3)도 비트 동일 — 전송 모델이 broker substrate 에 살아 있어, 실 소켓 와이어 위에서도 0004 전송 열화가 인메모리와 동일하게 작동(와이어 교체가 전송 모델과 직교).

## 5. ③ 프로세스 분리(소켓) — `isolate`, 통과 (재정렬 목표의 본진)

**각 서버 = 구분 OS 프로세스·통신은 실 TCP 소켓 프레임뿐**(seed 42 failover, 9 호스트):

```
broker pid P0 · listen 127.0.0.1:35667 · 호스트 9개 · 구분 pid 9개 · 구분 소켓(remote 포트) 9개
소켓 와이어: out 1162프레임/377829B · in 1171프레임/310448B(실제 바이트=헤더4+본문) · 양방향 직렬화 가능 true
배치(addr → host → pid):
  login → login → pid Pa     gateway → gateway → pid Pc    zone1 → zone1 → pid Pd
  registry → registry → Pb   zone2 → zone2 → pid Pe        orch → orch → pid Pf
  zone1f → zone1f → pid Pg    zone2f → zone2f → pid Ph      client0..5 → clients → pid Pi
```

- 9 호스트가 *9개 구분 pid* 에 살고, 전부 broker(P0)와 *다른 프로세스*다 — 공유 메모리 0, **IPC 채널도 0**(`spawn` 시 stdio 에 ipc 없음). 통신은 *오직 실 TCP 소켓* — broker 가 `127.0.0.1` 임시 포트에 listen, 각 호스트가 *구분되는 remote 포트* 9개로 연결(진짜 소켓 9개). 경계를 넘는 *모든* 프레임이 *양방향으로* 직렬화 가능(out 1162프레임/378KB · in 1171프레임/310KB — 바이트 수는 *실제 와이어 바이트*=길이 헤더 4 + 본문, 함수·심볼·순환·공유 참조 0). 클라(엣지)는 한 호스트에 묶고 서버 박스는 박스당 1 프로세스 — 목표 토폴로지와 일치. pid·포트는 실행마다 바뀌나 *구분성·broker 와의 분리*는 불변.

## 6. ④ 원격 한 줄 기동 · ⑤ 은닉 · 재현 — `hide`·`repro`, 통과

**원격 한 줄 기동(전 모드)** — `node step-0011/verify.js all` 한 줄이 (이 환경/CI 에서) broker 를 띄워 `127.0.0.1` 에 listen 시키고, broker 가 자식 프로세스를 spawn → 자식이 *실 TCP 소켓*으로 연결·init·구동·검증·정리한다. 로컬 엔진·특정 머신 비종속 — 척추 ⑤ 의 충족(전 4기둥 ALL OK, ~10s).

**은닉(`hide`)** — 전 시드: 실 소켓 전송(서버간) 후에도 클라 접점이 공개 주소(login·gateway)뿐, view_delta·keyframe 에 내부 토폴로지(zone/sessionId/handoff/ghost/lease/promote/orch) 누설 **0**, 뷰 받은 클라 4/4. 와이어가 실 소켓이 돼도 클라는 내부 토폴로지·프로세스 경계·소켓 포트를 모른다.

**재현(`repro`)** — 같은 시드 TCP 소켓 2회 → 같은 fullDigest, *인프로세스와도 동일*(와이어 교체가 결정론을 안 깸, `Math.random` 0): 42=0x14c8832e · 7=0xdb11d37e · 1234=0x13a96ce7 · 99=0x295569a2 · 2026=0x22f23174. **이 다이제스트는 0010·0009 의 repro 와 *완전히 일치*** — TCP 소켓 상태가 IPC·인프로세스 상태와 비트 동일이라는 교차 검증(0009→0010→0011 비트 사슬).

## 척추 체크 5항 ([SPINE.md](SPINE.md) §5)

1. **신성한 tick ✅** — 액터 로직 *무변경*(0010 그대로) — 존 tick 안엔 위치 갱신·핸드오프·ghost·증분·lease 만(I/O·인증·트랜잭션 0). broker·채널은 *전송 substrate/와이어* 일 뿐 — tick 안에 시뮬 외 작업을 넣지 않았다. HostNet send 는 버퍼링(메모리)뿐, 소켓 write 는 broker 회수 응답 한 번뿐.
2. **결정론 코어 🟡** — 액터는 시드 의사난수만(`Math.random` 0). 와이어가 갈려도 같은 입력열 → 같은 상태(실 전송 동치 — logDigest·fullDigest 비트 동일). broker lockstep 배리어가 전역 발신 순서를 보존(채널 무관·타이밍↔내용 분리, 0004 계승). 비트-결정론 복제는 여전히 C++ 승격의 일([STATE.md](STATE.md)).
3. **권위 단일 소유 🟡** — 0010 불변(무사망/사망 후 소유자=1·이중쓰기 0·failover bounded gap→회복)이 *실 소켓 전송 너머로도* 보존(sock: 승격 1·desync 0·full 비트 동일). 권위는 여전히 메시지(release+acquire·promote)로만 이동 — 와이어 교체가 권위 장부를 안 건드린다.
4. **은닉·단일 연결 ✅** — 클라는 게이트웨이만. 소켓 전송은 *서버간* 경계 — lease/promote/핸드오프/ghost 가 실 TCP 프레임이 됐어도 클라는 keyframe(view_delta reset)만 본다. 내부·프로세스 경계·소켓 포트 누설 0(`hide`).
5. **headless·원격 검증 ✅ (이 step 의 핵심)** — 전 서버가 UE/GUI 없이 별 OS 프로세스로 빌드·실행되고, `node verify.js` 한 줄이 원격(이 환경)에서 broker 를 listen 시켜 전 프로세스를 띄우고 *실 TCP 소켓으로 완전히 통신*하며 4기둥을 수치 증명(ALL OK). 어떤 박스도 로컬 엔진·특정 머신에 안 묶인다.

## 7. 의외의 발견

1. **와이어 교체가 *비트 동일* — 바이트 스트림 재조립이 동작뿐 아니라 비트까지 비-침습이다.** IPC 파이프(메시지 경계 보존)에서 TCP 소켓(바이트 스트림·경계 없음)으로 가면 보통 *프레이밍 버그*(부분 읽기·합본)가 순서·내용을 흔든다. 그런데 여기선 실 소켓 실행이 인프로세스와 *logDigest 비트 동일*까지 간다. 비결: ⒜ broker lockstep 배리어가 *채널 무관*이라 — `ch.rpc(host,msg)` 만 부르고 reqId 로 응답을 매칭 — 와이어가 뭐든 전역 발신 순서가 보존된다. ⒝ TCP 의 *순서 보장*(같은 소켓의 바이트는 in-order)을 길이-프리픽스 프레이밍이 그대로 메시지 순서로 옮긴다. "실 네트워크면 비결정"이라는 통념과 정반대 — *결정론 배리어 + 신뢰성 순서 전송(TCP)* 이 와이어 교체를 비트까지 투명하게 만든다.
2. **와이어 교체에 액터·배리어 코드 0줄 — 채널 추상이 *이미 거기 있을* 자리였다.** 0010 의 `Cluster` 가 이미 `rpc(host,msg)→Promise` 라는 *동기 RPC 모양*의 인터페이스였다(deliver/tick/snapshot). 그래서 그 뒤를 `ChannelBase` 로 일반화하고 와이어만 `IpcChannel`/`TcpChannel` 로 가르니, runMulti 루프(lockstep 배리어)는 *한 줄도* 안 변했다. 와이어 교체가 한 step 에 들어온 건 0010 이 이미 *전송을 RPC 이음새 뒤에* 두었기 때문 — 0010 §2 의 'channel.rpc 만 부른다' 설계가 0011 의 디딤돌이 됐다("씨앗=계약의 첫 구현"의 또 한 겹).
3. **IPC 가 *공짜로* 해주던 것 = 메시지 프레이밍. 그게 실 네트워크와의 진짜 차이다.** "프로세스를 나눴다"(0010)와 "실 네트워크로 통신한다"(0011)의 차이는 흔히 *지연·분단* 으로 오해되지만, 가장 먼저 부딪히는 구체적 차이는 *메시지 경계*다. child_process IPC 는 한 `send`=한 `message` 이벤트로 경계를 OS 가 보존했다 — 그래서 0010 은 프레이밍을 *전혀* 신경 쓸 필요가 없었다. TCP 는 그 보장을 안 준다(바이트 스트림). 실 네트워크 전송의 *첫 세금*은 지연이 아니라 **프레이밍**이고, 이 step 은 그 세금을 길이-프리픽스로 정확히 냈다(이후 지연·분단·재연결은 이 프레임 위에 선다).
4. **transport 시나리오(0004 전송 모델)가 실 소켓 위에서도 *그대로* — 모델 전송과 와이어 전송이 직교한다.** broker 가 substrate 에 입히는 전송 열화(지연·손실·재정렬·중복, 0004)는 *논리적*(큐 enqueue tick 조작)이고, 와이어(IPC/TCP)는 *물리적*(프로세스 간 운반)이다. 둘이 직교하므로, 실 TCP 소켓 위에서도 transport 시나리오가 인메모리와 비트 동일하게 손실 패턴을 재현했다(sock transport 행). 즉 *모델된 네트워크 열화*와 *실 와이어*가 한 substrate 에 공존 — 다음 step 에서 실 네트워크 열화(실 지연·분단)를 와이어 층에 넣을 때 이 분리가 토대가 된다.

## 8. 정직한 한계

1. **TCP 지만 *로컬 루프백*(127.0.0.1) — 실 네트워크 *분단·재연결·WAN 지연/MTU* 아님.** 경계는 진짜 OS 소켓·진짜 바이트 스트림·진짜 길이-프리픽스 프레이밍·공유 메모리 0 이지만, 전송 경로는 로컬 루프백이다 — 머신 간 실 네트워크(TCP RTT·패킷 분단·소켓 재연결·half-open)는 안 탔다([TOOLS.md](TOOLS.md) §2). 0004 의 전송 모델(지연·손실·재정렬)이 substrate 에 살아 transport 시나리오로 *모델된* 열화는 검증했으나, 와이어 층의 *실* 네트워크 열화·재연결 복원은 후속.
2. **broker 단일점 + lockstep 배리어 = 중앙 코디네이터(결정론의 대가).** 실 소켓이 됐어도 broker 는 여전히 전송·배리어의 단일점이고, 매 tick 전 호스트를 동기화한다. 상용은 broker 대신 *pub/sub 버스*(NATS/Redpanda)가 그 자리를 분산으로 채운다 — 서버간 N×N 직접 결합 제거([TOOLS.md](TOOLS.md) §2·§5). 이는 *원격 검증용 결정론 하니스*이지 자유 실행(비동기·실시간)이 아니다([STATE.md](STATE.md) §2 후속).
3. **사망 = 액터 무동작(진짜 소켓 끊김/kill 아님).** 0009 의 사망을 *액터 무동작*(deathTick 후 onTick/onMsg 정지)으로 유지했다 — reg/sock 비트 동일을 위해(진짜 `socket.destroy()`·`child.kill()` 은 비결정·배리어 교란). 진짜 소켓 단절 감지·재연결·죽은 호스트 재배선은 *강력한 데모*이나 결정론 검증과 긴장 — 후속.
4. **클라가 한 호스트에 묶임 · 정적 배치(0010 상속).** 클라(엣지)는 한 'clients' 호스트, 배치(addr→host)는 정적이다 — 동적 재배치·오토스케일·게이트웨이 군·존 샤딩은 후속.
5. **여전히 Node · C++ 시뮬 코어 미교체 · 존↔존 ghost 미착수(0006~0010 상속).** 전 박스가 Node 프로세스다 — 월드 박스의 C++ 결정론 시뮬 코어 교체([STATE.md](STATE.md) §3 🔴)는 여전히 선결 후속. 이 step 은 *와이어*를 현실화했지 *시뮬 언어*를 바꾸지 않았다 — 동결 `ISimCore` seam·정적 2 존 그대로다.
