# step-0011 — 실 네트워크 소켓 전송 현실화: child_process IPC 파이프 → 실 TCP 소켓 (와이어 현실화·원격 멀티프로세스 E2E)

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0011/net-core.js`(액터·토폴로지 빌더 **무수정 복사 전진**(0010 그대로) + `run`(인프로세스=engine Net) + 옵션 `onTick` 훅(reg-safe) + `runMulti`(멀티프로세스 위임)) · `step-0011/cluster.js`(**broker** — *TCP 서버*로 떠서 engine Net 을 전송 substrate 로 소유, **lockstep 배리어**로 원격 onMsg/onTick 디스패치·발신 회수, *길이-프리픽스 프레이밍*) · `step-0011/host.js`(자식 프로세스 진입점 — `child_process.spawn`(*IPC 채널 0*)으로 떠서 broker 의 TCP 포트로 역연결 + **HostNet shim**) · 헤드리스: `step-0011/verify.js` · 관찰: `step-0011/panel.js`(+`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **step-0010 은 각 서버 박스를 별 OS 프로세스(`child_process.fork`)로 분리하고 *fork 의 IPC 채널*(파이프·메시지 프레임 내장)로 통신시켜 프로세스 경계를 현실화했다 — 그러나 전송은 아직 *로컬 IPC 파이프*였고(실 네트워크 소켓 아님), fork 의 메시지-프레임 IPC 라 *TCP 스트림 재조립* 같은 실 와이어 문제를 우회했다(0010 §8.2·[STATE.md](STATE.md) §3 🔴). 이 step 은 그 와이어를 *실 TCP 소켓*으로 갈아끼운다([TOOLS.md](TOOLS.md) §2 버스·§6 transport seam). 인프로세스 모드(`run`)는 engine Net 그대로라 0010 와 *비트 동일*(reg 0). 멀티프로세스 모드(`runMulti`)는 각 서버 박스를 `child_process.spawn`(*IPC 채널 0*)으로 띄우고, broker(TCP 서버)와 *실 TCP 소켓*으로 연결해 *길이-프리픽스 프레이밍*된 JSON 메시지로만 onMsg/onTick 을 원격 디스패치한다 → broker.net.log 가 인프로세스와 *비트 동일*(실 소켓 위에서도 E2E 동치). 액터 로직·프로토콜·배리어는 *무변경* — *와이어만* 교체.** 클라는 여전히 게이트웨이만 — 소켓 분리는 *서버간* 경계(은닉).
>
> **관찰(눈으로)**: 헤드리스 미리보기는 `node step-0011/panel.js [seed]`(ANSI 스파크라인 — 프로세스 경계 소켓 와이어 트래픽·사망/승격 세로선). 전체 흐름 시각화는 `node run.js report`(현재 step 을 실 멀티프로세스 *녹화* → 자기완결 `report.html`). 시각화는 단일 testbed 로 일원화([TESTBED.md](TESTBED.md)).

step-0010 이 프로세스 경계를 현실화했다 — 각 서버가 별 OS 프로세스(fork)·공유 메모리 0·E2E 비트 동일. 그러나 전송은 *로컬 IPC 파이프*였다(0010 §8.2 🔴). 재정렬된 큰 목표는 *모든 서버가 원격에서 빌드·통신·검증되는 도는 인프라*이고([CLAUDE.md](CLAUDE.md) 큰 목표), 그 통신은 궁극적으로 *실 네트워크 전송*(소켓·버스)이어야 한다([TOOLS.md](TOOLS.md) §2). 이 step 은 그 와이어를 친다 — fork 의 내장 IPC 채널을 *실 TCP 소켓*(`net.createServer`/`net.connect`)으로 현실화하고, TCP 가 바이트 스트림이라는 첫 현실 문제를 *길이-프리픽스 프레이밍*으로 푼다. 0001~0010 의 프로토콜·토폴로지·복원·failover·lockstep 배리어는 *그대로* 두고, *와이어*(broker↔host RPC 전송)만 교체한다.

결과: **전 시드 전 항목 통과.** ① 회귀 0(`reg`) — 인프로세스 모드(와이어 OFF)면 0010 와 *비트 동일*(net.log 해시·상태, zones 1·2 · recovery off/on · failover off/on(+death) 전 조합 20/20) ② E2E 동치(`e2e`) — 멀티프로세스(각 서버 별 OS 프로세스·*실 TCP 소켓*) 실행이 인프로세스와 *비트 동일*(logDigest·fullDigest)·승격 수 일치·최종 desync 0(basic 6 프로세스·failover 9 프로세스, 5 시드·transport 손실 시나리오 포함) ③ 실 와이어(`wire`) — 전송이 *실 TCP 소켓*(net)·*길이-프리픽스 프레이밍*·fork IPC 채널 0(spawn)이고, 프레이밍이 *바이트 단위 분할·병합·임의 경계*에서 메시지를 정확히 재조립(스트림 복원) ④ 프로세스 분리(`isolate`) — 각 서버가 *구분되는 OS 프로세스*(pid)·broker 와도 다름·통신은 *실 TCP 소켓 프레임뿐*(공유 메모리 0·양방향 직렬화 가능 true) ⑤ 은닉(`hide`)·재현(`repro`) — 서버간 소켓 후에도 클라 접점 공개 주소뿐·누설 0, 같은 시드 멀티프로세스 2회 같은 상태 + 인프로세스와도 동일(더구나 fullDigest 가 *0010 과 비트 동일*).

## 검증 질문

> ① **회귀 0**: 인프로세스 모드(와이어 교체 OFF)면 0010 동작과 비트 동일한가? (`reg`)
> ② **E2E 동치**: 멀티프로세스(실 TCP 소켓) 실행이 인프로세스와 같은 상태(나아가 비트 동일)인가? (`e2e`)
> ③ **실 와이어**: 전송이 진짜 TCP 소켓·직접 프레이밍(스트림 재조립)이고 fork IPC 채널 0 인가? (`wire`)
> ④ **프로세스 분리·원격 한 줄 기동**: 각 서버가 별 OS 프로세스에 살고 실 소켓으로만 통신하며, `node verify.js` 한 줄이 전 프로세스를 TCP 소켓으로 묶어 4기둥을 ALL OK 로 검증하는가? (`isolate`·전 모드)
> ⑤ **은닉·재현**: 소켓 분리 후에도 클라에 내부가 안 새고, 같은 시드 → 같은 결과인가? (`hide`·`repro`)

모든 수치는 시드 [42, 7, 1234, 99, 2026], `node step-0011/verify.js <mode> [seed]` (mode: reg | e2e | wire | isolate | hide | repro | all). 기본 시나리오: 클라 6 · 이동 30 · grid 16×16 · 분할 경계 x=8 · AOI 반경 4. e2e/repro 의 failover 시나리오는 0009~0010 그대로(80 tick·사망 40·leaseTimeout 3), basic 은 48 tick. reg 은 0010 대조라 48 tick·클라 4. **배치(placement)**: 각 서버 박스 = 자기 프로세스(login·registry·gateway·zone1·zone2·orch·zone1f·zone2f), 클라는 한 호스트(엣지) — failover 시 9 프로세스 + broker. 사망은 0009~0010 모델 그대로(deathTick 이후 존 무동작) — *진짜 프로세스 kill* 은 후속(§8-3). broker 는 단일 TCP 코디네이터로 유지 — *버스 분산*(broker 단일점 해소)은 후속(§8-2).

## 2. 메커니즘 — 와이어를 IPC 파이프에서 실 TCP 소켓으로 (이 step 의 한 조각)

```
 인프로세스(run): engine/Net 그대로 — 0010 비트 동일(reg 0). 와이어 교체 OFF.
   buildTopology(opts) → 선언적 spec[] → makeActor → engine Net.register → net.step() 루프(0010 그대로)
   (+ 옵션 onTick(t, state) 훅 — 미제공이면 호출 0 → reg 0 불변. 레코더 per-tick 위치·AOI 활성용)

 멀티프로세스(runMulti): host 태그 = 실 프로세스 경계 + 실 TCP 소켓 와이어
   ┌── broker(코디네이터, cluster.js) = TCP 서버(net.createServer, ephemeral 포트) ───────────┐
   │  engine/Net 을 *전송 substrate* 로 소유(큐·seq·dedup·로그·전송 모델) — 액터는 원격(자식 프로세스)    │
   │  매 tick lockstep 배리어(engine step() 의미를 비동기 소켓 RPC 로 재현 — 0010 과 동일 로직):       │
   │    ① deliver: due 메시지를 호스트별로 묶어 원격 onMsg → 발신을 (전역 gi, 로컬 si)로 재정렬·재생       │
   │    ② tick:    전 액터 onTick(등록 순서) → 발신 (gi=등록idx, si)로 재정렬·재생                     │
   │    deliver 발신은 항상 tick 발신보다 먼저(engine step 의 deliver→onTick 순서 보존)                │
   │  와이어: 길이-프리픽스 프레이밍([4B BE 길이][UTF-8 JSON]) — TCP 바이트 스트림에서 메시지 경계 복원        │
   └────────┬─────────────────┬─────────────────┬────────────── ... ────────────────────────┘
       실 TCP 소켓        실 TCP 소켓         실 TCP 소켓           (공유 메모리 0 · fork IPC 채널 0)
   ┌────────▼─────┐ ┌──────▼───┐ ┌──────▼───┐
   │ host: gateway│ │host:zone1│ │host:orch │ ...  각 호스트 = child_process.spawn(IPC 0) 으로 뜬 별 OS 프로세스
   │  Gateway 액터 │ │ Zone 액터 │ │ Orch 액터 │      net.connect(brokerPort) 역연결 · HostNet shim(send 버퍼링)
   └──────────────┘ └──────────┘ └──────────┘      onMsg/onTick 실행 → 발신 회수 → broker 가 재생
```

0010 대비 더한 것은 *와이어의 현실화*뿐 — 액터·프로토콜·배리어·failover 는 *비트 그대로*:

1. **broker = TCP 서버 + 호스트 역연결.** broker 는 `net.createServer` 로 ephemeral 포트(`listen(0)`)에 떠서, 각 호스트가 `net.connect(brokerPort)` 로 *역연결*하면 첫 프레임(hello)으로 hostId·pid 를 식별해 매핑한다. broker↔host RPC(init/deliver/tick/snapshot/bye)는 이 소켓으로만 흐른다 — broker.net(engine Net)은 *게임 메시지 전송 substrate*(0004 모델), 소켓은 *broker↔host 디스패치 와이어*로 *층이 다르다*(전송 모델 ≠ 소켓 와이어).

2. **host = `child_process.spawn`(IPC 채널 0).** 0010 은 `fork`(내장 IPC 채널)였다 — 이 step 은 `spawn` 으로 띄워 *IPC 채널을 만들지 않는다*. 유일한 통신 경로가 TCP 소켓이다(broker 포트를 argv 로 받아 역연결). 그래서 "통신은 실 소켓뿐"이 *구조적*으로 참 — `process.send`/`process.on('message')` 가 아예 없다.

3. **길이-프리픽스 프레이밍 — TCP 스트림 재조립.** fork 의 IPC 는 메시지 경계를 내장하지만, TCP 는 *바이트 스트림*이라 한 `write` 가 여러 `data` 청크로 쪼개지거나 여러 메시지가 한 청크에 뭉칠 수 있다. `[4바이트 BE 길이][UTF-8 JSON]` 프레이밍 + 누적 `Framer`(청크가 헤더·페이로드 중간에서 끊겨도 안전)로 메시지 경계를 정확히 복원한다 — 실 와이어의 *첫 현실 문제*를 직접 푼 것(`wire` 모드가 바이트 단위 분할까지 검증).

4. **배리어·발신 순서 보존은 0010 그대로.** lockstep 배리어(deliver→onTick·(gi, si) 정렬 재생)는 *전송 무관* — RPC 가 fork IPC 든 TCP 소켓이든 broker 가 발신을 전역 순서로 재조립하므로 broker.net.log 가 인프로세스와 비트 동일. 와이어 교체가 결정론·동치를 *건드리지 않는다*(소켓 async ↔ 결정론 직교).

> 클라는 여전히 게이트웨이만 안다 — 소켓 분리는 *서버간* 경계다. lease/promote/핸드오프/ghost/증분이 전부 *실 TCP 소켓을 넘는 프레임*이 됐지만 클라엔 닿지 않는다(은닉 불변). `node verify.js` 한 줄이 broker(TCP 서버)를 띄우고 9 자식 프로세스를 spawn·소켓 연결·구동·검증한다 — 제1 운영 제약의 충족(원격·헤드리스).

- 멀티프로세스 실행이 인프로세스와 *logDigest 비트 동일*(전 메시지 from>to:payload 스트림 일치) + *fullDigest 동일* + 최종 desync 0. broker 가 전역 발신 순서를 보존하므로 *실 TCP 소켓 와이어가 의미를 완전히 보존*함을 증명 — 0001~0010 의 프로토콜·토폴로지·핸드오프·증분·복원·failover 가 실 소켓 너머로도 *그대로* 선다. **transport 시나리오**(손실 0.2·지연 0~2·중복 3)도 비트 동일 — 게임-층 손실은 broker 의 engine Net 이 결정론적으로 주입(전송 모델 ≠ 소켓 와이어, *층 분리*), 실 소켓 RPC 는 TCP 신뢰 전송이라 무손실. failover(사망 40·승격) 9 프로세스 — 제어 평면(lease/promote)이 소켓을 넘어도 승격 1·desync 0.

## 5. ③ 실 와이어 — `wire`, 통과 (이 step 의 한 조각)

**전송 = 실 TCP 소켓·길이-프리픽스 프레이밍·fork IPC 0**(seed 42 failover):

```
broker TCP :44999 · 와이어 tcp-socket · 프레임 out 1162/398491B · in 1171/330949B · 양방향 직렬화 true
프레이밍 재조립: 1바이트분할 OK · 병합 OK · 임의경계 OK (4 프레임)
```

- broker 가 *실 TCP 포트*(ephemeral, 실행마다 다름)에 떠서 호스트 역연결을 받는다 — 와이어 메타 `tcp-socket`. broker→host out 1162 프레임/398KB · host→broker in 1171 프레임/331KB(소켓 와이어 바이트 — 프레임 헤더·hostId 포함이라 0010 의 IPC payload 바이트와 다르나 *프레임 수 1162 는 동일* = 디스패치 로직 불변). **프레이밍 재조립 단위 검증**: 4개 대표 메시지(hello·deliver·view_delta·snapshot)를 한 버퍼로 이어붙여 ⒜ *1바이트씩* 흘려 넣어도(부분 헤더 포함 가혹 분할) ⒝ 전체를 한 청크로 뭉쳐도 ⒞ 임의 경계(헤더·페이로드 중간)에서 끊어도 — 전부 원본과 *정확히* 일치 재조립. fork 의 메시지-프레임 IPC 가 아니라 *실 TCP 바이트 스트림 + 직접 프레이밍*임의 증명.

## 6. ④ 프로세스 분리 · ⑤ 은닉 · 재현 — `isolate`·`hide`·`repro`, 통과

**프로세스 분리(`isolate`)** — 각 서버 = 구분되는 OS 프로세스·통신은 실 TCP 소켓 프레임뿐(seed 42 failover, 9 호스트):

```
broker pid P0(TCP :Pn) · 호스트 9개 · 구분 pid 9개 · 소켓 out 1162프레임/398491B · in 1171프레임/330949B · 양방향 직렬화 true
배치(addr → host → pid): login·registry·gateway·zone1·zone2·orch·zone1f·zone2f 각 1 프로세스 · client0..5 → clients 1 프로세스
```

- 9 호스트가 *9개 구분 pid* 에 살고 전부 broker(P0)와 *다른 프로세스*다 — 공유 메모리 0(별 OS 프로세스·별 주소공간·fork IPC 채널 0). 경계를 넘는 *모든* 소켓 프레임이 *양방향으로* 직렬화 가능(JSON round-trip, 함수·심볼·순환·공유 참조 0). pid·포트는 실행마다 바뀌나 *구분성·broker 와의 분리·소켓-only 통신*은 불변.

**원격 한 줄 기동(전 모드)** — `node step-0011/verify.js all` 한 줄이 (이 환경/CI 에서) broker(TCP 서버)를 띄우고 9 자식 프로세스를 spawn·소켓 연결·init·구동·검증·정리한다. 로컬 엔진·특정 머신 비종속 — 척추 ⑤ 의 충족(전 4기둥 ALL OK).

**은닉(`hide`)** — 전 시드: 멀티프로세스(서버간 소켓) 후에도 클라 접점이 공개 주소(login·gateway)뿐, view_delta·keyframe 에 내부 토폴로지(zone/sessionId/handoff/ghost/lease/promote/orch) 누설 **0**, 뷰 받은 클라 4/4. 소켓이 갈려도 클라는 내부 토폴로지·소켓 경계를 모른다.

**재현(`repro`)** — 같은 시드 멀티프로세스 2회 → 같은 fullDigest, *인프로세스와도 동일*(실 소켓이 결정론을 안 깸, `Math.random` 0): 42=0x14c8832e · 7=0xdb11d37e · 1234=0x13a96ce7 · 99=0x295569a2 · 2026=0x22f23174. **이 다이제스트는 0010(나아가 0009)의 failover repro 와 *완전히 일치*** — 와이어가 실 소켓이 돼도 상태가 *비트 동일*이라는 교차 검증.

## 척추 체크 5항 ([SPINE.md](SPINE.md) §5)

1. **신성한 tick ✅** — 액터 로직 *무변경*(0010 그대로). broker 는 *전송 substrate* 일 뿐, 와이어가 소켓이 돼도 tick 안에 시뮬 외 작업 0. HostNet send 는 버퍼링(메모리)뿐 — 소켓 write 는 broker 가 회수해 배리어 밖에서.

4. **은닉·단일 연결 ✅** — 클라는 게이트웨이만. 소켓 분리는 *서버간* 경계 — lease/promote/핸드오프/ghost 가 소켓 프레임이 됐어도 클라는 keyframe(view_delta reset)만 본다. 내부·소켓 경계 누설 0(`hide`).
5. **headless·원격 검증 ✅ (이 step 의 핵심)** — 전 서버가 UE/GUI 없이 별 OS 프로세스로 빌드·실행되고, `node verify.js` 한 줄이 원격(이 환경)에서 전 프로세스를 *실 TCP 소켓*으로 묶어 서로 직렬화 프레임으로 완전히 통신하며 4기둥을 수치 증명(ALL OK). 와이어가 실 소켓이라 *다른 머신으로의 이전*이 한 발 더 가까워졌다(localhost → 원격 호스트는 주소만 교체).

## 7. 의외의 발견

1. **와이어 교체가 *비트 동일*까지 비-침습이다 — 결정론은 *순서*의 함수지 *전송*의 함수가 아니다.** IPC 파이프 → 실 TCP 소켓은 전송 의미(신뢰·순서·프레이밍)가 다른데도 멀티프로세스 실행이 인프로세스와 *logDigest 비트 동일*까지 간다. 비결은 0010 의 *lockstep 배리어가 전송과 직교*하다는 것 — broker 가 발신을 (전역, 로컬) 순서로 재조립하므로, RPC 가 fork IPC 든 TCP 소켓이든 결과 스트림이 같다. "전송을 바꾸면 결과가 흔들린다"는 통념과 반대 — *순서 보존 배리어*가 와이어에 비트 투명하다. (repro 다이제스트가 0010·0009 와 정확히 일치 = 교차 증거.)
2. **TCP 스트림 재조립이 fork 가 숨긴 *실 와이어의 첫 현실 문제*였다.** fork 의 IPC 는 메시지 경계를 내장해 "한 send = 한 message" 가 공짜였다 — 그래서 0010 은 프레이밍을 *우회*했다. 실 소켓으로 내려가자 TCP 가 바이트 스트림이라 *프레이밍*이 강제됐다(한 write 가 쪼개지고 여러 메시지가 뭉친다). 길이-프리픽스 + 누적 Framer 한 조각으로 풀렸고, `wire` 모드의 1바이트 분할 검증이 이를 못 박는다 — *실 네트워크로 내려갈수록 와이어 책임이 늘어난다*는 실증(다음은 분단·재연결·MTU).
3. **`fork` → `spawn` 전환이 "소켓-only" 를 *구조적*으로 만든다.** fork 를 쓰면 IPC 채널이 *자동으로* 붙어 "소켓으로만 통신"을 *규율*로만 지킬 수 있다. `spawn`(IPC 0)으로 바꾸자 `process.send` 자체가 없어 — 소켓 외 통신이 *물리적으로 불가능*해졌다. 은닉·단일 연결 원칙([SPINE.md](SPINE.md) §5)을 *코드 규율*이 아니라 *런타임 구조*로 강제한 셈(0010 의 "공유 메모리 0" 가 주소공간 분리로 강제됐듯).
4. **전송 모델(게임-층 손실)과 소켓 와이어가 *깨끗이 두 층*으로 산다.** transport 시나리오(손실 0.2)가 실 소켓 위에서도 비트 동일인 이유: 게임-층 손실·지연·재정렬은 broker 의 engine Net(0004 모델)이 *결정론적으로 시뮬*하고, broker↔host 소켓은 *신뢰 전송*(TCP)이다. 두 층이 섞이지 않아 — "실 네트워크 열화"(소켓 분단·재연결)는 *소켓 층*에서, "게임 전송 모델"은 *substrate 층*에서 — 다음 step 이 소켓 층 열화를 더해도 substrate 층은 불변이다.

## 8. 정직한 한계

1. **broker lockstep 배리어 = 중앙 코디네이터(결정론의 대가). 진짜 비동기·실시간 아님.** 0010 §8.1 그대로 — 와이어가 실 소켓이 돼도 broker 가 전 프로세스를 tick 배리어로 묶는다. 매 tick 전 호스트의 deliver/tick 응답을 기다린다(소켓 RPC 왕복). 진짜 비동기 아래의 결정론(논리 클럭·인과 순서)은 후속.
2. **broker 단일점 + localhost·신뢰 소켓(버스 분산·실 네트워크 열화 아님).** 와이어는 *실 TCP 소켓*이지만 ⒜ broker 가 여전히 *단일 코디네이터*다 — 상용은 그 자리를 *pub/sub 버스*(NATS/Redpanda)가 분산으로 채운다(미착수, [TOOLS.md](TOOLS.md) §2). ⒝ 소켓은 *localhost*·TCP *신뢰 전송*이라 *실 네트워크 열화*(지연·**분단**·**재연결**·MTU·패킷 유실)는 아직 안 탔다 — 주소만 원격으로 바꾸면 다른 머신 이전은 되나, 분단·재연결 *내성*(권위 보존·desync 0)은 미검증. ⒞ 게임-층 전송 모델(0004)이 substrate 에 살아 손실 시나리오는 검증하나, *소켓 층* 분단은 별개. **버스 분산 + 실 네트워크 열화 내성**이 가장 유력한 다음(§9·[STATE.md](STATE.md) §2).
3. **진짜 프로세스 kill 아래 failover 아님.** 0009~0010 의 사망을 *액터 무동작*(deathTick 후 onTick/onMsg 정지)으로 유지했다 — reg/e2e 비트 동일을 위해. 진짜 `child.kill()`·소켓 끊김 감지·재배선·재-provisioning(거짓 사망·split-brain 펜싱)은 후속(0010 §8.3).
4. **클라가 한 호스트에 묶임 · 정적 배치.** 0010 §8.4 그대로 — 클라(엣지)는 한 'clients' 호스트, 배치(addr→host)는 정적. 동적 재배치·게이트웨이 군·존 샤딩(N 프로세스)은 후속.
5. **여전히 Node · C++ 시뮬 코어 미교체.** 전 박스가 Node 프로세스다 — 월드 박스의 C++ 결정론 시뮬 코어 교체(UE-모듈-free·헤드리스 shim, [STATE.md](STATE.md) §3 🔴)는 선결 후속. 이 step 은 *와이어*를 현실화했지 *시뮬 언어*를 바꾸지 않았다.
6. **존↔존 ghost·동적 경계·존 N개는 여전히 미착수(0006~0010 상속).** 이 step 은 *와이어*만 더했다.
7. **testbed 마무리 3건 중 onTick 만 착수.** STATE §2 가 새 템플릿에 넣자고 한 3건(⒜ `onTick` 훅 ⒝ verify `scenario` 모드 ⒞ scenario `inject`) 중 ⒜만 reg-safe 훅으로 net-core 에 심었다(레코더 per-tick 위치·AOI 활성의 선결). ⒝⒞ 와 run.js 레코더의 *위치 시각화 소비*는 후속(범위 격리 — 이 step 은 와이어 한 조각).
