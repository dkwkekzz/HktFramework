# step-0070 — failover 중 질의 연속성(presenceAnnounce)

> 직전: [step-0069](step-0069.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)
> 코드는 단일 소스 `src/`(제자리 수정) · 직전 동결 스냅샷 `baseline/` · reg 는 src vs baseline 비트 대조.

## 검증 질문

0067 의 failover 는 *발행(push)* 경로 연속성만 줬다(승격된 standby 가 svc.presence 인계 발행). 0069 의 *질의(pull)* 경로는 질의자가 *고정 주소*(primary)를 가리켜 primary 사망 후 질의가 끊긴다(0069 §9 한계). **읽기 경로도 failover 를 가로질러 연속인가?** standby 가 승격할 때 `svc.presence.active` 토픽으로 *새 active 주소를 공지*하고, 질의자(presmon)가 그 공지를 구독해 `queryAddr` 를 *재타깃*한다 → 죽음 후 질의도 승격된 박스가 답한다(읽기 경로 failover 서비스 디스커버리). 닫는 조건: 승격 공지·질의자 재타깃·죽음 후 질의 무손실(승격 박스가 응답)·신선한 read(permanent) vs 대조군 stale/손실·비-침습. 발행(0067)·질의(이 step) *둘 다* failover-safe → 프레즌스 박스가 진짜 failover-safe SSOT.

## 2. 메커니즘 — 승격 공지 + 질의자 재타깃 (`presenceAnnounce` OFF → baseline 비트 동일 = 회귀 0)

- **`src/svc-presence.js`**: `promote(tick)` 에 공지 추가 — `announceActive && bus` 면 `svc.presence.active {addr:this.addr}` 발행(`announced++`). `announceActive` 기본 false → 공지 0 = 0069 비트 동일.
- **`src/svc-presence-monitor.js`**: presmon 에 `svc.presence.active` 수신 분기 — `ev.addr` 로 `queryAddr` 갱신(`retargets++`). 이후 질의가 승격된 박스로 간다. 미구독이면 미발화(0069 비트 동일).
- **`src/topo-build.js`**: `presenceAnnounce` opt. standby(presence2)에 `announceActive:true` 전달. presmon 을 `svc.presence.active` 에 구독. presenceAnnounce OFF → 공지·재타깃 0.
- A/B 변수 = *공지/재타깃만*: ON/OFF 둘 다 failover(presenceFailover@30)·자율 승격(presenceLease)·질의(presenceQuery) — ON 만 공지+재타깃.

- **공지+재타깃**: 승격된 standby 가 `svc.presence.active` 공지(`announced=1`)·presmon 이 `queryAddr` 를 `presence`→`presence2` 로 재타깃(`retargets=1`). OFF 는 재타깃 0·`queryAddr=presence`(고정).
- **읽기 경로 연속성**: 죽음 전 질의는 primary 가(`repliesSent=2`)·죽음 후 질의는 승격된 standby 가(`repliesSent=2`) 답함 — 질의 무손실(`recv=sent=4`). `queried['ranking']='permanent'`(재타깃 덕에 신선).
- **대조군 갭(OFF)**: 재타깃 없으면 죽음 후 질의가 죽은 primary 로 → 승격 박스 응답 0(`std.repliesSent=0`)·손실(`recv 2 < sent 4`)·stale read(`queried['ranking']='down'`).
- **발행 경로 직교**: push 관측 state ON·OFF 둘 다 `permanent`(0067 발행 failover 는 공지와 무관·둘 다 연속). 질의(pull)·발행(push) 직교 증명.
- **비-침습**: `minted` ON==OFF·원장 정합.
- **회귀 0**: `node run.js`(4기둥+E2E 14프로세스 비트동일)·`node run.js spine`(70-step src 누적 회귀) ALL OK. reg(키트·presenceAnnounce 미설정) = 0069 비트 동일.

## 4. 척추 체크 5항

1. **신성한 tick** — 공지/재타깃은 존 tick 밖 코디네이션 제어 평면(승격 시 1회 공지·구독 수신). 시뮬 무관. ✅
2. **결정론 코어** — 세계 상태 무관. 공지·질의 5시드 동일·minted ON==OFF. ✅
3. **권위 단일 소유** — 공지는 *발행 권위 인계*의 신호일 뿐(승격=release+acquire). 질의는 읽기(SSOT 무변경). active 박스 항상 1. ✅
4. **은닉·단일 연결** — 질의자는 박스 *주소*를 공지(svc.presence.active)로 *동적 발견* — 정적 주소 결합 없이 active 박스를 따라간다(failover 디스커버리). 박스 내부 무지. ✅
5. **headless·원격 검증** — Node 헤드리스 `node run.js` 로 수치 증명(inproc 코디네이션 박스). ✅

## 9. 의외의 발견 / 정직한 한계

- **발행·질의 둘 다 failover-safe = 프레즌스 박스 골격 완성**: 0064(분리)→0065(보고 버스화)→0066(shadow)→0067(발행 failover)→0068(자율 감지)→0069(질의)→0070(질의 failover). 이제 프레즌스 박스는 *쓰기·발행·읽기* 전 경로가 단일점 없이 failover 를 견딘다 — SPINE 계층 5 "세션/프레즌스" SSOT 의 골격이 섰다.
- **재타깃 윈도 손실 가능**: 공지(t34)와 다음 질의 트리거(permanent 이벤트 t38) 사이에 재타깃이 완료돼 이 시나리오는 손실 0. 그러나 *재타깃 전*에 질의가 발생하면(공지 도착 전 윈도) 그 질의는 죽은 primary 로 가 손실된다 — 재시도/타임아웃 기반 질의(0058 recoverRetry 의 질의 판)는 미적용(후속).
- **단일 공지·1회 재타깃**: 공지는 승격 1회. 연쇄 failover(승격된 박스가 또 죽어 셋째가 승격→재공지) 시 질의자가 다시 재타깃하는가는 미검증(다중 standby·메아리 정리·0068 §9 와 함께 후속).
- **질의자가 여전히 active 박스만 안다**: 클라/게이트웨이 단일 진입점으로 질의를 다중화(클라는 어떤 presence 박스도 모름)하는 단계는 미적용 — 귓속말/파티 라우터 후속.
