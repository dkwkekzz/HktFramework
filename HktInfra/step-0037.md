# step-0037 — 버스 failover *요청 경로 무손실*: gateway producer replay 로 base 대비 mint 손실 0

> 직전: [step-0036](step-0036.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

step-0036 은 버스 crash gap 의 **`svc.item.out` *결과* 경로**를 가방(producer) replay 로 무손실화해 `itemDesync → 0` 을 달성했다. 그러나 그 거울인 **`svc.item` *요청* 경로**는 손실로 남았다(0036 §9): crash gap 에 떨군 클라 요청(pickup/give)은 **가방에 도달조차 못 해 mint 자체가 안 일어난다** → 원장이 base 보다 작다(`minted` 손실). 이 step 의 한 조각: **요청의 producer 인 게이트웨이가 발행 요청을 보관했다가 버스 복구 시 재발행**(0036 결과 replay 의 *요청 판*) → gap 에 떨군 요청이 가방에 도달해 mint → **base 대비 mint 손실 0**. SPINE §6 의 **버스** 박스(요청/결과 양 경로 신뢰성)를 채운다.

닫는 조건: ⒜ `busResendReq` OFF → 0036 비트 동일(reg 0) ⒝ recover(재구독만) = mint 손실 잔존(대조군) vs resendReq(재발행 ON) = `minted == base`(손실 0 *그리고* 이중 mint 0) ⒞ 재발행/dedup 이 원장 비-침습(보존·정합) ⒟ spine 37-step 사슬.

## 2. 메커니즘 — 요청 producer replay + reqId dedup (OFF 플래그 `busResendReq`)

**왜 게이트웨이가 producer 인가**: 0036 의 핵심(버스는 crash 후 *살아 돌아온 새 박스* — 라우팅 RAM 만 들고 영속 0)은 *요청* 경로에도 그대로 적용된다. gap 동안 도착한 pub(요청)은 빈 라우팅에 떨어져 사라지고, 버스 자신은 못 메운다. *결과* 의 진실 원천이 가방이었듯, *요청* 의 진실 원천은 그것을 발행한 **게이트웨이**다 — gap 을 살아남은 게이트웨이가 보관·재발행해야 한다.

**왜 dedup 이 필요한가 (0036 결과 경로와의 결정적 차이)**: 0036 결과 재발행은 클라 belief 가 `Set` 이라 *무조건 멱등*이었다(consumer dedup 불요). 그러나 요청 경로의 `pickup` 은 **매 처리마다 새 `itemId` 를 mint** — 멱등이 *아니다*. 게이트웨이가 보관 요청을 전량 재발행하면 gap *전* 도달분(이미 mint 됨)도 다시 오므로, dedup 없으면 **이중 mint**(dupe). 그래서 요청마다 producer-local 단조 `reqId` 를 실어 가방이 `seenReqs` 로 *최초 1회만* 처리한다(0023 persist `recvSeqs` 의 *요청 홉 판* — at-least-once 전송 + 멱등 소비 = effectively-once).

**한 조각**(닿는 박스 `gateway.js`·`svc-inventory.js`·`topology.js` 셋):
- `Gateway._itemReq(ev)`: `svc.item` 요청 발신을 감싸는 얇은 래퍼. `busResendReq` ON 이면 `reqId` 태깅 + `inBuffer` push(보관). OFF 면 ev 무변형 → `_svcSend` 그대로 = 0036 비트 동일.
- `Gateway.resendIn()`: 보관 요청을 `svc.item` 에 다시 pub. 버스 복구(재구독) *직후* 토폴로지가 트리거(가방 `resendOut()` 과 같은 위치).
- `InventoryService.onMsg`: `busResendReq` ON·`reqId` 실릴 때만 `seenReqs` dedup(이미 본 reqId → 폐기). OFF(reqId 없음)면 분기 휴면 = 0036 비트 동일.
- `topology.js`: `busRestart.renegAt` 의 재구독 sub 발신 **직후** `gateway.resendIn()` 호출(같은 tick·FIFO → bus 가 sub→pub 순 처리 = 라우팅 복구 후 fan-out). `busResendReq` OFF 면 호출돼도 즉시 반환.

**왜 desync 아닌 mint 손실로 측정하나**: 0036 이 확정했듯 *요청* 드롭은 mint 자체를 막아 **원장에도 없고 클라도 모른다 → 양측 일치 = desync 0**(behind 아님). 손실은 오직 *원장 mint 수가 base 보다 적음*으로만 보인다. 그래서 이 step 의 헤드라인 지표는 `itemDesync` 가 아니라 `minted`(= 후보 §2 "base 대비 mint 손실 0").

- **권위 보존**: 재발행/dedup 후 itemConserved(size==minted)·ledgerConsistent(byOwner≡ledger) 유지 — 재발행이 dupe 를 안 만든다.

## 4. 척추 체크 5항

① **신성한 tick**: 요청 보관·재발행은 게이트웨이의 *제어 평면*(존 tick 밖·net.log 비-기여)·dedup 은 가방의 순수 반응형 — 존 시뮬 비-침습. ② **결정론 코어**: `reqId` 는 producer-local 단조(클라 op 순서 = 시드 함수)·재발행은 제어 평면 트리거(시드 무관 상수 위치)·세계 상태 쓰기 경로 무변경. ③ **권위 단일 소유**: dedup 이 이중 mint 를 막아 원장 보존(소유자=1·dupe 0) 불변. ④ **은닉·단일 연결**: 클라는 여전히 gateway 만 안다(요청은 클라→gateway 정규 경로·재발행은 gateway 내부). ⑤ **headless·원격 검증**: Node `run.js` 로 수치 증명·멀티프로세스 E2E 영향 없음(busResendReq 인프로세스 가설 모드 — cluster 무수정).

## 9. 의외의 발견 / 정직한 한계

- **mint 18 손실은 단 2-tick gap 의 산물**: crash@12→reneg@14 의 2-tick gap 에서 51→33(18 손실)이 빠진다 — 활성 초반(요청 스트림이 몰리는 구간)을 가른 결과다. 재발행으로 18 전량(정확히) 복구되고 base 와 일치한다.
- **`itemId` 는 재배정되지만 mint 수·소유 분포는 보존**: 재발행된 gap 요청은 reneg 후 처리되므로(원래 tick 아님) 그 pickup 의 `itemId` 가 base 와 다르다(`invDigest` 불일치). 그래서 헤드라인 지표를 `invDigest`(정확 id 매칭)가 아니라 `minted`(수)로 잡았다 — mint 수·아바타별 보유 수는 보존(원장 보존/정합 단언으로 커버).
- **give 요청 재발행은 완전 복구가 아니다(transfers ≠ base)**: pickup(순수 생성)은 재발행으로 정확히 복구되나, *give* 요청은 result-ahead/클라 재-give 와 얽힌다 — gap 에 떨군 give 의 결과를 못 받은 클라가 같은 아이템을 *다시* give 하면, 재발행된 원 give 가 도착할 즈음엔 owner 가 바뀌어 실패한다(`failedOps` 발생). 결과는 base 와 *다른* transfer 집합으로 수렴하지만(transfers≠base) 원장은 자기-정합하고 클라는 desync 0 로 수렴한다(= 손실 아닌 *다른 유효 결과*). 완전한 give 복구는 0025 give-resend(클라 측) 결합 영역 — 이 요청-경로 조각과 직교.
- **inBuffer 무계(v1)**: 발행 요청을 전부 보관·복구 시 전량 재발행(0036 outBuffer·0017 무계 저널과 동형). 유계 슬라이딩 창(gap 만 덮는 K — 0032 wfWindow 패턴)은 후속.
