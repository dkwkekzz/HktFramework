## 검증 질문

0080 의 수신측 dedup(exactly-once)은 본 seq 를 *전부* 평면 `seen` Set 에 영구 보관한다 — 귓속말이 누적될수록 dedup 메모리가 run 길이에 비례해 무한 성장한다(0080 §9). 메모리를 *유계*로 묶으면서 dedup 정확도(중복 미적재)를 잃지 않을 수 있는가? SPINE 계층3(채팅/소셜) 수신 박스의 멱등 상태를 O(gap)로 유계화한다.

## 2. 메커니즘 — dedup seen 의 연속 워터마크 유계화 (플래그 OFF → baseline 비트 동일 = 회귀 0)

**관찰**: 라우터의 `deliverySeq` 는 *단조 증가*(producer 별 `++deliverySeq`)이고, 라우터는 whisperAck 를 받거나 상한 도달로 포기(undeliverable)하면 그 seq 를 다시 보내지 않는다. 따라서 수신측이 *연속으로* 본 seq 의 최고값(워터마크) 이하의 seq 는 영영 재발신되지 않는다 → 안전하게 잊어도 된다.

**구현** (`src/svc-mailbox.js`): `dedupBound` ON 일 때 평면 `seen` Set 대신
- `seenWm: Map<producer, seq>` — 본 *연속* 최고 seq. 이하는 전부 "본 것"으로 접힘(보관 0).
- `seenAbove: Map<producer, Set<seq>>` — wm 초과 *비순차* seq 의 희소 집합.

`_seenAdd(prod, seq)`: seenAbove 에 넣고 `wm+1` 이 차 있으면 연속 흡수하며 wm 전진(흡수분은 집합에서 제거). 순차 도착이면 즉시 흡수 → seenAbove ≈ 빈 집합. `_seenHas`: `seq ≤ wm`(접힘) 또는 `seenAbove.has(seq)` → 본 것. producer 키 = 전달자 addr(`m.from`). dedup 판정(중복=inbox 재적재 안 함·ack 재회신)은 0080 그대로 — 메모리 *표현*만 유계화.

0042 `busSeenBound`(inAcked 워터마크)·0047 `busSeenNs`(per-producer 가지치기)의 *전달 dedup* 판. `deliverDedupBound` OFF 면 `_seenHas/_seenAdd` 가 평면 Set 으로 디스패치 = 0080 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **발견**: 순차 도착에서 seenAbove 가 *정확히 0* 으로 유지된다 — 워터마크가 매 수신마다 즉시 흡수하므로 dedup 메모리가 사실상 상수(Map 항목 2개: wm 정수 + 빈 집합)다. 네트워크 재정렬이 있으면 잠시 gap 만큼 seenAbove 가 커졌다 흡수되며 줄어든다(유계의 상한 = 동시 비순차 gap 수).
- **한계**: producer(라우터)가 *재시작*하면 deliverySeq 가 0 부터 다시 시작할 수 있다 — 그러면 새 seq 가 옛 워터마크 이하로 잘못 접혀 *유실*될 위험이 있다(현재 라우터는 재시작 없으니 미발현). producer epoch/세션 키를 워터마크에 합치는 것(0048 lease lifecycle 류)이 후속. 또한 워터마크는 *단일 라우터 단조 seq* 를 가정 — 한 Mailbox 가 여러 라우터에게 받으면 producer 별로 이미 분리돼 있으나(seenWm/seenAbove 가 Map), 각 라우터의 seq 공간이 서로 독립이어야 안전(현 토폴로지 충족).
