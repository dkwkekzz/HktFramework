## 2. 메커니즘 — 박스 부품 분할 (export·동작·바이트 불변 = 회귀 0)

topo-build.js 를 두 파일로:
- **`topo-actors.js`** — *액터 팩토리 + 라우트 필터*: 박스 클래스 import(`__c`/`__p`) + `routeFilters` + `makeActor`(spec→`new X`→net.register). 분리 근거: 이 부분만 박스 클래스에 의존하고, `buildTopology`(선언적 spec 빌더)는 *외부 의존 0*(opts 만 만진다·검증으로 확인). export `{routeFilters, makeActor}`.
- **`topo-build.js`**(진입점) — `buildTopology`(verbatim 유지) + `topo-actors` require → `{routeFilters, buildTopology, makeActor}` 동일 export. net-core.js 의 `__p('topo-build')` 배선 무변경.

verbatim 이동(makeActor·routeFilters 텍스트 그대로) → src=baseline(0097) 비트 동일.

## 9. 의외의 발견 / 정직한 한계

- **발견**: `buildTopology`(선언적 spec 빌더)가 박스 클래스에 *전혀 의존하지 않는다* — spec 은 `{addr,kind,opts}` 데이터일 뿐이고, 클래스→인스턴스는 `makeActor` 한 곳뿐. 이 깔끔한 이음새(spec=데이터 ⟂ actor=구현) 덕에 import 블록 전체가 topo-actors 로 옮겨가도 buildTopology 가 무손상 — "선언적 토폴로지"(0009) 설계의 배당금.
- **한계**: buildTopology 자체는 여전히 ~24KB 단일 함수(플래그 destructuring + spec 빌딩 + 구독 테이블) — 더 자라면 *구독 테이블*(subs)을 별 함수로 빼는 둘째 분할이 후속. 현재는 유계 복귀로 충분.
