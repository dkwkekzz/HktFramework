# step-0029 — PersistStore quorum *쓰기* ack: W 정족수 확인 후 durable 선언·정합성 윈도 가시화

> 직전: [step-0028](step-0028.md) · 현재 위치·다음 가설의 권위: [STATE.md](STATE.md) · 척추: [SPINE.md](SPINE.md)

## 검증 질문

0028 이 N복제 fan-out + 생존 union 복구(quorum *read*)로 영속 단일점을 일반 해소했지만 §9 한계가 남았다: **fan-out 은 fire-and-forget — write quorum ack 가 없다.** primary 도달 후 일부 복제 미도달 상태에서 crash 시 정합성 윈도가 *보이지 않는다*(서비스가 무엇이 진짜 durable 인지 모름). 이 step 은 *쓰기 정족수 ack* 를 더해 그 윈도를 **가시화·유계화**한다 — 데이터 계층(계층 6)의 write-behind 신뢰성을 *durable 선언의 정확성*까지 닫는다.

닫는 조건: ⒜ 무손실=전 seq durable ⒝ per-link 손실에도 정족수 충족 seq 는 여전 durable ⒞ tail 정족수 미달 seq 는 `durableSeq` 가 *앞에서 멈춤*(윈도 가시) → 그 윈도만 crash 에 소실·durable 프런티어는 생존, ④ quorumW 0 이면 0028 비트 동일(reg 0).

## 2. 메커니즘 — 쓰기 정족수 ack (quorumW=0 면 휴면 = 0028 비트 동일)

```
InventoryService._journal(entry)              // primary + 복제 N 에 fan-out (0028)
  → quorumW>0 이면 각 발신에 { ...journal, q:true }   // ack 요청 플래그

PersistStore.onMsg({journal, q})              // 수신 = RAM 저장(별 박스)
  → 저장 후 p.q 면  net.send(서비스, {type:'journal_ack', seq})   // 저장 확인 회신(멱등 재-ack)

InventoryService.onMsg({journal_ack, seq, from})
  → ackSeqs[seq].add(from)                     // seq 별 durable 사본 집합
  → while ackSeqs[durableSeq+1].size ≥ W: durableSeq++   // 연속 커밋 워터마크 전진
                                                // durableSeq 위 = 정합성 윈도(아직 정족수 미확인)
```

`quorumW: 0`(default) → `_journal` 이 q 플래그를 안 붙임 → 저장소 ack 0 → `durableSeq` 미사용·페이로드가 0028 과 비트 동일 → **reg 0**. `durableSeq` 의 의미: **≥W 스토어에 durable(ack)된 seq 의 연속 프런티어 = (N+1−W) 죽음을 견디는 보장된 경계.** 그 위 seq 는 서비스가 *durable 로 선언하지 않는다*(낙관 금지) → 윈도가 워터마크 위로 정확히 드러난다.

## 9. 의외의 발견 / 정직한 한계

- **`durableSeq` 는 *연속(contiguous)* 워터마크 — 빈칸 하나가 그 뒤 전부를 보류**: seq T 가 정족수 미달이면 T+1.. 이 모두 ≥W ack 이라도 `durableSeq` 는 T−1 에 멈춘다(커밋 워터마크의 정의 — replay 가 연속 prefix 를 전제). 이는 *보수적*(안전)이나, 비연속 durable 까지 활용하려면 gap-fill(NAK 재전송, 0023) 과 결합해야 한다. 이 step 은 워터마크만 — gap-fill×정족수 결합은 후속.
- **ack = 라이브 in-RAM 저장 확인이지 디스크 fsync 아님**: 스토어가 받으면 곧 ack(별 박스 RAM). 진짜 내구성(디스크 fsync·전원 손실 생존)은 미착수 — ack 는 *복제 도달*의 정족수일 뿐. W+R>N+1 의 read/write 정족수 짝은 0028(read)·0029(write)로 성립하나 *공식 튜닝*(다양한 W·동적 N)은 후속.
- **윈도는 *감지*되지 durable 로 *전환*되지 않는다**: 이 step 은 정합성 윈도를 가시·유계화할 뿐, 윈도 seq 를 강제로 durable 로 끌어올리지(추가 재전송·재-fan-out) 않는다. 윈도 해소(W 미달 seq 재발행으로 정족수 채우기)는 0023 재전송 메커니즘과 결합할 후속 조각.
- **W 미달 seq 의 crash 생존은 손실 패턴 의존**: ⒞ 에서 윈도가 정확히 소실되는 것은 "윈도 seq 가 정확히 `{primary,persist4}` 2 홀더"라는 결정론 드롭 모델 때문. 실 분산에선 손실 분포가 달라 윈도 seq 도 일부 생존할 수 있다 — `durableSeq` 의 *보장*은 "durable 은 반드시 산다"이지 "윈도는 반드시 죽는다"가 아니다(보수적 하한).
