# step-0010 — 프로세스 경계 현실화: 인메모리 큐 → 실 프로세스/IPC (전송 seam 현실화·원격 멀티프로세스 E2E)

> 코어: `engine/`(공통 하니스 — **무수정**) · `step-0010/net-core.js`(액터 **무수정 복사 전진**(0009 그대로) + **토폴로지 빌더**(인프로세스/멀티프로세스 단일 구성 경로) + `run`(인프로세스=engine Net) + `runMulti`(멀티프로세스 위임)) · `step-0010/cluster.js`(**broker** — engine Net 을 전송 substrate 로 소유, **lockstep 배리어**로 원격 onMsg/onTick 디스패치·발신 회수) · `step-0010/host.js`(자식 프로세스 진입점 — 자기 몫 액터만 + **HostNet shim**) · 헤드리스: `step-0010/verify.js` · 관찰: `step-0010.html`(+ `step-0010/panel.js`·`engine/panel-kit.js`)
> 이 step 이 더한 한 조각: **0001~0009 는 전 "서버"(로그인·게이트웨이·존·추종자·orch·레지스트리)를 *단일 Node 프로세스 내 액터*로 두고 `engine/Net` 인메모리 큐로 통신시켜 netcode 프로토콜·토폴로지를 헤드리스로 증명했다([TOOLS.md](TOOLS.md) §6 'host 태그 경계'). 이 step 은 그 host 태그 경계를 *실 전송*(child_process IPC = 직렬화 메시지 경계)으로 갈아끼운다 — 재정렬된 큰 목표("모든 서버 headless·서로 완전 통신·원격 검증")의 *본진*([CLAUDE.md](CLAUDE.md) 큰 목표·[STATE.md](STATE.md) §2). 인프로세스 모드(`run`)는 engine Net 그대로라 0009 와 *비트 동일*(reg 0). 멀티프로세스 모드(`runMulti`)는 각 서버 박스를 *별도 OS 프로세스*에 띄우고(공유 메모리 0), broker 가 lockstep 배리어로 *전역 발신 순서를 정확히 보존*하며 IPC 로만 onMsg/onTick 을 원격 디스패치한다 → broker.net.log 가 인프로세스와 *비트 동일*(E2E 동치). 액터 로직·프로토콜은 *무변경* — 전송 seam 만 교체.** 클라는 여전히 게이트웨이만 — 프로세스 분리는 *서버간* 경계(은닉).
>
> **관찰(눈으로)**: `step-0010.html` 을 브라우저로 *그냥 열면* 프로세스 토폴로지가 뜬다 — 각 박스=독립 OS 프로세스, 선=프로세스 경계를 넘는 직렬화 IPC(굵기=메시지 수), ✝사망 존·▲승격 추종자. IPC 트래픽 타임라인에 사망(lease 끊김)·승격(keyframe 버스트) 세로선. (브라우저는 인프로세스 run() 만 그린다 — 멀티프로세스 E2E 는 node verify.js 로.) 헤드리스 미리보기는 `node step-0010/panel.js [seed]`(ANSI 스파크라인). 시각 셸 규약은 [CLAUDE.md](CLAUDE.md) "시각 관찰 셸 규약".

step-0009 가 추종자 승격으로 존 *사망*을 견디게 했다 — 그러나 전 서버는 여전히 *단일 Node 프로세스 내 액터*였다(0009 §8.7·[STATE.md](STATE.md) §3 🔴). host 태그 경계는 아직 *실 프로세스/소켓 분리*가 아니었다. 재정렬된 큰 목표는 *그림*이 아니라 *도는 인프라*다: 모든 서버가 headless 로 돌고, 서로 완전히 통신하며, 원격에서 E2E 로 검증되는 것 — 이것이 *제1 운영 제약*이다([CLAUDE.md](CLAUDE.md) 큰 목표). 이 step 은 그 본진을 친다 — `engine/Net` 의 인메모리 큐를 *실 전송*(child_process IPC)으로 현실화해, 각 서버 박스를 진짜 별 프로세스로 분리하고 원격 멀티프로세스 E2E 로 검증한다. 0001~0009 의 프로토콜·토폴로지·복원·failover 는 *그대로* 두고, *전송 seam* 만 교체한다([TOOLS.md](TOOLS.md) §6 transport seam).

결과: **전 시드 전 항목 통과.** ① 회귀 0(`reg`) — 인프로세스 모드(전송 seam OFF)면 0009 와 *비트 동일*(net.log 해시·상태, zones 1·2 · recovery off/on · failover off/on(+death) 전 조합 20/20) ② E2E 동치(`e2e`) — 멀티프로세스(각 서버 별 OS 프로세스·IPC) 실행이 인프로세스와 *비트 동일*(logDigest·fullDigest)·승격 수 일치·최종 desync 0(basic 6 프로세스·failover 9 프로세스, 5 시드) ③ 프로세스 분리(`isolate`) — 각 서버가 *구분되는 OS 프로세스*(pid)·broker 와도 다름·통신은 *직렬화 IPC 메시지뿐*(공유 메모리 0·전 메시지 직렬화 가능 true) ④ 은닉(`hide`) — 멀티프로세스(서버간 IPC) 후에도 클라 접점 공개 주소뿐·내부 누설 0 ⑤ 재현(`repro`) — 같은 시드 멀티프로세스 2회 같은 상태 + 인프로세스와도 동일(프로세스 분리가 결정론을 안 깸; 더구나 fullDigest 가 *0009 failover 다이제스트와 일치*).

## 2. 메커니즘 — 전송 seam 을 인메모리에서 실 프로세스로 (이 step 의 한 조각)

```
 인프로세스(run): engine/Net 그대로 — 0009 비트 동일(reg 0). 전송 seam 교체 OFF.
   buildTopology(opts) → 선언적 spec[] → makeActor → engine Net.register → net.step() 루프(0009 그대로)

 멀티프로세스(runMulti): host 태그 = 실 프로세스 경계(child_process.fork)
   ┌── broker(코디네이터, cluster.js) ──────────────────────────────────────────┐
   │  engine/Net 을 *전송 substrate* 로 소유(큐·seq·dedup·로그·전송 모델) — 액터는 원격     │
   │  매 tick lockstep 배리어(engine step() 의미를 비동기 IPC 로 재현):                  │
   │    ① deliver: due 메시지를 호스트별로 묶어 원격 onMsg → 발신을 (전역 gi, 로컬 si)로     │
   │       재정렬 후 net.send 재생(seq/id/enqueue/log = engine Net 그대로)               │
   │    ② tick:    전 액터 onTick(등록 순서) → 발신 (gi=등록idx, si)로 재정렬·재생         │
   │    deliver 발신은 항상 tick 발신보다 먼저(engine step 의 deliver→onTick 순서 보존)     │
   └────────────────┬──────────────┬──────────────┬────────────── ... ──────────┘
            IPC(직렬화 JSON)   IPC            IPC                  (공유 메모리 0)
   ┌────────▼─────┐ ┌──▼──────┐ ┌──▼──────┐
   │ host: gateway│ │host:zone1│ │host:orch │ ...  각 호스트 = 별 OS 프로세스(host.js)
   │  Gateway 액터 │ │ Zone 액터 │ │ Orch 액터 │      HostNet shim: send 를 버퍼링만(broker 가 seq 소유)
   └──────────────┘ └──────────┘ └──────────┘      onMsg/onTick 실행 → 발신 회수 → broker 가 재생
```

0009 대비 더한 것은 *전송 seam 의 현실화*뿐 — 액터(게이트웨이·존·추종자·orch·클라)·프로토콜·failover 는 *비트 그대로*:

1. **토폴로지 빌더 — 인프로세스/멀티프로세스 단일 구성 경로(E2E 동치의 토대).** 0009 의 `run()` 이 직접 하던 액터 생성·배선을 *선언적 spec*(`buildTopology`)으로 옮겼다 — 생성자 opts 에 전 배선을 담아(후처리 0) `makeActor(spec, net)` 가 spec→액터를 만든다. 인프로세스는 engine Net 에, 호스트는 HostNet shim 에 *같은 팩토리*로 register. 같은 spec → 같은 액터(시드 의사난수만, `Math.random` 0) → *프로세스가 갈려도 같은 초기 상태*. 등록(=onTick) 순서는 0009 와 *정확히* 일치(login·registry·gateway·zone1·zone2·[orch·zone1f·zone2f]·client*) — reg 0 의 전제.

2. **broker lockstep 배리어 — engine step() 의미를 IPC 로 *순서 보존* 재현.** broker 는 engine Net 을 *전송 substrate* 로 소유한다(큐·seq·dedup·로그·전송 모델 = 0004 그대로). 매 tick: ⒜ due 메시지를 호스트별로 묶어 원격 `deliver`(onMsg) → 각 발신을 (전역 인덱스 gi, 로컬 si)로 태그해 회수 → *(gi, si) 정렬* 후 `net.send` 로 재생. ⒝ 전 액터를 등록 순서로 원격 `tick`(onTick) → 발신 회수·정렬·재생. deliver 발신을 항상 tick 발신보다 먼저 재생한다(engine step 의 deliver→onTick 순서). 이 정렬이 *전역 발신 순서를 정확히 보존*하므로 broker.net.log 가 인프로세스와 *비트 동일*. (배치 IPC 로도 순서가 보존되는 근거는 §7-3.)

3. **host = 자식 프로세스(child_process.fork) + HostNet shim.** 각 호스트는 자기 몫의 액터만 산다 — 다른 호스트·broker 와 *메모리를 공유하지 않는다*(별 OS 프로세스·별 V8 isolate·별 주소공간). 액터의 `.net` 은 HostNet shim: `send` 를 버퍼에 모으기만 하고(전역 seq·큐·로그는 broker 가 소유) broker 가 회수한다. 액터 클래스는 net-core 의 것 *그대로*(makeActor) — 프로세스 분리가 액터를 수정하지 않는다(seam 만 교체). broker↔host 는 JSON 직렬화 메시지로만 통신(init/deliver/tick/snapshot/bye).

> 클라는 여전히 게이트웨이만 안다 — 프로세스 분리는 *서버간* 경계다. lease/promote/relink/reroute·핸드오프·ghost·증분이 전부 *프로세스 경계를 넘는 IPC* 가 됐지만 클라엔 닿지 않는다(은닉 불변). `node verify.js` 한 줄이 전 프로세스를 띄워(원격에서) 같은 4기둥을 검증한다 — 제1 운영 제약의 충족.

## 5. ③ 프로세스 분리 — `isolate`, 통과 (재정렬 목표의 본진)

**각 서버 = 구분되는 OS 프로세스·통신은 직렬화 IPC 뿐**(seed 42 failover, 9 호스트):

```
broker pid P0 · 호스트 9개 · 구분 pid 9개 · IPC out 1162건/373181B · in 1171건/305764B · 양방향 직렬화 가능 true
배치(addr → host → pid):
  login → login → pid Pa     gateway → gateway → pid Pc    zone1 → zone1 → pid Pd
  registry → registry → Pb   zone2 → zone2 → pid Pe        orch → orch → pid Pf
  zone1f → zone1f → pid Pg    zone2f → zone2f → pid Ph      client0..5 → clients → pid Pi
```

- 9 호스트가 *9개 구분 pid* 에 살고, 전부 broker(P0)와 *다른 프로세스*다 — 공유 메모리 0(별 OS 프로세스·별 주소공간). 경계를 넘는 *모든* IPC 메시지가 *양방향으로* 직렬화 가능(broker→host out 1162건/373KB · host→broker in 1171건/306KB — JSON round-trip, 함수·심볼·순환·공유 참조 0). 클라(엣지)는 한 호스트에 묶고 서버 박스는 박스당 1 프로세스 — 목표 토폴로지(박스=독립 서버)와 일치. pid 는 실행마다 바뀌나 *구분성·broker 와의 분리*는 불변.

## 7. 의외의 발견

1. **프로세스 경계가 *비트 동일* — 전송 seam 현실화가 동작뿐 아니라 비트까지 비-침습이다.** 보통 "인메모리 → 분산" 전환은 메시지 순서·타이밍이 흔들려 *동치*조차 어렵다. 그런데 여기선 멀티프로세스 실행이 인프로세스와 *logDigest 비트 동일*까지 간다. 비결은 두 가지: ⒜ `logDigest` 가 `from>to:payload` *순서의 함수*(seq/tick 무관)라, broker 가 *전역 발신 순서*만 보존하면 비트 동일이 따라온다. ⒝ broker 가 발신을 (전역 인덱스, 로컬 인덱스)로 정렬·재생해 engine step() 의 deliver→onTick 순서를 *정확히* 재현한다. "분산이면 비결정"이라는 통념과 정반대 — *결정론 배리어*가 프로세스 경계를 비트까지 투명하게 만든다.
2. **전송 seam 은 0001 부터 *이미 거기 있었다* — 현실화 = 디스패치 교체, 액터 무수정.** 0001 이래 모든 메시지가 *직렬화 가능*(JSON)이었고(SPINE §4 transport seam), 0004 가 전송 모델을 그 seam 에 입혔다. 그래서 프로세스 경계 현실화는 *새 직렬화·새 와이어 포맷*이 필요 없었다 — 인메모리 호출을 IPC 디스패치로 바꾸기만(액터 코드 0줄 변경). 경계가 *처음부터 직렬화 메시지*로 설계됐으므로(은닉·계약), 현실화가 한 step 에 들어왔다. "씨앗 = 같은 계약의 첫 구현"([SPINE.md](SPINE.md) §3)의 실증 — 더미가 throwaway 가 아니라 경계의 첫 구현이었다.
3. **tick 내 onMsg/onTick 이 *서로 독립*이라 배치 IPC 가 안전하다(per-message 왕복 불요).** engine step() 에서 한 tick 의 발신은 전부 *미래 tick*(queue[tick+1+])로 enqueue 된다 — 이번 tick 의 deliver/onTick 은 서로의 효과를 *못 본다*. 그래서 호스트별로 onMsg/onTick 을 *배치*해 한 번에 처리하고 발신만 (전역, 로컬)로 정렬해 재생해도 상태가 동일하다 — per-message IPC 왕복(수천 회)을 호스트·phase 당 1회(tick 당 ~2×호스트)로 줄였다. 결정론은 *순서 보존*만 요구하지 *직렬 실행*을 요구하지 않는다는 발견.
4. **failover(제어 평면)가 프로세스 경계를 *공짜로* 넘는다 — lease/promote 가 그냥 메시지라서.** 분산 failover 의 악명은 제어 평면(하트비트·승격)의 분산화인데 — 0009 가 lease/promote/relink/reroute 를 *전부 메시지*로 설계했으므로(서버간 제어 평면), 프로세스 분리에서 *추가 작업 0*으로 IPC 를 넘는다(orch 가 별 프로세스가 돼도 승격 1·이중쓰기 0·desync 0). 메시지-우선 설계가 토폴로지 변화에 *불변*임을 보였다.

## 8. 정직한 한계

1. **broker lockstep 배리어 = 중앙 코디네이터(결정론의 대가). 진짜 비동기·실시간 아님.** 결정론(비트 동일)을 위해 broker 가 *전 프로세스를 tick 배리어로 묶는다* — 매 tick 전 호스트가 deliver/tick 을 끝낼 때까지 동기화한다. 이는 *원격 검증용 결정론 하니스*이지 상용의 자유 실행(각 존이 자기 박자로 도는 비동기·실시간)이 아니다. 진짜 비동기 아래의 결정론(논리 클럭·인과 순서·재정렬 흡수)은 후속 — 이 step 은 *프로세스 경계의 현실화*만 측정한다(타이밍 모델은 0004 의 결정론 전송 위에 선다).
2. **IPC = child_process 파이프, *실 네트워크 소켓* 아님.** 경계는 진짜 OS 프로세스·진짜 직렬화·공유 메모리 0 이지만, 전송은 로컬 IPC(파이프)다 — TCP/소켓·NATS/Redpanda 같은 *실 네트워크 전송*(분단·재연결·MTU)은 안 탔다([TOOLS.md](TOOLS.md) §2 버스). 다만 0004 의 전송 모델(지연·손실·재정렬·중복)이 broker substrate 에 *그대로* 살아 있어, 전송 열화가 인메모리와 동일하게 주입됨을 `e2e` 의 transport 시나리오(손실 0.2·지연·중복 3)로 *검증*했다(비트 동일). 실 소켓·실 네트워크 *분단*은 후속.
3. **broker 단일점 + 사망 = 액터 무동작(진짜 프로세스 kill 아님).** broker 가 전송·배리어의 단일점이다 — 상용은 broker 대신 *버스*(NATS/Redpanda)가 그 자리를 분산으로 채운다(미착수). 또 0009 의 사망을 *액터 무동작*(deathTick 후 onTick/onMsg 정지)으로 유지했다 — reg/e2e 비트 동일을 위해(진짜 `child.kill()` 은 비결정·배리어 교란). 진짜 프로세스 kill 로의 failover(broker 가 죽은 호스트를 감지·재배선)는 *강력한 데모*이나 결정론 검증과 긴장 — 후속.
4. **클라가 한 호스트에 묶임 · 정적 배치.** 클라(엣지)는 한 'clients' 호스트에 묶었다(서버 박스 분리가 핵심이라). 또 배치(addr→host)는 정적이다 — 동적 재배치·오토스케일(오케스트레이터의 일)은 미착수. 게이트웨이 군·존 샤딩(N 프로세스)도 후속.
5. **여전히 Node · C++ 시뮬 코어 미교체.** 전 박스가 Node 프로세스다 — 월드 박스의 C++ 결정론 시뮬 코어 교체(UE-모듈-free·헤드리스 shim, [STATE.md](STATE.md) §3 🔴)는 여전히 선결 후속. 이 step 은 *프로세스 경계*를 현실화했지 *시뮬 언어*를 바꾸지 않았다 — 동결 `ISimCore` seam 은 그대로다.
6. **존↔존 ghost·동적 경계·존 N개는 여전히 미착수(0006~0009 상속).** 이 step 은 *프로세스 경계*만 더했다. 존↔존 ghost 는 여전히 전체 스냅샷, 경계는 정적 2 존이다.
