# MMORPG Cycle 기반 구현 운영 지침

모든 작업은 [`Design-ModulePlan-CycleWorkflow.md`](design/Design-ModulePlan-CycleWorkflow.md)를 최상위 구현 기준으로 삼는다.

## 1. 핵심 구현 구조

전체 모듈 구조와 구현 순서는 다음과 같이 고정한다.

```text
V → O → S → D → P → Q → W → R → E → G → C → X → N → A
```

모듈을 임의로 생략하거나 순서를 변경하지 않는다.

계획은 최종 플레이 경험에서 내부 원인을 찾는 역방향으로 수행하고, 실제 구현은 위 모듈 순서에 따라 정방향으로 수행한다.

## 2. Cycle의 정의

Cycle은 하나의 기능, NPC 행동, 테스트 장면이 아니다.

하나의 Cycle은 제한된 지역 안에서 다음 요소가 얇더라도 실제로 연결된 소형 MMORPG 세계다.

* 탐험
* 전투
* 채집과 자원 획득
* 제작
* 경제와 거래
* NPC 및 세력 관계
* 성장
* 여러 플레이어의 협력 또는 경쟁
* 권위 서버
* 저장과 재접속
* 플레이어가 없어도 진행되는 세계
* 플레이 결과가 남는 영속 상태

배고픈 NPC, 음식 하나, 자원 충돌과 같은 작은 장면은 Cycle로 만들지 않는다. 이러한 장면은 모듈의 정상·실패·경계 조건을 검증하는 Scenario로만 사용한다.

## 3. 작업 계층

작업 단위를 반드시 다음과 같이 구분한다.

```text
Cycle
→ Gameplay Loop
→ Situation
→ Scenario
→ Module Step
→ Implementation Task
```

* Cycle: 하나의 플레이 가능한 지역 MMORPG
* Gameplay Loop: 플레이어가 반복해서 수행할 활동
* Situation: 세계 상태와 여러 주체의 목적 충돌로 발생한 상황
* Scenario: 특정 조건을 재현하는 자동 검증 장면
* Module Step: 해당 Cycle에서 특정 모듈이 책임질 구현
* Implementation Task: 파일·타입·객체·함수·이벤트·UI·테스트 단위

## 4. Cycle 생성 원칙

각 Cycle은 하나의 명확한 플레이어 판타지를 가진다.

각 Cycle에는 다음이 반드시 존재해야 한다.

1. 탐험 가능한 지역
2. 서로 다른 목적을 가진 복수 주체와 세력
3. 최소 3개의 연결된 Gameplay Loop
4. 플레이어가 선택할 수 있는 여러 해결 방식
5. 플레이어가 개입하지 않았을 때의 세계 진행
6. 성장 전후의 가능성 변화
7. 자원 생산·소비·운송·거래 중 하나 이상의 경제 순환
8. 여러 플레이어가 같은 세계 상태에 영향을 주는 구조
9. 세션이 끝난 뒤에도 남는 결과
10. 개발자가 인과관계를 추적할 수 있는 증거

한 Cycle에서 모든 깊이를 동시에 확장하지 않는다. 다음 깊이 축 중 주축 하나와 보조축 하나만 선택한다.

* 인과 깊이
* 전략 깊이
* 주체·관계 깊이
* 세계 깊이
* 시간·성장 깊이
* 공간 깊이
* 온라인 깊이
* AI 제작 깊이

## 5. Module Step 규칙

각 Module Step은 반드시 다음 항목을 포함한다.

* 목적
* 이번 Cycle에서의 역할
* CREATE / EXTEND / REFINE / HARDEN / REUSE
* 입력 계약
* 출력 계약
* 읽는 상태
* 쓰는 상태
* 발생 이벤트
* 다음 모듈의 출력 소비자
* 플레이어에게 보이는 기여
* MMORPG Gameplay Loop 기여
* 구현할 타입과 객체
* 구현할 함수
* 정상 Scenario
* 실패 Scenario
* 경계값 Scenario
* 브라우저 Lab 검증 방법
* 결정성 검증
* 완료 증거

다음 모듈이나 실제 Gameplay Loop에서 사용하지 않는 출력은 구현하지 않는다.

코드를 수정하지 않는 모듈도 SKIP하지 않고 REUSE로 표시한 뒤 현재 Cycle의 데이터가 실제로 해당 모듈을 통과하는지 검증한다.

## 6. 구현 규칙

얇은 구현은 허용하지만 가짜 구현은 금지한다.

허용:

* 단일 프로세스 권위 서버
* 작은 지역
* 제한된 자원과 제작식
* 적은 수의 NPC와 세력
* 정적 AI 후보 생성기
* 단순한 전투와 경제 수식

금지:

* 하드코딩된 NPC 행동으로 P·R·E 우회
* X 계층에 직접 배치한 콘텐츠로 Q·W 우회
* 클라이언트가 N을 거치지 않고 소유권이나 전투 결과 결정
* 사건 없이 World State 직접 변경
* 플레이어 접속 시에만 작동하는 세계
* 퀘스트 스크립트로 세계 시뮬레이션을 대체
* 테스트 통과만을 위한 운영 코드 분기
* 미래 Cycle을 예상한 과잉 추상화

## 7. 플레이 표현과 개발자 검증의 분리

개발자는 다음 인과를 정확히 추적할 수 있어야 한다.

```text
공리
→ 주체
→ 의존성
→ 결핍
→ 가능성
→ 목적
→ 전략
→ 세계 요구
→ 세계 요소
→ 지각과 믿음
→ 행동 의도
→ 충돌
→ 사건
→ 성장
```

플레이어에게 이 그래프를 직접 보여주지 않는다.

플레이어는 다음을 통해 상황을 이해한다.

* 공간 변화
* 생물과 NPC의 행동
* 소리·빛·냄새·흔적
* 소문과 보고
* 가격과 재고 변화
* 관계 변화
* 이동로와 위험 변화
* 계약과 세력 반응

## 8. 완료 판정

Module Step은 테스트 통과만으로 완료되지 않는다.

다음 순서로 검증한다.

```text
Step 검증
→ 모듈 간 Handoff 검증
→ Situation 통합 검증
→ Cycle 전체 Gameplay Loop 검증
→ 멀티플레이 검증
→ 저장·재접속 검증
→ 이전 Cycle 전체 회귀 검증
→ 완료 증거 생성
```

Cycle은 다음 조건을 모두 만족해야 VERIFIED가 된다.

* 실제로 플레이할 수 있다.
* MMORPG의 반복 활동이 존재한다.
* 여러 해결 방식이 존재한다.
* 플레이어가 없어도 세계가 진행된다.
* 여러 플레이어가 세계 상태를 공유한다.
* 성장으로 새로운 가능성이 열린다.
* 결과가 영속 상태로 남는다.
* 모든 핵심 결과의 인과를 추적할 수 있다.
* 동일 시드와 동일 명령으로 재생할 수 있다.
* 이전 VERIFIED Cycle의 대표 리플레이가 깨지지 않는다.

검증되지 않은 Cycle을 기준선으로 다음 Cycle을 시작하지 않는다.
