# Intent Skill — 일감을 의도(Intent)에 결합

사용자가 `/intent <일감>` 으로 작업을 제시하면, 그 일감이 *왜 존재해야 하는지* 를 `Docs/intents/` 의 의도 트리에서 찾아 결합한다.

- 적합한 의도가 있으면 → **그 의도에 결합** 하고 ID 를 보고한다.
- 적합한 의도가 없으면 → 가장 가까운 **상위 의도 아래 새 하위 의도를 작성** 하고 결합한다.
- 어느 쪽인지 애매하면 → **후보 리스트를 제시** 하고 사용자에게 결정을 맡긴다.

`/intent` 단독 호출(일감 없음) 시 사용자에게 일감을 묻는다. 트리거 없이 자동 적용 금지.

## 환경 상수

```
INTENTS_DIR  = Docs/intents
ROOT_INTENT  = I-0001
ID_PATTERN   = ^I-\d{4}$
STATUSES     = active | proposed | realized | abandoned
```

## 현재 의도 트리 (depth 4)

탐색 시 우선 참조용. 사실의 진본은 항상 파일 (`Docs/intents/I-*.md`) 이며, 변동 시 본 표가 아니라 파일을 따른다.

```
I-0001 (root) 무한한 성장과 모험을 느끼게 해주는 open world MMORPG
├── I-0002 견고한 통신 기반
│   ├── I-0003 데디케이티드 서버, 클라이언트 간의 통신
│   └── I-0004 백엔드 및 인증 인프라 [proposed]
├── I-0005 무한한 컨텐츠 확장에 유연하게 대응할 기반
│   ├── I-0006 결정론적 시뮬레이션 시스템 (Story Script)
│   └── I-0007 렌더링 시스템 (HktCore → 시각화)
│       ├── I-0008 2d sprite HktEntity Rendering
│       ├── I-0009 2d sprite Animation
│       └── I-0010 2d sprite VFX Rendering [proposed]
├── I-0011 모험을 위한 월드 (Voxel Terrain)
├── I-0012 무한한 성장의 주체 (클래스 체인지) [proposed]
├── I-0013 성장을 위한 재료 (Voxel Spawner)
├── I-0014 모험과 성장을 위한 상호작용 (전투 / 원소)
└── I-0015 콘텐츠 자동화 및 에셋 파이프라인
```

## 1. 워크플로

`/intent <일감>` 수신 시 위에서 아래로 진행한다.

### 1단계 — 일감 이해

사용자의 발화에서 *무엇을 만들/고치/추가* 하는지를 한 문장으로 정리한다. 예:

| 사용자 발화 | 정리 |
|------|------|
| "spritegenerator 를 만들어줘" | 2D 스프라이트 자동 생성 도구 추가 |
| "spawner story 작성해줘" | Spawner Story 카탈로그에 신규 항목 추가 |
| "결정론 깨지는 버그 고쳐줘" | 시뮬레이션 결정론 회귀 수정 |

### 2단계 — 의도 트리 탐색

`Docs/intents/I-0001.md` 의 children 부터 하향 탐색한다. 각 노드에서:

1. **본 의도 (`## Intent` 본문)** 를 읽고, 일감의 정리된 주제가 본 의도의 *왜* 와 일치하는지 평가한다.
2. 일치하면 그 노드의 children 으로 더 내려간다.
3. 더 내려갈 곳이 없으면 그 노드가 후보.
4. 일감이 여러 가지에 걸쳐 있으면 모든 후보를 모은다 (예: 콘텐츠 자동 생성 도구는 I-0015 + I-0008 에 동시 봉사).

탐색은 사용자 힌트가 있으면 단축한다:
- 사용자가 ID 를 명시 (`"I-0013 에 붙여줘"`) → 그 노드로 직행.
- 사용자가 영역만 줌 (`"콘텐츠 자동화 쪽"`) → 그 영역 의도 (I-0015) 부터 탐색.

### 3단계 — 분기

탐색 결과에 따라 셋 중 하나로 진행한다.

#### 3.A — 단일 적합 의도 발견

해당 의도에 결합을 확정하고 보고한다. 의도 파일은 *건드리지 않는다* — 결합은 일감 측 메타데이터(예: 코드 헤더 주석, PR description, Story 사이드카) 의 책임이다.

```
일감: "<정리된 주제>"
결합 의도: I-XXXX (<title>)
경로: I-0001 → … → I-XXXX
근거: <왜 이 의도에 속하는지 한 문장>
```

#### 3.B — 복수 후보 / 애매함 → 사용자에게 묻기

후보가 2개 이상이거나 어느 의도에도 *명백히* 속하지 않으면 사용자에게 결정을 맡긴다. 같이 *새 하위 의도 작성* 선택지도 항상 함께 제시한다. `AskUserQuestion` 도구를 활용해 선택지를 제시한다.

#### 3.C — 적합 의도 없음 → 새 하위 의도 작성

탐색 결과 가장 가까운 상위 의도는 있으나, 그 아래에 일감을 정확히 표현하는 의도가 없을 때 §2 절차로 새 하위 의도를 만든다.

상위 의도조차 애매하면 `I-0001` 직속 새 영역을 만드는 것이 *아니라* — 먼저 사용자에게 "이 일감을 어느 영역으로 보십니까?" 를 묻는다. `I-0001` 직속 추가는 드물어야 한다 (현재 자식 7개로 이미 충분히 펼쳐져 있음).

## 2. 새 하위 의도 작성

### 2.1 절차

| # | 단계 |
|---|------|
| 1 | 부모 의도 ID 확정 — 사용자 합의 또는 §1.2 탐색의 leaf. 다중 parents 도 가능. |
| 2 | 새 ID 할당 — `ls Docs/intents/I-*.md` 의 최대 번호 + 1. ID 는 영구 불변, 폐기 시에도 재사용 금지. |
| 3 | 초안 제시 (§2.3) — 사용자 검토 후 확정. |
| 4 | `Docs/intents/I-XXXX.md` Write — frontmatter + 본문. |
| 5 | **부모 파일 갱신** — 모든 parents 의 `children:` 배열에 새 ID 추가, `## 하위 의도` 섹션에 링크 추가, `updated_at` 갱신. **양방향 일관성 필수.** |
| 6 | §3 검증. |
| 7 | 결합 보고 — 새 의도 ID 와 부모 갱신 내역. |

### 2.2 Frontmatter 규격

```yaml
---
id: I-XXXX                              # ^I-\d{4}$
title: <한 문장 요약, 200자 이내>
status: active                          # 또는 proposed (사용자 검토 중일 때)
created_at: 2026-MM-DDT00:00:00+09:00   # 현재 KST
updated_at: 2026-MM-DDT00:00:00+09:00
parents: [I-YYYY]                       # 1개 이상. 다중 가능.
children: []                            # 새 의도는 보통 []
tags: []                                # 현재 모든 의도가 [] — 임의 태그 도입 금지
---
```

### 2.3 본문 — 기존 의도들과 일관된 형태로

`## Intent` 섹션은 필수. 그 외 섹션은 의도가 leaf 인지 / 자식이 있는지에 따라 결정한다.

| 섹션 | 언제 | 예시 |
|------|------|------|
| `## Intent` | **필수.** *왜* 를 1~3 문단. *어떻게* 는 적지 않는다. | 모든 파일 |
| `## 하위 의도` | 자식이 있을 때 한 줄 요약 + 링크 | I-0001, I-0002, I-0005, I-0007 |
| `## 구현` | leaf 의도 — 실현 모듈 / Docs 링크 (불릿 목록) | I-0003, I-0006, I-0008~I-0015 |

### 2.4 톤 & 스타일 (기존 의도와 일치 필수)

- **한국어**. 코드 식별자·기술 용어는 원어 (`HktCore`, `chunk`, `Story`).
- **"왜" 만 적는다.** 구현 단계 / API / 코드 절차는 Design 문서나 별도 가이드로 분리.
- 용어: **본 의도 / 하위 의도 / 상위 의도 / 최상위 의도** 를 일관 사용.
- **bold** 로 핵심 단언, *italic* 으로 단어 강조.
- 의도 참조 링크: `[I-0013](I-0013.md)` 또는 `[I-0013 — 성장을 위한 재료](I-0013.md)`.
- 모듈 / 코드 경로 참조: `[HktCore](../../HktGameplay/Source/HktCore)`, `` `HktCore/Public/Terrain/HktFixed32.h` ``.
- Docs 참조: `[CombatSystemDesign.md](../CombatSystemDesign.md)`.
- 단정·대조 표현으로 의도의 *경계* 를 명확히: "~ 으로 환원되지 않는다", "양자택일이 아니다", "silent 손실되어선 안 된다" 등.
- 문장 끝은 평서종결 (`…한다` / `…이다`). 존댓말 X.
- 본문 길이: 추상·상위 의도는 짧게(1~2 문단). leaf 는 1~3 문단 + `## 구현` 불릿.

### 2.5 `## 구현` 섹션 패턴 (leaf 의도 전용)

```markdown
## 구현

- 모듈: [HktSpriteCore](../../HktGameplay/Source/HktSpriteCore) — 한 줄 설명
- Docs: [<문서명>.md](../<문서명>.md)
- [TODO] <아직 미정인 항목>
```

미정 영역은 `[TODO]` 로 본문에 명시 — 의도가 *완성* 되지 않아도 *선언* 되어 있어야 한다.

### 2.6 초안 제시 형식

파일을 만들기 전에 사용자에게 초안을 보여준다.

```
초안 (I-XXXX 후보 — 부모: I-YYYY):

---
id: I-XXXX
title: <제목>
status: proposed
created_at: <KST>
updated_at: <KST>
parents: [I-YYYY]
children: []
tags: []
---

## Intent

<왜 이 의도가 필요한가 — 동기 / 경계 / 기대 효과.>

## 구현

- 모듈: [<모듈>](../../...) — <한 줄>
- [TODO] <…>

확정할까요? (필요 시 제목·본문 수정 요청 가능)
```

사용자가 확정하면 4~7 단계 진행. `status` 는 보통 곧바로 `active` 로 둔다. 구현이 거의 없으면 `proposed`.

## 3. 검증

`Docs/intents/store/validator.js` 의 규칙을 따른다. 새 의도 작성 / 수정 시 반드시 통과해야 한다.

| # | 항목 | 확인 |
|---|------|------|
| 1 | 필수 필드 `id`, `title`, `status` 존재 | frontmatter 점검 |
| 2 | ID 패턴 `^I-\d{4}$` + 파일명 일치 | |
| 3 | status ∈ {active, proposed, realized, abandoned} | |
| 4 | title ≤ 200자 | |
| 5 | parents / children 의 모든 ref 가 실존 | 해당 `I-XXXX.md` 존재 확인 |
| 6 | **양방향 일관성** — `A.children: [B]` ↔ `B.parents: [A]` | 가장 자주 깨지는 지점 |
| 7 | DAG (사이클 없음) | |

사이트 (`Docs/intents/site.html`) 가 있으면 브라우저로 열어 errors 패널 확인. 없으면 위 7개 항목을 수동 점검.

## 4. 출력 — 작업 종료 시 사용자에게 보여줄 것

### 4.A — 기존 의도에 결합 (의도 파일 변경 없음)

```
일감: "<정리된 주제>"
결합 의도: I-XXXX (<title>)
근거: <한 문장>
```

### 4.B — 새 의도 작성 후 결합 (의도 파일 변경 있음)

```
일감: "<정리된 주제>"
신규 의도: I-XXXX (<title>) — 부모: I-YYYY
결합 의도: I-XXXX

변경된 파일:
  - Docs/intents/I-XXXX.md (신규)
  - Docs/intents/I-YYYY.md (children 갱신, updated_at 갱신)

검증: 통과 (§3 7 항목)
```

기능 브랜치에 커밋하라는 사용자 지시가 있으면 메시지 패턴:
`intents: add I-XXXX <title>` 또는 `intents: link <일감 요약> → I-XXXX`.

## 5. 강제 금지

- 사용자가 `/intent` 를 호출하지 않은 상태에서 일감을 의도와 결합하라고 강요.
- 의도 ID 재사용 (폐기된 ID 포함).
- 부모 / 자식 양방향을 한쪽만 갱신 (`children:` 만 추가하고 `## 하위 의도` 섹션 누락 등).
- 의도 본문에 *어떻게 구현하는지* 의 단계별 절차 기재 — 그건 Design 문서 / Story / 코드의 영역.
- 임의로 `tags` 분류 체계 도입.
- 기존 의도의 톤·문체를 무시한 자유 작성 — §2.4 가이드와 기존 파일들 (특히 I-0001, I-0006, I-0011) 을 *항상* 참조.
- 본 skill.md 의 "현재 의도 트리" 섹션을 사실의 진본으로 신뢰 — 항상 `Docs/intents/I-*.md` 파일을 우선 확인.
