# Intent Skill — 작업을 의도(Intent)에 결합시키는 워크플로

`Docs/intents/I-XXXX.md` 로 관리되는 의도(Intent) 트리에 사용자가 제시한 일감을 연결한다.
Intent 란 *"왜 이걸 하는가"* 의 근원 — `I-0001` (최상위) 을 뿌리로 한 DAG 로 모든 작업의 존재 이유가 거슬러 올라간다.

**활성화 트리거** — 사용자가 `/intent` 를 명시 호출하거나, 작업을 의도에 결합하라고 요청할 때만 동작. 자유 작업에 자동 적용 금지.

## 환경 상수

```
INTENTS_DIR  = Docs/intents
ROOT_INTENT  = I-0001
ID_PATTERN   = ^I-\d{4}$
STATUSES     = active | proposed | realized | abandoned
```

## 사용법

```
/intent show <ID>              — 의도 본문 + 부모/자식 표시
/intent tree [ID]              — ID 부터 (없으면 I-0001 부터) 트리 출력
/intent find "<일감>"           — 일감 → 적합한 의도 후보 탐색
/intent link "<일감>" <ID>      — 일감을 명시된 의도에 결합 (보고만, 파일은 안 만짐)
/intent new <PARENT_ID>        — PARENT 아래 새 하위 의도 작성 — 대화형
/intent edit <ID>              — 의도 수정
/intent validate               — 전체 검증 (frontmatter / DAG / 양방향)
```

`/intent` 단독 호출 시 사용자에게 무엇을 하고 싶은지 묻는다. 자동 분류 금지.

## 1. 의도 파일 형식

YAML frontmatter + 마크다운 본문. 모든 필드는 `Docs/intents/store/validator.js` 의 규칙을 따른다.

### 1.1 Frontmatter — 필수 / 권장

```yaml
---
id: I-XXXX                       # 필수 — ^I-\d{4}$ 패턴. 새 ID 는 §3.A 절차로 할당.
title: <한 문장 요약>             # 필수 — 200자 이내.
status: active                   # 필수 — active | proposed | realized | abandoned
created_at: 2026-MM-DDT00:00:00+09:00   # ISO8601 KST.
updated_at: 2026-MM-DDT00:00:00+09:00   # 수정 시 갱신.
parents: [I-YYYY, I-ZZZZ]        # 부모 ID 배열 — 최상위(I-0001)만 [] 허용. 다중 부모 허용.
children: [I-AAAA, I-BBBB]       # 자식 ID 배열 — 잎(leaf)은 [].
tags: []                         # 자유 태그. 현재 대부분 빈 배열.
---
```

### 1.2 본문 섹션 패턴 (선택적, 의도 성격에 따라 조합)

| 섹션 | 용도 | 예시 |
|------|------|------|
| `## Intent` | **필수.** 의도의 *왜* 를 한두 문단으로 진술. 시스템 구현 방법 X, 동기/제약/기대 효과 O. | 모든 의도 파일 |
| `## 하위 의도` | 자식 의도들이 본 의도를 어떻게 분담하는지 한 줄 요약 + 링크. | I-0004 |
| `## 적용 영역` | "일반 의도" 가 여러 영역에 동일 형태로 적용될 때 영역 목록. | I-0015, I-0017 |
| `## 본 의도가 의존하는 일반 의도` | 본 의도가 표현하는 보편 원칙이 다른 일반 의도로 끌어올려져 있을 때. | I-0014 |
| `## 구현 / 진척` | 본 의도의 구현 상태 — **상세는 별도 Design 문서로 분리** 권장. | I-0013, I-0014 |
| `## <자유 제목>` | 의도가 구체화된 메커니즘, 규약, 카탈로그 등 — 의도 본질에 직접 결부될 때만. | I-0010, I-0011, I-0012 |

### 1.3 톤 & 스타일 (기존 의도들과 일치 필수)

- **한국어로 작성**. 코드 식별자 / 외래 기술용어는 원어 유지 (`HktCore`, `chunk`, `Story` 등).
- **"왜" 를 적고 "어떻게" 를 적지 않는다.** 구현 방법은 Design 문서로 분리.
- **본 의도 / 하위 의도 / 상위 의도 / 일반 의도 / 최상위 의도** 라는 용어를 일관 사용.
- **bold** 로 핵심 단언을, *italic* 으로 단어 강조를 표현.
- 다른 의도 참조는 마크다운 링크 — `[I-0014](I-0014.md)` 또는 `[I-0014 (자연적인 Spawner 배치)](I-0014.md)`.
- 코드 경로 참조는 backtick + 상대경로 — `` `HktCore/Public/Terrain/HktFixed32.h` ``.
- 절대 원칙 / Absolute Principle 인용 시 번호 명시 — "(Absolute Principle 3·4)".
- 문장 끝은 평서종결 ("…한다" / "…이다"). 존댓말 X.
- **"silent 손실되어선 안 된다"**, **"양자택일이 아니다"**, **"~ 으로 환원되지 않는다"** 등의 단정/대조 표현으로 의도의 *경계* 를 그어준다.

### 1.4 본문 길이 가이드

| 의도 성격 | 본문 길이 |
|-----------|----------|
| 최상위 / 추상 의도 (I-0001, I-0002) | 2~3 문단. 한 두 문장의 핵심 진술. |
| 시스템 영역 의도 (I-0004, I-0010) | 한 두 문단 + `하위 의도` 섹션. |
| 일반 의도 (I-0015, I-0017) | "왜 일반 의도여야 하는가" 한 문단 + 적용 영역 목록. |
| 구체 의도 (I-0011, I-0012, I-0013, I-0014) | 의도 진술 + 메커니즘 / 구현 / 진척 섹션. 길어도 됨. |

## 2. 일감 → 의도 결합 (`/intent find`, `/intent link`)

사용자가 "X 라는 일감을 하려고 한다" 라고 제시했을 때 그 일감이 *무엇을 위해* 존재하는지를 의도 트리에서 찾는다.

### 2.1 탐색 절차

| # | 단계 |
|---|------|
| 1 | **루트부터 하향 탐색** — `I-0001` 의 children → 각 children 의 children. 일감과 의미가 가장 가까운 가지를 따라 내려감. |
| 2 | **잎(leaf) 또는 일치 노드 도달** — 일감이 명백히 해당하는 의도. |
| 3 | **다중 후보 시 모두 보고** — 일감이 여러 의도에 걸치면 (예: Story 작성은 I-0011 + I-0015 동시 봉사) 후보들을 함께 제시. |
| 4 | **적합 의도 없음 → §3.A 분기** — 가장 가까운 상위 의도 아래 새 하위 의도 작성 제안. |

### 2.2 사용자 힌트 처리

- 사용자가 의도 ID 를 명시했다면 (`"I-0014 에 연결"`) → 탐색 생략, 해당 의도로 직행.
- 사용자가 부분 힌트만 줬다면 (`"placement 관련 의도"`) → 힌트로 후보 범위를 좁힌 후 §2.1 의 1~3 진행.

### 2.3 출력 형식

```
일감: "<사용자 발화>"

후보 의도:
  - I-0014 (자연적인 Spawner 배치 및 생성 시스템) — 본 일감의 직접 부모
    경로: I-0001 → I-0002 → I-0004 → I-0014
    근거: Placement Story 작성은 본 의도의 핵심 메커니즘.
  - I-0015 (콘텐츠와 시스템 결합의 무결성) — 일반 의도로 동반 봉사
    근거: Placement 매핑 silent 손실 방지 적용 영역.

권장: I-0014 를 주 결합, I-0015 를 부 결합으로.
```

명시 결합이 필요하면 `/intent link` 로 확정 — 이 시점에서는 *보고만* 한다 (의도 파일 자체에 일감을 기재하지 않음. 일감의 *주체* 가 의도 ID 를 자기 메타데이터에 갖는 형태가 일반적).

## 3. 새 의도 작성·수정 (`/intent new`, `/intent edit`)

### 3.A 신규 작성 절차

| # | 단계 |
|---|------|
| 1 | **상위 의도 결정** — `/intent new <PARENT_ID>` 의 PARENT 가 적절한지 확인. 여러 parents 가능. |
| 2 | **새 ID 할당** — `Docs/intents/I-XXXX.md` 의 현재 최대 번호 + 1. `ls Docs/intents/I-*.md` 로 확인. ID 는 영구 불변, 폐기 시에도 재사용 금지. |
| 3 | **초안 작성** — §3.A.1 형식. 사용자와 협의하여 title / Intent 본문 확정. |
| 4 | **파일 생성** — `Docs/intents/I-XXXX.md` 에 frontmatter + 본문 Write. `created_at` / `updated_at` = 현재 KST. |
| 5 | **부모 의도 갱신** — 모든 parents 의 `children:` 배열에 새 ID 추가 + `updated_at` 갱신. 양방향 일관성 필수 (§4). |
| 6 | **검증** — §4 절차로 frontmatter / 양방향 / DAG / 사이트 표시 확인. |
| 7 | **커밋** — 기능 브랜치에 커밋. 메시지: `intents: add I-XXXX <title>`. |

#### 3.A.1 초안 형식

```
초안 (I-XXXX 후보):
---
id: I-XXXX
title: <기술된 제목>
status: proposed
created_at: <ISO8601 KST>
updated_at: <ISO8601 KST>
parents: [<제안 부모 ID>]
children: []
tags: []
---

## Intent

<왜 이 의도가 필요한가 — 한두 문단. 동기 / 경계 / 기대 효과.>

[필요 시 추가 섹션 — §1.2 표 참조]
```

사용자가 검토 / 수정 / 승인하면 `status: proposed` 를 `active` 로 바꿔도 됨 (대부분 곧바로 active).

#### 3.A.2 적절한 parent 가 없을 때

- 일감이 기존 트리 어디에도 매핑되지 않으면 **새 일반 의도** 가 필요할 수 있다 — 이 경우 보통 `I-0002` (인게임 코어) / `I-0007` (콘텐츠 자동화) / `I-0006` (백엔드) 같은 *영역 의도* 의 자식으로 들어간다.
- 영역 의도조차 적합하지 않으면 `I-0001` 직속 새 영역을 제안하되 — **이건 드물어야 한다**. 사용자에게 명시적으로 확인.

### 3.B 수정 (`/intent edit`)

| # | 단계 |
|---|------|
| 1 | 기존 파일 Read. |
| 2 | 변경 영향 분석 — 본문 변경은 안전, frontmatter 변경 (특히 parents / children / status) 은 양방향 영향 검토. |
| 3 | 사용자 확인 후 Edit. |
| 4 | `updated_at` 갱신. |
| 5 | parents / children 변경 시 상대편 파일도 함께 갱신. |
| 6 | §4 검증. |

### 3.C 폐기·대체

| 작업 | 처리 |
|------|------|
| 폐기 | `status: abandoned`. 자식 의도는 사용자 결정으로 재배치하거나 함께 폐기. **파일 삭제 X**. |
| 대체 | `status: superseded` 가 현재 validator 에 없음 — 필요해지면 validator 확장 후 도입. 그 전까지는 새 의도를 만들고 구 의도를 abandoned 처리. |

ID 는 영구 불변. 폐기되어도 재사용 금지.

## 4. 검증 (`/intent validate`)

`Docs/intents/store/validator.js` 의 규칙 — 사이트에서 자동 실행되지만 파일 작성 후 수동으로도 점검한다.

### 4.1 점검 항목

| # | 항목 | 점검 방법 |
|---|------|----------|
| 1 | 필수 필드 — `id`, `title`, `status` | frontmatter 누락 확인 |
| 2 | ID 패턴 — `^I-\d{4}$` | 파일명 ID 일치 확인 |
| 3 | status 허용값 — `active` / `proposed` / `realized` / `abandoned` | |
| 4 | title 200자 이하 | |
| 5 | parents / children 의 ref 가 실존 | 모든 ID 가 `I-XXXX.md` 존재 |
| 6 | 양방향 일관성 — `A.children: [B]` ↔ `B.parents: [A]` | 새 의도 추가 / 수정 시 가장 자주 깨지는 지점 |
| 7 | DAG (사이클 없음) | parents/children 가 순환하지 않음 |

### 4.2 수동 점검 명령 (사이트 검증을 신뢰하지 못할 때)

```bash
# 모든 의도 ID 목록
ls Docs/intents/I-*.md | sed 's|.*\(I-[0-9]\{4\}\)\.md|\1|'

# 특정 ID 의 parents 확인
grep '^parents:' Docs/intents/I-XXXX.md

# 양방향 누락 빠른 점검 — A.children 에 B 가 있는지 확인 후 B.parents 에 A 있는지 grep
grep -l 'I-XXXX' Docs/intents/I-*.md
```

사이트 (`Docs/intents/site.html`) 가 있다면 브라우저로 열어 validator 의 errors 패널을 확인.

## 5. 작업 종료 전 체크리스트

### `/intent new` / `/intent edit` 수행 시

1. 새/변경 파일의 frontmatter 가 §1.1 규격 충족.
2. parents / children 양방향 갱신 완료 (§4 6번).
3. 본문 톤이 §1.3 가이드와 일치 — "어떻게" 가 아니라 "왜".
4. 변경된 모든 의도 파일의 `updated_at` 갱신.
5. 사용자에게 변경된 의도 ID 목록 + 영향 범위 보고.
6. 사용자 승인 시 기능 브랜치에 커밋 (메시지: `intents: <add|update|abandon> I-XXXX[, I-YYYY] <요약>`).

### `/intent find` / `/intent link` 수행 시

1. 후보 의도와 그 경로 (`I-0001 → … → I-XXXX`) 를 함께 제시.
2. 다중 결합이 적절하면 주/부를 구분해서 보고.
3. 의도 파일은 *건드리지 않음* — 결합 보고만.

### `/intent validate` 수행 시

1. §4.1 의 7 항목 모두 점검.
2. 위반은 모두 **경고** — 사용자에게 알리되 자동 수정 금지.

## 6. 강제 금지

- 사용자가 호출하지 않은 상태에서 일감을 의도와 결합하라고 강요.
- 의도 ID 재사용 (폐기된 ID 포함).
- 상위/하위 양방향을 한쪽만 갱신 — 항상 동시 갱신.
- 의도 본문에 *어떻게 구현하는지* 의 단계별 절차를 적기 — 그건 Design 문서 / Story / 코드의 영역.
- 임의로 `tags` 분류 체계 도입 — 현재 모든 의도가 `tags: []`. 새 태그 체계 필요 시 사용자 합의 선행.
- 기존 의도의 톤·문체를 무시한 자유 작성 — §1.3 가이드와 기존 파일들을 *항상* 참조.
