# HktInfra 묶음 리뷰 루프 — 토큰 효율 실행 절차

이 스킬은 HktInfra 시리즈의 닫힌 step 들을 **10개 묶음**으로 회고한다. step-loop(`infra-step`)이 *인프라를 세우는* 것과 직교 — 리뷰는 *세워진 것을 인과로 설명하고 그 정당성을 검증*하며 **이슈를 전방(다음 step)으로 연결**한다. **작업 디렉토리: `HktInfra/`** — 이하 상대 경로는 이 폴더 기준. **프로토타입 코드·STATE·step 문서는 읽기만**(리뷰는 인프라를 안 바꾼다 — 회귀 사슬 불변).

## 리뷰의 본질 — "최초 구조에서 시작해, 각 step 이 왜 필요했나"를 인과로 풀고 그 정당성을 본다

리뷰의 핵심 질문은 둘이고, **둘 다 매 리뷰가 한다**(조건·트리거 없음):

1. **진행 지도** (`reviews/progress/` — 주제=계층별 파일) — *직관적으로 현재 진행 상태와 동작을 설명한다*. 무슨 서버를 만들고 있고, 어떤 기능들이 필요하고, 무엇이 구현됐고, 지금 무엇을 하고 있는지. **어떤 이론에 기반하는지, 거기서 어떤 기능을 어떻게 구현했는지 단계별로**. 핵심은 **최초 구조에서 출발해 각 step 이 왜 필요했는지를 인과관계로** 푸는 것이다(아래 §3·§3.5). 이게 이 스킬의 1차 산출물.
2. **정당성 감사** (`reviews/review-NNNN-MMMM.md` + `reviews/README.md` 원장) — *진행 지도가 푼 그 인과가 정당한가*. 척추 5불변을 실물 코드·run.js 재현으로 판정하고, 문제는 이슈로 남겨 후속 step 으로 연결한다(아래 §4·§5).

> **진행 지도가 먼저, 감사가 그 위에 선다.** 진행 지도는 "무엇을·왜·어떻게"를 비전문가도 따라오게 그리고(서사·인과), 감사는 그 서사의 각 마디가 척추를 지켰는지 점적(點的)으로 판정한다(정합·이슈). 진행 지도 없이 감사만 쌓으면 "10 step 마다 척추 OK" 라는 *점*만 남고 *무슨 서버가 어떤 이론으로 여기까지 왔는지*는 아무도 못 본다. 그래서 **매 리뷰가 이번 묶음을 인과 서사로 이어 그린다**.

## 핵심 원칙 — 리뷰는 "주장"이 아니라 "재현"이다

step 문서의 PASS 는 *주장*이다. 리뷰의 권위는 **실물 코드(현재 `src/*.js` + `engine/*.js`) + run.js 재현 + grep 감사**다. "문서가 PASS 라 함"으로 닫지 마라 — 직접 돌려 수치를 인용하고, 코드 라인(`src/<box>.js:line`)으로 알리바이를 댄다. 문서-코드 불일치를 찾는 게 정당성 감사의 본령. 진행 지도의 인과 서사도 *실물 코드가 실제로 그렇게 동작함*을 근거로만 쓴다(상상한 동작 금지).

> **단일 src 구조 유의 (0049 src/ 전환·이후 archive 폐기)**: HktInfra 는 더 이상 step 마다 `step-NNNN/` 디렉토리를 복사 전진하지 않는다 — 코드는 단일 살아있는 소스 `src/`(박스 1개=파일 1개) 한 곳에서 *제자리 수정*되고, 옛 동결 스냅샷 사슬은 삭제됐다. 따라서 알리바이는 *현재 코드*를 가리킨다: 어떤 불변이 걸린 메커니즘은 그게 사는 `src/<box>.js:line`(누적 코드 — 전 step 의 기능이 한 파일에 공존), 승격분은 `engine/<part>.js:line`. *그 step 이 더한 정확한 델타*가 필요하면 git 으로 캔다(`git log --oneline -- src/<box>.js` → `git show <commit>`). 역사 보존 = git 커밋(+ 이 reviews/ 원장).

# 리뷰 절차 — 4단계 (이 순서로 돈다)

리뷰는 다음 4단계를 차례로 밟는다. 1~3 이 진행 지도를 빚고, 4 가 감사를 빚는다.

## 1단계 — 전체 프로젝트 구조를 파악한다

이 인프라가 *무엇을 향해, 어떤 구조로* 가는지부터 잡는다. 이게 모든 인과 설명의 출발점("최초 구조")이다.

**필독**: `SPINE.md`(§1 토폴로지·§2 박스별 책임·§5 척추 5불변·§6 6계층) · `CLAUDE.md`(큰 목표·검증 4기둥) · `STATE.md`(§5 6계층 진행·§7 INDEX 로 묶음 범위 확인) · `reviews/README.md`(열린 이슈 원장) · `reviews/progress/`(직전까지의 인과 서사 — 이번 묶음을 *이어* 그린다).

여기서 잡을 것: **6계층(엣지·월드·게임 서비스·버스·코디네이션·데이터)과 그 안의 박스들**(로그인·게이트웨이·존·인스턴스·가방·채팅·랭킹·거래소·버스·세션·오케스트레이터·캐시·DB). 각 박스 = *원격에서 도는 독립 headless 서버* 의 씨앗. 이 구조가 진행 지도의 뼈대(계층별 파일·박스별 항목)다.

## 2단계 — 리뷰 범위의 step 을 파악한다

이번 묶음 10개 `step-NNNN.md` 만 읽는다(전체 읽기 OK — 리뷰 대상). 묶음 밖 옛 step 문서는 읽지 마라. 각 step 이 *어느 박스를 건드렸나·무슨 한 조각을 더했나*를 추린다.

**실물 코드(부분 읽기)**: 그 묶음이 더한 박스를 *현재* `src/<box>.js`·승격분(`engine/*.js`)에서 Grep/offset 으로 *해당 함수만*. 전체 통독 금지(큰 파일). *그 step 의 델타*가 모호하면 `git log -- src/<box>.js`/`git show` 로 캔다.

## 3단계 — 각 서버를 "무슨 서버인가 + 기능별 리스트"로 설명한다 → 진행 지도

**이게 이 스킬의 1차 산출물이자 가장 중요한 단계다.** 진행 지도의 단위는 *서버(박스)* 이고, 한 서버는 **여러 기능**으로 이뤄진다(기능마다 이론·접근이 다르다 — 이론은 서버당 하나가 아니다). 그래서 각 서버를 다음처럼 푼다:

1. **무슨 서버인가** — 이 서버가 무엇을 책임지는지 한 줄(+ 평이한 비유 한 줄).
2. **필요한 기능들 — 리스트로 나열.** 그 서버가 *제대로 서려면 갖춰야 할 기능*을 하나씩 나열한다. **각 기능마다 세 가지**를 단계별로:
   - **왜 필요한가** — 최초 구조(1단계)에서 *어떤 문제·요구*가 이 기능을 부르나.
   - **어떻게 구현하면 되나** — 그 기능을 푸는 이론/접근(결정론 복제·AOI·권위 쌍 거래·write-behind·quorum·saga·exactly-once·epoch 펜싱 등). 기능마다 다를 수 있다.
   - **무엇을 했나 / 상태** — 실제로 한 일(어느 `step-NNNN` 에서 무엇을)과 현재 상태(✅ 됨 / 🟡 부분 / ⬜ 남음). 안 한 것도 *남은 기능*으로 리스트에 적는다.
3. **지금 어디 / 다음** — 이 서버 전체가 지금 무엇을 하고 다음에 무엇을 하는지 한 줄.

> **핵심: "무엇을 했나"의 나열로 끝내지 말고 *기능 단위로 분해*하라.** 한 서버 = 기능 리스트, 각 기능 = (왜 필요 → 어떻게 구현 → 무엇을 했나/남았나). 여러 step 이 한 기능을 키우면 그 기능 항목 아래 단계로 묶고, 한 기능이 여러 step 에 걸치면 성장 사슬로 잇는다. 비전문가도 *이 서버에 무슨 기능이 있고 각각 어디까지 됐는지*를 리스트로 훑을 수 있어야 한다.

이 리스트를 `reviews/progress/<N-계층>.md` 의 *이번 묶음이 건드린 서버 항목*에 이어 그린다(형식·분할 규칙 §3.5).

## 4단계 — 3단계의 정당성을 판단한다 → 감사 + 이슈

3단계가 푼 인과("이 step 이 이 문제를 이렇게 풀었다")가 *정당한가*를 본다. 척추 5불변을 실물 코드·run.js 재현으로 판정하고, **문제가 있으면 review 파일에 이슈로 남긴다**.

- 척추 5불변 판정 + 코드 알리바이 + 검증 재현(grep·run.js) — 형식은 §4.
- 모든 이슈는 *반드시* 후속 step 으로 연결한다(해소 게이트 step 가리키기 or 원장 이월) — §5.

> **3→4 의 관계**: 진행 지도(3)가 "이렇게 동작한다·이래서 필요했다"고 말하면, 감사(4)는 "정말 그런가·척추를 지키며 그랬나"를 캐묻는다. 3 의 서사 한 마디가 코드에서 안 맞거나(문서-코드 불일치) 척추를 긴장시키면 그게 곧 4 의 이슈다.

# 산출물 — 매 리뷰가 셋을 더한다 (복사·누적 폐기)

1. **진행 지도 갱신** — `reviews/progress/<N-계층>.md` 의 *이번 묶음이 건드린 박스 항목만* 인과 서사로 이어 갱신(누적 아님·아래 §3.5). 매 리뷰 필수. **리뷰의 1차 산출물.**
2. **묶음 감사 1편** — `reviews/review-NNNN-MMMM.md`(아래 §4). ≤ 10KB. 닫으면 불변(역사).
3. **README 원장 갱신** — `reviews/README.md` §1 감사 인덱스 1줄 append + §2 열린 이슈 원장 갱신(해소분 떨굼·신규 이월).

그 외 복사 0. 진행 지도·감사는 step 문서를 복제하지 않는다(교차 참조만).

> **고도 분리 — 늘어나는 곳을 가른다**: `FOUNDATIONS`(프로젝트·동결) · **`progress/`(인과 서사 진행 지도·계층별 파일·덮어쓰기)** · `review-NNNN`(묶음·정당성 감사·늘어남) · `step-NNNN`(조각·늘어남). 진행 지도(progress)는 *무슨 서버가 어떤 이론으로 어떻게 여기까지 왔나*(인과·직관), 감사(review-NNNN)는 *그 인과가 척추에 정당한가*(정합·재현·이슈). 둘은 직교 — 서로 재서술하지 않는다. *무엇을 했나*의 점적 기록은 step 문서·STATE INDEX 가 가지므로 **둘 다 그걸 그대로 베끼지 않는다**(중복 0).

## 3.5 진행 지도 — `reviews/progress/` (매 리뷰 갱신·계층별 파일 분할·인과 서사·직관 우선)

각 박스(=서버)를 *무슨 서버인가 + 필요한 기능 리스트(기능마다 왜 필요→어떻게 구현→무엇을 했나)* 로 **비전문가도 리스트로 훑을 수 있게** 그린다. 핵심 규칙 셋:

1. **한 파일에 몰지 않는다 — 주제(계층)별 파일로 쪼갠다.** 6계층 = 파일 6개(`1-edge.md`·`2-world.md`·`3-services.md`·`4-bus.md`·`5-coordination.md`·`6-data.md`) + `README.md`(인덱스: 큰 줄기 한 줄 + 박스 상태 맵 + 다음 큰 걸음).
2. **단위는 박스(서버)다 — 서버를 기능 리스트로 분해한다.** 각 계층 파일 안에 그 계층의 박스(SPINE §2)마다 항목 하나. 박스 항목 형식:
   - **무슨 서버인가** — 이 박스가 무엇을 책임지는 서버인지 한 줄(+ 평이한 비유 한 줄).
   - **필요한 기능들 (리스트)** — 그 서버가 제대로 서려면 갖춰야 할 기능을 *번호/불릿 리스트*로 나열. **각 기능마다 세 가지**: ⒜ **왜 필요**(최초 구조에서 어떤 문제) ⒝ **어떻게 구현하면 되나**(이론/접근 — 기능마다 다름) ⒞ **무엇을 했나 / 상태**(어느 `step-NNNN` 에서 무엇을 + ✅됨/🟡부분/⬜남음). 한 기능이 여러 step 에 걸치면 성장 사슬로(예: 영속 = 저널→압축→quorum), 아직 안 한 기능도 ⬜ 로 리스트에 남긴다.
   - **지금 어디 / 다음** — 이 서버 전체가 지금 무엇을 하고 다음에 무엇을 하는지 한 줄.

   > 이론은 *서버당 하나가 아니다* — 기능마다 다른 이론에 기댄다. "무엇을 했나"의 평면 나열이 아니라 *기능 분해 리스트*(기능→왜/어떻게/했나)로 적는다.
3. **매 리뷰가 이번 묶음이 건드린 박스 항목만 이어 갱신한다**(조건·트리거 없음 — 모든 step 은 어떤 박스든 자라게 하므로 매 리뷰가 갱신 대상이 있다). 안 건드린 박스·계층 파일은 그대로 둔다.

권위는 SPINE §2/§6(구조)·STATE §5(진행 마커)·FOUNDATIONS(철학) — 충돌하면 위가 맞다. *무엇을 했나*의 점적·정합 판정은 감사·step 문서·STATE 가 가진다(progress 는 인과·직관 서사만 — 중복 0). 계층 파일은 ≤ 4KB 로 묶는다.

## 3.6 단계 판정 — "어디까지 진행할지"는 리뷰가 정한다 (너비 우선)

> **왜 리뷰가 정하나**: step-loop(`infra-step`)은 한 박스에 코를 박고 "한 조각"만 본다 — 그 고도에선 "capstone 하나만 더"가 늘 자연스러워, 한 박스를 무한히 깊게 파게 된다(0107~0200 이 증상: 거래소·우편·길드를 영속~정합 capstone 까지 파는 동안 인스턴스·캐시·월드 영속 박스는 *기본 통신조차* 못 섰다). **너비를 보는 건 6계층 지도에 10 step 을 대고 한꺼번에 보는 리뷰뿐.** `reviews/progress/README.md` 박스 상태 맵(⬜/🌱/🟡)이 그 너비 지도다 — 단계 판정은 거기서 읽어낸다.

**단계 정의 (이 기준으로 판정):**

- **1차 = 너비.** SPINE 6계층의 *모든 박스*를 **기본 통신** 선까지 먼저 세운다 — 각 박스가 ⒜ 분명한 목적 + ⒝ 그 목적 달성 *최소 연산*(요청/응답·pub/sub) + ⒞ 척추 5항 + reg 0. 예: 길드 = 생성·삭제·가입이면 충분. **1차 완료 = progress 맵에 ⬜/🌱 박스가 없음**(전 박스 🟡↑).
- **2차 = 고도화.** 영속·failover·스냅샷 압축·escrow 연동·saga liveness·정합 capstone 등 *심화*는 서버 내부 확장 문제 — 너비가 다 찬 뒤로. 1차 미완 중 발견된 심화 후보는 원장에 **"2차 대기"** 로 적되 STATE §2 로 승급하지 않는다.

**매 리뷰가 한 줄 평결을 낸다** (progress/README 큰 줄기 + `reviews/README.md` 원장):
1. progress 맵에서 ⬜ 미착수/🌱 스텁 박스를 추린다(현재: 인스턴스 ⬜·캐시 ⬜·로그인 🌱·오케스트레이터 배치·월드 영속).
2. **이번 묶음이 빈 박스를 세웠나, 아니면 이미 선 박스를 더 깊게 팠나**를 판정 — 후자면 *과심화*로 이슈 승격(§5).
3. **다음 방향**: 1차 미완이면 "다음 묶음은 빈 박스 X 우선"(원장 §2 에 목적지=STATE §2 NEXT 로). 1차 완료면 "너비 충족 — 2차 고도화 개시 가능" 선언.

> **집행 분리(불가침·§5 전파 경로 그대로)**: 리뷰는 평결을 *원장에 기록만* 한다. STATE §2 를 직접 고치지 않는다 — step-loop 이 원장을 읽어 빈 박스를 STATE §2 NEXT 로 승급·구현한다. review=판정·기록, step=집행. (CLAUDE.md 는 이 분리의 인덱스 한 줄만 둔다 — 기준 전문은 이 스킬.)

## 4. 묶음 감사 문서 — 3절 구조 (정당성 감사 전용·고정)

> **narrative 금지**: "각 step 이 뭘 했나" 요약표를 두지 않는다(인과 서사는 진행 지도가, 점적 기록은 STATE INDEX 가 가진다). 맨 위 한 줄로 *범위 + `progress/` 링크*만 가리키고 바로 감사로 들어간다.

- **§1 척추 정합성** — SPINE §5 **5불변**(①신성한 tick ②결정론 코어 ③권위 단일소유 ④은닉·단일연결 ⑤headless·원격검증) 각각 판정(✅/🟡/🔴) + **코드 알리바이**(`src/<box>.js:line` 또는 `engine/*.js:line`). 비판적으로 — 견고한 것은 견고하다 하고, 긴장·편차는 숨기지 말고 *이슈로 승격*. 회귀 0 규율·박스 파일 유계(30KB 예산·초과 시 정리 step) 구현 품질도 메타로.
- **§2 검증 재현** — 대표 step 들 `node run.js <NNNN>`(현재 step 만 가능 — archive 폐기) + `node run.js spine`(src 누적 회귀 — 전 역사 불변을 *현재 코드*에 단언·"어느 불변도 안 깨졌다"의 증거) + grep 감사 실행 출력 인용. 풀 spine 은 `run_in_background` 로.
- **§3 이슈 → 후속 step 연결** — 표(#|이슈|항|상태|목적지→게이트/해소). 4단계가 찾은 모든 정당성 문제를 여기로(아래 §5).

## 5. 이슈는 반드시 후속 step 으로 연결한다 (전파 고리 — 불가침)

리뷰는 회고이자 **전방 입력**이다. 핵심 원칙: **과거 step 은 동결 — 이슈는 *이후 게이트 step* 으로 반영한다**(플래그=0 → 회귀 0). 4단계가 찾은 모든 이슈는 *반드시* 둘 중 하나로 연결된다:

- **(a) 이미 해소** — 후속 게이트 step 이 메웠으면 그 step 을 가리킨다(예: "권위 공백 → step-00NN 핸드오프 쌍거래"). README 원장에서 제거, 해소 기록만.
- **(b) 미해소** — `reviews/README.md` §2 **열린 이슈 원장**에 이월하되 *세 가지를 명시*: ① **목적지**(load-bearing·무르익음 → STATE §2 NEXT / 경미·정리성 → §3 OPEN GAPS) ② **게이트 형태**(어떤 플래그를, 0 이면 회귀 0 으로) ③ **arc 정합**(SPINE §6 6계층 순서와 충돌하면 백로그 대기 — review 는 끼어들지 않는다).

> **전파 경로**: 리뷰는 원장에 *기록*만(write). step-loop(`infra-step`)이 다음 조각 고르기 전 원장을 *읽어*(§1) 무르익은 이슈를 STATE §2/§3 로 *승급*하고 게이트 step 으로 구현한다. **STATE 를 직접 고치지 마라** — STATE 권위는 step-loop. review=기록, step=승급·구현. 이 분리가 직교(리뷰 읽기 / step 쓰기)와 6계층 우선순위를 지킨다.

**양방향**: 다음 묶음 리뷰는 *먼저 원장을 재점검* — 코드 변경(grep/spine 사슬)으로 그새 해소된 이슈를 ✅떨군다(원장 무한 누적 방지). 미해소는 그대로 두되 목적지·게이트가 여전한지 갱신.

## 6. 닫기 체크리스트

1. **`reviews/progress/` 갱신** — 이번 묶음이 건드린 서버 항목을 해당 계층 파일에 *기능 리스트*로 반영(무슨 서버 + 기능마다 왜 필요→어떻게 구현→무엇을 했나/남음→지금 어디). 매 리뷰 필수·조건 없음. **진행 지도 없이는 리뷰를 닫지 않는다**(1차 산출물).
2. **단계 평결**(§3.6) — progress/README 박스 상태 맵에서 ⬜/🌱 박스를 추려 *1차 너비 완료 여부 + 이번 묶음이 과심화였나 + 다음 방향(빈 박스 우선 / 2차 개시)* 한 줄을 progress/README 큰 줄기와 원장에 남긴다. 과심화면 §5 이슈로 승급(목적지=STATE §2 NEXT).
3. 감사 §2 검증 재현 전부 실행·인용(spine 사슬 ALL OK 포함) — 미실행 추정 금지.
4. 감사 §1 척추 5불변 판정마다 코드 알리바이(`src/<box>.js:line` 또는 `engine/*.js:line`) 1개 이상.
5. 감사 §3 모든 이슈가 후속 step 에 연결됨(해소 게이트 step or 원장 이월+목적지·게이트).
6. 감사 문서에 narrative 요약표 없음(범위 한 줄 + `progress/` 링크만) — 중복 0.
7. `reviews/README.md` §1 감사 인덱스 append + §2 원장 갱신(해소 떨굼·신규 이월).
8. **알리바이**: `git status` 에 `reviews/`(+스킬) 만 — `src/`·`engine/`·`STATE.md`·`step-NNNN.md` diff **0**(리뷰는 인프라를 안 만진다). 잡히면 되돌려라.

## 금지 사항 (비용·정합 함정)

- **진행 지도 갱신을 거르지 않는다**(§3.5·1차 산출물) — 매 리뷰가 건드린 박스 항목을 `reviews/progress/` 에 인과 서사로 갱신한다(트리거·조건·예외 없음). 감사만 하고 인과를 안 그리면 미완 리뷰.
- **진행 지도를 "무엇을 했나"의 평면 나열로 쓰지 않는다** — *서버를 기능 리스트로 분해*하고 각 기능을 (왜 필요→어떻게 구현→무엇을 했나/남음)으로(§3·§3.5). 기능마다 이론이 다르다 — 서버당 이론 하나로 뭉뚱그리지 않는다. step 나열·상태 기호만으로는 부족하다. 점적 step 전문은 감사·step 문서.
- **진행 지도를 한 파일에 몰지 않는다** — 주제(계층)별 파일·박스(서버) 단위(§3.5).
- **문서 PASS 를 그대로 베끼지 않는다** — 직접 run.js 재현·grep 감사로 확인. 인과 서사도 *실물 코드가 실제로 그렇게 동작함*을 근거로만.
- **STATE·src·engine·step 문서를 고치지 않는다** — 리뷰는 읽기 회고 + 원장·진행 지도 쓰기뿐(권고는 원장에).
- **이슈를 후속 step 연결 없이 남기지 않는다**(§5 불가침) — 떠다니는 이슈 = 미완 리뷰.
- 원장에 ✅해소 이슈 전문을 누적 보존하지 않는다(인덱스서 제거·한 줄 기록만).
- 묶음 밖 step 을 "참고로" 읽지 않는다.
- 한 리뷰에 두 묶음 이상 넣지 않는다 — 10 step = 1 리뷰.
