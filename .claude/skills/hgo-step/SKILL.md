# HGO 디스패처 — "다음 step" 의 단일 진입점

사용자가 "HGO 다음 step / 진행" 처럼 *트랙을 지정하지 않고* 요청하면, 여기서 **어느 트랙을 진행할지 정하고 그 트랙의 실행 스킬을 부른다**. 트랙별 실제 루프(읽기→구현→검증→갱신→닫기)는 각 `hgo-<track>-step` 스킬이 한다 — 이 디스패처는 *고르고 넘기기만* 한다.

## 1. 트랙 선택

1. **사용자가 트랙을 명시했으면**(예 "render 다음 step", "atom step", "net 진행") → 그 트랙. (병행 핀 — 다른 창에서 트랙을 따로 굴릴 때.)
2. **미지정이면** `HGO/ROADMAP.md` 를 읽어 고른다 — **활성(🟢) 트랙 중 가장 foundational(생산자) 하고 다음 ☐ 가 남은 트랙.** 우선순위 = 생산자→소비자 = **atom ▶ render ▶ net**.
   - *왜 이 순서*: atom 이 세계를 만들고 render/net 은 그 세계를 소비(읽기)한다(SPINE §7 층위). 미지정이면 생산자를 먼저 민다 — 임의가 아니라 의존 순서.
   - 고른 트랙 섹션에 ☐ 가 없으면(다 ☑) 다음 활성 트랙으로. 활성 트랙에 남은 ☐ 가 없으면 사용자에게 알린다(다음은 §3 휴면 트랙 깨우기 또는 ROADMAP 재계획).

## 2. 디스패치

고른 트랙 T 의 실행 스킬 **`hgo-T-step` 을 Skill 도구로 호출**한다(예: atom → `hgo-atom-step`). 호출 전에 *어느 트랙을 골랐는지* 한 줄로 알린다(예 "트랙 미지정 → atom 진행"). 이후는 그 스킬의 절차(자기 트랙 섹션 첫 ☐ 자동 선택 → 구현 → 검증 → 갱신 → 닫기)를 그대로 따른다.

## 3. 휴면 트랙 활성화는 자동이 아니다

ROADMAP 마일스톤(◆)에 닿아 render/net 게이트가 열렸어도, 디스패처는 **활성 트랙만 라우팅**한다. 휴면 트랙은 사용자가 "HGO render 트랙 시작" 처럼 *명시적으로*, 되도록 *별도 세션*에서 깨운다(SPINE §7) — 그래야 병행 세션으로 갈린다. **디스패처가 멋대로 새 트랙을 만들지 않는다**(트랙 활성화는 의도적 행위).

## 참고

- **병행**: 트랙을 *지정*하면 그 트랙만 진행 — 다른 창에서 atom 과 render 를 동시에 굴릴 수 있다(쓰는 폴더가 disjoint, SPINE §7). 디스패처(미지정)는 *한* 트랙만 고른다.
- **단일 트랙 상태(지금)**: atom 만 활성이라 미지정 입력은 늘 atom → `hgo-atom-step` 으로 간다.
