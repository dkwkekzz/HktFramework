# HktAdvProtoF 단계 리뷰 — 실행 절차

**작업 디렉토리: `HktAdvProtoF/`** — 이하 상대 경로는 이 폴더 기준.
**규정 원본은 [modules/WORKFLOW.md](../../HktAdvProtoF/modules/WORKFLOW.md) §10** 이다 — 이 스킬은
그 규정을 정확히 로드해 실행하는 방아쇠일 뿐, 규정을 여기 중복 기재하지 않는다. §10 과 이 스킬이
어긋나면 §10 이 이긴다 (어긋남 발견 시 그것부터 보고).

## 실행 순서 (토큰 효율)

1. **읽기** — `STATE.md`(TODO 의 "리뷰 대기" 항목·열린 이슈 표·단계 게이트) →
   `modules/WORKFLOW.md` §10(원칙 셋·절차 다섯·산출물 둘) → `reviews/README.md`(직전까지의 지도·판정) →
   `CLAUDE.md`(북극성 2개). 리뷰 대상 단계의 원문 완료 조건은 `design/Design-ModulePlan.md` §18 에서
   해당 단계만 부분 읽기.
2. **재현** — `app/` 에서 `npm install`(신선한 환경이면) → `npm test` → `npm run verify`.
   수치(테스트 수·통과 수·exit code)를 리뷰에 인용한다. **커밋된** `app/packages/contracts/evidence/*.json`
   을 git 으로 열어 주장(계약 status·STATE.md·커밋 메시지)과 대조 — 불일치가 있으면 `git log` 로
   시점을 짚는다. 재실행 결과가 커밋 상태와 다르면 그 차이 자체가 발견이다.
3. **작성** — §10-2 절차 다섯(재현 → 완료 조건 → MasterPlan 대비 → 북극성 대조 → 이슈업)을 밟아
   `reviews/stageN-review.md` 를 §10-3 뼈대로 쓴다 (파일명에 날짜 금지 — 날짜는 문서 머리에).
   닫힌 단계가 여럿이면 단계별 문서로 나눈다. **§1 은 모듈별 목적→구현→사용처 드릴다운**(§10-3)이다 —
   기획 요약 재서술이 아니라, 목적마다 "무엇을 했나(객체·함수 실명 + 코드 위치 + 내용 요약, 확정
   목록은 실제 나열)" 와 "어떻게 쓰이나(소비 레이어 + 게임 화면에 나타나는 모습)" 로 타고 내려가고,
   끝에 함께 돌아가는 대표 장면을 재실행 실측값으로 세운다.
4. **갱신** — `reviews/README.md` 단계별 표에 한 줄 추가 + 전체 지도·다음 고비·총평 현행화.
   발견 문제는 STATE.md 열린 이슈 표(원본 장부)에 등록하고 GitHub 이슈로 미러, 다음 단계 착수를
   막아야 할 문제면 게이트에 "착수 전" 조건 명시. STATE.md TODO 의 "리뷰 대기" 항목 제거.
5. **닫기** — 커밋 1개(리뷰 문서 + 인덱스 + STATE.md 갱신) 후 결과를 사용자에게 요약:
   판정 한 줄 + 이슈 목록 + 링크.

## 하지 말 것

- 프로토타입 코드·계약·증거를 리뷰가 **바꾸지 않는다** — 리뷰는 읽고 재현하고 기록만 한다
  (이슈 수정은 별도 요청·별도 작업).
- STATE.md·커밋 메시지의 "VERIFIED" 를 재현 없이 옮겨 적지 않는다.
- 구현된 부품을 북극성의 핵심이라 부르지 않는다.
