# CC-THE-EFFECTIVE-IS-DERIVED-NOT-STORED

접수: 2026-08-21 (Feedback) — C023-what-you-wear-changes-you 의 MASTER FEEDBACK 이 보고한
반복 패턴이다. Cycle Agent 는 관찰만 보고했고, 승격 판단은 Human 이 한다.

## CANDIDATE STATEMENT

    여러 출처가 합쳐져 나오는 값은 **저장하지 않고 매번 다시 센다.** 출처가 달라질 때
    저장된 값을 더하거나 빼는 형태를 두지 않는다.

## 무엇을 말하는가 (예시)

    ❌ 흔한 방식 — 걸 때 더하고 풀 때 뺀다

        function equip(actor, item) {
          actor.equipment.set(slot, item);
          actor.physicalAttack += definition(item).attack;   // 더한다
        }
        function unequip(actor, slot) {
          const item = actor.equipment.get(slot);
          actor.equipment.delete(slot);
          actor.physicalAttack -= definition(item).attack;   // 뺀다
        }

        빠르고 읽기 쉽다. 문제는 **그 두 줄이 영원히 짝이 맞아야 한다**는 것이다.
        한쪽 경로에서 빼는 것을 잊으면(실패한 요청 · 예외 · 죽어서 장비가 날아가는
        경로 · 저장/복구) 값이 남는다. 소수 기여가 섞이면 부동소수 오차가 쌓인다.
        같은 물건을 두 자리에 걸었다가 하나만 풀면 무엇을 얼마나 뺄지가 애매해진다.
        그리고 **어긋난 뒤에는 되돌릴 방법이 없다** — 기본값이 어디에도 남아 있지 않다.

    ✅ C023 이 한 것 — 기본값에서 매번 다시 센다

        `content/proto-adventure/world/semantic/combat.ts`
            effectiveStat(actor, stat)
              = actor[stat] + equipmentContributions(actor.equipment)[stat]

        걸기는 자리에 넣는 일만 하고 값을 건드리지 않는다. 푸는 것도 마찬가지다.
        읽는 쪽이 부를 때 기본값에서 다시 센다. 그래서 **"표류하지 않는다" 가 검사가
        아니라 구조**다 — 표류할 자리가 없다. 저장하는 값이 하나뿐이므로 두 진실이
        어긋날 자리도 없다.

    같은 형태를 C022 가 자리에서 먼저 했다

        `world/rules/inventory-room.ts`
            ruleInventoryRoom(inventory) = Σ ⌈수량 / 겹침한도⌉

        `UsedSlots` 를 저장하지 않는다. 저장하면 `Items` 와 `UsedSlots` 라는 두 개의
        진실이 생기고 둘을 맞추는 책임이 **모든 변경 지점으로** 흩어진다 — 그것이
        정확히 "수량 변경은 단일 통로" 가 없애려던 것이다.

    무엇이 달라지나

        지키면    C023 실측 — 백 번 걸고 백 번 풀어도 값이 기본값 그대로다.
                  둘을 걸면 두 번 더해지고 **하나만 풀면 정확히 한 번어치가 남는다.**
                  디버그로 기본값을 50 으로 바꾼 뒤 걸면 62, 풀면 50 — 밖에서 손댄 값과
                  걸어서 생긴 값이 서로를 오염시키지 않는다
        어기면    위 세 각본 중 마지막 둘이 가감 구현에서 반드시 어긋난다.
                  그리고 어긋난 뒤 원래 값을 복구할 방법이 세계에 없다

## OBSERVED REPEATING PATTERN

    C022      `Inventory.UsedSlots` — 쓴 자리를 저장하지 않고 지닌 것에서 센다.
              동기는 "두 개의 진실을 만들지 않는다" 였다

    C023      유효 능력치 — 기본값과 걸린 것들의 기여로 매번 다시 센다.
              동기가 하나 더 붙었다: **되돌아옴이 정확해야 한다.**
              "풀면 정확히 이전의 몸으로" 는 이 Cycle 의 Goal 문장 자체이고,
              가감으로는 그것을 **약속할 수만** 있지 성립시킬 수 없다

    둘이 같은 형태이되 C023 이 이유를 하나 더 댄다 — C022 는 정합성을 위해,
    C023 은 **가역성**을 위해 파생을 골랐다. 그 둘째 이유가 이 후보를 낼 근거다.

## EXPECTED SCOPE

    아이템에 한정되지 않는다. 다만 **모든 값**도 아니다 — 가르는 선은 이렇다.

        대상    출처들의 **현재 상태**로부터 유도되는 값 (유효 능력치 · 쓴 자리)
        비대상  그 자체가 누적의 결과인 값 (HP · 기력 · 지닌 수량) — 이것들은
                "지금 얼마인가" 가 곧 진실이고 유도할 원본이 없다

    이 선을 문장으로 못박는 것이 승격의 실제 작업이다.

## REQUIRES

    - 합성된 값은 읽는 시점에 출처들로부터 계산한다
    - 출처가 달라지는 일(걸기·풀기·조건 부여·만료)은 **출처만** 바꾼다
    - 계산의 자리는 하나다 — 같은 값을 두 곳에서 다르게 세지 않는다

## PROHIBITS

    - 합성 결과를 상태로 저장하고 변경 지점마다 증감시키는 것
    - 관찰 계약에 기본값과 유효 값을 **둘 다** 싣는 것 — 화면이 어느 쪽을 쓸지 고를 수
      있게 되고 그 순간 세계의 권위가 둘이 된다 (C023 03 RATIONALE 8)

## PREFERS

    - 계산 비용이 걱정되면 캐시가 아니라 **출처의 수를 줄이는** 쪽을 먼저 본다.
      C023 은 자리 수가 고정(6)이라 계산이 상수이므로 캐시가 필요 없었다

## POTENTIAL CONFLICTS

    없음으로 보이나 하나가 남는다 — **영속(IE §39)** 이 서면 "저장하지 않는 값" 을
    저장/복구가 어떻게 다루는지가 물음이 된다. 답은 자명해 보인다(출처만 저장하고
    복구 뒤 다시 센다). 그리고 그 자명함이 이 원칙의 값어치이기도 하다 —
    IE §46 Test 13 이 걱정한 "로드를 두 번 하면 값이 누적된다" 가 애초에 불가능해진다.

## WHY THIS SHOULD BECOME A CONSTRAINT

    Cycle 둘이 독립적으로 같은 형태를 골랐고, 둘 다 그 이유를 03 의 RATIONALE 1번
    자리에 적었다. 그런데 **다음에 이 물음이 오는 곳은 아이템이 아니라 조건 층**이고,
    그 층은 아직 설계 문서가 없다 (MC-CONDITION-STACKING 이 `grounded: false`).
    문서가 오기 전에 이 형태가 원칙으로 서 있으면, 그 문서를 주입할 때 얼개를 하나로
    묶을 근거가 된다. 뒤에 세우면 이미 갈라진 둘을 합치는 일이 된다.

    세우지 않으면 위험은 조용하다 — 가감 구현은 **대부분의 경우 맞는 값을 낸다.**
    어긋나는 것은 실패 경로 · 중복 적용 · 복구처럼 드문 자리이고, 그런 버그는
    한참 뒤에 "값이 이상하다" 로만 나타난다.
