# [00·2.2] 행렬과 변환 (Matrices & Transforms)

> 회전·스케일·평행이동을 한 언어로 합성하는 아핀 4x4 행렬. 월드↔로컬, scene graph 계층의 토대.

## 1. 선형변환 vs 아핀변환 — 왜 4x4 인가

**선형변환(linear transform)** 은 행렬 곱 하나로 표현되는 변환이다. 정의상 `f(a+b) = f(a)+f(b)`, `f(k·a) = k·f(a)` 를 만족하며, 기하적으로 **원점을 고정**한다. `R^3` → `R^3` 의 회전·스케일·전단(shear)은 모두 선형이라 **3x3 행렬**로 충분하다.

문제는 **평행이동(translation)** 이다. 원점을 옮기므로 위 선형 조건을 깨고 — 즉 3x3 행렬 곱으로는 표현할 수 없다. 이를 통합하려고 **동차좌표(homogeneous coordinates)** 와 한 차원 높은 4x4 행렬을 쓴다.

```
점:    p = (x, y, z, 1)     // w=1 → 평행이동의 영향을 받음
벡터:  v = (x, y, z, 0)     // w=0 → 방향이므로 평행이동 무시, 회전/스케일만 적용
```

`w` 성분이 점과 방향벡터를 가르는 스위치다. 법선·속도 같은 **방향**을 변환할 땐 반드시 `w=0` 으로 둔다.

**아핀변환(affine transform)** = 선형변환 + 평행이동. 동차좌표 위에서 다음 4x4 행렬 하나로 표현된다.

```
      | R00 R01 R02 | Tx |        ┌ 좌상단 3x3 R : 회전·스케일·전단 (선형부)
M  =  | R10 R11 R12 | Ty |   ──→  │ 오른쪽 열  T : 평행이동
      | R20 R21 R22 | Tz |        └ 마지막 행 (0 0 0 1) : 동차좌표 유지
      |  0   0   0  |  1 |
```

핵심은 **선형부 `R` 과 평행이동 `T` 가 한 행렬 안에서 자리만 분리돼 공존**한다는 점이다. 점은 `p' = M·p` 로 회전+이동이 한 번에 적용되고, 방향벡터는 `w=0` 이라 `T` 열이 무시돼 `R` 만 적용된다.

> 스케일은 별도 자리가 없다 — 좌상단 3x3 안에서 회전과 곱해져 `R·S` 형태로 들어간다(`S = diag(sx,sy,sz)`). UE 규약의 적용 순서는 Scale → Rotate → Translate, 즉 `M = T·R·S`. 자세한 전개는 아래 [실전 예제](#실전-예제--캐릭터무기-소켓-월드-변환-ue5-규약) 참조.

## 2. 변환 합성 — 결합법칙 O, 교환법칙 X

여러 변환을 이어 붙일 때는 행렬을 곱한다.

```
M_total = M_a * M_b      // "먼저 M_b, 그다음 M_a" (열벡터 규약: column-major / right-multiply)
```

오른쪽 행렬이 점에 **먼저** 닿으므로 오른쪽→왼쪽 순으로 적용된다. 행렬곱의 두 성질이 합성의 규칙을 정한다.

- **결합법칙 성립**: `(A*B)*C = A*(B*C)` — 부분 변환을 미리 곱해 캐싱할 수 있다(scene graph 가 이걸 활용).
- **교환법칙 불성립**: `A*B != B*A` — **회전·이동의 순서가 결과를 바꾼다.** 부착 순서 버그의 근본 원인이며, 구체적 수치 비교는 아래 실전 예제에서 다룬다.

## 3. 좌표계 변환 (basis change) — 월드↔로컬

한 좌표계의 점을 다른 좌표계로 옮기는 것이 **기저 변환(basis change)** 이다. 대상 좌표계의 **기저벡터(basis vectors)를 열로 갖는 행렬**을 곱하면 된다.

```
M 의 각 열 = 새 좌표계의 축(기저)이 기존 좌표계에서 갖는 방향
```

월드↔로컬, 모델↔뷰(model↔view) 변환이 모두 이 한 가지 연산이다. 캐릭터의 월드 행렬은 곧 "캐릭터 로컬 좌표계의 기저를 월드에 박은 것" 이고, 그 역행렬이 월드점을 로컬로 되돌린다(§4).

---

## 4. 정규직교 행렬과 전치 — 역행렬을 공짜로

**정규직교 행렬(orthonormal / orthogonal matrix)**: 열(및 행)이 서로 직교하는 **단위벡터**인 행렬. **순수 회전 행렬**이 여기 속한다(비균등 스케일이 섞이면 깨진다). 핵심 성질은 다음과 같다.

```
R^T * R = I          // 전치(transpose)가 곧 역행렬
R^-1 = R^T           // 역행렬을 전치로 공짜 획득 — 성능상 큰 이점
det(R) = +1          // 순수 회전 (반사가 섞이면 -1)
|R v| = |v|          // 길이 보존 (isometry)
```

실무 임팩트: 회전 행렬의 역을 구할 때 일반 역행렬 계산(가우스 소거, O(n³))을 돌릴 필요 없이 **행/열만 바꾸면(전치)** 된다. 월드→로컬 역변환이 빈번한 게임에서 결정적인 최적화다.

> ⚠️ 전제 조건: 이 등식은 **정규직교일 때만** 성립한다. 비균등 스케일이 섞인 `R·S` 에는 적용되지 않는다 — 역변환 시 `S^-1` 을 따로 처리해야 하고, 법선 변환은 **역전치(inverse transpose)** 가 필요하다(아래 [관련 함정](#관련-함정) 참조).

## 5. 직교 기저 만들기 (Gram-Schmidt)

법선 하나로부터 **접선 공간(tangent space)** 의 직교 기저를 즉석에서 만드는 절차다. 마찰(friction) 방향 계산, 접촉 좌표계(contact frame) 구성 등에 자주 쓴다.

```
1) n 정규화
2) 보조벡터 a 선택 — n 과 평행하지 않게: |nx| < 0.9 면 a=(1,0,0), 아니면 (0,1,0)
3) t1 = normalize( a - (a·n)*n )    // a 에서 n 성분 제거 후 정규화
4) t2 = n x t1                       // 외적이라 이미 직교·단위
```

결과 `(t1, t2, n)` 이 정규직교 기저이므로, 이 세 벡터를 열로 모으면 곧 §4 의 회전 행렬이 된다.

## 실전 예제 — 캐릭터→무기 소켓 월드 변환 (UE5 규약)

위 추상 개념을 실제 게임 데이터로 굴려 보자. UE5 규약을 그대로 쓴다: **단위 cm, Z-up, 전방 +X·우측 +Y·상방 +Z**, 회전은 `FRotator(Pitch, Yaw, Roll)` 이고 yaw 는 Z 축 회전. 한 틱에서 "총구(muzzle) 가 월드 어디에 있는가" 를 구하는 흔한 문제다.

주어진 게임 데이터:
- 캐릭터 액터 월드 변환 (`AActor::GetActorTransform`): 위치 `T = (1000, 500, 0)`, **yaw = 90°**, 스케일 1.
- 총구 소켓의 **로컬** 오프셋(캐릭터 기준, `USkeletalMeshComponent` 소켓에서 읽음): `p_local = (50, 0, 150)` — 전방 50cm, 상방 150cm.

yaw 90° → `cos90°=0, sin90°=1`. 캐릭터의 4x4 월드 행렬(아핀):

```
        | 0  -1   0   1000 |       cos -sin 0 | Tx
M_char = | 1   0   0    500 |   ←   sin  cos 0 | Ty   (Z축 yaw + 평행이동)
        | 0   0   1      0 |        0    0  1 | Tz
        | 0   0   0      1 |
```

소켓 로컬점을 동차좌표 `(50, 0, 150, 1)` 로 보고 `p_world = M_char * p_local`:

```
x' = 0*50  + (-1)*0 + 0*150 + 1000 = 1000
y' = 1*50  +   0*0  + 0*150 +  500 =  550
z' = 0     +   0    + 1*150 +    0 =  150
p_world = (1000, 550, 150)
```

전방 +X 오프셋(50)이 yaw 90° 로 +Y 로 회전해 월드 Y 가 500→550 으로 늘었고, 상방 150 은 yaw(Z축 회전) 영향을 받지 않아 그대로 z=150. **w=1 이라 평행이동 `T` 가 더해진** 점이 핵심 — 만약 총구의 *발사 방향벡터* 를 옮긴다면 `w=0` 으로 두어 `T` 를 무시하고 회전만 적용한다.

**역변환 — 월드점을 캐릭터 로컬로 되돌리기** (`AActor::GetTransform().InverseTransformPosition`): 회전부 `R` 이 정규직교라 역행렬은 **전치 `R^T`** 로 공짜로 얻는다(위의 `R^-1 = R^T`).

```
p_local = R^T * (p_world - T)
        = R^T * ( (1000,550,150) - (1000,500,0) )
        = R^T * (0, 50, 150)

R^T = |  0  1  0 |   (R 의 전치)
      | -1  0  0 |
      |  0  0  1 |

x = 0*0 + 1*50 + 0*150  =  50
y = -1*0 + 0*50 + 0*150 =   0
z = 0 + 0 + 1*150       = 150
→ (50, 0, 150)   ✅ 원래 로컬 오프셋 복원
```

**합성과 비교환성 확인**: 총을 *손 소켓* 에 붙이고, 총구는 다시 *총 기준* 으로 정의하는 계층(scene graph)이라면 `M_muzzle_world = M_char * M_hand * M_gun`. 순서를 바꿔 `M_gun * M_hand` 로 곱하면 전혀 다른 자세가 나온다(`A*B != B*A`). 실제로 yaw 90° 회전 후 (50,0,0) 이동 vs (50,0,0) 이동 후 yaw 90° 회전은 각각 월드 `(1000,550,0)` 과 `(1050,500,0)` 로 갈린다 — 부착 순서 버그의 전형이다.

> UE5 주의: UE 는 **좌수(left-handed) 좌표계**에 행벡터·행우선(`FMatrix`, `v' = v * M`) 규약이라, 위 열벡터 수학 교과서 표기와 곱 순서/yaw 부호가 다를 수 있다([00-foundations §3](../00-foundations.md#3-한눈-요약--도구-비교) handedness 참조). 또 `FTransform` 은 회전을 행렬이 아닌 `FQuat` 로 저장하고 적용 순서는 **Scale → Rotate → Translate** 다. 수치 결과의 *의미* 는 같다.
