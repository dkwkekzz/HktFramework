# [00.2] 행렬과 변환 (Matrices & Transforms)

## 1. 왜 행렬인가 — 동기

벡터([01-vectors.md](01-vectors.md))가 "점과 방향을 담는 그릇"이라면, 행렬은 그 그릇들을 **한꺼번에 변환하는 함수**다. 회전, 스케일, 전단(shear)은 모두 **선형 변환(linear transform)** — 즉 `T(a + b) = T(a) + T(b)`, `T(s·a) = s·T(a)` 를 만족하는 변환 — 이고, 선형 변환은 정확히 행렬로 표현된다. 행렬-벡터 곱 한 번이 곧 변환의 적용이다.

문제는 **이동(translation)** 이다. 이동은 선형이 아니다(`T(0) ≠ 0`). 원점을 옮기기 때문이다. 게임의 씬 그래프(scene graph)는 "회전·스케일·이동을 한 객체로 합성하고 계층적으로 누적"하기를 원하는데, 3x3 선형 행렬만으로는 이동을 끼워 넣을 수 없다. 이 간극을 메우는 발명이 **동차좌표(homogeneous coordinates)** 와 **4x4 아핀 행렬(affine matrix)** 이다. 이것이 이 문서의 중심 무대다.

좌표계 규약을 명시한다(허브 §3). 별도 언급이 없으면 **열벡터(column vector)·열 우선(column-major)** 수학 교과서 관례로 식을 쓴다. `M v` 는 "벡터 v 에 변환 M 을 적용". 합성은 **오른쪽에서 왼쪽으로** 읽는다 — `M = T R S` 는 "먼저 S(스케일), 다음 R(회전), 마지막 T(이동)". 엔진별 행/열 우선 차이는 §6에서 정면으로 다룬다.

## 2. 정의 — 동차좌표와 아핀 4x4

3D 점 `(x, y, z)` 에 네 번째 성분 `w` 를 붙여 `(x, y, z, w)` 로 확장한다. 점은 `w = 1`, 방향(벡터)은 `w = 0` 으로 둔다. 이 한 비트가 결정적 차이를 만든다 — 이동 행은 `w` 와 곱해지므로, **점은 이동되고 방향은 이동되지 않는다**. 물리적으로 정확하다. "위치"는 옮겨야 하지만 "속도·법선 같은 방향"은 평행이동에 불변이어야 하기 때문이다.

아핀 변환은 4x4 행렬로 쓴다. 상단 3x3 블록 `A` 가 선형부(회전·스케일·전단), 우측 3x1 열 `t` 가 이동, 하단 행은 `(0 0 0 1)`.

```
       | A00 A01 A02 | tx |
M  =   | A10 A11 A12 | ty |
       | A20 A21 A22 | tz |
       |  0   0   0  | 1  |
```

점 `p = (px, py, pz, 1)` 에 적용하면:

```
M p = ( A · (px,py,pz) + t , 1 )
```

즉 "선형부로 돌리고 늘인 뒤 t 만큼 옮긴다". 방향 `d = (dx, dy, dz, 0)` 에 적용하면 `t` 항이 사라져 `M d = (A·d, 0)` — 이동 없이 선형부만 작용한다. 이것이 `w` 트릭의 핵심이다.

## 3. 수식 — 합성·역행렬·법선 변환

### 3.1 합성 (composition)

변환의 누적은 행렬 곱이다. 객체 로컬 → 부모 → 월드 로 올라가는 씬 그래프는 각 단계 행렬을 곱해 누적한다.

```
M_world = M_parent * M_local
p_world = M_world * p_local
```

행렬 곱은 **결합법칙은 성립하지만 교환법칙은 성립하지 않는다**(`R S ≠ S R`). "먼저 회전 후 스케일"과 "먼저 스케일 후 회전"은 다른 결과다 — 비균등 스케일이 끼면 특히 그렇다. 그래서 표준 TRS 순서(`M = T R S`)를 합의해 두는 것이 중요하다.

### 3.2 역변환 (inverse)

부모 좌표를 로컬로 되돌리거나, 월드 공간 광선을 객체 로컬로 끌어올 때 역행렬이 필요하다. 일반 4x4 역행렬은 비싸지만, **아핀이고 선형부가 회전(직교)뿐이면** 닫힌 형태로 싸게 구한다.

```
# A 가 순수 회전 R (직교, det=+1) 이고 이동이 t 일 때
M^-1 = | R^T | -R^T t |
       |  0  |    1   |
```

회전의 역은 전치(`R^-1 = R^T`)라는 사실(§4)을 이용한 것이다. 스케일이 섞이면 이 지름길이 깨지므로, 균등 스케일까지만 닫힌 형태로 처리하고 일반 비균등 스케일·전단은 정식 역행렬을 쓴다.

### 3.3 법선 변환 — 역전치 (inverse transpose)

이 절은 실무에서 가장 자주 틀리는 지점이다. 점과 방향은 `M`(또는 그 3x3 선형부 `A`)로 변환하면 되지만, **표면 법선(normal)** 은 그렇지 않다. 법선은 "표면에 수직"이라는 성질로 정의되는데, **비균등 스케일** 행렬로 법선을 그냥 변환하면 더 이상 표면에 수직이 아니게 된다.

직관: x축으로만 2배 늘인 평면을 생각하자. 평면 위 접선 벡터는 x로 늘어나지만, 그에 수직이던 법선은 오히려 **x 방향으로 줄어들어야** 수직이 유지된다. 즉 법선은 접선과 "반대로" 변환되어야 한다. 수식으로, 접선 `t` 와 법선 `n` 의 수직 조건 `n · t = 0` 을 변환 후에도 보존하려면:

```
n' = (A^-1)^T  n        # = inverse-transpose 로 법선 변환
```

(유도: `n'·t' = (A^-T n)·(A t) = n^T A^-1 A t = n^T t = n·t`. 직교성이 보존된다.) `A` 가 순수 회전이면 `A^-T = A` 이므로 차이가 없지만(그래서 평소엔 티가 안 난다), 비균등 스케일이 들어오는 순간 역전치를 써야만 라이팅·충돌 법선이 올바르다. 변환 후에는 길이가 변하므로 **재정규화**도 잊지 말 것([01-vectors.md](01-vectors.md) §4).

## 4. 알고리즘 — 정규직교성과 Gram-Schmidt 재직교화

회전 행렬의 3x3 블록은 **정규직교(orthonormal)** 여야 한다 — 세 열(또는 행)이 서로 직교하는 단위 벡터다. 이때 `R^T R = I`, `R^-1 = R^T`, `det(R) = +1`(반사가 없는 순수 회전). 이 성질이 깨지면 회전이 스케일·전단을 슬그머니 섞기 시작한다.

문제는 **수치 누적**이다. 각속도로 회전 행렬을 반복 적분하면(상세 [03-rotations.md](03-rotations.md)), 부동소수점 오차가 쌓여 열들이 더 이상 정확히 직교·단위가 아니게 된다. 그대로 두면 객체가 미세하게 늘어나거나 찌그러진다. 해법은 주기적으로 **재직교화(re-orthonormalization)** 하는 것이고, 고전적 도구가 **Gram-Schmidt** 다.

```
# 3x3 회전 행렬의 세 열 c0, c1, c2 를 재직교화
function gram_schmidt(c0, c1, c2):
    c0 = normalize(c0)                       # 첫 축을 기준으로 고정
    c1 = c1 - (c1 · c0) * c0                  # c1 에서 c0 성분 제거
    c1 = normalize(c1)
    c2 = c2 - (c2 · c0) * c0 - (c2 · c1) * c1 # c2 에서 c0,c1 성분 제거
    c2 = normalize(c2)
    return (c0, c1, c2)
```

핵심 아이디어는 "각 축에서 이미 확정된 앞 축들의 성분(내적으로 측정)을 빼내어 직교하게 만든 뒤 정규화"다. 단, 고전 Gram-Schmidt 는 입력이 거의 종속이면 수치적으로 불안정하다. 실무에서는 (a) 자주 호출해 드리프트를 작게 유지하거나, (b) 더 안정한 변형을 쓰거나, (c) 애초에 **회전을 사원수로 보관**해 정규화 한 번(4성분)으로 끝내는 길을 택한다 — 후자가 현대 엔진의 표준이며, 그래서 행렬 재직교화는 점점 덜 쓰인다([03-rotations.md](03-rotations.md)).

마지막으로 `det(R) = -1` 이면 반사(거울상)가 섞인 것이다. 이는 좌표계 손잡이를 뒤집으므로, 회전이어야 할 행렬에서는 결코 허용해선 안 된다.

## 5. UE5 워크드 예제 — `FTransform` 합성과 법선

UE5 의 Chaos 는 변환을 일반 4x4 대신 **분해된 형태** `FTransform = (Rotation: FQuat, Translation: FVector, Scale3D: FVector)` 로 보관한다. 행렬보다 회전을 사원수로 다루기 쉽고, 보간·정규화가 싸기 때문이다.

자식 변환을 부모로 누적하는 합성은 다음 의미를 갖는다(개념 코드).

```cpp
// 월드 = 부모 * 로컬  (UE 관례: A * B 는 "B 먼저, A 나중")
FTransform LocalToWorld = ParentToWorld * ChildLocal;

// 한 점을 로컬에서 월드로
FVector WorldP = LocalToWorld.TransformPosition(LocalP);   // w=1 취급: 스케일·회전·이동 모두 적용
FVector WorldDir = LocalToWorld.TransformVector(LocalDir); // w=0 취급: 이동 제외, 스케일·회전만
```

`TransformPosition` 은 점(이동 포함), `TransformVector` 는 방향(이동 제외)을 처리한다 — 정확히 §2의 `w=1`/`w=0` 구분이다. 그런데 **법선**은 또 다르다. 비균등 `Scale3D` 에서 법선을 `TransformVector` 로 옮기면 §3.3 의 함정에 빠진다. UE 는 이를 위해 별도 경로를 제공한다.

```cpp
// 비균등 스케일에서 법선을 올바르게: 역전치(스케일의 역수) 적용 후 재정규화
FVector WorldN = LocalToWorld.TransformVectorNoScale(LocalN); // 스케일 무시(균등/회전만일 때)
// 또는 비균등 스케일이 실재하면 스케일의 역수를 곱한 뒤 정규화하는 보정 경로를 사용
WorldN = WorldN.GetSafeNormal(); // 변환 후 반드시 재정규화
```

또 하나의 UE 특이점은 **좌표계**다. UE 는 **왼손 좌표계, Z-up**(X 전방, Y 우측, Z 상방)이고 회전 단위로 도(degree) 기반 `FRotator`(Pitch/Yaw/Roll)를 노출한다. 외부 라이브러리(대개 오른손·Y-up·라디안)와 데이터를 주고받을 때는 **축 재배치 + 손잡이 반전 + 단위 변환**이 모두 필요하다. 이 경계 변환을 한 곳에 격리하지 않으면 외적 부호·회전 방향 버그가 산발한다(허브 §5).

마지막으로 UE5 의 `FVector` 는 **double(LWC)** 다. 거대 월드의 떨림을 줄이기 위한 엔진 차원의 대응이며(상세 [05-numerical-floating-point.md](05-numerical-floating-point.md)), 변환 누적 과정의 정밀도에도 영향을 준다.

## 6. 실무 트레이드오프 — row/column-major 와 handedness

### 6.1 메모리 레이아웃 vs 수학 규약 — 서로 다른 두 축

여기서 가장 큰 혼란이 발생하므로 두 개념을 분리한다.

- **저장 레이아웃(row-major vs column-major)**: 행렬 16개 float 을 메모리에 행 순서로 까느냐 열 순서로 까느냐. 이는 순전히 메모리 배치 문제다.
- **벡터 관례(row-vector vs column-vector)**: `v M` 로 쓰느냐 `M v` 로 쓰느냐. 이는 곱 순서와 합성 방향을 결정하는 수학 규약이다.

두 축이 독립이지만 전통적으로 묶여 다닌다.

| 진영 | 저장 | 벡터 | 곱 순서(합성) |
|---|---|---|---|
| DirectX / HLSL | row-major | row-vector | `v M`, 합성은 **왼→오** (`S R T`) |
| OpenGL / 수학 교과서 | column-major | column-vector | `M v`, 합성은 **오→왼** (`T R S`) |

핵심 사실: **row-major 저장 + row-vector** 와 **column-major 저장 + column-vector** 는 메모리 바이트가 동일하다. 한 관례를 다른 관례로 해석하면 그 행렬은 **전치(transpose)** 된 것으로 보인다. 그래서 두 엔진/셰이더 환경 사이에서 행렬을 주고받을 때 "전치가 필요한가?"를 항상 확인해야 한다. 잘못 넘기면 회전이 통째로 뒤집혀 보인다.

### 6.2 handedness — 외적 부호와 회전 방향

좌표계 손잡이(오른손/왼손)는 외적의 부호([01-vectors.md](01-vectors.md))와 양의 회전 방향을 결정한다. 오른손계에서 `+z` 축 양의 회전은 `x→y` 반시계, 왼손계에서는 시계다. UE5(왼손·Z-up), Unity(왼손·Y-up), OpenGL/대부분 수학 문헌(오른손·Y-up)이 제각각이다. 행렬 자체에 손잡이가 "내장"되는 게 아니라, **벡터·외적·회전 공식을 작성할 때 가정한 손잡이**가 일관되어야 한다. 혼용은 부호 버그의 단골이다.

### 6.3 실용 지침

- 프로젝트 안에서 **저장 레이아웃·벡터 관례·손잡이를 한 번 정하고 문서화**한다.
- 외부 인터롭(셰이더 상수 버퍼, 임포트한 메시, 외부 물리 라이브러리)은 **경계에서만** 변환(전치/축 재배치/단위 변환)한다.
- 비균등 스케일이 있으면 **법선은 역전치**로(§3.3), 변환 후 **재정규화**.
- 회전은 가능하면 행렬 대신 **사원수**로 보관해 재직교화 비용을 피한다([03-rotations.md](03-rotations.md)).

## 7. 실무 (엔진은 무엇을 쓰는가)

- **DirectX/HLSL 계열**: row-major·row-vector 전통(`mul(v, M)`). 셰이더로 넘길 때 전치 여부가 단골 이슈.
- **OpenGL/GLSL·수학 문헌**: column-major·column-vector(`M * v`).
- **Bullet**: `btTransform`(회전 `btMatrix3x3` + 이동 `btVector3`)으로 분해 저장 — 4x4 를 풀어 들고 다님. 역변환은 회전 전치 지름길 사용.
- **PhysX**: `PxTransform`(`PxQuat` + `PxVec3`) — 회전을 사원수로. 행렬 `PxMat44` 는 렌더/임포트 경계용.
- **Jolt**: `Mat44`(column-major, SIMD), 강체 자세는 `Quat`. `RMat44`(double 평행이동 버전)로 큰 월드 대응.
- **Chaos(UE5)**: `FTransform`(`FQuat`+`FVector`+`Scale3D`), `FMatrix`(row-major·row-vector, UE 관례). **왼손·Z-up**, `FVector` 는 **double(LWC)**. 법선은 비균등 스케일에서 역전치 보정 경로.

공통 패턴: **변환을 풀 4x4 가 아니라 (사원수 회전 + 벡터 이동 [+ 스케일])로 분해 저장**하고, 행렬은 렌더/임포트 경계에서만 만든다. 회전을 사원수로 두면 재직교화가 정규화 한 번으로 끝나기 때문이다.
