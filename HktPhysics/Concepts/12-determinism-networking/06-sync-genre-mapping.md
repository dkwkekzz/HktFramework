# [12·2.6] 물리 동기화: 전체 시뮬 vs 상태 복제 — 장르 매핑 (Sim-share vs State-replication)

> 두 축(입력 전송 / 상태 전송)의 트레이드오프를 한 표로 못 박고, 어떤 장르가 왜 어느 쪽을 고르는지 직관으로 잇는다.
> **상위 노드**: [12-determinism-networking.md](../12-determinism-networking.md) · **상위 지도**: [README.md](../README.md) · **의존**: [05-network-models](05-network-models.md)

---

[05-network-models](05-network-models.md) 의 네 모델은 결국 두 축으로 수렴한다 — **전체 결정적 시뮬을 공유(입력 전송)** 하느냐, **상태를 복제(transform 전송)** 하느냐.

| 축 | 전체 결정적 시뮬 (입력 전송) | 상태 복제 (transform 전송) |
|---|---|---|
| 보내는 것 | 입력만 | 위치/회전/속도 스냅샷 |
| 대역폭 | 객체 수 무관 (입력 크기) | 객체 수에 비례 |
| 결정론 요구 | **필수** (bit-exact) | 거의 불필요 |
| 권위 | 분산(모두 동일 시뮬) 또는 서버 | 서버 권위 |
| 실패 모드 | desync (전체 붕괴) | 약간의 위치 오차/보정 튐 |
| **장르** | **RTS, 격투, lockstep MMO, 시뮬** | **FPS/슈터, 배틀로얄, 대규모 MMO** |

## 어떻게 고르는가 — 직관

동기화해야 할 **동적 객체가 많고**(수천 유닛) 대역폭이 병목이면 → 결정적 시뮬(입력 전송). 입력만 보내므로 유닛이 1000이든 10000이든 대역폭이 같다. 대신 결정론이 깨지면 전체가 붕괴하고, 모든 비결정 진입점을 닫는 비용을 처음부터 치러야 한다([04-deterministic-sim-requirements](04-deterministic-sim-requirements.md)).

동적 객체가 적고(플레이어·발사체) **반응성·치트 저항** 이 우선이면 → 서버 권위 상태 복제. 상태를 직접 보내니 결정론이 거의 필요 없고 서버가 진실이라 치트에 강하다. 대신 대역폭이 객체 수에 비례하고, 보정 시 약간의 튐이 생긴다.

> 많은 현대 게임은 **혼합** 이다 — 핵심 캐릭터/발사체는 서버 권위 상태 복제(반응성·공정성), 잔해/장식 물리는 비동기 로컬(결정론 불필요, 화면용). "모든 물리를 한 모델로"가 아니라 *객체의 역할별로* 동기화 전략을 나누는 게 실무의 정답에 가깝다.
