# 플레이어블 설계 — 사람이 세계에 들어온다 (Playable)

> **종류:** 플레이어 층 설계 (입력·권위·상태 계약 + 플레이어블 로드맵 P0~P3)
> **상위 설계:** [Design-WorldComposition.md](Design-WorldComposition.md)(콘텐츠) ·
> [Design-Visualization.md](Design-Visualization.md)(본격 렌더 — P3 에서 합류)
> **상태:** v0.1 / 2026-07-20 — P0 구현·검증 완료 (`src/play/`, `demo/play.*`, `test/play.test.js`)
> 불변 원칙 ①~⑥은 [CLAUDE.md](CLAUDE.md).

## 1. 원칙 — 플레이어는 특별하지 않다

봇·NPC·플레이어는 **같은 행위자 사슬**을 쓴다 (상위 설계 §7): 상태 변경은 법칙 `apply()` 로만,
완료는 `done_when` 술어로만, 진행은 파문으로만. 플레이어 층이 추가하는 것은 규칙이 아니라
**입력 통로와 상태 화면**뿐이다. 그래서:

- **서버가 권위다.** 클라이언트에는 게임 규칙이 한 줄도 없다 — 버튼 배치는 표현이고 판정은
  전부 서버(법칙·시간 창·에너지). `test/play.test.js` 가 클라이언트의 `src/` import 0 을 강제한다
  (불변 원칙 ⑥의 플레이 버전).
- **시간은 하나다.** 전역 CycleClock 을 실시간 구동기(`tick_ms`)가 민다. 이동은 액터별 travel 로
  따로 센다 — 개인 이동이 전역 시계를 밀면 타인의 시간이 왜곡된다(멀티플레이 요건).
- **규칙 거부는 오류가 아니라 피드백이다.** 창 밖·에너지 부족·경로 없음은 HTTP 200 +
  `{ok:false, error}` — 세계가 말을 거는 방식이다.

## 2. P0 — 구현된 것 (첫 플레이어블 수직 절편)

| 구성 | 실물 | 내용 |
|---|---|---|
| 게임 | `src/play/game.js` | join·move(지역 그래프·비용 틱)·act(법칙 경유)·setActiveGoal·tick·state |
| 페이싱 | `data/world-play.yaml` | 플레이 주기(순행 90/25 등 축소판)·원천(regen/gate/consume)·초기 에너지 |
| API | `demo/server.js` `/api/play/*` | join / act / move / goal / state — 폴링 |
| 클라이언트 | `demo/play.html` `play.js` | 지도(클릭 이동)·무대 카드(행동 버튼)·목적 카드(조건 서술, 퍼센트 금지)·주기 칩·피드·소지품. `?name=` 자동 입장, `?id=` 재접속 |
| 검증 | `test/play.test.js` 9건 | C1 루프 완주·시간 창 거부·이동/발견·R0 월식 잠금·소진 경쟁·플레이어 독립·HTTP 종단·원칙 ⑥ |

P0 에서 플레이 가능한 것: **C1 루프**(창 안 채취→관찰→수확) + 심장 적출(분산 창, 소진 경쟁,
DAG 이중 파문) + R2 채굴(표층/심부) + R3 균류·정제 + R5 협상 + 지역 이동·무대 발견 + 봇과 동거
(타인의 파문·경쟁). 같은 주소를 여러 탭/기기로 열면 같은 세계다.

## 3. 페이싱 규약

- 콘텐츠 정본(world-composition `cycles`)은 시뮬 틱 기준, 플레이 픽스처(world-play)는 실시간
  기준의 **축소판**이다. 서로 소 관계는 유지한다. 두 파일의 주기 이름은 반드시 일치.
- 원천 규약: `regen`(창이 열리면 되살아남 — 리듬의 산물, 스폰 아님) · `gate`(그 창에만 상호작용)
  · `consume`(성공 시 소진 — 선착 경쟁). 새 무대를 플레이에 올릴 때 이 세 속성만 정하면 된다.

## 4. 로드맵 — P1~P3

- **P1 — 플레이가 깊어진다**: 전투(둥지·수송대)와 제작 개입(결합 중 폭주 제어)을 버튼이 아닌
  **과정**으로. 방사형/별자리 뷰(demo/graph-*.js)를 플레이 화면에 통합(내 믿음 그래프 열람),
  가설 수립·실험 UI(H1/H2), 상향 발견(retro-bind) 연출. 활성 말단의 demand 공명 표시(§6.4).
- **P2 — 세계가 남는다**: 세계 스냅샷 영속(서버 재시작 생존), 계정(이름→고정 id), 관전 페이지와
  통합, aftermath 가 플레이어 간에 흐르는 시나리오(한 명의 완료가 다른 플레이어의 신규 목적).
- **P3 — 보이는 세계**: Design-Visualization 의 하이브리드 렌더(three.js·속성 채널)가 이
  상태 payload 의 Scene 서술자 판을 소비한다 — play.js 는 임시 렌더러였고 여기서 교체된다
  (렌더러 교체 가능 원칙 ⑥의 실행).

각 P 단계는 CLAUDE.md §3 step 규율(구현→검증→기록)을 따르고, 완료 판정은 "사람이 브라우저로
그 플레이를 실제로 할 수 있고, 같은 플레이가 테스트로 재현된다"이다.
