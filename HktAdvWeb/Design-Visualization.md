> **종류:** 시각화·렌더 설계 (계획/설계 전용 — 본 문서는 코드를 동반하지 않는다)
> **상위 설계:** [Design-ObjectiveHierarchy.md](Design-ObjectiveHierarchy.md) — 특히 §6 시각 표현을 구체화한다
> **상태:** v0.1 / 2026-07-20
> 불변 원칙(특히 ⑤ 검증·⑥ 렌더 분리)은 [CLAUDE.md](CLAUDE.md).

## 1. 목표·전제

목적 계층 설계 §6이 정한 시각 언어(속성은 행동으로 보인다 · 앎의 상태를 그린다 · 숫자 없는
파문)를 **실제로 만들 수 있는 형태**로 구체화한다.

전제:

- **아트 리소스는 전량 AI 에이전트가 생산한다** — 수작업 보정 없이 파이프라인(§7)으로 품질을 보장한다.
- **타겟: 모바일 + PC**, 웹 브라우저 실행. 성능 예산은 모바일 기준으로 잡는다 (§8).
- **실행 환경은 서버+클라이언트 웹 구성**: 원클릭 실행 스크립트 → 설치→테스트→서버→봇→관전
  브라우저, 자동 회귀(`npm test`) + 스크린샷 눈 검증(`npm run shot`)이 상시 재현된다 (§9).
- **3D 지면 + 고정 뷰 + 스프라이트 중심 하이브리드**: 세계는 3D 공간이지만 카메라는 고정되고,
  대부분의 존재는 스프라이트다. 3D 는 필요한 곳에만 쓴다 (§3).

핵심 결정 한 줄 요약:

> **에셋은 속성을 모르고, 속성은 셰이더가 그린다.** AI 가 만드는 원본 에셋(스프라이트·모델)은
> 속성 중립이며, 속성·발견 상태·목적 관련성은 전부 런타임 시각 채널(§4)로 **합성**한다.
> 이것이 "재료 10종 × 속성 수십 개 × 발견 상태 4값"의 조합 폭발을 에셋 수 폭발 없이 감당하는 방법이다.

## 2. 렌더 스택 · 카메라 · 무대 공간

### 2.1 스택

| 결정 | 내용 | 이유 |
|---|---|---|
| 렌더 API | WebGL2 (three.js 채택, 단 Scene 소비자로 격리) | 모바일 웹 지원 폭, 스프라이트 인스턴싱·커스텀 셰이더 용이 |
| 구조 | `세계 속성 → ViewModel → Scene 서술자 → 렌더러` | 불변 원칙 ⑥ — three.js 는 렌더러 내부 구현일 뿐, 교체 가능 |
| UI 레이어 | DOM/Canvas 2D 오버레이 (월드 렌더와 분리) | 목적 그래프·도감·HUD 는 해상도 독립이 필요 (§6) |

### 2.2 카메라 — 고정 뷰

```
투영:   원근(perspective), FOV 30° (좁게 — 준-등각 느낌, 스프라이트 왜곡 최소)
피치:   지면에서 55° 내려다봄 (고정)
요:     고정 (회전 없음) — 세계의 "정면"이 하나다
줌:     3 단계 스텝 줌만 허용 (근·중·원) — 연속 줌 없음, 스프라이트 픽셀 밀도 보장
이동:   지면 평면 팬 (팔로우: 내 캐릭터 중심 + 약간의 선행 오프셋)
```

- 요 회전이 없으므로 **스프라이트는 카메라를 향해 세운 빌보드**(수직 실린더형)로 충분하고,
  방향 표현은 개체의 진행 방향에 따른 방향별 스프라이트(§3 Tier M)가 담당한다.
- 스텝 줌은 아트 제작 규격을 3개 픽셀 밀도로 고정해 주므로 AI 생산 규격(§7)이 단순해진다.

### 2.3 지면 — 3D 로 만드는 유일한 "바닥"

- 지면은 실제 3D 메시: 셀 그리드 기반 낮은 기복(low-relief) 하이트필드 + 타일 텍스처 스플랫.
  초기 버전은 평면 + 스플랫만, 기복은 이후 단계.
- **지면은 정보 표면이다** — 목적 시스템의 상당수가 지면 데칼로 표현된다:
  - 탐색 영역(정보 정확도별 부채꼴→영역→원, 상위 설계 §6.2) = 지면 데칼 링/부채꼴
  - 무대의 문턱(기회 영역 경계) = 경계 데칼 + 영역 내 지면 틴트 변화
  - 오염·독기·신성 방사 같은 **장(field) 속성** = 지면 틴트/텍스처 오버레이
  - 거대 생물의 이동 흔적, 재앙의 흉터 = 흔적 데칼 (정보 재료의 실물)
- 조명: 방향광 1 + 앰비언트. 그림자는 **전 개체 블롭 섀도** 통일(3D 개체 포함) — 스프라이트와
  3D 가 같은 무대에 서 있다는 착지감을 주는 최소 비용 수단이며, 실시간 그림자는 쓰지 않는다.

## 3. 표현 계층 (Tier) — 무엇을 스프라이트로, 무엇을 3D 로

### 3.1 계층 정의

| Tier | 대상 | 형식 | 규격 |
|---|---|---|---|
| **S — 단일뷰 스프라이트** | 재료(약초·광물·조직·균류·오염물·잔해), 소형 생물, 소품, 드롭된 아이템 | 빌보드 1뷰 (+ 상태 변형 1~3장: 온전/손상/고갈) | 기준 128px, 아틀라스 배치 |
| **M — 멀티뷰 스프라이트 (2.5D)** | 중형 생물(마수·권속·NPC 다수), 이동·전투하는 존재 | 방향 4뷰(전후좌우) × 동작 4종(대기·이동·행동·피격) × 4~6프레임 | 기준 256px |
| **D — 3D 저폴리** | 플레이어(아바타), 보스(거대 신 등), 핵심 장치(제작 시설·봉인 장치), 랜드마크(폐허·거대 구조물) | 저폴리 + 단일 텍스처, 골격 애니메이션 최소 세트 | ≤ 5k tri (보스·랜드마크 ≤ 15k) |
| **U — UI 스프라이트** | 목적 그래프 노드, 도감, 아이콘, HUD 표식 | 2D 스프라이트 — **월드 Tier S 원본과 동일 에셋 재사용** | 128px 원본에서 파생 |

### 3.2 승격 기준 — 어떤 존재가 위 Tier 를 받는가

아래 질문에 "예"가 많을수록 위 Tier 로. 기본값은 항상 Tier S (가장 싸다):

1. **화면 점유가 큰가?** (보스·랜드마크 → D)
2. **방향·회전이 의미를 갖는가?** (이동·전투하는 생물 → M, 회전 연출이 필요한 장치 → D)
3. **플레이어가 오래·자주 보는가?** (아바타 → D, 핵심 제작 시설 → D)
4. **실루엣이 세계의 이정표인가?** (랜드마크 → D — 고정 뷰에서 원거리 식별의 닻)
5. **과정에 개입하는 연출이 필요한가?** (제작 개입 §5.4 의 장치 → D)

역방향 규칙: 3D 로 만들 이유를 증명 못 하면 스프라이트다. **3D 개체 수는 화면당 한 자릿수**를
유지한다 (성능이 아니라 연출 집중의 문제 — 3D 는 "특별함"의 신호다).

### 3.3 계층 간 착지 통일

서로 다른 형식이 한 무대에 서려면 공유 규약이 필요하다:

- **접지점 규약**: 모든 에셋은 발밑 원점(스프라이트: 하단 중앙, 3D: 바닥 원점) + 블롭 섀도.
- **조명 방향 규약**: 스프라이트 원본의 그림자·하이라이트는 좌상단 광원 고정으로 생산(§7 스타일
  바이블) — 방향광과 일치시켜 3D 와 음영 방향이 어긋나지 않게.
- **스케일 규약**: 1 월드 유닛 = 사람 키의 1/2. 에셋 메타데이터에 월드 높이 명기, 렌더러가
  픽셀→유닛 자동 환산.

## 4. 속성 시각 채널 — "속성은 행동으로 보인다"의 구현

상위 설계 §6.4 의 원칙을 **6개 시각 채널**로 구현한다. 채널은 에셋과 독립인 셰이더/이펙트이고,
어떤 Tier 에도 합성 가능하다. ViewModel 이 세계 속성을 채널 강도(0~1)로 번역해 Scene 에 싣는다.

### 4.1 채널 정의

| 채널 | 시각 효과 | 구현 (스프라이트/3D 공통) |
|---|---|---|
| **발광 GLOW** | 은은한 외곽·내부 발광, 색상 가변 | 외곽선 셰이더 + 가산 블렌드 스프라이트 링 |
| **진동 JITTER** | 표면 떨림, 미세 위치 진동 | 정점 셰이더 노이즈 오프셋 (강도=진폭) |
| **입자 PARTICLE** | 개체 주변 입자(상승·낙하·궤도) | 공용 파티클 아틀라스, 색·중력·패턴 파라미터 |
| **왜곡 DISTORT** | 주변 공간의 굴절·흔들림 | 화면공간 굴절 패스 (모바일: 저해상도 반경 한정) |
| **변색 TINT** | 색조 램프 이동(생기→퇴색, 오염 침식) | 팔레트 램프 셰이더 (원본 팔레트 → 목표 램프 보간) |
| **부유 FLOAT** | 주변 소품·먼지의 들림, 본체의 저속 부상 | 정점 y 오프셋 사인파 + 주변 입자 상승 |

### 4.2 속성 → 채널 매핑 (발췌 — 데이터 주도, 표가 곧 데이터)

| 세계 속성 | 채널 조합 |
|---|---|
| 높은 열전도 | GLOW(주황, 맥동 빠름) + PARTICLE(아지랑이) |
| 불안정성 | JITTER(강도=불안정도) + PARTICLE(불규칙 스파크) + 균열 TINT |
| 신성 에너지 | FLOAT(주변 부유) + DISTORT(빛 왜곡) + GLOW(백금색) |
| 독성 | TINT(주변 지면·식생 데칼 변색) + PARTICLE(낙하성 포자) |
| 공명 | JITTER(특정 주기 동기화 — 소리와 위상 일치) + GLOW(맥동) |
| 높은 순도 | GLOW(일정·안정 맥동) — 채널 수 적음 = 순수함의 기호 |
| 혼합물 | 복수 채널 동시·불규칙 — 채널 충돌 자체가 "섞임"의 기호 |
| 오염 | TINT(침식 진행률=오염도) + PARTICLE(검은 입자) |

읽는 법을 학습시키는 규칙: **채널의 문법은 전 세계 공통**이다 — 어떤 개체든 JITTER 가 보이면
불안정하고, FLOAT 가 보이면 신성/반중력 계열이다. 플레이어의 '관찰' 행위는 이 채널을 읽고
속성을 추론하는 것(상위 설계 §6.4)이므로, 채널-속성 대응은 예외 없이 일관되게 유지한다.

### 4.3 목적 관련성 오버레이 — 공명 발광

활성 말단의 demand 속성을 가진 대상이 시야에 들면 **GOAL 오버레이**(전용 외곽 발광, 목적 그래프
노드와 같은 색)를 합성한다. 속성 채널과 구분되도록: 속성 채널은 개체 "자신의 상태", GOAL
오버레이는 "나와의 관계" — 색과 리듬을 UI 색 체계(§6.5)와 공유해 세계·UI 가 같은 말을 쓴다.

## 5. 재료 10종의 시각 문법

재료마다 "월드에서 어떻게 보이는가 / 획득이 어떻게 보이는가 / UI(그래프·도감)에서 어떻게
보이는가"를 정한다. 원칙: **보유형은 실물로, 상태형은 세계의 상태 변화로** 보여준다.

| 재료 | 월드 표현 | 획득 연출 | UI 표현 |
|---|---|---|---|
| **물질** | Tier S 스프라이트 + 속성 채널 | 개체가 축소되며 캐릭터로 흡수, 잔량 상태 변형(온전→고갈) 전환 | 동일 스프라이트 = 아이콘 |
| **에너지** | 실물 없음 — 보유·흐름만: 이체 시 발광 궤적(출발→도착), 개체의 충전도는 GLOW 강도 | 궤적 도착 + 짧은 충전 링 | 게이지 아님 — 잔량을 GLOW 강도로 갖는 결정 아이콘 |
| **정보** | 세계에 남은 **흔적**: 발자국·흉터·기록 데칼, 조사 가능 오브젝트의 미세 GLOW | 조사 순간 흔적에서 글리프 입자가 떠올라 화면 밖(저널 방향)으로 날아감 | 글리프 조각 — 같은 주제의 조각이 모이면 문장(도감 항목)으로 조립 |
| **지식** | 실물 없음 — 검증 전에는 그래프 위 가설 노드로만 존재 | 검증 성공 순간 가설 노드가 "굳는" 연출 (§6.4 파문과 연동) | 흐린 글리프(추정) → 선명한 인장(확인) → 깨진 인장(반증) |
| **능력** | 사용 순간에만 보임 — 시전 이펙트에 능력 계열 색 | 습득 시 캐릭터에 짧은 각인 연출 | 인장형 아이콘 (지식과 같은 문법, 색으로 구분) |
| **생명체** | Tier S/M 개체가 추종 상태로 뒤따름 (포획 후) | 포획 성공 시 개체 위 소유 링 점등 | 개체 스프라이트 축소판 + 소유 링 |
| **관계** | 대상 NPC/세력 개체 위 관계 표식(신뢰 단계별 색) — 상시가 아니라 조준 시 표시 | 관계 변화 순간 양자 간 연결선 1회 연출 | 초상(개체 스프라이트) + 관계 단계 링 |
| **접근권** | 잠긴 문·경계가 "닫힘 채널"(차가운 TINT + 정지) → 획득 후 해제 연출 | 경계 데칼이 열리는 1회 연출 | 열쇠/인장 아이콘 |
| **환경 상태** | **화면 전체가 재료다**: 하늘·조명 색, 지면 톤, 전역 입자(비·재·꽃가루) | 획득이 아니라 **도래** — 상태 진입 시 전환 연출(월식이 "시작되는" 하늘) | 주기 다이얼: 현재 상태와 다음 도래 시점을 도는 바늘 |
| **시간과 기회** | 임박 신호: 관련 무대 방향의 지평선 연출(먼 울음, 번식기의 무리 이동이 실제로 보임) | 포착 = 그 시간창 안에 말단을 완료 — 시간창 동안 무대 GLOW | 주기 다이얼 공유 + 기회 창 구간 하이라이트 |

핵심 규칙 셋:

1. **단일 원본 원칙**: 월드 스프라이트 = 도감 아이콘 = 그래프 노드 썸네일. 하나의 Tier S 원본이
   세 곳에 쓰인다 — AI 생산량을 1/3로 줄이고, "세계에서 본 그것"이 UI 에서 즉시 재인식된다.
2. **상태형 재료는 UI 를 공유한다**: 환경 상태와 시간·기회는 하나의 **주기 다이얼** UI 로 통합 —
   "기다리고 포착하는" 플레이가 한 화면에서 계획된다.
3. **정보·지식은 글리프 문법**: 관측(정보)은 조각, 검증된 이해(지식)는 인장, 반증은 깨진 인장 —
   발견 상태 4값(미발견/추정/확인/반증)이 글리프의 시각 상태와 1:1 대응한다.

### 5.4 무대(기회)와 제작의 시각화

- **무대**: 경계 데칼(문턱) + 명패(진입 1회) + 영역 지면 틴트. obstacles 는 §4 채널로 정직하게
  사전 표시(독기=지면 TINT+포자, 수호 생명체=실물 배치, 시간 소멸=대상의 TINT 퇴색 진행).
  choices(다량·신속 vs 소량·정밀)는 상호작용 UI 가 아니라 **행동 방식**으로: 채취 버튼을 오래
  누를수록 많이·거칠게(오염 채널 상승이 실시간으로 보임), 짧게 끊으면 적게·깨끗하게.
- **제작(과정 개입, 상위 설계 §6.5)**: 제작 시설은 Tier D. 재료 투입 → 시설 위 **실물 스프라이트가
  실제 변형**(TINT 램프·JITTER·결정 성장 스프라이트 시퀀스)되고, 폭주 임박이 JITTER+GLOW 로
  보이면 플레이어가 개입(온도·압력 조작)한다. 완성물의 속성 채널이 과정의 결과로 결정된다 —
  제작 UI 는 게이지가 아니라 **채널을 읽는 눈**으로 조작하게 설계한다.

## 6. UI · 목적 그래프의 구체 설계

톤: UI 는 Tier U 스프라이트로 월드와 같은 팔레트·같은 글리프 문법. "메뉴"가 아니라 "탐험 도구"
(지도·저널·다이얼)의 물성을 갖는다.

### 6.1 HUD (상시) — 최소주의

```
좌상: 주기 다이얼 (환경 상태·기회 창)      우상: (비움 — 알림 파문만 지나감)
하단 중앙: 활성 말단 카드 1장               우하: 상호작용 버튼 (모바일) / 키 힌트 (PC)
```

- **활성 말단 카드**: 대상 썸네일(=월드 스프라이트) + 말단 문장 1줄 + 충족 조건 점등 슬롯.
  퍼센트 없음(상위 설계 §6.3). 카드 탭 → 방사형 그래프로 확장.
- **나침반**: 화면 가장자리 호(arc)에 활성 말단 관련 신호만 — 탐색 영역 방향(정확도가 낮으면
  호가 넓음 → 정확해질수록 좁아짐: §6.2 의 정확도 문법을 나침반에도 적용).

### 6.2 방사형 목적 그래프 (열어보는 창)

- 중앙: 현재 핵심 목적 노드. 1환: 필요 조건들. 2환: 각 조건의 재료·행동 노드. 간선: 인과·의존.
- 노드 = 글리프 인장 + 썸네일. 발견 상태 렌더 문법(상위 설계 §6.2)을 그대로:
  확인=선명 / 추정=흐림+떨림(JITTER 채널을 UI 에도) / 분기=유령 가지 / 미발견=성운 / 반증=붕괴.
- 조작: 노드 탭 → 활성 말단 교체(HUD 카드 갱신). 롱탭 → 도감 항목. 바깥 원주 드래그 → 형제
  목적 회전.
- **모바일**: 전체 화면 시트로 상승. **PC**: 우측 패널 또는 전체 화면 토글 — 레이아웃은 동심원
  그대로, 밀도만 다름.

### 6.3 별자리 지도 (전체 화면)

- 축적된 전체 DAG. 완료=밝은 별, 진행=맥동, 추정=깜빡임, 미발견 가지=성운 덩어리.
- 교차 간선(DAG 다중 부모)은 별자리 연결선 — 한 별에서 두 계보로 빛이 갈라져 오르는 것이
  이 화면의 핵심 스펙터클(§6.4 파문).
- 줌: 별자리 군(뿌리 단위) → 개별 성좌(가지) 2단계. 검색 대신 **회상**: 도감에서 재료를 골라
  "이게 쓰이는 곳" 역추적 하이라이트 (상향 발견의 UI 대응물).

### 6.4 파문·발견·붕괴 연출 (월드 ↔ UI 관통)

| 사건 | 월드 연출 | UI 연출 |
|---|---|---|
| 말단 완료 | 개체 위 완료 링 → 화면 가장자리로 빛줄기 이탈 | HUD 카드 조건 슬롯 점등 → (열려 있으면) 그래프 계보 타고 상향 파문 |
| 다중 파문 (DAG) | 빛줄기가 2갈래로 갈라져 이탈 | 별자리 지도에서 두 계보 동시 점등 — 최고 순간의 연출 예산 집중 |
| 상향 발견 | 획득한 재료가 반짝이며 "자리 찾음" 신호 | 새 가지 일괄 점등 + 보유 글리프들이 날아가 결합 |
| 가설 반증 | (해당 실험 현장에 실패 연출) | 인장 깨짐 → 가지 붕괴(재편성) — 상실도 성대하게 |
| 타인의 파문 | 타 플레이어 위 희미한 완료 링 (색 익명화) | 없음 (세계에서만 — 사회적 배경 복사) |

### 6.5 색 체계 (UI·채널 공유)

- **목적 관련(GOAL)**: 단일 시그니처 색 (월드 오버레이 = HUD = 그래프 활성 경로).
- **발견 상태**: 확인=본색 / 추정=탈색+떨림 / 반증=파괴 텍스처 — 색이 아니라 **질감·안정성**으로
  구분 (색약 접근성: 상태를 색에만 싣지 않는다는 원칙을 전 UI 에 적용).
- **재료 10종**: 종별 색은 두지 않는다 — 종은 글리프 형태로 구분 (색은 속성·상태의 몫).

## 7. AI 에셋 파이프라인 — 에이전트가 만드는 아트

### 7.1 스타일 바이블 (생성의 헌법 — 별도 문서로 상세화 예정)

- **스타일**: 스타일라이즈드 일러스트, 강한 실루엣, 두꺼운 외곽 없음(외곽은 셰이더 몫),
  좌상단 광원 고정, 절제된 명도 대비. AI 생성물의 품질 편차를 스타일이 흡수한다.
- **팔레트**: 마스터 팔레트 (본색 영역 + 채널용 예약색 영역 분리 — TINT 램프가 원본을 안전하게
  변조할 수 있도록 채도·명도 대역을 규정).
- **규격**: Tier S 128px / M 256px / U 는 S 파생. 접지점·여백·알파 규칙 명문화.

### 7.2 생성 파이프라인 (에셋 1종의 여정)

```
1 의뢰서 생성    설계 문서·세계 데이터에서 에셋 명세(archetype, 월드 높이, 상태 변형 수,
                 방향/동작 매트릭스)를 기계 생성 — 프롬프트가 아니라 명세가 원본
2 생성           명세 → 프롬프트 템플릿(Tier 별) → 이미지 생성 (Tier M 은 방향 턴어라운드
                 시트로 일괄 생성해 뷰 간 일관성 확보; Tier D 는 컨셉 시트 → 저폴리 모델링)
3 후처리         배경 제거 → 접지점 정렬 → 규격 리사이즈 → 팔레트 사상(마스터 팔레트로 양자화)
4 자동 QA        실루엣 판독성(축소 32px 테스트) · 팔레트 준수 · 알파 누수 · 접지점 오차 ·
                 방향 뷰 간 높이/볼륨 일관성 — 실패 시 2로 반려 (사람 개입 없이 루프)
5 등록           아틀라스 패킹 + 매니페스트 기입: {id, tier, 월드 높이, 상태 변형, 애니 프레임,
                 도감 크롭 좌표} — 렌더러는 매니페스트만 읽는다
```

- **속성·발견 상태는 파이프라인에 없다** — §1 의 핵심 결정. 에셋은 "무엇인가"만 담고,
  "어떤 상태인가"는 채널이 그린다. 따라서 신규 속성 추가에 에셋 재생산이 필요 없다.
- **상향 발견 대응**: 신규 재료 아키타입은 명세 1건 추가로 자동 생산 — 세계가 새 재료를 만들
  때(생성 규칙 §5) 아트가 병목이 되지 않는다.
- Tier D 는 수량이 적으므로(화면당 한 자릿수 원칙) 건당 공정이 길어도 총비용이 작다 —
  컨셉 다중 생성 → 자동 실루엣 평가로 선별 → 모델링.

### 7.3 검증 (불변 원칙 ⑤ 의 아트 버전)

- `npm run shot` 계열로 **시각 명제 스크린샷**을 상시 재현: ① 계층 혼합 무대(S+M+D+지면이 한
  화면에 착지) ② 속성 채널 8종 합성 데모 ③ 파문·발견·붕괴 연출 ④ 3단계 줌별 픽셀 밀도.
- 에셋 QA(파이프라인 4단계)는 회귀 테스트로 상시 실행 — 아틀라스가 바뀌면 실루엣·팔레트 검사가
  자동으로 다시 돈다.

## 8. 플랫폼·성능 예산 (모바일 기준 상한)

| 항목 | 예산 | 수단 |
|---|---|---|
| 프레임 | 모바일 30fps 보장 / PC 60fps | 고정 뷰 = 컬링 단순(카메라 절두체 고정), 스텝 줌 = LOD 3단 고정 |
| 드로 콜 | 월드 ≤ 50 | Tier S/M 전 개체 인스턴스드 빌보드(아틀라스 단위 배칭), 채널은 인스턴스 속성 |
| 텍스처 | 아틀라스 2048² × 4장 이내 (S/M/이펙트/지면) | 팔레트 양자화 + 상태 변형 최소화(채널로 대체) |
| 3D | 화면당 개체 ≤ 8, 합계 ≤ 60k tri | §3.2 승격 기준으로 원천 통제 |
| 포스트 | DISTORT 는 저해상도 반경 한정, 모바일 저사양은 채널 폴백(DISTORT→GLOW) | 채널별 품질 폴백 표를 채널 정의에 포함 |
| UI | DOM/Canvas 분리 — 월드 프레임과 독립 갱신 | 그래프는 열었을 때만 렌더 |

- 입력: 터치(탭=상호작용, 롱프레스=거친 채취, 드래그=이동)와 마우스/키보드를 같은 의미 계층으로
  — 플랫폼별 UI 는 배치만 다르고 문법은 같다 (§6).

## 9. 실행 환경 계획

서버+클라이언트 웹 구성, 원클릭 재현:

```
run.sh / run.bat    # 설치 → 테스트 → 서버 → 봇 N기 → 관전 브라우저
npm test            # 규칙·시각 매니페스트 회귀
npm run shot        # 헤드리스 브라우저 스크린샷 — §7.3 시각 명제 4종 고정 캡처
npm run demo        # 데모 서버 — 브라우저로 눈 확인
```

- 봇이 목적 사슬을 실제로 굴리는 무대를 관전 브라우저로 본다 — 시각화 설계의 검증 무대이자
  데모. 서버는 세계 속성·사건만 방송하고, 클라이언트 ViewModel 이 Scene 서술자로 번역한다.
- Scene 서술자 계약(렌더러 교체 seam)의 최소 형태:
  `{ ground, entities[{archetype, pos, dir, channels{}}], decals[], effects[], ui{goalGraph, dial, card} }`
  — 상세 스키마는 구현 첫 step 에서 확정.
