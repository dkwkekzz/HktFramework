# Phase 8 — 표현 고도화

> 근거: §42-8(지도, 캐릭터 아이콘, 대화, 능력 효과, 사건 연출), §36(4개 화면), §33.3(표현 생성), §2.1 Presentation Time, §3 Event Interpreter·Web Viewer.

## 목표

상태 변화와 사건을 사람이 이해할 수 있는 표현으로 변환한다(§2.1 Presentation Time). §36 의 4개 화면을 완성하고, Event Interpreter 가 구조화 사건을 읽을 수 있는 문장으로 바꾼다. **표현은 세계 상태를 절대 변경하지 않는다**(§33 마지막 문단).

## 산출 모듈

- `viewmodel/` — SceneViewModel 스키마 완성(`map`/`events`/`agentPanel`/`eventDetail`) + 화면별 빌더 4개. **시뮬레이션 의미 해석은 전부 여기서 끝난다.**
  - `MapViewBuilder.ts` — 3D→2D 톱다운 투영·정규화·색상 키·심볼 키·신호 속성 (§36.2, §42-8)
  - `AgentViewBuilder.ts` — §36.3 목록 8항목 + 모드(개발자/플레이어) 파라미터
  - `EventViewBuilder.ts` — §36.4 목록 8항목 + "알려진 정보 ↔ 실제 원인" 두 판본
  - `NarrationBuilder.ts` — 런타임 → 순수 데이터(`NarrationRequest`) 추출 (§33.3)
  - `ScenePayloadBuilder.ts` — 세 빌더의 진입점, 경계 밖으로 나가는 `SceneViewPayload`
  - `phase8Checks.ts` — 화면 항목·렌더러 격리·모드 대비·누출 감사·§44 게이트 측정 (verify 와 테스트가 공유)
- `rendering/`(§37) — `WorldMapRenderer` / `EntityRenderer` / `SignalRenderer` / `EventOverlay` + `CanvasSceneRenderer`(층 합성) + `TextSceneRenderer`(격리 증명) + `SceneSurface`(그리기 표면) + `palette`(키→시각 언어 표).
- `app/`(§37) — `WorldSeedPage` / `WorldEditorPage` / `SimulationPage` / `EventInspectorPage` + 탭 셸(`main.ts`).

## 상세 설계

### 8.0 ViewModel 파이프라인 (분해 원칙 5 — 이 Phase 의 최상위 제약)

Phase 0 §0.6 에서 확립한 경계를 전 화면 규모로 완성한다.

```
WorldState patch / 사건 / 믿음·기억·관계     (시뮬레이션 속성)
        ↓  ViewModelBuilder — 의미 해석·모드 필터·좌표 정규화 전부 여기서
SceneViewModel                               (렌더링 속성 — 표현 중립)
        ↓  렌더러/페이지 — 속성 그대로 매핑, 해석 없음
Canvas / DOM                                 (표현)
```

- **렌더링 속성의 완결성**: 렌더러가 그리는 데 필요한 모든 값(정규화 좌표, 심볼 키, 강도 0~1, 색상 키, 라벨 문자열, 타임라인 항목)은 ViewModel 에 이미 들어 있다. 렌더러에 `if (danger > 50)` 같은 시뮬레이션 값 해석이 한 줄이라도 있으면 설계 위반 — 그 판단은 빌더가 `colorKey: "danger-high"` 처럼 속성으로 변환해 넘긴다.
- **표현 방식 변경의 격리 증명**: 같은 SceneViewModel 을 소비하는 두 번째 렌더러(텍스트 덤프 렌더러)를 유지한다. 두 렌더러가 공유하는 것은 ViewModel 속성뿐이므로, 어느 한쪽을 어떻게 바꾸든 빌더·코어의 diff 는 0 이다. **린트가 이것을 상시 강제한다** — `rendering/**` 는 `../viewmodel/SceneViewModel` 과 자기 디렉터리 밖의 어떤 모듈도 import 할 수 없다(core·shared·generation·app 전부 금지).
- **모드는 빌더의 입력이다**: 개발자/플레이어 모드(§36.3)는 렌더러 분기가 아니라 빌더 파라미터(`SceneViewContext.mode`). 플레이어 모드 빌더는 Phase 7 지식 필터(`playerStateOf` + `BeliefView.perceive`)를 통과한 것만 ViewModel 에 넣는다 — 렌더러는 자기가 어느 모드인지 모른다.
- **빌더는 시뮬레이션 쪽에서 돈다**: `SceneViewPayload` 가 Worker 경계를 넘는다. 그래서 메인 스레드에는 patch·정의·사건 원본이 도착하지 않고, 해석 코드도 없다(§38). 화면이 `core/**`·`generation/**`·`content/**` 를 import 하지 못하도록 린트로 막았고, 그 결과 **세계 생성(§5 15단계)도 Worker 뒤로 옮겨졌다**.

### 8.1 화면별 구성 (§36 명세 그대로)

**세계 생성 화면(§36.1)** — Phase 5 에서 기능 확보됨. 생성 구조 검토를 `WorldEditorPage` 로 승격: 단계 아티팩트 트리 뷰 + 개별 항목 재생성 버튼(`regenerate_step` → `ArtifactStore.before(stepIndex)` + `resumeFrom` = Phase 6 §6.3 증분 재실행).

**월드 지도 화면(§36.2)** — 2D 지역 지도(지역 사각형·연결 그래프), 지역 기후·위험도(두 색상 키가 각각 바탕·테두리), 이동 중 주체(궤적), 자원 분포, 발생 중 사건(오버레이 반경 + 시급도), 시간 배속. 공간 데이터는 3D(§13)이므로 **3D→2D 톱다운 투영은 빌더가 수행**하고 고도(z)는 `elevation`/`elevationShade` 표시 속성으로 실린다.

**주체 관찰 화면(§36.3)** — 목록 8항목 그대로. **개발자 모드 = 실제+믿음 병렬, 플레이어 모드 = 관찰 가능한 현상만** — 같은 표의 `actual`/`believed` 두 열이 모드에 따라 채워지거나 아예 없다.

**사건 화면(§36.4)** — 목록 8항목 그대로. "알려진 정보 vs 실제 원인" 은 `getEventViewFor(observer)` vs 원본 change 로그의 병렬 표시이며, 플레이어 시점에서는 오른쪽 칸이 비어 있다.

### 8.2 Event Interpreter (§33.3)

- 생성 대상 6종: 사건 제목 / 인물 대화 / 소문 / 문서 / 관찰 묘사 / 사건 요약.
- 입력은 **구조화 정보만**(§33 예시 JSON 형식): 화자의 values·fear·currentGoal·관계 수치, knownFacts/unknownFacts(관찰자 시점 API 산출), conversationPurpose.
- **unknownFacts 는 프롬프트에 "말하면 안 되는 것" 으로 명시**되고, 생성된 문장은 같은 목록으로 다시 검사된다. 누출이면 그 문장은 버려지고 템플릿으로 되돌아간다 — 새는 문장이 화면에 오르는 경로가 없다.
- 캐시·폴백: 같은 (종류, 사건, 시점, 관찰자, 화자) 는 캐시. 포트 부재 시 템플릿 문장 폴백 — 표현 계층이 없어도 시스템 전체는 동작(§2.1).
- **읽기 전용 강제는 타입과 린트로** — `presentation/**` 는 `core/**`·`viewmodel/**` 를 import 할 수 없다. Interpreter 에게 도착하는 것은 `NarrationRequest` 라는 순수 데이터뿐이며, 세계를 만질 손잡이가 없다.

### 8.3 연출 요소 (§42-8 목록)

- 캐릭터 아이콘: 빌더가 종족·조직·유형 태그를 `symbolKey` 로 변환하고, 렌더러는 키→글리프 매핑표(`palette.GLYPHS`)만 담당. 아이콘 스타일 교체는 그 표의 교체다.
- 능력 효과·사건 연출: 행동의 `visibleSignals`(=능력의 `observableSignals`)와 그 행동이 남긴 change 를 맞춰 `{channelKey, intensity, point, ttl}` 로 변환하고, `SignalRenderer` 가 채널별 시각 언어(파문·잔광·아이콘)로 표시 — **별도 연출 스크립트 없음**.

### 8.4 설계에서 옮겨진 것 (구현 중 확정)

| 설계 | 구현에서 달라진 것 | 이유 |
|---|---|---|
| 빌더가 메인 스레드에서 patch 를 해석 (§8.0 초안) | 빌더가 **Worker 쪽**에서 돌고 `SceneViewPayload` 가 경계를 넘는다 | 지도·목적 그래프·관계는 patch 에 없는 정의·런타임 정보를 필요로 한다. 정의를 메인 스레드로 보내면 "화면은 ViewModel 만 안다"가 깨진다 — 해석을 경계 안에서 끝내는 쪽이 §38 과 분해 원칙 5 를 동시에 지킨다 |
| 화면이 `compileWorld` 를 직접 호출 (Phase 5 잔재) | `generate_world`/`regenerate_step` 요청으로 Worker 에 위임 | 같은 이유. 덤으로 15단계 컴파일이 UI 스레드를 막지 않는다(§38) |
| 렌더러가 `CanvasRenderingContext2D` 를 직접 사용 | `SceneSurface`(그리기 동사) 뒤로 격리 | 화면 없이도 같은 그림을 판정하려면 표면을 갈아 끼울 수 있어야 한다. `RecordingSurface` 가 "무엇이 실렸는가"를 브라우저 없이 세어 준다 |
| 누출 검사 = unknownFacts 문장의 단어 대조 | **구조화 금지 사실**(`ForbiddenFact`)의 3항 대조 — 문장 일치 / 한 절 안의 (대상+상태+값) / 모르는 참여자 이름 | 단어 단위로 막으면 관찰자가 이미 아는 지역·참여자 이름까지 금지어가 되어 "안전한 문장"이 아니라 빈 문장이 된다. 비밀은 이름이 아니라 "그 대상의 그 상태가 그 값"이다 |
| 플레이어 모드는 남의 상태만 필터 | 플레이어 모드에서는 **자기 자신을 볼 때도** 감각을 통과 (`source: self`) | 조작 중인 주체라고 실제값 열을 열면 "플레이어 모드에 실제 상태는 없다"가 깨진다. verify 가 이 누출을 잡아냈다 |
| 플레이어 모드 = 관찰자 지정 | 관찰자가 **조작 중인 주체(§31 지식 필터 보유)** 가 아니면 화면이 빈다 | 시점만 바꿔 놓고 실제 세계를 그려 버리는 사고를 막는다. 필터 없는 "플레이어 시점"은 존재하지 않는다 |

### 화면은 시점을 바꾸면 다른 것을 보여준다 (§36.3)

같은 세계, 같은 주체(`creature.echo_beast_mother`)를 두 시점으로 만든 결과:

| | 상태 항 | 실제값 열 | 감춰짐 | 지도 주체 | 필터 위반 |
|---|---|---|---|---|---|
| 개발자 | 28 | 28 | — | 6명 | — |
| 플레이어 | 2 | **0** | 26종 | **1명** | 0건 |

플레이어 시점에서 반향수에 대해 남는 것은 두 항뿐이고, 실제값 열은 존재하지 않는다. 지도에 찍히는 주체도 6명에서 1명으로 줄어든다 — 감각이 닿지 않는 자리는 지도에도 없다.

사건도 같다. `event.3`(`subjugation_muster`)의 실제 원인은 개발자 시점에 7줄로 보인다:

```
14일 01:00 마을 지도자 마르.delegated_goal goal.subjugate_beast→goal.gather_for_village ← 마을 원로회 action.delegate
```

플레이어 시점에서 같은 자리는 **0줄**이고, 대신 "아는 사실 1건 · 아는 참여자 4 / 모르는 참여자 5"만 남는다.

### 표현이 정보 비대칭을 새게 하지 않는다 (§33.3)

- 요청 154건(사건 24건 × 6종 + 관찰 묘사 10건) 중 **153건에 금지 사실이 있었다** — 금지 사실 총 6,106개. 막을 것이 있었다는 것이 먼저 증거다.
- 화면에 게시된 문장 166개에서 누출 **0건**.
- 금지 사실을 그대로 흘리는 포트를 붙이면 그 문장 12개가 전부 폐기되고 템플릿으로 되돌아간다.
- 캐시 적중 154/154 — 같은 (종류, 사건, 시점, 관찰자) 는 두 번 만들지 않는다.
- AI 포트 없이 만들어진 문장의 예:
  - 제목 — `마을의 subjugation muster — 사냥꾼 카엘 외 3명`
  - 소문 — `"마을에서 subjugation muster이 있었다더군. …" — 출처는 분명하지 않다`
  - 관찰 묘사 — `침묵림 — 사냥꾼 카엘의 health는 0 · … 그 밖의 것은 보이지 않는다.`

### 표현 방식은 갈아 끼울 수 있다 (§8.0)

- `rendering/` 8개 파일의 import 전부가 `../viewmodel/SceneViewModel` 또는 같은 디렉터리 — 위반 0건(린트가 상시 강제).
- 같은 SceneViewModel 하나로 Canvas 렌더러는 171회(문자 100회) 그리고, 텍스트 렌더러는 294줄을 쓴다. 두 표현이 함께 실은 표시 대상 35개, 누락 0.
- 브라우저에서도 같다 — `npm run smoke` 의 출력:

```
SMOKE OK — 네 화면 전부 동작
① 생성 — 제약의 대륙 · 생성 호출 79회 · 최대 입력 3035B · 심볼 435개 · 규칙 59개 · 개체 136개
② 구조 검토 — 단계 15개 · 증분 재실행에서 재사용 11단계
③ 지도 — Canvas 채워진 픽셀 445041/518400 · 관찰 표 33행 (플레이어 시점 실제값 0항)
④ 사건 — "마을의 rumor spread — 사냥꾼 카엘 외 8명" event.0 · 중요도 887 · 바뀐 상태 53종
```

  Canvas 픽셀을 세는 이유는 "그렸다"는 주장 대신 **칠해진 면적**을 남기기 위해서다. 모드 전환도 브라우저에서 판정한다 — 플레이어 시점의 상태 표에서 실제값 칸이 채워진 행은 0개다.
