# CLAUDE.md — HktFeature 작업 규칙 (간략·불변)

> 이 문서는 **목표·규칙·작업 방식**만 정한다. 아주 간략하며 왠만하면 변하지 않는다.
> 현재 어디까지 왔는지는 [STATE.md](STATE.md), 각 기능의 상세는 `features/`.

> **불변 원칙 ① — 모든 feature 는 반드시 직관적으로 검증 가능해야 한다.**
> 명제가 참인지 누구나(비전문가 포함) 눈으로 보거나 한 번에 재현해 납득할 수 있어야 한다.
> 직관적으로 검증할 수 없는 feature 는 아직 feature 가 아니다 — 검증 방법부터 세운다.

> **불변 원칙 ② — feature 는 근본적·물리적으로 정의한다(개념을 뭉치지 말 것).**
> feature 를 세우거나 고칠 때는 먼저 그 현상을 **물리학적으로 끝까지 분해**한다: 무엇이 진짜 사건이고,
> 그 사건의 **주체(주인)** 는 누구/무엇인가. 서로 다른 사건을 편의로 한 feature 에 뭉치지 않는다.
> - **주체를 정확히 가른다**: 예) "생명체가 에너지를 발산해 투사체를 만든다"(생명의 행위)와 "투사체·물질이
>   터진다"(물질의 사건)는 **다른 주체의 다른 사건**이다 — 폭발은 생명만의 일이 아니다(폭탄·결정도 터진다).
>   한 함수·한 feature 에 두 사건을 묶으면 개념이 틀어진다. 주체별로 feature 를 가른다.
> - **표면 서사가 아니라 바탕 물리로 환원한다**: "연소"에 갇히지 말고 "폭발=급격한 에너지 방출→여러 채널
>   (열복사·압력파·파편)"처럼 근본 기제로 내려간다. 연소는 그중 한 채널일 뿐임이 드러난다.
> - **기존 규칙을 재사용한다**: 새 현상은 이미 있는 보편 규칙(feature-0013 상태전이 A·B·C 등)을 *유발*하도록
>   얹는다 — 규칙을 엉뚱한 주인에게 복제하지 않는다. "이 현상의 올바른 주인은 누구인가?"를 항상 먼저 묻는다.

## 1. 목표

오픈월드 MMORPG 에 쓸 **규칙을 정의하고 시뮬레이션**하여 기반을 만든다.
규칙을 하나씩 쌓아 **방대한 복잡계**를 구현하고, 그 복잡계가 결과적으로 **다채로운 게임**을 표현하게 한다.

## 2. 작업 방식 — feature 단위

- **feature** = 하나의 직관적/추상적 기능. **분명한 최종 목적**을 가지며, 그 목적은 **측정 가능**해야 한다.
- 최종 목적에 도달할 때까지 **step** 으로 분할해 진행하고, 과정을 feature 문서에 **간단히** 남긴다.
- feature 하나 = `features/feature-NNNN-<slug>.md` 문서 하나. 명제·최종 목적·step 로그·검증법을 담는다.
- 상세하게 남길 내용이 있으면 **별도 문서화하고 feature 문서에 인덱스**를 남긴다.
- **직관적 검증이 필수다**(위 불변 원칙): 모든 명제는 `npm test`(자동 회귀) + 봇 시뮬/브라우저 뷰어(사람이 눈으로 확인)로 **언제든 재현·검증**된다. 측정 목적은 참/거짓이 한눈에 갈리게 정의하고, 검증 없는 수치는 문서에 쓰지 않는다. 검증법을 못 세우면 그 feature 는 시작하지 않는다.
- **시각화는 최소·명확**: 렌더는 원장을 눈으로 확인하는 읽기 전용 뷰어. 화려함보다 명확함.
- **web 환경 개발**: 결과는 **클라우드 환경에서도 확실히 검증**될 수 있어야 한다(설치·테스트·시뮬이 한 번에 재현).

## 3. 문서 지도 · 작성 규칙

| 문서 | 역할 |
|---|---|
| `CLAUDE.md` | 목표·규칙·방식 (이 문서 — 잘 안 변함) |
| `STATE.md` | **현재 한눈에 + NEXT(다음 할 일) + 명제 목록** — 다음 세션이 이것만 보고 시작할 수 있어야 한다 |
| `README.md` | 사람 진입용 실행 스냅샷 + 세계 흐름 지도(전체 에너지 흐름·라이브 감사) |
| `features/feature-NNNN-*.md` | 각 feature: 명제 → 최종 목적 → step 로그 → 검증 (상세·이력의 집) |

**문서 규칙 — 트리는 현재 참인 명제만 든다, 이력은 git 이 든다:**

- **STATE.md 에 완료 로그를 쌓지 않는다.** 완료된 것은 지운다 — 상세는 해당 feature 문서로 이동하고 인덱스로 연결. STATE 는 명제·상태·NEXT 만 남긴다. **NEXT 에는 논의 요지(왜 이 작업인가)를 다음 세션이 맥락 없이 시작할 수 있을 만큼** 적는다.
- **묘비 문서 금지.** 한 시스템/한 명제를 여러 문서가 나눠 갖게 되면 하나로 합친다: 살아있는 정의·향후 step 을 흡수 문서로 옮겨 **혼자 읽혀도 완결**되게 하고, 원본은 **삭제**한다(완결 마커+포인터만 남는 껍데기를 두지 않는다 — step 로그·튜닝 이력은 git 히스토리에 있고, 검증의 실체는 지금도 도는 테스트다).
- **번호는 은퇴만, 재사용 금지.** 삭제된 feature 번호는 비워 둔다(커밋·이력이 그 번호를 가리킨다). 남는 참조(코드 주석·문서)는 `구 feature-00XX(현 NNNN)` 로 정리해 끊긴 링크를 만들지 않는다.
- **합치기의 한계 = 불변 원칙 ②.** 주체·사건이 다른 feature 는 합치지 않는다 — 통합은 "같은 명제의 두 절반" 또는 "한 파이프라인을 나눠 가진 문서들"에만.
- **수리(버그) 이력**은 STATE 가 아니라 해당 feature 문서 step 로그에 **"수리" 행**으로 남긴다(원인·수정·회귀 테스트).

## 4. 실행 · 검증 (자동 회귀 + 시각 검증 — 둘 다 상시 재현)

```
run.bat            # Windows — 설치→테스트→서버→봇 8기→관전 브라우저 원클릭
./run.sh [봇수]    # macOS / Linux (관전: http://localhost:8080/?name=관전자)
npm test           # 규칙 회귀 검증 (보존·불변식 상시 확인)
npm run shot       # 시각 검증 — 헤드리스 크로미움이 실제 뷰어를 스크린샷으로 캡처 (tools/shots/*.png)
npm run demo       # 시각 데모 서버 — 브라우저로 http://localhost:8080 열어 눈으로 확인
```

> **시각 검증은 상시 재현된다 — 세션마다 다시 요청할 필요가 없다.** 불변 원칙(모든 feature 는 직관적으로
> 검증 가능)을 자동화한 것이 `npm run shot` 이다: 제어 데모(`tools/demo-control.mjs`)를 띄우고 실제
> `client/` 뷰어를 헤드리스 크로미움으로 열어 명제가 눈에 보이는 세 시점을 `tools/shots/control-*.png` 로
> 굳힌다(클라우드 환경에 크로미움 사전 설치, `playwright-core` devDependency). 새 feature 를 세울 때는
> **자동 회귀(`npm test`) + 시각 검증(`npm run shot` 또는 해당 데모)** 을 함께 남겨, 사람이 매번 "눈으로
> 보여달라"고 요청하지 않아도 스크린샷/데모로 즉시 확인되게 한다. 시각 검증을 못 세우면 그 feature 는 아직 닫지 않는다.
