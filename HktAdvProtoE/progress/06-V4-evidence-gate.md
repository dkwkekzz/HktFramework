## 무엇을 막는 모듈인가

원문 「23」의 마지막 줄은 “증거 없이 `VERIFIED` 표시”를 금지한다. V4 는 그 금지를 **문서가 아니라 코드로**
만든다.

| 우회 경로 | 막는 방법 |
|---|---|
| 상태를 손으로 적는다 | `issueEvidence` 는 `status` 를 인자로 받지 않는다 |
| 증거 파일의 `status` 를 고친다 | 감사가 게이트로 다시 계산해 `E_STATUS_ABOVE_GATES` 로 잡는다 |
| 슬라이스를 건너뛴다 | G6 이 막으면 사다리가 `LAB_PASS` 에서 멈춘다 |
| 측정하지 않은 것을 통과로 적는다 | 게이트에 `measured` 가 따로 있다 — 미측정은 통과가 아니다 |
| 선행이 바뀐 뒤에도 옛 증거를 쓴다 | 발급 시점의 선행 계약 해시를 증거에 박아 두고 대조한다 |
| 발급 도구가 자기 규칙을 쓴다 | `tools/verify.mjs` 는 측정만 하고 발급은 V4 가 한다 |

## 설계 판단

- **상태는 게이트에서만 나온다.** 원문 「5」의 G0~G8 을 원문 「4」의 사다리에 1:1로 붙였다.
  아래에서 위로 올라가다 막히는 곳에서 멈추고, 어느 칸도 건너뛰지 않는다. 속성 테스트 500표본으로
  “슬라이스가 전부 통과하지 않으면 절대 `VERIFIED` 가 나오지 않는다”를 확인한다.
- **미측정은 통과가 아니다.** 게이트마다 `measured` 를 따로 둔 이유다. `--regression` 없이 돌리면
  G7 은 미측정이고, 미측정은 사다리를 막는다. 안 본 것을 통과로 적으면 게이트 전체가 장식이 된다.
- **증거에 선행 계약 해시를 박는다.** 원문 「2.5」의 무효화 연쇄는 “계약이 바뀌었는가”를 물어야 판정할 수
  있는데, 그 물음의 기준점은 **발급 시점의 선행 계약**이다. 이 값이 증거에 없으면 감사는 무효화 판정을
  내릴 수 없으므로, 기록이 없는 증거는 `E_DEPENDENCY_CONTRACT_UNRECORDED` 로 **믿지 않는다**.
- **무효화는 파일을 고치지 않는다.** 원문 「2.5」는 “테스트를 다시 실행하는 것이 아니라 의존 모듈의
  `VERIFIED` 상태를 자동으로 해제한다”고 쓴다. 그래서 증거 파일은 그대로 두고 **감사가** 상태를 내린다.
  화면과 판단은 `declaredStatus`(파일에 적힌 값)가 아니라 `effectiveStatus`(감사 결과)를 쓴다.
- **무효화 이유는 거리마다 다르다.** 직접 의존은 `E_DEPENDENCY_CONTRACT_CHANGED`, 간접 의존은
  `E_DEPENDENCY_INVALIDATED`. 다섯 모듈 사슬에서 N0 이 왜 막혔는지 두 단계 거슬러 볼 수 있어야 한다.
- **선행 미검증은 BLOCKED 가 아니라 천장이다.** 원문 「4」는 `BLOCKED` 를 “선행 모듈이 검증되지 않음”으로
  정의한다. 문자 그대로 적용하면 V0 이 `VERIFIED` 가 아닌 지금 V1~V4 가 모두 `BLOCKED` 가 되어,
  원문 「28」이 정한 진행 방식(V 페이즈를 먼저 마치고 VS0 에서 함께 승격)과 충돌한다. 그래서
  **계약 변경으로 인한 무효화는 `BLOCKED`**(원문이 V4 에 요구한 대표 검증 그대로), **선행 미검증은
  `VERIFIED` 로 올라가지 못하게 하는 천장**으로 나눴다. 후자는 `E_DEPENDENCY_NOT_VERIFIED` 로 보고한다.
- **완성 판정에서 미측정 지표를 0 으로 적지 않는다.** 원문 「27」의 열 지표 중 세계 쪽 여섯 개는 담당 모듈
  (A5·K3·W3·A2·R4)이 아직 없다. `null` 로 두고 `pending` 에 담당을 적는다. 측정하지 않은 것을 통과로
  적는 순간 이 판정 전체가 쓸모없어진다.
- **자기 검증에 V3 를 쓴다.** V4 의 대표 장면은 그 자체가 Given-When-Then 이다 — “검증된 모듈이 있다 /
  선행의 계약을 바꾼다 / 하위가 `BLOCKED` 가 된다.” 실행기와 판정기를 각각 따로 만들면 둘 중 무엇이 틀렸는지
  알 수 없게 되므로, V3 의 `ScenarioRunner` 에 `issue_evidence` · `edit_contract` · `set_measurement` ·
  `forge_status` · `run_audit` 단계를 등록해 굴린다. 조건은 `/audit/status/K3 equals BLOCKED` 처럼 데이터다.
- **장면은 합성 저장소를 쓴다.** 실제 저장소의 증거는 `pnpm verify` 때마다 코드 해시가 바뀌어 고정 입력이
  될 수 없다. 원문 「2.5」가 예로 든 `K2 → K3 → I3 → R3 → N0` 를 합성 계약으로 세웠다. 실제 저장소를
  대상으로 한 감사는 `tests/integration/` 이 따로 돌린다 — 그쪽이 “이 저장소가 지금 정직한가”를 본다.

## 도구와 검사기를 V4 로 옮겼다

두 곳에 흩어져 있던 판정 규칙을 이 모듈로 모았다.

| 옮긴 것 | 전 | 후 |
|---|---|---|
| 증거 문서 생성·상태 결정 | `tools/verify.mjs` 가 직접 만들었다 | 측정만 하고 `issueForModule` 을 부른다 |
| 증거 형식·상태값 검사 | `tests/conventions.test.ts` 가 손으로 적었다 | `validateEvidenceDocument` 에 위임한다 |
| 계약 변경 감지 | 없었다 | `auditRepository` — 규약 검사에 새로 들어왔다 |

`tools/load-ts.mjs` 는 Node 스크립트에서 워크스페이스 TypeScript 를 부르기 위한 얇은 로더다. 새 의존을
들이지 않고 이미 있는 Vite 의 SSR 로더를 쓴다 — `apps/lab` 이 같은 패키지를 같은 규칙으로 번들하므로
도구가 보는 코드와 Lab 이 보는 코드가 갈라지지 않는다.

이 이전으로 **저장소 규약 검사에 새 항목이 하나 생겼다**: “선행 계약이 바뀐 채로 남은 증거가 없다”.
앞으로 어떤 `MODULE.yaml` 을 고치면 `pnpm test` 가 그 하위 모듈의 증거를 다시 발급하라고 요구한다.

## 지금 저장소의 판정

`pnpm verify <ID> --lab` 을 V0~V4 에 다시 돌려 새 형식으로 증거를 재발급했다. 다섯 모듈 모두 같은 자리에 있다.

```text
status=LAB_PASS
  막힌 게이트 G6 통합 게이트 — 슬라이스 1개 · 미통과 VS0
  막힌 게이트 G7 회귀 게이트 — 미측정 (회귀 측정 없음)
```

이 두 줄이 지금 V 페이즈의 정직한 상태다. G6 은 K0~K3 이 와야 열리고, G7 은 `--regression` 을 켜야
측정된다. 둘 다 열리기 전에는 어떤 모듈도 `VERIFIED` 가 될 수 없다.
