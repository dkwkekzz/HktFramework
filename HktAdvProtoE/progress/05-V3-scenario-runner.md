## 설계 판단

- **조건은 데이터다.** `{ path, op, value }` 세 조각뿐이고 표현식·콜백을 두지 않았다.
  원문 「23」의 “임의 실행 코드를 콘텐츠 데이터에 삽입” 금지는 콘텐츠뿐 아니라 **시나리오 데이터**에도
  그대로 적용된다. 조건 하나가 코드가 되는 순간, 시나리오는 검증 대상이 아니라 또 하나의 프로그램이 된다.
- **보고의 중심은 판정이 아니라 전후다.** 원문이 V3 에 요구한 직관 검증이 “실패한 조건의 전후 상태가 한
  화면에 표시”이므로, `ConditionResult` 는 통과 여부와 함께 `before`(Given 시점 값) · `after`(평가 시점 값) ·
  `blame`(그 경로를 마지막으로 바꾼 단계)을 **언제나** 담는다. 자식 경로를 바꾼 단계도 부모 조건의 원인으로 센다.
- **거부(규칙)와 오류(버그)를 나눴다.** `StepRejection` 은 상태를 전혀 바꾸지 않고 다음 단계로 가고,
  그 밖의 예외는 그 자리에서 시나리오를 멈춘다(`stoppedAt`). 이 구분이 없으면 VS0 의 완료 조건
  “네 번째 행동은 상태를 전혀 변경하지 않는다”를 표현할 수 없다.
- **실행 전 거부(preflight).** 모르는 픽스처·단계, 잘못된 `params`, 잘못된 조건은 한 단계도 굴리기 전에
  `/given/fixture` · `/when/0/step` · `/when/1/params/amount` · `/then/0/path` 를 지목하며 거부한다.
  절반쯤 굴러간 상태에서 나온 판정은 아무것도 증명하지 못한다. `params` 검사는 V1 스키마가 한다.
- **상태는 깊게 동결한다.** 단계가 받은 상태를 직접 고치면 “누가 이 값을 바꿨는가”를 추적할 수 없고
  전후 비교가 거짓이 된다. 동결해 두면 위반이 조용히 지나가지 않고 `TypeError` 로 드러난다.
  실제로 그런 단계를 등록해 굴려 보는 장면(`step_must_not_mutate_given_state`)을 두었다.
- **단계별 하위 난수 스트림.** `` `${stepId}#${occurrence}` `` 이름표로 V2 의 fork 를 연다.
  뒤에 단계를 덧붙여도 앞 단계의 난수열이 밀리지 않는다 — 단위 테스트로 고정했다.
- **digest 는 “일어난 일”만 담는다.** 제목·설명을 고쳤다고 리플레이가 깨졌다고 보면, 문서를 못 고치게 된다.
- **기본 단계는 일반 JSON 연산뿐이다.** 세계가 무엇인지는 K 페이즈가 정한다. V3 는 실행기이지 세계가 아니다.

## 선행에 V0 를 넣은 판단

원문 「8」의 표는 V3 의 선행을 `V1, V2` 로 적는다. 그것은 **검증 기능상의** 선행이고, 이 저장소의 V3
패키지는 그 위에 원문 「3.2」의 공통 TypeScript 계약(`ModuleDefinition` · `VerificationScenario` ·
`LabViewModel`)과 `sha256` 을 실제로 쓴다. 그 계약을 소유한 모듈이 V0 다.

의존을 숨기면 V4 의 무효화 연쇄(원문 「2.5」)가 **틀린 답**을 낸다 — V0 의 계약이 바뀌어도 V3 가
무효화되지 않기 때문이다. 그래서 실제로 쓰는 의존을 그대로 적었다. 원문 「28」의 고정 순서(V0~V4)에서
V0 은 이미 V3 보다 앞이므로 순서를 어기지 않으며, 원문이 V4 의 선행을 `V0~V3` 로 적는 것도 같은 독법이다.

V2 는 같은 자리에서 반대 선택(선언에 없는 V1 의존을 만들지 않는다)을 했는데, 그때는 손으로 쓴 검증기로
대체할 수 있었고 여기서는 **계약 타입 자체**라 대체하면 정의가 둘로 갈라진다는 점이 다르다.

## VS0 의 장면 형태를 미리 굴려 보았다

대표 장면 `rejected_step_leaves_state_unchanged` 는 VS0(원문 「20」)의 장면을 그대로 흉내 낸다 —
에너지 10, 행동마다 3 소비, 네 번째는 실패, 상태 변화 없음, 결과 1.

이것은 **VS0 통과가 아니다.** 세계 규칙은 K2 의 몫이고 사건 로그는 K3 의 몫이다. 다만 “VS0 을 표현할 수
있는 실행기인가”는 여기서 답이 나왔고, K 페이즈가 왔을 때 시나리오 형식을 다시 발명하지 않아도 된다.
`tests/integration/scenarios.test.ts` 에 `it.todo('VS0 — K0~K3 의 세계 규칙으로 다시 통과시킨다')` 로
자리를 남겼다.

## 발견한 것

`FixtureLoader` 가 같은 픽스처를 두 번 등록할 때 거부했다 — 저장본은 키 순서를 정규화(`deepClone`)해 두고
비교는 원본과 했기 때문이다. 단위 테스트(`같은 내용의 재등록은 허용한다`)가 잡았고, 비교도 정규화한 값끼리
하도록 고쳤다.
