## 목적 (G0)

행동 의도를 규칙의 조건·비용·효과에 따라 원자적으로 처리해, 성공이면 비용과 효과가 함께 적용되고 실패면 아무것도 적용되지 않게 한다.

## 계약 (G1)

| 항목 | 값 |
|---|---|
| 소유 상태 | `rule_book` |
| 입력 | `intent` · `rule_spec` · `world_state` |
| 출력 | `transaction_outcome` · `state_delta` · `rejection_cause` |

```text
Intent → Rule 조건·비용 검사 → StateDelta
```

## 설계 판단

### ① 원자성은 순서가 아니라 K0 의 불변 저장소에서 온다

“절반만 적용”을 예외 처리 규약으로 막으면 언젠가 새는 경로가 생긴다. 여기서는 작업용 저장소에
비용과 효과를 쌓다가, 하나라도 어긋나면 **그 저장소를 통째로 버린다.** 원본은 손댄 적이 없으므로
그대로 남는다 — 거부된 트랜잭션은 입력과 **같은 객체**를 돌려준다.

순서(비용 → 효과)는 다른 것을 정한다. 지불 능력을 **효과가 일어나기 전 상태**로 재는 것이다.
효과가 자원을 늘리는 규칙이라도, 아직 없는 자원으로 비용을 낼 수는 없다.

### ② 지불 능력은 컴포넌트 스키마가 정한다

“에너지가 모자라면 실패한다”를 K2 안에 적지 않았다. `energy.current` 의 스키마가 `minimum: 0` 이면
1 에서 3 을 더 빼는 순간 K0 이 거부하고, K2 는 그 거부를 `E_UNAFFORDABLE_COST` 로 옮긴다.

- 자원마다 하한을 다시 적을 필요가 없다.
- 하한이 **한 곳**(스키마)에만 있으므로 둘이 갈라질 수 없다.
- 산술 효과(`add`·`multiply`·`transfer`)의 스키마 위반은 언제나 “하한을 넘었다”는 뜻이므로 비용이든
  효과든 가리지 않고 지불 불가로 옮긴다. 값을 통째로 갈아 끼우는 `set` 의 위반은 규칙이 잘못 적힌
  것이므로 `E_BAD_EFFECT` 다.

### ③ 의도를 세계에 잠깐 올린다

규칙의 `when` 은 `PredicateSpec` 이고, `PredicateSpec` 은 세계 상태에 대한 조건이다. 그런데
“이 의도가 공격인가”는 세계 어디에도 없다. `RuleSpec` 에 `verb` 칸을 새로 파는 것은 상위 계약
변경이므로(원본 15.3 · 원문 「23」), 반대로 **의도를 임시 실체로 세계에 올린다.**

```ts
when: { op: 'eq', path: 'intent.intent_spec.verb', value: 'strike' }
```

원본 19.4 의 사건 해결도 “제출된 Intent”를 세계의 일부로 다룬다. 임시 실체는 트랜잭션이 끝나기 전에
반드시 지운다 — 남으면 세계 해시가 흔들려 재생이 깨진다(속성 테스트가 이것을 지킨다).

### ④ 제약 규칙과 행동 규칙

비용도 효과도 흔적도 없는 규칙은 **제약 규칙**이다. 선을 긋는 것이 그 규칙의 전부이므로 골라서
적용하지 않는다 — 그러지 않으면 “아무 일도 하지 않은 성공”이 나온다.

| 막는 규칙 | 언제 막는가 |
|---|---|
| 제약 규칙 | 계층과 무관하게 언제나 (L6 개인의 맹세도 L1 물리 행동을 막을 수 있다) |
| 행동 규칙 | 고른 규칙보다 권위가 높을 때(scope 번호가 작을 때) |

행동 규칙 중에서는 **가장 국소적인 것**(scope 번호가 큰 것)을 고른다 — 원본 15.1 의
“낮은 단계의 규칙은 높은 단계의 규칙이 허용하는 범위 안에서만 예외를 만들 수 있다”가 그 뜻이다.
축복받은 기사는 L4 지역 규칙으로 더 싸게 때리지만, 죽은 기사는 L4 의식이 있어도 L1 의
“죽은 신체는 행동할 수 없다”를 넘지 못한다.

### ⑤ 규칙집은 만들 때 한 번 정렬한다

`scope` 오름차순 → `priority` 내림차순 → `id` 오름차순. 선언 순서가 결과를 바꾸면 같은 세계가
서버마다 다르게 굴러간다(GI-12). 규칙집 해시도 이 정렬 뒤에 계산하므로 선언 순서와 무관하다.

### ⑥ 델타에 없는 변화는 없다

효과를 적용하는 자리가 `StateDelta` 를 만드는 **유일한** 자리다. 델타에 없는 변화는 K3 이 사건으로
기록할 수 없고, 그것이 곧 GI-01(사건 없는 상태 변경) 위반이다.

실패해도 세계가 바뀌는 경로는 하나뿐이다 — 규칙이 `failureEffects` 를 **미리 선언**한 경우.
그 변화도 델타에 남으므로 기록 없는 상태 변경이 아니다. 비용·효과 델타와는 따로 센다.

### ⑦ `schedule_event` 는 예약만 한다

상태를 바꾸지 않고 `scheduled` 목록에만 남긴다. 실제로 일으키는 일은 K3 의 Scheduler 가 한다.
