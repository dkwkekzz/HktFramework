# 에너지 보존 동기화 (Energy Conservation Sync) — 초경량 MMORPG 서버 설계

> 상태: 제안 v0.1
> 관련 문서: [HktSim_Design.md](HktSim_Design.md) §5 보존 법칙 · §7 하이브리드 권위, [CombatSystemDesign.md](CombatSystemDesign.md), [Runtime-Pipeline.md](Runtime-Pipeline.md)

## 0. 한 줄 요약

> **서버는 시뮬레이터가 아니라 회계사(ledger arbiter)다.** 서버가 유지·검증·동기화하는 것은 오직 "에너지 원장" — 보존되는 스칼라 풀(pool)들과 그 사이의 이체(transaction)뿐이다. 움직임·물리·연출·VM 세부는 전부 클라이언트가 결정론적으로 유도한다.

기존 아키텍처(이벤트 배치 동기화 + GGPO 롤백)는 **대역폭은 이미 가볍다**. 무거운 것은 *서버 CPU* — 서버가 전체 월드를 풀 결정론 시뮬레이션한다는 점이다. 이 설계는 서버의 책임을 보존 법칙 하나로 축소해 서버 비용을 O(엔티티 × 시스템) 에서 **O(트랜잭션/초)** 로 낮춘다.

---

## 1. 왜 "보존 법칙"이 동기화의 최소 단위가 되는가

MMORPG 에서 서버가 반드시 해야 하는 일을 끝까지 깎으면 세 가지만 남는다.

1. **희소성 보증** — 자원·데미지·아이템이 무에서 창조되지 않음 (치팅 방지)
2. **순서 중재** — 같은 자원을 두 클라이언트가 동시에 집었을 때 승자 결정
3. **무결성 검증** — 클라이언트 상태가 규칙을 벗어났는지 감지

셋 모두 **보존 법칙 하나로 환원된다**:

- 희소성 = "모든 풀의 합은 불변" (에너지 생성 금지)
- 중재 = "이체는 원장에 기록된 순서로만 유효, 잔고 초과분은 클램프" — [HktSim_Design.md](HktSim_Design.md) §5 의 추출 클램프(`Got < Want`)와 동일 원리
- 검증 = "지역별 풀 합계 체크섬 비교" — int64 덧셈 하나로 O(1) 갱신

반대로 위치·애니메이션·VFX·경로는 보존량이 아니다 → 서버가 들고 있을 이유가 없다. 결정론 VM(HktCore)이 이미 있으므로 **같은 입력에서 같은 세부가 유도**되고, 서버는 입력의 순서와 에너지 수지만 보증하면 된다.

## 2. 모델 — 풀과 트랜잭션

### 2.1 에너지 풀 (Pool)

세계의 모든 "가치"는 풀에 담긴 정수 에너지로 표현한다.

| 풀 종류 | 예시 | 소유 |
|---|---|---|
| **엔티티 풀** | 유닛의 생체 에너지 (HP/Mana/CP 는 이 풀의 파티션 뷰) | 엔티티 |
| **필드 풀** | 셀/청크의 원소 농도·열 (HktSim FieldChunk) | 지역(청크) |
| **인벤토리 풀** | 아이템 = 응축된 에너지 덩어리 | 엔티티 |
| **월드 소스/싱크** | 스폰 예산, 사망 소멸분, 시스템 보상 | 서버 전용 |

- 잔고는 `int64`, 이체량은 `int32` — 결정론(정수 연산)과 오버플로 안전을 동시에 확보.
- 비보존 게임플레이(버프, 경험치, 리스폰)는 **월드 소스/싱크 풀과의 이체**로 표현한다. 무에서 창조가 아니라 서버 전용 풀에서의 인출이므로 감사 추적(audit trail)이 유지되고, 불변식은 "전 풀 합 = 상수"로 그대로 성립한다.

### 2.2 트랜잭션 (Transaction) — 유일한 동기화 단위

```
FHktEnergyTransaction (16 bytes)
 ├─ FromPool  : uint32   ← 출금 풀 (엔티티 ID | 청크셀 ID | 시스템 풀 ID)
 ├─ ToPool    : uint32   ← 입금 풀
 ├─ Amount    : int32    ← 이체량 (서버 클램프 후 확정값)
 └─ CauseTag  : uint16 + Frame 하위비트 : uint16
```

모든 게임플레이 효과가 이체로 환원된다:

- 데미지 = 공격자 스킬 풀 → 피격자 생체 풀 차감 (싱크 경유)
- 채집 = 필드 셀 풀 → 인벤토리 풀 (= HktSim 응축)
- 스킬 시전 = 생체 풀 → 싱크 (기존 `SkillCPCost` 가 그대로 이체량)
- 이동 = 생체 풀 → 환경 싱크 (스태미나 지출; §5.2 이동 검증의 근거)

### 2.3 서버가 하는 일의 전부

```
클라 A: 의도(intent) ──→ ① 클램프: Amount = min(요청, FromPool 잔고)
                          ② 순서 확정: Frame + Seq 부여 (동시성 중재)
                          ③ 원장 커밋: 잔고 갱신 + 지역 합계 O(1) 갱신
                          ④ 브로드캐스트: relevancy 셀 내 클라에게 tx 스트림
                                        + 주기적 지역 체크섬 (int64 1개)
```

서버는 Movement/Gravity/Physics/VM 시스템을 **돌리지 않는다**. relevancy 와 사거리 검증용으로 저빈도(예: 2Hz) 양자화된 **좌표 비콘**만 클라에게서 수신해 유지한다.

## 3. 클라이언트 — 세부는 전부 로컬에서 유도

클라이언트는 기존 파이프라인을 그대로 쓴다. 바뀌는 것은 "서버 batch 의 내용물"뿐이다.

- 기존: `FHktSimulationEvent` batch = 전체 시뮬 입력 → 클라가 풀 시뮬 재실행 + 롤백(`UndoDiff`)
- 변경: batch = **확정된 트랜잭션 스트림 + 입력 이벤트** → 클라 VM 이 이를 결정론적으로 소화

즉 `UHktProxySimulatorComponent` 의 예측·롤백·화해 루프(`ProcessPendingServerBatches`)는 수정 없이 재사용된다. 트랜잭션은 "또 하나의 결정론 이벤트 타입"일 뿐이다.

- **예측**: 클라는 자기 의도의 이체를 낙관 적용해 즉시 연출 (기존 로컬 예측 프레임과 동일).
- **화해**: 서버 확정 Amount 가 예측과 다르면(잔고 부족 클램프, 경합 패배) 기존 롤백 경로로 되감고 재적용. `Got < Want` 는 실패가 아니라 게임플레이(고갈)다.

## 4. 무결성 — 체크섬으로 상태 동기화를 대체

전체 상태 해시나 프로퍼티 복제 대신, 보존 불변식 자체를 검증 채널로 쓴다.

1. 서버는 relevancy 그리드 셀(기존 `HktGridRelevancyComponent` 격자 재사용) 단위로 **풀 합계 int64** 를 유지 — 이체마다 출금 셀 -Amount, 입금 셀 +Amount, O(1).
2. N 프레임(기본 30, CVar)마다 셀 체크섬을 tx 스트림에 piggyback.
3. 클라는 로컬 원장 합계와 비교. 불일치 = 그 셀만 desync → **그 셀의 풀 스냅샷만 재요청** (풀 목록은 작다 — 셀당 수십 개의 int64).

효과: 주기적 풀 스테이트 동기화가 사라지고, 복구 비용이 "틀린 지역 한 칸"으로 국소화된다. [HktSim_Design.md](HktSim_Design.md) §2.5 재시딩 트릭과 결합하면 서버 영속화 대상도 원장 잔고뿐이다.

### 대역폭 추정

| 항목 | 크기 | 빈도 | 플레이어당 하향 |
|---|---|---|---|
| 트랜잭션 | 16 B | relevancy 내 ~50 엔티티 × 평균 2 tx/s | ~1.6 KB/s |
| 지역 체크섬 | 8 B | 관심 셀 ~9개 × 2 Hz | ~150 B/s |
| 좌표 비콘 | 8 B (양자화) | ~50 엔티티 × 2 Hz | ~800 B/s |

합계 ≈ **2~3 KB/s** — 프로퍼티 복제형 MMORPG(수십 KB/s) 대비 한 자릿수 이상 절감. 서버 CPU 는 시뮬 시스템 8종 → 정수 덧셈 원장 하나.

## 5. 치팅 모델 — 보존이 곧 안티치트

- **에너지 생성 치트** (데미지 뻥튀기, 아이템 복제): 원장 클램프가 구조적으로 차단. 검증 코드가 아니라 자료구조가 막는다.
- **스피드핵**: 이동 = 에너지 지출(§2.2)이므로, 좌표 비콘 간 이동 거리가 지출 에너지로 불가능하면 기각. 서버는 물리를 몰라도 *예산 초과*는 안다.
- **원거리 상호작용 치트**: 이체 요청 시 FromPool/ToPool 소유자의 비콘 거리 검증 (양자화 좌표로 충분 — 정밀 판정이 아니라 개연성 판정).
- **잔여 리스크**: 서버가 세부를 모르므로 "회피했는데 맞았다" 류의 판정 분쟁은 클라 결정론에 위임된다. 고부가 판정(PvP, 레이드 보스)은 §7 의 선택적 재시뮬 감사로 보강.

## 7. 단계적 도입 로드맵

각 단계는 독립적으로 가치가 있고, 이전 단계 위에 위성처럼 붙는다.

| 단계 | 내용 | 완료 기준 | 서버 부하 변화 |
|---|---|---|---|
| **0. 원장 코어** | `FHktEnergyLedger` + `Energy` 프로퍼티, 데미지/코스트를 tx 로 표현 (동기화는 기존 그대로) | 단위 테스트: 임의 tx 시퀀스 후 전 풀 합 불변 | 없음 (기반) |
| **1. tx 수송** | tx 를 `FHktSimulationEvent` 에 편입, 서버 클램프·순서 확정 | 두 클라 동시 채집 → 한쪽 `Got < Want` 클램프 재현 | 없음 |
| **2. 체크섬 채널** | 지역 int64 합계 + 주기 브로드캐스트 + 셀 단위 스냅샷 복구 | 인위적 desync 주입 → 해당 셀만 복구 | 소폭 감소 (상태 sync 제거) |
| **3. 서버 슬리밍** | 서버에서 Movement/Gravity/Physics 시스템 off, 좌표 비콘 + 예산 검증으로 대체 | 서버 tick 프로파일: 시뮬 비용 → 원장 비용 | **핵심 절감 지점** |
| **4. 필드 편입** | HktSim FieldChunk 풀을 원장에 연결, diffusion 을 이웃 셀 간 정수 이체(zero-sum)로 | 고갈→회복 루프가 tx 로그만으로 재생 가능 | 필드 동기화 공짜 편입 |
| **5. 감사(audit)** | 고부가 판정 샘플링 재시뮬 (서버가 랜덤하게 일부 상호작용만 풀 시뮬 검증) | 조작된 클라 판정 탐지율 측정 | 튜닝 가능한 소량 |

**권장 시작점: 단계 0.** HktCore 순수 모듈이라 네트워크 없이 단위 테스트만으로 보존 불변식을 확정할 수 있고, 이후 모든 단계가 이 자료구조 위에 선다.

## 8. 한계와 정직한 트레이드오프

- **위치는 보존량이 아니다.** 위치 정밀 동기화가 필요한 장르 요소(논타겟 정밀 히트박스 PvP)는 이 모델만으로 부족 — 좌표 비콘 빈도를 올리거나(§2.3) 해당 지역만 기존 풀 시뮬 모드로 승격하는 **레벨 오브 시뮬레이션** ([HktSim_Design.md](HktSim_Design.md) §7) 과 병행해야 한다.
- **클라 결정론 신뢰.** 세부 판정을 클라에 위임하므로, 결정론 드리프트는 체크섬으로 *감지*는 되지만 *판정 정당성*은 보증하지 못한다 → 단계 5 감사가 보완 장치.
- **모든 것을 에너지로 환원하는 디자인 비용.** 스킬·아이템·경제를 이체 문법으로 기술해야 한다. 다만 이는 [히키토의_대모험_방향성.md](히키토의_대모험_방향성.md) 의 보존 기반 순환 디자인과 방향이 일치하며, Story 바이트코드(JSON schema 2)에 tx 스니펫 하나를 추가하는 것으로 흡수 가능하다.
