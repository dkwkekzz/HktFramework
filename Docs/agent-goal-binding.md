# Goal 작업 운영 가이드

> **종류:** 운영 절차 명세
> **의존 문서:** `goal-system-design.md`
> **사용 모델:** 사용자가 필요 시 본 문서를 명시적으로 참조하며 Goal 관련 작업을 요청한다. 자동/암묵적 적용은 의도되지 않음.
> **상태:** v0.3 / 2026-05-04

---

## 1. 적용 모델

### 1.1 호출 모델

본 가이드는 **사용자 명시 호출형**이다:

- 사용자가 Goal 관련 작업이 필요하다고 판단할 때 본 문서를 참조하며 에이전트에게 작업을 요청한다.
- 일반 작업에 본 가이드를 자동 적용하지 않는다.
- 본 가이드는 `CLAUDE.md` 등 자동 로드 컨텍스트에 포함되지 않는다.

### 1.2 호출 트리거 (예)

| 사용자 발화 | 트리거되는 작업 |
|------------|----------------|
| "G-XXXX 보여줘 / 분해해줘 / 검증해줘" | 4절 라이프사이클 (Goal 작업) |
| "이 작업을 Goal로 정리하자" | 4.2 A (작성) |
| "이 코드는 어느 Goal에 봉사해?" | 4.1 Q (조회) |
| "버그 분석에 Goal 양상 분류 적용해줘" | 3절 (버그 양상 분류) |

본 가이드 호출 없이 진행되는 일반 작업은 Goal과 결합되지 않은 채로 진행된다.

### 1.3 강제 금지

다음 행동은 본 가이드와 무관하게 금지된다:

- Goal ID 없는 작업의 거부
- 사용자가 호출하지 않은 상태에서 Goal 결합을 강요
- 자유 작업마다 "이건 Goal 결합 없이 처리합니다" 같은 안내

## 2. 작업 분류

### 2.1 분류표

본 가이드 호출 시, 받은 작업을 다음 4가지로 분류:

| 유형 | 정의 | Goal 결합 |
|------|------|----------|
| **Goal 작업** | Goal 시스템 자체 조작 (Q/A/P/V) | 입출력이 Goal 파일 |
| **의도 작업** | 새 시스템·기능·아키텍처 추가 | Goal 작성 제안 (수락 시 결합) |
| **봉사 작업** | 기존 Goal 실현 개선 | 봉사 Goal 명시·추론 |
| **자유 작업** | 위 셋에 해당 안 됨 | 결합 없음 |

### 2.2 분류 결정 절차

위에서 아래로 평가, 첫 Yes에서 멈춤:

| # | 질문 | Yes → 분류 |
|---|------|----------|
| 1 | 사용자가 Goal ID를 명시했는가? | 봉사 작업 |
| 2 | 사용자가 Goal 자체를 다루는 동사("보여줘", "만들어줘", "검증해줘")를 썼는가? | Goal 작업 |
| 3 | 작업이 버그 수정/증상 보고인가? | 3절 적용 (양상별 재분류) |
| 4 | 작업이 새 시스템·기능·아키텍처 추가인가? | 의도 작업 |
| 5 | 모두 No | 자유 작업 |

### 2.3 분류별 사용자 노출

| 분류 | 알릴 내용 |
|------|----------|
| Goal 작업 | 변경할 Goal 파일과 영향 범위 |
| 의도 작업 | Goal 작성 제안 (수락/거부 선택지) |
| 봉사 작업 | 봉사 Goal ID와 결합 근거 |
| 자유 작업 | 알리지 않음 |

### 2.4 분류 수정

에이전트 분류는 제안. 사용자가 다른 분류를 명시하면 따름.

## 3. 버그 수정 양상 분류

### 3.1 양상표

| ID | 정의 | 처리 분류 | 우선순위 |
|----|------|----------|---------|
| B1 | 증상이 기존 Goal의 success criterion 위반 | 봉사 작업 | 일반 |
| B2 | 증상이 Constraint Goal 위반 | 봉사 작업 | 긴급 |
| B3 | 수정 중 "이런 의도가 있었어야 했다" 인식 | Goal 작업 (A) + 봉사 작업 | 일반 |
| B4 | 위 셋에 해당 안 됨 | 자유 작업 | 일반 |

### 3.2 판정 절차

| # | 질문 | Yes → 양상 |
|---|------|----------|
| 1 | 증상이 기존 Goal의 success criterion 위반? | B1 |
| 2 | 증상이 Constraint Goal 위반? | B2 |
| 3 | 수정 중 명시되지 않은 의도가 드러나는가? | B3 |
| 4 | 모두 No | B4 |

### 3.3 양상별 처리

| 양상 | 절차 |
|------|------|
| B1 | 4.4 S (봉사) 절차로 처리. 회귀 테스트를 success criterion 측정에 통합. |
| B2 | 4.4 S (봉사) 절차로 처리. 다른 작업 중단. 위반 경로 분석을 보고에 포함. |
| B3 | 1) 버그 수정 완료. 2) 사용자에게 Goal 작성 제안. 3) 수락 시 4.2 A 진입. 거부 시 종결. |
| B4 | 결합 없이 수정. |

### 3.4 B3 제안 형식

```
수정 완료. 작업 중 "<드러난 의도>"가 명시된 Goal로 없음을 확인.
Goal로 추가 시 효과:
- 동종 버그 회귀 검증 자동화
- 해당 영역 의도 명시화
추가할까요?
```

### 3.5 양상 비율의 신호

| 비율 | 시사 |
|------|-----|
| B1, B2 다수 | success criterion이 측정 가능하게 작성됨 (정상) |
| B3 다수 | 해당 영역 Goal 커버리지 부족 |
| B4 다수 | 정상 (모든 작업이 Goal일 필요 없음) |

## 4. Goal 라이프사이클 절차

5종 작업: **Q**uery, **A**uthor, **P**lan, **S**erve, **V**erify.

### 4.1 Q — 조회

#### 트리거
- "Goal 보여줘 / 검색해줘"
- "이 코드는 어느 Goal에 봉사해?"
- 다른 작업 시작 시 관련 Goal 파악

#### 절차

| # | 단계 |
|---|------|
| 1 | 단순 조회는 자동 생성 뷰(`INDEX.md`/`TREE.md`/`graph.mmd`) 우선 사용 |
| 2 | 복잡 조회는 frontmatter 필터링 (도구 호출) |
| 3 | 결과를 ID 목록 + 요약으로 출력 |

#### 출력 형식

```
조회 결과 (필터: <조건>)
- G-0110 <title> (active)
- G-0142 <title> (active) — 다중 부모: G-0010, G-0020
총 N개. 상세: docs/goals/G-XXXX.md
```

### 4.2 A — 작성·수정

#### 트리거
- 의도 작업의 Goal 작성 제안 수락
- B3 후속 작성
- "Goal 만들어줘 / 수정해줘 / 폐기해줘"

#### 4.2.1 신규 작성 절차

| # | 단계 |
|---|------|
| 1 | `next-id` 도구로 ID 할당 |
| 2 | 사용자와 대화로 필수 필드 채움 (title, intent, success_criteria, parents, constraints) |
| 3 | 초안 제시 → 사용자 검토 |
| 4 | 무결성 검증 (도구 호출) |
| 5 | 자동 생성 뷰 갱신 트리거 |

#### 4.2.2 초안 제시 형식

```
초안:
---
id: <할당 예정>
title: <기술된 제목>
status: proposed
parents: [<제안 부모 + 근거>]
constraints: [<해당 시>]
success_criteria:
  - description: ...
    measurable: true | false
    measure: ...
---
검토 후 확정 시 ID 부여.
```

#### 4.2.3 수정 절차

| # | 단계 |
|---|------|
| 1 | 기존 Goal 파일 읽음 |
| 2 | 영향 분석: 봉사 코드, 자식 Goal에 미치는 영향 |
| 3 | 사용자 확인 후 변경 적용 |
| 4 | `updated_at` 갱신 |

#### 4.2.4 폐기·대체

| 작업 | 처리 |
|------|------|
| 폐기 | `status: abandoned`. 자식 Goal은 재배치 또는 함께 폐기 (사용자 결정). 파일 삭제 X. |
| 대체 | `status: superseded` + `superseded_by: G-YYYY`. 파일 삭제 X. |

### 4.3 P — 일감 도출

#### 트리거
- "Goal 분해해줘 / 일감으로 풀어줘"
- 봉사 작업 시작 전 작업 목록 도출

#### 절차

| # | 단계 |
|---|------|
| 1 | 대상 Goal의 success criteria 읽음 |
| 2 | 현재 `realizes` 코드 점검 |
| 3 | 미달 부분 식별 |
| 4 | 각 미달 부분을 좁히기 위한 Task 후보 생성 |
| 5 | 각 Task에 봉사 Goal ID 명시 |

#### Task 최소 표현

본 문서는 Task 시스템 상세를 정의하지 않음. Goal 결합을 위한 최소 필드만:

```yaml
goal_id: G-0142          # 다중 가능
title: <짧은 제목>
description: <상세>
status: todo | in_progress | done | cancelled
created_at: <ISO8601>
```

### 4.4 S — 봉사 작업

#### 트리거
- 도출된 Task 구현
- 사용자가 Goal ID 명시한 구현 요청

#### 절차

| # | 단계 |
|---|------|
| 1 | 봉사 Goal의 intent와 constraints를 컨텍스트에 로드 |
| 2 | constraints 위반 가능성 사전 점검 |
| 3 | 코드 작성/수정 |
| 4 | 새/변경 코드에 `@goal:` 태그 추가/유지 |
| 5 | Goal `realizes` 갱신 (도구 호출) |
| 6 | 완료 보고에 봉사 Goal 명시 |

#### 4.4.1 제약 위반 발견 시

| # | 처리 |
|---|------|
| 1 | 진행 중단 |
| 2 | 위반 원인 보고 |
| 3 | 회피 옵션 제시 (재설계 / 우회 / 별도 Goal 분리) |
| 4 | 사용자 결정 후 진행 |

### 4.5 V — 달성 검증

#### 트리거
- "Goal 달성됐는지 검증해줘"
- `status: achieved`로 변경 전

#### 절차

| # | 단계 |
|---|------|
| 1 | success criteria 읽음 |
| 2 | `measurable=true` 항목 자동 측정 시도 (`verify-goal` 도구) |
| 3 | `measurable=false` 또는 자동화 미구현 항목은 수동 확인 요청 |
| 4 | 결과 보고 |
| 5 | status 변경은 사용자 확인 후 (자동 변경 금지) |

#### 출력 형식

```
G-XXXX 검증 결과

Criterion 1: <description>
  측정: <measure>
  결과: ✅ pass | ❌ fail | ⚠ manual_required
  현재 값: <value>

종합: N/M 충족
권장 status: active 유지 | achieved 변경 가능 | 추가 봉사 작업 도출
```

## 5. 워크플로 통합

### 5.1 Chat ↔ Code 핸드오프

| 단계 | 도구 | 산출물 | 라이프사이클 |
|------|------|--------|-------------|
| 의도 정립 | Claude Chat | Goal 파일 | A |
| 일감 분해 | Claude Chat | Task 목록 (Goal ID 포함) | P |
| 구현 | Claude Code | 코드 + `@goal:` 태그 | S |
| 검증 | Claude Code 또는 CI | 검증 보고서 | V |

핸드오프 매개는 Goal ID. Code 측은 Goal ID로 Goal 파일을 읽어 intent/constraints/success_criteria를 컨텍스트에 로드.

| 상황 | 분류 | 근거 |

| "이 함수 리팩토링" | 봉사 (태그 있음) / 자유 (태그 없음) | `@goal` 태그 유무 |

| "라이브러리 교체" | 의도 / 자유 | 아키텍처 영향에 따라 |
| "문서 업데이트" | Goal 작업 / 자유 | Goal 파일 변경이면 Goal 작업 |
