## Intent

획득한 재료를 *조합* 해 새 산출물을 만든다. 두 개 이상의 아이템 엔티티(또는 스냅샷)를 *소비* 하고 새 아이템 엔티티를 SpawnEntity 한다 — 성장 루프의 마지막 단계이자 [I-0013 — 성장을 위한 재료](I-0013.md) 의 종착점.

조합은 *재료의 의미를 변환* 한다. 월드에서 떨어진 단편(나무·돌·뼈) 이 그대로 전투력이 되지 않고, *조합* 의 인과를 거쳐야 무기·도구·소비재가 된다. 이 한 단계가 있어야 *재료 수집* 이 단순한 줍기가 아니라 *목적 있는 행위* 가 된다.

## 현재 구현 상태

**미구현.** Story Event Tag `Story.Event.Item.Craft` 가 [Design-Entity-Item-System.md](../Design-Entity-Item-System.md) §3.4 에 *향후* 항목으로만 명시되어 있고, 다음이 모두 누락:

- Recipe 데이터 모델 (입력 ItemId × 수량 → 출력 ItemId × 수량) 없음
- Recipe DataAsset / GameplayTag 분류 체계 없음
- `Story_ItemCraft.json` 없음 — 소비/생성 시퀀스 미정의
- 제작 UI 패널 없음 ([SHktIngameHudWidget](../../HktGameplay/Source/HktUI/Private/Widgets/SHktIngameHudWidget.h) 에 Skills/Inventory/Equipment 만 존재)
- 작업대 / 위치 기반 제약 미정 (어디서나 제작 vs 특정 voxel/structure 에서만 제작)

## 구현 (제안)

### 데이터 모델

- **`UHktRecipeDataAsset`** (신규) — `RecipeTag: FGameplayTag` 식별, `Inputs: TArray<{ItemId, Count}>`, `Output: {ItemId, Count, 초기 스탯 override}`, `RequiredStation: FGameplayTag` (선택).
- **GameplayTag**: `Recipe.{Category}.{Name}` (예: `Recipe.Weapon.WoodSpear`).
- **로딩**: [HktAsset](../../HktGameplay/Source/HktAsset) 의 GameplayTag → DataAsset 비동기 로딩 채널 재사용.

### Story / 권위

- **Event 진입점**: `Story.Event.Item.Craft` — Client Intent. Param: RecipeTag (또는 RecipeId 정수).
- **Precondition**:
  1. RecipeTag 가 유효한 등록 Recipe 인가
  2. 입력 재료가 *어디에* 있는가 — [I-0038](I-0038.md) 의 Player Inventory 또는 Entity 가방(InBag) 에서 수량 충족 검증
  3. `RequiredStation` 이 있으면 Self 위치가 해당 voxel/structure 근접 범위 안인가
- **본문**:
  1. 입력 아이템 소비 — InBag 스냅샷에서 차감 또는 엔티티 RemoveEntity (수량만큼)
  2. 출력 아이템 SpawnEntity — `OwnerEntity = Self`, `OwnerUid` 자동 전파, `ItemState = 1 (InBag)` 또는 Inventory 로 직접 Grant
- **결정론**: Recipe 의 출력 스탯이 random growth 를 포함할 경우, 시뮬레이션 시드 사용 (C++ random 금지 — VM Op 경유)

### UI

- 제작 패널 신규 (HUD 하단 바에 "Craft" 버튼 추가) — Recipe 목록 / 입력 재료 표시 / 보유 수량 / 제작 가능 여부 표시.
- 재료 소스: Player Inventory ([I-0038](I-0038.md)) 우선, 없으면 현재 Entity 가방 ([I-0037](I-0037.md)) 폴백 — 또는 Inventory 전용으로 한정 (정책 미정).

### TODO / 격차

- **Recipe DataAsset 스키마 확정** — 입력/출력만의 단순 모델 vs 확률 분기·실패율·품질 등급을 포함하는 확장 모델 중 선택. 1차는 결정론적 단순 모델 권장.
- **재료 소스 정책** — Inventory 전용 / 가방 폴백 / 둘 다 가능 중 결정 (I-0038 과 동시 결정 필요).
- **작업대 (Crafting Station) 모델** — voxel 자체의 능력 ([I-0013](I-0013.md), [I-0027](I-0027.md)) 과 통합. *모루 voxel 근처에서만 무기 조합 가능* 같은 정책을 voxel attribution 으로 환원.
- **성장 / 강화 시스템** — [Design-Entity-Item-System.md](../Design-Entity-Item-System.md) §8.2 의 *같은 아이템 2 개를 소비해 Level 증가* 가 본 의도의 특수 케이스인가 별도 의도인가 결정.
- **연쇄 조합 / 자동화** — 1차에서는 1 회 1 Recipe 만. 자동 반복·일괄 제작은 추후.
