## Intent

entity 는 *죽음과 동시에* 들고 있던 아이템을 월드에 떨어뜨리고, 다른 살아있는 entity 는 그것을 *주워* 다시 자신의 슬롯으로 가져갈 수 있다. 죽음 → 드랍 → 픽업 한 줄기가 모험·성장의 *순환* 을 만든다 — 죽인 것에서 무언가가 남고, 그것이 다음 entity 의 능력으로 흡수된다.

**드랍은 Lifecycle 안의 한 줄이다.** 사망은 [I-0034 — 엔티티 수명주기](I-0034.md) 의 lifecycle Story 가 `WaitTag(Self, StateDead)` 로 깨어나는 지점에 정의되어 있고, 드랍은 그 깨어남의 *직접적 결과* 다. 드랍을 lifecycle 바깥의 별도 시스템(별도 이벤트 채널, C++ 사망 후크) 으로 분리하면 사망의 인과가 lifecycle / drop / cleanup 세 곳으로 흩어져, 어느 한 곳에서만 손실되어도 *시체는 남지만 아이템이 사라지는* 회귀가 silent 로 새어 나간다. 동일 패턴이 여러 lifecycle (NPC / Player / Voxel unit / Building) 에서 반복되므로, 드랍은 **snippet 으로 모듈화** 되어 [HktSnippetItem](../../HktGameplay/Source/HktStory/Public/Snippets/HktSnippetItem.h) 의 `DropToGround` / `SpawnGroundItemAtPos` 한 줄로 호출되어야 한다 — 같은 의미의 코드가 lifecycle 마다 손으로 복제되는 순간 본 의도는 무너진다.

**픽업은 클라이언트 액션이다.** 서버가 매 틱 모든 living entity × 모든 ground item 의 proximity 를 폴링하면 *상호작용이 일어나지 않는 시점에도* 전수 계산이 깔리고, 월드 규모가 커질수록 그 비용이 폭증한다. 픽업은 사용자(또는 NPC Brain) 가 *명시적으로 시도* 했을 때만 서버 판정이 일어나야 한다 — 클라이언트는 근접한 ground item 을 인식해 `Story.Event.Item.Pickup` 을 디스패치하고, 서버는 [Story_ItemPickup](../../HktGameplay/Content/Stories/Story_ItemPickup.json) 의 precondition (거리·상태·빈 슬롯) 으로 *권위 있는 한 번* 의 판정만 수행한다. 클라가 픽업 모양을 잘못 그리면 *눈에 보이는 픽업 범위* 와 *서버 판정 범위* 가 어긋나므로, 픽업 볼륨의 정합은 [I-0033 — 엔티티 충돌·선택의 시뮬레이션 일치](I-0033.md) 위에 선다.
