## Intent

러너의 질주에 *목표* 를 주는 것은 보상이다. 본 의도는 두 층의 보상 척추를 세운다 — **처치 보상** 과 **현상금 계약**. 적을 처치하면 *부(富)* 가 쌓이고(짧은 루프), 특정 대상에 걸린 *현상금* 을 회수하면 큰 보상이 터진다(중간 루프). [방향성 문서](../히키토의_대모험_방향성.md) Pillar 3 의 마이크로·미들 도파민 루프를 러너 한 판 안에 압축한다.

*현상금* 은 단순 처치 보상을 넘어선다. 플레이어/NPC 가 특정 대상(적·보스·타플레이어) 에 *부를 걸어* 계약을 만들고, 그 대상을 처치한 자가 *수령* 한다. "내가 건 현상금에 누군가 응한다" 와 "남이 건 현상금을 내가 회수한다" 가 서버 단위 상호작용을 만든다 — [방향성 문서](../히키토의_대모험_방향성.md) Pillar 4 (사회적 관계망) 의 씨앗이다.

설계 원칙은 [I-0014](I-0014.md) 와 동일하다 — *보상 인과 전부가 결정론 VM 안의 Story op 으로 표현* 된다. 처치 시 누구에게 얼마가 가는지를 C++ 보상 매니저가 결정하기 시작하면 무너진다. 핵심 결합 채널은 이미 존재한다 — [I-0036](I-0036.md) 의 `LastAttacker` 가 *처치자 신원* 을 알려준다. 죽음 분기에서 `LastAttacker` 를 읽어 부를 귀속시키면 된다.

## 현재 구현 상태

- **재화/통화 없음.** `Gold`/`Wealth`/`Currency` 류 프로퍼티 미존재 ([HktCoreProperties.h](../../HktGameplay/Source/HktCore/Public/HktCoreProperties.h)). "부" 는 아직 개념뿐.
- **현상금 없음.** `BountyValue` 류 프로퍼티·계약 데이터 모델·UI 전무.
- **처치자 신원 채널은 존재.** `LastAttacker`(Cold) — 공격 Story 가 `ApplyDamage` 직전 기록, Brain 폴링용 ([I-0036](I-0036.md)). 보상 귀속의 단일 출처로 재사용 가능.
- **죽음·전리품 경로는 존재.** `SnippetCheckDeath` + `Story_NPCLifecycle` die 분기의 loot drop ([I-0035](I-0035.md) · [Design-I0035-ItemDropPickup.md](../Design-I0035-ItemDropPickup.md)). 부 보상을 *끼워 넣을* 자연스러운 지점.
- **아이템 소유/스택 모델은 성숙.** [I-0028](I-0028.md) · [I-0040](I-0040.md) · [I-0041](I-0041.md). 통화를 *아이템 스택* 으로 환원할지 *전용 프로퍼티* 로 둘지의 선택지를 제공.

## 구현 (제안)

### 부 (통화) 의 substrate

- **결정: 전용 프로퍼티 `Wealth`(Cold)** — 결정론·합산이 단순. 통화를 아이템 엔티티로 두면(I-0040/41) 가방 슬롯·스폰 비용이 붙어 러너의 짧은 루프에 과하다. 대량 드롭 표현은 [I-0035](I-0035.md) 의 호(arc) 픽업 연출만 시각적으로 빌리고 값은 `Wealth` 에 직접 가산.
- 신규 프로퍼티: `Wealth`(Cold) — 보유 부. (선택) `BountyValue`(Cold) — 그 엔티티 처치 시 지급될 현상금.

### 처치 보상

- **죽음 분기 훅** — `Story_NPCLifecycle` (및 추후 PvP 시 `Story_PlayerLifecycle`) 의 die 분기에서:
  1. `LastAttacker` 읽기 → 처치자 엔티티.
  2. 보상액 산출 — 기본 드롭값 + `BountyValue`(걸려 있으면).
  3. 처치자 `Wealth += 보상액` (`SnippetResourceGainClamped` 패턴 재사용 가능).
  4. 픽업 연출 — [I-0035](I-0035.md) 의 arc VFX 만 차용 (값은 이미 가산됨).
- **결정론** — 보상 random(변이) 이 있으면 시뮬 시드 경유 (`RandomInt` op). C++ random 금지.

### 현상금 계약

- **데이터** — 계약 = (대상 식별, 건 금액, 의뢰자). 1차는 *엔티티에 부착* 모델: 대상 엔티티의 `BountyValue` 에 가산 + 의뢰자 기록(별도 채널). 지역/조건부 현상금은 추후.
- **걸기** `Story.Event.Bounty.Place` — 의뢰자 `Wealth -= 금액` (precondition: 잔액 검증), 대상 `BountyValue += 금액`. 
- **회수** — 위 *처치 보상* 경로가 `BountyValue` 를 자동 포함하므로 별도 회수 op 불필요. 처치 = 회수.
- **표시** — 현상금 걸린 대상의 머리 위 마커/금액 (Presentation, 읽기 전용 — [I-0007](I-0007.md) 계약 준수).

## 격차 / TODO

- **통화 vs 아이템 최종 결정** — 본 의도는 전용 `Wealth` 프로퍼티를 권장하나, [I-0042](I-0042.md) 아이템 조합 경제와의 환율/연동 시 재검토.
- **의뢰자 채널** — `BountyValue` 만으로는 *누가 걸었는가* 가 소실. 의뢰자 귀속(보상 분배·취소 환불) 이 필요하면 별도 프로퍼티/스토리지 모델 필요.
- **PvP 현상금** — 타플레이어 대상 계약은 서버 권위·악용 방지(자작극 farming) 설계 선행. 1차는 NPC 대상 한정 권장.
- **부의 사용처** — 축적된 `Wealth` 의 소비 루프(상점·강화·현상금 걸기) 가 없으면 도파민이 닫히지 않는다. 최소 1개 소비처 동반 필요.
- **영속성** — `Wealth`/`BountyValue` 의 서버 저장/세션 유지 범위.
- **spec** — 죽음 분기 보상 귀속 invariant 를 `*.spec.json` 으로 검증 (`LastAttacker → Wealth` 가산, BountyValue 합산).
