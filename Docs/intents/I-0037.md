## Intent

Entity 는 습득한 아이템을 보관하는 *가방* 을 가진다. 가방은 그 Entity 의 *몸에 붙은* 보관 공간이며, Entity 자신이 자기 아이템과 상호작용할 수 있게 만든다 — 장착(Activate), 보관(Deactivate / BagStore), 다시 꺼내 장착(BagRestore), 버리기(Drop).

가방은 Entity 의 *속성* 이지 별도의 인벤토리 테이블이 아니다. 용량은 엔티티별 `BagCapacity` Cold Property 로 가변이며 — 플레이어 캐릭터 기본 8, 이동형 창고·NPC 등은 다른 값. 이로써 *NPC 가 아이템을 떨어뜨린다 / 창고가 보관한다* 같은 메커닉이 같은 시스템 위에서 표현된다.

핵심 분리:
- **장착 상태 (Active)** — 아이템이 *엔티티* 로 살아 있다 (`EquipIndex 0~8`, `ItemState=2`). 스탯/Stance 가 캐릭터에 합산되고, 무기 메쉬가 소켓에 부착된다.
- **보관 상태 (InBag)** — 아이템이 *엔티티가 아닌 경량 스냅샷* (`FHktBagItem`) 으로 보관된다. VM 시뮬레이션 부담 0, 가방 슬롯만 점유. BagRestore 시 다시 엔티티로 부활.

- 서버 처리: `OnReceived_BagRequest` (Action=StoreFromSlot → Deactivate, RestoreToSlot → 엔티티 부활 + Activate) — [HktRule/HktServerRule.cpp](../../HktGameplay/Source/HktRule/Private/HktServerRule.cpp)

### 슬롯·상태 요약 (단일 진실원: [Design-Entity-Item-System.md](../Design-Entity-Item-System.md) §3, §4)

```
   Pickup       BagStore (Deactivate)
[Ground] ─────► [Active(N)] ─────────► [InBag(BagSlot=K)]
  State=0       State=2,Equip=N         FHktBagItem 스냅샷
                  ◄────────────────────
                  BagRestore (Activate, EquipIndex 지정)
                  ◄──── Drop
                        State=0, Owner 해제
```

### 미구현 / TODO

- **BagCapacity 검증 단일화** — Pickup precondition 의 빈 EquipSlot 검증과 Bag 의 슬롯 용량 검증이 분리되어 있다. Entity 가방의 *총 보관 가능량* (Active + InBag) 을 한 상수로 묶는 규칙 정의.
- **NPC 가방** — NPC Entity 의 BagCapacity 활용 사례 미구현. NPC 가 죽으면 가방의 InBag 스냅샷을 Ground 로 떨어뜨리는 lifecycle 분기가 필요 ([I-0035](I-0035.md) 의 drop snippet 확장).
- **이동형 창고 Entity** — `BagCapacity` 가 다른 비-캐릭터 엔티티로 확장 (창고·말·동물 등). 소유권 모델은 동일.
- **Entity ↔ Entity 가방 이동** — 현재 자기 가방 안에서의 Active/InBag 토글만 가능. 다른 Entity 가방으로의 직접 이동(예: 캐릭터 → 동행 NPC) 은 [I-0038](I-0038.md) 의 Inventory 경유 또는 신규 Story 필요.
