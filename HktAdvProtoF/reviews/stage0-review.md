# 단계 0 리뷰 — M0 결정적 세계 (V0~V4 · O0~O2)

> 2026-08-03 (목적 → 구현 → 사용처 드릴다운으로 재작성). 인덱스·전체 지도는 [README.md](README.md).
> 원 리뷰 시점 재현은 테스트 887개 전원 통과 · verify 전부 exit 0 이었고, 이 재작성 시점 재실행은
> `npm test` 1140개 전원 통과(84+867+99+90) · `npm run verify` exit 0 이다. 계약 등록·자리 수 등
> 아래 수치는 재실행에서 다시 뽑았다. 코드 경로는 `app/packages/` 기준이다.

**단계의 목표(원문 §18):** 계약 등록 가능 · 결정적 실행 가능 · 시나리오 자동 실행 가능 · 브라우저 Lab 확인 가능.
**판정 한 줄:** 내용은 건전하다 — 그러나 **판정 체계 자체에 결함 2건**이 있었고, 그중 하나는 이 단계의
"닫힘" 선언을 형식상 무효로 만든다 (§3 — 두 건 모두 이후 V4-e·V0-c 로 상환됨, STATE.md 열린 이슈 표).

**왜 게임보다 먼저인가:** 게임 코드를 한 줄도 짜기 전에 **"완료라고 거짓말할 수 없는 작업장"** 을
먼저 지었다. 이 프로젝트는 AI 에이전트가 구현을 진행하므로 "다 됐습니다" 라는 선언을 사람이 일일이
검산할 수 없다 — 선언 대신 증거가 말하게 만드는 것이 단계 0 의 전부다.

## 1. 무엇을 만들었나 — 목적에서 구현으로 타고 내려가기

### V1 — 목적: 같은 시드는 **항상 같은 세계** — 결정성을 기반 시설로

**무엇을 했나:**
- 난수를 시드에서만 뽑는다 — `createRandom(seed)` + `split(state, label)` (`core/src/v1/random.ts:33·115`).
  갈래마다 라벨로 쪼갠 독립 스트림이라, 한 시스템의 난수 소비가 다른 시스템을 흔들지 않는다.
- ID 를 시각·카운터가 아니라 **내용에서** 만든다 — `deterministicId(kind, ...parts)` (`v1/id.ts:16`).
  같은 것을 두 번 만들면 같은 ID 다.
- 순회 순서까지 못박는다 — `stableSort` (`v1/stable-sort.ts:8`).
- 어떤 상태든 해시 하나로 접는다 — `canonicalize` + `stateHash` (`v1/hash.ts:109·151`).
  키 순서·중복 표기가 달라도 같은 상태면 같은 해시.

**어떻게 쓰이나:** 이후 모든 계층이 이 위에 선다 — 단계 1 의 그래프 해시·D4 압력 재현성, 증거의
리플레이 해시가 전부 `stateHash` 다. 검증 방식 자체가 "같은 입력 → 같은 해시" 대조로 가능해진
것이 이 모듈의 산출이다. 게임에서는: 리플레이, 서버-클라이언트 상태 검증, "같은 시드를 넣으면
같은 세계" 공유가 서게 될 자리. 재실행 확인: 같은 시드 100회 → 상태 해시 1개, 시드 한 글자를
바꾸면 사건 #0 부터 갈라진다.

### V2 — 목적: 모든 모듈은 **장면 3종(정상·실패·경계)** 으로 스스로를 재생한다

**무엇을 했나:**
- 장면을 자료구조로 — `Scenario{arrange, act, assert}` + `defineScenario` (`scenarios/src/scenario.ts:48`).
- 실행기 — `runScenarios` 와 모듈당 정상·실패·경계 3종이 다 있는지 세는 `coverageOf`
  (`scenarios/src/runner.ts:178·202`).
- 실패를 경로로 짚는다 — `divergences(expected, actual)` (`scenarios/src/diff.ts:63`) 가 기대와
  실제가 처음 갈라진 상태 경로(예: `$.stock.b`)를 출력한다.

**어떻게 쓰이나:** 이후 모든 모듈(O·S·D·P)의 "검증 3종" 이 이 실행기에 실렸다 — 이 재실행의
계층 스위트 전부가 `defineScenario` 로 쓰여 있다. 게임에서는: 회귀가 "테스트 몇 개 깨짐" 이 아니라
"어느 값이 어디서부터 달라졌나" 로 보고되는 개발 표면.

### V0 — 목적: 모듈은 **계약으로만 존재한다** — 목적 없는 코드·순환 의존 금지

**무엇을 했나:**
- 계약 객체 — `ModuleContract` (`contracts/src/contract.ts:31`): 목적·입출력·의존·검증법·상태 원소.
- 레지스트리 — `buildRegistry(sources, { evidence, sourceHashes })` (`contracts/src/registry.ts:156`):
  위상 정렬(순환 의존은 등록 거부), 완료 주장과 증거의 교차 대조(`evidence-unsupported` — 강등·낡음·
  없음이면 기각), 그리고 "의존이 전부 VERIFIED 인 미완료 모듈" 을 계산하는 **착수 가능 목록**.

**어떻게 쓰이나:** 개발 파이프라인의 척추다 — 재실행에서 실제 계약 22개(21 VERIFIED + P4 PLANNED)가
위상 순서 `V1→V2→V0→V4→V3→O1→O2→O0→S0…→P3` 로 등록되고, 착수 가능 목록이 다음 할 일로 P4 를
계산한다. 게임 자체보다 "게임을 만드는 과정" 이 소비자다 — 다음 세션이 무엇을 해야 하는지를
사람 기억이 아니라 레지스트리가 답한다.

### V4 — 목적: "완료" 는 사람이 아니라 **산출물이 판정한다**

**무엇을 했나:**
- 증거 객체와 유일한 판정자 — `Evidence` + `buildEvidence(input)` (`contracts/src/evidence.ts:62`):
  단위 테스트·시나리오 3종·리플레이 해시·Lab 확인이 **전부** 통과해야 `VERIFIED` 가 찍히고,
  하나라도 빠지면 그 아래 등급이다. status 를 손으로 적는 경로 자체가 없다.
- 자동 낡음 — `isFresh(evidence, currentSourceHash)` (`evidence.ts:162`): 증거가 소스 해시를 품고
  있어, 소스를 고치면 예전 증거는 저절로 낡아 완료가 풀린다.
- (#662 상환 후) 수집기가 검증 전량 → 일괄 기록 두 마당으로 나뉘어(`collect.ts`), 기록 중의 증거가
  다음 검증을 오염시키는 순서 버그가 구조적으로 막혔다.

**어떻게 쓰이나:** 매 모듈의 완료 판정이 이 함수 하나를 지난다 — 단계 1 의 S0~D4 아홉 모듈
전부의 `evidence/*.json` 이 이것으로 생성됐다. AI 가 구현하는 프로젝트에서 "다 됐습니다" 를
검산 불가능한 선언이 아니라 git 에 커밋되는 파일로 만든 것이 이 모듈이다.

### V3 — 목적: 코드를 안 읽는 사람도 모듈 작동을 **눈으로 확인한다**

**무엇을 했나:**
- 모듈당 브라우저 페이지 1개 + **화면 7요소** 규격(입력·처리·후보·선택·전후 비교·실패 이유·인과) —
  `lab/src/pages/` 에 모듈별 페이지, `lab/verify/v3.ts` 가 7요소 충족과 렌더 결정성(같은 데이터
  100번 → 같은 그림)을 검사한다.
- 공용 렌더러의 자리를 열었다 — 이후 D1(그래프 뷰)·D3(diff 뷰)·D4(게이지·추이)가 채웠고,
  단계 1 리뷰의 모든 "화면" 서술이 이 위에 서 있다.

**어떻게 쓰이나:** 사람 눈검증의 표면이자 이 리뷰 자체의 도구다. 남은 부채도 정직하게: 브라우저
확인은 아직 수동이고(증거의 `labScenarios: manual`), 자동화는 V3-b(Playwright 스모크) 카드로
STATE.md 부채 표에 걸려 있다.

### O1 — 목적: 세계의 모든 것을 **12타입으로만** 말한다

**무엇을 했나:**
- 존재론 12타입 — `ONTOLOGY_KINDS` (`core/src/o1/kinds.ts:12`): Subject(주체) · Entity(사물) ·
  State(상태) · Rule(규칙) · Phenomenon(현상) · Claim(주장) · Commitment(약속) · Affordance(어포던스) ·
  Event(사건) · Dependency(의존) · Possibility(가능성) · WorldRequirement(세계요구).
- 주체 5종 이름표 — `SUBJECT_KINDS`(사람·생물·조직·국가·신, `o1/being.ts:22`)와 상태 9영역
  이름표 `STATE_DOMAINS` (`being.ts:40`) 를 여기서 미리 고정했다(내용은 S0·O2 가 채운다).
- 원문 개념 40종 ↔ 12타입 전수 대조(`o1/catalog.ts`) + 목록 안 누락 검사(`o1/coverage.ts`).
- **실제와 믿음을 처음부터 딴 타입으로** — 같은 약초가 실제(마비독)는 `State`, 믿음(치유 효과)은
  `Claim` 으로 나란히 선다.

**어떻게 쓰이나:** 모든 후속 모듈의 타입 어휘다 — S0 의 주체도, D1 의 의존도, P3 의 가능성도
전부 이 12타입의 인스턴스로 서고, 관문("가능성이 아니라 바람이다")도 O1 검사가 낸다.
State/Claim 분리는 R4(거짓 믿음)가 서게 될 기반. 게임에서는: "이 세계에 존재할 수 있는 것" 의
문법 — AI 생성(A 계층)이 이 문법 밖의 것을 만들면 타입에서 걸린다.

### O2 — 목적: 상태는 **9영역 트리의 정해진 자리에만** 적힌다

**무엇을 했나:**
- 세계 스키마 — `STATE_SCHEMA` (`core/src/o2/schema.ts:531`): 9영역(물리·생물·생태·관계·제도·경제·
  정보·의념·초월) 아래 자리 57개, 자리마다 타입·범위·단위·주인이 `FieldSpec` 으로 못박힌다.
- 조립 관문 — `assembleWorld` / `readSlot` (`o2/world.ts:67·140`): 스키마에 없는 자리·범위 밖 값은
  세계에 들어가지 못하고, 같은 자리의 두 값은 거부된다.
- 원문 §12.1 저장소 9종·필드 39개와의 전수 대조 장부(`MASTERPLAN_DOMAINS`, `ORIGINAL_FIELDS` —
  같음·개명·흡수로 남김없이 해소).

**어떻게 쓰이나:** D4 의 세계 스냅샷(`snapshotOf`)이 이 조립 관문을 그대로 통과해 세계의 첫 값을
세웠고, 단계 1 의 "잴 수 없는 읽기 거부" 가 전부 이 스키마 검사다. 게임에서는: 세이브 파일·서버
상태의 스키마 — 치트 값·버그 값이 저장 시점에 걸리는 자리.

### O0 — 목적: 세계관은 문장이 아니라 **관문**이다 — 공리 8개

**무엇을 했나:**
- 공리 8개 — `AXIOM_CLAUSES` (`core/src/o0/axiom.ts:23`): 생명은 의념을 낳는다(psychic-life) ·
  강한 효과엔 검증 가능한 비용(verifiable-cost) · 능력은 흔적을 남긴다(observable-trace) ·
  집단의 반복은 신을 만든다(emergent-divinity) · 관측 못한 것은 정밀 조작 불가(observed-manipulation) ·
  안정된 것일수록 바꾸기 어렵다(stability-resistance) · 같은 자리에 양립 불가한 두 값 금지
  (state-exclusion) · 원인 없는 지속 없음(caused-persistence).
- 원문 16문장 → 8공리 환원 장부 — `AXIOM_RECONCILIATION` (`axiom.ts:371`).
- 강제 지점 — `enforcementReport` (`o0/enforcement.ts:289`): 공리가 실제로 정의를 거부하는 곳
  10곳을 프로브로 확인 (2곳은 R3·W2 구현 시 갚을 부채로 명시).
- 다산성 검사 — `derivationReport` (`o0/derivation.ts:63`, O0-d): **같은 공리에서 서로 다른 종·능력·
  신이 도출되는가**를 재고, 세계를 넓히지 못하는 공리는 불모로 찍는다.

**어떻게 쓰이나:** 단계 1 의 종·문화·개체 조립(S1~S3)이 능력을 붙일 때마다 이 관문을 지났다 —
"공리를 어긴 능력" 은 조립 거부가 실제로 난다. 북극성 기준의 위치도 여기서 정직하게: 비용·흔적
공리는 능력 체계(①)의 **부품**이고, 다산성 검사는 방대한 세계관(②)의 **씨앗**이다 — 핵심(넨급
문법 G5·G6, 병합 W1)은 아직 멀리 있다.

### 함께 돌아가면 — 작업장이 스스로를 검증하는 한 바퀴 (재실행 실측)

단계 0 의 대표 장면은 게임 장면이 아니라 **검증 한 바퀴**다. 이 재실행에서:
`npm test` 가 워크스페이스 넷에서 1140개를 돌리고(전원 통과), `npm run verify` 가 — V1 같은 시드
100회 → 해시 1개 · V2 장면 스위트와 고의 결함의 최초 분기 경로 · V0 실제 계약 22개 위상 등록과
착수 가능 목록(P4) 계산 · V4 증거 교차검사(커밋된 증거 21개 전부 VERIFIED, 강등·낡음·없음이면
기각) — 를 차례로 확인하고 exit 0 으로 끝난다. 단계 1 이 "세계가 값을 갖는" 것을 보였다면, 단계 0 은 **그 값을 믿을 수 있는 이유**
전부다.

## 2. MasterPlan 대비

- MasterPlan §12.1 의 상태 저장소 9종 ↔ O2 의 9영역이 정확히 1:1 이다. 원문 이름 9개가 같음·개명·흡수로 남김없이 해소된 대조표가 있다.
- MasterPlan §13.1 의 핵심 통찰 — **실제 사실과 주체가 믿는 사실의 분리** — 가 O1 에서 이미 산다.
  같은 약초를 두고 실제(마비독)와 믿음(치유 효과)이 각각 `State` 와 `Claim` 으로 나란히 서는 장면이 테스트로 고정돼 있다.
- MasterPlan §3.2 의 규칙 6계층(절대 불변 → 개인 능력)은 아직 O0 의 최상층(절대 불변)만 구현됐다.
  지역 규칙·개인 능력 규칙은 W2·G5·G6 의 몫으로 남아 있고, O0 관문 10곳 중 2곳이 그쪽에 부채로 걸려 있다 — 정직하게 기록돼 있다.

### 평가

전체 목표와의 관계를 직관적으로 말하면: **단계 0 은 게임이 아니라 "게임이 거짓말을 못 하게 하는 헌법"** 이다.
이후 어떤 계층(AI 생성 포함)이 무엇을 만들어도 이 관문을 지나야 하므로, 투자 가치가 있는 기반이다.

주의할 것: O0 이 실체화한 "비용·흔적" 공리는 **헌터헌터급의 핵심(북극성 ①)이 아니라 그 능력 체계의 부품 하나**다.
핵심 — 넨처럼 능력이 캐릭터를 표현하는 깊은 문법(MasterPlan §10)과 방대하고 다채로운 세계관 — 은
각각 G 계층(G5·G6)과 W·C·A 계층의 몫으로 아직 멀리 있다. 지금 단계에서 그 방향으로
심긴 씨앗은 하나뿐이다: O0-d 도출 대조 — **같은 공리에서 서로 다른 능력·종·신이 도출되는지**를 검사해,
공리가 세계를 다채롭게 넓히지 못하면 불모로 찍는 장치다.

## 3. 이 단계에서 발견한 결함 (이슈 — 발견 당시 기록, 두 건 모두 이후 상환됨)

### [#662](https://github.com/dkwkekzz/HktFramework/issues/662) — V3 증거가 강등된 채 3커밋 연속 커밋됨 (중요)

커밋된 `evidence/V3.json` 은 D2 완료 커밋(`d9fc105`)부터 줄곧 `unitTests: failed / status: IMPLEMENTED` 인데,
STATE.md·계약·커밋 메시지는 전부 VERIFIED 와 "단계 닫힘" 을 주장한다. 프로젝트 자신의 규칙("완료 판정은 증거 파일로만")으로 재면
**단계 0·1 게이트는 형식상 닫히지 않은 상태로 커밋돼 있다.**

원인은 verify 파이프라인의 순서 버그다: 증거 생성기가 새 모듈의 증거 JSON 을 쓰는 도중 lab 의 스냅샷 신선도 테스트가
낡음을 감지해 실패하고, 그 실패가 V3 증거에 박제된다. 즉 **모듈을 하나 완료하는 바로 그 실행마다 V3 이 강등**된다.
이 리뷰 환경에서 조용히 재실행하면 81/81 통과로 자가 치유됨을 확인했다 — 내용상 V3 은 건강하고, 판정 체계가 오작동한 것이다.
당시 verify 가 exit 1 로 실패 신호를 냈는데도 커밋된 점이 더 본질적인 문제다. **(상환: V4-e —
수집기를 검증 전량 → 일괄 기록 두 마당으로 분리, 위반 시 exit 1)**
