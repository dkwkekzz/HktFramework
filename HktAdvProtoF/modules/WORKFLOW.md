# WORKFLOW.md — 작업 방식 설계

> [design/Design-ModulePlan.md](../design/Design-ModulePlan.md)(원문)의 모듈 분할을 **그대로** 따르며,
> 그 모듈들을 구현해 나가는 **작업 방식**을 정의한다.
> 모듈별 목적·입력·출력·상태 원소·시각화 정의는 [MODULES.md](MODULES.md)에 있다.
> 이후 모든 작업은 이 문서의 절차를 따른다.

## 0. 네 가지 불변 원칙

모든 작업은 아래 네 원칙을 위반할 수 없다. 위반이 발견되면 그 작업은 완료로 인정하지 않는다.

| # | 원칙 | 강제 방법 |
|---|---|---|
| ① | **목적 우선** — 모든 작업은 도달하려는 목적을 한 문장으로 정의한다. 복잡해지면 목적을 구체적 하위 작업으로 분할한다. | 작업 카드(§2)의 `목적` 필드 + 분할 규칙(§3) |
| ② | **계약 우선** — 모듈 간 입력과 출력을 스키마로 분명하게 정의한다. | [MODULES.md](MODULES.md) 레지스트리 + 모듈별 `MODULE.yaml`(§4) |
| ③ | **눈 검증** — 모든 작업 결과는 직관적으로 확인 가능해야 한다. 모듈이 정의하는 모든 개념은 **최소 세계 상태 원소**(직렬화 가능한 데이터)로 환원되고, 모든 상태 원소는 Lab에서 시각화된다. | 상태 원소 규칙(§6) + Lab 페이지 의무(§5-5단계) |
| ④ | **스택 고정** — TypeScript 단일 언어. 서버는 Node.js 권위 시뮬레이션, 클라이언트는 Three.js 3D 뷰어. | 코드 배치 규칙(§1) |

## 1. 코드 구조 — 스택 배치

```
HktAdvProtoF/
  design/               # 원문 (수정 금지, 인용만)
  modules/              # 파생 작업 설계 (이 문서, MODULES.md, MODULE-TEMPLATE.yaml)
  app/                  # 구현 루트 — npm workspaces 모노레포, 전부 TypeScript
    package.json
    packages/
      core/             # 순수 결정적 시뮬레이션 — V1 + O·S·D·P·Q·W·R·E·G·C 계층
      contracts/        # V0 모듈 계약 레지스트리 + V4 완료 증거(evidence/*.json)
      scenarios/        # V2 시나리오 (arrange / act / assert)
      lab/              # V3 브라우저 검증 Lab (Vite) — core 를 직접 import
      server/           # Node.js 권위 서버 — R 계층 호스트, 이후 N 계층
      client/           # Three.js 3D 뷰어 — X 계층
      studio/           # A 계층 (AI 제작 자동화) — 최후반 단계에서 생성
```

배치 규칙:

- **core 는 순수하다.** I/O·네트워크·DOM·`Date.now()`·`Math.random()` 금지.
  난수는 V1 Seeded Random, 시간은 V1 Tick Clock 만 사용한다. 모든 함수는
  `(상태, 입력) → (새 상태, 사건[])` 형태를 지향한다.
- **server / client / lab 은 core 의 소비자다.** core 의 공개 API 로만 접근하고,
  시뮬레이션 로직을 자체 구현하지 않는다. 서버와 Lab 이 같은 core 를 실행하므로
  결정성 검증(같은 시드 → 같은 해시)이 두 환경에서 동일하게 성립해야 한다.
- **권위는 서버에만 있다.** client 는 의도(ActionIntent)를 제출하고 확정 상태를 수신할 뿐,
  세계 상태를 직접 변경하지 않는다 (N0 원칙의 선행 적용).

## 2. 작업 단위 — 작업 카드

작업의 단위는 **모듈 1개**(또는 그 하위 작업 1개)다. MODULES.md 에 없는 작업은 존재하지 않는다.
모든 작업은 착수 전에 아래 **작업 카드**를 STATE.md TODO 항목으로 작성한다.

```md
### [D4] 의존 충족도 평가
- 목적: 현재 세계 상태에서 각 의존 노드의 압력을 계산해 5단계 충족 상태를 판정한다. (한 문장)
- 입력: DependencyGraph, WorldState 스냅샷
- 출력: PressureReport (노드별 Pressure 수치 + 충족/불안정/결핍/위기/붕괴)
- 검증 장면: 인간 1 + 음식 재고 1 → 재고를 3틱마다 감소시키면 압력이 단조 증가한다.
- 상태 원소: DependencyNode.pressure, DependencyNode.fulfillment
- 시각화: Lab 그래프 렌더러 — 노드 색 = 충족 5단계, 게이지 = Pressure
```

필드 6개(목적·입력·출력·검증 장면·상태 원소·시각화)는 생략 불가.
입력·출력은 MODULES.md 의 해당 모듈 행과 일치해야 한다 — 다르면 먼저 MODULES.md 를 갱신하는
별도 작업을 만든다.

## 3. 분할 규칙 — 복잡하면 쪼갠다

작업 카드를 쓰다가 아래 중 하나라도 걸리면, 그 작업은 **하위 작업으로 분할**한다.

| 신호 | 판정 |
|---|---|
| 목적이 한 문장으로 안 써진다 ("~하고 ~한다"가 된다) | 접속사 앞뒤로 분할 |
| 검증 장면이 2개 이상 필요하다 | 장면 1개당 하위 작업 1개 |
| 새로 정의하는 상태 원소가 3종을 초과한다 | 원소 묶음별로 분할 |
| 구현 예상이 커밋 1개(≈수 시간)를 넘는다 | 파이프라인 단계 경계로 분할 |

하위 작업 이름은 `모듈ID-소문자`로 붙인다 (예: `D4-a 압력 공식`, `D4-b 5단계 판정`, `D4-c Lab 게이지`).
하위 작업도 각각 완전한 작업 카드를 가지며, 부모 모듈은 모든 하위 작업이 닫혀야 완료된다.
분할은 재귀적이다 — 하위 작업이 또 복잡하면 다시 쪼갠다.

## 4. 모듈 계약 — MODULE.yaml

원문 V0(모듈 계약 레지스트리)를 작업 방식의 뼈대로 선행 적용한다.
모듈 구현에 착수할 때 `app/packages/contracts/<모듈ID>.yaml` 을 먼저 작성한다.
서식은 [MODULE-TEMPLATE.yaml](MODULE-TEMPLATE.yaml).

```yaml
id: D4
name: dependency-evaluator
purpose: 현재 세계 상태에서 각 의존 노드의 압력을 계산해 5단계 충족 상태를 판정한다.
inputs:  [DependencyGraph, WorldStateSnapshot]
outputs: [PressureReport]
writes:  [DependencyNode.pressure, DependencyNode.fulfillment]   # 변경 가능한 상태 범위
depends: [V1, V2, D1, D2]
scenarios: [d4-hunger-rise, d4-satiation-fall, d4-boundary-zero]
lab: /lab/d4
status: PLANNED | IN_PROGRESS | IMPLEMENTED | VERIFIED
```

V0 구현 완료 후에는 레지스트리가 이 파일들을 검사한다:
목적 없는 모듈 등록 불가 · 입출력 없는 처리 모듈 등록 불가 · 순환 의존 등록 불가 ·
시나리오 없는 모듈 완료 불가 (원문 V0 검증 조항 그대로).

## 5. 한 작업의 사이클 — 8단계

모든 작업은 아래 사이클을 돈다. **커밋 1개 = 작업 1개.**
(실행 방아쇠: `/advproto-step` 스킬 — 이 규정을 효율적 순서로 실행한다. 규정 원본은 이 문서다.)

```
1. 읽기    STATE.md → MODULES.md 해당 행 → 선행 모듈 status 확인
           게이트: depends 에 VERIFIED 아닌 모듈이 있으면 착수 금지 (원문 §3 규칙)
2. 카드    작업 카드 작성 → 분할 규칙(§3) 통과 확인 → STATE.md TODO 에 기록
3. 계약    MODULE.yaml 작성/갱신 — 입출력 스키마를 core 타입으로 먼저 선언
4. 구현    core 우선 구현 → server/client/lab 은 소비만
5. 검증    시나리오 3종 실행 — 정상 1 + 실패 1 + 경계 1
           결정성 검사 — 같은 시드 반복 실행, 사건 순서·상태 해시 동일
6. 눈검증  Lab 페이지에서 확인 — 입력 / 처리 과정 / 후보 / 선택 결과 / 상태 전후 / 실패 이유
           (원문 V3 화면 7요소) — 확인한 장면을 한 줄로 STATE.md 에 기록
7. 증거    evidence/<모듈ID>.json 생성 (원문 V4 형식) → status: VERIFIED
8. 닫기    STATE.md 갱신(TODO 제거, 현황 반영) → 커밋
```

- 5·6·7 을 건너뛴 작업은 status 를 올릴 수 없다 — "완료 선언"은 증거 파일로만 한다 (V4 원칙).
- V0~V4 자체가 구현되기 전(단계 0 진행 중)에는 5~7 을 수동으로 수행하고,
  V0~V4 가 완성되는 즉시 소급 등록한다.
- **`npm run verify` 의 exit 0 이 8단계(커밋)의 전제 조건이다.** 대시보드에 VERIFIED 아닌 모듈이
  하나라도 있으면 원인을 해소하기 전에 커밋하지 않는다 — 남의 모듈의 강등이라도 마찬가지다
  (V3 강등 사건 #662: verify 가 exit 1 을 냈는데도 커밋되어 IMPLEMENTED 증거가 main 에 남았다).
  커밋 직전 `git status` 로 증거·파생 스냅샷 재생성분이 전부 스테이징됐는지 확인한다.

## 5.1 검증 3종 규격

| 종류 | 규격 | 출처 |
|---|---|---|
| 시나리오 | `arrange(): InitialState` → `act(state): ScenarioResult` → `assert(result): Assertion[]`. 실패 시 초기 상태·입력·기대·실제·**최초로 달라진 상태 경로** 출력 | 원문 V2 |
| 결정성 | 같은 시드로 100회 실행 → 사건 순서·최종 상태 해시 동일 | 원문 V1 |
| Lab | 모듈당 페이지 1개, 화면 7요소(입력·처리·후보·선택·상태 전후·실패 이유·인과) | 원문 V3 |

## 6. 상태 원소 규칙 — 모든 개념은 보이는 데이터다

원칙 ③의 구체 규정:

1. 모듈이 정의하는 모든 종류(개념)는 **최소 세계 상태 원소**로 설명될 수 있어야 한다.
   상태 원소 = JSON 직렬화 가능한 데이터 + O1 존재론 12타입 중 하나로 분류됨.
   함수·클로저·암묵 상태로만 존재하는 개념은 금지.
2. 모든 상태 원소는 **공용 렌더러 5종** 중 하나 이상으로 Lab 에서 시각화된다.
   새 렌더러가 필요하면 그것도 작업 카드로 만든다.

### 공용 렌더러 5종 (lab 패키지)

| 렌더러 | 그리는 것 | 소비 계층 |
|---|---|---|
| **그래프 뷰** | 노드·간선 + 색/굵기 속성 | D 의존, P 가능성, Q 요구, W1 병합, X0 의미 공간, E4 연쇄 |
| **게이지·수치판** | 압력, 충족 5단계, 효율, 안정도 | D4, G2, C4 등 스칼라 상태 |
| **타임라인** | 사건 로그, 역사, 계약 상태 전이 | R1, W5, E2, N3 |
| **상태 diff 뷰** | 임의 상태 트리의 전/후 비교 | 모든 모듈의 "상태 전후" 화면 |
| **3D 씬 (Three.js)** | 지형, 주체 위치, 이동로, 현상 흔적 | W4, X 계층, C1 |

모듈별 원소↔렌더러 배정은 MODULES.md 각 행의 `시각화` 열에 있다.

## 7. 진행 순서 — 단계 게이트

원문 §18 점진적 구현 순서를 그대로 따른다. **앞 단계의 완료 조건이 증거로 확인되기 전에는
다음 단계의 어떤 모듈도 착수하지 않는다.**

| 단계 | 모듈 | 대표 장면 | 수직 목표 |
|---|---|---|---|
| 0 | V0~V4, O0~O2 | 계약 등록·결정 실행·시나리오·Lab 확인 | M0 결정적 세계 |
| 1 | S0~S3, D0~D4 | 배고픈 인간 1 + 음식 1 (아직 행동 없음) | M1 의존하는 주체 |
| 2 | P0~P5 | 배고픈 인간이 음식을 발견한다 | M2 목적을 만드는 주체 |
| 3 | R0~R6, E0~E4 | 두 인간이 음식 하나를 원한다 | M3 충돌하는 주체 |
| 4 | Q0~Q3, W0~W6 | 다섯 주체의 요구 → 국경 협곡 하나 | M4 세계를 요구하는 주체들 |
| 5 | G0~G5 | 반복된 식량 부족 → 전략 전문화 | M5 성장하는 주체 |
| 6 | C0~C4 | 국가가 광맥 개발, 신의 앵커 이동 | M6 복합 세계 |
| 7 | X0~X4 | 협곡을 브라우저에서 걷는다 | M7 플레이 가능한 3D 지역 |
| 8 | N0~N3 | 두 플레이어가 같은 사건에 개입 | M8 영속 MMORPG |
| 9 | A0~A4 | AI 후보 생성 → 자동 검증 통과 | M9 AI 확장 세계 |

단계 내 모듈 순서는 MODULES.md 의 `depends` 위상 순서를 따른다.
D5(의존 충돌 탐지)는 원문 §18 대로 단계 3(다주체 등장) 시점에 붙인다.

**단계가 닫히면 STATE.md TODO 에 "단계 N 리뷰 대기" 항목을 남긴다.** 리뷰(§10) 자체는
**사용자가 요청할 때만** 진행한다 — 다음 단계 착수를 리뷰가 막지 않는다. 단, 이미 진행된
리뷰가 이슈업한 게이트 조건(STATE.md 열린 이슈 표의 "착수 전" 항목)은 여전히 착수 전에 닫는다.

## 8. STATE.md 운용

- **착수 전**: STATE.md 를 읽는다. 작업 카드를 TODO 에 쓴다.
- **닫을 때**: 구현 현황 표에 `모듈ID — 상태 — Lab 확인 장면 한 줄` 을 남기고 TODO 에서 제거한다.
- 완료 상세가 쌓이면 `progress/stage-N.md` 로 분리하고 STATE.md 에는 핵심만 남긴다 (CLAUDE.md 규칙).

## 9. 첫 진입점

단계 0 의 작업 카드 초안은 STATE.md TODO 에 있다. 순서는:

```
V1 결정적 실행 환경   (모든 것의 전제 — 시드·틱·해시 없이는 검증 자체가 불가)
→ V2 시나리오 실행기   (V1 을 사용해 검증을 자동화)
→ V0 모듈 계약 레지스트리 (contracts/*.yaml 파싱·검사)
→ V4 완료 증거         (V2 결과를 증거 JSON 으로)
→ V3 브라우저 Lab      (Vite 셸 + 공용 렌더러 중 상태 diff 뷰 1종 우선)
→ O1 공통 존재론 → O2 상태 스키마 → O0 세계관 공리
```

원문은 V0 을 먼저 두지만, V0 의 검사기는 V2 로 검증해야 하므로 구현 순서는 V1→V2→V0 이 실용적이다.
이는 계층 의존(V 가 O 보다 먼저)을 깨지 않는다.

## 10. 단계 리뷰 — 닫힌 단계를 사람에게 설명하고 그 주장을 검증한다

**리뷰는 사용자가 요청할 때 진행한다** (`/advproto-review` 스킬 또는 "리뷰 진행" 요청).
단계가 닫히면 STATE.md TODO 에 "단계 N 리뷰 대기" 만 남겨 잊히지 않게 한다 — 자동으로 쓰지 않는다.
닫힌 단계가 여럿 쌓였으면 단계별로 문서를 나눠 쓴다.

**단위는 단계다, 모듈이 아니다.** 모듈의 검증은 계약·증거(`contracts/`)가 이미 담당한다 —
리뷰는 그 위에서 "이 단계가 정말 전체 목표(콘텐츠 루프·CLAUDE.md 북극성)에 다가갔는가" 를 묻는다.
모듈 = 구현·검증의 단위, 단계 = 비전 증명의 단위.

### 10-1. 원칙 셋

| # | 원칙 | 뜻 |
|---|---|---|
| ① | **주장이 아니라 재현** | STATE.md·증거·커밋 메시지의 주장을 옮겨 적지 않는다. 리뷰 환경에서 `npm test`·`npm run verify` 를 직접 돌리고, **커밋된** 증거 파일을 git 으로 열어 주장(계약 status·STATE.md·커밋 메시지)과 대조하며, 핵심 공식·관문은 코드 라인(`core/src/…:줄`)으로 인용한다. 재실행이 커밋 상태와 다르게 나오면 그 차이 자체가 발견이다 |
| ② | **직관 우선** | 비전문가가 읽는다. 모듈마다 "풀어 쓰면 무엇인가" 한 줄 + "확인한 실물" 을 표로. 전체 루프 지도에서 지금 어디인지, 이 단계가 무엇을 새로 할 수 있게 했는지를 서사로 |
| ③ | **과장 금지** | 구현된 부품을 핵심이라 부르지 않는다. 북극성 2개(CLAUDE.md) 기준으로 이 단계의 산출이 **핵심인지 / 기반층인지 / 부품인지 / 씨앗인지** 위치를 명시한다 (예: 비용 공리는 능력 체계의 부품, S3 유래 추적은 특색의 기반층) |

### 10-2. 절차 다섯

```
1. 재현    npm test · npm run verify 실행 — 결과 수치를 리뷰에 인용.
           git 으로 커밋된 증거 vs 주장 대조 (증거 status 가 계약·STATE.md·커밋 메시지와 일치하는가.
           불일치가 있으면 언제부터인지 git log 로 시점을 짚는다)
2. 완료 조건  원문 §18 의 이 단계 완료 조건이 하나하나 값으로 확인되는가
3. MasterPlan 대비  이 단계가 원문(MasterPlan)의 어떤 조항을 실현했고 무엇이 남았는지 표로 —
           "완료 / 씨앗만 / 미착수" 로 정직하게
4. 북극성 대조  이 단계가 북극성 ①(능력 문법)·②(방대한 세계관)에 무엇을 보탰는지 —
           원칙 ③의 위치 구분으로
5. 이슈업   발견 문제는 STATE.md 열린 이슈 표(원본 장부)에 등록하고 GitHub 이슈로 미러한다.
           다음 단계 착수를 막아야 할 문제면 §7 게이트에 "착수 전" 조건으로 명시한다.
           해결되면 표에서 취소선 + 상환 내용으로 남긴다
```

### 10-3. 산출물 둘

1. **`reviews/stageN-review.md`** — 파일명에 날짜를 넣지 않는다 (작성·개정 날짜는 문서 머리에
   적는다). 뼈대는 고정:
   - 머리: 단계 목표(원문 §18) + **판정 한 줄** + 재현 수치(테스트·verify)
   - §1 무엇을 만들었나 — **모듈별 목적→구현→사용처 드릴다운.** 기획 문서의 요약을 되풀이하지
     않는다 — 목적에서 실물로 직관적으로 타고 내려갈 수 있어야 한다. 모듈마다 세 칸:
     - ① **목적** — 이 모듈이 이루려 한 것 한 줄 (예: "기댈 수 있는 모든 대상을 11종으로 분류한다")
     - ② **무엇을 했나** — 그 목적을 위해 정의한 객체·구현한 함수를 **실명과 코드 위치**(`src/…:줄`)로
       들고, 내용은 요약으로 적는다. 확정한 분류·목록은 이름을 실제로 나열한다 (11종이면 11종을 적는다)
     - ③ **어떻게 쓰이나** — 어느 레이어가 이것을 소비하는가(입출력 연결) + 게임 화면에서 무엇으로
       나타나는가. 아직 없는 표면은 "서게 될 자리" 로 정직하게 구분한다
     §1 끝에 모듈들이 **함께 돌아가는 대표 장면**을 재실행 실측값으로 세운다 (표·틱 추이 등)
   - §2 MasterPlan 대비 + 평가(북극성 위치 구분 포함)
   - §3 이 단계에서 발견한 이슈, 또는 다음 단계에 남긴 인계 사항
2. **`reviews/README.md` 갱신** — 단계별 표에 한 줄(단계·수직 목표·대표 장면·리뷰 링크·판정 한 줄)
   추가, 전체 지도·다음 고비·총평을 현행화.

이슈의 원본 장부는 언제나 STATE.md 열린 이슈 표다 (CLAUDE.md 규칙) — 리뷰 문서와 GitHub 이슈는
각각 설명과 알림을 맡을 뿐, 세션 간 전달은 STATE.md 가 한다.
