## A부 — 독립 설계

### A1. 핵심 결정: 공리는 문장이 아니라 **관문 술어**다

원문 O0 의 검증 조건이 설계를 결정한다:

> - 공리를 위반하는 능력이나 생물 정의가 **거부**되는가?
> - 같은 공리로부터 **여러 종류**의 능력과 종이 도출되는가?

"거부"가 가능하려면 공리는 설정집의 문구 배열이어서는 안 되고,
**후보 정의를 받아 위반 여부를 판정하는 함수**여야 한다.
"여러 종류 도출"이 가능하려면 공리는 특정 결과물을 지정하지 않고
**조건만 제약**해야 한다 (충족 방법은 열려 있다).

따라서 공리 하나 = (원문 출처 + 적용 범위 + 검사 술어) 삼중이다.

```ts
/** 공리가 판정할 수 있는 후보 정의 — O1 존재론 타입의 부분집합 */
type CandidateKind = "ability" | "species" | "subject" | "rule" | "phenomenon";

interface Candidate {
  kind: CandidateKind;
  id: string;
  body: unknown; // kind 별 스키마 (능력이면 costs·restrictions·trace 필드 등)
}

interface AxiomViolation {
  axiomId: string;
  path: string;    // 후보 안에서 위반이 확인된 필드 경로 (예: "costs" 가 빈 배열)
  reason: string;  // 사람이 읽는 한 문장
}

interface Axiom {
  id: string;              // 예: "cost", "trace", "will-from-life", "god-from-repetition"
  sourceRef: string;       // 원문 문서·절 (모든 공리는 원문 문장에 유래를 댄다)
  statement: string;       // 원문 문장 그대로
  appliesTo: CandidateKind[];
  check(c: Candidate): AxiomViolation[]; // 빈 배열 = 통과
}
```

원문에서 추출할 공리 후보 (MasterPlan §3.1 universalInvariants + §3.2 1계층 + §10 + ModulePlan O0 예시):

| id | 원문 문장 | 거부하는 것 |
|---|---|---|
| `cost` | 지속적인 변화에는 비용이 필요하다 | 대가·조건 없는 능력 (`costs: []`) |
| `information` | 관측하지 못한 상태를 완전히 이용할 수 없다 | 관측 조건 없는 원격 조작 능력 |
| `resistance` | 안정된 상태일수록 변화시키기 어렵다 | 대상 저항 무시 효과 |
| `consequence` | 큰 변화는 반드시 다른 영역에 흔적을 남긴다 | 흔적 없는 능력 (관찰 불가 효과) |
| `will-from-life` | 생명은 의념(의지장)을 발생시킨다 | 생명 아닌 것이 의지장을 소스로 갖는 정의 |
| `verified-cost` | 강한 의념 효과에는 검증 가능한 비용이 필요하다 | 강도 대비 대가가 명목뿐인 능력 |
| `no-uncaused` | 원인 없는 지속적 결과는 없다 | 유래 없는 세계 요소·상태 |
| `god-from-repetition` | 집단의 반복 행동은 독립된 신적 주체를 만들 수 있다 | 숭배·반복 행동 유래가 없는 신 정의 |

### A2. 하위 작업 분할 (커밋 단위)

**O0-a. 공리 추출과 스키마.**
입력: 원문 문장 목록(`SourceSentence[]` — 문서·절 좌표 포함).
출력: `Axiom[]`.
함수: `extractAxioms(sentences): Axiom[]`.
검사: 모든 공리가 `sourceRef` 를 갖고, 원문에 없는 공리가 없다 (창작 금지).
술어가 없는 문장(순수 배경 설정)은 공리로 승격하지 않고 "비공리" 명단에 남긴다 —
무엇이 탈락했는지도 산출물이다.

**O0-b. 관문 함수.**
입력: `Axiom[]` + `Candidate`.
출력: `Verdict`.

```ts
type Verdict =
  | { admitted: true; checkedBy: string[] }              // 통과한 공리 id 목록
  | { admitted: false; violations: AxiomViolation[] };   // 전 위반 열거 (첫 위반에서 멈추지 않는다)

function checkCandidate(axioms: Axiom[], c: Candidate): Verdict;
```

설계 제약: 관문은 **하나의 함수**이고, 이후 계층의 모든 등록 지점(능력 등록·종 등록·
규칙 등록·세계 요소 등록…)이 이 함수를 다시 쓴다. 공리 검사가 각 모듈에
if 문으로 흩어지면 공리를 추가할 때 세계 전체가 갱신되지 않는다.

**O0-c. 반례 코퍼스.**
입력: 공리마다 최소 1개의 위반 후보 정의 (수제).
출력: 전부 `admitted: false` + 기대한 `axiomId`·`path` 로 거부.
예: 무비용 순간이동(`cost`), 흔적 없는 완전 은폐(`consequence`),
돌맹이가 의지장 발생(`will-from-life`), 숭배 없는 신(`god-from-repetition`).
동시에 **정상 후보**(예: MasterPlan §10.3 기록 수집가 — 조건·제한·대가 완비)가
통과해야 한다. 거부만 검사하면 모든 것을 거부하는 관문도 통과하기 때문이다.

**O0-d. 다산성 증명.**
입력: 같은 `Axiom[]` + 서로 다른 의도 시드 2개 이상.
출력: 같은 공리를 **서로 다른 방식으로** 충족하는 후보 2개 이상 + 유래표.

```ts
interface DerivationRecord {
  candidateId: string;
  satisfies: { axiomId: string; how: string }[]; // 같은 공리를 어떻게 다르게 충족했는가
}
```

검사: 두 후보의 `satisfies[cost].how` 가 서로 달라야 한다 (예: 하나는 기억 상실,
하나는 신체 소모). 공리가 결과물을 하나로 강제하면 그것은 공리가 아니라 콘텐츠다.

### A3. 직관 검증 설계 — 무엇을 넣어 무엇을 보는가

시각화의 중심은 **공리 × 후보 매트릭스**다. 이 표 자체가 검증이다.

```
              무비용    흔적없는   기록      돌의      숭배없는   협곡의
              순간이동  은폐      수집가    의지장    신        신
cost            ✕        ○        ○        ○         ○        ○
consequence     ○        ✕        ○        ○         ○        ○
will-from-life  ○        ○        ○        ✕         ○        ○
god-from-rep    -        -        -        -         ✕        ○
...
판정            거부      거부      통과      거부       거부      통과
```

- 행 = 공리 (클릭하면 원문 문장과 `sourceRef`)
- 열 = 후보 정의 (반례 코퍼스 + 정상 후보 + 다산성 도출물)
- ✕ 칸 클릭 = `path`·`reason` (후보의 어느 필드가 왜 걸렸는가)
- `-` = `appliesTo` 밖 (신 공리는 능력을 검사하지 않는다)

**장면 1 (거부):** 무비용 순간이동을 입력 → `cost` 행에서 ✕, path=`costs`,
reason="대가 없는 지속 효과". 기대와 다르면 관문이 죽은 것이다.

**장면 2 (통과):** 기록 수집가 입력 → 전 행 ○. 모든 것을 거부하는 관문 배제.

**장면 3 (다산성):** 같은 공리 집합에서 도출된 두 후보를 나란히 놓고
`satisfies` 유래표를 diff — 같은 공리, 다른 충족 방식이 **눈으로** 보여야 한다.

**장면 4 (결정성):** 같은 후보 100회 판정 → verdict 해시 동일 (V1 결합).

### A4. 이 모듈이 정하지 않는 것 (경계)

- 공리로부터 종·능력을 **자동 생성**하는 일 — 그것은 S·A 계층. O0 은 판정만 한다.
- 수치 밸런스(강도 공식) — §10.2 는 G5/E3 몫. O0 은 "비용이 존재·검증 가능한가"만 본다.
- 존재론 타입 자체의 정의 — O1 몫. O0 은 O1 타입을 `Candidate.kind` 로 소비한다.

## B부 — 구현 대조

읽은 것: `contracts/O0.yaml` · `core/src/o0/{axiom,definition,derivation,enforcement}.ts` ·
`lab/src/pages/o0.ts` 서두. 구현은 O0-a(공리 확정)·O0-b(정의 검사)·O0-c(강제 프로브)·
O0-d(도출 대조)·O0-e(눈검증) 다섯 하위 작업, 전부 DONE·VERIFIED.

### B1. 일치한 것 — 설계의 뼈대는 같았다

| A부 결정 | 구현 |
|---|---|
| 공리 = 문장이 아니라 **관문 술어** | `validateDefinition` — 조항별 검사기(`CLAUSE_CHECKERS`)가 위반을 `{rule, clause, path, message}` 로 낸다 |
| 위반은 던지지 않고 **전부 열거** | 동일 태도 명시 ("거부된 정의도 사유·경로와 함께 화면에 실려야 한다") |
| `appliesTo` 로 적용 범위 제한 | `Axiom.appliesTo: DefinitionKind[]` — 빈 배열 = 정의 층위 비검사 |
| 모든 공리는 원문 유래를 댄다 | `Axiom.sources` + 근거 없는 공리를 `ungroundedAxioms` 로 잡는 검사까지 |
| 반례 코퍼스 + **정상 후보 동시 통과** | `BROKEN_DEFINITIONS` 14종 거부 + `VEIL_DEFINITIONS` 능력 3·종 4 통과, "공리를 빼면 통과한다" 장면까지 |
| 다산성: 같은 공리에서 ≥2 정의, 하나뿐이면 실패 | `derivationReport` — `MIN_DERIVATIONS=2`, `barren`(불모)·`monotone`(하나뿐) 판정. 실패 문구가 A부의 논리 그대로다: "공리가 아니라 그 정의를 다른 말로 적은 것이다" |

공리 개수도 수렴했다 — A부 표 8개 후보와 구현 8조항이 1:1 로 같은 문장을 가리킨다
(`will-from-life`↔`psychic-life`, `no-uncaused`↔`caused-persistence` 등 이름만 다르다).
원문만 성실히 읽으면 같은 공리 집합이 나온다는 것 자체가 O0-a 의 방법(원문 대조)이
옳았다는 방증이다.

### B2. 구현이 더 나았던 것

**① 공리는 새 타입이 아니라 O1 `Rule` 의 확장이다.**
A부는 `Axiom` 을 독립 인터페이스로 세웠다. 구현은 "공리 = 근거가 자기 자신인 규칙"
(`Rule.axiomId === null` 인 자리)로 정의해, 세계의 **모든** 규칙이 여덟 공리로 거슬러
올라가는 단일 사슬을 만들었다. 검사할 정의(능력·종)도 `Rule` 확장이라 O1 검사기를
그대로 재사용한다. 존재론(O1)을 먼저 세운 보람이 여기서 나온다 — A부처럼 독립 타입으로
가면 "공리 계층 ↔ 규칙 계층" 을 잇는 다리를 따로 만들어야 했다.

**② 원문 대조표(reconciliation)가 값이다.**
A부는 `sourceRef` 한 줄 + "비공리 명단"으로 끝냈다. 구현은 원문이 **세 곳에 다르게 적은**
최상위 제약 16문장 전부를 `AXIOM_RECONCILIATION` 으로 해소한다 — 문장마다
같음(same)·합침(merged)·재서술(restated)과 사유가 적히고, `axiomSetReport` 가
미해소 문장·근거 없는 공리·없는 조항으로 보낸 문장을 기계 검사한다.
"원문에 있는데 공리에 없다"가 재발할 수 없는 구조다.

**③ 강제 지점 + 프로브 — A부가 놓친 가장 큰 것.**
A부는 "관문은 하나의 함수, 이후 계층이 재사용"이라고 **선언**만 했다. 구현은 선언이
거짓말이 되는 것을 막는 장치를 세웠다: 공리마다 `enforcedBy`(어느 관문이 막는가)를 적고,
O0-c 프로브가 **위반 값을 실제로 그 관문에 넣어** 거부가 나오는지 실행 확인한다.
정의 층위에서 검사할 수 없는 공리(관측·안정도)는 A부처럼 `-` 로 넘기지 않고
`deferredTo`(R3·W2 — 갚을 모듈)로 남긴다. "아무도 지키지 않고 갚을 곳도 없는 공리"는
`unenforced` 로 실패다. 공리 모듈의 진짜 난점은 판정 로직이 아니라
**공리가 장식이 되는 것**인데, 구현은 그것을 정면으로 검사한다.

**④ "검증 가능한 비용"의 직역 — 비용이 깎을 자리가 세계에 실재해야 한다.**
A부의 `cost` 검사는 `costs: []` 여부까지였다. 구현은 한 겹 더 들어간다:
비용이 깎는 자리(`CostSpec.domain/path`)와 흔적이 적힐 자리(`TraceSpec`)가
O2 상태 스키마에 **실재**하는지 본다 (`unverifiable-cost` — "세계에 없는 자리를 깎는
대가는 확인할 방법이 없다"). 공리 문장의 "검증 가능한"이 스키마 조회로 구현된 것이다.
O2 를 O0 보다 먼저 세운 위상 순서(O1→O2→O0)가 이것을 가능하게 했다 —
A부는 O0 을 먼저 놓아 이 검사를 표현할 수단이 없었다.

**⑤ 막힌 정의는 도출로 세지 않는다.**
다산성 집계 전에 관문(O0-b)을 먼저 지난다 — 공리를 어긴 정의가 "이 공리에서 나왔다"로
세계를 넓힌 척하는 구멍을 막는다. A부 다산성 설계에는 이 전제가 없었다.

### B3. 설계가 더 나았던 것 (이슈 후보 — 여기서 결론내리지 않는다)

**㉠ 다산성이 개수만 세고 "충족 방식의 다름"은 보지 않는다.**
구현의 `diverse` 는 distinct 정의 ID ≥ 2 다. 두 정의가 같은 공리를 **사실상 같은
방식으로** 충족해도(예: 비용이 둘 다 같은 자리를 깎는 사본 능력) monotone 을 지난다.
A부는 `DerivationRecord.satisfies[].how`(어떻게 충족했는가)를 값으로 남기고 그것의
diff 를 요구했다 — "같은 공리, 다른 충족"이 개수가 아니라 내용으로 검증된다.
Lab 의 "같은 공리에서 유래가 다른 두 신" 장면이 눈으로는 이것을 보이지만,
기계 판정은 개수뿐이다. → STATE.md 열린 이슈 표 후보.

**㉡ 공리 × 후보 매트릭스 화면.**
구현 Lab 은 대조표·강제 지점·판정 데모를 절로 나눠 보인다. A부의 매트릭스(행=공리,
열=후보, 칸=○/✕/-, ✕ 클릭=사유)는 "어느 공리가 무엇을 거르고 어느 칸이 비검사인가"를
한 장에 보인다 — 특히 `appliesTo` 밖(`-`)과 통과(`○`)가 구분되어, 비검사를 통과로
착각하는 일을 막는다. 강제 지점 열을 덧붙이면 구현의 ②③ 정보도 같은 표에 실린다.
Lab 개선 아이디어로만 남긴다.

### B4. 한 줄 요약

뼈대(관문 술어·appliesTo·반례+정상·다산성 하한)는 원문에서 유일하게 결정될 만큼
원문이 강했고, 구현의 우위는 전부 **앞 계층의 재사용**(O1 Rule 확장 · O2 자리 실재 검사)과
**자기 의심 장치**(대조표 · 프로브 · deferredTo)에서 나왔다. 설계가 남긴 것은
다산성의 질적 판정(㉠) 하나다.
